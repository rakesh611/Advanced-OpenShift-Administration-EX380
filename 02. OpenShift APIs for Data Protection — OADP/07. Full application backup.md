# Full Application Backup in OpenShift APIs for Data Protection — OADP

**Audience:** Advanced OpenShift Administrator / Platform Engineer with 10+ years experience  
**Scope:** Red Hat OpenShift Container Platform application backup using OADP / Velero  
**Focus:** Full application-level backup, not etcd backup or full OpenShift cluster disaster recovery

---

## 1. What “Full Application Backup” Means in OADP

A **full application backup** in OADP means backing up everything required to recover an application workload to a usable state. It normally includes:

- Namespace-scoped Kubernetes resources
- Application controller objects such as `Deployment`, `StatefulSet`, `DaemonSet`, `Job`, `CronJob`
- Services, Routes, Ingress objects, ConfigMaps, Secrets, ServiceAccounts
- RBAC objects required by the application
- PersistentVolumeClaim data
- PersistentVolume metadata where applicable
- Internal image references or ImageStreams where applicable
- Application custom resources, if the application is managed by an Operator
- Optional related cluster-scoped resources such as `StorageClass`, `ClusterRole`, `ClusterRoleBinding`, CRDs, SCCs, and webhooks, depending on restore design

In OpenShift administration, “full application backup” must not be confused with **full cluster backup**. OADP is used to protect applications and application-related resources. It is not a replacement for:

- `etcd` backup
- control plane disaster recovery
- full cluster rebuild automation
- Operator lifecycle backup
- machine configuration backup
- infrastructure-as-code backup

For cluster-level disaster recovery, you still need OpenShift control plane backup, GitOps/IaC, registry backup strategy, cluster installation assets, and platform-level documentation.

## 2. OADP Architecture Recap for Full Application Backup

OADP installs and manages Velero on OpenShift. Velero performs Kubernetes API discovery, resource backup, restore orchestration, and persistent volume backup integration.

### 2.1 Main Components

```text
User / Admin
   |
   | oc apply Backup / Schedule / Restore CR
   v
openshift-adp namespace
   |
   |-- OADP Operator
   |-- DataProtectionApplication CR
   |-- Velero Deployment
   |-- Velero plugins
   |-- Node Agent DaemonSet, for File System Backup when enabled
   |
   +--> BackupStorageLocation  ---> Object Storage: S3 / ODF MCG / Azure / GCP / MinIO
   |
   +--> VolumeSnapshotLocation ---> Cloud snapshot API or storage provider snapshot API
   |
   +--> CSI snapshot objects ---> VolumeSnapshot / VolumeSnapshotContent / VolumeSnapshotClass
```

### 2.2 Important OADP APIs

| API | Purpose |
|---|---|
| `DataProtectionApplication` | Main OADP configuration object. Deploys Velero, plugins, backup locations, snapshot locations, and node agent. |
| `BackupStorageLocation` | Defines where Velero stores Kubernetes metadata backups and File System Backup data. |
| `VolumeSnapshotLocation` | Defines where volume snapshots are stored for native cloud/provider snapshots. |
| `Backup` | One-time backup request. |
| `Schedule` | Recurring backup request using cron syntax. |
| `Restore` | Restore request from a backup. |

## 3. What Gets Backed Up in a Full Application Backup

A complete application backup normally has two major parts:

### 3.1 Kubernetes Resource Metadata

These are stored in object storage through `BackupStorageLocation`:

- Namespace object
- Workload definitions
- Services and Routes
- ConfigMaps and Secrets
- RBAC bindings
- PVC definitions
- Application CRs
- NetworkPolicies
- HorizontalPodAutoscalers
- PodDisruptionBudgets
- ServiceMonitors, PrometheusRules, or monitoring CRs if used
- BuildConfigs, ImageStreams, DeploymentConfigs in OpenShift workloads
- Operator-owned custom resources if included

### 3.2 Persistent Volume Data

PV data can be backed up using one of these approaches:

| Method | Best For | Notes |
|---|---|---|
| CSI VolumeSnapshot | Block/file storage with CSI snapshot support | Fast and crash-consistent; storage-provider dependent. |
| Cloud native snapshot | AWS EBS, Azure Disk, GCP PD, etc. | Requires correct provider plugin and `VolumeSnapshotLocation`. |
| File System Backup, Kopia or Restic | NFS, local PV, unsupported snapshot storage, generic volumes | Backs up files from mounted volume to object storage; usually slower but portable. |
| CSI snapshot data movement | Snapshot data copied to object storage or another location | Useful when local snapshots are not enough for DR. |

A senior administrator should choose the method based on RPO, RTO, storage class capability, consistency requirement, portability, and failure domain.

## 4. Full Application Backup Is Not Always “Include Everything”

Blindly backing up every object in a namespace is not always correct. Some resources are generated, temporary, or unsafe to restore into another cluster.

### 4.1 Usually Include

```text
Namespace
Deployments / StatefulSets / DaemonSets
Services
Routes / Ingresses
ConfigMaps
Secrets
ServiceAccounts
Roles / RoleBindings
PVCs
NetworkPolicies
HPAs
PDBs
Application CRs
ImageStreams / BuildConfigs if OpenShift-native CI/CD is used
```

### 4.2 Usually Exclude or Review Carefully

```text
Pods
ReplicaSets
Endpoints
EndpointSlices
Events
ControllerRevisions
Lease objects
Temporary Jobs
Completed Pods
Generated tokens
Cluster-scoped operator resources
OLM resources unless explicitly planned
Node-specific resources
MachineConfig / MachineConfigPool
```

Velero can filter by namespace, resource type, label selector, and annotations.

## 5. Full Application Backup Design Checklist

Before creating a backup, answer these questions.

### 5.1 Application Scope

```bash
APP_NS=myapp-prod
oc get all -n ${APP_NS}
oc get pvc -n ${APP_NS}
oc get route,ingress -n ${APP_NS}
oc get configmap,secret -n ${APP_NS}
oc get role,rolebinding -n ${APP_NS}
oc get networkpolicy -n ${APP_NS}
oc api-resources --namespaced=true | grep -i <app-or-operator-kind>
```

### 5.2 Storage Scope

```bash
oc get pvc -n ${APP_NS} -o wide
oc get pv
oc get storageclass
oc get volumesnapshotclass
oc get volumesnapshot -A
```

Check:

- Which PVCs are attached to the application?
- Which StorageClass is used?
- Does the CSI driver support snapshots?
- Are snapshots stored outside the cluster failure domain?
- Do you need File System Backup instead?
- Are there database workloads that need pre/post hooks?

### 5.3 Application Consistency

For stateless applications, resource backup might be enough. For stateful applications, decide whether backup is:

| Consistency Level | Meaning | Example |
|---|---|---|
| Crash-consistent | Similar to power failure recovery | Snapshot without DB quiesce |
| Application-consistent | Application flushes or freezes writes before backup | PostgreSQL checkpoint, MySQL flush, MongoDB lock, app maintenance mode |
| Logical backup | Database dump exported as file/object before OADP backup | `pg_dump`, `mysqldump`, app export |

A full application backup is not automatically application-consistent. You must design hooks or application-native backup steps for databases.

## 7. Example DataProtectionApplication for S3-Compatible Backup with File System Backup

This is a generic example for S3-compatible storage such as ODF MCG, Ceph RGW, or MinIO. Adjust provider, endpoint, bucket, region, CA, and credentials according to your environment.

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-s3
  namespace: openshift-adp
spec:
  backupLocations:
    - name: default
      velero:
        provider: aws
        default: true
        objectStorage:
          bucket: oadp-backups
          prefix: prod-cluster
        credential:
          name: cloud-credentials
          key: cloud
        config:
          region: us-east-1
          s3ForcePathStyle: "true"
          s3Url: "https://s3.example.com"
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
    nodeAgent:
      enable: true
      uploaderType: kopia
```

Apply and validate:

```bash
oc apply -f dpa-s3.yaml
oc get dpa -n openshift-adp
oc get pods -n openshift-adp
oc get backupstoragelocation -n openshift-adp
```

## 8. Backup CR for Full Namespace Application Backup

This is the most common full application backup pattern: include one complete application namespace and its PVC data.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-prod-full-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - myapp-prod
  storageLocation: default
  ttl: 720h0m0s
  defaultVolumesToFsBackup: true
```

Apply:

```bash
oc apply -f backup-myapp-prod-full.yaml
```

Watch status:

```bash
oc get backup -n openshift-adp
oc describe backup myapp-prod-full-001 -n openshift-adp
velero backup describe myapp-prod-full-001 --details
velero backup logs myapp-prod-full-001
```

`defaultVolumesToFsBackup: true` tells Velero to use File System Backup for pod volumes by default. Use it when your storage does not support snapshots or when you intentionally want filesystem-level backup to object storage.

## 9. Backup CR for Snapshot-Based Full Application Backup

When the storage class supports CSI snapshots and you want snapshot-based backup, use a Backup CR without forcing all volumes to File System Backup.

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-prod-csi-snapshot-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - myapp-prod
  storageLocation: default
  ttl: 720h0m0s
  snapshotVolumes: true
```

Validate snapshot objects:

```bash
oc get volumesnapshot -A
oc get volumesnapshotcontent
velero backup describe myapp-prod-csi-snapshot-001 --details
```

Snapshot-based backups are usually faster than File System Backup, but the snapshot must be recoverable in the expected disaster scenario. A snapshot stored only inside the same storage system might not protect you from storage-system failure.

## 10. Application-Consistent Backup Using Hooks

For databases, a full application backup should include pre/post backup hooks.

### 10.1 PostgreSQL Example Concept

A common strategy:

1. Run `CHECKPOINT` or application-specific freeze/flush command.
2. Take snapshot or file backup.
3. Resume writes if they were paused.

Example pod annotations:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: myapp-prod
spec:
  template:
    metadata:
      annotations:
        pre.hook.backup.velero.io/container: postgres
        pre.hook.backup.velero.io/command: '["/bin/bash", "-c", "psql -U postgres -c CHECKPOINT"]'
        pre.hook.backup.velero.io/timeout: 60s
```

This is only an example. For production PostgreSQL, MySQL, MongoDB, Oracle, Kafka, and other platforms, use vendor-supported backup procedures. OADP protects Kubernetes resources and volume data; it does not replace database-native consistency logic.

### 10.2 Hook Failure Policy

For critical databases, configure hooks so backup fails if the consistency command fails. A backup that completes with a failed quiesce hook can be worse than no backup because it gives false confidence.

## 11. Excluding Objects from Full Application Backup

Some objects should not be backed up. Add this annotation to resources you want Velero to skip:

```yaml
metadata:
  annotations:
    velero.io/exclude-from-backup: "true"
```

Example:

```bash
oc annotate secret temp-token -n myapp-prod velero.io/exclude-from-backup=true
```

Common exclusions:

- Temporary secrets
- Completed job artifacts
- Cache-only PVCs
- Generated config
- Runtime-only objects
- Large non-critical scratch volumes

## 12. Label-Selective Full Application Backup

In shared namespaces, you might not want to back up the entire namespace. Use labels.

```bash
oc label deployment frontend -n myapp-prod app.kubernetes.io/part-of=myapp
oc label deployment backend -n myapp-prod app.kubernetes.io/part-of=myapp
oc label statefulset postgres -n myapp-prod app.kubernetes.io/part-of=myapp
oc label service frontend -n myapp-prod app.kubernetes.io/part-of=myapp
```

Backup CR:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-prod-label-full-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - myapp-prod
  labelSelector:
    matchLabels:
      app.kubernetes.io/part-of: myapp
  storageLocation: default
  ttl: 720h0m0s
```

Be careful: label-selective backups can miss dependent resources if labels are inconsistent. For production, enforce labels through GitOps policies, Kyverno, Gatekeeper, or CI checks.

## 13. Including Cluster-Scoped Resources

Namespace backup alone may not include all dependencies. Some applications require cluster-scoped objects:

- `ClusterRole`
- `ClusterRoleBinding`
- `CustomResourceDefinition`
- `StorageClass`
- `SecurityContextConstraints`
- `MutatingWebhookConfiguration`
- `ValidatingWebhookConfiguration`
- `PriorityClass`
- `RuntimeClass`

Example:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: myapp-prod-with-cluster-resources-001
  namespace: openshift-adp
spec:
  includedNamespaces:
    - myapp-prod
  includeClusterResources: true
  storageLocation: default
  ttl: 720h0m0s
```

Use this carefully. Restoring cluster-scoped resources into another cluster can break platform policies, overwrite newer definitions, or conflict with existing Operators.

Senior admin recommendation:

- Keep platform resources in GitOps/IaC.
- Use OADP for application state and application-owned Kubernetes objects.
- Restore CRDs and Operators through their supported installation method.
- Restore application CR instances after the CRD and controller are available.

## 14. Scheduled Full Application Backup

A one-time backup is not enough for production. Use `Schedule` CRs.

Example: daily backup at 01:30.

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: myapp-prod-daily-full
  namespace: openshift-adp
spec:
  schedule: "30 1 * * *"
  template:
    includedNamespaces:
      - myapp-prod
    storageLocation: default
    ttl: 168h0m0s
    defaultVolumesToFsBackup: true
```

Apply:

```bash
oc apply -f schedule-myapp-prod-daily.yaml
oc get schedule -n openshift-adp
velero schedule get
```

Important scheduling rules:

- Backup frequency must be longer than backup duration.
- Do not schedule every 5 minutes if backup takes 20 minutes.
- Avoid backup storms across many namespaces at the same time.
- Spread schedules by application criticality.
- Align with database maintenance windows.
- Monitor object storage growth and TTL cleanup.

## 15. Verification After Backup

A full application backup is not successful just because the CR says `Completed`. Validate all layers.

### 15.1 Backup Object

```bash
oc get backup -n openshift-adp
oc get backup myapp-prod-full-001 -n openshift-adp -o yaml
oc describe backup myapp-prod-full-001 -n openshift-adp
```

Check:

```text
status.phase: Completed
status.errors: 0 preferred
status.warnings: reviewed and understood
progress.itemsBackedUp equals expected item count
expiration timestamp matches TTL policy
```

### 15.2 Velero Details

```bash
velero backup describe myapp-prod-full-001 --details
velero backup logs myapp-prod-full-001
```

Look for:

- Skipped resources
- Hook failures
- PVC backup method
- Snapshot IDs
- PodVolumeBackup objects
- Warnings about CRDs or API discovery

### 15.3 File System Backup Objects

```bash
oc get podvolumebackup -n openshift-adp
oc describe podvolumebackup -n openshift-adp
```

### 15.4 Snapshot Objects

```bash
oc get volumesnapshot -A
oc get volumesnapshotcontent
```

### 15.5 Object Storage

Validate that the backup exists in your object storage bucket:

```text
/backups/<backup-name>/
/restic/ or /kopia/ repository data, if File System Backup is used
```

## 16. Restore Test Is Mandatory

A backup that has never been restored is only a hope. Perform regular restore tests.

### 16.1 Restore into a Test Namespace

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: myapp-prod-full-001-restore-test
  namespace: openshift-adp
spec:
  backupName: myapp-prod-full-001
  namespaceMapping:
    myapp-prod: myapp-restore-test
```

Apply:

```bash
oc apply -f restore-test.yaml
oc get restore -n openshift-adp
oc describe restore myapp-prod-full-001-restore-test -n openshift-adp
```

Validate:

```bash
oc get all -n myapp-restore-test
oc get pvc -n myapp-restore-test
oc get route -n myapp-restore-test
oc logs -n myapp-restore-test deploy/<deployment-name>
```

Application-level validation:

```bash
curl -k https://<restored-route>
# login test
# transaction test
# database row count check
# API health endpoint
# smoke test
```

## 17. Full Application Backup Workflow for Production

```text
1. Identify application namespace and dependencies.
2. Classify workload as stateless or stateful.
3. Check PVCs, StorageClass, and snapshot capability.
4. Decide backup method: CSI snapshot, provider snapshot, FSB, or data mover.
5. Configure DPA and verify BSL/VSL readiness.
6. Add backup hooks for application consistency.
7. Exclude temporary or unsafe resources.
8. Create one-time Backup CR.
9. Review backup details, logs, warnings, snapshots, and PodVolumeBackups.
10. Restore into test namespace or test cluster.
11. Run application smoke test and data validation.
12. Convert to Schedule CR.
13. Monitor success, duration, repository health, and storage growth.
14. Document RPO, RTO, restore steps, and ownership.
```

## 18. Troubleshooting Full Application Backup

### 18.1 Backup Stuck in New or InProgress

Check Velero pod:

```bash
oc get pods -n openshift-adp
oc logs deploy/velero -n openshift-adp
oc describe backup <backup-name> -n openshift-adp
```

Possible causes:

- Velero cannot reach object storage
- API discovery issues
- Plugin crash
- Large number of resources
- CRD API unavailable
- Node Agent not running
- Snapshot API timeout

### 18.2 BackupStorageLocation Unavailable

```bash
oc describe backupstoragelocation default -n openshift-adp
oc logs deploy/velero -n openshift-adp
```

Common causes:

- Wrong bucket name
- Wrong access key or secret key
- Wrong S3 endpoint
- Missing `s3ForcePathStyle` for S3-compatible storage
- Proxy issue
- DNS issue
- CA trust issue
- Firewall or egress network policy issue

### 18.3 PVC Data Not Backed Up

Check backup details:

```bash
velero backup describe <backup-name> --details
oc get podvolumebackup -n openshift-adp
oc get volumesnapshot -A
```

Possible causes:

- No pod mounting the PVC when File System Backup is used
- Node Agent not enabled
- Incorrect `defaultVolumesToFsBackup`
- CSI snapshot class missing
- StorageClass does not support snapshots
- PVC uses unsupported volume type
- Volume excluded by annotation

### 18.4 Backup Completed with Warnings

Never ignore warnings in production.

```bash
velero backup logs <backup-name> | grep -i warning
velero backup describe <backup-name> --details
```

Typical warnings:

- Some resources skipped
- API group unavailable
- CRD not found
- Hook command failed
- Snapshot partially failed
- File System Backup skipped a volume

### 18.5 Restore Fails Due to Existing Resources

Restore into clean namespace when possible. If restoring into an existing namespace, define whether the restore should skip, update, or conflict with existing objects.

Recommended approach:

```text
Production DR: restore into clean rebuilt cluster or clean namespace.
Partial recovery: restore selected resources carefully.
Migration: use namespace mapping and review cluster-scoped dependencies.
```

## 19. Security Considerations

A full application backup can contain sensitive data.

### 19.1 Secrets

OADP backs up Kubernetes Secrets if they are in scope. Treat object storage as sensitive.

Controls:

- Bucket encryption
- KMS-managed keys
- Least privilege IAM policy
- Private endpoints
- TLS validation
- Object lock or immutability if required
- Separate buckets per environment
- Access audit logging

### 19.2 RBAC

Only trusted platform backup administrators should create cluster-wide backups.

Use separate roles for:

- OADP installation
- Backup creation
- Restore approval
- Backup inspection
- Object storage administration

### 19.3 Cross-Cluster Restore Risk

Restoring Secrets, Routes, OAuth clients, certificates, and webhooks into another cluster can cause conflicts or security exposure.

Before cross-cluster restore:

- Rotate credentials if required
- Review TLS certificates
- Review Route hostnames
- Review image pull secrets
- Review service account tokens
- Review external DNS and load balancer configuration

## 20. Performance and Scale Considerations

Large production backups need tuning.

### 20.1 Factors That Increase Backup Time

- Large PVCs
- Many small files
- Slow object storage
- Cross-region object storage latency
- Too many Kubernetes objects
- Slow API server response
- Node Agent CPU/memory limits
- Storage snapshot latency
- Database write load during backup

### 20.2 Good Practices

- Prefer CSI snapshots for large block volumes when supported.
- Use File System Backup for unsupported storage or portability requirements.
- Separate cache PVCs from critical data PVCs.
- Avoid backing up generated or temporary data.
- Stagger backup schedules.
- Monitor backup duration and object storage growth.
- Test restores after every major application or platform change.

## 22. Recommended Enterprise Backup Strategy

For a production OpenShift environment, use layered protection:

| Layer | Tooling | Purpose |
|---|---|---|
| Cluster control plane | OpenShift etcd backup | Recover control plane state. |
| Application manifests | GitOps, Helm, Kustomize | Recreate desired application definitions. |
| Application runtime state | OADP Backup / Schedule | Recover Kubernetes objects and PV data. |
| Database logical backup | DB-native tools | Application-consistent recovery. |
| Container images | Registry backup / mirror | Ensure image availability. |
| External dependencies | IaC / CMDB / docs | DNS, certificates, IAM, storage, firewall, secrets manager. |

OADP is one layer, not the entire disaster recovery strategy.

## 23. Interview-Level Explanation

If asked “How do you perform a full application backup with OADP?” answer like this:

> I first define the application boundary: namespace, PVCs, Routes, Secrets, ConfigMaps, RBAC, CRs, and any cluster-scoped dependencies. I verify OADP is installed, the DPA is Ready, BackupStorageLocation is Available, and snapshot or File System Backup is configured correctly. For stateful workloads, I design application-consistent hooks or DB-native backup steps. Then I create a Velero Backup CR scoped to the application namespace, optionally including cluster resources if required, and choose CSI snapshot or File System Backup for PVC data. After the backup completes, I review Velero logs, warnings, snapshot or PodVolumeBackup objects, and object storage. Finally, I perform a restore test into a separate namespace or test cluster and validate the application with smoke tests. In production, I convert the design into a Schedule CR, monitor backup health, and document RPO/RTO.

## 24. Practical Production Example

### 24.1 Variables

```bash
export APP_NS=myapp-prod
export BACKUP_NAME=myapp-prod-full-$(date +%Y%m%d-%H%M)
```

### 24.2 Precheck

```bash

oc get backupstoragelocation -n openshift-adp
oc get pods -n openshift-adp
oc get pvc -n ${APP_NS}

```

```bash
cat <<'BACKUPYAML' | oc apply -f -

  name: ${BACKUP_NAME}

    - ${APP_NS}
```

## 25. Common Mistakes by Administrators

1. Thinking OADP is a full OpenShift cluster backup tool.
2. Not testing restore.
3. Ignoring backup warnings.
4. Backing up PVC metadata but not actual PV data.
5. Not checking `BackupStorageLocation` status.
6. Using File System Backup for very large high-change databases without consistency planning.
7. Assuming storage snapshots are available in another cluster or region.
8. Restoring Operator CRs before installing the Operator/CRD.
9. Including cluster-scoped resources without reviewing conflicts.
10. Keeping backup object storage credentials too broad.
11. Not monitoring schedule failures.
12. Forgetting that Secrets are included and must be protected.
13. Not documenting exact restore sequence.

---

## 26. Best Practices Summary

- Define the application boundary clearly.
- Prefer namespace-scoped backups for applications.
- Include cluster-scoped resources only when required and reviewed.
- Use CSI snapshots for supported storage and fast recovery.
- Use File System Backup for unsupported volumes or portability.
- Use application hooks or DB-native backup for consistency.
- Verify backup logs, warnings, snapshots, and object storage.
- Perform regular restore tests.
- Use Schedule CRs for recurring backups.
- Protect backup storage with encryption, IAM, private networking, and audit logging.
- Maintain restore runbooks for every critical application.
- Combine OADP with GitOps, etcd backup, registry backup, and database-native backup.

## 28. Final Senior Admin Note

A full application backup is successful only when all three conditions are true:

```text
1. The Kubernetes resources are backed up.
2. The persistent data is backed up consistently.
3. The application is successfully restored and validated.
```

Without restore validation, backup status alone is not enough for production confidence.
