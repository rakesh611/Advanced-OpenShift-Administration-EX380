## 1. Big Picture

OADP is Red Hat's OpenShift-supported data protection framework built around **Velero**. OADP protects application resources such as:

- Namespaces
- Deployments, StatefulSets, DaemonSets, Jobs, CronJobs
- Services, Routes, ConfigMaps, Secrets
- PersistentVolumeClaims and volume data
- OpenShift-specific resources
- Internal images, depending on configuration

For persistent volume data, OADP can use multiple strategies:

1. **CSI snapshots** — storage backend snapshot through CSI VolumeSnapshot APIs.
2. **OADP Data Mover** — snapshot first, then move snapshot data to object storage.
3. **File System Backup (FSB)** — read mounted pod volume files from the node filesystem and upload them to backup storage using Restic or Kopia.

**Restic** and **Kopia** are not OpenShift storage classes. They are backup uploaders/repository engines used by Velero/OADP to copy file-level data to an object store.

In modern OADP design, **Kopia is the strategic uploader**. Restic remains important for legacy understanding and upgrade scenarios, but it is deprecated in OADP 1.5.

## 2. Where Restic and Kopia Fit in OADP

Think of OADP as three layers:

```text
+-------------------------------------------------------------+
|                    OpenShift Application                    |
|  Pods, PVCs, Deployments, StatefulSets, Services, Routes     |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                         OADP / Velero                       |
|  Backup CR, Restore CR, Schedule CR, BSL, VSL, hooks         |
+-------------------------------------------------------------+
                              |
         +--------------------+--------------------+
         |                                         |
         v                                         v
+-----------------------+             +------------------------+
| CSI Snapshot /        |             | File System Backup     |
| CSI Data Mover        |             | Restic / Kopia         |
+-----------------------+             +------------------------+
         |                                         |
         v                                         v
+-----------------------+             +------------------------+
| Storage snapshot API  |             | Object storage repo    |
| or DataUpload object  |             | S3 / MCG / Azure / GCS |
+-----------------------+             +------------------------+
```

Restic/Kopia are used in the **File System Backup** path. Kopia is also used by the **built-in Data Mover** as the uploader mechanism.

## 3. What Problem Restic and Kopia Solve

CSI snapshots are fast and usually storage-native, but they require snapshot support from the storage provider. Many environments do not have usable snapshots:

- NFS-backed persistent volumes
- Some RWX storage backends
- Legacy storage provisioners
- Local PVs
- Certain external storage systems without CSI snapshot support
- Cross-cloud or cross-region migration where native snapshots cannot move directly
- Disaster recovery design that requires data outside the primary cluster/storage backend

Restic/Kopia solve this by reading the volume files from the worker node and storing them in an object storage repository.

### Simple definition

```text
Restic/Kopia = file-level volume backup engines used by Velero/OADP when snapshots are unavailable, unsuitable, or when file-level backup is explicitly selected.
```

## 5. Restic Concept

Restic is an open-source backup program that provides:

- Deduplicated backups
- Encrypted repositories
- Snapshot-based backup history
- Object storage support through repository backends
- Incremental backup behavior at repository level

In Velero/OADP, Restic was historically used to back up Kubernetes pod volumes at the file level. It works by scanning files in a mounted volume, chunking/deduplicating data, encrypting it, and uploading repository objects to the configured backend.

### Restic in OADP terms

```text
Pod volume -> nodeAgent/restic process -> Restic repository -> object storage
```

### Why Restic existed in OADP

Restic was used because Kubernetes backup needed a storage-independent way to protect persistent data. It allowed OADP to protect volumes even when the storage provider had no snapshot API.

### Restic operational characteristics

- Works at file level.
- Does not depend on CSI snapshot capability.
- Reads from live mounted pod volumes.
- Needs node-level access to pod volume paths.
- Can be slower for large databases or millions of small files.
- Is sensitive to permissions, security context, and filesystem layout.
- Is now considered legacy for OADP design.

### Restic lifecycle status

In OADP 1.5, Restic is deprecated. The older `configuration.restic` DPA field is also deprecated. For current environments, use `spec.configuration.nodeAgent.uploaderType` and prefer `kopia`.

---

## 6. Kopia Concept

Kopia is a modern backup repository engine and uploader used by Velero/OADP for file system backup and data movement.

Kopia provides:

- Content-addressed storage
- Deduplication
- Encryption
- Repository snapshots
- Object storage repository support
- Efficient backup and restore primitives
- Library integration suitable for Velero internals

In Velero, Kopia is integrated into the codebase as a generic file-system uploader and as a repository backend. Velero uses Kopia modules internally rather than simply shelling out like a traditional external command in all cases.

### Kopia in OADP terms

```text
Pod volume -> nodeAgent/data mover pod -> Kopia uploader -> Kopia repository -> object storage
```

### Why Kopia is preferred

Kopia is the strategic direction because it integrates well with Velero's newer **Unified Repository** model and with CSI snapshot data movement.

In OADP:

- Kopia can be used for File System Backup.
- Built-in Data Mover requires Kopia.
- Restic is deprecated in OADP 1.5.

---

## 7. Restic vs Kopia

| Area | Restic | Kopia |
|---|---|---|
| OADP status | Legacy / deprecated in OADP 1.5 | Preferred / strategic uploader |
| File System Backup | Supported in supported legacy paths | Supported |
| Built-in Data Mover | Not used | Required/default uploader mechanism |
| Repository model | Restic repository | Kopia repository / Unified Repository integration |
| Operational future | Avoid for new deployment where possible | Use for new deployment |
| Typical use case | Legacy OADP clusters, migration support | Current FSB and Data Mover designs |
| DPA config | `nodeAgent.uploaderType: restic` in newer syntax | `nodeAgent.uploaderType: kopia` |
| Old DPA field | `configuration.restic` existed historically | Use `configuration.nodeAgent` |
| Troubleshooting objects | BackupRepository, PodVolumeBackup, PodVolumeRestore | Same, plus DataUpload/DataDownload for Data Mover |

### Senior admin recommendation

For a fresh OADP deployment, choose **Kopia** unless Red Hat support or a strict legacy compatibility requirement tells you otherwise.

## 9. OADP Architecture with File System Backup

### High-level architecture

```text
+-----------------------+      +-----------------------------+
| Backup CR             | ---> | Velero server               |
| defaultVolumesToFs... |      | openshift-adp namespace     |
+-----------------------+      +-----------------------------+
                                           |
                                           v
                              +-----------------------------+
                              | BackupRepository CR         |
                              | one repo per namespace      |
                              +-----------------------------+
                                           |
                                           v
+-----------------------+      +-----------------------------+      +------------------+
| Worker node           | ---> | nodeAgent DaemonSet         | ---> | Data mover pod   |
| /var/lib/kubelet/pods |      | PVB/PVR controller          |      | Kopia/Restic     |
+-----------------------+      +-----------------------------+      +------------------+
                                                                          |
                                                                          v
                                                               +----------------------+
                                                               | Object storage / BSL |
                                                               | S3 / MCG / Azure     |
                                                               +----------------------+
```

### Main components

#### 1. Velero deployment

Runs in the OADP namespace, normally `openshift-adp`. It watches Backup, Restore, Schedule, BackupStorageLocation, and related CRs.

#### 2. nodeAgent DaemonSet

Runs on nodes and processes data movement/file-system backup operations. It needs access to pod volume mount paths on the node.

#### 3. BackupStorageLocation

Defines the object store. For Kopia/Restic, the repository is stored under this bucket/prefix.

#### 4. BackupRepository

Velero creates/manages a repository per namespace when file-system backup or data movement is used.

#### 5. PodVolumeBackup / PodVolumeRestore

These CRs represent individual volume backup and restore actions.

## 10. Backup Workflow Internals

A file-system backup is not just one backup command. It is a sequence of Kubernetes controllers and CRs.

### Step-by-step backup flow

```text
1. Admin creates Backup CR.
2. Velero scans selected namespaces/resources.
3. Velero determines which volumes require File System Backup.
4. Velero ensures BackupRepository exists for the namespace.
5. Velero creates one PodVolumeBackup per selected pod volume.
6. nodeAgent on the node where the pod is running handles the PodVolumeBackup.
7. nodeAgent/data mover pod accesses the volume path through the node filesystem.
8. Kopia or Restic scans, chunks, deduplicates, encrypts, and uploads data.
9. PodVolumeBackup becomes Completed or Failed.
10. Velero backup completes, partially fails, or fails depending on object and volume results.
```

### Important internal detail

FSB backs up **pod volumes**, not standalone PVCs. If a PVC is not mounted by a running pod, FSB cannot read it directly. The usual workaround is to create a temporary staging pod that mounts the PVC, then run the backup.

### Why this matters

When troubleshooting, do not only check the `Backup` CR. Also check:

- BackupRepository readiness
- PodVolumeBackup phase
- nodeAgent logs
- data mover pod logs
- object store connectivity
- pod scheduling and volume mount status

## 11. Restore Workflow Internals

### Step-by-step restore flow

```text
1. Admin creates Restore CR.
2. Velero restores Kubernetes objects.
3. For volumes backed up through FSB, Velero identifies matching PodVolumeBackup metadata.
4. Velero ensures BackupRepository exists and can be connected.
5. Velero adds an init container to restored pods.
6. Velero creates PodVolumeRestore CRs.
7. nodeAgent handles PodVolumeRestore on the node where the pod is scheduled.
8. Kopia/Restic downloads and restores files into the mounted pod volume path.
9. A restore marker is written under .velero in the volume.
10. Init container detects completion and allows application containers to start.
```

### Why restored pods may wait

If the init container is waiting forever, usually one of these is happening:

- PodVolumeRestore failed or is stuck.
- nodeAgent is not running on the target node.
- PVC did not bind.
- The pod cannot schedule.
- StorageClass is missing on the target cluster.
- BackupRepository cannot connect to object storage.
- Repository password mismatch.
- Security context/SCC issue blocks restore access.

## 12. BackupRepository Concept

A **BackupRepository** represents the repository used by Velero to store file-level volume backup data.

Velero typically creates one backup repository per namespace when the first FSB backup/restore or Data Mover operation targets that namespace.

Example conceptual object path:

```text
s3://my-oadp-bucket/velero/kopia/my-namespace/
```

or, for legacy Restic:

```text
s3://my-oadp-bucket/velero/restic/my-namespace/
```

### Repository password

Velero creates or uses a repository password secret. The repository password must be considered long-lived and critical.

**Important:** Set a custom repository password before the first backup if your policy requires it. If you change the repository password after a repository has already been initialized, older backups might become inaccessible.

### Useful commands

```bash
oc get backuprepositories.velero.io -n openshift-adp
oc describe backuprepository -n openshift-adp <repo-name>
velero repo get
```

If you use only `oc` and the Velero CLI is inside the Velero container:

```bash
oc -n openshift-adp exec deploy/velero -- /velero repo get
```

## 14. Data Mover and Kopia

OADP Data Mover is different from plain FSB.

### File System Backup

```text
Live mounted pod volume -> Kopia/Restic -> object storage
```

### CSI Snapshot Data Mover

```text
PVC -> CSI VolumeSnapshot -> temporary volume from snapshot -> Kopia -> object storage
```

Data Mover gives better consistency than direct FSB because the data is read from a snapshot copy, not from a constantly changing live filesystem.

### Important point

For OADP built-in Data Mover, Kopia is used as the uploader mechanism regardless of the Restic/Kopia choice for regular FSB. Therefore, if you plan to use Data Mover, you must understand Kopia operationally.

---

## 15. When to Use FSB, CSI Snapshot, or Data Mover

| Requirement | Recommended Approach | Reason |
|---|---|---|
| Storage supports CSI snapshots and restore in same cluster | CSI snapshot | Fast, storage-native, lower data movement. |
| Need off-cluster durable copy of snapshot data | CSI snapshot + Data Mover | Snapshot consistency plus object storage durability. |
| NFS/RWX volume without snapshot support | FSB with Kopia | Snapshot not available. |
| Legacy OADP with Restic only | Restic until upgraded | Compatibility. |
| Cross-cloud migration | FSB or Data Mover depending on storage support | Native snapshots often cannot move across providers. |
| Large active database | Prefer app-native backup or snapshot with quiesce | FSB reads live files and may not be application-consistent. |
| Unmounted PVC | Not direct FSB | Use CSI snapshot or staging pod. |
| hostPath volume | Not supported for FSB | Excluded/unsupported. |

### Senior design rule

Use this order of preference:

```text
1. Application-native backup for databases when consistency matters most.
2. CSI snapshot + Data Mover for durable off-cluster volume backup.
3. CSI snapshot for fast same-platform recovery.
4. FSB with Kopia when snapshots are unavailable or unsuitable.
5. Restic only for legacy compatibility.
```

## 16. Configuring Kopia in DataProtectionApplication

Example DPA using Kopia nodeAgent:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-sample
  namespace: openshift-adp
spec:
  backupLocations:
    - velero:
        provider: aws
        default: true
        objectStorage:
          bucket: my-oadp-bucket
          prefix: velero
        config:
          region: us-east-1
          s3Url: https://s3.example.com
          s3ForcePathStyle: "true"
        credential:
          name: cloud-credentials
          key: cloud
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi
      featureFlags:
        - EnableCSI
    nodeAgent:
      enable: true
      uploaderType: kopia
```

### Important fields

| Field | Purpose |
|---|---|
| `backupLocations` | Defines object storage target. |
| `configuration.velero.defaultPlugins` | Enables platform/provider plugins. |
| `configuration.velero.featureFlags` | Enables features such as CSI support where required. |
| `configuration.nodeAgent.enable` | Deploys nodeAgent DaemonSet. Required for FSB/Data Mover. |
| `configuration.nodeAgent.uploaderType` | Selects `kopia` or `restic` for FSB. |

### Verify DPA

```bash
oc get dpa -n openshift-adp
oc describe dpa dpa-sample -n openshift-adp
oc get pods -n openshift-adp
oc get ds -n openshift-adp
```

Expected components:

```text
velero deployment running
node-agent daemonset running on worker nodes
backupstoragelocation Available
```

## 17. Legacy Restic Configuration

For legacy Restic-based FSB, newer OADP configuration uses nodeAgent uploader type:

```yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-restic-legacy
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
    nodeAgent:
      enable: true
      uploaderType: restic
```

### Avoid old field in new OADP

Do not design new manifests around this older pattern:

```yaml
spec:
  configuration:
    restic:
      enable: true
```

That field is deprecated in OADP 1.5. Use:

```yaml
spec:
  configuration:
    nodeAgent:
      enable: true
      uploaderType: kopia
```

## 18. Backup CR Examples

### Example 1: Back up all pod volumes with FSB/Kopia

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: mysql-fsb-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - mysql
  storageLocation: default
  defaultVolumesToFsBackup: true
  snapshotVolumes: false
  ttl: 720h0m0s
```

Explanation:

| Field | Meaning |
|---|---|
| `includedNamespaces` | Namespace to protect. |
| `storageLocation` | BackupStorageLocation name. |
| `defaultVolumesToFsBackup: true` | Use File System Backup by default for pod volumes. |
| `snapshotVolumes: false` | Do not attempt volume snapshots. |
| `ttl` | Backup retention period. |

Apply:

```bash
oc apply -f mysql-fsb-backup.yaml
```

Watch:

```bash
oc get backup -n openshift-adp mysql-fsb-backup -w
oc describe backup -n openshift-adp mysql-fsb-backup
oc get podvolumebackups -n openshift-adp
```

---

### Example 2: Back up selected volumes only by annotation

Patch a StatefulSet pod template:

```bash
oc -n mysql patch statefulset mysql \
  --type='merge' \
  -p '{
    "spec": {
      "template": {
        "metadata": {
          "annotations": {
            "backup.velero.io/backup-volumes": "mysql-data"
          }
        }
      }
    }
  }'
```

Then create a Backup CR:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: mysql-selected-volume-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - mysql
  storageLocation: default
  snapshotVolumes: false
  ttl: 720h0m0s
```

This approach is cleaner when a pod has multiple volumes but only one volume contains application data.

---

### Example 3: Exclude specific volumes in opt-out mode

Patch pod template annotation:

```bash
oc -n app patch deployment app1 \
  --type='merge' \
  -p '{
    "spec": {
      "template": {
        "metadata": {
          "annotations": {
            "backup.velero.io/backup-volumes-excludes": "cache,tmp"
          }
        }
      }
    }
  }'
```

Backup CR:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app1-fsb-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app1
  storageLocation: default
  defaultVolumesToFsBackup: true
  snapshotVolumes: false
  ttl: 720h0m0s
```

## 19. Pod Annotation Strategy

Velero discovers volumes for FSB using one of two approaches.

### Opt-in approach

Only annotated volumes are backed up.

```bash
backup.velero.io/backup-volumes: data,logs
```

Best for:

- Stateful workloads with multiple volumes
- Avoiding caches and temporary directories
- Reducing backup size
- Avoiding accidental backup of non-critical data

### Opt-out approach

All pod volumes are backed up by default, except excluded volumes and known exceptions.

```bash
backup.velero.io/backup-volumes-excludes: cache,tmp
```

Best for:

- Simple namespaces
- Small applications
- Environments where application teams do not reliably annotate data volumes

### Senior admin warning

Do not annotate only live pods manually for long-term production. Pods are ephemeral. Annotate the controller pod template instead:

- Deployment `.spec.template.metadata.annotations`
- StatefulSet `.spec.template.metadata.annotations`
- DaemonSet `.spec.template.metadata.annotations`

## 21. Consistency and Application Quiescing

FSB reads files from a live mounted filesystem. This is the most important concept for production.

### What FSB guarantees

FSB can copy file data that exists on disk during the backup scan.

### What FSB does not automatically guarantee

FSB does not automatically guarantee application-level consistency for active applications, especially:

- Databases
- Message queues
- Applications with write-ahead logs
- Applications with memory-only state
- Applications writing many files during backup
- Applications using custom flush behavior

### Why this matters

A successful Velero backup can still produce an application-inconsistent restore if the application was writing data during backup.

### Use backup hooks

Use Velero/OADP hooks to quiesce or flush applications before FSB.

Example pre/post hook idea for a database:

```yaml
metadata:
  annotations:
    pre.hook.backup.velero.io/command: '["/bin/sh", "-c", "mysqladmin flush-tables --lock-tables"]'
    post.hook.backup.velero.io/command: '["/bin/sh", "-c", "mysqladmin unlock-tables"]'
```

This is only a conceptual example. Real database hooks must be tested carefully.

## 22. Database Backup Strategy

For databases, do not blindly rely on file-level backup.

### Better database strategy

| Database Type | Preferred Backup Pattern |
|---|---|
| PostgreSQL | `pg_dump`, `pg_basebackup`, WAL archiving, operator-native backup, or CSI snapshot with quiesce. |
| MySQL/MariaDB | Logical dump, Percona XtraBackup, operator-native backup, or quiesced snapshot. |
| MongoDB | `mongodump`, filesystem snapshot with `fsyncLock`, or operator-native backup. |
| Redis | RDB/AOF flush strategy, operator-native backup, or controlled dump. |
| Elasticsearch/OpenSearch | Snapshot API to object storage, not raw data directory copy. |
| Kafka | Topic-level replication, MirrorMaker, storage snapshot only with full broker consistency design. |

### FSB with databases

Use FSB for databases only when:

- Application is stopped during backup, or
- Pre/post hooks quiesce the database safely, or
- Database operator documents Velero/OADP FSB support, or
- You are backing up a logical dump file, not live database files.

### Senior admin rule

```text
For database data, application-consistent backup is more important than backup CR phase = Completed.
```

## 23. Security Architecture

### Repository encryption

Restic and Kopia repositories are encrypted. Object storage encryption is still useful, but it is not a replacement for repository password governance.

### Repository password governance

Protect the repository password secret:

```bash
oc get secret -n openshift-adp velero-repo-credentials -o yaml
```

Best practices:

- Set custom password before first FSB/Data Mover backup if required by security policy.
- Store password in external secret management if your organization requires it.
- Do not rotate blindly after repository creation.
- Treat repository password like a disaster recovery key.
- Include it in DR documentation securely.

### Object storage IAM

Use least privilege:

- List bucket/prefix
- Get object
- Put object
- Delete object only if backup deletion/maintenance requires it
- Avoid broad admin permissions

### TLS and custom CA

For S3-compatible storage such as MCG, MinIO, Ceph RGW, or enterprise object stores:

- Use TLS.
- Configure custom CA if self-signed/internal CA is used.
- Test Velero CLI, Velero server, and nodeAgent connectivity.

### Node-level access

nodeAgent needs access to volume paths on worker nodes. This has security implications:

- HostPath access must be allowed.
- SCC/PSA constraints must permit required behavior.
- Restrict OADP namespace admin access.
- Monitor who can create Backup/Restore CRs.

### Multi-tenant risk

In multi-tenant OpenShift, backup/restore permissions are powerful. A user who can restore Secrets or volumes into a namespace might indirectly access sensitive data. Use OADP self-service features carefully and with RBAC review.

## 24. Performance Tuning

FSB performance depends on many factors:

- Number of files
- Size of files
- Change rate
- CPU available to nodeAgent/data mover pod
- Memory available
- Object storage latency
- Network bandwidth
- Node disk I/O
- Application write activity
- Repository maintenance status
- Encryption and deduplication overhead

### Why millions of small files are slow

Small files create metadata and object operation overhead. Deduplication also needs to inspect file content. A 100 GB volume with 10 large files can be faster than a 20 GB volume with 5 million small files.

### Why databases can be slow

Large database files may change internally even when file size appears stable. The uploader must inspect and identify changed chunks.

### Practical tuning actions

1. Prefer Kopia for new deployments.
2. Prefer CSI snapshot/Data Mover for large block volumes when available.
3. Run backups outside peak I/O periods.
4. Avoid backing up cache directories.
5. Use annotations to include only real data volumes.
6. Increase resources for nodeAgent/data mover pods if supported in your OADP version.
7. Ensure object storage is close enough from a network latency perspective.
8. Use dedicated bucket/prefix for OADP.
9. Monitor object store throttling.
10. Test restore time, not only backup time.

### Backup window planning

For each application, document:

```text
RPO: acceptable data loss window
RTO: acceptable recovery time
Backup duration: observed average and p95
Restore duration: observed average and p95
Volume size: logical and changed data
Object store growth: daily/weekly/monthly
```

## 25. Storage and Object Store Design

### Object storage must be off-cluster

If your object storage is inside the same cluster and the cluster is lost, your backup may also be lost. For true disaster recovery, store backups outside the failure domain.

Common targets:

- AWS S3
- Azure Blob
- Google Cloud Storage
- Red Hat OpenShift Data Foundation Multicloud Object Gateway with external replication/design
- Ceph RGW
- S3-compatible enterprise object store

### Bucket design

Recommended pattern:

```text
bucket: company-ocp-prod-oadp
prefix: clusters/prod-01/velero
```

For multiple clusters:

```text
s3://company-oadp-backups/clusters/prod-01/
s3://company-oadp-backups/clusters/prod-02/
s3://company-oadp-backups/clusters/dr-01/
```

Avoid sharing the exact same prefix between clusters unless your design explicitly requires it and you understand restore/discovery behavior.

### Immutability

For ransomware resistance:

- Enable object lock/versioning where supported.
- Use retention policies.
- Separate backup write identity from backup delete identity.
- Regularly test restore from immutable backups.

## 26. Limitations and Edge Cases

### 1. hostPath volumes

FSB does not support backing up `hostPath` volumes.

### 2. PVC must be mounted by a pod

FSB backs up volumes attached to pods. It does not directly back up an idle PVC that is not mounted.

### 3. Live filesystem consistency

FSB reads from live volume data. It might not capture a single point-in-time application-consistent state unless the app is quiesced.

### 4. Service account token, Secret, and ConfigMap volumes

In opt-out mode, certain Kubernetes-generated volumes such as service account tokens, Secrets, and ConfigMaps are excluded because they are recreated from Kubernetes resources.

### 5. Restore scheduling matters

If restored pods cannot schedule, volume restore may not complete.

### 6. Repository password mismatch

Changing the repository password after repository initialization can break access to older backups.

### 7. StorageClass mismatch in DR cluster

A restore to a different cluster might fail or hang if the target StorageClass does not exist or behaves differently.

### 8. UID/GID and SCC differences

OpenShift namespace UID/GID ranges can differ between clusters. Restored data permissions may need careful validation.

### 9. Large files and deduplication

Even when backup data is incremental at repository level, large active files still need scanning/chunking to determine changed data.

### 10. Read-only root filesystem with Kopia

Kopia needs writable cache/config paths. If Velero or nodeAgent is forced to run with a read-only root filesystem without proper writable paths, Kopia backups can fail.

Symptoms:

- Worker `/var` partition grows during backup/restore
- Node disk pressure

- Run backup during lower activity window.

## 29. Production Best Practices

### 1. Prefer Kopia

Use Kopia for new OADP deployments.

### 2. Use off-cluster object storage

Do not store backups only inside the same cluster failure domain.

### 3. Test restore regularly

A backup that has never been restored is only an assumption.

### 4. Define workload classes

Classify apps:

```text
Class A: Critical DB, strict RPO/RTO, app-native backup + snapshot/Data Mover
Class B: Stateful app, moderate RPO/RTO, CSI snapshot/Data Mover
Class C: NFS/RWX app, FSB with Kopia
Class D: Stateless app, metadata-only backup or GitOps redeploy
```

### 5. Avoid backing up cache data

Use annotations to exclude:

- `/tmp`
- cache directories
- generated files
- log archives if shipped elsewhere

### 6. Document repository credentials

Without repository password and object store credentials, DR restore may fail.

### 7. Use backup hooks carefully

Pre/post hooks can improve consistency but can also break apps if not tested.

### 8. Separate schedules

Do not run all backups at the same time. Stagger by namespace/application criticality.

### 9. Monitor backup status

Monitor:

- Backup phase
- PartiallyFailed count
- PVB/PVR failures
- BSL phase
- repository maintenance
- object storage growth
- node disk pressure
- nodeAgent restarts

### 10. Keep OADP upgraded within support policy

Do not skip required minor upgrade paths. Validate OADP, Velero, OpenShift, and storage plugin compatibility.

## 30. Interview-Level Explanation

### Short explanation

Restic and Kopia are file-level backup engines used by OADP/Velero when storage snapshots are unavailable or not preferred. They read pod volume data from the node filesystem through nodeAgent and upload encrypted, deduplicated data to object storage. Restic is the older/legacy option; Kopia is the preferred modern uploader and is required by OADP built-in Data Mover.

### Senior explanation

In OADP, Kubernetes object metadata and persistent volume data are handled differently. Velero can back up Kubernetes resources directly from the API server, but volume data needs either a snapshot mechanism or a file-level data movement mechanism. Restic and Kopia implement the file-level mechanism. The nodeAgent DaemonSet runs on workers, accesses pod volume paths under the kubelet directory, and processes PodVolumeBackup and PodVolumeRestore CRs. During backup, Velero creates a BackupRepository per namespace and one PodVolumeBackup per selected volume. Kopia or Restic then scans and uploads deduplicated encrypted data to the BackupStorageLocation. During restore, Velero creates PodVolumeRestore objects, injects an init container into pods, and waits until data has been restored into the volumes before application containers start. In current OADP, Kopia is preferred and Restic is deprecated.

### One-line design rule

```text
Use CSI snapshot/Data Mover when available for consistency and scale; use Kopia FSB when snapshots are unavailable; avoid Restic for new designs.
```

## 31. Real-World Scenarios

### Scenario 1: NFS-backed application has no CSI snapshot support

Problem:

```text
Application uses RWX NFS PVC. VolumeSnapshotClass does not exist.
```

Solution:

```text
Use OADP FSB with Kopia.
```

Actions:

```bash
oc -n app patch deployment app \
  --type='merge' \
  -p '{"spec":{"template":{"metadata":{"annotations":{"backup.velero.io/backup-volumes":"data"}}}}}'
```

Backup:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: app-nfs-kopia-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - app
  storageLocation: default
  snapshotVolumes: false
  ttl: 720h0m0s
```

---

### Scenario 2: PostgreSQL StatefulSet on CSI block storage

Best design:

```text
Use PostgreSQL-native backup or CSI snapshot with quiesce/Data Mover.
```

Avoid relying only on raw FSB of live PostgreSQL data directory unless the database is stopped or safely quiesced.

---

### Scenario 3: Migration to another OpenShift cluster

Problem:

```text
Need to move namespace app1 from old cluster to new cluster.
```

Checks:

- OADP version compatibility
- Kubernetes/OpenShift API compatibility
- Operators installed on target cluster
- StorageClass exists on target cluster
- SCC and UID/GID behavior
- Routes/DNS differences
- Secrets and image pull secrets
- Object store reachable from target cluster

For volume data:

- Use FSB/Kopia if snapshots cannot move across providers.
- Use Data Mover if CSI snapshot data movement is supported.

---

### Scenario 4: Backup completes but restore data is corrupt

Likely cause:

```text
Backup was file-level successful but not application-consistent.
```

Fix:

- Use application-native backup.
- Add safe pre/post hooks.
- Stop app during backup window if acceptable.
- Use CSI snapshot/Data Mover for point-in-time volume image.
- Test restore at application level, not only Kubernetes object level.

---

### Scenario 5: OADP Restic cluster upgrade

Problem:

```text
Existing OADP uses Restic. New OADP deprecates Restic.
```

Plan:

1. Document current DPA and backup repository state.
2. Export current OADP resources.
3. Confirm restore requirement for old backups.
4. Deploy/upgrade OADP using supported path.
5. Use `nodeAgent.uploaderType: kopia` for new backups.
6. Retain old Restic backup repository until retention expires.
7. Perform test restore from old and new backup sets.
