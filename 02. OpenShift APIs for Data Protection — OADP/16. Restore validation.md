## 1. What Restore Validation Means

**Restore validation** is the controlled verification process that proves an OADP restore is technically complete, operationally correct, secure, reachable, and useful to the application owner.

In a production OpenShift environment, a restore is **not valid** just because the `Restore` custom resource shows `Completed`. A restore is valid only when all important layers are confirmed:

| Validation Layer | What You Validate |
|---|---|
| OADP control plane | Velero pod, node-agent/restic/kopia pods, BackupStorageLocation, VolumeSnapshotLocation, DPA health |
| Backup source | Backup exists, phase is usable, artifact exists in object storage, restore source is correct |
| Restore CR | Correct backup name, namespace mapping, included/excluded resources, PV restore setting, hooks |
| Kubernetes resources | Namespace, deployments, statefulsets, services, routes, configmaps, secrets, PVCs, RBAC |
| Storage | PVC bound, PV provisioned, snapshots restored, filesystem backup restored, data present |
| Application | Pods ready, logs clean, app endpoint reachable, login/API/database checks successful |
| Security | ServiceAccount, SCC, RoleBinding, ClusterRoleBinding, NetworkPolicy, secrets, image pulls |
| Network | Service endpoints, DNS, route/ingress, egress, NetworkPolicy, cross-namespace connectivity |
| Business validation | Data is correct, application owner confirms expected state, RPO/RTO objectives are met |

A senior administrator should treat restore validation as a **DR assurance activity**, not just a Kubernetes command check.

## 2. Why Restore Validation Is More Important Than Backup Success

A backup can succeed while the restore can still fail or produce an unusable application. Common reasons include:

- The backup completed but the target cluster lacks the required `StorageClass`.
- The restored PVC is `Bound`, but application data is missing or stale.
- The route exists but DNS or router admission is not working.
- Deployment is restored, but pods fail because SCC, secrets, image pull secrets, or ConfigMaps are wrong.
- NetworkPolicy restores correctly but blocks required traffic.
- A CR is restored before its Operator is ready.
- The restore shows `PartiallyFailed`, but teams ignore warnings/errors.
- The restore completes, but RPO is missed because the backup was too old.
- Application starts but database recovery is inconsistent.

In production DR, the real question is not:

```text
Did Velero restore the objects?
```

The real question is:

```text
Can the business workload run correctly from the restored state within the agreed RTO/RPO?
```

## 3. OADP Restore Architecture Refresher

OADP is Red Hat's OpenShift distribution/integration around Velero. It protects application namespaces, application-related resources, persistent volumes, internal images, and, when configured, virtual machine workloads.

At restore time, these components matter:

| Component | Restore Role |
|---|---|
| `DataProtectionApplication` | OADP control object that deploys/configures Velero, plugins, credentials, node-agent/restic/kopia, etc. |
| Velero deployment | Main controller that watches `Backup` and `Restore` CRs and performs restore operations |
| `Backup` CR | Source object describing what was backed up |
| `Restore` CR | Desired restore operation |
| `BackupStorageLocation` | Object storage location where backup metadata/artifacts exist |
| `VolumeSnapshotLocation` | Provider-specific snapshot location, when native snapshots are used |
| CSI snapshot objects | `VolumeSnapshot`, `VolumeSnapshotContent`, `VolumeSnapshotClass` used for CSI snapshot backup/restore |
| Node-agent / Restic / Kopia | File system backup and restore path for volume data when snapshot-based restore is not used |
| Velero plugins | OpenShift, CSI, AWS, Azure, GCP, kubevirt, and custom plugins used during backup/restore |

### 3.1 Restore Flow at High Level

A normal restore looks like this:

```text
User/Admin creates Restore CR
        |
        v
Velero RestoreController validates Restore CR
        |
        v
Velero checks source Backup CR and backup artifact
        |
        v
Velero downloads backup metadata from object storage
        |
        v
Velero sorts resources and applies restore rules
        |
        v
Velero recreates Kubernetes/OpenShift resources
        |
        v
Velero restores PV data using snapshot / CSI / Restic / Kopia / Data Mover path
        |
        v
Pods start through normal Kubernetes controllers
        |
        v
Admin validates application health, data, networking, and security
```

### 3.2 Important Restore Behavior

- Velero restores resources in a defined order so foundational resources such as CRDs, namespaces, storage resources, RBAC, secrets, configmaps, PVCs, and workloads are created in a logical sequence.
- If a resource already exists, Velero is normally non-destructive and skips the existing object unless an update policy is explicitly configured.
- PVC restore behavior depends on how the volume was backed up:
  - Native snapshot plugin
  - CSI snapshot
  - File System Backup using Restic/Kopia/node-agent
  - Data Mover
- A completed restore can still have warnings that must be reviewed.
- A partially failed restore must be treated as **not production-approved** until every error is understood and either fixed or formally accepted.

## 4. Restore Validation Lifecycle

Restore validation should be divided into phases.

```text
Phase 1: Pre-restore validation
Phase 2: Restore plan/spec validation
Phase 3: Restore execution monitoring
Phase 4: Kubernetes resource validation
Phase 5: Storage/data validation
Phase 6: Application validation
Phase 7: Security/network validation
Phase 8: Business sign-off and evidence capture
```

### 4.1 Restore Validation Mindset

For a 10+ year admin, validation should answer these questions:

1. **Can OADP read the backup?**
2. **Is the selected backup correct and recent enough?**
3. **Is the target cluster compatible?**
4. **Were all expected Kubernetes resources restored?**
5. **Were all PVCs and volume data restored?**
6. **Did controllers recreate pods successfully?**
7. **Are application endpoints reachable?**
8. **Are RBAC, SCC, secrets, routes, NetworkPolicies, quotas, and limits correct?**
9. **Did the app owner confirm business data and function?**
10. **Did restore meet RTO/RPO?**

## 5. Pre-Restore Validation

Pre-restore validation prevents bad restores. Never start a production restore blindly.

### 5.1 Validate OADP Installation

```bash
oc get ns openshift-adp
oc get pods -n openshift-adp
oc get dpa -n openshift-adp
oc describe dpa -n openshift-adp
```

Expected:

```text
Velero pod is Running
DPA status is reconciled/available
No crashlooping Velero/plugin/node-agent pods
```

Useful command:

```bash
oc get deployment -n openshift-adp
oc get daemonset -n openshift-adp
oc get events -n openshift-adp --sort-by=.lastTimestamp
```

If Velero is not healthy, restore validation is meaningless because the controller itself may not process the restore correctly.

### 5.2 Validate Velero CLI Access

In OADP, the Velero binary is available inside the Velero deployment.

```bash
alias velero='oc -n openshift-adp exec deployment/velero -c velero -- ./velero'

velero version
velero backup get
velero restore get
```

If `velero version` fails, check:

```bash
oc get pod -n openshift-adp -l deploy=velero
oc logs deployment/velero -n openshift-adp -c velero
oc describe deployment/velero -n openshift-adp
```

### 5.3 Validate BackupStorageLocation

```bash
oc get backupstoragelocation -n openshift-adp
oc describe backupstoragelocation -n openshift-adp
velero backup-location get
```

Expected:

```text
PHASE: Available
No authentication error
No bucket access error
No TLS or CA error
No object store timeout
```

If the BSL is unavailable, restore can fail because Velero cannot read backup artifacts.

### 5.4 Validate VolumeSnapshotLocation

For snapshot-based backups:

```bash
oc get volumesnapshotlocation -n openshift-adp
oc describe volumesnapshotlocation -n openshift-adp
velero snapshot-location get
```

Expected:

```text
Provider configured correctly
Region/location correct
Credentials valid
Snapshot API reachable
```

### 5.5 Validate Source Backup Exists

```bash
velero backup get
velero backup describe <backup-name> --details
```

Check:

- Backup phase is `Completed` or otherwise acceptable for your restore policy.
- Backup includes the target namespace.
- Backup includes expected resources.
- Backup includes PV data if the application is stateful.
- Backup timestamp satisfies RPO.
- Backup has no unaccepted warnings/errors.

Example:

```bash
velero backup describe app-prod-backup-20260703 --details
```

### 5.6 Validate Backup Artifact in Object Storage

From Velero perspective:

```bash
velero backup describe <backup-name> --details
velero backup logs <backup-name> | less
```

From object storage perspective, depending on provider:

```bash
# Example only: S3-compatible check
aws s3 ls s3://<bucket>/backups/<backup-name>/ --recursive
```

Expected backup artifact examples:

```text
<backup-name>-logs.gz
<backup-name>-resource-list.json.gz
<backup-name>.tar.gz
<backup-name>-volumesnapshots.json.gz
```

The exact artifact names can differ by OADP/Velero version and backup method, but the key idea is that backup metadata and resource archive must be readable.

### 5.7 Validate Target Namespace Decision

Before restore, decide one of these:

| Restore Type | Typical Use Case | Risk |
|---|---|---|
| Same namespace restore | Accidental deletion, in-place recovery | Existing resources can be skipped or conflict |
| Different namespace restore | Testing restore, blue/green validation, migration | Namespace mapping and references must be checked |
| Different cluster restore | DR, migration, cluster replacement | Storage class, routes, DNS, operators, SCC, image registry, network differences |

### 5.8 Validate Target Cluster Compatibility

Check OpenShift version:

```bash
oc version
oc get clusterversion
```

Check APIs and CRDs:

```bash
oc api-resources | grep -E 'route|deploymentconfig|volumesnapshot|securitycontextconstraints'
oc get crd | grep -i '<application-or-operator-crd>'
```

Check storage:

```bash
oc get sc
oc get volumesnapshotclass
oc get csidriver
```

Check image pull access:

```bash
oc get secret -A | grep -i pull
oc get imagecontentsourcepolicy
oc get imagedigestmirrorset
oc get imagetagmirrorset
```

Check cluster networking:

```bash
oc get ingresscontroller -n openshift-ingress-operator
oc get pods -n openshift-ingress
oc get network.operator cluster -o yaml
```

## 6. Restore Specification Validation

The `Restore` CR is the restore plan. Validate it like you would validate a production change request.

### 6.1 Basic Restore CR

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-app-prod-20260703
  namespace: openshift-adp
spec:
  backupName: app-prod-backup-20260703
  includedNamespaces:
    - app-prod
  restorePVs: true
```

Apply:

```bash
oc apply -f restore-app-prod-20260703.yaml
```

### 6.2 Restore to Different Namespace

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: restore-app-prod-to-dr
  namespace: openshift-adp
spec:
  backupName: app-prod-backup-20260703
  includedNamespaces:
    - app-prod
  namespaceMapping:
    app-prod: app-prod-dr
  restorePVs: true
```

Equivalent Velero CLI style:

```bash
velero restore create restore-app-prod-to-dr \
  --from-backup app-prod-backup-20260703 \
  --namespace-mappings app-prod:app-prod-dr \
  --restore-volumes=true
```

### 6.3 Restore Only Selected Resources

Example: restore ConfigMaps and Secrets only.

```bash
velero restore create restore-config-only \
  --from-backup app-prod-backup-20260703 \
  --include-namespaces app-prod \
  --include-resources configmaps,secrets
```

### 6.4 Restore by Label

```bash
velero restore create restore-payment-app \
  --from-backup app-prod-backup-20260703 \
  --selector app=payment
```

### 6.5 Exclude Dangerous or Unwanted Resources

For many production restores, you might exclude:

- `events`
- temporary pods/jobs
- old replicasets
- cluster-scoped resources not owned by the app
- operator-managed resources that should be recreated by the Operator

Example:

```bash
velero restore create restore-app-prod-safe \
  --from-backup app-prod-backup-20260703 \
  --include-namespaces app-prod \
  --exclude-resources events,events.events.k8s.io
```

### 6.6 Validate Restore CR Before Applying

```bash
oc apply --dry-run=server -f restore.yaml
oc explain restore.spec --api-version=velero.io/v1
```

Check these fields carefully:

| Field | Validation Question |
|---|---|
| `spec.backupName` | Is this the correct backup? |
| `includedNamespaces` | Are you restoring the correct namespace? |
| `excludedNamespaces` | Are you avoiding namespaces that must not be touched? |
| `includedResources` | Are all required objects included? |
| `excludedResources` | Are you accidentally excluding required resources? |
| `labelSelector` | Does it match all app resources? |
| `namespaceMapping` | Are old and new namespace names correct? |
| `restorePVs` | Is PV restore enabled for stateful apps? |
| `existingResourcePolicy` | Are you intentionally skipping or updating existing objects? |
| hooks | Are restore hooks safe and idempotent? |

## 7. Executing Restore Safely

### 7.1 Create Change Window Evidence

Before production restore, capture current state:

```bash
mkdir -p restore-evidence/pre

oc get ns > restore-evidence/pre/namespaces.txt
oc get pods -A > restore-evidence/pre/pods-all.txt
oc get pv,pvc -A > restore-evidence/pre/storage-all.txt
oc get route -A > restore-evidence/pre/routes-all.txt
oc get events -A --sort-by=.lastTimestamp > restore-evidence/pre/events-all.txt
velero backup get > restore-evidence/pre/velero-backups.txt
velero restore get > restore-evidence/pre/velero-restores.txt
```

### 7.2 Pause Conflicting Automation

Before restoring, consider pausing:

- GitOps sync for target namespace
- Argo CD auto-sync
- CI/CD deployments
- HPA scale changes
- Operators that may reconcile restored resources aggressively
- External automation that recreates resources
- CronJobs that may run during restore

Examples:

```bash
# Suspend CronJobs in target namespace
oc get cronjob -n app-prod -o name | xargs -r -I{} oc patch {} -n app-prod -p '{"spec":{"suspend":true}}'
```

For Argo CD, use your organization-approved method to disable auto-sync or place the app in a maintenance mode.

### 7.3 Execute Restore

```bash
oc apply -f restore-app-prod-20260703.yaml
```

Watch:

```bash
watch -n 5 'oc get restore -n openshift-adp'
watch -n 5 'oc get pods,pvc -n app-prod'
```

Velero CLI:

```bash
velero restore get
velero restore describe restore-app-prod-20260703 --details
```

## 8. Restore CR and Velero-Level Validation

This is the first formal validation layer after restore execution.

### 8.1 Check Restore Phase

```bash
oc get restore -n openshift-adp
oc describe restore restore-app-prod-20260703 -n openshift-adp
```

Common phases include:

| Phase | Meaning | Action |
|---|---|---|
| `New` | CR created, not processed yet | Wait/check controller |
| `InProgress` | Restore running | Monitor logs/events |
| `Completed` | Restore finished without errors | Continue deeper validation |
| `PartiallyFailed` | Restore completed with one or more errors | Investigate before approval |
| `Failed` | Restore failed | Do not approve; troubleshoot |

### 8.2 Describe Restore with Details

```bash
velero restore describe restore-app-prod-20260703 --details
```

Check these sections:

```text
Phase
Backup
Namespaces
Resources
Warnings
Errors
Restored items
HooksAttempted
HooksFailed
```

### 8.3 Retrieve Restore Logs

```bash
velero restore logs restore-app-prod-20260703 > restore-app-prod-20260703.log
less restore-app-prod-20260703.log
```

Search for errors:

```bash
grep -Ei 'error|failed|warning|timeout|denied|forbidden|already exists|not found|invalid' restore-app-prod-20260703.log
```

### 8.4 Understand Velero Error Categories

Velero restore descriptions commonly group warnings and errors into categories:

| Category | Meaning |
|---|---|
| `Velero` | Problem in Velero itself, object storage access, backup archive read, plugin issue, etc. |
| `Cluster` | Problem restoring cluster-scoped resources |
| `Namespaces` | Problem restoring namespaced resources in one or more namespaces |

Treat namespace-specific errors seriously. For example, an error restoring one `Secret`, `Route`, `PVC`, or `RoleBinding` can make the application unusable.

### 8.5 Validate Events in OADP Namespace

```bash
oc get events -n openshift-adp --sort-by=.lastTimestamp
```

Look for:

```text
FailedValidation
BackupNotFound
BackupStorageLocationUnavailable
RestoreFailed
SnapshotContentNotFound
PodVolumeRestoreFailed
DataDownloadFailed
```

### 8.6 Validate Velero Controller Logs

```bash
oc logs deployment/velero -n openshift-adp -c velero --since=2h | tee velero-restore-controller.log

grep -Ei 'restore-app-prod-20260703|error|failed|warning|timeout|forbidden|denied' velero-restore-controller.log
```

### 8.7 Validate Node-Agent / Restic / Kopia Logs

If using filesystem backup:

```bash
oc get pods -n openshift-adp -o wide
oc logs daemonset/node-agent -n openshift-adp --since=2h
```

Depending on OADP version/configuration, node-agent/restic/kopia pod naming can vary. Use labels if needed:

```bash
oc get pods -n openshift-adp --show-labels
```

## 9. Namespace and Resource Validation

### 9.1 Validate Namespace Exists

```bash
oc get ns app-prod
oc describe ns app-prod
```

For mapped restore:

```bash
oc get ns app-prod-dr
oc describe ns app-prod-dr
```

Check labels/annotations:

```bash
oc get ns app-prod -o yaml | egrep -i 'labels:|annotations:|openshift.io|pod-security'
```

### 9.2 Validate Restored Resource Inventory

Capture actual resources:

```bash
oc api-resources --namespaced=true -o name | while read r; do
  oc get "$r" -n app-prod --ignore-not-found
 done
```

More targeted:

```bash
oc get all -n app-prod
oc get cm,secret,sa,role,rolebinding -n app-prod
oc get pvc,pod,deploy,sts,ds,job,cronjob -n app-prod
oc get route,svc,endpoints,endpointslice,networkpolicy -n app-prod
```

### 9.3 Compare Backup Resource List with Restored State

Backup detail:

```bash
velero backup describe app-prod-backup-20260703 --details > backup-details.txt
velero restore describe restore-app-prod-20260703 --details > restore-details.txt
```

Compare expected application objects:

```bash
oc get deploy,sts,svc,route,pvc,cm,secret,sa,rolebinding -n app-prod -o name | sort > restored-objects.txt
```

If you maintain a GitOps manifest source:

```bash
# Example idea only
find ./manifests/app-prod -type f -name '*.yaml' | sort > expected-manifests.txt
```

### 9.4 Validate Velero Labels on Restored Objects

Velero adds labels to help identify restore origin.

```bash
oc get all -n app-prod -l velero.io/restore-name=restore-app-prod-20260703
oc get pvc -n app-prod -l velero.io/restore-name=restore-app-prod-20260703
```

Check one object:

```bash
oc get deploy <deploy-name> -n app-prod -o yaml | grep -A5 'velero.io'
```

### 9.5 Validate Quotas and LimitRanges

Restored workloads can fail if quotas/limits are restored differently or target cluster quotas are stricter.

```bash
oc get resourcequota,limitrange -n app-prod
oc describe resourcequota -n app-prod
oc describe limitrange -n app-prod
```

Look for pods stuck with:

```text
Exceeded quota
minimum memory usage per Container is ...
maximum cpu usage per Container is ...
```

## 10. Persistent Volume and Data Validation

For stateful apps, restore validation is mostly storage validation.

### 10.1 Validate PVC Status

```bash
oc get pvc -n app-prod
oc describe pvc -n app-prod
```

Expected:

```text
STATUS: Bound
VOLUME: assigned
STORAGECLASS: correct for target cluster
CAPACITY: expected size
ACCESS MODES: expected mode
```

### 10.2 Validate PV Status

```bash
oc get pv | grep app-prod
oc describe pv <pv-name>
```

Check:

- PV status is `Bound`.
- ClaimRef points to correct namespace/PVC.
- Reclaim policy is expected.
- StorageClass is expected.
- CSI volume handle or underlying volume ID exists.
- No stale source-cluster references remain.

### 10.3 Validate VolumeSnapshot Objects

For CSI snapshot restore:

```bash
oc get volumesnapshot -A
oc get volumesnapshotcontent
oc describe volumesnapshot -n app-prod
```

Expected:

```text
ReadyToUse: true
BoundVolumeSnapshotContentName exists
No snapshot restore errors
```

### 10.4 Validate DataDownloads / PodVolumeRestores

For filesystem backup, Kopia, Restic, or Data Mover paths:

```bash
oc get podvolumerestores -n openshift-adp
oc describe podvolumerestore -n openshift-adp

oc get datadownloads -n openshift-adp
oc describe datadownload -n openshift-adp
```

If these resources do not exist, your OADP/Velero version or backup method might use different CR names. Check available Velero CRDs:

```bash
oc get crd | grep -i velero
oc api-resources | grep -i velero
```

### 10.5 Validate Files Inside Restored Volume

Create a temporary debug pod that mounts the PVC.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pvc-validate
  namespace: app-prod
spec:
  restartPolicy: Never
  containers:
  - name: check
    image: registry.access.redhat.com/ubi9/ubi
    command: ["/bin/bash", "-c", "sleep 3600"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: <pvc-name>
```

Apply and inspect:

```bash
oc apply -f pvc-validate.yaml
oc rsh -n app-prod pvc-validate

ls -lah /data
du -sh /data
find /data -maxdepth 2 -type f | head
```

For data integrity, compare a known file checksum from pre-backup evidence:

```bash
sha256sum /data/<important-file>
```

Delete debug pod after validation:

```bash
oc delete pod pvc-validate -n app-prod
```

### 10.6 Validate Filesystem Ownership and SELinux Context

Many restored apps fail due to UID/GID or SCC mismatch.

Inside debug pod:

```bash
ls -ln /data
stat /data
```

In pod logs, look for:

```text
permission denied
read-only file system
operation not permitted
cannot create directory
```

If SCC requires random UID, ensure directories are group-writable as needed:

```bash
chmod -R g+rwX /data
chgrp -R 0 /data
```

Use this carefully and only when consistent with application/security policy.

## 11. Workload Readiness Validation

### 11.1 Validate Deployments

```bash
oc get deploy -n app-prod
oc rollout status deploy/<deploy-name> -n app-prod --timeout=5m
oc describe deploy/<deploy-name> -n app-prod
```

Check:

```text
AVAILABLE equals desired replicas
No ProgressDeadlineExceeded
No image pull errors
No SCC/security errors
```

### 11.2 Validate StatefulSets

```bash
oc get sts -n app-prod
oc rollout status sts/<sts-name> -n app-prod --timeout=10m
oc describe sts/<sts-name> -n app-prod
```

Check:

- PVC templates restored or recreated correctly.
- Pod ordinal sequence is correct.
- Each replica has its own PVC.
- Readiness/liveness probes pass.
- Storage is writable.

### 11.3 Validate DaemonSets

```bash
oc get ds -n app-prod
oc describe ds/<ds-name> -n app-prod
```

Check:

```text
DESIRED = CURRENT = READY
Node selectors and tolerations match target cluster
```

### 11.4 Validate Pods

```bash
oc get pods -n app-prod -o wide
oc describe pod <pod-name> -n app-prod
oc logs <pod-name> -n app-prod --all-containers=true --tail=200
```

Search all pod logs:

```bash
for p in $(oc get pod -n app-prod -o name); do
  echo "===== $p ====="
  oc logs "$p" -n app-prod --all-containers=true --tail=100 | egrep -i 'error|fail|exception|denied|timeout|panic|fatal' || true
 done
```

### 11.5 Common Pod Failure Reasons After Restore

| Pod State | Likely Cause | Validation Command |
|---|---|---|
| `ImagePullBackOff` | Image registry/auth/mirror problem | `oc describe pod` |
| `CrashLoopBackOff` | Bad config, missing data, permission issue | `oc logs --previous` |
| `CreateContainerConfigError` | Missing secret/configmap | `oc describe pod` |
| `Pending` | PVC not bound, quota, node selector, taint | `oc describe pod` |
| `Running` but not Ready | Probe failure, dependency unavailable | `oc describe pod`, `oc logs` |
| `Error` | Init container or command failure | `oc logs -c <container>` |

- CSI snapshots with application quiescing.
- Operator-supported backup/restore mechanism combined with OADP for Kubernetes objects.

## 16. Cross-Namespace and Cross-Cluster Restore Validation

### 16.1 Namespace Mapping Validation

If restoring `app-prod` to `app-prod-dr`:

```bash
oc get all -n app-prod-dr
oc get pvc,route,svc,secret,cm,sa,rolebinding -n app-prod-dr
```

Search for old namespace references:

```bash
oc get all,cm,secret,rolebinding,networkpolicy,route -n app-prod-dr -o yaml | grep -n 'app-prod' || true
```

Old namespace references can remain in:

- ConfigMaps
- Secrets
- environment variables
- app config files
- Route hosts
- NetworkPolicy namespace selectors
- RoleBinding subjects
- External URLs
- Service mesh configs
- Monitoring configs

### 16.2 Route Host Conflict Validation

If restoring to same cluster but different namespace, route hostnames can conflict.

```bash
oc get route -A | grep <route-host>
oc describe route <route-name> -n app-prod-dr
```

If route is not admitted:

```text
HostAlreadyClaimed
```

Fix by assigning a DR/test hostname:

```bash
oc patch route <route-name> -n app-prod-dr --type=merge -p '{"spec":{"host":"app-prod-dr.apps.example.com"}}'
```

### 16.3 StorageClass Mapping Validation

If target cluster uses different storage class names, configure/validate storage class mapping.

Check source and target:

```bash
oc get sc
oc get pvc -n app-prod-dr -o wide
```

Example Velero storage class mapping ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: change-storage-class-config
  namespace: openshift-adp
  labels:
    velero.io/plugin-config: ""
    velero.io/change-storage-class: RestoreItemAction
data:
  old-storage-class: new-storage-class
```

Apply before restore:

```bash
oc apply -f change-storage-class-config.yaml
```

### 16.4 Image Registry Mapping Validation

If restoring to a disconnected or different cluster, image references may need remapping.

```bash
oc get deploy,sts,ds -n app-prod-dr -o yaml | grep 'image:'
```

If images point to a source-cluster internal registry that is unreachable, update image references or configure image registry mirroring.

For most application restores, you should avoid restoring the Operator installation itself unless you have a tested procedure. Usually:

### 19.1 RTO Validation

RTO means **how long it took to restore service**.

Capture:

```text
Restore start time
Restore CR completion time
First pod ready time
Application health endpoint success time
Business validation sign-off time
```

Example evidence:

```bash
date -Is | tee restore-timeline.txt

oc get pods -n app-prod -o wide > pods-final.txt
curl -k -w '\nHTTP=%{http_code} TIME=%{time_total}\n' https://<route-host>/health | tee app-health.txt
```

RTO result:

```text
Restore started: 10:05
Restore CR completed: 10:17
Pods ready: 10:21
Application health OK: 10:23
Business sign-off: 10:30
RTO actual: 25 minutes
RTO target: 30 minutes
Result: PASS
```

RPO means **how much data loss is acceptable**.

Validate from:

- Backup completion timestamp.
- Database latest transaction timestamp.
- Application audit/event timestamp.
- User/business confirmation.

```sql
SELECT MAX(created_at) FROM transactions;
```

RPO result:

```text
Incident: 11:00
Latest restored transaction: 10:47
RPO target: 30 minutes
Data loss: 13 minutes
Result: PASS
```

```bash
oc adm top pods -n app-prod
oc adm top nodes
```

Check application response:

```bash
for i in {1..10}; do
  curl -k -o /dev/null -s -w "HTTP=%{http_code} TIME=%{time_total}\n" https://<route-host>/health
 done
```

Check pod restarts:

```bash
oc get pods -n app-prod
```

## 20. Common Restore Validation Failures and Fixes

### 20.1 Restore Shows `PartiallyFailed`

Check:

```bash
velero restore describe <restore-name> --details
velero restore logs <restore-name>
oc describe restore <restore-name> -n openshift-adp
```

Typical causes:

| Cause | Fix |
|---|---|
| Resource already exists | Restore to clean namespace or use intended existing resource policy |
| Missing CRD | Install Operator/CRD first, then restore CRs |
| Missing StorageClass | Create mapping or install storage provider |
| Route host conflict | Patch route host for DR namespace |
| SCC denied | Bind required SCC to ServiceAccount |
| Image pull error | Fix pull secret, mirror image, or registry access |
| NetworkPolicy blocks traffic | Validate selectors and namespace labels |
| PVC pending | Fix StorageClass, quota, topology, node availability |
| Snapshot not found | Validate snapshot location/provider credentials |
| File restore timeout | Tune timeout/resources; validate node-agent |

### 20.2 PVC Stuck Pending

```bash
oc describe pvc <pvc-name> -n app-prod
oc get sc
oc describe sc <storageclass>
oc get events -n app-prod --sort-by=.lastTimestamp
```

Common messages:

```text
waiting for first consumer
storageclass not found
failed to provision volume
exceeded quota
```

Fix based on root cause:

- Create correct StorageClass.
- Use storage class mapping.
- Ensure pod is created for `WaitForFirstConsumer` storage.
- Fix quota.
- Check CSI driver health.

### 20.3 Pod Fails Because Secret Missing

```bash
oc describe pod <pod-name> -n app-prod
oc get secret -n app-prod
```

Fix:

- Restore missing secret.
- Recreate secret manually from approved source.
- Check if secret was excluded from backup.

### 20.4 Pod Fails Because SCC Denied

```bash
oc describe pod <pod-name> -n app-prod | grep -i scc -A5 -B5
```

Fix example:

```bash
oc adm policy add-scc-to-user anyuid -z <sa-name> -n app-prod
```

Use the least-privilege SCC possible.

### 20.5 Route Restored but Not Reachable

```bash
oc get route -n app-prod
oc describe route <route-name> -n app-prod
oc get endpoints <svc-name> -n app-prod
curl -k -v https://<route-host>
```

Possible causes:

- Route not admitted.
- Service has no endpoints.
- DNS not updated.
- TLS certificate mismatch.
- NetworkPolicy blocks backend.
- Router pod problem.

### 20.6 Service Has No Endpoints

```bash
oc get svc <svc-name> -n app-prod -o yaml
oc get pods -n app-prod --show-labels
```

Fix selector labels:

```bash
oc patch svc <svc-name> -n app-prod --type=merge -p '{"spec":{"selector":{"app":"myapp"}}}'
```

### 20.7 ImagePullBackOff After Restore

```bash
oc describe pod <pod-name> -n app-prod
oc get secret -n app-prod
oc get deploy <deploy-name> -n app-prod -o yaml | grep image:
```

Fix:

- Recreate image pull secret.
- Link secret to ServiceAccount.
- Mirror image to target registry.
- Update image reference.

Example:

```bash
oc secrets link <sa-name> <pull-secret-name> --for=pull -n app-prod
```

### 20.8 App Restored but Database Empty

Validate:

```bash
oc get pvc -n app-prod
oc rsh <db-pod> -n app-prod
ls -lah <db-data-path>
```

Possible causes:

- PV was not included in backup.
- `restorePVs` disabled.
- Wrong PVC mounted.
- Application initialized a new empty database before restore completed.
- Restore to different namespace changed references incorrectly.

### 20.9 Admission Webhook Blocks Restore

Symptoms:

```text
failed calling webhook
connection refused
no endpoints available for service
```

Fix options:

- Ensure webhook service is available before restoring dependent resources.
- Temporarily disable non-critical validating/mutating webhook during restore, if approved.
- Restore in correct order.
- Install Operator/webhook dependencies first.

## 22. Automation Script: Restore Validation Checklist

Save as `oadp-restore-validate.sh`.

```bash
#!/usr/bin/env bash
set -euo pipefail

RESTORE_NAME="${1:-}"
TARGET_NS="${2:-}"
OADP_NS="${OADP_NS:-openshift-adp}"

if [[ -z "$RESTORE_NAME" || -z "$TARGET_NS" ]]; then
  echo "Usage: $0 <restore-name> <target-namespace>"
  echo "Example: $0 restore-app-prod-20260703 app-prod"
  exit 1
fi

OUT="restore-validation-${RESTORE_NAME}-$(date +%Y%m%d%H%M%S)"
mkdir -p "$OUT"

echo "[INFO] Output directory: $OUT"

echo "[INFO] Checking OADP namespace pods"
oc get pods -n "$OADP_NS" -o wide | tee "$OUT/oadp-pods.txt"

echo "[INFO] Checking DPA"
oc get dpa -n "$OADP_NS" -o yaml > "$OUT/dpa.yaml" || true

echo "[INFO] Checking BackupStorageLocation and VolumeSnapshotLocation"
oc get backupstoragelocation -n "$OADP_NS" -o wide | tee "$OUT/bsl.txt" || true
oc get volumesnapshotlocation -n "$OADP_NS" -o wide | tee "$OUT/vsl.txt" || true

echo "[INFO] Checking Restore CR"
oc get restore "$RESTORE_NAME" -n "$OADP_NS" -o yaml > "$OUT/restore.yaml"
oc describe restore "$RESTORE_NAME" -n "$OADP_NS" > "$OUT/restore-describe-oc.txt"

echo "[INFO] Running Velero restore describe/logs"
oc -n "$OADP_NS" exec deployment/velero -c velero -- ./velero restore describe "$RESTORE_NAME" --details > "$OUT/restore-describe-velero.txt" || true
oc -n "$OADP_NS" exec deployment/velero -c velero -- ./velero restore logs "$RESTORE_NAME" > "$OUT/restore-logs.txt" || true

echo "[INFO] Searching restore logs for common problems"
grep -Ein 'error|failed|warning|timeout|forbidden|denied|not found|already exists|invalid|crash|panic' "$OUT/restore-logs.txt" > "$OUT/restore-log-problems.txt" || true

echo "[INFO] Checking namespace resources"
oc get all -n "$TARGET_NS" -o wide > "$OUT/all.txt" || true
oc get pvc -n "$TARGET_NS" -o wide > "$OUT/pvc.txt" || true
oc get pv > "$OUT/pv-all.txt" || true
oc get svc,endpoints,endpointslice,route -n "$TARGET_NS" -o wide > "$OUT/network-objects.txt" || true
oc get cm,secret,sa,role,rolebinding,networkpolicy -n "$TARGET_NS" > "$OUT/config-security.txt" || true
oc get events -n "$TARGET_NS" --sort-by=.lastTimestamp > "$OUT/events.txt" || true

echo "[INFO] Checking pods not Running/Completed"
oc get pods -n "$TARGET_NS" --no-headers 2>/dev/null | awk '$3 != "Running" && $3 != "Completed" {print}' > "$OUT/problem-pods.txt" || true

echo "[INFO] Collecting pod descriptions and recent logs"
mkdir -p "$OUT/pods"
for pod in $(oc get pod -n "$TARGET_NS" -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}' 2>/dev/null); do
  oc describe pod "$pod" -n "$TARGET_NS" > "$OUT/pods/${pod}-describe.txt" || true
  oc logs "$pod" -n "$TARGET_NS" --all-containers=true --tail=200 > "$OUT/pods/${pod}-logs.txt" 2>&1 || true
  grep -Ein 'error|failed|exception|denied|timeout|panic|fatal|permission' "$OUT/pods/${pod}-logs.txt" > "$OUT/pods/${pod}-log-problems.txt" || true
done

echo "[INFO] Checking Velero data restore objects"
oc get podvolumerestores -n "$OADP_NS" -o wide > "$OUT/podvolumerestores.txt" 2>/dev/null || true
oc get datadownloads -n "$OADP_NS" -o wide > "$OUT/datadownloads.txt" 2>/dev/null || true

echo "[INFO] Summary"
{
  echo "Restore: $RESTORE_NAME"
  echo "Target namespace: $TARGET_NS"
  echo "OADP namespace: $OADP_NS"
  echo
  echo "Restore phase:"
  oc get restore "$RESTORE_NAME" -n "$OADP_NS" -o jsonpath='{.status.phase}{"\n"}' 2>/dev/null || true
  echo
  echo "PVC status:"
  oc get pvc -n "$TARGET_NS" 2>/dev/null || true
  echo
  echo "Problem pods:"
  cat "$OUT/problem-pods.txt" 2>/dev/null || true
  echo
  echo "Restore log problem count:"
  wc -l "$OUT/restore-log-problems.txt" 2>/dev/null || true
} | tee "$OUT/summary.txt"

echo "[INFO] Validation evidence saved in: $OUT"
```

Run:

```bash
chmod +x oadp-restore-validate.sh
./oadp-restore-validate.sh restore-app-prod-20260703 app-prod
```

This script does not replace application-owner validation. It only collects technical restore evidence.

## 23. Interview and Real-World Scenario Questions

### Question 1: Restore CR is `Completed`, but app is down. What do you check?

Check in order:

1. `velero restore describe --details`
2. `velero restore logs`
3. `oc get pods,pvc,svc,endpoints,route -n <ns>`
4. Pod events and logs
5. PVC binding and data mount
6. Service selectors/endpoints
7. Route admission and DNS
8. Secret/ConfigMap references
9. SCC/RBAC errors
10. NetworkPolicy
11. Application dependency checks

### Question 2: Restore is `PartiallyFailed`. Can you approve it?

Not automatically. `PartiallyFailed` means at least one error occurred. You must identify whether the failed resources are irrelevant or business-critical. Approval requires documented risk acceptance or a fix and rerun.

### Question 3: PVC is Bound but app data is missing. Why?

Possible reasons:

- Backup did not include volume data.
- Restore used wrong backup.
- `restorePVs` was false.
- StorageClass mapping created a fresh empty volume.
- Application initialized new data before old data was restored.
- Wrong PVC mounted.
- File system backup failed but was ignored.
- Database expected application-consistent backup but got crash-consistent data.

### Question 4: Route exists but URL fails. What do you check?

```bash
oc describe route <route> -n <ns>
oc get svc,endpoints -n <ns>
oc get pods -n <ns> --show-labels
curl -k -v https://<host>
oc logs -n openshift-ingress deployment/router-default
```

Likely issues:

- Route not admitted.
- Host conflict.
- Service has no endpoints.
- TLS termination mismatch.
- DNS points elsewhere.
- Backend pod not ready.

### Question 5: How do you validate restore to another namespace?

Validate:

- `namespaceMapping` correct.
- Resources exist in target namespace.
- No hardcoded old namespace remains.
- PVCs bound in target namespace.
- Routes use non-conflicting hosts.
- RoleBinding subjects updated if needed.
- NetworkPolicy namespace selectors still allow required traffic.
- Application config does not point to old services.

### Question 6: Why should Operators be excluded from many app backups?

Operators own reconciliation logic and CRDs. Restoring Operator deployment/OLM objects blindly can conflict with the target cluster's Operator Lifecycle Manager state. A safer pattern is to install the Operator first, validate CRDs, then restore app custom resources and allow the Operator to reconcile.

## 24. Best Practices

### 24.1 Validate Restores Regularly

A backup strategy without restore testing is incomplete. Schedule restore drills:

```text
Dev/test restore: weekly or monthly
Critical production app restore drill: quarterly
Full DR restore test: semi-annually or annually
```

### 24.2 Maintain Application Restore Profiles

For every critical namespace, document:

```text
Application owner
Namespace
Required Operators/CRDs
Required StorageClass
PVC list and mount paths
Route hosts
Secrets source
SCC requirements
NetworkPolicy requirements
Database validation commands
Health check URLs
RTO/RPO
```

### 24.3 Prefer Test Namespace Validation First

Before in-place production restore, test backup quality by restoring to a different namespace:

```bash
velero restore create restore-app-prod-test \
  --from-backup app-prod-backup-20260703 \
  --namespace-mappings app-prod:app-prod-restore-test
```

Then validate:

```bash
oc get all,pvc,route,svc,endpoints -n app-prod-restore-test
```

### 24.4 Keep Restore Evidence

For audits and incident reviews, retain:

- Restore CR YAML
- Backup describe output
- Restore describe output
- Restore logs
- OADP/Velero pod logs
- Target namespace resource inventory
- PVC status
- Route/health check output
- DB validation output
- RTO/RPO calculation
- Application owner sign-off

### 24.5 Use Labels for Backup/Restore Scope

Label application resources clearly:

```bash
oc label deploy,pvc,svc,route -n app-prod app.kubernetes.io/part-of=payment-platform
oc label ns app-prod backup=enabled
```

Then backup/restore can be scoped more safely.

### 24.6 Avoid Restoring Everything Blindly

Do not restore full cluster-scoped resources unless required. Application restore should be focused and intentional.

Avoid casually restoring:

- ClusterRoleBinding
- SecurityContextConstraints
- MutatingWebhookConfiguration
- ValidatingWebhookConfiguration
- Operator subscriptions and CSVs
- Node-specific resources
- Infrastructure namespaces

### 24.7 Treat `Completed` as Technical Completion, Not Business Completion

`Completed` means Velero finished the restore operation. It does not mean:

- The app is reachable.
- The database is consistent.
- The data is correct.
- Security is correct.
- RPO/RTO passed.
- Users can work.

### 24.8 Validate Before Deleting Old Environment

For migrations or DR failover, do not delete the source namespace/cluster until:

- Restored app passes health checks.
- Business owner signs off.
- Data consistency is validated.
- External integrations are repointed.
- Monitoring confirms stable behavior.
- Rollback decision is documented.

## 25. Summary

Restore validation in OADP is a multi-layer production discipline.

A good restore validation process confirms:

```text
OADP is healthy
Backup source is usable
Restore CR is correct
Restore phase is acceptable
Warnings/errors are reviewed
Kubernetes resources exist
PVCs are bound
Volume data is present
Pods are ready
Services have endpoints
Routes are admitted and reachable
Secrets/configs/RBAC/SCC are correct
NetworkPolicy allows required traffic
Application functions correctly
Database data is consistent
RTO/RPO are met
Evidence is captured
Business owner signs off
```

For an advanced OpenShift administrator, the most important lesson is:

> Restore validation is not a Velero-only task. It is an OpenShift, storage, network, security, application, and business-continuity validation process.
