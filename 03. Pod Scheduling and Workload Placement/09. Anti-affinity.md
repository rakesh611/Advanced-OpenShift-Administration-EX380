## 1. Executive Summary

**Pod anti-affinity** is a Kubernetes/OpenShift scheduler feature that tells the scheduler:

> “Do not place this pod near pods matching a given label selector within a specified topology domain.”

In simple words:

- Keep replicas of the same application away from each other.
- Keep critical pods away from noisy or conflicting pods.
- Spread workloads across nodes, racks, zones, or other topology domains.
- Reduce the blast radius of node, rack, or zone failure.

Anti-affinity is configured inside the pod specification:

```yaml
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution: []
      preferredDuringSchedulingIgnoredDuringExecution: []
```

For workloads such as `Deployment`, `DeploymentConfig`, `StatefulSet`, `DaemonSet`, `Job`, and `CronJob`, it is placed under the **pod template**:

```yaml
spec:
  template:
    spec:
      affinity:
        podAntiAffinity:
          ...
```

OpenShift administrators use anti-affinity when they need workload separation based on **other pods**, not just based on node labels.

## 2. Why Anti-affinity Matters in OpenShift

In an enterprise OpenShift cluster, workload placement is not only about “where can this pod fit?” It is about:

- availability,
- fault tolerance,
- performance isolation,
- tenant separation,
- planned maintenance,
- infrastructure cost,
- upgrade safety,
- avoiding correlated failure.

Without anti-affinity, the scheduler may legally place all replicas of an application on the same worker node if resource scoring allows it. That may be acceptable for a dev workload, but it is dangerous for production.

Example risk:

```text
Deployment: payment-api
Replicas:   3
Placement:  all 3 pods on worker-2
Failure:    worker-2 reboots
Impact:     full payment-api outage
```

With anti-affinity:

```text
payment-api-1 -> worker-1
payment-api-2 -> worker-2
payment-api-3 -> worker-3
```

Now a single node failure affects only one replica.

Anti-affinity is especially useful for:

| Use Case | Anti-affinity Goal |
|---|---|
| Web/API replicas | Spread replicas across nodes |
| Redis/Cache replicas | Avoid multiple cache replicas on one node |
| Stateful databases | Place members on different nodes/zones |
| Monitoring stack | Keep Prometheus/Alertmanager replicas separated |
| CI/CD runners | Avoid noisy build pods near latency-sensitive apps |
| Multi-tenant clusters | Keep selected tenant workloads apart |
| Application pairs | Avoid incompatible workloads sharing a failure domain |

## 3. Scheduling Mental Model

The OpenShift scheduler is based on the Kubernetes scheduler framework. For a new pending pod, it broadly performs:

```text
1. Queue pending pod
2. Filter unsuitable nodes
3. Score remaining nodes
4. Pick highest-scoring node
5. Bind pod to selected node
6. Kubelet starts pod on that node
```

Anti-affinity participates mainly in these phases:

| Anti-affinity Type | Scheduler Phase | Behavior |
|---|---|---|
| `requiredDuringSchedulingIgnoredDuringExecution` | Filter | Node is rejected if rule is violated |
| `preferredDuringSchedulingIgnoredDuringExecution` | Score | Node receives lower/higher score depending on preference |

Important words:

### `required`

Hard rule. If no node satisfies the rule, the pod remains `Pending`.

### `preferred`

Soft rule. Scheduler tries to honor it, but the pod can still run if the preference cannot be satisfied.

### `DuringScheduling`

The rule is evaluated when the pod is being scheduled.

### `IgnoredDuringExecution`

After the pod is already running, OpenShift does not evict it just because labels changed later and the rule is no longer satisfied.

This is a very important production detail. Anti-affinity controls **placement at scheduling time**, not continuous enforcement after scheduling.

## 4. Affinity vs Anti-affinity vs Node Affinity vs Taints

Do not confuse these scheduling controls.

| Feature | Based On | Direction | Typical Use |
|---|---|---|---|
| `nodeSelector` | Node labels | Must run on matching nodes | Simple placement |
| Node affinity | Node labels | Prefer/require selected nodes | Advanced node targeting |
| Pod affinity | Other pod labels | Place near matching pods | Co-locate app components |
| Pod anti-affinity | Other pod labels | Avoid matching pods | Spread or isolate pods |
| Taints/tolerations | Node taints + pod tolerations | Node repels pods | Dedicated/special nodes |
| Topology spread constraints | Pod labels + topology | Even distribution | Controlled HA spread |

### Key difference

Node affinity asks:

```text
Does this node have the labels I want?
```

Pod anti-affinity asks:

```text
Are there already pods matching my selector in this node/rack/zone/domain?
If yes, avoid or reject this node/domain.
```

### Example comparison

Node affinity:

```yaml
nodeAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    nodeSelectorTerms:
    - matchExpressions:
      - key: node-role.kubernetes.io/infra
        operator: Exists
```

Meaning:

```text
Run only on infra nodes.
```

Pod anti-affinity:

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        app: payment-api
    topologyKey: kubernetes.io/hostname
```

Meaning:

```text
Do not run this pod on a node that already has another pod labeled app=payment-api.
```

## 5. Anti-affinity Types

OpenShift supports two anti-affinity types.

### 5.1 Hard Anti-affinity

Field:

```yaml
requiredDuringSchedulingIgnoredDuringExecution
```

This is mandatory. If the rule cannot be satisfied, the pod remains pending.

Use it when violating the rule is worse than not running the pod.

Good use cases:

- database quorum members,
- critical API replicas,
- highly available ingress-like components,
- avoiding same-node placement for replicas where single-node failure would cause outage.

Risk:

- If replicas exceed the number of valid topology domains, extra pods stay pending.
- If node labels are missing or inconsistent, pods may not schedule.
- If resources are insufficient on distinct nodes, pods may not schedule.

### 5.2 Soft Anti-affinity

Field:

```yaml
preferredDuringSchedulingIgnoredDuringExecution
```

This is a preference. Scheduler tries to honor it but can violate it if needed.

Use it when spreading is desirable but availability of the application is more important than perfect placement.

Good use cases:

- stateless web workloads,
- dev/test environments,
- large replica sets,
- clusters with frequent autoscaling,
- workloads where temporary co-location is acceptable.

Example:

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app: web
      topologyKey: kubernetes.io/hostname
```

## 6. Core YAML Structure

### 6.1 For a Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: demo-pod
  namespace: demo
  labels:
    app: demo
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: demo
        topologyKey: kubernetes.io/hostname
  containers:
  - name: app
    image: registry.access.redhat.com/ubi9/ubi-minimal:latest
    command: ["sleep", "3600"]
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]
```

### 6.2 For a Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-api
  namespace: demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: demo-api
  template:
    metadata:
      labels:
        app: demo-api
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: demo-api
            topologyKey: kubernetes.io/hostname
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi-minimal:latest
        command: ["sleep", "3600"]
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 200m
            memory: 256Mi
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop: ["ALL"]
```

Meaning:

```text
Each demo-api replica should run on a different node.
```

## 7. Required Hard Anti-affinity

### 7.1 Basic hard anti-affinity per node

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        app: payment-api
    topologyKey: kubernetes.io/hostname
```

This means:

```text
Reject any node that already has a pod labeled app=payment-api.
```

If you have:

```text
3 replicas
3 worker nodes
```

Placement can be:

```text
payment-api-1 -> worker-1
payment-api-2 -> worker-2
payment-api-3 -> worker-3
```

If you scale to 4 replicas but only 3 eligible nodes exist:

```text
payment-api-4 -> Pending
```

The fourth pod remains pending because the hard anti-affinity rule cannot be satisfied.

### 7.2 Hard anti-affinity across zones

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        app: payment-api
    topologyKey: topology.kubernetes.io/zone
```

This means:

```text
Do not schedule two matching payment-api pods in the same zone.
```

If there are only two zones and three replicas, one pod may remain pending.

Use this carefully. Zone-level hard anti-affinity is stronger than node-level hard anti-affinity.

### 7.3 Hard anti-affinity for different applications

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        workload-type: batch-heavy
    topologyKey: kubernetes.io/hostname
```

This says:

```text
Do not schedule this pod on a node that already runs a batch-heavy pod.
```

Useful for protecting latency-sensitive workloads from CPU/I/O-heavy batch workloads.

## 8. Preferred Soft Anti-affinity

Soft anti-affinity is usually safer for large production clusters because it reduces pending pod risk.

### 8.1 Basic preferred anti-affinity

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app: frontend
      topologyKey: kubernetes.io/hostname
```

This means:

```text
Prefer nodes that do not already have pods labeled app=frontend.
If no such node exists, still schedule the pod.
```

### 8.2 Weight value

The `weight` field must be between `1` and `100`.

- Higher weight = stronger preference.
- Multiple preferred rules can be defined.
- The scheduler adds preferred-rule scores with other scheduling scores.

Example:

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app: api
      topologyKey: kubernetes.io/hostname
  - weight: 50
    podAffinityTerm:
      labelSelector:
        matchLabels:
          tier: backend
      topologyKey: topology.kubernetes.io/zone
```

Meaning:

```text
Strongly prefer not to place same app on same node.
Also prefer not to concentrate backend tier in one zone.
```

## 9. Topology Keys Explained Deeply

The `topologyKey` defines the failure domain or placement domain where the anti-affinity rule applies.

It is a **node label key**.

The scheduler looks at nodes and groups them by the value of that label.

### 9.1 Common topology keys

| Topology Key | Meaning | Example Use |
|---|---|---|
| `kubernetes.io/hostname` | Individual node | Spread replicas across nodes |
| `topology.kubernetes.io/zone` | Availability zone | Spread across cloud zones |
| `topology.kubernetes.io/region` | Cloud region | Avoid same region, uncommon inside one cluster |
| `rack` | Custom rack label | Spread across racks in bare metal DC |
| `room` | Custom room/datacenter area | Physical fault isolation |
| `node-role.kubernetes.io/worker` | Not usually ideal as topology key | Role-based grouping, rarely useful |

### 9.2 Node-level topology

```yaml
topologyKey: kubernetes.io/hostname
```

This is the most common anti-affinity topology.

Meaning:

```text
Do not place matching pods on the same node.
```

### 9.3 Zone-level topology

```yaml
topologyKey: topology.kubernetes.io/zone
```

Meaning:

```text
Do not place matching pods in the same availability zone.
```

This is powerful but dangerous if used as hard anti-affinity with more replicas than zones.

### 9.4 Rack-level topology

For bare metal clusters, label nodes:

```bash
oc label node worker-1 topology.example.com/rack=rack-a
oc label node worker-2 topology.example.com/rack=rack-b
oc label node worker-3 topology.example.com/rack=rack-c
```

Then use:

```yaml
topologyKey: topology.example.com/rack
```

Meaning:

```text
Avoid placing matching pods in the same rack.
```

### 9.5 Validate topology labels

```bash
oc get nodes --show-labels
```

Better:

```bash
oc get nodes -L kubernetes.io/hostname,topology.kubernetes.io/zone
```

For custom rack:

```bash
oc get nodes -L topology.example.com/rack
```

### 9.6 Important topology warning

All eligible nodes should consistently have the topology label used by anti-affinity. Missing topology labels can cause confusing scheduling behavior.

For example, if your pod uses:

```yaml
topologyKey: topology.kubernetes.io/zone
```

but some nodes do not have that label, scheduling may not behave as expected.

## 10. Label Selectors and Operators

Anti-affinity works by selecting **existing pods** using labels.

### 10.1 `matchLabels`

Simple equality selector:

```yaml
labelSelector:
  matchLabels:
    app: web
```

Equivalent logic:

```text
app == web
```

### 10.2 `matchExpressions`

Advanced selector:

```yaml
labelSelector:
  matchExpressions:
  - key: app
    operator: In
    values:
    - web
    - api
```

Equivalent logic:

```text
app in (web, api)
```

### 10.3 Supported operators

For pod affinity and anti-affinity, commonly used operators are:

| Operator | Meaning |
|---|---|
| `In` | Label value must be in list |
| `NotIn` | Label value must not be in list |
| `Exists` | Label key must exist |
| `DoesNotExist` | Label key must not exist |

Examples:

```yaml
matchExpressions:
- key: tier
  operator: In
  values:
  - frontend
```

```yaml
matchExpressions:
- key: workload-type
  operator: Exists
```

```yaml
matchExpressions:
- key: environment
  operator: NotIn
  values:
  - dev
  - test
```

### 10.4 Label selector risk

Anti-affinity can accidentally match more pods than intended.

Bad example:

```yaml
matchLabels:
  app: web
```

If many teams use `app=web`, your rule can match unrelated pods.

Better:

```yaml
matchLabels:
  app.kubernetes.io/name: payment-api
  app.kubernetes.io/instance: payment-api-prod
```

Recommended label style:

```yaml
app.kubernetes.io/name: payment-api
app.kubernetes.io/instance: payment-api-prod
app.kubernetes.io/component: api
app.kubernetes.io/part-of: payment-platform
app.kubernetes.io/managed-by: helm
```

## 11. Namespace Scope, `namespaces`, and `namespaceSelector`

By default, pod anti-affinity normally evaluates matching pods in the **same namespace** as the incoming pod.

### 11.1 Same namespace anti-affinity

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        app: web
    topologyKey: kubernetes.io/hostname
```

Meaning:

```text
Avoid pods labeled app=web in the same namespace.
```

### 11.2 Match specific namespaces

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        app: batch-worker
    namespaces:
    - batch-prod
    - batch-shared
    topologyKey: kubernetes.io/hostname
```

Meaning:

```text
Do not run near batch-worker pods from namespaces batch-prod or batch-shared.
```

### 11.3 Match namespaces by namespace label

First label namespaces:

```bash
oc label namespace team-a tenant=team-a
oc label namespace team-b tenant=team-b
oc label namespace batch-prod workload-class=batch
```

Then use:

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          workload-type: batch-heavy
      namespaceSelector:
        matchLabels:
          workload-class: batch
      topologyKey: kubernetes.io/hostname
```

Meaning:

```text
Prefer not to place this pod on nodes already running batch-heavy pods from namespaces labeled workload-class=batch.
```

### 11.4 Important multi-tenancy warning

Cross-namespace anti-affinity can introduce tenant coupling. One tenant’s labels can influence another tenant’s scheduling if cluster admins allow it in templates or shared Helm charts.

For strict multi-tenancy, be careful with:

```yaml
namespaceSelector: {}
```

An empty `namespaceSelector` can match all namespaces, depending on API behavior and context.

Use explicit namespace labels and governance.

## 12. Real Production Patterns

### Pattern 1: Spread same application replicas across nodes

Use for stateless apps:

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app.kubernetes.io/name: checkout-api
      topologyKey: kubernetes.io/hostname
```

Recommended for most web/API deployments.

### Pattern 2: Strict separation for critical replicas

Use hard anti-affinity:

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        app.kubernetes.io/name: identity-api
    topologyKey: kubernetes.io/hostname
```

Use only when enough eligible nodes exist.

### Pattern 3: Avoid noisy neighbor

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 90
    podAffinityTerm:
      labelSelector:
        matchLabels:
          workload-profile: cpu-heavy
      topologyKey: kubernetes.io/hostname
```

Use for latency-sensitive apps.

### Pattern 4: Separate primary and analytics workload

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        workload-role: analytics
    topologyKey: kubernetes.io/hostname
```

Use when analytics workloads heavily consume CPU, memory, disk, or network.

### Pattern 5: Zone-aware HA

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app.kubernetes.io/name: payment-api
      topologyKey: topology.kubernetes.io/zone
```

Use preferred zone anti-affinity first. Use required zone anti-affinity only if replica count and zone count are carefully controlled.

### Pattern 6: Dedicated node pool + anti-affinity

Combine node affinity and pod anti-affinity:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: node-role.kubernetes.io/app
          operator: Exists
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app.kubernetes.io/name: payment-api
      topologyKey: kubernetes.io/hostname
```

Meaning:

```text
Run only on app nodes, and do not place two payment-api pods on the same app node.
```

## 13. OpenShift Deployment Examples

### 13.1 Create project

```bash
oc new-project sched-demo
```

### 13.2 Deployment with hard pod anti-affinity

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: sched-demo
  labels:
    app.kubernetes.io/name: payment-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app.kubernetes.io/name: payment-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: payment-api
        app.kubernetes.io/component: api
        app.kubernetes.io/part-of: payment-platform
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app.kubernetes.io/name: payment-api
            topologyKey: kubernetes.io/hostname
      containers:
      - name: payment-api
        image: registry.access.redhat.com/ubi9/ubi-minimal:latest
        command: ["/bin/sh", "-c", "while true; do echo payment-api; sleep 30; done"]
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 200m
            memory: 256Mi
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop: ["ALL"]
```

Apply:

```bash
oc apply -f payment-api-hard-antiaffinity.yaml
```

Check placement:

```bash
oc get pods -n sched-demo -o wide
```

Expected:

```text
Each replica should be on a different node if enough eligible nodes exist.
```

### 13.3 Scale beyond available nodes

```bash
oc scale deployment/payment-api -n sched-demo --replicas=10
oc get pods -n sched-demo -o wide
```

If fewer than 10 eligible nodes exist, some pods can stay pending.

Check events:

```bash
oc describe pod -n sched-demo <pending-pod-name>
```

You may see scheduling failures related to pod anti-affinity.

### 13.4 Convert hard rule to soft rule

Patch by editing:

```bash
oc edit deployment/payment-api -n sched-demo
```

Replace:

```yaml
requiredDuringSchedulingIgnoredDuringExecution:
- labelSelector:
    matchLabels:
      app.kubernetes.io/name: payment-api
  topologyKey: kubernetes.io/hostname
```

With:

```yaml
preferredDuringSchedulingIgnoredDuringExecution:
- weight: 100
  podAffinityTerm:
    labelSelector:
      matchLabels:
        app.kubernetes.io/name: payment-api
    topologyKey: kubernetes.io/hostname
```

Now scheduler will prefer spreading but still schedule when perfect spreading is impossible.

## 14. StatefulSet Anti-affinity

Stateful workloads often need stricter placement control than stateless deployments.

Example: Redis StatefulSet replicas should not run on the same node.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
  namespace: cache-prod
spec:
  serviceName: redis
  replicas: 3
  selector:
    matchLabels:
      app.kubernetes.io/name: redis
  template:
    metadata:
      labels:
        app.kubernetes.io/name: redis
        app.kubernetes.io/component: cache
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app.kubernetes.io/name: redis
            topologyKey: kubernetes.io/hostname
      containers:
      - name: redis
        image: registry.redhat.io/rhel9/redis-7:latest
        ports:
        - containerPort: 6379
          name: redis
        resources:
          requests:
            cpu: 100m
            memory: 256Mi
          limits:
            cpu: 500m
            memory: 512Mi
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop: ["ALL"]
```

### StatefulSet production notes

For stateful applications, also check:

```bash
oc get pvc -n cache-prod
oc get pv
oc get pods -n cache-prod -o wide
oc describe pod -n cache-prod <pod>
```

Anti-affinity can conflict with storage topology. For example, a PVC may bind to storage available only in one zone, while anti-affinity requires placement in a different zone.

For storage-backed workloads, always validate:

- `StorageClass` volume binding mode,
- zone/rack storage availability,
- PV node affinity,
- StatefulSet replica count,
- pod anti-affinity topology key.

## 15. Multi-zone / Multi-rack Designs

### 15.1 Cloud zone labels

Common node labels:

```bash
oc get nodes -L topology.kubernetes.io/zone,topology.kubernetes.io/region
```

Example output:

```text
NAME       ZONE        REGION
worker-1   zone-a      region-1
worker-2   zone-b      region-1
worker-3   zone-c      region-1
```

### 15.2 Zone-level soft anti-affinity

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app.kubernetes.io/name: order-api
      topologyKey: topology.kubernetes.io/zone
```

This tries to spread replicas across zones.

### 15.3 Node-level hard + zone-level soft

This is a strong production pattern:

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app.kubernetes.io/name: order-api
      topologyKey: kubernetes.io/hostname
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app.kubernetes.io/name: order-api
        topologyKey: topology.kubernetes.io/zone
```

Meaning:

```text
Must not place two replicas on the same node.
Prefer spreading replicas across zones.
```

This is usually safer than hard zone-level anti-affinity.

### 15.4 Bare metal rack labels

```bash
oc label node worker-1 topology.example.com/rack=rack-1
oc label node worker-2 topology.example.com/rack=rack-2
oc label node worker-3 topology.example.com/rack=rack-3
```

Use:

```yaml
topologyKey: topology.example.com/rack
```

Validation:

```bash
oc get nodes -L topology.example.com/rack
```

## 17. Anti-affinity vs Topology Spread Constraints

Anti-affinity and topology spread constraints overlap but are not identical.

### 17.1 Anti-affinity

Anti-affinity says:

```text
Avoid or reject topology domains where matching pods already exist.
```

Example:

```text
Do not place two app=web pods on the same node.
```

### 17.2 Topology spread constraints

Topology spread constraints say:

```text
Keep the number of matching pods balanced across topology domains within maxSkew.
```

Example:

```text
Keep app=web pods evenly distributed across zones with maxSkew=1.
```

### 17.3 Comparison

| Requirement | Better Fit |
|---|---|
| Never place two replicas on same node | Hard pod anti-affinity |
| Prefer replicas apart but do not block scheduling | Soft pod anti-affinity |
| Evenly spread many replicas across zones | Topology spread constraints |
| Control skew precisely | Topology spread constraints |
| Avoid specific conflicting workload | Pod anti-affinity |
| Avoid noisy neighbors | Pod anti-affinity |
| Spread across node/rack/zone with HA balancing | Topology spread constraints or combination |

### 17.4 Example topology spread constraint

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app.kubernetes.io/name: payment-api
```

This means:

```text
Keep payment-api pods balanced across zones with skew no more than 1.
If that cannot be satisfied, do not schedule.
```

### 17.5 Practical recommendation

For most production stateless apps:

```text
Use topologySpreadConstraints for balanced zone/node spreading.
Use podAntiAffinity when you specifically need to avoid matching pods.
```

For critical small replica workloads:

```text
Hard node-level anti-affinity + soft zone-level spreading is a strong pattern.
```

## 18. Interaction with Resource Requests, Quotas, PDBs, HPA, and Cluster Autoscaler

### 18.1 Resource requests

Scheduler considers resource requests, not actual usage.

Example:

```yaml
resources:
  requests:
    cpu: 500m
    memory: 1Gi
```

If anti-affinity requires each replica on a separate node, every target node must have enough allocatable resources.

Troubleshoot:

```bash
oc describe node <node>
oc adm top nodes
oc adm top pods -A
```

### 18.2 ResourceQuota

Namespace quotas can block pod creation or updates before scheduling.

Check:

```bash
oc get resourcequota -n <namespace>
oc describe resourcequota -n <namespace>
```

### 18.3 LimitRange

LimitRange may inject default requests. This can change scheduling behavior.

Check:

```bash
oc get limitrange -n <namespace>
oc describe limitrange -n <namespace>
```

### 18.4 PodDisruptionBudget

PDB controls voluntary disruptions, not initial scheduling.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-api-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: payment-api
```

With anti-affinity, PDB becomes more effective because replicas are not concentrated on one node.

### 18.5 HPA

HPA can scale replicas beyond the number of eligible topology domains.

Example:

```text
Hard anti-affinity per node
Eligible nodes: 3
HPA maxReplicas: 10
Result: replicas 4-10 may become Pending
```

For HPA-driven workloads, prefer soft anti-affinity unless strict separation is mandatory.

### 18.6 Cluster Autoscaler

Anti-affinity can trigger scale-up if the cluster autoscaler can add eligible nodes. But autoscaling may not help if:

- node group max size is reached,
- new nodes lack required labels,
- taints are not tolerated,
- storage topology prevents binding,
- hard zone anti-affinity requires zones not available in the machine set,
- project/node selectors conflict.

Check MachineSets:

```bash
oc get machinesets -n openshift-machine-api
oc describe machineset -n openshift-machine-api <machineset>
```

Check cluster autoscaler logs if installed:

```bash
oc get pods -n openshift-machine-api
oc logs -n openshift-machine-api deployment/cluster-autoscaler-operator
```

## 21. Common Scheduling Event Messages

### 21.1 Pod anti-affinity conflict

Possible event:

```text
0/3 nodes are available: 3 node(s) didn't match pod anti-affinity rules.
```

Meaning:

```text
Every candidate node violates required pod anti-affinity.
```

Fix options:

- reduce replicas,
- add nodes,
- change hard rule to preferred,
- correct labels,
- change topology key,
- remove unintended matching pods,
- use topology spread constraints instead.

### 21.2 Insufficient resources

```text
0/3 nodes are available: 2 Insufficient memory, 1 node(s) didn't match pod anti-affinity rules.
```

Meaning:

```text
Scheduling is blocked by multiple filters.
```

Do not only focus on anti-affinity. Check resources too.

### 21.3 Taint conflict

```text
node(s) had taint {node-role.kubernetes.io/infra: }, that the pod didn't tolerate
```

Fix:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

Use only when the workload is allowed on those nodes.

### 21.4 Node selector / node affinity conflict

```text
node(s) didn't match Pod's node affinity/selector
```

Check:

```bash
oc get nodes --show-labels
oc get pod <pod> -n <ns> -o yaml
```

### 21.5 PVC / storage topology conflict

```text
pod has unbound immediate PersistentVolumeClaims
```

Or:

```text
volume node affinity conflict
```

Check:

```bash
oc get pvc -n <ns>
oc describe pvc -n <ns> <pvc>
oc describe pv <pv>
```

## 22. Performance and Scale Considerations

Inter-pod affinity and anti-affinity are more expensive than simple node selectors because the scheduler must evaluate existing pods and topology domains.

For very large clusters, avoid unnecessary hard pod anti-affinity on many high-replica workloads.

### 22.1 Why it can be expensive

For each pending pod, scheduler may need to evaluate:

```text
candidate nodes × existing pods × topology domains × selector rules
```

This can slow scheduling in large clusters.

### 22.2 Scale-safe recommendations

Use:

```yaml
preferredDuringSchedulingIgnoredDuringExecution
```

instead of hard rules where possible.

Prefer topology spread constraints when the goal is even distribution of many replicas.

Keep selectors narrow:

```yaml
app.kubernetes.io/name: payment-api
app.kubernetes.io/instance: payment-prod
```

Avoid broad selectors:

```yaml
app: web
```

Avoid cross-namespace all-pod matching unless required.

## 23. Security and Multi-tenancy Considerations

Anti-affinity is not a security boundary.

It is a scheduling preference/constraint. It does not replace:

- RBAC,
- SCC/Pod Security Admission,
- NetworkPolicy,
- namespace isolation,
- node taints,
- dedicated node pools,
- compliance controls.

### 23.1 Tenant isolation

For stronger tenant isolation, combine:

- dedicated node labels,
- taints/tolerations,
- node affinity,
- namespace governance,
- RBAC,
- ResourceQuota,
- NetworkPolicy.

Example:

```yaml
nodeAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    nodeSelectorTerms:
    - matchExpressions:
      - key: tenant
        operator: In
        values:
        - finance
```

With node taint:

```bash
oc adm taint nodes worker-finance-1 tenant=finance:NoSchedule
```

And toleration:

```yaml
tolerations:
- key: tenant
  operator: Equal
  value: finance
  effect: NoSchedule
```

Anti-affinity can complement this, but should not be the only isolation method.

## 24. Best Practices for 10+ Years Admins

### 24.1 Prefer soft anti-affinity for stateless apps

For normal stateless web/API workloads:

```yaml
preferredDuringSchedulingIgnoredDuringExecution
```

is usually safer than hard anti-affinity.

### 24.2 Use hard anti-affinity only with capacity planning

Before hard anti-affinity, confirm:

```text
replicas <= eligible topology domains
```

Example:

```text
3 replicas <= 3 worker nodes -> OK
5 replicas > 3 worker nodes -> Pending pods likely
```

### 24.3 Use stable, unique labels

Avoid generic labels.

Bad:

```yaml
app: web
```

Good:

```yaml
app.kubernetes.io/name: checkout-api
app.kubernetes.io/instance: checkout-prod
```

### 24.4 Use `kubernetes.io/hostname` for node separation

Most common:

```yaml
topologyKey: kubernetes.io/hostname
```

### 24.5 Be careful with hard zone-level anti-affinity

This can easily block scaling.

If you have 3 zones and 6 replicas, hard zone-level anti-affinity prevents more than 3 matching pods.

For zone spreading, often prefer:

```yaml
topologySpreadConstraints
```

or soft zone-level anti-affinity.

### 24.6 Combine hard node-level and soft zone-level rules

Strong practical pattern:

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        app.kubernetes.io/name: api
    topologyKey: kubernetes.io/hostname
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app.kubernetes.io/name: api
      topologyKey: topology.kubernetes.io/zone
```

### 24.7 Validate node labels before rollout

```bash
oc get nodes -L kubernetes.io/hostname,topology.kubernetes.io/zone
```

### 24.8 Avoid editing Operator-owned Deployments

Configure the Operator custom resource instead.

### 24.9 Treat anti-affinity as scheduling-time logic

It does not continuously evict running pods when labels change.

### 24.10 Document scheduling intent

Add annotations:

```yaml
metadata:
  annotations:
    scheduling.openshift.io/intent: "Spread payment-api replicas across nodes for HA"
```

This helps future admins understand why the rule exists.

## 25. Exam / Interview Notes

### 25.1 One-line definition

Pod anti-affinity prevents or discourages a pod from being scheduled in the same topology domain as other pods matching a label selector.

### 25.2 Important fields

```yaml
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      preferredDuringSchedulingIgnoredDuringExecution:
```

### 25.3 Hard vs soft

| Type | Field | Result |
|---|---|---|
| Hard | `requiredDuringSchedulingIgnoredDuringExecution` | Pod pending if not satisfied |
| Soft | `preferredDuringSchedulingIgnoredDuringExecution` | Scheduler tries, but may violate |

### 25.4 Most common topology key

```yaml
topologyKey: kubernetes.io/hostname
```

### 25.5 Common troubleshooting command

```bash
oc describe pod <pod> -n <namespace>
```

### 25.6 Common mistake

Replica count is greater than available eligible nodes while using hard anti-affinity.

Example:

```text
Deployment replicas: 5
Eligible nodes: 3
Hard anti-affinity on hostname
Result: 2 pods pending
```

### 25.7 Another common mistake

Selector matches the wrong pods because labels are too broad.

Bad:

```yaml
app: web
```

Better:

```yaml
app.kubernetes.io/name: payment-api
app.kubernetes.io/instance: prod
```

## 26. Hands-on Lab

### Goal

Deploy an application with anti-affinity and observe scheduling behavior.

### Step 1: Create namespace

```bash
oc new-project anti-affinity-lab
```

### Step 2: Create deployment with hard anti-affinity

Create `web-hard-aa.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-hard-aa
  namespace: anti-affinity-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-hard-aa
  template:
    metadata:
      labels:
        app: web-hard-aa
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: web-hard-aa
            topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: registry.access.redhat.com/ubi9/ubi-minimal:latest
        command: ["/bin/sh", "-c", "while true; do echo web-hard-aa; sleep 30; done"]
        resources:
          requests:
            cpu: 20m
            memory: 32Mi
          limits:
            cpu: 100m
            memory: 128Mi
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop: ["ALL"]
```

Apply:

```bash
oc apply -f web-hard-aa.yaml
```

### Step 3: Check placement

```bash
oc get pods -n anti-affinity-lab -o wide
```

### Step 4: Scale beyond nodes

```bash
oc scale deploy/web-hard-aa -n anti-affinity-lab --replicas=20
```

Check pending pods:

```bash
oc get pods -n anti-affinity-lab
oc describe pod -n anti-affinity-lab <pending-pod>
```

### Step 5: Convert to soft anti-affinity

Edit deployment:

```bash
oc edit deploy/web-hard-aa -n anti-affinity-lab
```

Change anti-affinity to:

```yaml
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: web-hard-aa
        topologyKey: kubernetes.io/hostname
```

Trigger rollout:

```bash
oc rollout restart deploy/web-hard-aa -n anti-affinity-lab
```

Observe:

```bash
oc get pods -n anti-affinity-lab -o wide
```

Now pods should schedule even if not perfectly spread.

### Step 6: Clean up

```bash
oc delete project anti-affinity-lab
```

## 27. Production Checklist

Before using anti-affinity in production, verify:

```text
[ ] Is the goal HA, performance isolation, tenant separation, or topology spreading?
[ ] Is pod anti-affinity the correct tool, or is topologySpreadConstraints better?
[ ] Are pod labels unique and stable?
[ ] Does the selector match only intended pods?
[ ] Is the topologyKey present on every eligible node?
[ ] Are enough eligible nodes/topology domains available?
[ ] Are resource requests realistic?
[ ] Are project node selectors or node affinity also restricting placement?
[ ] Are taints/tolerations compatible?
[ ] Does storage topology conflict with scheduling topology?
[ ] Will HPA scale above available topology domains?
[ ] Is the workload Operator-managed?
[ ] Is the rule hard only where truly required?
[ ] Have you tested node drain/reboot behavior?
[ ] Are PDBs configured for voluntary disruption protection?
```

## Final Admin Takeaway

For advanced OpenShift administration, anti-affinity should be treated as a **production scheduling policy**, not just YAML syntax.

Use it when you need pods to avoid each other based on labels and topology. Prefer soft rules for general spreading, use hard rules only for strict HA or failure-domain requirements, and always validate capacity, labels, storage topology, taints, node affinity, quotas, and HPA behavior before applying it to production workloads.
