# Required vs Preferred Affinity in OpenShift

**Topic:** Pod Scheduling and Workload Placement  
**Audience:** Advanced OpenShift Administration / Senior Kubernetes-OpenShift Engineer  
**Level:** 10+ years production administration perspective  
**Platform:** Red Hat OpenShift Container Platform 4.x / Kubernetes scheduling concepts

---

## 1. Executive Summary

In OpenShift, **affinity** is used to influence where Pods run. It is part of the Kubernetes scheduling model and is defined inside the Pod template, usually under a `Deployment`, `DeploymentConfig`, `StatefulSet`, `DaemonSet`, `Job`, or directly in a `Pod` spec.

The most important distinction is:

| Type | Meaning | Scheduler behavior | Risk |
|---|---|---|---|
| `requiredDuringSchedulingIgnoredDuringExecution` | Hard rule | Pod is scheduled only if the rule is satisfied | Pod can remain `Pending` if no node matches |
| `preferredDuringSchedulingIgnoredDuringExecution` | Soft rule | Scheduler tries to place the Pod on a better matching node, but can choose another node | Placement may not be exactly as expected |

For a senior OpenShift administrator, the practical rule is:

> Use **required affinity** only for non-negotiable placement requirements. Use **preferred affinity** for optimization, availability preference, performance preference, locality, and cost-aware scheduling.

---

## 2. What Affinity Solves

OpenShift clusters are usually not homogeneous. Nodes can differ by:

- CPU architecture
- CPU generation
- memory size
- disk type
- network zone
- availability zone
- worker / infra / storage role
- GPU availability
- compliance boundary
- application tier
- environment
- cost profile
- latency domain

Affinity lets you express placement intent such as:

- Run database Pods only on storage-optimized nodes.
- Prefer frontend Pods in the same zone as backend Pods.
- Keep replicas away from each other for high availability.
- Prefer cheaper nodes for batch workloads.
- Require GPU nodes for ML workloads.
- Avoid placing noisy workloads together.
- Keep monitoring or ingress workloads on infrastructure nodes.

## 3. Affinity Types in OpenShift

OpenShift supports Kubernetes affinity concepts:

```yaml
spec:
  affinity:
    nodeAffinity: {}
    podAffinity: {}
    podAntiAffinity: {}
```

### 3.1 Node Affinity

Node affinity places Pods based on **node labels**.

Example use cases:

- Place Pods only on nodes labeled `node-role.kubernetes.io/infra=`.
- Place Pods only in zone `topology.kubernetes.io/zone=zone-a`.
- Prefer SSD nodes using `disk=ssd`.
- Require Linux nodes using `kubernetes.io/os=linux`.

### 3.2 Pod Affinity

Pod affinity places Pods based on **other Pods already running** in a topology domain.

Example use cases:

- Place application Pods near cache Pods.
- Place frontend Pods in the same zone as backend Pods.
- Co-locate sidecar-like helper workloads with a main workload.

### 3.3 Pod Anti-Affinity

Pod anti-affinity prevents or discourages Pods from running near other matching Pods.

Example use cases:

- Spread replicas across nodes.
- Avoid placing multiple database replicas on the same node.
- Prevent noisy workloads from sharing a node.
- Separate critical application tiers.

## 4. Required vs Preferred: Core Difference

### 4.1 Required Affinity

Required affinity is a **hard scheduling constraint**.

```yaml
requiredDuringSchedulingIgnoredDuringExecution:
```

Meaning:

- The scheduler must satisfy this rule.
- Nodes that do not match are removed from the candidate list.
- If no node matches, the Pod remains `Pending`.
- Required rules are evaluated during scheduling.
- `IgnoredDuringExecution` means the Pod is not evicted automatically if labels change after scheduling.

Use required affinity when placement is mandatory.

Examples:

- GPU workload must run on GPU nodes.
- Application must run only in a compliance-approved zone.
- Storage workload must run only on storage nodes.
- Infrastructure workload must run only on infra nodes.
- Workload requires a specific CPU architecture.

### 4.2 Preferred Affinity

Preferred affinity is a **soft scheduling preference**.

```yaml
preferredDuringSchedulingIgnoredDuringExecution:
```

Meaning:

- The scheduler tries to satisfy the rule.
- Matching nodes receive a higher scheduling score.
- If no preferred node is available, the Pod can still run elsewhere.
- Preferred rules are useful for optimization, not enforcement.
- Each preferred term has a `weight` from `1` to `100`.

Use preferred affinity when placement is desirable but not mandatory.

Examples:

- Prefer same zone for lower latency.
- Prefer SSD nodes, but allow HDD nodes if needed.
- Prefer spreading replicas across nodes.
- Prefer spot / lower-cost nodes for non-critical workloads.
- Prefer app Pods near cache Pods but do not block deployment.

## 5. Scheduling Flow: How the Scheduler Thinks

A simplified scheduling flow looks like this:

```text
1. Pod is created
2. Scheduler checks unscheduled Pod
3. Scheduler filters nodes using hard constraints
   - nodeSelector
   - required node affinity
   - required pod affinity
   - required pod anti-affinity
   - taints not tolerated
   - resource availability
   - volume constraints
   - node readiness
4. Scheduler scores remaining nodes
   - preferred affinity
   - resource scoring
   - image locality
   - topology spread
   - other scheduler plugins
5. Highest scoring suitable node is selected
6. Pod is bound to the node
7. Kubelet starts containers
```

Important production interpretation:

> Required affinity decides **which nodes are eligible**. Preferred affinity decides **which eligible node is better**.

---

## 6. Meaning of `IgnoredDuringExecution`

Both required and preferred affinity use this suffix:

```text
DuringSchedulingIgnoredDuringExecution
```

This means:

- The rule is evaluated when the scheduler places the Pod.
- After the Pod is already running, the rule is not continuously enforced.
- If a node label changes later and the Pod no longer matches the affinity rule, the Pod continues running.
- The scheduler does not automatically evict the Pod only because affinity is no longer satisfied.

Example:

1. Node has label `disk=ssd`.
2. Pod with required node affinity for `disk=ssd` is scheduled there.
3. Admin removes label `disk=ssd` from the node.
4. Existing Pod keeps running.
5. New Pods with the same required affinity cannot schedule on that node anymore.

Operational impact:

- Affinity is not a runtime compliance enforcement tool.
- Use admission policies, MachineConfig, taints, node lifecycle controls, and operational governance if runtime enforcement is required.

## 7. Node Affinity: Required Example

### 7.1 Label a Node

```bash
oc get nodes --show-labels

oc label node worker01.example.com workload=db
oc label node worker01.example.com disk=ssd
oc label node worker01.example.com topology.kubernetes.io/zone=zone-a --overwrite
```

Verify:

```bash
oc get node worker01.example.com --show-labels
```

### 7.2 Deployment With Required Node Affinity

This Deployment can run only on nodes with `workload=db` and `disk=ssd`.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mysql-required-affinity
  namespace: database
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mysql-required-affinity
  template:
    metadata:
      labels:
        app: mysql-required-affinity
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: workload
                operator: In
                values:
                - db
              - key: disk
                operator: In
                values:
                - ssd
      containers:
      - name: mysql
        image: registry.redhat.io/rhel8/mysql-80
        env:
        - name: MYSQL_ROOT_PASSWORD
          value: redhat
        - name: MYSQL_DATABASE
          value: appdb
        ports:
        - containerPort: 3306
```

Apply:

```bash
oc new-project database
oc apply -f mysql-required-affinity.yaml
oc get pods -n database -o wide
```

If no node has both labels, the Pod remains `Pending`.

Check why:

```bash
oc describe pod -n database -l app=mysql-required-affinity
```

Typical event:

```text
0/5 nodes are available: 5 node(s) didn't match Pod's node affinity/selector.
```

## 8. Node Affinity: Preferred Example

This Deployment prefers SSD nodes but can run elsewhere if SSD nodes are unavailable.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-preferred-affinity
  namespace: apps
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx-preferred-affinity
  template:
    metadata:
      labels:
        app: nginx-preferred-affinity
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 80
            preference:
              matchExpressions:
              - key: disk
                operator: In
                values:
                - ssd
          - weight: 20
            preference:
              matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                - zone-a
      containers:
      - name: nginx
        image: registry.k8s.io/nginx
        ports:
        - containerPort: 80
```

Explanation:

- Nodes with `disk=ssd` receive a strong preference score.
- Nodes in `zone-a` receive an additional smaller preference score.
- A node matching both preferences is usually favored over a node matching only one.
- A node matching neither can still be selected if it is otherwise the best or only feasible node.

## 9. Combining Required and Preferred Node Affinity

This is one of the most useful production patterns.

Example requirement:

- Must run on Linux worker nodes.
- Must run only in approved zones.
- Prefer SSD nodes.
- Prefer zone-a over zone-b.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payment
spec:
  replicas: 4
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
        tier: backend
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: kubernetes.io/os
                operator: In
                values:
                - linux
              - key: node-role.kubernetes.io/worker
                operator: Exists
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                - zone-a
                - zone-b
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 70
            preference:
              matchExpressions:
              - key: disk
                operator: In
                values:
                - ssd
          - weight: 30
            preference:
              matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                - zone-a
      containers:
      - name: payment-api
        image: quay.io/example/payment-api:1.0
        ports:
        - containerPort: 8080
```

Production interpretation:

- If a node is not Linux, it is rejected.
- If a node is not a worker, it is rejected.
- If a node is not in zone-a or zone-b, it is rejected.
- Among remaining nodes, SSD nodes are preferred.
- Among remaining nodes, zone-a is preferred.
- If no SSD node exists, the Pod can still run on non-SSD nodes in approved zones.

## 10. Required Node Affinity Logic: OR and AND

This is very important for troubleshooting.

### 10.1 Multiple `nodeSelectorTerms` Are ORed

```yaml
requiredDuringSchedulingIgnoredDuringExecution:
  nodeSelectorTerms:
  - matchExpressions:
    - key: disk
      operator: In
      values:
      - ssd
  - matchExpressions:
    - key: workload
      operator: In
      values:
      - db
```

Meaning:

```text
Node is eligible if:
  disk=ssd
OR
  workload=db
```

### 10.2 Multiple `matchExpressions` in One Term Are ANDed

```yaml
requiredDuringSchedulingIgnoredDuringExecution:
  nodeSelectorTerms:
  - matchExpressions:
    - key: disk
      operator: In
      values:
      - ssd
    - key: workload
      operator: In
      values:
      - db
```

Meaning:

```text
Node is eligible if:
  disk=ssd
AND
  workload=db
```

### 10.3 Common Mistake

Admins often accidentally create OR logic when they wanted AND logic.

Wrong if you need both labels:

```yaml
nodeSelectorTerms:
- matchExpressions:
  - key: disk
    operator: In
    values: ["ssd"]
- matchExpressions:
  - key: workload
    operator: In
    values: ["db"]
```

Correct if you need both labels:

```yaml
nodeSelectorTerms:
- matchExpressions:
  - key: disk
    operator: In
    values: ["ssd"]
  - key: workload
    operator: In
    values: ["db"]
```

## 11. Node Affinity Operators

Node affinity supports these operators:

| Operator | Meaning | Example |
|---|---|---|
| `In` | Node label value must be in given list | `disk In [ssd]` |
| `NotIn` | Node label value must not be in given list | `workload NotIn [gpu]` |
| `Exists` | Node must have the key | `node-role.kubernetes.io/worker Exists` |
| `DoesNotExist` | Node must not have the key | `dedicated DoesNotExist` |
| `Gt` | Node label value must be greater than value | `cpu-count Gt 16` |
| `Lt` | Node label value must be less than value | `cpu-count Lt 64` |

Example using `Exists`:

```yaml
- key: node-role.kubernetes.io/infra
  operator: Exists
```

Example using `NotIn`:

```yaml
- key: workload
  operator: NotIn
  values:
  - noisy
  - batch
```

Important:

- `Gt` and `Lt` require integer-like label values.
- `Exists` and `DoesNotExist` do not require `values`.
- `NotIn` and `DoesNotExist` can be used to create node anti-affinity-like behavior.

## 12. Preferred Affinity Weights

Preferred node affinity uses weight:

```yaml
preferredDuringSchedulingIgnoredDuringExecution:
- weight: 100
  preference:
    matchExpressions:
    - key: disk
      operator: In
      values:
      - ssd
```

Rules:

- Weight must be between `1` and `100`.
- Higher weight means stronger preference.
- The scheduler adds the weight of each matched preferred rule to the node score.
- The final scheduling decision also includes other scheduler scoring logic, not only affinity.

Example:

```yaml
preferredDuringSchedulingIgnoredDuringExecution:
- weight: 100
  preference:
    matchExpressions:
    - key: workload-tier
      operator: In
      values:
      - premium
- weight: 20
  preference:
    matchExpressions:
    - key: topology.kubernetes.io/zone
      operator: In
      values:
      - zone-a
```

Interpretation:

- `workload-tier=premium` is much more important than `zone-a`.
- A node matching both gets more score.
- A node matching only `zone-a` gets a small score boost.

## 13. Pod Affinity: Required Example

Pod affinity is based on existing Pods, not node labels.

Example requirement:

> Schedule `frontend` Pods only in a zone where a `cache` Pod is already running.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: app-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
        tier: frontend
    spec:
      affinity:
        podAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - cache
            topologyKey: topology.kubernetes.io/zone
      containers:
      - name: frontend
        image: quay.io/example/frontend:1.0
        ports:
        - containerPort: 8080
```

Meaning:

- For a node to be eligible, its zone must already contain at least one Pod with `app=cache`.
- If no cache Pod exists in any zone, the frontend Pod can remain `Pending`.

Production caution:

- Required pod affinity can create scheduling deadlocks if not designed carefully.
- It depends on current Pods and labels.
- It is more expensive for the scheduler than node affinity.
- Use it carefully in large clusters.

## 14. Pod Affinity: Preferred Example

Example requirement:

> Prefer to run frontend Pods in the same zone as cache Pods, but do not block frontend deployment if cache Pods are temporarily unavailable.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-prefer-cache
  namespace: app-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: frontend-prefer-cache
  template:
    metadata:
      labels:
        app: frontend-prefer-cache
        tier: frontend
    spec:
      affinity:
        podAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 80
            podAffinityTerm:
              labelSelector:
                matchExpressions:
                - key: app
                  operator: In
                  values:
                  - cache
              topologyKey: topology.kubernetes.io/zone
      containers:
      - name: frontend
        image: quay.io/example/frontend:1.0
        ports:
        - containerPort: 8080
```

Meaning:

- Prefer zones where `app=cache` Pods already exist.
- If no such zone exists, the Pod can still be scheduled elsewhere.

This is usually safer than required pod affinity for production applications.

## 15. Pod Anti-Affinity: Required Example

Example requirement:

> Never place two replicas of the same application on the same node.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: critical-api
  namespace: prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: critical-api
  template:
    metadata:
      labels:
        app: critical-api
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - critical-api
            topologyKey: kubernetes.io/hostname
      containers:
      - name: critical-api
        image: quay.io/example/critical-api:1.0
        ports:
        - containerPort: 8443
```

Meaning:

- The scheduler cannot place two `app=critical-api` Pods on the same node.
- `topologyKey: kubernetes.io/hostname` means node-level separation.
- If you request 3 replicas but only 2 eligible nodes exist, the third Pod remains `Pending`.

This is strong high-availability behavior, but it can reduce scheduling flexibility.

## 16. Pod Anti-Affinity: Preferred Example

Example requirement:

> Try to spread replicas across nodes, but allow multiple replicas on the same node if capacity is limited.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-soft-spread
  namespace: prod
spec:
  replicas: 5
  selector:
    matchLabels:
      app: web-soft-spread
  template:
    metadata:
      labels:
        app: web-soft-spread
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchExpressions:
                - key: app
                  operator: In
                  values:
                  - web-soft-spread
              topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: registry.k8s.io/nginx
        ports:
        - containerPort: 80
```

Meaning:

- Scheduler strongly prefers not to place replicas on the same node.
- If there are fewer nodes than replicas, scheduling still succeeds.
- This is often better than required anti-affinity for normal web apps.

## 17. Topology Key Explained

`topologyKey` defines the domain where pod affinity or anti-affinity applies.

Common topology keys:

| Topology key | Domain |
|---|---|
| `kubernetes.io/hostname` | Node |
| `topology.kubernetes.io/zone` | Availability zone |
| `topology.kubernetes.io/region` | Region |
| Custom label such as `rack` | Rack or custom failure domain |

Example:

```yaml
topologyKey: kubernetes.io/hostname
```

Means:

- Apply rule at node level.
- Useful for spreading replicas across nodes.

Example:

```yaml
topologyKey: topology.kubernetes.io/zone
```

Means:

- Apply rule at zone level.
- Useful for zone-aware placement.

Production caution:

- Every node should be consistently labeled with the topology key.
- Missing topology labels can cause unexpected scheduling behavior.
- Do not use random or inconsistent labels as topology keys.

## 18. Required vs Preferred Decision Matrix

| Requirement | Use required? | Use preferred? | Reason |
|---|---:|---:|---|
| GPU workload must run on GPU node | Yes | No | Non-GPU node cannot run workload correctly |
| Database must run on encrypted-storage nodes | Yes | Maybe | Compliance/storage requirement is mandatory |
| Web Pods should spread across nodes | Usually no | Yes | Better availability but avoid Pending Pods |
| Critical replicas must never share same node | Yes | Maybe | Strong HA requirement |
| Prefer same zone as database for latency | No | Yes | Latency optimization should not block startup |
| Keep workloads away from noisy batch Pods | Maybe | Yes | Depends on severity |
| Infra components must run only on infra nodes | Yes | Maybe | Dedicated infrastructure boundary |
| Prefer SSD but allow fallback | No | Yes | Availability is more important than ideal disk |
| Legal/compliance zone restriction | Yes | No | Mandatory boundary |
| Cost optimization to prefer cheaper nodes | No | Yes | Cost should not break scheduling unless policy demands it |

## 19. Required Affinity Failure Scenarios

### 19.1 No Matching Node Labels

Problem:

```text
Pod remains Pending
```

Check:

```bash
oc describe pod <pod-name> -n <namespace>
oc get nodes --show-labels
```

Fix:

```bash
oc label node <node-name> workload=db disk=ssd --overwrite
```

Or update the workload affinity.

### 19.2 Wrong Label Key

Common mistake:

```yaml
key: topology.kubernetes.io/zones
```

Correct:

```yaml
key: topology.kubernetes.io/zone
```

Check actual labels:

```bash
oc get nodes -L topology.kubernetes.io/zone
```

### 19.3 Required Anti-Affinity Too Strict

Example:

- Deployment has 5 replicas.
- Required pod anti-affinity says one replica per node.
- Only 3 eligible nodes exist.

Result:

- 3 Pods run.
- 2 Pods remain `Pending`.

Fix options:

- Add more eligible nodes.
- Change required anti-affinity to preferred anti-affinity.
- Use topology spread constraints with controlled skew.
- Reduce replicas.

### 19.4 Combining Node Selector and Node Affinity Incorrectly

If both `nodeSelector` and `nodeAffinity` exist, both must match.

Example:

```yaml
nodeSelector:
  workload: frontend

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: workload
          operator: In
          values:
          - db
```

Meaning:

```text
workload=frontend AND workload=db
```

Unless a node has both labels, the Pod cannot schedule.

## 21. Patching Existing Deployments

You cannot directly modify affinity on an already scheduled standalone Pod and expect it to be rescheduled automatically. For controller-managed workloads, patch the Pod template and let the controller create new Pods.

### 21.1 Patch Deployment With Required Node Affinity

```bash
oc patch deployment nginx -n apps --type='merge' -p '
{
  "spec": {
    "template": {
      "spec": {
        "affinity": {
          "nodeAffinity": {
            "requiredDuringSchedulingIgnoredDuringExecution": {
              "nodeSelectorTerms": [
                {
                  "matchExpressions": [
                    {
                      "key": "disk",
                      "operator": "In",
                      "values": ["ssd"]
                    }
                  ]
                }
              ]
            }
          }
        }
      }
    }
  }
}'
```

Restart rollout if needed:

```bash
oc rollout restart deployment/nginx -n apps
oc rollout status deployment/nginx -n apps
oc get pods -n apps -o wide
```

### 21.2 Remove Affinity From Deployment

```bash
oc patch deployment nginx -n apps --type='json' -p '[
  {
    "op": "remove",
    "path": "/spec/template/spec/affinity"
  }
]'
```

## 22. Affinity vs `nodeSelector`

`nodeSelector` is simpler but less expressive.

Example:

```yaml
nodeSelector:
  disk: ssd
```

Equivalent simple required node affinity:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: disk
          operator: In
          values:
          - ssd
```

Use `nodeSelector` when:

- You need simple exact-match labels.
- The rule is basic.
- You want readability.

Use node affinity when:

- You need `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, or `Lt`.
- You need OR logic.
- You need preferred/soft rules.
- You need multiple weighted preferences.

Important:

> If both `nodeSelector` and `nodeAffinity` are configured, both must be satisfied.

## 23. Affinity vs Taints and Tolerations

Affinity attracts Pods to nodes. Taints repel Pods from nodes.

| Feature | Purpose | Direction |
|---|---|---|
| Node affinity | Pod chooses suitable nodes | Pod -> Node |
| Pod affinity | Pod chooses nodes near other Pods | Pod -> Pod topology |
| Pod anti-affinity | Pod avoids nodes near other Pods | Pod -> Pod topology |
| Taint | Node rejects Pods without toleration | Node -> Pod |
| Toleration | Pod is allowed onto tainted node | Pod -> Node permission |

Production pattern for dedicated nodes:

1. Label dedicated nodes.
2. Taint dedicated nodes.
3. Add required node affinity to intended workloads.
4. Add toleration to intended workloads.

Example:

```bash
oc label node worker-infra01 node-role.kubernetes.io/infra= infra=true
oc adm taint nodes worker-infra01 dedicated=infra:NoSchedule
```

Workload:

```yaml
spec:
  template:
    spec:
      tolerations:
      - key: dedicated
        operator: Equal
        value: infra
        effect: NoSchedule
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: infra
                operator: In
                values:
                - "true"
```

Why both?

- Taint prevents unwanted workloads from landing on infra nodes.
- Affinity ensures intended workloads actually target infra nodes.

## 24. Affinity vs Topology Spread Constraints

For spreading replicas evenly, pod anti-affinity is not always the best tool.

Use pod anti-affinity when:

- You want to avoid co-location with specific Pods.
- You want simple one-per-node behavior.
- You need hard separation.

Use topology spread constraints when:

- You want balanced distribution across nodes, zones, racks, or regions.
- You want controlled skew.
- You want better scheduling behavior for large replica sets.
- You want to avoid overly strict anti-affinity.

Example topology spread:

```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app: web
```

Meaning:

- Try to keep web Pods balanced across nodes.
- `ScheduleAnyway` behaves like a soft preference.

Hard spread example:

```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: web
```

Meaning:

- Do not schedule if it breaks zone skew beyond the configured limit.

## 25. OpenShift-Specific Operational Notes

### 25.1 Node Labels Are Cluster-Level Controls

Node labels affect scheduling cluster-wide. Be careful when changing labels on production nodes.

Check labels first:

```bash
oc get nodes --show-labels
```

Add or overwrite labels:

```bash
oc label node <node-name> key=value --overwrite
```

Remove labels:

```bash
oc label node <node-name> key-
```

### 25.2 Infrastructure Nodes

For infra workloads, a common pattern is:

```bash
oc label node <node-name> node-role.kubernetes.io/infra=
oc label node <node-name> infra=true
```

Then use:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: node-role.kubernetes.io/infra
          operator: Exists
```

In production, combine with taints and tolerations to keep application workloads away from infra nodes.

### 25.3 Project-Level Node Selectors

OpenShift can also use project-level node selectors. If a namespace has a node selector annotation, it can combine with Pod placement rules and make scheduling stricter.

Check namespace annotations:

```bash
oc get namespace <namespace> -o yaml
```

Look for:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: key=value
```

If a Pod is unexpectedly `Pending`, check:

- Pod `nodeSelector`
- Pod node affinity
- Namespace/project node selector
- Taints and tolerations
- Resource requests
- PVC zone or storage topology

### 25.4 Scheduler Profiles

OpenShift exposes scheduler profile configuration through the cluster `Scheduler` object.

Check:

```bash
oc get scheduler cluster -o yaml
```

Edit:

```bash
oc edit scheduler cluster
```

Common profile values include:

```yaml
spec:
  profile: LowNodeUtilization
```

or:

```yaml
spec:
  profile: HighNodeUtilization
```

Affinity is still part of the workload specification, but scheduler profile scoring can influence which candidate node wins after required constraints are satisfied.

## 26. Production Design Patterns

### 26.1 Mandatory Dedicated Node Placement

Use for:

- infra workloads
- ingress routers
- logging
- monitoring
- storage services
- GPU workloads

Pattern:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: infra
  effect: NoSchedule
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: node-role.kubernetes.io/infra
          operator: Exists
```

### 26.2 Soft High Availability for Web Apps

Use preferred anti-affinity:

```yaml
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: web
        topologyKey: kubernetes.io/hostname
```

Why:

- Reduces chance of all replicas on one node.
- Avoids unnecessary Pending Pods during node shortage.

### 26.3 Strict High Availability for Critical Apps

Use required anti-affinity:

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: critical-db
      topologyKey: kubernetes.io/hostname
```

Use only when:

- You have enough eligible nodes.
- Pending replicas are preferable to unsafe co-location.
- Operational team understands scaling impact.

### 26.4 Latency-Aware Placement

Use preferred pod affinity:

```yaml
affinity:
  podAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 70
      podAffinityTerm:
        labelSelector:
          matchLabels:
            app: redis
        topologyKey: topology.kubernetes.io/zone
```

Why:

- Improves locality.
- Does not block application startup.

### 26.5 Compliance Zone Restriction

Use required node affinity:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: compliance-zone
          operator: In
          values:
          - pci
```

Why:

- Compliance restrictions are hard boundaries.
- Preferred affinity is not enough for compliance.

## 27. Anti-Patterns

### 27.1 Using Required Affinity Everywhere

Bad practice:

```yaml
requiredDuringSchedulingIgnoredDuringExecution:
```

for every minor preference.

Impact:

- Pods remain Pending during node pressure.
- Cluster autoscaler behavior can become harder to predict.
- Upgrades and maintenance become more fragile.
- Workload availability suffers.

Better:

- Use required only for hard requirements.
- Use preferred for normal placement intent.

### 27.2 Overusing Required Pod Anti-Affinity

Bad for large clusters and large replica sets.

Impact:

- Slower scheduling.
- Pending Pods if node count is insufficient.
- More complex troubleshooting.

Better:

- Use preferred pod anti-affinity for soft spreading.
- Use topology spread constraints for controlled distribution.

### 27.3 Inconsistent Topology Labels

Bad:

- Some nodes have `topology.kubernetes.io/zone`.
- Some nodes do not.

Impact:

- Pod affinity/anti-affinity can behave unexpectedly.

Better:

```bash
oc get nodes -L topology.kubernetes.io/zone,kubernetes.io/hostname
```

Ensure all nodes have expected topology labels.

### 27.4 Confusing Security With Scheduling

Affinity is not a security boundary.

Bad assumption:

> If I schedule app A away from app B, security is guaranteed.

Better controls:

- NetworkPolicy
- SCC / Pod Security Admission
- RBAC
- namespace isolation
- image policy
- secrets management
- node isolation with taints and dedicated nodes
- compliance monitoring

## 28. Real-World Troubleshooting Case Studies

### Case 1: Pod Pending After Adding Required Node Affinity

Symptom:

```bash
oc get pods -n payment
```

```text
payment-api-xxx   0/1   Pending
```

Event:

```text
0/6 nodes are available: 6 node(s) didn't match Pod's node affinity/selector.
```

Investigation:

```bash
oc get deploy payment-api -n payment -o yaml | grep -A30 affinity
oc get nodes -L workload,disk,topology.kubernetes.io/zone
```

Root cause:

```yaml
values:
- ssd
```

but actual label is:

```text
disk=nvme
```

Fix options:

```bash
oc label node worker01 disk=ssd --overwrite
```

or update YAML:

```yaml
values:
- ssd
- nvme
```

### Case 2: Required Pod Anti-Affinity Blocks Scaling

Symptom:

- Deployment replicas increased from 3 to 6.
- Only 3 worker nodes available.
- 3 Pods remain Pending.

Affinity:

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        app: web
    topologyKey: kubernetes.io/hostname
```

Root cause:

- Hard one-Pod-per-node rule.
- Not enough nodes.

Fix options:

- Add nodes.
- Change to preferred anti-affinity.
- Use topology spread constraints.

Recommended general web app fix:

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app: web
      topologyKey: kubernetes.io/hostname
```

### Case 3: Preferred Affinity Not Followed

Symptom:

- Pod preferred `disk=ssd`.
- Pod scheduled on `disk=hdd`.

Possible reasons:

- SSD nodes lacked CPU or memory.
- SSD nodes had taints not tolerated.
- SSD nodes were NotReady.
- PVC topology prevented scheduling there.
- Other scheduler scores made another node better.
- Preferred affinity is not mandatory.

Check:

```bash
oc describe pod <pod> -n <namespace>
oc describe node <ssd-node>
oc get nodes -L disk
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Resolution:

- If SSD is mandatory, use required node affinity.
- If SSD is only preferred, accept fallback behavior.
- Adjust resource requests or taints/tolerations.

## 30. Senior Admin Checklist

Before applying required affinity in production, ask:

- How many nodes match this rule today?
- How many nodes will match after maintenance or upgrade?
- Does autoscaling know how to create nodes with these labels?
- Are labels managed manually or by MachineSets/MachineConfig?
- Does storage topology conflict with the rule?
- Do taints require matching tolerations?
- Does namespace node selector add another hidden constraint?
- Could this block disaster recovery?
- Is this a compliance requirement or only a preference?
- Is topology spread a better choice?

Before applying preferred affinity, ask:

- Is fallback acceptable?
- Are weights meaningful?
- Are multiple preferences conflicting?
- Will operators understand that preferred rules are not guaranteed?
- Is the rule observable and documented?

## 31. Exam and Interview Points

### 31.1 Key Definitions

- Required affinity is hard scheduling enforcement.
- Preferred affinity is soft scheduling preference.
- Required rules can make Pods Pending.
- Preferred rules affect scoring, not eligibility.
- `IgnoredDuringExecution` means running Pods are not evicted if labels change.
- Node affinity uses node labels.
- Pod affinity and anti-affinity use labels on existing Pods and a topology key.
- Multiple required node selector terms are ORed.
- Multiple match expressions inside one term are ANDed.
- Preferred weights range from 1 to 100.

### 31.2 Common Practical Questions

**Question:** A Pod has required node affinity for `disk=ssd`, but no node has that label. What happens?  
**Answer:** The Pod remains Pending.

**Question:** A Pod has preferred node affinity for `disk=ssd`, but no SSD node is available. What happens?  
**Answer:** The Pod can still be scheduled on another eligible node.

**Question:** What does `IgnoredDuringExecution` mean?  
**Answer:** The rule is not enforced after the Pod is already running; label changes do not automatically evict the Pod.

**Question:** If both `nodeSelector` and node affinity are configured, what happens?  
**Answer:** Both must be satisfied.

**Question:** What is the difference between pod affinity and node affinity?  
**Answer:** Node affinity uses node labels. Pod affinity uses labels of existing Pods within a topology domain.

**Question:** Why can required pod anti-affinity be dangerous?  
**Answer:** It can block scheduling if there are not enough eligible topology domains, such as nodes or zones.

## 32. Recommended Production Defaults

For most OpenShift environments:

1. Use **required node affinity** for mandatory hardware, role, compliance, or isolation needs.
2. Use **preferred node affinity** for optimization and cost/performance preferences.
3. Use **preferred pod anti-affinity** for normal replica spreading.
4. Use **required pod anti-affinity** only for critical workloads where co-location is unacceptable.
5. Use **topology spread constraints** for even distribution across zones or nodes.
6. Combine **taints/tolerations + node affinity** for dedicated nodes.
7. Keep topology labels consistent on all nodes.
8. Document every required affinity rule because it can directly affect availability.

## 34. Final Summary

Required and preferred affinity are both powerful, but they solve different problems.

Use required affinity when the workload **must not run** unless the rule is satisfied. Use preferred affinity when the workload **should ideally run** in a certain place but availability is more important than perfect placement.

In production OpenShift administration, the safest design is usually:

```text
Hard constraints: required affinity + taints/tolerations
Soft optimization: preferred affinity + topology spread constraints
Troubleshooting: oc describe pod + oc get nodes --show-labels + oc get events
```

A mature OpenShift administrator does not only ask, “Can I place this Pod there?”  
A mature administrator asks:

> “What happens during node failure, upgrade, autoscaling, storage topology conflict, and disaster recovery if this affinity rule becomes impossible to satisfy?”

That question is the difference between basic scheduling knowledge and production-grade OpenShift workload placement.
