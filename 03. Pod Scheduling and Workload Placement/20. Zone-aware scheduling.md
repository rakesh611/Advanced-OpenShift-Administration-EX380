# Zone-aware Scheduling in OpenShift

**Topic area:** Pod Scheduling and Workload Placement  
**Audience:** Advanced OpenShift Administration / senior Linux-Kubernetes-OpenShift administrators  
**Experience level:** Production-focused, suitable for engineers with around 10 years of infrastructure, Linux, DevOps, and platform administration experience  
**Platform focus:** Red Hat OpenShift Container Platform 4.x, Kubernetes scheduler behavior, multi-zone and failure-domain-aware workload placement

---

## 1. Executive Summary

**Zone-aware scheduling** means placing application pods intelligently across different failure domains, usually availability zones, racks, rooms, datacenters, or custom infrastructure zones, so that a single node, rack, or zone failure does not take down the whole application.

In OpenShift, zone-aware scheduling is not a single object called `ZoneAwareScheduling`. It is a design pattern implemented by combining Kubernetes and OpenShift scheduling features:

- Node topology labels such as `topology.kubernetes.io/zone`
- `topologySpreadConstraints`
- Pod anti-affinity
- Node affinity
- Taints and tolerations
- Storage topology and `WaitForFirstConsumer`
- PodDisruptionBudget
- HPA / scaling behavior
- Descheduler profiles for rebalancing after cluster changes
- Correct node and MachineSet labeling

The main production goal is simple:

> Keep enough replicas running in independent failure domains so the application remains available when one node or one zone fails.

For an advanced OpenShift administrator, zone-aware scheduling is part of high availability engineering, not just YAML configuration. You must understand how the scheduler filters nodes, scores nodes, calculates skew, respects labels, interacts with storage, and behaves during scaling, upgrades, zone failure, and node replacement.

---

## 2. Why Zone-aware Scheduling Matters

Without zone-aware placement, a Deployment with three replicas might accidentally place all pods in the same zone or even the same worker node if capacity and scoring allow it. That creates hidden risk:

- Node failure can remove multiple replicas.
- Rack failure can remove all replicas.
- Cloud availability zone failure can make the service unavailable.
- Rolling updates can temporarily reduce availability.
- Cluster autoscaling can create uneven placement.
- Storage-backed applications can become stuck if PVCs are bound to one zone but pods are scheduled to another.

Zone-aware scheduling is important for:

- HA web applications
- API gateways
- ingress/router workloads
- monitoring stacks
- databases with replicas
- message brokers
- stateful applications
- critical internal services
- multi-zone cloud OpenShift clusters
- on-premises clusters with rack/room/datacenter separation
- edge environments where sites or zones have unstable connectivity

## 3. Important Terminology

| Term | Meaning |
|---|---|
| Node | A worker or control-plane machine where pods can run. |
| Zone | A failure domain such as `us-east-1a`, `az-1`, `rack-a`, or `dc1-room2`. |
| Region | A larger failure domain that can contain multiple zones. |
| Topology domain | A group of nodes with the same value for a topology label. |
| Topology key | The node label key used to define topology domains, for example `topology.kubernetes.io/zone`. |
| Skew | The difference in number of matching pods between topology domains. |
| maxSkew | Maximum allowed imbalance between domains. |
| Hard constraint | A rule that must be satisfied, usually `DoNotSchedule`. |
| Soft constraint | A preference that scheduler tries to honor, usually `ScheduleAnyway` or preferred affinity. |
| Failure domain | Infrastructure boundary where failure can affect multiple components at once. |
| Placement | The final node selected for a pod. |

## 4. OpenShift Scheduler Placement Flow

When a new pod is created, the OpenShift default scheduler follows the Kubernetes scheduling framework. At a high level:

1. The scheduler watches for unscheduled pods.
2. It filters nodes that cannot run the pod.
3. It scores eligible nodes.
4. It selects the best node.
5. It binds the pod to that node.

For zone-aware scheduling, the important part is that topology constraints participate in node filtering and scoring.

### 4.1 Filtering Phase

A node can be rejected because of:

- insufficient CPU or memory requests
- node selector mismatch
- node affinity mismatch
- taint not tolerated
- required pod anti-affinity conflict
- required topology spread constraint violation
- volume topology mismatch
- node not ready
- unschedulable node
- security or admission constraints

### 4.2 Scoring Phase

If more than one node is eligible, the scheduler scores them. Soft rules influence scoring:

- preferred node affinity
- preferred pod affinity / anti-affinity
- `topologySpreadConstraints` with `whenUnsatisfiable: ScheduleAnyway`
- resource scoring
- image locality
- balanced allocation

### 4.3 Binding Phase

After a node is selected, the scheduler creates a binding between pod and node. After binding, most scheduling rules are not continuously enforced. For example, if labels later change, already-running pods normally continue running unless something like the descheduler evicts them.

## 5. How OpenShift Knows About Zones

OpenShift uses Kubernetes node labels to understand topology. In cloud installations, labels are often added automatically by the installer, cloud provider integration, Machine API, or node lifecycle components.

Common topology labels:

```bash
topology.kubernetes.io/region
topology.kubernetes.io/zone
kubernetes.io/hostname
```

Example:

```bash
oc get nodes -L topology.kubernetes.io/region,topology.kubernetes.io/zone,kubernetes.io/hostname
```

Example output:

```text
NAME       STATUS   ROLES    REGION      ZONE        HOSTNAME
worker-1   Ready    worker   us-east-1   us-east-1a   worker-1
worker-2   Ready    worker   us-east-1   us-east-1b   worker-2
worker-3   Ready    worker   us-east-1   us-east-1c   worker-3
```

On bare metal or VMware environments, zone labels might not exist by default. In that case, you must define your own topology model and label nodes consistently.

Example for on-premises rack-aware scheduling:

```bash
oc label node worker-1 topology.kubernetes.io/zone=rack-a
oc label node worker-2 topology.kubernetes.io/zone=rack-b
oc label node worker-3 topology.kubernetes.io/zone=rack-c
```

Or use custom labels:

```bash
oc label node worker-1 topology.company.example/rack=rack-a
oc label node worker-2 topology.company.example/rack=rack-b
oc label node worker-3 topology.company.example/rack=rack-c
```

Use standard Kubernetes labels where possible because many components already understand them.

## 6. Topology Spread Constraints: The Core Feature

The main modern way to implement zone-aware scheduling is `topologySpreadConstraints`.

A topology spread constraint tells the scheduler:

> For pods matching this selector, keep the number of pods balanced across topology domains defined by this node label.

Basic example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: web
      containers:
        - name: web
          image: registry.access.redhat.com/ubi9/httpd-24
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
```

This means:

- Count pods with label `app=web`.
- Group nodes by `topology.kubernetes.io/zone`.
- Keep pod counts balanced across zones.
- Do not schedule a new pod if placement would violate `maxSkew: 1`.

---

## 7. Understanding `maxSkew`

`maxSkew` controls how uneven pod distribution is allowed to become.

Assume three zones:

```text
zone-a: 2 pods
zone-b: 1 pod
zone-c: 1 pod
```

The lowest pod count is `1`. Skew is calculated compared with the lowest domain:

```text
zone-a skew = 2 - 1 = 1
zone-b skew = 1 - 1 = 0
zone-c skew = 1 - 1 = 0
```

With `maxSkew: 1`, this is acceptable.

Now assume:

```text
zone-a: 3 pods
zone-b: 1 pod
zone-c: 1 pod
```

Skew:

```text
zone-a skew = 3 - 1 = 2
zone-b skew = 1 - 1 = 0
zone-c skew = 1 - 1 = 0
```

With `maxSkew: 1`, this is not acceptable for a hard constraint.

### Practical Recommendation

For HA stateless workloads, start with:

```yaml
maxSkew: 1
whenUnsatisfiable: DoNotSchedule
```

For workloads where availability is more important than perfect spread, use:

```yaml
maxSkew: 1
whenUnsatisfiable: ScheduleAnyway
```

`ScheduleAnyway` allows the pod to run even if perfect balancing is not possible. The scheduler still prefers better spread, but does not block the workload.

---

## 8. `DoNotSchedule` vs `ScheduleAnyway`

| Setting | Behavior | Production Use |
|---|---|---|
| `DoNotSchedule` | Hard rule. Pod stays Pending if spread cannot be satisfied. | Strong HA, strict failure-domain control. |
| `ScheduleAnyway` | Soft rule. Scheduler prefers better spread but can still place pod. | Better availability when capacity is uneven. |

### 8.1 When to Use `DoNotSchedule`

Use hard constraints when:

- each zone has enough capacity
- zone labels are consistent
- replica count matches zone count well
- application must tolerate zone failure
- you prefer Pending pods over risky placement

Example:

```yaml
whenUnsatisfiable: DoNotSchedule
```

### 8.2 When to Use `ScheduleAnyway`

Use soft constraints when:

- clusters are small
- zones have uneven capacity
- autoscaling is expected
- not all zones always have nodes
- pending pods would cause bigger outage than imbalance

Example:

```yaml
whenUnsatisfiable: ScheduleAnyway
```

### 8.3 Senior Admin Rule

In production, strict spreading sounds attractive, but it can cause outages during node pressure or zone capacity shortage. For critical front-end workloads, a common pattern is:

- use `ScheduleAnyway` for zone spreading
- use hard `PodDisruptionBudget`
- use proper readiness probes
- ensure enough replicas
- monitor imbalance
- use descheduler carefully if needed

## 9. Important Fields in `topologySpreadConstraints`

A full constraint can look like this:

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    minDomains: 3
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: web
    matchLabelKeys:
      - pod-template-hash
    nodeAffinityPolicy: Honor
    nodeTaintsPolicy: Honor
```

Always verify exact field support on your cluster:

```bash
oc explain pod.spec.topologySpreadConstraints
oc explain pod.spec.topologySpreadConstraints.minDomains
oc explain pod.spec.topologySpreadConstraints.nodeAffinityPolicy
oc explain pod.spec.topologySpreadConstraints.nodeTaintsPolicy
```

### 9.1 `topologyKey`

The node label key used to define domains.

Common values:

```yaml
topologyKey: topology.kubernetes.io/zone
```

```yaml
topologyKey: kubernetes.io/hostname
```

```yaml
topologyKey: topology.company.example/rack
```

### 9.2 `labelSelector`

This decides which existing pods are counted.

Correct:

```yaml
labelSelector:
  matchLabels:
    app: web
```

Pod template must also have the same label:

```yaml
metadata:
  labels:
    app: web
```

Wrong pattern:

```yaml
labelSelector:
  matchLabels:
    app: frontend
```

but pod has:

```yaml
labels:
  app: web
```

This causes unexpected placement because the pod may not count itself in future spread calculations.

### 9.3 `matchLabelKeys`

`matchLabelKeys` is useful during rolling updates. A Deployment adds a changing label such as `pod-template-hash`. If you include it, the scheduler can calculate spread among pods from the same rollout revision.

Example:

```yaml
matchLabelKeys:
  - pod-template-hash
```

Use it carefully. In many normal admin scenarios, `labelSelector` is enough.

### 9.4 `minDomains`

`minDomains` defines the minimum number of eligible topology domains required for skew calculation. This helps avoid false balance when only one or two zones are eligible.

Example:

```yaml
minDomains: 3
```

Use it when:

- you expect three zones
- you do not want scheduling to proceed as if one zone is enough
- autoscaler or cloud capacity behavior must be controlled

Be careful: if only two zones are available and `minDomains: 3` with a hard rule, pods might stay Pending.

### 9.5 `nodeAffinityPolicy`

Controls whether node affinity / node selector rules are considered when calculating eligible topology domains.

Common setting:

```yaml
nodeAffinityPolicy: Honor
```

Meaning: count only domains that also satisfy the pod's node affinity.

### 9.6 `nodeTaintsPolicy`

Controls whether taints and tolerations are considered when calculating eligible topology domains.

Common setting:

```yaml
nodeTaintsPolicy: Honor
```

Meaning: do not count nodes in a zone if the pod cannot tolerate their taints.

## 10. Zone-aware Deployment Example: Strict HA

This example runs six replicas across zones with hard spread.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
  namespace: payments
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: payments-api
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: payments-api
      containers:
        - name: payments-api
          image: registry.example.com/payments/api:v1
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: 1
              memory: 1Gi
```

This does two things:

1. Spreads pods across zones.
2. Spreads pods across nodes inside zones.

The second constraint prevents placing too many replicas on the same node even when zones are balanced.

## 11. Zone-aware Deployment Example: Flexible Production Pattern

This version prefers zone spread but avoids Pending pods when one zone lacks capacity.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: prod
spec:
  replicas: 6
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app: frontend
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app: frontend
      containers:
        - name: frontend
          image: registry.example.com/apps/frontend:v1
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
```

This is often safer for business-critical stateless apps because it favors running pods over perfect topology.

## 12. Combining Zone-aware Scheduling with Node Affinity

Sometimes you want pods only on application worker nodes, but still spread across zones.

Example labels:

```bash
oc label node worker-a1 node-role.kubernetes.io/app=
oc label node worker-b1 node-role.kubernetes.io/app=
oc label node worker-c1 node-role.kubernetes.io/app=
```

Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders
  namespace: prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: orders
  template:
    metadata:
      labels:
        app: orders
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: node-role.kubernetes.io/app
                    operator: Exists
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: orders
          nodeAffinityPolicy: Honor
      containers:
        - name: orders
          image: registry.example.com/orders:v1
```

Senior admin point:

> If only one zone has nodes matching node affinity, zone spreading cannot magically use other zones. The topology spread domain is calculated from eligible nodes, not from your design diagram.

## 13. Combining Zone-aware Scheduling with Taints and Tolerations

Assume infra nodes are tainted:

```bash
oc adm taint nodes infra-1 node-role.kubernetes.io/infra=:NoSchedule
oc adm taint nodes infra-2 node-role.kubernetes.io/infra=:NoSchedule
oc adm taint nodes infra-3 node-role.kubernetes.io/infra=:NoSchedule
```

To place router-like or infra workload pods across infra zones:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: custom-router
  namespace: openshift-ingress-custom
spec:
  replicas: 3
  selector:
    matchLabels:
      app: custom-router
  template:
    metadata:
      labels:
        app: custom-router
    spec:
      tolerations:
        - key: node-role.kubernetes.io/infra
          operator: Exists
          effect: NoSchedule
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: custom-router
          nodeTaintsPolicy: Honor
      containers:
        - name: router
          image: registry.example.com/router:v1
```

Important:

- Taints repel pods.
- Tolerations permit scheduling but do not attract pods.
- Use toleration plus node selector / node affinity when you need targeted placement.
- Use `nodeTaintsPolicy: Honor` so spread calculations match actual eligible nodes.

## 14. Zone-aware Scheduling vs Pod Anti-affinity

Before topology spread constraints became common, administrators used pod anti-affinity to spread replicas.

Example hard pod anti-affinity by zone:

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: web
        topologyKey: topology.kubernetes.io/zone
```

This says: do not place another `app=web` pod in the same zone.

That sounds good, but it has limitations:

- With three zones, you can schedule only three matching pods.
- The fourth replica stays Pending.
- It is too strict for many horizontally scaled apps.
- It does not express controlled imbalance like `maxSkew: 1`.

Topology spread constraints are more flexible because they allow multiple pods per zone while controlling imbalance.

### Comparison

| Requirement | Better Feature |
|---|---|
| One replica per node | Pod anti-affinity or hostname topology spread |
| Balanced replicas across zones | Topology spread constraints |
| Avoid exact co-location with another app | Pod anti-affinity |
| Prefer same zone as cache/database | Pod affinity or node affinity |
| Hard isolate workload to specific nodes | Node selector / node affinity / taints |
| Fine-grained spread with skew | Topology spread constraints |

## 15. Multi-level Zone-aware Scheduling

A strong production pattern is to spread across both zones and nodes.

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: api
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: api
```

This means:

- first ensure zone balance
- also ensure node balance

Be careful. Multiple hard constraints must all be satisfied. If the cluster has insufficient nodes per zone, pods may remain Pending.

Recommended approach:

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: api
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app: api
```

This keeps zone HA strict but node-level spread flexible.

## 16. Replica Count Planning

Zone-aware scheduling works best when replica count is planned against zone count.

### 16.1 Three Zones

| Replicas | Expected Spread |
|---:|---|
| 1 | One zone only; no HA across zones. |
| 2 | Two zones used; one zone empty. |
| 3 | One pod per zone. |
| 4 | 2-1-1 distribution. |
| 5 | 2-2-1 distribution. |
| 6 | 2-2-2 distribution. |
| 9 | 3-3-3 distribution. |

### 16.2 Production Recommendation

For stateless HA services in three zones:

- minimum recommended replicas: `3`
- better for rolling updates: `4` or more
- better for one zone failure: `6` or more

Why six? If one zone fails in a 3-zone cluster with 6 replicas, you may still have around 4 pods running in the remaining zones before rescheduling.

## 17. Zone Failure Behavior

Assume 6 pods across 3 zones:

```text
zone-a: 2
zone-b: 2
zone-c: 2
```

If `zone-c` fails:

```text
zone-a: 2
zone-b: 2
zone-c: 0 unavailable
```

The Deployment controller creates replacement pods, but the scheduler behavior depends on rules:

### With `DoNotSchedule`

If the scheduler still considers the failed zone as unavailable and cannot satisfy skew, replacement pods may remain Pending.

This can be acceptable when strict topology is required, but it can reduce service capacity.

### With `ScheduleAnyway`

Replacement pods can be scheduled into remaining zones, for example:

```text
zone-a: 3
zone-b: 3
zone-c: 0
```

This provides better availability during zone outage.

### Senior Admin Decision

For most stateless business services:

- use `ScheduleAnyway` if running capacity matters most
- use `DoNotSchedule` only when violating zone spread is more dangerous than reduced capacity

For stateful quorum systems, the decision depends on the application's replication and quorum behavior.

## 18. Zone-aware Scheduling for StatefulSets

StatefulSets require more care because pods often use PVCs.

Example:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: kafka
  namespace: messaging
spec:
  serviceName: kafka
  replicas: 3
  selector:
    matchLabels:
      app: kafka
  template:
    metadata:
      labels:
        app: kafka
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: kafka
      containers:
        - name: kafka
          image: registry.example.com/kafka:v1
          volumeMounts:
            - name: data
              mountPath: /var/lib/kafka
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes:
          - ReadWriteOnce
        storageClassName: fast-block
        resources:
          requests:
            storage: 100Gi
```

### 18.1 Storage Topology Problem

For block storage, a PV is often zone-bound. A pod using a PVC bound to `zone-a` cannot move freely to `zone-b`.

Common symptoms:

```text
0/9 nodes are available: 3 node(s) had volume node affinity conflict
```

or:

```text
pod has unbound immediate PersistentVolumeClaims
```

### 18.2 Use `WaitForFirstConsumer`

A StorageClass with `volumeBindingMode: WaitForFirstConsumer` delays PV provisioning until the scheduler knows where the pod should run.

Example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-block
provisioner: csi.example.com
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
```

This helps align storage provisioning with pod scheduling.

### 18.3 StatefulSet Best Practices

- Use one replica per zone for quorum systems where possible.
- Understand application-level replication.
- Use anti-affinity or topology spread constraints carefully.
- Use `WaitForFirstConsumer` for topology-aware storage.
- Avoid manually deleting PVCs unless you understand data loss risk.
- Review storage provider zone behavior.
- Test failover before production.

## 19. Zone-aware Scheduling and PodDisruptionBudget

Zone-aware placement protects from infrastructure failure. A PodDisruptionBudget protects from voluntary disruptions such as:

- node drain
- cluster upgrade
- machine replacement
- descheduler eviction
- admin maintenance

Example PDB:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payments-api-pdb
  namespace: payments
spec:
  minAvailable: 4
  selector:
    matchLabels:
      app: payments-api
```

For 6 replicas across 3 zones, `minAvailable: 4` means OpenShift should avoid voluntary disruption that drops healthy pods below 4.

Alternative:

```yaml
spec:
  maxUnavailable: 1
```

### Senior Admin Warning

PDB does not prevent involuntary failures such as power loss, kernel panic, node crash, or zone outage. It only controls voluntary evictions.

## 20. Zone-aware Scheduling and HPA

Horizontal Pod Autoscaler can change replica count dynamically. When HPA scales out, the scheduler applies topology spread constraints to new pods.

Example HPA:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: frontend
  namespace: prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: frontend
  minReplicas: 3
  maxReplicas: 12
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```

Recommended:

- Set `minReplicas` at least equal to number of zones for zone HA.
- Ensure each zone has enough CPU/memory headroom.
- Use resource requests; HPA and scheduler both depend on requests.
- Avoid hard topology constraints if autoscaler can scale faster than nodes become ready.

## 21. Zone-aware Scheduling and Cluster Autoscaler

In cloud OpenShift clusters, workers may be managed by MachineSets in multiple zones.

Example MachineSets:

```text
worker-us-east-1a
worker-us-east-1b
worker-us-east-1c
```

Zone-aware scheduling depends on all zones having capacity or autoscaler support.

Potential issue:

- You have topology spread requiring three zones.
- One zone's MachineSet is scaled to zero.
- Scheduler sees no nodes in that zone.
- Pods may remain Pending or spread only across existing zones depending on constraints and feature behavior.

Recommended checks:

```bash
oc get machinesets -n openshift-machine-api
oc get machines -n openshift-machine-api -o wide
oc get nodes -L topology.kubernetes.io/zone
oc describe pod <pending-pod> -n <namespace>
```

Senior admin practice:

- Keep at least one worker per zone for critical workloads.
- Do not scale a zone's MachineSet to zero if hard zone spread is required.
- Validate autoscaler behavior with topology constraints before production.

## 22. Zone-aware Scheduling for Ingress, Monitoring, and Operators

### 22.1 Ingress Routers

OpenShift ingress routers should be distributed across zones when possible. If all router pods run in one zone, route traffic can be affected by a zone failure.

Check:

```bash
oc get pods -n openshift-ingress -o wide
oc get nodes -L topology.kubernetes.io/zone
```

### 22.2 Monitoring Stack

Prometheus, Alertmanager, Thanos Ruler, and related monitoring components should also be distributed across topology domains in multi-zone environments. Monitoring loss during zone failure makes incident response harder.

Check:

```bash

```

### 22.3 Operators

Operator-managed workloads might overwrite manual changes. If an Operator owns the Deployment or StatefulSet, configure topology spread through the Operator's supported custom resource fields, not by manually patching generated objects unless Red Hat or vendor documentation supports it.

## 25. Troubleshooting Pending Pods

When topology rules are too strict or labels are missing, pods may stay Pending.

Start with:

```bash
oc describe pod <pod-name> -n <namespace>
```

Look at Events:

```text
Warning  FailedScheduling  default-scheduler  0/6 nodes are available: 3 node(s) didn't match pod topology spread constraints, 3 node(s) didn't match Pod's node affinity/selector.
```

### 25.1 Common Causes

| Symptom | Likely Cause | Fix |
|---|---|---|
| Pending with topology spread message | Hard `DoNotSchedule` cannot be satisfied | Add capacity, relax to `ScheduleAnyway`, adjust replicas/skew. |
| All pods in one zone | Missing or inconsistent zone labels | Fix node/MachineSet labels. |
| Pod does not count itself | Pod labels do not match `labelSelector` | Align labels and selectors. |
| PVC volume node affinity conflict | PV is bound to different zone | Use correct StorageClass, `WaitForFirstConsumer`, recreate PVC carefully if needed. |
| New pods only use two zones | Third zone has no eligible nodes | Check node readiness, taints, affinity, capacity, MachineSet. |
| Hard node and zone constraints conflict | Too many required rules | Convert some rules to preferred/soft rules. |
| Operator reverts changes | Workload controlled by Operator | Configure topology in the Operator CR. |

### 25.2 Check Node Labels

```bash
oc get nodes --show-labels | grep topology.kubernetes.io/zone
```

Better:

```bash
oc get nodes -L topology.kubernetes.io/zone,kubernetes.io/hostname
```

### 25.3 Check Taints

```bash
oc describe node <node-name> | grep -i taints -A3
```

or:

```bash
oc get nodes -o json | jq -r '.items[] | [.metadata.name, (.spec.taints // [])] | @json'
```

### 25.4 Check Node Affinity and Selectors

```bash
oc get pod <pod-name> -n <namespace> -o yaml | yq '.spec.nodeSelector, .spec.affinity'
```

Without `yq`:

```bash
oc get pod <pod-name> -n <namespace> -o yaml | sed -n '/nodeSelector:/,/containers:/p'
```

### 25.5 Check Scheduler Events

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp | grep -i scheduling
```

### 25.6 Check Deployment Template

```bash
oc get deployment web -n prod -o yaml | sed -n '/topologySpreadConstraints:/,/containers:/p'
```

## 26. Troubleshooting Uneven Distribution

If pods are running but not evenly distributed:

### Step 1: Confirm Labels

```bash
oc get pods -n prod -l app=web --show-labels
```

Confirm the pod labels match the topology spread `labelSelector`.

### Step 2: Confirm Node Zones

```bash

```

Every eligible node should have the topology key. Nodes without the key may be ignored for that topology calculation.

### Step 3: Confirm Existing Pods Were Scheduled Before the Rule

Topology constraints affect scheduling of new pods. Existing pods are not automatically moved just because you changed the Deployment template.

To gradually rebalance:

```bash

```

Or carefully delete one pod at a time:

```bash
oc delete pod <pod-name> -n prod
```

### Step 4: Consider Descheduler

OpenShift provides the Kube Descheduler Operator. For topology imbalance, relevant profiles include topology and duplicate-related strategies. Use carefully with PDBs and business workloads.

## 27. Descheduler and Zone-aware Rebalancing

The scheduler only places new pods. It does not continuously move old pods to improve topology.

The descheduler can evict pods so the scheduler can place replacements more appropriately.

Use cases:

- new zone added
- nodes added after a scale-out
- old pods concentrated in one zone
- node labels changed
- topology constraints added after workload already existed

High-level flow:

1. Install Kube Descheduler Operator.
2. Configure a `KubeDescheduler` custom resource.
3. Start in predictive or safe mode where possible.
4. Ensure PDBs exist.
5. Monitor evictions.
6. Use automatic mode only when understood.

Example concept:

```yaml
apiVersion: operator.openshift.io/v1
kind: KubeDescheduler
metadata:
  name: cluster
  namespace: openshift-kube-descheduler-operator
spec:
  managementState: Managed
  mode: Predictive
  profiles:
    - TopologyAndDuplicates
```

Production caution:

- Do not enable descheduler without PDB review.
- Do not use aggressive intervals for critical applications.
- Do not assume descheduler will fix bad workload design.
- Avoid profile conflicts.
- Review OpenShift version-specific profile names and support status.

## 28. Zone-aware Scheduling and OpenShift Upgrades

During OpenShift upgrades, nodes are drained and rebooted in controlled waves through MachineConfigPool behavior.

Zone-aware workloads should have:

- replicas across zones
- PDBs
- readiness probes
- sufficient spare capacity
- topology constraints that do not block replacement pods

Before upgrade:

```bash
oc get clusterversion
oc get mcp
oc get nodes -L topology.kubernetes.io/zone
oc get pdb -A
oc get pods -A -o wide | grep -E 'CrashLoopBackOff|Pending|Error'
```

For each critical namespace:

```bash
oc get deployment,statefulset,pdb -n <namespace>
oc get pods -n <namespace> -o wide
```

If all replicas are in one zone before upgrade, fix placement before the maintenance window.

## 29. Zone-aware Scheduling and Routes / Services

Kubernetes Services load balance across ready endpoints. Zone-aware scheduling does not automatically make Service traffic zone-local unless additional features or network policies are involved.

Important points:

- A Service sees ready pods as endpoints.
- If pods are spread across zones, endpoints are spread too.
- Cross-zone traffic may still occur.
- Ingress controllers, external load balancers, and cloud provider settings influence actual traffic path.
- Readiness probes are critical so failed-zone pods are removed from endpoints.

Check endpoints:

```bash
oc get endpoints -n prod web
oc get endpointslices -n prod -l kubernetes.io/service-name=web
```

Check route:

```bash
oc get route -n prod
```

## 30. Zone-aware Scheduling in On-premises OpenShift

Cloud zones are easy because cloud providers expose AZ labels. On-premises design requires discipline.

Possible topology model:

```text
region: dc-delhi
zone: room-a / room-b / room-c
rack: rack-01 / rack-02 / rack-03
power-domain: ups-a / ups-b
network-domain: tor-a / tor-b
```

Label examples:

```bash
oc label node worker-1 topology.kubernetes.io/region=dc-delhi
oc label node worker-1 topology.kubernetes.io/zone=room-a
oc label node worker-1 topology.company.example/rack=rack-01
oc label node worker-1 topology.company.example/power=ups-a
```

Use cases:

- spread routers across rooms
- spread monitoring replicas across racks
- keep database replicas across power domains
- isolate GPU workloads to GPU nodes but spread them across racks
- keep production and non-production on different node pools

On-premises warning:

> Bad labels create fake HA. If all nodes labeled as different zones are actually connected to the same switch, same UPS, and same storage controller, you do not have real failure-domain isolation.

## 33. Exam / Interview Style Questions

### Q1. What is zone-aware scheduling?

Zone-aware scheduling is the practice of distributing pods across infrastructure failure domains such as zones, racks, or datacenters by using topology labels and scheduling constraints. In OpenShift, it is commonly implemented with `topologySpreadConstraints` using `topology.kubernetes.io/zone`.

### Q2. What happens if `labelSelector` does not match the pod's own labels?

The scheduler does not count those pods correctly for spread calculation. This can cause unexpected imbalance because the workload is not grouped as intended.

### Q3. Difference between pod anti-affinity and topology spread constraints?

Pod anti-affinity repels pods from a topology domain and can become too strict. Topology spread constraints allow controlled imbalance using `maxSkew`, making them better for scalable HA workloads.

### Q4. Why can a pod remain Pending with zone-aware scheduling?

Common reasons include hard `DoNotSchedule` constraints, missing topology labels, insufficient zone capacity, node affinity conflicts, taints not tolerated, or PVC volume node affinity conflicts.

### Q5. Does the scheduler rebalance old pods after adding topology constraints?

No. The scheduler handles new pod placement. Existing pods remain where they are unless recreated or evicted by another mechanism such as rollout restart, manual deletion, or descheduler.

### Q6. How do you verify zone distribution?

Use:

```bash
oc get pods -o wide
oc get nodes -L topology.kubernetes.io/zone
```

Then map pod node names to node zone labels.

### Q7. What is the safest setting for business-critical stateless workloads?

Often `ScheduleAnyway` with `maxSkew: 1`, plus enough replicas, PDBs, readiness probes, monitoring, and capacity planning. Use `DoNotSchedule` only when strict topology is required.

- [ ] Confirm taints/tolerations allow placement in intended zones.
- [ ] Confirm pod labels match `labelSelector`.
- [ ] Confirm replica count makes sense for number of zones.

- [ ] Test rolling update.
- [ ] Test node drain.
- [ ] Test zone capacity loss if possible.
- [ ] Check HPA min/max replicas.
- [ ] Review Operator-managed workload configuration.
- [ ] Document the topology model.

## 35. Recommended Production Patterns

### Pattern 1: Stateless Web App, Three Zones

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app: web
```

Use with:

- replicas: 3 or more
- PDB: `maxUnavailable: 1`
- HPA minReplicas: 3
- readiness probe

### Pattern 2: Critical API, Strict HA

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: critical-api
```

Use with:

- guaranteed zone capacity
- strong monitoring
- runbook for Pending pods
- tested upgrade procedure

### Pattern 3: Spread Across Zones and Nodes

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: api
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app: api
```

This provides strong zone spread and soft node spread.

### Pattern 4: Dedicated Node Pool with Zone Spread

```yaml
nodeSelector:
  node-role.kubernetes.io/app: ""
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: backend
    nodeAffinityPolicy: Honor
```

Use when application workloads must run only on dedicated app workers.

## 36. Common Mistakes by Administrators

### Mistake 1: Labeling Only Some Nodes

If only some nodes have the topology key, scheduling behavior becomes confusing.

Fix:

```bash
oc get nodes -L topology.kubernetes.io/zone
```

Label all eligible nodes consistently.

### Mistake 2: Using Hard Rules in Small Clusters

In a two-node or two-zone lab, strict rules can block scheduling.

Fix:

- reduce constraints
- use `ScheduleAnyway`
- increase node/zone capacity

### Mistake 3: Mismatched Selectors

Deployment selector, pod labels, service selector, and topology label selector must be aligned.

Check:

```bash
oc get deploy web -n prod -o yaml | grep -A20 -E 'selector:|labels:|topologySpreadConstraints:'
```

### Mistake 4: Forgetting Storage Topology

A pod can be perfectly scheduled from compute perspective but blocked by PV zone affinity.

Check:

```bash
oc describe pod <pod> -n <namespace>
oc get pv <pv-name> -o yaml
oc get sc <storageclass> -o yaml
```

### Mistake 5: Expecting Automatic Rebalancing

The scheduler does not move old pods. Restart or deschedule carefully.

### Mistake 6: Manual Patch on Operator-managed Workloads

Operator reconciliation may revert manual changes.

Fix:

- configure CR supported fields
- check Operator docs
- do not fight reconciliation loops

## 39. Design Decisions for Senior Administrators

When designing zone-aware scheduling, answer these questions first:

1. What is the real failure domain?
2. How many zones exist?
3. Are zones equal in capacity?
4. What is the minimum replica count?
5. Can the application tolerate one zone failure?
6. Should pods remain Pending rather than violating spread?
7. Is storage zone-bound?
8. Is traffic zone-local or global?
9. Are workloads stateless or stateful?
10. Are operators managing the pods?
11. Does autoscaler understand the topology?
12. Are PDBs configured?
13. How will this behave during upgrade?
14. How will you monitor imbalance?
15. How will you recover from zone outage?

## 40. Final Best Practices

- Prefer `topologySpreadConstraints` over hard pod anti-affinity for scalable HA workloads.
- Use `topology.kubernetes.io/zone` for zone-aware scheduling where available.
- Keep node topology labels consistent.
- Use `maxSkew: 1` as a starting point.
- Choose `DoNotSchedule` only when strict placement is required and capacity is guaranteed.
- Use `ScheduleAnyway` for most stateless production apps where running service capacity is more important than perfect spread.
- Set replica count at least equal to zone count.
- Combine zone spread with hostname spread for stronger resilience.
- Align Deployment selector, pod labels, Service selector, and topology spread selector.
- Use PDBs for voluntary disruption protection.
- Use readiness probes so Services route only to healthy pods.
- Understand storage topology before applying strict zone rules to StatefulSets.
- Use `WaitForFirstConsumer` for topology-aware storage provisioning.
- Remember that scheduling affects new pods; it does not automatically move existing pods.
- Use descheduler only with planning, PDBs, and monitoring.
- Always test node drain and zone failure behavior before claiming HA.
