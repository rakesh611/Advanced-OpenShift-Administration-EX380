# Preventing Workload Placement on Specific Nodes in OpenShift

**Area:** Pod Scheduling and Workload Placement  
**Level:** Advanced OpenShift Administration / 10+ years operations mindset  
**Platform focus:** Red Hat OpenShift Container Platform 4.x, verified against OpenShift 4.20 documentation on 2026-07-03  
**Primary tools:** `oc adm cordon`, `oc adm drain`, taints, tolerations, node labels, node selectors, node affinity, project node selectors, scheduler configuration

---

## 1. Executive summary

Preventing workload placement on specific nodes means controlling whether the OpenShift scheduler is allowed to place new pods on a node, and whether existing pods should stay there or be evicted. In real production clusters, this is used for maintenance, hardware failure isolation, infrastructure node reservation, GPU/storage/node-pool isolation, security boundaries, cost control, compliance zones, and noisy-neighbor prevention.

There is no single universal command for every situation. The correct mechanism depends on your intent:

| Requirement | Best mechanism | Existing pods affected? | Typical use case |
|---|---|---:|---|
| Temporarily stop new pods from landing on a node | `oc adm cordon` | No | Maintenance preparation |
| Move existing normal workload pods away from a node | `oc adm drain` | Yes, controlled pods are evicted | Node reboot, OS/MCO maintenance, hardware work |
| Permanently reserve a node so only approved workloads can run there | Taint + matching toleration | Depends on taint effect | Infra nodes, GPU nodes, dedicated nodes |
| Prevent an application from using a specific node | Required node affinity with `NotIn` or `DoesNotExist` | New pods only unless recreated | App-level exclusion |
| Restrict all workloads in a namespace/project to approved nodes | Project node selector | New pods in project | Multi-tenancy and governance |
| Apply default placement policy cluster-wide | Scheduler `defaultNodeSelector` | New pods | Strong cluster-wide default, use carefully |
| Keep user workloads off control-plane nodes | `mastersSchedulable: false` and control-plane taint | New pods | Standard OCP control-plane protection |
| Remove a node from service completely | Cordon + drain + MachineSet scale-down / node deletion | Yes | Decommissioning |

A senior administrator should always distinguish between **scheduling prevention** and **eviction**:

- `cordon` prevents new pods only.
- `NoSchedule` taint prevents new non-tolerating pods only.
- `NoExecute` taint prevents new non-tolerating pods and evicts existing non-tolerating pods.
- `drain` actively evicts pods from a node by using the eviction API, respecting PodDisruptionBudgets where applicable.
- Node affinity and node selectors constrain scheduling decisions but do not normally move already-running pods automatically.

## 2. Scheduler mental model

When a pod is created, OpenShift uses the Kubernetes scheduler framework to choose a node. At a high level, scheduling has two big stages:

1. **Filtering:** Remove nodes that are not eligible.
2. **Scoring:** Rank remaining eligible nodes and choose the best one.

A node can be filtered out for many reasons:

- Node is `NotReady`.
- Node is marked `SchedulingDisabled` because it is cordoned.
- Node has an unmatched `NoSchedule` or `NoExecute` taint.
- Pod `nodeSelector` does not match node labels.
- Pod required node affinity does not match node labels.
- Namespace/project node selector conflicts with pod placement.
- Node lacks CPU, memory, ephemeral storage, hugepages, device plugin resources, or extended resources.
- PersistentVolume topology conflicts with the node.
- Pod anti-affinity rules reject that node.
- Topology spread constraints cannot be satisfied.
- Admission or security policies prevent pod creation.

Preventing workload placement means deliberately introducing one or more of these filter conditions.

## 3. Key principle: negative control vs positive control

There are two ways to prevent placement on a node.

### 3.1 Negative control

You mark a node as unattractive or forbidden.

Examples:

```bash
oc adm cordon worker-1.example.com
oc adm taint node worker-1.example.com quarantine=true:NoSchedule
oc adm taint node worker-1.example.com quarantine=true:NoExecute
```

This is direct and useful when the node itself is the problem.

### 3.2 Positive control

You define where workloads are allowed to run, so excluded nodes are naturally avoided.

Examples:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload-zone: general
```

or:

```yaml
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: node.openshift.example.com/blocked-for-app
                operator: DoesNotExist
```

This is better for long-term policy because the workload definition clearly states the placement requirement.

## 4. Method 1 — Cordon: stop new pods from landing on a node

### 4.1 What cordon does

`cordon` marks a node as unschedulable. In node status you normally see:

```text
Ready,SchedulingDisabled
```

This blocks new pods from being scheduled onto the node. Existing pods are not removed.

Use `cordon` when:

- You plan to reboot or patch a node.
- You want to freeze new scheduling while investigating node health.
- You want to stop workload growth on a node before draining.
- You want a reversible, low-risk first step.

Do not use `cordon` alone when:

- You must move current workloads off the node.
- The node is unhealthy and existing pods must be replaced elsewhere.
- You need long-term workload segregation. Use taints, selectors, or affinity instead.

### 4.2 Commands

Mark one node unschedulable:

```bash
oc adm cordon worker-1.example.com
```

Verify:

```bash
oc get node worker-1.example.com
oc describe node worker-1.example.com | egrep -i 'Unschedulable|Taints|Conditions'
```

Expected status:

```text
NAME                   STATUS                     ROLES    AGE   VERSION
worker-1.example.com   Ready,SchedulingDisabled   worker   30d   v1.xx.x
```

Mark it schedulable again:

```bash
oc adm uncordon worker-1.example.com
```

Cordon multiple nodes by label selector:

```bash
oc adm cordon --selector=node-role.kubernetes.io/worker=
```

Uncordon multiple nodes by selector:

```bash
oc adm uncordon --selector=maintenance-window=completed
```

### 4.3 What happens internally

Cordon sets the node field:

```yaml
spec:
  unschedulable: true
```

The scheduler filters out the node for normal pending pods. Kubelet continues running existing pods. Controllers such as Deployment, StatefulSet, ReplicaSet, DaemonSet, and Job controllers continue managing desired state, but their replacement pods will not be placed on that cordoned node.

### 4.4 Operational notes

- Cordon is safe and reversible.
- It does not kill pods.
- It does not remove DaemonSet pods.
- It does not prevent static pods from running.
- It does not stop kubelet.
- It is not a security boundary.
- It is not a long-term policy mechanism by itself.

## 5. Method 2 — Drain: move workloads away from a node

### 5.1 What drain does

`drain` evicts pods from a node so that workload controllers can recreate them elsewhere. Drain is normally used after cordon:

```bash
oc adm cordon worker-1.example.com
oc adm drain worker-1.example.com --ignore-daemonsets --delete-emptydir-data
```

OpenShift documentation recommends marking nodes unschedulable before evacuation. This avoids a situation where replacement pods are scheduled back to the same node while you are trying to empty it.

### 5.2 Standard production workflow

```bash
NODE=worker-1.example.com

# 1. Review current pods on the node
oc get pods -A --field-selector spec.nodeName=$NODE -o wide

# 2. Cordon first
oc adm cordon $NODE

# 3. Dry-run drain
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --dry-run=server

# 4. Drain
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --timeout=10m

# 5. Verify node is empty except DaemonSet/static/system pods
oc get pods -A --field-selector spec.nodeName=$NODE -o wide

# 6. Perform maintenance
# reboot, hardware work, OS/MCO remediation, etc.

# 7. Return node to service
oc adm uncordon $NODE
```

### 5.3 Common drain options

| Option | Meaning | Production caution |
|---|---|---|
| `--ignore-daemonsets` | Ignore DaemonSet-managed pods | Almost always required because DaemonSets run one pod per node |
| `--delete-emptydir-data` | Allow deletion of pods using `emptyDir` | Data in `emptyDir` is local and temporary; confirm app can tolerate loss |
| `--force` | Delete pods not managed by a controller | Risky; bare pods will not be recreated automatically |
| `--grace-period=<seconds>` | Override pod termination grace period | Avoid overly aggressive values for stateful workloads |
| `--timeout=<duration>` | Time to wait before giving up | Use realistic values for production apps |
| `--pod-selector=<selector>` | Drain selected pods only | Useful for targeted evacuation |
| `--dry-run=server` | Show what would happen | Recommended before real drain |

### 5.4 Drain and PodDisruptionBudgets

Drain uses the eviction API for many pods. If a workload has a PodDisruptionBudget (PDB), eviction can be blocked when evicting the pod would violate the allowed disruption level.

Typical error:

```text
Cannot evict pod as it would violate the pod's disruption budget
```

Senior admin response:

1. Identify the blocking PDB:

```bash
oc get pdb -A
oc describe pdb <pdb-name> -n <namespace>
```

2. Check replicas and readiness:

```bash
oc get deploy,sts,rs,pod -n <namespace> -o wide
```

3. Make the workload disruption-safe:

```bash
oc scale deploy/<name> --replicas=<higher-count> -n <namespace>
```

4. Wait for readiness:

```bash
oc rollout status deploy/<name> -n <namespace>
oc get pods -n <namespace> -o wide
```

5. Retry drain.

Avoid simply deleting or weakening PDBs in production unless there is an approved change and the application owner accepts the risk.

### 5.5 Drain limitations

Drain might not remove:

- DaemonSet pods unless ignored.
- Static pods / mirror pods.
- Pods blocked by PDBs.
- Bare pods unless `--force` is used.
- Pods stuck because finalizers, storage detach, CNI, CSI, or kubelet health issues.
- Pods on single-node OpenShift where drain is unavailable or inappropriate.

### 5.6 When drain is the right answer

Use drain when the requirement is:

- “Move workloads off this node.”
- “Patch/reboot this worker safely.”
- “Replace hardware.”
- “Decommission a node.”
- “Evacuate apps from a degraded node.”

Do not use drain as a long-term scheduling policy. After the node is uncordoned, workloads can come back unless you add a placement rule such as taint, selector, or affinity.

## 6. Method 3 — Taints and tolerations: make a node reject normal pods

### 6.1 Concept

A **taint** is applied to a node. A **toleration** is applied to a pod.

A taint says:

> “Do not schedule pods here unless they explicitly tolerate this taint.”

A toleration says:

> “This pod is allowed to run on nodes with this taint.”

Taints are one of the strongest tools for preventing workload placement on specific nodes.

### 6.2 Taint effects

| Effect | Scheduling behavior | Existing pod behavior | Use case |
|---|---|---|---|
| `NoSchedule` | New pods without matching toleration cannot be scheduled | Existing pods remain | Reserve node for special workloads |
| `PreferNoSchedule` | Scheduler tries to avoid the node but may still schedule there | Existing pods remain | Soft avoidance |
| `NoExecute` | New pods without matching toleration cannot be scheduled | Existing pods without matching toleration are evicted | Evacuate/quarantine node |

### 6.3 Add a `NoSchedule` taint

```bash
oc adm taint node worker-1.example.com workload=blocked:NoSchedule
```

Verify:

```bash
oc describe node worker-1.example.com | grep -i Taints -A2
```

Example output:

```text
Taints: workload=blocked:NoSchedule
```

Now normal pods without a matching toleration will not be scheduled on that node.

### 6.4 Remove a taint

```bash
oc adm taint node worker-1.example.com workload-
```

The trailing hyphen removes all taints with that key.

### 6.5 Add a toleration to an allowed workload

Example Deployment that can tolerate the tainted node:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: approved-app
  namespace: app-team-a
spec:
  replicas: 2
  selector:
    matchLabels:
      app: approved-app
  template:
    metadata:
      labels:
        app: approved-app
    spec:
      tolerations:
      - key: workload
        operator: Equal
        value: blocked
        effect: NoSchedule
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/httpd-24
```

Important: A toleration only permits scheduling on a tainted node. It does not force the pod to use that node. To force or prefer the pod to use that node, combine toleration with a node selector or node affinity.

### 6.6 Dedicated-node pattern

This is a common production pattern:

1. Label the dedicated node:

```bash
oc label node worker-gpu-1.example.com workload-type=gpu
```

2. Taint the dedicated node:

```bash
oc adm taint node worker-gpu-1.example.com workload-type=gpu:NoSchedule
```

3. Add both node selector and toleration to approved pods:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gpu-inference
  namespace: ai-prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: gpu-inference
  template:
    metadata:
      labels:
        app: gpu-inference
    spec:
      nodeSelector:
        workload-type: gpu
      tolerations:
      - key: workload-type
        operator: Equal
        value: gpu
        effect: NoSchedule
      containers:
      - name: app
        image: example.com/ai/inference:1.0
        resources:
          limits:
            nvidia.com/gpu: 1
```

Why both are needed:

- The taint keeps unapproved pods away.
- The selector attracts approved pods to the node pool.
- The toleration allows approved pods through the taint.

### 6.7 Quarantine-node pattern with `NoExecute`

If a node is suspected unhealthy and you want non-tolerating pods evicted:

```bash
oc adm taint node worker-1.example.com quarantine=true:NoExecute
```

This blocks new non-tolerating pods and evicts existing non-tolerating pods.

Use carefully. `NoExecute` is more disruptive than `NoSchedule`.

A pod can tolerate `NoExecute` for a limited time:

```yaml
spec:
  tolerations:
  - key: quarantine
    operator: Equal
    value: "true"
    effect: NoExecute
    tolerationSeconds: 600
```

This means the pod can remain bound for 600 seconds after the taint is added, then it is evicted if the taint remains.

### 6.8 Multiple taints

A node can have multiple taints:

```bash
oc adm taint node worker-1.example.com workload=infra:NoSchedule
oc adm taint node worker-1.example.com compliance=pci:NoSchedule
oc adm taint node worker-1.example.com quarantine=true:NoExecute
```

A pod must tolerate all relevant taints that would otherwise block or evict it. If even one unmatched `NoSchedule` taint remains, the pod cannot schedule there. If one unmatched `NoExecute` taint remains, existing non-tolerating pods are evicted.

### 6.9 Taint using YAML

```yaml
apiVersion: v1
kind: Node
metadata:
  name: worker-1.example.com
spec:
  taints:
  - key: workload
    value: blocked
    effect: NoSchedule
```

Prefer `oc adm taint` for quick operations. Prefer MachineSet or MachineConfig/Machine API approaches for persistent node-pool policy.

### 6.10 Apply taints at MachineSet level

For cloud or Machine API managed clusters, direct changes to node objects can be lost when nodes are replaced. For node-pool level policy, add taints to the MachineSet template so newly created machines/nodes inherit the taints.

Example conceptual MachineSet fragment:

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: cluster-worker-infra-us-east-1a
  namespace: openshift-machine-api
spec:
  template:
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/infra: ""
      taints:
      - key: node-role.kubernetes.io/infra
        value: reserved
        effect: NoSchedule
```

Always check the actual MachineSet API in your cluster:

```bash
oc explain machineset.spec.template.spec --api-version=machine.openshift.io/v1beta1
oc get machineset -n openshift-machine-api <name> -o yaml
```

### 6.11 Built-in/system taints

OpenShift and Kubernetes can add taints automatically for node conditions such as:

- `node.kubernetes.io/not-ready`
- `node.kubernetes.io/unreachable`
- `node.kubernetes.io/memory-pressure`
- `node.kubernetes.io/disk-pressure`
- `node.kubernetes.io/pid-pressure`
- `node.kubernetes.io/network-unavailable`
- `node.kubernetes.io/unschedulable`

Many system pods and DaemonSet pods have built-in tolerations. This is why you may still see OpenShift system pods on nodes that normal user pods cannot use.

## 7. Method 4 — Node labels and node selectors

### 7.1 Concept

A node selector is a simple key/value match. A pod can run only on nodes that have all the selected labels.

Label a node:

```bash
oc label node worker-2.example.com placement=allowed
```

Add a node selector to a workload:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: app-team-a
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      nodeSelector:
        placement: allowed
      containers:
      - name: web
        image: registry.access.redhat.com/ubi9/httpd-24
```

This does not say “avoid worker-1.” It says “only use nodes labeled `placement=allowed`.” If worker-1 does not have that label, it is excluded.

### 7.2 Node selector limitation

`nodeSelector` supports exact positive matching only.

It cannot express:

- `not this node`
- `not in this set`
- `label key does not exist`
- OR conditions
- soft preferences

For negative matching, use node affinity.

### 7.3 Updating node labels

Add or update label:

```bash
oc label node worker-2.example.com placement=allowed
```

Overwrite existing label:

```bash
oc label node worker-2.example.com placement=allowed --overwrite
```

Remove label:

```bash
oc label node worker-2.example.com placement-
```

Show node labels:

```bash
oc get nodes --show-labels
oc get nodes -L placement,workload-type,topology.kubernetes.io/zone
```

### 7.4 Persistence warning

In Machine API environments, direct node labels might not survive node replacement. Apply long-term labels at MachineSet level where appropriate.

For quick troubleshooting or temporary exclusion, direct labels are fine. For production node-pool design, prefer MachineSet templates or supported operator configuration.

## 8. Method 5 — Node affinity: explicitly avoid specific nodes

### 8.1 Why node affinity matters

Node affinity is more expressive than `nodeSelector`. It can use operators such as:

- `In`
- `NotIn`
- `Exists`
- `DoesNotExist`
- `Gt`
- `Lt`

For preventing workload placement on specific nodes, the most useful operators are `NotIn` and `DoesNotExist`.

### 8.2 Avoid one specific node by hostname

Every node normally has a hostname label:

```bash
oc get nodes -L kubernetes.io/hostname
```

Deployment example that avoids `worker-1.example.com`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: app-team-a
spec:
  replicas: 3
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: kubernetes.io/hostname
                operator: NotIn
                values:
                - worker-1.example.com
      containers:
      - name: backend
        image: registry.access.redhat.com/ubi9/httpd-24
```

Meaning:

- During scheduling, the pod must not land on a node whose hostname is `worker-1.example.com`.
- `IgnoredDuringExecution` means already-running pods are not evicted just because labels later change.

To move existing pods, restart/rollout the workload after applying the affinity:

```bash
oc rollout restart deployment/backend -n app-team-a
oc rollout status deployment/backend -n app-team-a
```

### 8.3 Avoid a group of nodes

Label nodes that should be avoided:

```bash
oc label node worker-1.example.com blocked-for-backend=true
oc label node worker-2.example.com blocked-for-backend=true
```

Require that the label does not exist:

```yaml
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: blocked-for-backend
                operator: DoesNotExist
```

This pattern scales better than listing hostnames.

### 8.4 Soft avoidance

If you prefer to avoid a node but allow scheduling there when capacity is tight, use preferred node affinity:

```yaml
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            preference:
              matchExpressions:
              - key: maintenance-risk
                operator: NotIn
                values:
                - high
```

This is a scoring preference, not a hard rule. It is not suitable for strict prevention.

### 8.5 Node affinity vs taints

| Topic | Node affinity | Taints/tolerations |
|---|---|---|
| Stored on | Pod spec | Node taint + pod toleration |
| Best for | Workload declares where it can run | Node declares who is allowed |
| Negative matching | Yes, with `NotIn` / `DoesNotExist` | Indirect, via no toleration |
| Existing pods evicted? | No | Only with `NoExecute` |
| Multi-tenant governance | Good with templates/admission/project policy | Excellent for reserved nodes |
| Dedicated nodes | Needs selector/affinity | Needs taint/toleration; best combined |

## 9. Method 6 — Project-level node selectors

### 9.1 Concept

OpenShift supports project-level node selectors through a namespace annotation:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: "placement=team-a"
```

When pods are created in that project, OpenShift applies the node selector and schedules pods only on matching nodes.

This is very useful for multi-tenancy:

- Team A workloads run only on Team A nodes.
- PCI workloads run only on PCI-approved nodes.
- Dev workloads stay off production nodes.
- Regional workloads stay in approved data-center nodes.

### 9.2 Configure project selector

Label nodes:

```bash
oc label node worker-a1.example.com placement=team-a
oc label node worker-a2.example.com placement=team-a
oc label node worker-b1.example.com placement=team-b
```

Annotate namespace/project:

```bash
oc annotate namespace app-team-a openshift.io/node-selector='placement=team-a' --overwrite
```

Verify:

```bash
oc get namespace app-team-a -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
```

Create a workload and verify node placement:

```bash
oc get pods -n app-team-a -o wide
oc get nodes -L placement
```

### 9.3 Conflicts

If a pod specifies a node selector that conflicts with the project node selector, the pod may be rejected or remain unschedulable.

Example conflict:

Project selector:

```text
placement=team-a
```

Pod selector:

```yaml
nodeSelector:
  placement: team-b
```

No node can be both `placement=team-a` and `placement=team-b` for the same key. The workload will fail admission or scheduling.

### 9.4 Removing project selector

```bash
oc annotate namespace app-team-a openshift.io/node-selector- 
```

Be careful: removing a project selector allows future pods in that project to schedule according to other rules only.

## 10. Method 7 — Cluster-wide default node selector

### 10.1 Concept

OpenShift scheduler configuration supports a default cluster-wide node selector. This is applied to pods created in the cluster unless overridden or superseded by project-level selectors.

View scheduler config:

```bash
oc get scheduler cluster -o yaml
```

Edit scheduler config:

```bash
oc edit scheduler cluster
```

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: node-role.kubernetes.io/worker=
```

### 10.2 Production warning

Use cluster-wide default selectors carefully. A bad default selector can make many pods unschedulable, including workloads that were never designed for that constraint.

Risks:

- Operators may create pods with different node requirements.
- Cluster components may conflict with your default selector.
- Namespaces with special workloads may need project-level selectors.
- If the default selector key conflicts with pod labels/selectors, behavior can surprise administrators.

In many production environments, project-level selectors and taints are safer than a broad cluster-wide default.

## 11. Method 8 — Control-plane schedulability

### 11.1 Default behavior

In standard OpenShift clusters, control-plane nodes are generally protected from normal user workload scheduling. OpenShift control-plane nodes commonly carry role labels and taints that keep ordinary workloads away.

Check control-plane nodes:

```bash
oc get nodes -l node-role.kubernetes.io/master -o wide
oc get nodes -l node-role.kubernetes.io/control-plane -o wide
oc describe node <control-plane-node> | grep -i Taints -A3
```

You may see a taint like:

```text
node-role.kubernetes.io/master:NoSchedule
```

### 11.2 `mastersSchedulable`

OpenShift controls whether control-plane nodes can accept normal workloads through the Scheduler resource:

```bash
oc edit schedulers.config.openshift.io cluster
```

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  mastersSchedulable: false
```

Set to:

- `false`: disallow normal scheduling on control-plane nodes.
- `true`: allow control-plane nodes to be schedulable.

Production guidance:

- Keep `mastersSchedulable: false` in normal multi-node production clusters.
- Compact clusters and bare-metal clusters without compute nodes may require schedulable control-plane nodes.
- If enabling control-plane scheduling, consider workload partitioning, careful resource requests/limits, and strict placement rules to protect control-plane services.

## 12. Method 9 — Infrastructure node protection

### 12.1 Goal

Infrastructure nodes are used for cluster-supporting workloads such as routers, registry, monitoring, logging, GitOps, Pipelines, ODF, service mesh, or other supported platform components.

You usually want:

- Infra workloads should run on infra nodes.
- User application workloads should not run on infra nodes.

### 12.2 Basic infra node pattern

Label infra nodes:

```bash
oc label node worker-infra-1.example.com node-role.kubernetes.io/infra=""
oc label node worker-infra-2.example.com node-role.kubernetes.io/infra=""
```

Taint infra nodes:

```bash
oc adm taint node worker-infra-1.example.com node-role.kubernetes.io/infra=reserved:NoSchedule
oc adm taint node worker-infra-2.example.com node-role.kubernetes.io/infra=reserved:NoSchedule
```

Then configure only selected infra workloads with:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Equal
  value: reserved
  effect: NoSchedule
```

### 12.3 IngressController example

Many OpenShift operators expose supported placement fields. For ingress, the concept looks like this:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Equal
      value: reserved
      effect: NoSchedule
```

Always confirm the exact CRD schema in your cluster:

```bash
oc explain ingresscontroller.spec.nodePlacement --api-version=operator.openshift.io/v1
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
```

### 12.4 Important infra-node caution

Do not simply taint infra nodes and assume operators will automatically tolerate the taint. If an operator-managed component does not have matching tolerations, its pods may become pending.

Correct order:

1. Confirm operator supports node placement/tolerations.
2. Configure operator-managed workload placement.
3. Verify new pods can run on infra nodes.
4. Add taint to infra nodes.
5. Watch rollout and events.

## 13. Advanced decision matrix

| Scenario | Recommended action | Why |
|---|---|---|
| Need to reboot worker node tonight | Cordon → drain → reboot → uncordon | Standard controlled maintenance |
| Node has suspected disk issue | Cordon immediately; drain if safe; investigate | Stops new placement first, then evacuates |
| Keep user apps off infra nodes | Taint infra nodes + configure infra workload tolerations | Node refuses ordinary workloads |
| Keep one app away from one bad node | Required node affinity `hostname NotIn` | App-specific hard exclusion |
| Keep all apps in a project on Team A nodes | Namespace annotation `openshift.io/node-selector` | Project-level governance |
| Keep all normal pods on worker nodes | Cluster default node selector, with caution | Broad default policy |
| Temporarily discourage scheduling but allow fallback | `PreferNoSchedule` taint or preferred affinity | Soft avoidance |
| Evict pods immediately from node | `NoExecute` taint or drain | `NoExecute` is direct; drain is maintenance-safe |
| Dedicated GPU nodes | Label + taint GPU nodes; add selector + toleration to GPU pods | Prevents non-GPU workload waste |
| Decommission node | Cordon → drain → scale MachineSet/delete node/decommission host | Clean removal |
| Pods pending due to “untolerated taint” | Add proper toleration or remove taint | Scheduler is correctly blocking placement |

## 14. End-to-end scenario: prevent workloads from using one node

### 14.1 Requirement

`worker-1.example.com` has intermittent hardware issues. You want no new user workloads on it while you investigate, but existing workloads can continue for now.

### 14.2 Option A — Fast admin response

```bash
oc adm cordon worker-1.example.com
```

Verify:

```bash
oc get node worker-1.example.com
oc get pods -A --field-selector spec.nodeName=worker-1.example.com -o wide
```

This is the least disruptive immediate response.

### 14.3 Option B — Prevent only a specific application

Patch the Deployment with node affinity excluding that hostname:

```bash
oc patch deployment backend -n app-team-a --type='merge' -p '
{
  "spec": {
    "template": {
      "spec": {
        "affinity": {
          "nodeAffinity": {
            "requiredDuringSchedulingIgnoredDuringExecution": {
              "nodeSelectorTerms": [
                {
                  "matchExpressions": [
                    {
                      "key": "kubernetes.io/hostname",
                      "operator": "NotIn",
                      "values": ["worker-1.example.com"]
                    }
                  ]
                }
              ]
            }
          }
        }
      }
    }
  }
}'
```

Restart rollout to move existing pods:

```bash
oc rollout restart deployment/backend -n app-team-a
oc rollout status deployment/backend -n app-team-a
oc get pods -n app-team-a -o wide
```

### 14.4 Option C — Quarantine node for all normal workloads

```bash
oc adm taint node worker-1.example.com quarantine=true:NoSchedule
```

This prevents future non-tolerating pods, even after the node is uncordoned. Existing pods remain.

To evict existing non-tolerating pods:

```bash
oc adm taint node worker-1.example.com quarantine=true:NoExecute
```

Use `NoExecute` carefully because it can evict running pods.

## 16. Common mistakes and fixes

### Mistake 1: “I cordoned the node but pods are still running there”

Expected behavior. Cordon blocks new scheduling only. Existing pods remain.

Fix if you need to move them:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

### Mistake 2: “I added `NoSchedule` taint but existing pods did not leave”

Expected behavior. `NoSchedule` affects new scheduling only.

Fix if eviction is required:

```bash
oc adm taint node <node> key=value:NoExecute
```

or perform controlled drain:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

### Mistake 3: “A pod still scheduled on a tainted node”

Possible causes:

- Pod has matching toleration.
- It is a DaemonSet pod with broad default tolerations.
- It is a system/operator pod.
- Taint effect is `PreferNoSchedule`, which is only a soft preference.
- The pod was already running before `NoSchedule` taint was added.

Check:

```bash
oc get pod <pod> -n <ns> -o yaml | grep -A20 tolerations
oc describe node <node> | grep -i Taints -A3
```

### Mistake 4: “I added a toleration but the pod does not run on the dedicated node”

A toleration permits scheduling but does not select the node.

Fix: add `nodeSelector` or node affinity:

```yaml
nodeSelector:
  workload-type: gpu
```

### Mistake 5: “Project node selector broke my deployment”

The pod selector probably conflicts with the namespace annotation.

Check:

```bash
oc get ns <ns> -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
oc get deploy <deploy> -n <ns> -o yaml | grep -A10 nodeSelector
```

Fix by aligning the pod selector with the namespace selector or changing the namespace selector.

### Mistake 6: “Drain is stuck”

Common causes:

- PDB blocks eviction.
- Pod uses `emptyDir` and you did not pass `--delete-emptydir-data`.
- Bare pod requires `--force`.
- DaemonSet pods require `--ignore-daemonsets`.
- Pod finalizer is stuck.
- Storage detach or CSI problem.

Commands:

```bash
oc get pdb -A
oc describe pod <pod> -n <ns>
oc get events -A --sort-by=.lastTimestamp | tail -50
```

### Mistake 7: “I labeled a node but replacement nodes do not have the label”

Direct node labels are not necessarily persistent after node replacement in Machine API clusters.

Fix: apply labels through MachineSet template or your node provisioning automation.

### Mistake 8: “Default node selector made system pods pending”

Cluster-wide defaults can affect many pods. Use them carefully.

Fix:

```bash
oc edit scheduler cluster
```

Remove or correct:

```yaml
spec:
  defaultNodeSelector: ...
```

Then recreate affected pods if needed.

## 17. Production-grade design patterns

### 17.1 Maintenance pattern

Goal: safely patch or reboot nodes.

```bash
NODE=worker-1.example.com
oc adm cordon $NODE
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --timeout=15m
# perform maintenance
oc adm uncordon $NODE
```

Recommended pre-checks:

```bash
oc get nodes
oc adm top nodes
oc get pods -A --field-selector spec.nodeName=$NODE -o wide
oc get pdb -A
oc get mcp
```

### 17.2 Quarantine pattern

Goal: keep workloads away from suspicious nodes until investigation completes.

```bash
oc adm cordon worker-1.example.com
oc adm taint node worker-1.example.com quarantine=true:NoSchedule
```

If existing pods must leave:

```bash
oc adm drain worker-1.example.com --ignore-daemonsets --delete-emptydir-data
```

or:

```bash
oc adm taint node worker-1.example.com quarantine=true:NoExecute
```

### 17.3 Dedicated hardware pattern

Goal: protect expensive or special hardware nodes.

```bash
oc label node gpu-worker-1 workload-type=gpu
oc adm taint node gpu-worker-1 workload-type=gpu:NoSchedule
```

Approved workloads:

```yaml
nodeSelector:
  workload-type: gpu
tolerations:
- key: workload-type
  operator: Equal
  value: gpu
  effect: NoSchedule
```

### 17.4 Compliance-zone pattern

Goal: ensure PCI workloads run only on PCI nodes.

Nodes:

```bash
oc label node pci-worker-1 compliance-zone=pci
oc label node pci-worker-2 compliance-zone=pci
oc adm taint node pci-worker-1 compliance-zone=pci:NoSchedule
oc adm taint node pci-worker-2 compliance-zone=pci:NoSchedule
```

Namespace:

```bash
oc annotate ns payments-prod openshift.io/node-selector='compliance-zone=pci' --overwrite
```

Workloads:

```yaml
tolerations:
- key: compliance-zone
  operator: Equal
  value: pci
  effect: NoSchedule
```

### 17.5 Noisy-neighbor isolation pattern

Goal: prevent batch workloads from affecting latency-sensitive apps.

Batch nodes:

```bash
oc label node batch-worker-1 workload-class=batch
oc adm taint node batch-worker-1 workload-class=batch:NoSchedule
```

Batch jobs:

```yaml
nodeSelector:
  workload-class: batch
tolerations:
- key: workload-class
  operator: Equal
  value: batch
  effect: NoSchedule
```

Latency-sensitive apps:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: workload-class
          operator: NotIn
          values:
          - batch
```

## 18. Exam and interview notes

### 18.1 Short definitions

**Cordon:** Marks node unschedulable. No new pods. Existing pods stay.

**Drain:** Evicts pods from a node, usually after cordon, so they can be recreated elsewhere.

**Taint:** Node-side repulsion rule. Prevents pods without matching toleration.

**Toleration:** Pod-side permission to schedule onto a tainted node.

**Node selector:** Simple pod rule requiring matching node labels.

**Node affinity:** Advanced pod rule requiring or preferring node label expressions.

**Project node selector:** OpenShift namespace annotation that constrains pods in that project.

**Default node selector:** Cluster-wide scheduler default selector; powerful but risky.

### 18.2 Most common exam commands

```bash
# View nodes
oc get nodes -o wide
oc describe node <node>

# Stop scheduling to node
oc adm cordon <node>

# Allow scheduling again
oc adm uncordon <node>

# Evacuate pods
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data

# Add taint
oc adm taint node <node> key=value:NoSchedule

# Remove taint
oc adm taint node <node> key-

# Label node
oc label node <node> key=value

# Remove label
oc label node <node> key-

# Show pods on node
oc get pods -A --field-selector spec.nodeName=<node> -o wide

# Check scheduler config
oc get scheduler cluster -o yaml

# Set namespace node selector
oc annotate ns <namespace> openshift.io/node-selector='key=value' --overwrite
```

### 18.3 Fast troubleshooting flow

1. Is the pod pending?

```bash
oc get pods -n <ns>
oc describe pod <pod> -n <ns>
```

2. Does the event mention taints?

```bash
oc describe node <node> | grep -i Taints -A3
oc get pod <pod> -n <ns> -o yaml | grep -A20 tolerations
```

3. Does the event mention node selector or affinity?

```bash
oc get pod <pod> -n <ns> -o yaml | grep -A50 'nodeSelector\|affinity'
oc get nodes --show-labels
```

4. Is the namespace injecting a selector?

```bash
oc get ns <ns> -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
```

5. Is the node cordoned?

```bash
oc get nodes
oc describe node <node> | grep -i Unschedulable
```

6. Is there enough capacity?

```bash
oc adm top nodes
oc describe node <node> | grep -A8 Allocatable
```

## 20. Hands-on lab: Prevent placement using taint

### Objective

Block normal pods from scheduling on one node using `NoSchedule`.

### Steps

```bash
NODE=worker-1.example.com

oc describe node $NODE | grep -i Taints -A2
```

Create a normal pod:

```bash

oc run normal-pod --image=registry.access.redhat.com/ubi9/ubi -- sleep 3600
oc describe pod normal-pod
```

If the cluster has other nodes, the pod should run elsewhere. If all available nodes are blocked by taints, the pod remains pending with an event about untolerated taints.

Create a pod with matching toleration:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: tolerated-pod
  namespace: taint-test
spec:
  tolerations:
  - key: dedicated
    operator: Equal
    value: blocked
    effect: NoSchedule
  containers:
  - name: ubi
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "3600"]
```

Apply:

```bash
oc apply -f tolerated-pod.yaml
oc get pod tolerated-pod -o wide
```

Cleanup:

```bash
oc delete project taint-test
oc adm taint node $NODE dedicated-
```

### Expected learning

Taint blocks pods without matching toleration. Toleration permits but does not force node selection.

## 27. Practical comparison: cordon vs taint vs affinity

| Feature | Cordon | Taint `NoSchedule` | Taint `NoExecute` | Node affinity `NotIn` |
|---|---|---|---|---|
| Scope | Whole node | Whole node except tolerating pods | Whole node except tolerating pods | Specific workload |
| Stops new pods | Yes | Yes for non-tolerating pods | Yes for non-tolerating pods | Yes for that workload |
| Evicts existing pods | No | No | Yes for non-tolerating pods | No |
| Good for maintenance | Yes | Sometimes | Risky | No |
| Good for permanent policy | No | Yes | Sometimes | Yes |
| Requires pod spec change | No | Only for allowed pods | Only for allowed pods | Yes |
| Reversible | Yes | Yes | Yes but disruptive | Yes |
| Typical command | `oc adm cordon` | `oc adm taint` | `oc adm taint` | `oc patch deployment` |

## 28. Deep troubleshooting examples

### 28.1 Pending pod due to untolerated taint

Event:

```text
0/3 nodes are available: 1 node(s) had untolerated taint {workload: gpu}
```

Diagnosis:

```bash
oc describe node gpu-worker-1 | grep -i Taints -A3
oc get pod <pod> -n <ns> -o yaml | grep -A20 tolerations
```

Fix options:

- Add toleration if the pod is approved for that node.
- Remove taint if the taint is wrong.
- Add nodeSelector/affinity if the pod must target a different node pool.

### 28.2 Pending pod due to node selector mismatch

Event:

```text
0/5 nodes are available: 5 node(s) didn't match Pod's node affinity/selector
```

Diagnosis:

```bash
oc get pod <pod> -n <ns> -o yaml | grep -A30 'nodeSelector\|affinity'
oc get nodes -L placement,team,workload-type
oc get ns <ns> -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
```

Fix options:

- Correct node labels.
- Correct pod selector/affinity.
- Correct project selector.
- Add more nodes matching the policy.

### 28.3 Pod scheduled onto a node you thought was blocked

Diagnosis flow:

```bash
POD=<pod>
NS=<namespace>
NODE=<node>

oc get pod $POD -n $NS -o wide
oc get pod $POD -n $NS -o yaml | grep -A30 tolerations
oc get pod $POD -n $NS -o yaml | grep -A50 'nodeSelector\|affinity'
oc describe node $NODE | grep -i Taints -A5
oc get node $NODE --show-labels
```

Likely causes:

- Taint is `PreferNoSchedule` only.
- Pod has a broad `Exists` toleration.
- Pod was already on node before `NoSchedule` taint.
- Node was uncordoned.
- The workload has `nodeName` set manually.
- DaemonSet/controller created the pod with tolerations.

### 28.4 Drain blocked by PDB

Diagnosis:

```bash
oc get pdb -A
oc describe pdb <pdb> -n <ns>
oc get deploy,sts,pod -n <ns> -o wide
```

Resolution path:

- Increase replicas.
- Fix unready pods first.
- Wait until `ALLOWED DISRUPTIONS` is greater than zero.
- Coordinate application maintenance window.

### 28.5 Drain blocked by storage

Symptoms:

- Pods stuck in `Terminating`.
- PVC/PV detach takes long time.
- CSI volume attachment errors.

Commands:

```bash
oc describe pod <pod> -n <ns>
oc get pvc -n <ns>
oc describe pvc <pvc> -n <ns>
oc get volumeattachment
oc get events -A --sort-by=.lastTimestamp | tail -100
```

Resolution depends on storage backend. Avoid force deletion of stateful pods unless you understand data consistency impact.

## 29. Best practices

1. Use `cordon` before `drain`.
2. Use `drain --dry-run=server` before draining important nodes.
3. Prefer `NoSchedule` for reservation, `NoExecute` for eviction/quarantine.
4. Combine taints with node selectors or affinity for dedicated nodes.
5. Use project node selectors for namespace-level governance.
6. Use cluster-wide default node selectors sparingly.
7. Do not directly edit node labels/taints as your only long-term policy if nodes are MachineSet-managed.
8. Avoid hostnames in app specs for long-term rules; use stable labels where possible.
9. Keep at least enough schedulable capacity before draining nodes.
10. Review PDBs before maintenance.
11. Do not weaken PDBs without application owner approval.
12. Treat `NoExecute` as disruptive.
13. Watch events during placement changes.
14. Document every taint and label with purpose and owner.
15. Periodically audit taints, selectors, and pending pods.

## 32. Senior-admin recommendations

For a 10-year OpenShift/Linux administrator, the mature approach is:

1. **Use cordon/drain for lifecycle operations.**  
   This is operational control for maintenance, patching, rebooting, and decommissioning.

2. **Use taints for node-side protection.**  
   Taints are ideal when a node pool must reject ordinary workloads.

3. **Use selectors/affinity for workload-side intent.**  
   Workloads should declare where they are allowed to run.

4. **Use project node selectors for tenant governance.**  
   This keeps developers from accidentally escaping assigned node pools.

5. **Avoid cluster-wide defaults unless your governance model is very clear.**  
   A wrong default node selector can cause broad scheduling failures.

6. **Make policy persistent at the node-pool level.**  
   In Machine API clusters, configure MachineSets or supported operator CRs so replacement nodes inherit labels and taints.

7. **Always verify with events.**  
   The scheduler tells you exactly why a pod is pending. `oc describe pod` is your first diagnostic command.

## 34. Final takeaway

To prevent workload placement on specific OpenShift nodes, select the mechanism based on intent:

- **Temporary stop:** `oc adm cordon`
- **Move workloads away:** `oc adm drain`
- **Reserve nodes:** taints and tolerations
- **Exclude nodes for one app:** node affinity with `NotIn` or `DoesNotExist`
- **Control namespace placement:** project node selector
- **Control cluster default:** scheduler `defaultNodeSelector`
- **Protect control plane:** `mastersSchedulable: false` plus control-plane taints

The most reliable production design usually combines **node labels + taints + workload selectors/affinity + tolerations**, with clear ownership and audit commands.
