# Pod Topology Spread Constraints in OpenShift

**Topic:** Pod Scheduling and Workload Placement  
**Audience:** Advanced OpenShift Administration / DO380-level administrators  
**Experience level:** Production-focused explanation for an administrator with ~10 years of Linux, Kubernetes, and OpenShift experience  

---

## 1. What are Pod topology spread constraints?

**Pod topology spread constraints** are Kubernetes/OpenShift scheduling rules that control how replicas of a workload are distributed across topology domains such as:

- nodes
- zones
- regions
- racks
- data centers
- machine config pools
- custom failure domains

They are configured under:

```yaml
spec:
  template:
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: payment-api
```

The main goal is to avoid placing too many matching pods in the same failure domain.

In simple words:

> Topology spread constraints tell the scheduler: “Keep these pods balanced across this type of infrastructure boundary.”

For example, if you run six replicas of an application in a three-zone OpenShift cluster, you usually want this:

```text
zone-a: 2 pods
zone-b: 2 pods
zone-c: 2 pods
```

Not this:

```text
zone-a: 6 pods
zone-b: 0 pods
zone-c: 0 pods
```

The second placement is dangerous because failure of `zone-a` can take down the complete application.

---

## 2. Why this matters in Advanced OpenShift Administration

In a real OpenShift environment, scheduling is not only about “can this pod run somewhere?” It is about:

- high availability
- zone failure tolerance
- node failure tolerance
- upgrade safety
- maintenance safety
- workload isolation
- latency reduction
- storage locality
- avoiding noisy neighbor concentration
- preventing all replicas from landing on the same physical rack or hypervisor cluster

Topology spread constraints are important when you manage:

- multi-zone OpenShift clusters
- bare-metal OpenShift clusters
- OpenShift Virtualization environments
- telco / edge clusters
- stateful workloads
- OpenShift Data Foundation or storage-sensitive apps
- high-availability application platforms
- production Deployments with HorizontalPodAutoscaler
- workloads that must survive node drains and upgrades

They are more flexible than simple pod anti-affinity because they let you define **how much imbalance is acceptable**, instead of only saying “do not colocate.”

## 3. The problem topology spread constraints solve

Assume you have this cluster:

```text
worker-a1   zone=zone-a
worker-a2   zone=zone-a
worker-b1   zone=zone-b
worker-b2   zone=zone-b
worker-c1   zone=zone-c
worker-c2   zone=zone-c
```

You deploy an application with six replicas.

Without explicit constraints, the scheduler considers CPU, memory, taints, node affinity, resource requests, existing load, and default spread behavior. However, it may still place pods in a way that is not aligned with your application HA design.

With topology spread constraints, you explicitly define:

```text
Spread pods matching app=payment-api across topology.kubernetes.io/zone.
Allow maximum skew of 1.
Do not schedule a new pod if the rule would be violated.
```

That gives you predictable placement for production workloads.

## 4. Core terms

### 4.1 Topology

A **topology** is a logical or physical grouping of nodes.

Examples:

```text
topology.kubernetes.io/zone=zone-a
topology.kubernetes.io/region=us-east-1
kubernetes.io/hostname=worker01.example.com
rack=rack-22
datacenter=dc-delhi-01
mcp=worker-a
node-role.kubernetes.io/infra=
```

The scheduler reads topology information from **node labels**.

Example:

```bash
oc get nodes --show-labels
```

Common topology labels:

```text
kubernetes.io/hostname
 topology.kubernetes.io/zone
 topology.kubernetes.io/region
```

On cloud-based OpenShift clusters, zone and region labels are often populated automatically by the infrastructure/cloud provider integration. On bare metal or custom environments, you may need to label nodes yourself.

---

### 4.2 Topology domain

A **topology domain** is one value of a topology key.

Example:

```yaml
topologyKey: topology.kubernetes.io/zone
```

If your nodes have these labels:

```text
worker-1 topology.kubernetes.io/zone=zone-a
worker-2 topology.kubernetes.io/zone=zone-a
worker-3 topology.kubernetes.io/zone=zone-b
worker-4 topology.kubernetes.io/zone=zone-c
```

Then the domains are:

```text
zone-a
zone-b
zone-c
```

If you use:

```yaml
topologyKey: kubernetes.io/hostname
```

Each node hostname becomes a separate topology domain.

---

### 4.3 `labelSelector`

The `labelSelector` defines **which existing pods are counted** for spreading.

Example:

```yaml
labelSelector:
  matchLabels:
    app: payment-api
```

This means:

> Count pods in the same namespace with label `app=payment-api`, then spread the incoming pod based on that count.

Important production rule:

> The pod template labels should match the topology spread `labelSelector`.

Correct example:

```yaml
metadata:
  labels:
    app: payment-api
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: payment-api
```

Bad example:

```yaml
metadata:
  labels:
    app: payment-api-v2
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: payment-api
```

In the bad example, the pod may not count itself correctly after scheduling. This can cause confusing placement behavior.

---

### 4.4 `topologyKey`

The `topologyKey` is the node label key used to divide nodes into topology domains.

Examples:

```yaml
topologyKey: kubernetes.io/hostname
```

Spread across individual nodes.

```yaml
topologyKey: topology.kubernetes.io/zone
```

Spread across zones.

```yaml
topologyKey: rack
```

Spread across custom rack labels.

```yaml
topologyKey: datacenter
```

Spread across data centers.

The key must exist on eligible nodes. If nodes are missing the topology key, the scheduler can ignore those nodes for that constraint, which may lead to unexpected placement or Pending pods.

---

### 4.5 `maxSkew`

`maxSkew` defines the maximum allowed difference in matching pod count between topology domains.

Example:

```yaml
maxSkew: 1
```

This means the scheduler tries to keep the count difference between domains no more than 1.

Example distribution across zones:

```text
zone-a: 2
zone-b: 2
zone-c: 1
```

Skew calculation:

```text
minimum pod count = 1
zone-a skew = 2 - 1 = 1
zone-b skew = 2 - 1 = 1
zone-c skew = 1 - 1 = 0
```

This is valid for `maxSkew: 1`.

Another distribution:

```text
zone-a: 4
zone-b: 1
zone-c: 1
```

Skew calculation:

```text
minimum pod count = 1
zone-a skew = 4 - 1 = 3
zone-b skew = 1 - 1 = 0
zone-c skew = 1 - 1 = 0
```

This violates `maxSkew: 1`.

---

### 4.6 `whenUnsatisfiable`

This controls what happens when the spread rule cannot be satisfied.

There are two values:

```yaml
whenUnsatisfiable: DoNotSchedule
```

Hard rule. If placing the pod would violate the skew, the scheduler leaves the pod Pending.

```yaml
whenUnsatisfiable: ScheduleAnyway
```

Soft rule. The scheduler can still place the pod, but gives preference to nodes that reduce imbalance.

Use `DoNotSchedule` for strict HA requirements.

Use `ScheduleAnyway` when availability is important but you prefer the application to run somewhere instead of staying Pending.

---

### 4.7 `minDomains`

`minDomains` defines the minimum number of eligible topology domains required for a strict spread calculation.

Example:

```yaml
minDomains: 3
```

This is useful when your design requires at least three zones or three racks.

Example:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  minDomains: 3
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: payment-api
```

Meaning:

> Spread `payment-api` pods across at least three eligible zones. If fewer than three domains are available, calculate skew as if the global minimum were zero, making strict placement harder to satisfy.

Use this carefully. It can protect HA design, but it can also keep pods Pending if your cluster does not currently have enough eligible domains.

---

### 4.8 `matchLabelKeys`

`matchLabelKeys` lets the scheduler use label values from the incoming pod when selecting the group of pods to spread with.

Common use case:

```yaml
matchLabelKeys:
- pod-template-hash
```

This is useful for Deployments during rolling updates. The Deployment controller automatically adds `pod-template-hash` to pods from different ReplicaSets.

Without `matchLabelKeys`, old and new revision pods may be counted together during a rollout. After the old pods are removed, the remaining new pods may end up less evenly spread than expected.

Example:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: payment-api
  matchLabelKeys:
  - pod-template-hash
```

For production Deployments with frequent rollouts, this is a strong pattern.

---

### 4.9 `nodeAffinityPolicy`

`nodeAffinityPolicy` controls whether node affinity and node selectors are honored when calculating eligible topology domains.

Values:

```yaml
nodeAffinityPolicy: Honor
nodeAffinityPolicy: Ignore
```

- `Honor`: calculate spread only across nodes that match the pod's node affinity or node selector.
- `Ignore`: calculate spread across topology domains without considering the pod's node affinity or node selector.

Production recommendation:

```yaml
nodeAffinityPolicy: Honor
```

This is usually safer because the scheduler calculates spread only across nodes where the pod can actually run.

---

### 4.10 `nodeTaintsPolicy`

`nodeTaintsPolicy` controls whether node taints are considered while calculating eligible topology domains.

Values:

```yaml
nodeTaintsPolicy: Honor
nodeTaintsPolicy: Ignore
```

- `Honor`: count only nodes whose taints are tolerated by the incoming pod.
- `Ignore`: ignore node taints during skew calculation.

Production recommendation:

```yaml
nodeTaintsPolicy: Honor
```

This prevents the scheduler from calculating spread across domains where the pod cannot actually run because of untolerated taints.

## 5. Scheduler mental model

When a new pod is created, the scheduler roughly asks:

```text
1. Which existing pods match the topologySpreadConstraints labelSelector?
2. Which topology key should be used?
3. Which nodes are eligible after nodeSelector, nodeAffinity, taints, resources, and other filters?
4. How many matching pods are already present in each topology domain?
5. Would placing this new pod in a candidate domain violate maxSkew?
6. If yes, should I reject the node or only lower its score?
7. Pick the best node after all scheduler plugins score the candidates.
```

Important points:

- Topology spread constraints are evaluated during scheduling.
- They do not automatically rebalance already running pods.
- They count pods in the same namespace.
- They depend on accurate labels on nodes and pods.
- Multiple constraints are ANDed; all must be satisfied.
- Missing topology labels can cause unexpected behavior.
- `DoNotSchedule` can make pods Pending.
- `ScheduleAnyway` improves balance but does not guarantee perfect spread.

## 6. Basic Deployment example: spread across nodes

This example spreads application replicas across nodes using `kubernetes.io/hostname`.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payments
spec:
  replicas: 4
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: payment-api
      containers:
      - name: payment-api
        image: registry.ocp4.example.com:8443/redhattraining/hello-world-nginx:v1.0
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 512Mi
```

Expected behavior:

- The scheduler counts existing `app=payment-api` pods in the `payments` namespace.
- It groups nodes by hostname.
- It tries to keep the pod count per node balanced.
- If placing a pod would exceed `maxSkew: 1`, the pod remains Pending.

Use this when you want to avoid multiple replicas on the same node.

This is common in cloud OpenShift or multi-zone bare-metal OpenShift.

```yaml

```

## 8. Combining node-level and zone-level spreading

A strong HA pattern is to spread across zones and also avoid piling pods onto the same node.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: ecommerce
spec:
  replicas: 6
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: order-service
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: order-service
      containers:
      - name: order-service
        image: quay.io/example/order-service:v1
        resources:
          requests:
            cpu: 200m
            memory: 256Mi
```

Design explanation:

- Zone spread is hard: do not break zone HA.
- Node spread is soft: prefer better node distribution, but do not block scheduling unnecessarily.

This is often more practical than making both rules hard.

## 9. Hard vs soft spread rules

### 9.1 Hard spread

```yaml
whenUnsatisfiable: DoNotSchedule
```

Use when:

- regulatory or HA rules require strict distribution
- application cannot tolerate colocated replicas
- zone failure tolerance is mandatory
- you want failures to be visible as Pending pods

Risk:

- pods may remain Pending if the cluster has insufficient capacity or missing labels

Example Pending event:

```text
0/6 nodes are available: 3 node(s) didn't match pod topology spread constraints.
```

---

### 9.2 Soft spread

```yaml
whenUnsatisfiable: ScheduleAnyway
```

Use when:

- workload should run even if perfect spread is impossible
- cluster capacity is uneven
- non-critical services need best-effort HA
- HPA can create temporary imbalance
- you prefer availability over perfect placement

Risk:

- pods may be scheduled in a less ideal distribution

## 10. Skew explained deeply

Assume three zones:

```text
zone-a
zone-b
zone-c
```

Existing matching pods:

```text
zone-a: 2
zone-b: 1
zone-c: 1
```

Global minimum:

```text
1
```

Skew:

```text
zone-a: 2 - 1 = 1
zone-b: 1 - 1 = 0
zone-c: 1 - 1 = 0
```

With `maxSkew: 1`, this is valid.

Now try to schedule one more pod into `zone-a`:

```text
zone-a: 3
zone-b: 1
zone-c: 1
```

Global minimum:

```text
1
```

Skew:

```text
zone-a: 3 - 1 = 2
```

This violates `maxSkew: 1`.

The scheduler will reject `zone-a` if `whenUnsatisfiable: DoNotSchedule`.

It will prefer `zone-b` or `zone-c` if `whenUnsatisfiable: ScheduleAnyway`.

## 13. `minDomains` production pattern

Use `minDomains` when you want to enforce that the scheduler considers a minimum number of topology domains.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: fraud-engine
  namespace: banking
spec:
  replicas: 3
  selector:
    matchLabels:
      app: fraud-engine
  template:
    metadata:
      labels:
        app: fraud-engine
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        minDomains: 3
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: fraud-engine
      containers:
      - name: fraud-engine
        image: quay.io/example/fraud-engine:v2
        resources:
          requests:
            cpu: 500m
            memory: 1Gi
```

Meaning:

- The workload expects three eligible zones.
- Distribution must remain strict.
- If fewer than three eligible zones exist, pods may not schedule as expected.

Use cases:

- strict three-zone HA
- telco HA domain design
- financial workloads
- critical control-plane-like application services
- applications with quorum-sensitive topology rules

Be careful with small labs. In a two-node or single-zone lab, this can intentionally block pod scheduling.

## 14. `matchLabelKeys` for safe rolling updates

Recommended pattern for Deployments:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-api
  namespace: ecommerce
spec:
  replicas: 6
  selector:
    matchLabels:
      app: catalog-api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
  template:
    metadata:
      labels:
        app: catalog-api
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: catalog-api
        matchLabelKeys:
        - pod-template-hash
      containers:
      - name: catalog-api
        image: quay.io/example/catalog-api:v2
        resources:
          requests:
            cpu: 200m
            memory: 256Mi
```

Why this matters:

During a rolling update, old and new ReplicaSet pods can coexist. `matchLabelKeys` allows the scheduler to use the incoming pod's label value, such as `pod-template-hash`, so that spreading can be calculated per revision.

This avoids misleading spread calculations where old revision pods influence placement of new revision pods.

## 15. Topology spread with node affinity

A common advanced pattern is:

1. Use node affinity to restrict a workload to a node pool.
2. Use topology spread constraints to spread pods within that selected node pool.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ml-inference
  namespace: ai
spec:
  replicas: 4
  selector:
    matchLabels:
      app: ml-inference
  template:
    metadata:
      labels:
        app: ml-inference
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: workload
                operator: In
                values:
                - gpu
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: ml-inference
        nodeAffinityPolicy: Honor
      containers:
      - name: ml-inference
        image: quay.io/example/ml-inference:v1
        resources:
          requests:
            cpu: "1"
            memory: 2Gi
```

Explanation:

- Only nodes labeled `workload=gpu` are eligible.
- Spread is calculated across zones that contain eligible GPU nodes.
- `nodeAffinityPolicy: Honor` avoids calculating skew across zones where the pod cannot run.

## 16. Topology spread with taints and tolerations

Assume dedicated infra nodes or GPU nodes are tainted:

```bash
oc adm taint nodes worker-gpu-1 dedicated=gpu:NoSchedule
oc adm taint nodes worker-gpu-2 dedicated=gpu:NoSchedule
```

Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gpu-worker
  namespace: ai
spec:
  replicas: 2
  selector:
    matchLabels:
      app: gpu-worker
  template:
    metadata:
      labels:
        app: gpu-worker
    spec:
      tolerations:
      - key: dedicated
        operator: Equal
        value: gpu
        effect: NoSchedule
      nodeSelector:
        workload: gpu
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: gpu-worker
        nodeAffinityPolicy: Honor
        nodeTaintsPolicy: Honor
      containers:
      - name: gpu-worker
        image: quay.io/example/gpu-worker:v1
        resources:
          requests:
            cpu: "2"
            memory: 4Gi
```

Explanation:

- Toleration allows scheduling on tainted GPU nodes.
- Node selector restricts workload to GPU nodes.
- Topology spread avoids both replicas landing on the same hostname.
- `nodeTaintsPolicy: Honor` makes skew calculation align with taint/toleration reality.

## 17. StatefulSet example

Stateful workloads need careful topology design. Topology spread constraints can help distribute replicas, but they do not replace storage topology, PV zone binding, anti-affinity, or application quorum design.

Example:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis-ha
  namespace: cache
spec:
  serviceName: redis-ha
  replicas: 3
  selector:
    matchLabels:
      app: redis-ha
  template:
    metadata:
      labels:
        app: redis-ha
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: redis-ha
      containers:
      - name: redis
        image: redis:7
        ports:
        - containerPort: 6379
        volumeMounts:
        - name: data
          mountPath: /data
        resources:
          requests:
            cpu: 200m
            memory: 512Mi
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes:
      - ReadWriteOnce
      resources:
        requests:
          storage: 10Gi
```

Important StatefulSet notes:

- Storage class topology must support the selected zone placement.
- If PVC binding is delayed with `WaitForFirstConsumer`, scheduler and storage provisioning interact.
- If a PV is zone-bound, the pod must schedule in the same zone as the volume.
- Incorrect topology constraints can conflict with volume node affinity.
- For quorum systems, combine topology spread with PodDisruptionBudget.

## 18. PodDisruptionBudget plus topology spread

Topology spread protects placement. PodDisruptionBudget protects voluntary disruption.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-api-pdb
  namespace: payments
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: payment-api
```

Use both:

```text
Topology spread constraint: keep replicas across failure domains.
PDB: prevent too many replicas from being evicted during drains/upgrades.
```

For production OpenShift upgrades, this combination is important.

## 19. HPA interaction

HorizontalPodAutoscaler can increase or decrease replicas dynamically.

Topology spread constraints are evaluated when new pods are scheduled.

Example:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: payment-api-hpa
  namespace: payments
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-api
  minReplicas: 3
  maxReplicas: 12
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60
```

Design notes:

- HPA scale-out creates new pods; scheduler applies spread rules.
- HPA scale-down removes pods based on controller behavior, not necessarily to preserve perfect spread.
- After scale-down, distribution can become imbalanced.
- Topology spread constraints do not automatically move running pods.
- Descheduler may be needed in some environments to rebalance pods after topology changes.

---

## 20. DaemonSet interaction

DaemonSets already create one pod per eligible node.

Topology spread constraints are usually not necessary for DaemonSets because the controller itself ensures node-level distribution.

Use topology spread constraints mainly for:

- Deployment
- StatefulSet
- ReplicaSet
- ReplicationController
- custom controllers that create replicated pods

## 21. How topology spread differs from pod anti-affinity

### Pod anti-affinity example

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: payment-api
      topologyKey: kubernetes.io/hostname
```

This means:

> Do not place another `payment-api` pod on a node where one already exists.

This is strict and binary.

### Topology spread example

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: payment-api
```

This means:

> Keep pod count balanced across hostnames with a skew of 1.

This is more flexible.

### Comparison

| Feature | Pod anti-affinity | Topology spread constraints |
|---|---|---|
| Main purpose | Keep pods apart | Keep pods balanced |
| Strict mode | `requiredDuringScheduling...` | `DoNotSchedule` |
| Soft mode | `preferredDuringScheduling...` | `ScheduleAnyway` |
| Can define allowed imbalance | No | Yes, with `maxSkew` |
| Good for 2 replicas | Yes | Yes |
| Good for many replicas | Sometimes too restrictive | Yes |
| Good for zone distribution | Yes, but less flexible | Yes |
| Works well with autoscaling | Can become restrictive | Usually better |
| Troubleshooting complexity | Medium | Medium to high |

Production guidance:

- Use anti-affinity when you need a strict “never colocate” rule.
- Use topology spread constraints when you need balanced distribution at scale.
- Avoid unnecessary hard anti-affinity for large deployments; it can block scheduling.

## 22. Relationship with nodeSelector, node affinity, taints, and tolerations

Topology spread does not replace other placement mechanisms.

Think of scheduling controls like layers:

```text
1. Node labels define infrastructure meaning.
2. nodeSelector / nodeAffinity select eligible nodes.
3. Taints and tolerations repel or allow workloads.
4. Topology spread balances pods across domains.
5. Resource requests decide whether a node has enough allocatable capacity.
6. PDB controls disruption, not initial scheduling.
```

Example design:

```text
Requirement:
Run payment pods only on PCI nodes.
Spread them across zones.
Avoid putting too many on the same node.
```

Implementation:

```yaml
nodeSelector:
  compliance: pci

topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: payment-api
  nodeAffinityPolicy: Honor
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: ScheduleAnyway
  labelSelector:
    matchLabels:
      app: payment-api
  nodeAffinityPolicy: Honor
```

## 23. Full production manifest

```yaml

metadata:
  name: payments
---

kind: Deployment

  name: payment-api
  namespace: payments
  labels:
    app: payment-api
spec:
  replicas: 6
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
        tier: backend
    spec:
      nodeSelector:
        workload: app
      topologySpreadConstraints:
      - maxSkew: 1

            app: payment-api

        - pod-template-hash
        nodeAffinityPolicy: Honor
        nodeTaintsPolicy: Honor
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: payment-api
        matchLabelKeys:
        - pod-template-hash
        nodeAffinityPolicy: Honor
        nodeTaintsPolicy: Honor
      containers:
      - name: payment-api
        image: quay.io/example/payment-api:v1
        imagePullPolicy: IfNotPresent
        ports:
        - containerPort: 8080
          name: http
        readinessProbe:
          httpGet:
            path: /ready
            port: http
          initialDelaySeconds: 10
          periodSeconds: 10
        livenessProbe:
          httpGet:
            path: /healthz
            port: http
          initialDelaySeconds: 30
          periodSeconds: 10
        resources:
          requests:
            cpu: 250m
            memory: 256Mi
          limits:
            cpu: "1"
            memory: 1Gi
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop:
            - ALL
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-api-pdb
  namespace: payments
spec:
  minAvailable: 4
  selector:
    matchLabels:
      app: payment-api
```

Design explanation:

- `nodeSelector` restricts pods to application nodes.
- Zone spread is strict.
- Hostname spread is soft.
- `minDomains: 3` enforces three-domain HA expectation.
- `matchLabelKeys: pod-template-hash` improves rollout behavior.
- `nodeAffinityPolicy: Honor` and `nodeTaintsPolicy: Honor` make skew calculation match real schedulability.
- PDB protects against voluntary disruptions.
- Security context is aligned with OpenShift restricted-style workload expectations.

## 25. Troubleshooting guide

### 25.1 Pod is Pending due to topology spread

Command:

```bash
oc describe pod <pod-name> -n <namespace>
```

Possible event:

```text
0/6 nodes are available: 3 node(s) didn't match pod topology spread constraints.
```

Check:

```bash
oc get nodes -L topology.kubernetes.io/zone,kubernetes.io/hostname
oc get pods -n <namespace> -l app=<app> -o wide
oc get deployment <deployment> -n <namespace> -o yaml
```

Common causes:

- strict `DoNotSchedule` rule
- insufficient nodes in some zones
- missing topology labels on nodes
- wrong pod labels
- wrong `labelSelector`
- node affinity excludes some zones
- taints exclude some zones
- resources unavailable in the less-populated zone
- `minDomains` set higher than actual eligible domains
- volume node affinity conflict

---

### 25.2 Missing topology labels

Check:

```bash
oc get nodes -L topology.kubernetes.io/zone
```

If output is empty for some nodes:

```text
NAME       STATUS   ROLES    AGE   VERSION   ZONE
worker-1   Ready    worker   20d   v1.x      zone-a
worker-2   Ready    worker   20d   v1.x      <none>
```

Fix:

```bash
oc label node worker-2 topology.kubernetes.io/zone=zone-a
```

Important:

- Use consistent labels across nodes.
- Avoid typos such as `topology.kubernetes.io/zones` instead of `topology.kubernetes.io/zone`.
- Do not mix custom `zone` and standard `topology.kubernetes.io/zone` unless intentional.

---

### 25.3 Pod labels do not match selector

Check deployment labels:

```bash
oc get deployment <name> -n <ns> -o jsonpath='{.spec.template.metadata.labels}'
```

Check topology selector:

```bash
oc get deployment <name> -n <ns> -o jsonpath='{.spec.template.spec.topologySpreadConstraints}'
```

The labels must align.

Correct:

```yaml
template:
  metadata:
    labels:
      app: api
  spec:
    topologySpreadConstraints:
    - labelSelector:
        matchLabels:
          app: api
```

Incorrect:

```yaml
template:
  metadata:
    labels:
      app: api-v2
  spec:
    topologySpreadConstraints:
    - labelSelector:
        matchLabels:
          app: api
```

---

### 25.4 Node affinity conflicts with spread

Example problem:

```yaml
nodeSelector:
  workload: pci

topologySpreadConstraints:
- topologyKey: topology.kubernetes.io/zone
```

But only `zone-a` has nodes labeled:

```text
workload=pci
```

Then strict three-zone spreading is impossible.

Check:

```bash
oc get nodes -l workload=pci -L topology.kubernetes.io/zone
```

Fix options:

- add eligible PCI nodes in other zones
- change `DoNotSchedule` to `ScheduleAnyway`
- remove or adjust `minDomains`
- change topologyKey to hostname
- use `nodeAffinityPolicy: Honor`
- align infrastructure labels with workload placement design

---

### 25.5 Taints conflict with spread

Check taints:

```bash
oc describe node <node> | grep -i taints
```

Check tolerations:

```bash
oc get pod <pod> -n <ns> -o yaml | grep -A20 tolerations
```

If a zone has only tainted nodes and the pod does not tolerate them, that zone is not practically eligible.

Fix options:

- add toleration
- remove taint if wrong
- add untainted nodes
- use `nodeTaintsPolicy: Honor`

---

### 25.6 Resource shortage conflict

Even if topology spread is correct, resource requests can block scheduling.

Check:

```bash
oc describe pod <pod> -n <namespace>
oc adm top nodes
oc adm top pods -n <namespace>
```

Example event:

```text
Insufficient cpu
Insufficient memory
node(s) didn't match pod topology spread constraints
```

The pod may need to go to a less-populated zone, but that zone may not have enough CPU or memory.

Fix options:

- reduce requests if oversized
- add capacity in constrained zone
- rebalance other workloads
- allow soft spread with `ScheduleAnyway`
- use cluster autoscaler/machine autoscaler where available

---

### 25.7 PVC / volume topology conflict

For stateful workloads, storage can restrict pod placement.

Check PVC:

```bash
oc get pvc -n <namespace>
oc describe pvc <pvc> -n <namespace>
```

Check PV node affinity:

```bash
oc get pv <pv-name> -o yaml | grep -A20 nodeAffinity
```

If the volume is bound to `zone-a`, but topology spread wants to place the pod in `zone-b`, scheduling can fail.

Fix options:

- use a StorageClass with `volumeBindingMode: WaitForFirstConsumer`
- ensure storage exists in all zones
- design StatefulSet replicas and PVs per zone
- avoid hard spread rules that conflict with storage topology

---

## 26. Operational checklist

Before applying topology spread constraints in production, verify:

```text
[ ] Workload has more than one replica.
[ ] Pod template labels match labelSelector.
[ ] Nodes have consistent topology labels.
[ ] All target topology domains have enough capacity.
[ ] Node affinity does not restrict pods to only one domain.
[ ] Taints and tolerations are aligned.
[ ] Storage topology is compatible.
[ ] PDB is configured for critical workloads.
[ ] Rolling update strategy is compatible.
[ ] HPA min/max replicas make sense for number of domains.
[ ] Hard vs soft spread choice is intentional.
[ ] minDomains is not higher than available eligible domains unless intentionally strict.
[ ] Monitoring alerts exist for Pending pods.
```

## 27. Design decision matrix

| Requirement | Recommended approach |
|---|---|
| Avoid two replicas on same node | `topologyKey: kubernetes.io/hostname`, `maxSkew: 1` |
| Spread across zones | `topologyKey: topology.kubernetes.io/zone` |
| Strict HA | `whenUnsatisfiable: DoNotSchedule` |
| Best-effort spread | `whenUnsatisfiable: ScheduleAnyway` |
| Rolling update safe spread | Add `matchLabelKeys: [pod-template-hash]` |
| Dedicated node pool | Combine nodeSelector/nodeAffinity with spread |
| Tainted dedicated nodes | Add tolerations and `nodeTaintsPolicy: Honor` |
| Three-zone minimum design | Use `minDomains: 3` carefully |
| Bare-metal rack awareness | Custom label such as `rack=rack-a` |
| Stateful storage workloads | Validate PV/PVC topology first |
| Large autoscaled workloads | Prefer topology spread over strict anti-affinity |

## 28. Common mistakes

### Mistake 1: Using topology spread with one replica

If replicas are `1`, spreading has no real HA benefit.

```yaml
replicas: 1
```

Better:

```yaml
replicas: 3
```

---

### Mistake 2: Selector mismatch

Bad:

```yaml
metadata:
  labels:
    app: frontend-v2
labelSelector:
  matchLabels:
    app: frontend
```

The scheduler counts different pods than expected.

---

### Mistake 3: Hard spread in a small lab

Bad for a two-node lab:

```yaml
minDomains: 3
whenUnsatisfiable: DoNotSchedule
```

This can intentionally block pods.

---

### Mistake 4: Missing node topology labels

Bad:

```text
worker-1 zone=zone-a
worker-2 zone=zone-b
worker-3 <no zone label>
```

The unlabeled node may not participate correctly.

---

### Mistake 5: Making every rule hard

Bad:

```yaml
- topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
- topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: DoNotSchedule
- topologyKey: rack
  whenUnsatisfiable: DoNotSchedule
```

This can make scheduling very fragile.

Better pattern:

```yaml
zone: hard
hostname: soft
rack: soft or hard depending on real requirement
```

---

### Mistake 6: Expecting automatic rebalance

Topology spread constraints affect scheduling of new pods. They do not automatically move running pods after:

- node label changes
- node addition
- scale down
- zone restoration
- failed node recovery

For rebalancing, consider:

- rollout restart
- controlled pod deletion
- descheduler strategy where appropriate
- scaling down/up carefully

```yaml
topologySpreadConstraints:
```

Use when your failure boundary is a rack, TOR switch, power feed, or virtualization cluster.

### 29.4 Infra workload pattern

For workloads allowed on infra nodes:

```yaml

      app: router-like-workload

```

This pattern is useful for custom infra-style workloads, but always verify the exact taints and labels used in your cluster.

## 31. Exam and interview points

For Advanced OpenShift Administration, be ready to explain:

1. Topology spread constraints are configured in the pod spec.
2. They spread pods based on node labels.
3. `topologyKey` selects the node label used as the topology domain.
4. `labelSelector` selects which pods are counted.
5. Only same-namespace pods are counted for the constraint.
6. `maxSkew` controls permitted imbalance.
7. `DoNotSchedule` is strict.
8. `ScheduleAnyway` is preferred/best-effort.
9. Multiple constraints must all be satisfied.
10. Missing topology labels cause unexpected scheduling behavior.
11. They do not rebalance already running pods.
12. They are different from anti-affinity because they control skew, not only colocate/avoid.
13. Combine with node affinity, taints/tolerations, PDB, and resource requests for production design.
14. For rolling updates, `matchLabelKeys: [pod-template-hash]` can improve revision-aware spreading.
15. For strict zone HA, use `topology.kubernetes.io/zone`, `maxSkew: 1`, and possibly `minDomains`.

## 34. Summary

Pod topology spread constraints are a powerful OpenShift scheduling feature used to distribute pods across failure domains.

They answer this question:

> “How evenly should these replicas be distributed across nodes, zones, racks, or any custom topology?”

Key points:

- They use node labels as topology domains.
- They count matching pods using `labelSelector`.
- `maxSkew` controls allowed imbalance.
- `DoNotSchedule` enforces strict placement.
- `ScheduleAnyway` gives best-effort placement.
- `minDomains` protects minimum HA domain design.
- `matchLabelKeys` helps rolling-update behavior.
- `nodeAffinityPolicy` and `nodeTaintsPolicy` make spread calculation align with real node eligibility.
- They complement node selectors, affinity, taints, tolerations, PDBs, HPA, and storage topology.
- They do not automatically rebalance existing pods.

For a senior OpenShift administrator, topology spread constraints are not just YAML fields. They are part of production availability architecture.

Use them to make pod placement predictable, failure-domain-aware, and operationally safe.
