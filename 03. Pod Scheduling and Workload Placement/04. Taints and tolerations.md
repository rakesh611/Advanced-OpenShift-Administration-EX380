# Taints and Tolerations in OpenShift: Advanced Pod Scheduling and Workload Placement

**Audience:** Advanced OpenShift Administrator / Platform Engineer with ~10 years of Linux, Kubernetes, and production operations experience  
**Platform focus:** Red Hat OpenShift Container Platform 4.x  
**Topic area:** Pod Scheduling and Workload Placement  
**Primary tools:** `oc`, OpenShift Scheduler, Machine API, Deployments, DaemonSets, StatefulSets, Operators

---

## 1. Executive Summary

Taints and tolerations are one of the most important workload placement controls in Kubernetes and OpenShift. They are used to **repel pods from nodes unless those pods explicitly tolerate the node condition or node purpose**.

In simple terms:

- **Taint = rule on a node** saying: “Do not place normal pods here unless they have permission.”
- **Toleration = permission on a pod** saying: “This pod is allowed to run on nodes with this taint.”

Taints and tolerations are commonly used for:

- Dedicated infrastructure nodes.
- GPU or special hardware nodes.
- Storage nodes.
- Logging, monitoring, ingress, or platform component isolation.
- Workload isolation between teams or environments.
- Preventing workloads from scheduling on degraded nodes.
- Handling node conditions such as `NotReady`, `Unreachable`, `MemoryPressure`, and `DiskPressure`.
- Controlled eviction behavior using `NoExecute` and `tolerationSeconds`.

For an advanced OpenShift administrator, taints and tolerations are not just YAML fields. They are part of a larger placement strategy that also includes:

- Node labels.
- `nodeSelector`.
- Node affinity.
- Pod affinity and anti-affinity.
- Topology spread constraints.
- MachineSets.
- MachineConfigPools.
- Operator workload placement.
- Pod disruption budgets.
- Cluster autoscaling behavior.
- Storage topology.
- Infrastructure node design.

The key rule is:

> **Taints repel pods. Tolerations only allow scheduling; they do not force scheduling.**

To force or strongly guide a workload to specific nodes, combine tolerations with node labels and node affinity or node selectors.

## 2. Why Taints and Tolerations Matter in Production OpenShift

In a small lab cluster, the scheduler can place most workloads anywhere. In production OpenShift, that approach becomes risky.

You might have different node groups such as:

- Worker nodes for normal application workloads.
- Infrastructure nodes for routers, registry, monitoring, logging, GitOps, or operators.
- GPU nodes for AI/ML workloads.
- High-memory nodes for databases or analytics.
- Storage-optimized nodes for OpenShift Data Foundation or local storage.
- Security-sensitive nodes for regulated workloads.
- Edge nodes with special topology.
- Spot or preemptible nodes for fault-tolerant workloads.

Without taints, any workload that has compatible CPU, memory, storage, and selectors might be scheduled on these nodes. That can cause:

- Application pods consuming capacity on infrastructure nodes.
- Non-GPU pods wasting expensive GPU node capacity.
- Platform components competing with tenant workloads.
- Stateful workloads landing on unreliable nodes.
- Uncontrolled blast radius during node failure.
- Poor isolation between teams.
- Hard-to-debug scheduling issues.

Taints and tolerations solve this by giving nodes a way to say:

> “Only pods that explicitly know about this node type should run here.”

## 3. Core Concept

### 3.1 Taint

A taint is configured on a **node**.

Example:

```bash
oc adm taint nodes worker-gpu-1 workload=gpu:NoSchedule
```

This means:

- Node: `worker-gpu-1`
- Taint key: `workload`
- Taint value: `gpu`
- Effect: `NoSchedule`

Now normal pods cannot be scheduled on this node unless they have a matching toleration.

### 3.2 Toleration

A toleration is configured on a **pod spec**.

Example:

```yaml
tolerations:
- key: "workload"
  operator: "Equal"
  value: "gpu"
  effect: "NoSchedule"
```

This means the pod is allowed to run on nodes tainted with:

```text
workload=gpu:NoSchedule
```

### 3.3 Important Scheduling Truth

A toleration does **not** attract a pod to a node.

It only allows the scheduler to consider that node.

For example, this pod tolerates GPU nodes:

```yaml
tolerations:
- key: "workload"
  operator: "Equal"
  value: "gpu"
  effect: "NoSchedule"
```

But the scheduler can still place it on a normal worker node unless you also add a placement constraint such as:

```yaml
nodeSelector:
  workload: gpu
```

or node affinity:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: workload
          operator: In
          values:
          - gpu
```

Production rule:

> **Use taints to repel unwanted pods. Use labels and node affinity to attract or require wanted pods.**

## 4. Taint Syntax

General command:

```bash
oc adm taint nodes <node-name> <key>=<value>:<effect>
```

Example:

```bash
oc adm taint nodes worker-1 dedicated=payments:NoSchedule
```

The taint format is:

```text
key=value:effect
```

Example parts:

| Part | Example | Meaning |
|---|---|---|
| Key | `dedicated` | Taint category |
| Value | `payments` | Taint value |
| Effect | `NoSchedule` | Scheduler behavior |

View taints on all nodes:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
```

View taints on one node:

```bash
oc describe node worker-1 | grep -i taints -A5
```

or:

```bash
oc get node worker-1 -o jsonpath='{.spec.taints}' | jq
```

## 5. Taint Effects

Taint effects define how strictly the taint is enforced.

There are three effects:

1. `NoSchedule`
2. `PreferNoSchedule`
3. `NoExecute`

---

## 6. `NoSchedule`

`NoSchedule` is the most common taint effect.

It means:

- New pods that do not tolerate the taint are not scheduled on the node.
- Existing pods already running on the node are not evicted.

Example:

```bash
oc adm taint nodes worker-1 dedicated=infra:NoSchedule
```

A pod without this toleration will not be scheduled on `worker-1`:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: infra
  effect: NoSchedule
```

### 6.1 Production Use Cases

Use `NoSchedule` when you want to protect a node pool but do not want to evict already running pods.

Common examples:

- Dedicated infra nodes.
- GPU nodes.
- Storage nodes.
- Database nodes.
- Team-specific nodes.
- Compliance-specific nodes.

### 6.2 Example: Dedicated Infra Nodes

Label the node:

```bash
oc label node worker-infra-1 node-role.kubernetes.io/infra=""
oc label node worker-infra-1 workload=infra
```

Taint the node:

```bash
oc adm taint node worker-infra-1 dedicated=infra:NoSchedule
```

Then configure infrastructure workloads with:

```yaml
nodeSelector:
  workload: infra
tolerations:
- key: dedicated
  operator: Equal
  value: infra
  effect: NoSchedule
```

This combination means:

- Taint keeps normal apps away.
- Node selector or affinity places infra workload on infra nodes.

---

## 7. `PreferNoSchedule`

`PreferNoSchedule` is a soft taint.

It means:

- The scheduler tries not to place non-tolerating pods on the node.
- If there is no better option, the scheduler may still place the pod there.
- Existing pods remain running.

Example:

```bash
oc adm taint nodes worker-spot-1 capacity=spot:PreferNoSchedule
```

### 7.1 Production Use Cases

Use `PreferNoSchedule` when the placement rule is preferred but not mandatory.

Examples:

- Avoid placing normal workloads on spot nodes unless necessary.
- Prefer not to use high-cost nodes for generic workloads.
- Keep burst nodes as last-resort capacity.
- Reserve a node group for priority workloads but allow fallback.

### 7.2 Why It Is Less Common

In strict enterprise OpenShift environments, `PreferNoSchedule` is less common than `NoSchedule` because it does not provide a hard guarantee.

For dedicated nodes, use `NoSchedule`.

For cost optimization or soft separation, use `PreferNoSchedule`.

---

## 8. `NoExecute`

`NoExecute` is the strictest taint effect.

It means:

- New pods that do not tolerate the taint cannot schedule on the node.
- Existing pods already running on the node are evicted if they do not tolerate the taint.

Example:

```bash
oc adm taint nodes worker-1 quarantine=true:NoExecute
```

### 8.1 Production Use Cases

Use `NoExecute` carefully.

Examples:

- Quarantine unhealthy nodes.
- Evict workloads from nodes under special maintenance conditions.
- Remove pods from nodes with critical issues.
- Custom node health automation.
- Evict non-approved workloads from dedicated nodes.

### 8.2 Risk

`NoExecute` can immediately evict pods. If workloads do not have enough replicas, proper disruption budgets, or available capacity elsewhere, this can cause outages.

Before applying `NoExecute`, check:

```bash
oc get pods -A -o wide --field-selector spec.nodeName=<node-name>
oc get pdb -A
oc adm top nodes
oc adm top pods -A
```

### 8.3 Safer Maintenance Alternative

For planned maintenance, the standard OpenShift/Kubernetes approach is usually:

```bash
oc adm cordon <node-name>
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data
```

Use `NoExecute` only when you specifically want taint-based eviction behavior.

## 9. Toleration Operators

Tolerations support two operators:

1. `Equal`
2. `Exists`

---

## 10. `Equal` Operator

`Equal` requires key, value, and effect to match.

Example taint:

```bash
oc adm taint nodes worker-1 dedicated=payments:NoSchedule
```

Matching toleration:

```yaml
tolerations:
- key: "dedicated"
  operator: "Equal"
  value: "payments"
  effect: "NoSchedule"
```

This matches only:

```text
dedicated=payments:NoSchedule
```

It does not match:

```text
dedicated=infra:NoSchedule
dedicated=payments:NoExecute
workload=payments:NoSchedule
```

### 10.1 Default Operator

If `operator` is not specified, Kubernetes treats it as `Equal`.

Still, in production YAML, it is better to specify `operator` explicitly for readability.

---

## 11. `Exists` Operator

`Exists` requires key and effect to match. The value is ignored and must not be specified.

Example toleration:

```yaml
tolerations:
- key: "dedicated"
  operator: "Exists"
  effect: "NoSchedule"
```

This matches:

```text
dedicated=payments:NoSchedule
dedicated=infra:NoSchedule
dedicated=security:NoSchedule
```

But it does not match:

```text
dedicated=payments:NoExecute
```

because the effect is different.

### 11.1 When to Use `Exists`

Use `Exists` when the workload can tolerate any value for a taint key.

Examples:

- DaemonSet agents that should run on all dedicated node types.
- Cluster-level monitoring/logging agents.
- Security agents.
- Node exporters.
- Backup agents.

### 11.2 Dangerous Wildcard Toleration

This toleration matches all taints:

```yaml
tolerations:
- operator: "Exists"
```

It allows the pod to tolerate any taint, including control plane, infra, storage, GPU, and pressure-related taints depending on effect behavior.

Use this only for very specific system-level DaemonSets or privileged platform workloads.

Avoid giving normal application workloads this toleration.

---

## 12. Matching Logic

A toleration matches a taint when:

For `Equal`:

- Key is the same.
- Value is the same.
- Effect is the same.

For `Exists`:

- Key is the same.
- Effect is the same.
- Value is not used.

Example:

Node taints:

```text
dedicated=infra:NoSchedule
disktype=ssd:NoSchedule
maintenance=true:NoExecute
```

Pod tolerations:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: infra
  effect: NoSchedule
- key: disktype
  operator: Exists
  effect: NoSchedule
```

Result:

- `dedicated=infra:NoSchedule` is tolerated.
- `disktype=ssd:NoSchedule` is tolerated.
- `maintenance=true:NoExecute` is not tolerated.

If the pod is already running on that node and the `maintenance=true:NoExecute` taint is added, the pod is evicted unless it has a matching `NoExecute` toleration.

---

## 13. Multiple Taints on a Node

A node can have multiple taints.

Example:

```bash
oc adm taint nodes worker-1 dedicated=infra:NoSchedule
oc adm taint nodes worker-1 disktype=ssd:NoSchedule
oc adm taint nodes worker-1 maintenance=true:NoExecute
```

The scheduler processes taints like a filter:

1. Ignore taints that the pod tolerates.
2. Evaluate remaining taints.
3. If any unmatched `NoSchedule` taint remains, the pod cannot schedule there.
4. If any unmatched `NoExecute` taint remains, the pod cannot run there and existing pods may be evicted.
5. If only unmatched `PreferNoSchedule` taints remain, the scheduler avoids the node if possible.

### 13.1 Example

Node has:

```text
dedicated=infra:NoSchedule
disktype=ssd:NoSchedule
```

Pod tolerates only:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: infra
  effect: NoSchedule
```

The pod still cannot schedule on the node because it does not tolerate:

```text
disktype=ssd:NoSchedule
```

Production lesson:

> **A pod must tolerate every hard taint on a node to be scheduled there.**

---

## 14. Toleration Seconds

`tolerationSeconds` applies to `NoExecute` taints.

It controls how long a pod can remain bound to a node after a matching `NoExecute` taint appears.

Example:

```yaml
tolerations:
- key: "node.kubernetes.io/unreachable"
  operator: "Exists"
  effect: "NoExecute"
  tolerationSeconds: 600
```

This means:

- If the node becomes unreachable, the pod can stay bound for 600 seconds.
- If the node recovers within 600 seconds, the pod remains.
- If the node is still unreachable after 600 seconds, the pod is evicted.

### 14.1 No `tolerationSeconds`

If a pod has a matching `NoExecute` toleration without `tolerationSeconds`, it can remain bound indefinitely for that taint.

Example:

```yaml
tolerations:
- key: "maintenance"
  operator: "Equal"
  value: "true"
  effect: "NoExecute"
```

This pod tolerates the `maintenance=true:NoExecute` taint forever.

### 14.2 Stateful Workload Example

For stateful workloads, immediate eviction during a short network partition may be worse than waiting.

Example:

```yaml
tolerations:
- key: "node.kubernetes.io/not-ready"
  operator: "Exists"
  effect: "NoExecute"
  tolerationSeconds: 900
- key: "node.kubernetes.io/unreachable"
  operator: "Exists"
  effect: "NoExecute"
  tolerationSeconds: 900
```

This allows the pod to wait 15 minutes before eviction.

Use this carefully. Delaying eviction can improve stability for local-state workloads, but it can also delay recovery if the node is truly lost.

## 15. Built-in OpenShift and Kubernetes Node Taints

OpenShift automatically uses several node condition taints.

Common built-in taints include:

| Taint | Meaning |
|---|---|
| `node.kubernetes.io/not-ready` | Node is not ready |
| `node.kubernetes.io/unreachable` | Node controller cannot reach node |
| `node.kubernetes.io/memory-pressure` | Node has memory pressure |
| `node.kubernetes.io/disk-pressure` | Node has disk pressure |
| `node.kubernetes.io/pid-pressure` | Node has PID pressure |
| `node.kubernetes.io/network-unavailable` | Node network is unavailable |
| `node.kubernetes.io/unschedulable` | Node is unschedulable |
| `node.cloudprovider.kubernetes.io/uninitialized` | Node is not initialized by cloud provider yet |

OpenShift also commonly uses role-based node taints for control plane scheduling protection, such as:

```text
node-role.kubernetes.io/master:NoSchedule
```

or in newer naming contexts:

```text
node-role.kubernetes.io/control-plane:NoSchedule
```

The exact key visible in your cluster depends on OpenShift/Kubernetes version and cluster configuration.

Check your cluster directly:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,ROLES:.metadata.labels,TAINTS:.spec.taints
```

## 16. Taint Nodes by Condition

OpenShift enables node condition tainting behavior by default.

When a node reports a problem, the control plane can add taints automatically.

Examples:

```text
node.kubernetes.io/memory-pressure:NoSchedule
node.kubernetes.io/disk-pressure:NoSchedule
node.kubernetes.io/not-ready:NoExecute
node.kubernetes.io/unreachable:NoExecute
```

This helps the scheduler avoid unhealthy nodes.

### 16.1 Example: Memory Pressure

If a node reports memory pressure, OpenShift may add:

```text
node.kubernetes.io/memory-pressure:NoSchedule
```

New pods without a matching toleration are not scheduled there.

This does not necessarily evict existing pods unless eviction thresholds are hit by kubelet eviction logic or a `NoExecute` taint is involved.

### 16.2 Why You Should Not Blindly Tolerate Pressure Taints

Do not add broad tolerations such as this to normal applications:

```yaml
tolerations:
- key: "node.kubernetes.io/memory-pressure"
  operator: "Exists"
  effect: "NoSchedule"
```

unless you have a strong reason.

A workload tolerating memory pressure may land on a node that is already unhealthy.

## 17. Default `not-ready` and `unreachable` Tolerations

Kubernetes/OpenShift normally adds default tolerations to pods for:

```text
node.kubernetes.io/not-ready
node.kubernetes.io/unreachable
```

with `NoExecute` and a default delay, commonly 300 seconds.

Example:

```yaml
tolerations:
- key: node.kubernetes.io/not-ready
  operator: Exists
  effect: NoExecute
  tolerationSeconds: 300
- key: node.kubernetes.io/unreachable
  operator: Exists
  effect: NoExecute
  tolerationSeconds: 300
```

This means the platform does not instantly evict every pod during a short node communication issue.

### 17.1 Operational Impact

If a node becomes unreachable, pods might remain shown as running or terminating for some time before replacement pods are created elsewhere.

For highly available applications, this is usually acceptable.

For applications with strict recovery time objectives, review:

- Replica count.
- Readiness probes.
- Pod disruption budgets.
- StatefulSet behavior.
- Storage detach/attach timing.
- Application failover logic.
- Custom toleration seconds.

## 18. DaemonSets and Tolerations

DaemonSets often need to run on all or many nodes, including nodes with special taints.

Examples:

- Logging agents.
- Monitoring agents.
- CNI agents.
- CSI node plugins.
- Security agents.
- Node exporters.
- Storage agents.

DaemonSet pods commonly have broader tolerations than normal application pods.

Example:

```yaml
tolerations:
- operator: Exists
```

This is acceptable for certain node-level platform agents, but dangerous for normal workloads.

### 18.1 Troubleshooting DaemonSet Not Running on Tainted Node

Check taints:

```bash
oc describe node <node-name> | grep -i taints -A5
```

Check DaemonSet tolerations:

```bash
oc get ds <daemonset-name> -n <namespace> -o yaml | yq '.spec.template.spec.tolerations'
```

Check DaemonSet events:

```bash
oc describe ds <daemonset-name> -n <namespace>
```

Check pods:

```bash
oc get pods -n <namespace> -o wide
```

If the node has a taint that the DaemonSet does not tolerate, add the correct toleration in the DaemonSet pod template.

## 19. Difference Between Taints, Node Selectors, and Node Affinity

These controls are often confused.

| Feature | Applied To | Purpose | Hard/Soft |
|---|---|---|---|
| Taint | Node | Repel pods | Hard or soft depending on effect |
| Toleration | Pod | Allow pod to run on tainted node | Permission only |
| Node selector | Pod | Require node labels | Hard |
| Node affinity | Pod | Require or prefer node labels | Hard or soft |
| Pod affinity | Pod | Place near matching pods | Hard or soft |
| Pod anti-affinity | Pod | Avoid matching pods | Hard or soft |
| Topology spread | Pod | Spread pods across topology domains | Hard or soft |

### 19.1 Practical Rule

Use this pattern for dedicated nodes:

```text
Node label + node affinity/nodeSelector + node taint + pod toleration
```

Why?

- Taint prevents unrelated pods from landing there.
- Toleration allows approved pods to use those nodes.
- Node affinity/nodeSelector ensures approved pods actually go there.

## 20. Dedicated Node Pattern

### 20.1 Goal

Only `payments` workloads should run on dedicated payments nodes.

### 20.2 Label Nodes

```bash
oc label node worker-payments-1 dedicated=payments
oc label node worker-payments-2 dedicated=payments
```

### 20.3 Taint Nodes

```bash
oc adm taint node worker-payments-1 dedicated=payments:NoSchedule
oc adm taint node worker-payments-2 dedicated=payments:NoSchedule
```

### 20.4 Deployment YAML

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
  namespace: payments
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      tolerations:
      - key: "dedicated"
        operator: "Equal"
        value: "payments"
        effect: "NoSchedule"
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: dedicated
                operator: In
                values:
                - payments
      containers:
      - name: payments-api
        image: registry.access.redhat.com/ubi9/httpd-24
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 512Mi
```

### 20.5 Validate

```bash
oc get pods -n payments -o wide
oc describe pod <pod-name> -n payments
oc get node worker-payments-1 --show-labels
oc describe node worker-payments-1 | grep -i taints -A5
```

Expected result:

- Payments pods run only on nodes labeled `dedicated=payments`.
- Other workloads without toleration cannot use those nodes.

## 21. Infrastructure Node Pattern

Infrastructure nodes are commonly used for platform workloads such as:

- Ingress router.
- Image registry.
- Monitoring stack.
- Logging stack.
- GitOps controllers.
- Cluster observability components.
- Selected operators.

### 21.1 Example Node Preparation

```bash
oc label node worker-infra-1 node-role.kubernetes.io/infra=""
oc label node worker-infra-1 workload=infra
oc adm taint node worker-infra-1 dedicated=infra:NoSchedule
```

### 21.2 Workload Placement

A workload intended for infra nodes should include:

```yaml
nodeSelector:
  workload: infra
tolerations:
- key: dedicated
  operator: Equal
  value: infra
  effect: NoSchedule
```

### 21.3 Important OpenShift Note

For OpenShift-managed platform components, you usually configure placement through the component's custom resource, not by manually editing generated pods.

Examples:

- IngressController placement is configured in the `IngressController` custom resource.
- Image Registry placement is configured in the image registry operator config.
- Monitoring placement is configured through cluster monitoring configuration.
- Logging placement is configured through logging custom resources.

Do not directly edit pods created by operators. The operator will reconcile them back.

## 22. GPU Node Pattern

### 22.1 Goal

Only GPU workloads should run on GPU nodes.

### 22.2 Label and Taint GPU Node

```bash
oc label node worker-gpu-1 workload=gpu
oc label node worker-gpu-1 accelerator=nvidia
oc adm taint node worker-gpu-1 workload=gpu:NoSchedule
```

### 22.3 GPU Workload YAML

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gpu-inference
  namespace: ai
spec:
  replicas: 1
  selector:
    matchLabels:
      app: gpu-inference
  template:
    metadata:
      labels:
        app: gpu-inference
    spec:
      tolerations:
      - key: workload
        operator: Equal
        value: gpu
        effect: NoSchedule
      nodeSelector:
        workload: gpu
      containers:
      - name: inference
        image: example.com/ai/inference:latest
        resources:
          limits:
            nvidia.com/gpu: 1
```

### 22.4 Why Both GPU Resource and Toleration Are Needed

The GPU resource request ensures the pod needs a GPU device.

The toleration allows the pod to run on tainted GPU nodes.

The node selector ensures it lands on the intended GPU node group.

## 24. Team-Based Isolation Pattern

### 24.1 Goal

Team A workloads should be allowed on Team A nodes. Other teams should not land there.

### 24.2 Configure Nodes

```bash
oc label node worker-team-a-1 team=team-a
oc adm taint node worker-team-a-1 dedicated=team-a:NoSchedule
```

### 24.3 Configure Workload

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: team-a
  effect: NoSchedule
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: team
          operator: In
          values:
          - team-a
```

### 24.4 Additional Governance

Taints alone do not stop a user from adding a matching toleration if they have permission to edit pod specs.

For stronger governance, combine with:

- RBAC.
- Admission control.
- Namespace-level policies.
- Security Context Constraints.
- Validating admission policies or policy engines.
- GitOps-controlled workload templates.
- Separate projects/namespaces.
- Resource quotas.

## 25. OpenShift MachineSet Taints

In cloud or Machine API-managed OpenShift clusters, worker nodes are often created by MachineSets.

You can define taints in the MachineSet template so newly created machines automatically receive those taints.

### 25.1 Why MachineSet-Level Taints Matter

If you manually taint an existing node, the taint can disappear when:

- The node is replaced.
- A MachineSet scales up new machines.
- Autoscaling adds new nodes.
- Machines are recreated during lifecycle events.

MachineSet-level taints provide consistent taints for the node group.

### 25.2 Example MachineSet Snippet

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: worker-gpu-us-east-1a
  namespace: openshift-machine-api
spec:
  template:
    spec:
      taints:
      - key: workload
        value: gpu
        effect: NoSchedule
```

### 25.3 Commands

Edit MachineSet:

```bash
oc edit machineset <machineset-name> -n openshift-machine-api
```

List MachineSets:

```bash
oc get machinesets -n openshift-machine-api
```

Check machines:

```bash
oc get machines -n openshift-machine-api
```

Check resulting nodes:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
```

### 25.4 Important Operational Note

Changing the MachineSet template affects newly created machines. Depending on the change and platform behavior, existing machines might need replacement or rollout actions to receive the desired configuration consistently.

Plan carefully before scaling MachineSets down or replacing nodes in production.

## 26. Applying Taints Safely in Production

### 26.1 Recommended Sequence

For existing nodes with running workloads:

1. Identify target nodes.
2. Label nodes.
3. Update approved workloads with tolerations and node affinity/selectors.
4. Roll out approved workloads.
5. Validate approved pods can run on the target nodes.
6. Apply taints.
7. Watch scheduling and events.
8. Clean up misplaced pods if necessary.

### 26.2 Why Add Tolerations First

If you add a `NoExecute` taint before workloads have tolerations, existing pods can be evicted.

If you add a `NoSchedule` taint before workloads have tolerations, new pods may remain pending.

Safer order:

```text
Pod toleration first -> Node taint second
```

### 26.3 Validation Commands

```bash
oc get nodes
oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
oc get pods -A -o wide | grep <node-name>
oc get events -A --sort-by=.lastTimestamp | tail -50
oc describe pod <pod-name> -n <namespace>
```

Look for scheduler events such as:

```text
0/5 nodes are available: 1 node(s) had untolerated taint
```

## 28. Cordon/Drain vs Taints

Taints are not the same as cordon and drain.

| Operation | Purpose | Existing Pods | New Pods |
|---|---|---|---|
| `oc adm cordon` | Mark node unschedulable | Stay running | Not scheduled |
| `oc adm drain` | Evict pods for maintenance | Evicted | Not scheduled while cordoned |
| `NoSchedule` taint | Repel non-tolerating pods | Stay running | Non-tolerating pods blocked |
| `NoExecute` taint | Repel and evict non-tolerating pods | Evicted if not tolerated | Non-tolerating pods blocked |

### 28.1 When to Use Cordon/Drain

Use cordon/drain for planned node maintenance:

```bash
oc adm cordon worker-1
oc adm drain worker-1 --ignore-daemonsets --delete-emptydir-data
```

### 28.2 When to Use Taints

Use taints for long-term placement policy or taint-based eviction logic:

```bash
oc adm taint node worker-1 dedicated=infra:NoSchedule
```

## 29. Interaction With Scheduler Filtering

During scheduling, the OpenShift scheduler evaluates many constraints, including:

- Node readiness.
- Resource requests.
- Taints and tolerations.
- Node selectors.
- Node affinity.
- Pod affinity and anti-affinity.
- Topology spread constraints.
- Volume binding and storage topology.
- Port conflicts for host networking.
- Pod security and admission outcomes.

Taints are only one part of the scheduling decision.

A pod can tolerate all taints and still remain pending if:

- CPU or memory is insufficient.
- PVC cannot bind.
- Node affinity does not match.
- Required pod anti-affinity cannot be satisfied.
- Image pull secret is missing.
- Security constraints reject the pod.
- Required device plugin resource is unavailable.
- Project node selector conflicts with pod node affinity.

## 32. Real-World Scenario: Pod Pending Due to Untolerated Infra Taint

### Problem

A developer deploys an app and it remains pending.

```bash
oc get pods -n app1
```

Output:

```text
NAME                     READY   STATUS    RESTARTS   AGE
web-7c9bdb4df9-r7f2k     0/1     Pending   0          5m
```

Describe pod:

```bash
oc describe pod web-7c9bdb4df9-r7f2k -n app1
```

Event:

```text
0/4 nodes are available: 2 node(s) had untolerated taint {dedicated: infra}, 2 node(s) didn't match Pod's node affinity/selector.
```

### Analysis

There are two different scheduling blockers:

1. Two nodes are infra nodes and the pod does not tolerate `dedicated=infra:NoSchedule`.
2. Two other nodes do not match node affinity or selector.

Adding only a toleration may not solve the issue if node affinity still conflicts.

### Fix Options

If this is a normal app, do not add infra toleration. Instead correct the node selector/affinity so it targets normal worker nodes.

If this app is supposed to run on infra nodes, add both:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: infra
  effect: NoSchedule
nodeSelector:
  workload: infra
```

## 33. Real-World Scenario: GPU Workload Scheduled on Non-GPU Node

### Problem

A pod has a GPU toleration but lands on a normal worker.

### Root Cause

The pod has a toleration but no node selector, node affinity, or GPU resource request.

A toleration does not force scheduling onto GPU nodes.

### Correct Design

```yaml
tolerations:
- key: workload
  operator: Equal
  value: gpu
  effect: NoSchedule
nodeSelector:
  workload: gpu
containers:
- name: app
  image: example.com/gpu-app:latest
  resources:
    limits:
      nvidia.com/gpu: 1
```

A security agent DaemonSet is expected on every node but is missing from tainted nodes.

### Check

oc get pods -n security -o wide

### Likely Cause

The DaemonSet lacks tolerations for node taints.

```yaml

  operator: Exists
  effect: NoSchedule
```

Use only the keys actually present in your cluster.

## 40. Taints and Autoscaling

Taints also matter for cluster autoscaling.

If pending pods cannot tolerate a tainted MachineSet or node group, the autoscaler may not treat that node group as a useful scale-up target for those pods.

### 40.1 Example

Pending pod has no GPU toleration.

GPU MachineSet has taint:

```text
workload=gpu:NoSchedule
```

The autoscaler should not scale GPU nodes for that generic pod because the pod cannot schedule there.

### 40.2 Production Design

For autoscaling node groups:

- Define taints in MachineSet or MachinePool templates.
- Ensure workloads have matching tolerations.
- Ensure workloads also have correct node affinity or selectors.
- Test scale-from-zero scenarios where applicable.
- Validate cluster autoscaler logs if scale-up does not happen.

---

## 41. Taints and Priority Classes

Taints and tolerations are independent from priority classes.

A high-priority pod does not automatically tolerate a taint.

If a high-priority pod lacks a toleration for a `NoSchedule` taint, it cannot schedule on that node.

However, priority and preemption can affect scheduling among eligible nodes.

Production rule:

> **Priority does not bypass taints.**

## 42. Taints and Security

Taints are not a hard security boundary by themselves.

Why?

A user who can create or modify pods may add tolerations unless admission policies prevent it.

For strong isolation, combine taints with:

- Namespaces/projects.
- RBAC.
- Security Context Constraints.
- NetworkPolicy.
- ResourceQuota.
- LimitRange.
- Admission control.
- GitOps review.
- Image policies.
- Runtime security tooling.

Use taints as a scheduling and operational isolation mechanism, not as the only security control.

## 43. Design Patterns and Anti-Patterns

### 43.1 Good Patterns

#### Dedicated Workload Pool

```text
label: dedicated=payments
taint: dedicated=payments:NoSchedule
pod: toleration + required node affinity
```

#### Infra Pool

```text
label: workload=infra
taint: dedicated=infra:NoSchedule
platform components: nodeSelector + toleration
```

#### GPU Pool

```text
label: workload=gpu
taint: workload=gpu:NoSchedule
GPU pods: toleration + GPU resource request + node selector
```

#### Soft Cost Avoidance

```text
taint: capacity=expensive:PreferNoSchedule
selected pods: toleration if allowed to use expensive nodes
```

#### Temporary Quarantine

```text
taint: quarantine=true:NoExecute
```

Use only after understanding eviction impact.

---

### 43.2 Anti-Patterns

#### Anti-Pattern 1: Toleration Without Selector

```yaml
tolerations:
- key: workload
  operator: Equal
  value: gpu
  effect: NoSchedule
```

Problem:

The pod can run on GPU nodes, but it is not forced to run there.

Fix:

Add node selector or node affinity.

#### Anti-Pattern 2: Wildcard Toleration on Application Pods

```yaml
tolerations:
- operator: Exists
```

Problem:

The application can tolerate all taints and may land on inappropriate nodes.

Fix:

Use specific tolerations.

#### Anti-Pattern 3: Tainting Nodes Before Updating Workloads

Problem:

Pods become pending or evicted.

Fix:

Add tolerations to approved workloads first.

#### Anti-Pattern 4: Manually Editing Operator-Managed Pods

Problem:

Operator reconciles the change away.

Fix:

Configure the operator custom resource.

#### Anti-Pattern 5: Using Taints as the Only Isolation Control

Problem:

Users may add tolerations if allowed.

Fix:

Use RBAC and admission governance.

## 45. Naming Standards for Enterprise Clusters

Use consistent taint keys and values.

Good examples:

```text
dedicated=infra:NoSchedule
dedicated=payments:NoSchedule
workload=gpu:NoSchedule
workload=storage:NoSchedule
capacity=spot:PreferNoSchedule
maintenance=planned:NoExecute
quarantine=true:NoExecute
```

Avoid vague names:

```text
test=true:NoSchedule
special=yes:NoSchedule
node=abc:NoSchedule
```

Recommended enterprise convention:

```text
<domain-or-team>/<purpose>=<value>:<effect>
```

Example:

```text
platform.example.com/dedicated=infra:NoSchedule
platform.example.com/workload=gpu:NoSchedule
```

This reduces naming conflicts with built-in Kubernetes keys.

## 46. Exam and Interview Notes

### 46.1 Key Points to Remember

- Taints are applied to nodes.
- Tolerations are applied to pods.
- Toleration permits scheduling but does not guarantee scheduling.
- `NoSchedule` blocks new non-tolerating pods.
- `PreferNoSchedule` tries to avoid scheduling but is not strict.
- `NoExecute` blocks new pods and evicts existing non-tolerating pods.
- `tolerationSeconds` applies to `NoExecute`.
- Use node affinity or node selectors with tolerations for dedicated placement.
- Use MachineSet taints for persistent node group taints.
- Add tolerations before tainting existing nodes.
- Check pod events for `had untolerated taint`.

## 49. Decision Matrix

| Requirement | Recommended Control |
|---|---|
| Keep normal apps away from infra nodes | `NoSchedule` taint on infra nodes |
| Allow infra pods onto infra nodes | Matching toleration |
| Force infra pods onto infra nodes | Node selector or required node affinity |
| Prefer but not require avoiding nodes | `PreferNoSchedule` |
| Evict existing pods from node | `NoExecute` or `oc adm drain` |
| Planned node maintenance | `cordon` + `drain` |
| Run agent on all nodes | DaemonSet with necessary tolerations |
| Isolate GPU nodes | Taint + toleration + GPU resource + node affinity |
| Persist taints for autoscaled workers | MachineSet taints |
| Strong tenant security | Taints plus RBAC/admission/security controls |

## 50. Production Best Practices

1. Use `NoSchedule` for most dedicated node pools.
2. Use `NoExecute` only when you intentionally want eviction behavior.
3. Do not use wildcard tolerations on normal apps.
4. Always combine tolerations with node selectors or node affinity for dedicated placement.
5. Add tolerations before applying taints to existing nodes.
6. Use MachineSet-level taints for machine-managed node pools.
7. Avoid manually editing operator-managed pods.
8. Check project-level node selectors when troubleshooting.
9. Standardize taint key naming across the platform.
10. Monitor events after applying taints.
11. Document which teams own which taints.
12. Test placement policy in non-production first.
13. Validate PodDisruptionBudgets before using `NoExecute` or drain operations.
14. Do not tolerate node pressure taints unless the workload is designed for it.
15. Remember that toleration is permission, not attraction.

| Pod not on dedicated node | Toleration without selector | `oc get pod -o yaml` | Add nodeSelector/nodeAffinity |
| App running on infra node | Missing taint | `oc describe node` | Add taint to infra node |
| DaemonSet missing on tainted node | Missing toleration | `oc describe ds` | Add toleration to DaemonSet |
| Pods evicted after taint | `NoExecute` taint | `oc get events` | Add tolerationSeconds or remove taint |
| New node missing taint | Manual taint not in MachineSet | `oc get machineset -o yaml` | Add taint to MachineSet template |
| Operator workload ignores manual edit | Operator reconciliation | `oc get events`, operator logs | Configure supported custom resource |

---

## 52. Final Summary

Taints and tolerations are a powerful scheduling mechanism in OpenShift. They allow nodes to reject pods unless the pods explicitly tolerate the node's taint. For production-grade workload placement, they should be used together with node labels, node selectors, node affinity, resource requests, topology design, and operator-supported placement configuration.

The most important concepts are:

- Taints live on nodes.
- Tolerations live on pods.
- `NoSchedule` blocks new non-tolerating pods.
- `PreferNoSchedule` is a soft avoidance rule.
- `NoExecute` evicts existing non-tolerating pods.
- `tolerationSeconds` controls delayed eviction for `NoExecute` taints.
- Tolerations do not force scheduling; use labels and affinity for that.
- MachineSet taints are important for consistent node group behavior.
- Taints are scheduling controls, not complete security boundaries.

For a senior OpenShift administrator, the right mindset is:

> **Design node pools intentionally, label them clearly, taint them safely, tolerate them only from approved workloads, and validate placement with scheduler events.**
