# Eviction Scenarios in Pod Scheduling and Workload Placement

**Track:** Advanced OpenShift Administration  
**Audience:** OpenShift/Kubernetes administrators with production operations experience  
**Focus:** Eviction behavior, node pressure, drain operations, descheduler, troubleshooting, and prevention  
**Verified against:** OpenShift Container Platform 4.19 and Kubernetes scheduling/eviction documentation as of July 2026

---

## 1. Executive Summary

In OpenShift, **eviction** means a pod is terminated or removed from a node so that cluster/node health, maintenance, or placement rules can be preserved. Eviction is closely related to scheduling, but it is not the same thing as scheduling.

A simple way to remember it:

```text
Scheduler     = decides where a NEW pod should run.
Kubelet       = may evict RUNNING pods when the node is under pressure.
NodeController= handles pods on NotReady/Unreachable nodes through node conditions/taints.
Descheduler   = evicts already-running pods so they can be placed better later.
Drain/MCO     = intentionally evicts pods for maintenance, upgrade, reboot, or machine deletion.
```

For an advanced administrator, eviction analysis is not only about seeing `Evicted` in pod status. You must identify **who initiated the eviction**, **why the pod was selected**, **whether the replacement pod can be scheduled**, and **whether the original cause still exists**.

---

## 2. Eviction Is Not One Single Mechanism

OpenShift has multiple eviction paths. They look similar from an application owner’s point of view, but their rules are different.

| Eviction Type | Initiator | Typical Reason | PDB Respected? | Grace Period Respected? | Common Evidence |
|---|---|---|---|---|---|
| Node-pressure eviction | kubelet | MemoryPressure, DiskPressure, PIDPressure, ephemeral storage exhaustion | No | Hard eviction: no. Soft eviction: kubelet max grace applies | `Warning Evicted`, node condition pressure, kubelet logs |
| API-initiated eviction | API server via `oc adm drain`, automation, custom client | Node maintenance, drain, machine deletion | Yes | Yes, pod `terminationGracePeriodSeconds` | Drain output, PDB status, events |
| Taint-based eviction | Node controller / taint manager | `NoExecute` taints such as node not ready/unreachable | Not a normal PDB protection path | Based on toleration/tolerationSeconds | Node taints, pod tolerations |
| Descheduler eviction | Kube Descheduler Operator | Better placement, affinity violation, topology, duplicate pods, node utilization | Yes, via eviction subresource | API eviction behavior | Descheduler logs, KubeDescheduler CR |
| Machine Config / node update drain | Machine Config Operator / Machine Config Daemon | OS config change, kubelet config change, node reboot | Yes, because it drains | Drain behavior | MCP updating, MCD logs |
| Machine deletion drain | Machine controller / autoscaler / admin | MachineSet scale down, autoscaler, MachineHealthCheck | Yes, because it drains | Drain behavior | Machine conditions: Drainable/Drained |
| OOM kill | Linux kernel/kubelet | Container exceeds memory limit or node OOM before kubelet evicts | Not eviction | Container restart policy applies | `OOMKilled`, restart count, container status |

**Important production point:** Every `Evicted` pod is a symptom. The root cause is usually node resource pressure, maintenance automation, taints, or placement policy drift.

## 3. Where Eviction Fits in Workload Placement

### 3.1 Normal scheduling flow

When a pod is created:

1. The API server stores the pod.
2. The scheduler watches for unscheduled pods.
3. The scheduler filters nodes based on hard constraints:
   - node selector
   - required node affinity
   - taints and tolerations
   - resource requests
   - topology spread hard rules
   - volume binding
   - security and admission constraints
4. The scheduler scores remaining nodes.
5. The scheduler binds the pod to a node.
6. The kubelet on that node starts containers.

### 3.2 Eviction flow

Eviction happens **after** a pod is already bound to a node.

A pod can be perfectly scheduled at 10:00 and evicted at 10:10 because:

- the node runs out of memory,
- `/var/lib/containers` fills up,
- container logs consume root filesystem space,
- an admin drains the node,
- the Machine Config Operator reboots the node,
- a `NoExecute` taint appears,
- the descheduler decides placement is no longer correct,
- a node becomes unreachable.

### 3.3 Scheduling and eviction feedback loop

Eviction creates replacement demand. For controller-managed workloads such as Deployments, ReplicaSets, StatefulSets, Jobs, and some operators, a new pod is created after eviction. That new pod must pass normal scheduling again.

This creates a loop:

```text
Pod evicted -> controller creates replacement -> scheduler tries placement -> pod may land elsewhere -> if cluster still unhealthy, pod may remain Pending or get evicted again
```

That is why advanced troubleshooting must check both:

- **eviction cause**, and
- **replacement scheduling result**.

## 4. Core Eviction Concepts

## 4.1 Node pressure

Node pressure means the kubelet has detected that a local node resource is close to exhaustion.

Common node pressure conditions:

```text
MemoryPressure=True
DiskPressure=True
PIDPressure=True
Ready=False or Ready=Unknown
```

Check them:

```bash
oc describe node <node-name>
oc get nodes
oc get node <node-name> -o jsonpath='{.status.conditions}' | jq
```

Useful compact view:

```bash
oc get nodes -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status,MEMORY:.status.conditions[?(@.type=="MemoryPressure")].status,DISK:.status.conditions[?(@.type=="DiskPressure")].status,PID:.status.conditions[?(@.type=="PIDPressure")].status'
```

## 4.2 Eviction signals

The kubelet compares measured signals to configured eviction thresholds.

Important signals:

| Signal | Meaning |
|---|---|
| `memory.available` | Available memory on node |
| `nodefs.available` | Available space on node filesystem |
| `nodefs.inodesFree` | Free inodes on node filesystem |
| `imagefs.available` | Available space on image filesystem |
| `imagefs.inodesFree` | Free inodes on image filesystem |
| `containerfs.available` | Available space on container filesystem, where supported |
| `containerfs.inodesFree` | Free inodes on container filesystem, where supported |
| `pid.available` | Available process IDs |

In OpenShift, disk pressure commonly comes from:

- container images,
- container writable layers,
- container logs,
- `emptyDir` volumes,
- node OS logs,
- local temporary files,
- too many small files causing inode exhaustion.

## 4.3 Soft vs hard eviction thresholds

| Threshold Type | Behavior |
|---|---|
| Soft eviction | Threshold plus grace period. The signal must stay beyond threshold for the configured grace period. |
| Hard eviction | No grace period. The kubelet takes immediate action. |

Example:

```yaml
evictionSoft:
  memory.available: "500Mi"
evictionSoftGracePeriod:
  memory.available: "1m30s"
evictionHard:
  memory.available: "200Mi"
```

Meaning:

- If memory available stays below `500Mi` for `1m30s`, soft eviction can start.
- If memory available drops below `200Mi`, hard eviction can start immediately.

## 4.4 EvictionPressureTransitionPeriod

A node can oscillate above and below soft thresholds. This can make node conditions flip repeatedly and cause poor scheduling decisions. `evictionPressureTransitionPeriod` delays transition out of pressure state.

Example:

```yaml
evictionPressureTransitionPeriod: 3m
```

Production meaning:

- Do not make this too aggressive.
- Avoid repeated node condition flapping.
- Flapping causes new pods to land on nodes that immediately become unhealthy again.

## 5. Pod Selection During Node-Pressure Eviction

When the kubelet must evict pods, it tries to choose victims in a predictable order.

The kubelet considers:

1. Whether pod usage exceeds its requests for the starved resource.
2. Pod priority.
3. Amount of usage above request.

QoS class is a useful operational approximation:

| QoS Class | How Created | Eviction Risk |
|---|---|---|
| BestEffort | No CPU/memory requests or limits | Highest risk |
| Burstable | Some request/limit, but not Guaranteed | Medium risk |
| Guaranteed | CPU and memory request equals limit for every container | Lowest risk |

However, do not oversimplify this as “Guaranteed can never be evicted.” A Guaranteed pod can still be affected by severe node failure, admin drain, taint-based eviction, machine deletion, or node loss. For node-pressure memory eviction, Guaranteed pods are much better protected because they should not exceed their memory requests if requests equal limits.

Example QoS manifests:

### BestEffort pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: besteffort-demo
spec:
  containers:
  - name: app
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "3600"]
```

No requests and no limits: highest eviction risk.

### Burstable pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: burstable-demo
spec:
  containers:
  - name: app
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "3600"]
    resources:
      requests:
        memory: "128Mi"
        cpu: "100m"
      limits:
        memory: "512Mi"
        cpu: "500m"
```

Has requests, but request does not equal limit.

### Guaranteed pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: guaranteed-demo
spec:
  containers:
  - name: app
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "3600"]
    resources:
      requests:
        memory: "512Mi"
        cpu: "500m"
      limits:
        memory: "512Mi"
        cpu: "500m"
```

CPU and memory request equals limit for every container.

# 6. Major Eviction Scenarios

---

## Scenario 1: MemoryPressure Eviction

### What happens

The kubelet detects that node memory is too low. It attempts to protect the node from system-wide out-of-memory conditions by evicting pods.

Typical signs:

```bash
oc get nodes
oc describe node <node>
oc get events -A --sort-by=.lastTimestamp | grep -i -E 'memory|evict|pressure'
oc get pods -A | grep -i Evicted
```

Pod description often shows something like:

```text
Status:   Failed
Reason:   Evicted
Message:  The node was low on resource: memory. Container <name> was using ...
```

### Why it happens

Common causes:

- pods have no memory requests,
- requests are too low compared to real usage,
- overcommit is too aggressive,
- memory leak in application,
- node system daemons use more than reserved memory,
- too many pods are packed onto a node,
- Guaranteed/Burstable design is poor,
- high page cache or local storage workload creates memory pressure,
- kubelet cannot observe pressure before the kernel OOM killer acts.

### Troubleshooting commands

Top node memory usage:

```bash
oc adm top nodes
```

Top pod memory usage:

```bash
oc adm top pods -A --sort-by=memory
```

Describe the affected pod:

```bash
oc describe pod <pod> -n <namespace>
```

Check node conditions:

```bash
oc describe node <node-name> | egrep -A8 'Conditions|Allocated resources|Events'
```

Inspect kubelet logs from the node:

```bash
oc debug node/<node-name>
chroot /host
journalctl -u kubelet --since "2 hours ago" | grep -i -E 'evict|memory|pressure|threshold|oom'
```

Check kernel OOM messages:

```bash
journalctl -k --since "2 hours ago" | grep -i -E 'oom|killed process|out of memory'
```

Check current kubelet config:

```bash
NODE=<node-name>
oc get --raw /api/v1/nodes/${NODE}/proxy/configz | jq '.kubeletconfig | {evictionHard, evictionSoft, evictionSoftGracePeriod, evictionPressureTransitionPeriod, systemReserved}'
```

### Admin interpretation

If a pod is evicted for memory, ask:

1. Did the pod have memory requests?
2. Did it exceed its request?
3. Was it BestEffort, Burstable, or Guaranteed?
4. Was the node overcommitted?
5. Were system daemons using too much memory?
6. Did kubelet evict, or did Linux OOM killer kill a container first?

### Remediation

Application-level:

```yaml
resources:
  requests:
    memory: "512Mi"
    cpu: "250m"
  limits:
    memory: "1Gi"
    cpu: "1"
```

Namespace-level defaults:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-compute-limits
  namespace: app-prod
spec:
  limits:
  - type: Container
    defaultRequest:
      memory: "256Mi"
      cpu: "100m"
    default:
      memory: "512Mi"
      cpu: "500m"
```

Resource quota:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: app-prod-quota
  namespace: app-prod
spec:
  hard:
    requests.memory: "20Gi"
    limits.memory: "40Gi"
    requests.cpu: "10"
    limits.cpu: "20"
    pods: "100"
```

Node-level:

- increase node size,
- scale more worker nodes,
- tune `systemReserved`,
- tune eviction thresholds carefully,
- reduce pod density,
- isolate noisy workloads on dedicated nodes.

## Scenario 2: DiskPressure Eviction on `nodefs`

### What happens

The kubelet detects low free disk space or low free inodes on the node filesystem. It can evict pods to recover space.

`nodefs` commonly includes:

- `/var/lib/kubelet`,
- `emptyDir` volumes not backed by memory,
- pod logs,
- local ephemeral storage,
- root filesystem content depending on node layout.

### Typical signs

```bash
oc get nodes
oc describe node <node-name> | grep -A5 DiskPressure
oc get events -A --sort-by=.lastTimestamp | grep -i -E 'disk|nodefs|evict|pressure'
```

Pod message might show:

```text
The node was low on resource: ephemeral-storage.
Container <name> was using ... which exceeds its request of ...
```

or:

```text
The node had condition: [DiskPressure]
```

### Troubleshooting commands

Check filesystem usage:

```bash
oc debug node/<node-name>
chroot /host

# filesystem space
df -h

# inode usage
df -ih

# common OpenShift/container paths
du -xh /var/lib/kubelet 2>/dev/null | sort -h | tail -30
du -xh /var/lib/containers 2>/dev/null | sort -h | tail -30
du -xh /var/log 2>/dev/null | sort -h | tail -30
```

Check pod logs consuming space:

```bash
find /var/log/pods -type f -name "*.log" -printf '%s %p\n' 2>/dev/null | sort -nr | head -20
```

Check kubelet messages:

```bash
journalctl -u kubelet --since "2 hours ago" | grep -i -E 'disk|imagefs|nodefs|evict|garbage|threshold'
```

### Common root causes

- noisy application logs,
- missing log rotation or abnormal log volume,
- large `emptyDir` usage,
- image cache growth,
- failed pods leaving terminated container data,
- too many tiny files causing inode exhaustion,
- local PV or hostPath misuse,
- temporary data written to container writable layer.

### Remediation

Short-term:

```bash
# Delete failed/evicted pods after confirming they are no longer needed
oc delete pod -A --field-selector=status.phase=Failed
```

If you need namespace-specific cleanup:

```bash
oc delete pod -n <namespace> --field-selector=status.phase=Failed
```

Do **not** manually delete random CRI-O directories unless you are following a vendor-supported recovery procedure. Prefer kubelet garbage collection, safe log cleanup, or node replacement.

Application prevention:

```yaml
resources:
  requests:
    ephemeral-storage: "512Mi"
  limits:
    ephemeral-storage: "2Gi"
```

`emptyDir` size limit:

```yaml
volumes:
- name: cache
  emptyDir:
    sizeLimit: 1Gi
```

Logging controls:

- reduce application log verbosity,
- ship logs quickly,
- avoid writing high-volume logs to stdout without capacity planning,
- review cluster logging retention and node log volume.

## Scenario 3: DiskPressure on `imagefs`

### What happens

The node image filesystem fills due to cached images. The kubelet first tries image garbage collection by deleting unused images. If that is not enough, disk pressure can still lead to pod eviction.

### Important behavior

OpenShift image garbage collection removes images not referenced by running pods. It uses a high threshold and low threshold model:

```text
imageGCHighThresholdPercent = trigger GC
imageGCLowThresholdPercent  = target to free down to
```

Defaults commonly used in OpenShift documentation:

```text
High threshold: 85%
Low threshold:  80%
```

### Troubleshooting

```bash
oc debug node/<node-name>
chroot /host

crictl images
crictl ps -a
journalctl -u kubelet --since "2 hours ago" | grep -i -E 'image garbage|imagefs|free|disk'
```

Check current image GC config:

```bash
NODE=<node-name>
oc get --raw /api/v1/nodes/${NODE}/proxy/configz | jq '.kubeletconfig | {imageMinimumGCAge, imageGCHighThresholdPercent, imageGCLowThresholdPercent}'
```

### Remediation

- Increase node disk size.
- Reduce image churn from CI/CD.
- Avoid constantly changing image tags that force pulls.
- Use image pull policies correctly.
- Tune image GC thresholds via `KubeletConfig` if required.
- Separate filesystems if design requires isolation.

Example KubeletConfig for worker image GC:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-image-gc
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
  kubeletConfig:
    imageMinimumGCAge: 5m
    imageGCHighThresholdPercent: 80
    imageGCLowThresholdPercent: 75
```

After applying:

```bash
oc apply -f worker-image-gc.yaml
oc get mcp
oc describe mcp worker
```

Remember: changing kubelet configuration causes Machine Config Operator rollout behavior on matching nodes. Plan this change as node maintenance.

## Scenario 4: Inode Exhaustion

### What happens

Disk has free GBs, but the filesystem runs out of inodes. The node cannot create new files even though `df -h` looks healthy.

### Symptoms

```bash
df -h     # looks okay
df -ih    # inode use is 100%
```

OpenShift symptoms:

- `DiskPressure=True`,
- container creation fails,
- image pull fails,
- pod logs cannot be written,
- kubelet evicts pods,
- events mention `inodesFree`.

### Troubleshooting

```bash
oc debug node/<node-name>
chroot /host

df -ih
find /var/lib/kubelet -xdev -type f | wc -l
find /var/lib/containers -xdev -type f | wc -l
find /var/log -xdev -type f | wc -l

# Identify directories with many files
for d in /var/lib/kubelet /var/lib/containers /var/log; do
  echo "### $d"
  find "$d" -xdev -type f 2>/dev/null | sed 's|/[^/]*$||' | sort | uniq -c | sort -nr | head -20
done
```

### Common root causes

- app creates millions of small files,
- cache directories in `emptyDir`,
- log fragmentation,
- image layer explosion,
- build workloads writing many small artifacts,
- hostPath misuse.

### Remediation

- Apply `emptyDir.sizeLimit`.
- Use PVC with suitable filesystem/inode design for file-heavy workloads.
- Move build/cache workloads to dedicated nodes.
- Clean failed build pods.
- Fix application file lifecycle.

## Scenario 5: Ephemeral Storage Eviction

### What counts as local ephemeral storage

Kubernetes/OpenShift local ephemeral storage includes node-local data such as:

- container writable layers,
- container logs,
- `emptyDir` volumes,
- temporary local data used by pods.

### Why this matters

A pod can have correct CPU/memory requests but still be evicted because it consumes too much ephemeral storage.

### Example risky pod

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: logger-risky
spec:
  replicas: 1
  selector:
    matchLabels:
      app: logger-risky
  template:
    metadata:
      labels:
        app: logger-risky
    spec:
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi
        command: ["/bin/bash", "-c"]
        args:
        - |
          while true; do
            dd if=/dev/zero bs=1M count=100 >> /tmp/bigfile
            sleep 5
          done
```

No ephemeral-storage request/limit. It can consume node disk until node pressure starts.

### Better pod design

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: logger-controlled
spec:
  replicas: 1
  selector:
    matchLabels:
      app: logger-controlled
  template:
    metadata:
      labels:
        app: logger-controlled
    spec:
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi
        command: ["sleep", "3600"]
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
            ephemeral-storage: "512Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"
            ephemeral-storage: "2Gi"
      volumes:
      - name: cache
        emptyDir:
          sizeLimit: 1Gi
```

### Troubleshooting

```bash
oc describe pod <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
oc adm top pods -A
oc describe node <node>
```

On node:

```bash
oc debug node/<node>
chroot /host

du -xh /var/lib/kubelet/pods 2>/dev/null | sort -h | tail -50
du -xh /var/log/pods 2>/dev/null | sort -h | tail -50
```

## Scenario 6: PIDPressure Eviction

### What happens

A pod or many pods create too many processes/threads. The node reaches PID pressure.

Symptoms:

```text
PIDPressure=True
Too many processes
fork: Resource temporarily unavailable
container start failures
```

OpenShift has pod PID limits controlled by kubelet configuration. In modern OpenShift versions, the pod PID limit is commonly visible in the kubelet configuration.

Check:

```bash
oc debug node/<node>
chroot /host
cat /etc/kubernetes/kubelet.conf | grep -i pids
```

Or via configz:

```bash
NODE=<node-name>
oc get --raw /api/v1/nodes/${NODE}/proxy/configz | jq '.kubeletconfig | {podPidsLimit, systemReserved}'
```

### Troubleshooting process count

```bash
oc debug node/<node>
chroot /host

ps -eLf | wc -l
ps -eLf --sort=-nlwp | head -30
```

Inside a pod:

```bash
oc exec -n <namespace> <pod> -- ps -eLf | wc -l
oc exec -n <namespace> <pod> -- ps -eLf | head
```

### Common root causes

- thread leak,
- fork bomb,
- Java app with uncontrolled thread pool,
- too many worker processes,
- sidecar malfunction,
- build or CI workload spawning many processes.

### Remediation

- Fix app process/thread limits.
- Tune worker counts.
- Use separate nodes for CI/build workloads.
- Use sane pod PID limits.
- Monitor process count.

## Scenario 7: NodeNotReady / Node Unreachable Evictions

### What happens

If a node becomes NotReady or Unreachable, the control plane eventually treats pods on that node as unavailable and replacement pods may be created elsewhere, depending on workload controller and tolerations.

OpenShift/Kubernetes can apply taints such as:

```text
node.kubernetes.io/not-ready:NoExecute
node.kubernetes.io/unreachable:NoExecute
```

Pods without matching tolerations are evicted after toleration behavior expires.

### Evidence

```bash
oc get nodes
oc describe node <node>
oc get node <node> -o json | jq '.spec.taints'
oc get events -A --sort-by=.lastTimestamp | grep -i -E 'notready|unreachable|evict|taint'
```

Pod side:

```bash
oc describe pod <pod> -n <namespace>
```

### Common root causes

- node reboot,
- kubelet down,
- CRI-O down,
- network partition,
- SDN/CNI failure,
- certificate issue,
- disk full affecting kubelet,
- RHCOS/MCO update,
- cloud instance failure,
- bare metal hardware issue.

### Remediation flow

1. Check node status:

```bash
oc get node <node> -o wide
oc describe node <node>
```

2. Debug node if accessible:

```bash
oc debug node/<node>
chroot /host
systemctl status kubelet crio
journalctl -u kubelet --since "1 hour ago"
journalctl -u crio --since "1 hour ago"
```

3. Check Machine API:

```bash
oc get machines -A
oc describe machine <machine> -n openshift-machine-api
```

4. Check MachineConfigPool:

```bash
oc get mcp
oc describe mcp worker
```

5. If the node is permanently lost, follow platform-specific node replacement procedure.

## Scenario 8: Admin Drain / Maintenance Eviction

### What happens

An admin intentionally drains a node:

```bash
oc adm cordon <node>
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

This uses API-initiated eviction where possible. It respects PodDisruptionBudgets and pod grace periods.

### Common drain blockers

- PDB does not allow disruption,
- standalone pod not managed by a controller,
- pod uses local storage,
- DaemonSet pods require `--ignore-daemonsets`,
- `emptyDir` data requires `--delete-emptydir-data`,
- terminating pod stuck due to finalizer,
- pod has very long termination grace period,
- unhealthy pods guarded by restrictive PDB.

### Safe drain command pattern

```bash
oc adm cordon <node>
oc adm drain <node> \
  --ignore-daemonsets \
  --delete-emptydir-data \
  --grace-period=-1 \
  --timeout=10m
```

Meaning:

- `--ignore-daemonsets`: DaemonSet pods are not drained because the controller expects one per node.
- `--delete-emptydir-data`: allows deletion of pods using `emptyDir`; data is lost.
- `--grace-period=-1`: use pod-defined termination grace.
- `--timeout=10m`: do not wait forever.

After maintenance:

```bash
oc adm uncordon <node>
```

### PDB check before drain

```bash
oc get pdb -A
oc describe pdb <pdb-name> -n <namespace>
```

If a PDB has `maxUnavailable: 0` or `minAvailable: 100%`, it can block voluntary evictions.

Example PDB allowing one unavailable replica:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: web
```

For 3+ replicas, this usually permits one pod to be drained at a time.

## Scenario 9: Machine Config Operator Evictions

### What happens

OpenShift Machine Config Operator manages RHCOS and node configuration. When certain machine config or kubelet config changes are applied, nodes may be drained and rebooted.

Typical triggers:

- kubelet config change,
- MachineConfig change,
- OS update,
- kernel argument change,
- CRI-O or kubelet-related configuration,
- selected registry configuration changes.

### Evidence

```bash
oc get mcp
oc describe mcp worker
oc get machineconfig
oc get pods -n openshift-machine-config-operator
oc logs -n openshift-machine-config-operator ds/machine-config-daemon -c machine-config-daemon --since=2h
```

Node events may show drain/cordon behavior. Application pods may show termination and replacement during node reboot.

### Production guidance

- Treat KubeletConfig changes as node-impacting.
- Apply to custom MachineConfigPool when possible.
- Check PDBs before cluster-wide changes.
- Do not make multiple kubelet and machine config changes blindly.
- Watch MCP rollout:

```bash
watch oc get mcp
```

- If worker pool is large, ensure `maxUnavailable` is appropriate.

## Scenario 10: Machine Deletion / Cluster Autoscaler Eviction

### What happens

When a machine is deleted or a MachineSet is scaled down, OpenShift attempts to drain the backed node before removing it. Autoscaler or MachineHealthCheck can also trigger replacement.

Evidence:

```bash
oc get machines -n openshift-machine-api
oc describe machine <machine-name> -n openshift-machine-api
oc get nodes
oc get events -n openshift-machine-api --sort-by=.lastTimestamp
```

Machine deletion flow commonly includes:

```text
Machine marked for deletion
preDrain hooks checked
node drained
instance removed from provider
Node object removed
```

### Common blockers

- restrictive PDB,
- standalone pods,
- pods with local storage,
- finalizers,
- unhealthy workload protected by PDB,
- control plane lifecycle hooks.

### Admin note

Do not casually use `oc delete node` in cloud-integrated OpenShift clusters. Work through Machine API / MachineSet where applicable.

## Scenario 11: Descheduler Evictions

### What happens

The scheduler only places new pods. It normally does not move already-running pods when cluster conditions change. The descheduler fills this gap by evicting pods so the scheduler can place replacements more appropriately.

Typical reasons:

- nodes are underutilized or overutilized,
- new nodes were added,
- affinity/anti-affinity rules changed,
- node labels/taints changed,
- topology spread is no longer ideal,
- duplicate pods exist on the same topology domain,
- pods restarted too many times,
- pod lifetime policy is exceeded.

### OpenShift KubeDescheduler example

```yaml
apiVersion: operator.openshift.io/v1
kind: KubeDescheduler
metadata:
  name: cluster
  namespace: openshift-kube-descheduler-operator
spec:
  managementState: Managed
  mode: Automatic
  deschedulingIntervalSeconds: 3600
  profiles:
  - AffinityAndTaints
  - TopologyAndDuplicates
  profileCustomizations:
    namespaces:
      excluded:
      - critical-apps
    thresholdPriorityClassName: high-priority
  evictionLimits:
    total: 20
```

### Predictive vs Automatic

| Mode | Meaning |
|---|---|
| Predictive | Shows what would be evicted but does not evict. Useful for testing. |
| Automatic | Actually evicts pods. Use carefully. |

### Descheduler protections

OpenShift descheduler avoids many risky evictions by default. For example, protected namespaces and critical pods are protected. Pods subject to PDB are not evicted if eviction would violate the PDB. Certain pods, such as standalone pods or DaemonSet pods, are generally not safe descheduler targets.

### Troubleshooting

```bash
oc get pods -n openshift-kube-descheduler-operator
oc get kubedeschedulers.operator.openshift.io cluster -n openshift-kube-descheduler-operator -o yaml
oc logs -n openshift-kube-descheduler-operator deploy/kube-descheduler-operator --since=2h
oc get events -A --sort-by=.lastTimestamp | grep -i desched
```

### Production guidance

Start with Predictive mode:

```yaml
spec:
  mode: Predictive
```

Review logs, excluded namespaces, priority threshold, PDB coverage, and eviction limits before using Automatic mode.

## Scenario 12: NoExecute Taint-Based Eviction

### What happens

A `NoExecute` taint evicts pods that do not tolerate it. This is different from `NoSchedule`, which only prevents new pods from scheduling.

Example:

```bash
oc adm taint node worker1 dedicated=infra:NoExecute
```

Pods without this toleration are evicted:

```yaml
tolerations:
- key: "dedicated"
  operator: "Equal"
  value: "infra"
  effect: "NoExecute"
  tolerationSeconds: 3600
```

Meaning: the pod can remain for 3600 seconds after the taint appears, then it is evicted.

### Built-in examples

Common built-in taints include:

```text
node.kubernetes.io/not-ready
node.kubernetes.io/unreachable
node.kubernetes.io/memory-pressure
node.kubernetes.io/disk-pressure
node.kubernetes.io/pid-pressure
node.kubernetes.io/network-unavailable
node.kubernetes.io/unschedulable
```

### Troubleshooting

```bash
oc get node <node> -o json | jq '.spec.taints'
oc get pod <pod> -n <namespace> -o json | jq '.spec.tolerations'
oc describe pod <pod> -n <namespace>
```

### Admin caution

When applying a `NoExecute` taint to existing nodes, add tolerations to the intended pods first. Otherwise, running workloads can be evicted immediately.

## Scenario 13: OOMKilled vs Evicted

This is one of the most important distinctions.

| Condition | Meaning | Pod Phase | What restarts? | Typical Reason |
|---|---|---|---|---|
| `OOMKilled` | Container was killed by memory control / kernel OOM | Pod may stay Running | Container restarts if restartPolicy allows | Container exceeded memory limit or node OOM |
| `Evicted` | Pod was terminated/failed by kubelet/API/taint/descheduler | Usually Failed | Controller creates a new pod | Node pressure, drain, taint, maintenance |

Check OOMKilled:

```bash
oc get pod <pod> -n <ns> -o json | jq '.status.containerStatuses[] | {name, restartCount, lastState}'
oc describe pod <pod> -n <ns>
```

Example output:

```text
Last State: Terminated
Reason:     OOMKilled
Exit Code:  137
```

If the pod is OOMKilled repeatedly, eviction tuning will not fix the application. You need to fix memory sizing, memory leak, JVM/container memory flags, or limits.

# 8. KubeletConfig for Eviction and Garbage Collection

OpenShift manages kubelet configuration using `KubeletConfig` custom resources tied to MachineConfigPools.

## 8.1 View existing KubeletConfig objects

```bash
oc get kubeletconfig
oc get kubeletconfig -o yaml
```

## 8.2 View current node kubelet config

```bash
NODE=<node-name>
oc get --raw /api/v1/nodes/${NODE}/proxy/configz | jq '.kubeletconfig'
```

## 8.3 Example full eviction/GC config

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-eviction-gc
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
  kubeletConfig:
    evictionSoft:
      memory.available: "500Mi"
      nodefs.available: "10%"
      nodefs.inodesFree: "5%"
      imagefs.available: "15%"
      imagefs.inodesFree: "10%"
    evictionSoftGracePeriod:
      memory.available: "1m30s"
      nodefs.available: "1m30s"
      nodefs.inodesFree: "1m30s"
      imagefs.available: "1m30s"
      imagefs.inodesFree: "1m30s"
    evictionHard:
      memory.available: "200Mi"
      nodefs.available: "5%"
      nodefs.inodesFree: "4%"
      imagefs.available: "10%"
      imagefs.inodesFree: "5%"
    evictionPressureTransitionPeriod: 3m
    imageMinimumGCAge: 5m
    imageGCHighThresholdPercent: 80
    imageGCLowThresholdPercent: 75
```

Apply:

```bash
oc apply -f worker-eviction-gc.yaml
oc get mcp
```

## 8.4 Critical warning

OpenShift supports only one `KubeletConfig` object per MachineConfigPool. Do not create multiple independent KubeletConfig CRs for the same pool unless you know exactly how your version handles them. Prefer editing the existing one.

Also, for `evictionHard`, specify the full set of required parameters. Partial hard eviction configuration can lead to unexpected garbage collection behavior.

# 9. Node Allocatable and Eviction Thresholds

The scheduler does not use raw node capacity. It uses node allocatable.

Conceptually:

```text
Allocatable = Node Capacity - systemReserved - Hard Eviction Thresholds
```

Example:

```text
Node memory capacity: 32Gi
systemReserved:       3Gi
evictionHard:         100Mi
Effective allocatable: about 28.9Gi
```

Why this matters:

- If allocatable is too high, scheduler overpacks the node.
- If systemReserved is too low, kubelet/CRI-O/system daemons compete with pods.
- If eviction threshold is too low, node may hit kernel OOM before kubelet can evict cleanly.
- If eviction threshold is too high, usable capacity is wasted.

Check allocatable:

```bash
oc get node <node> -o json | jq '.status.capacity, .status.allocatable'
```

Check allocated requests:

```bash
oc describe node <node> | sed -n '/Allocated resources:/,/Events:/p'
```

# 10. Eviction and PodDisruptionBudget

## 10.1 What PDB protects

PDB protects against voluntary/API-initiated disruptions such as:

- `oc adm drain`,
- descheduler eviction using eviction subresource,
- machine deletion drain,
- maintenance automation using eviction API.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: api
```

For a 3-replica app, at least 2 must stay available.

## 10.2 What PDB does not protect

PDB does **not** prevent:

- node-pressure eviction,
- node crash,
- kernel OOM,
- hardware failure,
- accidental direct pod delete by workload owner,
- some involuntary disruptions.

## 10.3 Common PDB mistakes

### Mistake: one replica with minAvailable 1

```yaml
spec:
  minAvailable: 1
```

For one replica, this blocks voluntary eviction. Node drain can hang.

Better options:

- run at least 2 replicas,
- use `maxUnavailable: 1`,
- design HA properly,
- temporarily relax PDB during maintenance if approved.

### Mistake: overlapping PDB selectors

If multiple PDBs select the same pod, eviction can fail with API errors.

Check selectors:

```bash
oc get pdb -n <namespace> -o yaml
oc get pods -n <namespace> --show-labels
```

# 12. Production Prevention Checklist

## 12.1 Workload design

- Set CPU and memory requests for every container.
- Set memory limits for workloads that can leak memory.
- Set ephemeral-storage requests/limits for log-heavy/cache-heavy workloads.
- Use `emptyDir.sizeLimit` where appropriate.
- Avoid BestEffort pods in production.
- Size JVM/Go/Node.js apps with container awareness.
- Avoid writing large data to container writable layer.
- Use PVCs for persistent or large temporary data.

## 12.2 Namespace guardrails

Use LimitRanges:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: "100m"
      memory: "256Mi"
      ephemeral-storage: "512Mi"
    default:
      cpu: "500m"
      memory: "512Mi"
      ephemeral-storage: "2Gi"
```

Use ResourceQuotas:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: namespace-quota
spec:
  hard:
    pods: "100"
    requests.cpu: "20"
    requests.memory: "40Gi"
    requests.ephemeral-storage: "100Gi"
    limits.cpu: "40"
    limits.memory: "80Gi"
    limits.ephemeral-storage: "200Gi"
```

## 12.3 Node design

- Keep enough node disk for images, logs, and kubelet data.
- Monitor inode usage, not only disk GB.
- Reserve resources for system daemons.
- Align hard eviction thresholds with node allocatable.
- Avoid excessive pod density.
- Use dedicated nodes for noisy workloads.
- Use infra nodes for infrastructure components where appropriate.
- Plan MCO rollouts and upgrades with PDBs.

## 12.4 High availability design

- Use multiple replicas.
- Use PDBs correctly.
- Use topology spread constraints.
- Use anti-affinity for critical replicas.
- Avoid single-replica critical workloads unless downtime is acceptable.
- Test node drain before production upgrades.

## 12.5 Monitoring alerts

Recommended alert areas:

```text
Node MemoryPressure=True
Node DiskPressure=True
Node PIDPressure=True
Node Ready=False/Unknown
Filesystem usage > 80%
Filesystem inode usage > 80%
High container restarts
Frequent Evicted pods
MCP updating/degraded too long
PDB blocking drain
High pod ephemeral storage usage
```

Useful commands for quick checks:

```bash
oc adm top nodes
oc adm top pods -A --sort-by=memory
oc get nodes
oc get mcp
oc get co
oc get pdb -A
oc get events -A --sort-by=.lastTimestamp | tail -100
```

# 13. Real Incident Runbooks

## Runbook A: Pod shows `Evicted`

```bash
NS=<namespace>
POD=<pod>

oc describe pod $POD -n $NS
oc get pod $POD -n $NS -o yaml > ${NS}-${POD}.yaml
NODE=$(oc get pod $POD -n $NS -o jsonpath='{.spec.nodeName}')
echo $NODE
oc describe node $NODE > node-${NODE}.txt
oc get events -A --sort-by=.lastTimestamp | grep -i -E "$POD|evict|pressure|$NODE"
```

Decision:

- Message says memory -> go to MemoryPressure runbook.
- Message says ephemeral-storage/disk -> go to DiskPressure runbook.
- Node NotReady/Unreachable -> go to node health runbook.
- Drain/MCO events -> go to maintenance runbook.

## Runbook B: Node has DiskPressure

```bash
NODE=<node>
oc describe node $NODE | egrep -A10 'DiskPressure|Events'
oc debug node/$NODE
chroot /host

df -h
df -ih
du -xh /var/lib/kubelet 2>/dev/null | sort -h | tail -30
du -xh /var/lib/containers 2>/dev/null | sort -h | tail -30
du -xh /var/log 2>/dev/null | sort -h | tail -30
journalctl -u kubelet --since "2 hours ago" | grep -i -E 'disk|nodefs|imagefs|evict|garbage'
```

Fix path:

- logs huge -> reduce logging, rotate, check logging stack,
- imagefs huge -> image GC thresholds, CI churn,
- kubelet pods huge -> `emptyDir` or writable layer,
- inode full -> identify small-file producer.

## Runbook C: Drain stuck

```bash
NODE=<node>
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data --timeout=5m
```

If blocked:

```bash
oc get pdb -A
oc describe pdb <pdb> -n <namespace>
oc get pods -A --field-selector spec.nodeName=$NODE
oc get pods -A --field-selector spec.nodeName=$NODE -o wide
```

Check for:

- PDB `Allowed disruptions: 0`,
- standalone pod,
- local storage,
- finalizers,
- unhealthy pods,
- too long grace period.

## Runbook D: Evictions after new nodes added

Possible causes:

- descheduler enabled,
- cluster autoscaler consolidation,
- rebalancing profile,
- topology profile.

Check:

```bash
oc get kubedeschedulers.operator.openshift.io -A
oc get pods -n openshift-kube-descheduler-operator
oc get events -A --sort-by=.lastTimestamp | grep -i -E 'desched|evict'
oc get machines -n openshift-machine-api
```

# 14. Exam and Interview Notes

## Common interview question: “Does PDB prevent pod eviction?”

Strong answer:

> PDB prevents or limits voluntary/API-initiated evictions such as drain and descheduler eviction through the eviction subresource. It does not prevent involuntary node-pressure eviction, node failure, or kernel OOM. PDB also counts involuntary disruptions against the budget, so later drains may be blocked.

## Common interview question: “What is the difference between OOMKilled and Evicted?”

Strong answer:

> OOMKilled is usually container-level termination due to memory limit or kernel OOM, and the container can restart in the same pod. Evicted is pod-level termination/removal, usually with pod phase Failed, and a controller must create a replacement pod.

## Common interview question: “Why did a BestEffort pod get evicted first?”

Strong answer:

> BestEffort pods have no requests, so any usage is above request. During node-pressure eviction, kubelet ranks pods by whether usage exceeds requests, priority, and usage above requests. That makes BestEffort pods the first practical victims under pressure.

## Common interview question: “Why does drain hang?”

Strong answer:

> Most drain hangs are due to PDB allowed disruptions being zero, standalone pods, DaemonSets without `--ignore-daemonsets`, pods using local storage without `--delete-emptydir-data`, finalizers, or unhealthy pods protected by strict PDBs.

## Common interview question: “How do you prevent DiskPressure evictions?”

Strong answer:

> Monitor nodefs/imagefs and inode usage, set ephemeral-storage requests and limits, limit `emptyDir`, tune image garbage collection, reduce image churn, control application logs, keep enough disk capacity, and isolate noisy workloads.

# 16. Key Takeaways

1. Eviction is pod removal from a node; scheduling is pod placement onto a node.
2. Node-pressure eviction is done by kubelet and does not respect PDB.
3. API-initiated eviction, such as drain, respects PDB and termination grace.
4. DiskPressure includes both free space and inode pressure.
5. Image GC happens before or alongside disk pressure handling, but it cannot fix all disk problems.
6. BestEffort pods are most vulnerable because they have no requests.
7. PDB is necessary for safe maintenance but cannot protect against node resource exhaustion.
8. Evicted pods may remain as failed records and can be deleted after investigation.
9. KubeletConfig changes are powerful and node-impacting in OpenShift.
10. Good eviction prevention starts with requests, limits, storage limits, HA replicas, PDBs, and node capacity planning.
