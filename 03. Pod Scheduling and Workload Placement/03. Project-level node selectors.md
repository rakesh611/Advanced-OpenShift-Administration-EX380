## 1. Executive Summary

A **project-level node selector** is an OpenShift-specific workload placement control that applies a default `nodeSelector` to pods created inside a specific project/namespace.

In OpenShift, a project is backed by a Kubernetes `Namespace`. You configure the project-level selector by adding the following namespace annotation:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: "key=value,key2=value2"
```

When a pod is created in that namespace, OpenShift uses this selector to constrain the pod to nodes whose labels match the selector. This is useful when you want all workloads in a project to run only on a specific node pool, hardware class, region, cost tier, security zone, or tenant-dedicated worker group.

Example:

```bash
oc annotate namespace finance-prod \
  openshift.io/node-selector='workload=finance,environment=prod' \
  --overwrite
```

Nodes must have matching labels:

```bash
oc label node worker-a workload=finance environment=prod
oc label node worker-b workload=finance environment=prod
```

Any pod created in `finance-prod` must now land on a node matching:

```yaml
workload: finance
environment: prod
```

Project-level node selectors are powerful because they operate at the namespace boundary. Application teams do not need to add node placement rules to every `Deployment`, `StatefulSet`, `Job`, or `Pod` manifest. The platform team can centrally control where project workloads land.

## 2. Why Project-level Node Selectors Matter

In large OpenShift environments, workload placement cannot be left fully random. You usually need to answer questions like:

- Should production workloads share nodes with development workloads?
- Should PCI workloads run only on hardened/dedicated nodes?
- Should GPU workloads run only on GPU nodes?
- Should logging, monitoring, registry, and router workloads run on infrastructure nodes?
- Should a specific business unit or tenant have dedicated capacity?
- Should high-I/O workloads avoid general-purpose worker nodes?
- Should workloads run in a specific zone or region?
- Should cost-sensitive workloads land on spot/preemptible nodes?

OpenShift provides several workload placement mechanisms:

| Mechanism | Scope | Purpose |
|---|---:|---|
| `spec.nodeSelector` on pod template | Workload-specific | Simple hard node label match |
| Project-level node selector | Namespace/project | Default placement policy for all pods in a project |
| Cluster-wide `defaultNodeSelector` | Cluster-wide | Default placement policy for namespaces without project selectors |
| Node affinity | Workload-specific | More expressive hard or soft node selection |
| Taints and tolerations | Node and pod | Keep pods away unless explicitly tolerated |
| Topology spread constraints | Workload-specific | Spread pods across zones/nodes/racks |
| Pod affinity/anti-affinity | Workload-specific | Place pods near or away from other pods |

Project-level node selectors fill an important gap: **placement policy at namespace scope**.

They are especially valuable in enterprise OpenShift because project boundaries commonly map to teams, environments, tenants, applications, or business units.

## 3. Core Scheduling Background

Before understanding project-level node selectors, understand the basic scheduler flow.

When a pod is created, the Kubernetes/OpenShift scheduler does not immediately pick a random worker node. It evaluates several constraints:

1. **Node readiness**
   - Is the node `Ready`?
   - Is the node schedulable or cordoned?

2. **Taints and tolerations**
   - Does the node repel the pod with a `NoSchedule` taint?
   - Does the pod tolerate that taint?

3. **Node selector / node affinity**
   - Does the node have the required labels?
   - Does the pod require a specific zone, disk type, CPU type, GPU, or node pool?

4. **Resource fit**
   - Does the node have enough allocatable CPU, memory, ephemeral storage, and extended resources?

5. **Volume constraints**
   - Can the requested persistent volume attach to that node?
   - Does the storage class use topology constraints?

6. **Inter-pod rules**
   - Does pod affinity or anti-affinity allow the placement?

7. **Topology spread constraints**
   - Would the placement violate required skew across zones, nodes, or other topology domains?

8. **Scoring**
   - Among the nodes that pass all hard filters, the scheduler scores the remaining nodes and binds the pod to the best candidate.

A project-level node selector affects the scheduling process by adding a **hard node label requirement** to pods in a namespace.

If no node matches that requirement, the pod remains `Pending` or is rejected if there is a selector conflict during pod creation.

## 4. What Is a Project-level Node Selector?

A project-level node selector is a selector stored on the namespace annotation:

```yaml
openshift.io/node-selector: "key=value,key2=value2"
```

Example namespace:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: app-prod
  annotations:
    openshift.io/node-selector: "workload=app,environment=prod"
```

This means pods created in `app-prod` should run only on nodes matching both labels:

```yaml
workload: app
environment: prod
```

A node with only one matching label is not enough. `nodeSelector` is an AND condition.

Matching node:

```yaml
metadata:
  labels:
    workload: app
    environment: prod
    kubernetes.io/os: linux
```

Non-matching node:

```yaml
metadata:
  labels:
    workload: app
    environment: dev
```

The second node does not match because `environment=prod` is required.

## 5. How OpenShift Applies Project-level Node Selectors

At a high level, the flow is:

```text
Namespace annotation exists
        ↓
Pod is created in that namespace
        ↓
OpenShift applies or validates the project-level node selector
        ↓
Pod has effective node placement requirement
        ↓
Scheduler filters nodes by labels and other constraints
        ↓
Pod is bound to a matching node
```

For example, assume this project annotation:

```bash
oc annotate ns team-a openshift.io/node-selector='team=team-a,node-pool=gold' --overwrite
```

And this deployment has no explicit node selector:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: team-a
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: api
        image: quay.io/example/api:1.0
```

The resulting pods are constrained to nodes matching:

```yaml
team: team-a
node-pool: gold
```

The application manifest remains clean. The platform placement policy lives at the project level.

### Important Operational Detail

Project-level node selectors affect **new pod creation**. Existing running pods are not automatically evicted just because you add or change the namespace annotation.

For controller-managed workloads, recreate pods after changing the selector:

```bash
oc rollout restart deployment/api -n team-a
```

Or delete pods and allow the controller to recreate them:

```bash
oc delete pod -l app=api -n team-a
```

For standalone pods, you usually delete and recreate the pod.

## 6. Selector Precedence and Conflict Rules

Project-level node selectors interact with other selector sources.

### 6.1 Cluster-wide default node selector

OpenShift also supports a cluster-wide default node selector through the `Scheduler` custom resource:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: "type=user-node,region=east"
```

This default applies to pods created in namespaces that do not have their own project-level node selector.

If a namespace has the `openshift.io/node-selector` annotation, the project-level selector takes preference over the cluster-wide default.

### 6.2 Pod-level node selector

A pod or pod template can also define:

```yaml
spec:
  nodeSelector:
    disk: ssd
```

If the namespace has this project-level selector:

```yaml
openshift.io/node-selector: "region=east,type=user-node"
```

And the pod adds this selector:

```yaml
nodeSelector:
  disk: ssd
```

The effective placement requirement is:

```yaml
region: east
type: user-node
disk: ssd
```

That is an intersection. The node must match all required labels.

### 6.3 Conflicting key with different value

A pod can add additional keys, but it cannot use a different value for a key controlled by the project selector.

Project selector:

```yaml
openshift.io/node-selector: "region=east"
```

Pod selector:

```yaml
spec:
  nodeSelector:
    region: west
```

This conflicts. OpenShift rejects the pod with an error similar to:

```text
Error from server (Forbidden): error when creating "pod.yaml": pods "pod-4" is forbidden: pod node label selector conflicts with its project node label selector
```

This is admission-time protection. OpenShift does not silently choose one value over the other.

### 6.4 Practical precedence summary

| Policy source | Example | Effect |
|---|---|---|
| Cluster-wide default | `spec.defaultNodeSelector: type=user-node` | Applies to namespaces without project selector |
| Project-level selector | `openshift.io/node-selector: type=finance` | Takes preference over cluster default |
| Pod-level selector with extra key | `disk=ssd` | ANDed with project selector |
| Pod-level selector with same key, same value | `type=finance` | Allowed |
| Pod-level selector with same key, different value | `type=dev` | Rejected as conflict |

## 7. Designing a Node Label Strategy

Project-level node selectors are only as good as your node labels.

A weak label strategy causes scheduling failures, operational confusion, and accidental workload concentration.

### 7.1 Good label examples

Use labels that describe durable node characteristics or intended node pool ownership:

```text
node-pool=app-prod
node-pool=app-dev
workload=general
workload=infra
workload=ml
workload=database
team=payments
environment=prod
environment=nonprod
hardware=gpu
storage=nvme
zone=az-a
cost-tier=spot
compliance=pci
```

### 7.2 Avoid unstable labels

Avoid labels that change frequently or describe temporary state:

```text
cpu-free=high
memory-pressure=false
incident=active
maintenance-window=today
```

The scheduler is not a real-time monitoring engine. Labels should represent stable placement categories.

### 7.3 Prefer platform-owned label prefixes for enterprise governance

For production governance, consider labels with your organization domain:

```text
platform.example.com/node-pool=finance-prod
platform.example.com/compliance=pci
platform.example.com/hardware=gpu
platform.example.com/cost-tier=reserved
```

This reduces collision risk with application labels and built-in Kubernetes/OpenShift labels.

### 7.4 Keep selectors simple

Project node selectors use simple equality-based matching. Keep them short and intentional:

Good:

```text
node-pool=finance-prod
```

Acceptable:

```text
node-pool=finance-prod,region=east
```

Risky:

```text
node-pool=finance-prod,region=east,hardware=nvme,cost-tier=reserved,compliance=pci,owner=finance
```

Every additional selector key reduces the number of eligible nodes.

## 8. Creating Project-level Node Selectors

### 8.1 Create a new project with a node selector

```bash
oc adm new-project app-prod \
  --node-selector='node-pool=app-prod,environment=prod'
```

Verify:

```bash
oc get namespace app-prod -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
```

Expected output:

```text
node-pool=app-prod,environment=prod
```

### 8.2 Add a selector to an existing project

```bash
oc annotate namespace app-prod \
  openshift.io/node-selector='node-pool=app-prod,environment=prod' \
  --overwrite
```

Or patch it:

```bash
oc patch namespace app-prod --type=merge -p \
  '{"metadata":{"annotations":{"openshift.io/node-selector":"node-pool=app-prod,environment=prod"}}}'
```

### 8.3 YAML method

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: app-prod
  annotations:
    openshift.io/node-selector: "node-pool=app-prod,environment=prod"
```

Apply:

```bash
oc apply -f namespace-app-prod.yaml
```

### 8.4 Set an empty selector intentionally

To disable a default project-wide selector for a namespace, set the annotation to an empty string:

```bash
oc patch namespace app-prod -p \
  '{"metadata":{"annotations":{"openshift.io/node-selector":""}}}'
```

This is commonly needed for DaemonSet-style workloads that must run across many or all nodes.

### 8.5 Remove the annotation completely

```bash
oc annotate namespace app-prod openshift.io/node-selector-
```

If the cluster has a cluster-wide `defaultNodeSelector`, removing the project annotation can cause the namespace to fall back to the cluster-wide default for newly created pods.

## 9. Labeling Nodes Correctly

A project node selector is useless until matching nodes exist.

### 9.1 Label a node directly

```bash
oc label node worker-1 node-pool=app-prod environment=prod
oc label node worker-2 node-pool=app-prod environment=prod
```

Verify:

```bash
oc get nodes -l node-pool=app-prod,environment=prod
```

Show labels:

```bash
oc get nodes --show-labels
```

Or more focused:

```bash
oc get nodes -L node-pool -L environment
```

### 9.2 Overwrite an existing label

```bash
oc label node worker-1 node-pool=app-prod --overwrite
```

### 9.3 Remove a node label

```bash
oc label node worker-1 node-pool-
```

### 9.4 Prefer labeling MachineSets for durable labels

In installer-provisioned infrastructure, worker nodes are often created by MachineSets.

If you label only the current Node object, the label might disappear when the machine is replaced. A better approach is to label the MachineSet template so future nodes inherit the label.

Example:

```bash
oc patch machineset <machineset-name> \
  -n openshift-machine-api \
  --type='merge' \
  -p '{
    "spec": {
      "template": {
        "spec": {
          "metadata": {
            "labels": {
              "node-pool": "app-prod",
              "environment": "prod"
            }
          }
        }
      }
    }
  }'
```

Verify MachineSet template labels:

```bash
oc get machineset <machineset-name> \
  -n openshift-machine-api \
  -o yaml | grep -A10 'metadata:'
```

Then roll or replace machines according to your operational process so newly created nodes pick up the labels.

### 9.5 MachineSet labels versus Kubernetes labels

MachineSet template labels are applied to machine/node lifecycle objects when new machines are created. Existing nodes may not immediately receive new labels until machines are recreated or manually labeled.

In production, use a controlled process:

1. Patch MachineSet template.
2. Label existing nodes if immediate scheduling is required.
3. Roll nodes gradually if you need template labels to become authoritative.
4. Verify replacement nodes receive the expected labels.

## 10. Testing and Verifying Placement

### 10.1 Create a test project selector

```bash
oc new-project selector-test

oc annotate ns selector-test \
  openshift.io/node-selector='node-pool=app-prod' \
  --overwrite
```

### 10.2 Label one worker node

```bash
oc label node worker-1 node-pool=app-prod
```

### 10.3 Create a deployment

```bash
oc create deployment hello \
  --image=registry.access.redhat.com/ubi9/httpd-24 \
  -n selector-test
```

### 10.4 Check pod placement

```bash
oc get pods -n selector-test -o wide
```

Expected result: the pod should run on `worker-1` or another node labeled `node-pool=app-prod`.

### 10.5 Inspect the effective pod node selector

```bash
POD=$(oc get pod -n selector-test -l app=hello -o jsonpath='{.items[0].metadata.name}')

oc get pod "$POD" -n selector-test \
  -o jsonpath='{.spec.nodeSelector}{"\n"}'
```

You should see the selector that controls placement.

### 10.6 Describe the pod

```bash
oc describe pod "$POD" -n selector-test
```

Look for:

```text
Node-Selectors: node-pool=app-prod
Node:           worker-1/...
Events:         Successfully assigned selector-test/hello-... to worker-1
```

## 11. Changing or Removing a Project Node Selector

### 11.1 Change the selector

```bash
oc annotate ns app-prod \
  openshift.io/node-selector='node-pool=app-prod-v2' \
  --overwrite
```

This affects new pods. Existing running pods normally stay where they are.

For deployments:

```bash
oc rollout restart deployment -n app-prod --all
```

For a specific deployment:

```bash
oc rollout restart deployment/api -n app-prod
```

### 11.2 Remove the selector

```bash
oc annotate ns app-prod openshift.io/node-selector-
```

Then restart workloads if you want new scheduling decisions:

```bash
oc rollout restart deployment -n app-prod --all
```

### 11.3 Set it to empty string

```bash
oc annotate ns app-prod openshift.io/node-selector='' --overwrite
```

An empty string is not the same operationally as forgetting the setting when a cluster-wide default selector exists. An explicit empty annotation can be used to override or disable project default behavior for that namespace.

## 12. Interaction with Cluster-wide Default Node Selectors

Cluster-wide default node selectors are configured in the Scheduler object:

```bash
oc edit scheduler cluster
```

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: "node-pool=general"
```

View current value:

```bash
oc get scheduler cluster -o jsonpath='{.spec.defaultNodeSelector}{"\n"}'
```

### 12.1 Behavior

If no project-level selector exists, newly created pods can receive the cluster default selector.

If a project has this annotation:

```yaml
openshift.io/node-selector: "node-pool=finance"
```

Then the project-level selector is used in preference to the cluster default.

### 12.2 Operational warning

Changing the cluster-wide default selector is much riskier than changing a project-level selector.

A bad cluster default can break many namespaces at once. Use project-level selectors when you want targeted placement control.

### 12.3 Good use of cluster-wide default

A common use is to keep regular user workloads on worker nodes:

```yaml
spec:
  defaultNodeSelector: "node-role.kubernetes.io/worker="
```

However, be careful when mixing node roles such as `worker`, `infra`, and `master/control-plane`. A default selector can make operator pods, daemonset pods, or specialized workloads unschedulable if their own selectors conflict.

## 13. Interaction with Pod-level Node Selectors

A pod-level selector is defined in the pod template:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      nodeSelector:
        disk: ssd
      containers:
      - name: api
        image: quay.io/example/api:1.0
```

If the project has:

```yaml
openshift.io/node-selector: "node-pool=finance"
```

Then effective placement is:

```yaml
node-pool: finance
disk: ssd
```

The pod must land on a node with both labels.

### 13.1 Additive use case

Project controls tenant pool:

```text
node-pool=finance
```

Application controls hardware type:

```text
disk=ssd
```

This is a good model if the platform team and app team have clear ownership.

### 13.2 Conflict use case

Project controls:

```text
node-pool=finance
```

Application tries:

```text
node-pool=general
```

This is not allowed. The pod is rejected because it conflicts with the namespace placement policy.

## 14. Interaction with Node Affinity

Node affinity is more expressive than `nodeSelector`.

With `nodeSelector`, you can only express simple equality:

```yaml
nodeSelector:
  hardware: gpu
```

With node affinity, you can express conditions such as:

- `In`
- `NotIn`
- `Exists`
- `DoesNotExist`
- `Gt`
- `Lt`
- required rules
- preferred rules

Example:

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: topology.kubernetes.io/zone
            operator: In
            values:
            - east-a
            - east-b
```

### 14.1 Project selector plus node affinity

If a project selector requires:

```text
node-pool=finance
```

And pod node affinity requires:

```text
topology.kubernetes.io/zone In [east-a, east-b]
```

The scheduler must find nodes satisfying both:

```text
node-pool=finance
AND zone in east-a/east-b
```

### 14.2 Best practice

Use project-level node selectors for broad namespace boundaries:

```text
node-pool=finance
```

Use node affinity for workload-specific advanced rules:

```text
hardware In gpu-a10,gpu-a100
zone In east-a,east-b
```

Do not overload project selectors with too many conditions.

## 15. Interaction with Taints and Tolerations

Node selectors and taints solve different problems.

| Mechanism | Direction | Meaning |
|---|---|---|
| Node selector | Pod chooses node labels | “This pod can run only on matching nodes.” |
| Taint | Node repels pods | “Do not run pods here unless they tolerate this taint.” |
| Toleration | Pod accepts taint | “This pod is allowed on tainted nodes.” |

### 15.1 Dedicated node pool pattern

For strong workload separation, use both labels and taints.

Label dedicated finance nodes:

```bash
oc label node worker-fin-1 node-pool=finance
oc label node worker-fin-2 node-pool=finance
```

Taint dedicated finance nodes:

```bash
oc adm taint nodes worker-fin-1 dedicated=finance:NoSchedule
oc adm taint nodes worker-fin-2 dedicated=finance:NoSchedule
```

Set project selector:

```bash
oc annotate ns finance-prod \
  openshift.io/node-selector='node-pool=finance' \
  --overwrite
```

Workloads in `finance-prod` still need a toleration if the nodes are tainted:

```yaml
spec:
  template:
    spec:
      tolerations:
      - key: dedicated
        operator: Equal
        value: finance
        effect: NoSchedule
```

### 15.2 Why selector alone is not enough for exclusivity

A project-level selector ensures that finance pods go to finance nodes.

It does **not** prevent other pods from landing on finance nodes if those other pods have no restriction and the finance nodes are otherwise eligible.

For exclusivity, add a taint to finance nodes and tolerations only for allowed workloads.

### 15.3 Project selector plus taint model

```text
Label + project selector = attract/require intended workloads
Taint + toleration       = repel unauthorized workloads
RBAC/GitOps policy       = control who can add tolerations
```

This is a more complete enterprise isolation model.

## 16. Interaction with DaemonSets

DaemonSets are special because they are commonly expected to run one pod per eligible node.

Examples:

- log collectors
- monitoring agents
- storage agents
- network plugins
- node exporters
- security agents

A project-level node selector can accidentally restrict a DaemonSet to only matching nodes.

If the namespace has:

```yaml
openshift.io/node-selector: "node-pool=app-prod"
```

A DaemonSet in that namespace might run only on nodes matching `node-pool=app-prod`, not all nodes.

### 16.1 Disable selector for DaemonSet namespaces when required

```bash
oc patch namespace node-agents -p \
  '{"metadata":{"annotations":{"openshift.io/node-selector":""}}}'
```

Or create the project with an empty node selector:

```bash
oc adm new-project node-agents --node-selector=""
```

### 16.2 Use DaemonSet-level nodeSelector when intentional

If the DaemonSet should run only on infra nodes:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
```

This should be intentional and documented.

## 17. Interaction with MachineSets and Autoscaling

Project-level node selectors often depend on MachineSets because MachineSets define worker pools.

Example node pools:

```text
app-prod-us-east-1a
app-prod-us-east-1b
app-dev-us-east-1a
gpu-prod-us-east-1a
infra-us-east-1a
```

Each MachineSet should stamp durable labels onto created nodes:

```yaml
spec:
  template:
    spec:
      metadata:
        labels:
          node-pool: app-prod
          environment: prod
          topology.kubernetes.io/zone: us-east-1a
```

### 17.1 Autoscaler consideration

If a project selector requires:

```text
node-pool=gpu-prod
```

But the cluster autoscaler does not know how to scale a MachineSet that can satisfy this selector, pods may remain Pending.

Check:

```bash
oc get machinesets -n openshift-machine-api
oc get nodes -L node-pool -L hardware
oc describe pod <pod> -n <namespace>
```

### 17.2 Minimum capacity

For critical projects, keep at least two or three nodes matching the selector across failure domains if high availability is required.

A selector that matches only one node creates a single point of failure.

## 18. Interaction with Storage and PVC Topology

Storage can impose hidden placement requirements.

A pod might match the project node selector but still remain Pending because its PVC can only attach in another zone or node topology.

Common storage-related constraints:

- Local persistent volumes
- CSI drivers with topology awareness
- EBS/Azure Disk/GCE PD style zonal volumes
- `WaitForFirstConsumer` binding mode
- OpenShift Data Foundation / Ceph topology
- ReadWriteOnce volume already attached to another node

### 18.1 Example failure pattern

Project selector:

```text
zone=east-a
```

PVC-bound PV topology:

```text
zone=east-b
```

Pod event:

```text
0/6 nodes are available: volume node affinity conflict
```

This is not a pure node selector problem. It is a combined placement problem.

### 18.2 Troubleshooting commands

```bash
oc describe pod <pod> -n <namespace>
oc get pvc -n <namespace>
oc describe pvc <pvc> -n <namespace>
oc get pv <pv-name> -o yaml
oc get storageclass
oc describe storageclass <storageclass-name>
oc get nodes -L topology.kubernetes.io/zone -L node-pool
```

### 18.3 Best practice

When using project-level node selectors and persistent storage, align:

```text
Project selector
Node labels
MachineSet zone
StorageClass allowed topology
PV node affinity
Application HA design
```

## 20. Troubleshooting Pending Pods

### 20.1 Common symptom

```bash
oc get pods -n app-prod
```

Output:

```text
NAME                   READY   STATUS    RESTARTS   AGE
api-6fd86cc9d8-2qlx7   0/1     Pending   0          5m
```

Describe the pod:

```bash
oc describe pod api-6fd86cc9d8-2qlx7 -n app-prod
```

Common event:

```text
0/5 nodes are available: 5 node(s) didn't match Pod's node affinity/selector.
```

### 20.2 Step-by-step diagnosis

#### Step 1: Check project selector

```bash
oc get ns app-prod -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
```

Example:

```text
node-pool=app-prod,environment=prod
```

#### Step 2: Check pod selector

```bash
oc get pod api-6fd86cc9d8-2qlx7 -n app-prod \
  -o jsonpath='{.spec.nodeSelector}{"\n"}'
```

#### Step 3: Check matching nodes

```bash
oc get nodes -l node-pool=app-prod,environment=prod
```

If this returns no nodes, the selector has no eligible target.

#### Step 4: Check node readiness

```bash
oc get nodes
```

A node with matching labels must also be `Ready`.

#### Step 5: Check taints

```bash
oc describe node <node-name> | grep -i taints -A2
```

If the node has a `NoSchedule` taint, the pod needs a matching toleration.

#### Step 6: Check resource fit

```bash
oc describe pod <pod> -n app-prod
oc adm top nodes
oc adm top pods -A
```

A node can match the selector but still not have enough CPU or memory.

#### Step 7: Check PVC/storage events

```bash
oc get pvc -n app-prod
oc describe pvc <pvc> -n app-prod
oc describe pod <pod> -n app-prod
```

Look for volume node affinity conflicts or attach errors.

#### Step 8: Check cluster-wide default selector

```bash
oc get scheduler cluster -o jsonpath='{.spec.defaultNodeSelector}{"\n"}'
```

If there is no project selector, the cluster default might be constraining pods.

### 20.3 Fast triage command set

```bash
NS=app-prod
POD=$(oc get pod -n $NS -o jsonpath='{.items[0].metadata.name}')

echo "Namespace selector:"
oc get ns $NS -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'

echo "Pod selector:"
oc get pod $POD -n $NS -o jsonpath='{.spec.nodeSelector}{"\n"}'

echo "Pod node:"
oc get pod $POD -n $NS -o wide

echo "Events:"
oc describe pod $POD -n $NS | sed -n '/Events:/,$p'

echo "Cluster default selector:"
oc get scheduler cluster -o jsonpath='{.spec.defaultNodeSelector}{"\n"}'
```

## 21. Troubleshooting Admission Conflicts

Sometimes the pod does not even get created.

Example:

```text
Error from server (Forbidden): error when creating "pod.yaml": pods "pod-4" is forbidden: pod node label selector conflicts with its project node label selector
```

### 21.1 Cause

Namespace selector:

```text
region=east
```

Pod selector:

```yaml
nodeSelector:
  region: west
```

OpenShift rejects the pod because the same selector key has different values.

### 21.2 Fix options

Option 1: Change the pod selector to match the project:

```yaml
nodeSelector:
  region: east
```

Option 2: Remove the pod-level conflicting key:

```yaml
nodeSelector:
  disk: ssd
```

Option 3: Change the project selector if the project policy is wrong:

```bash
oc annotate ns app-prod openshift.io/node-selector='region=west' --overwrite
```

Option 4: Move the workload to a different namespace with the desired placement policy.

### 21.3 Do not bypass the policy

Avoid using `spec.nodeName` as a workaround. It bypasses normal scheduler selection and creates operational risk. Use selectors, affinity, taints/tolerations, and correct namespace policy instead.

## 22. Production Best Practices

### 22.1 Use project selectors for broad tenant boundaries

Good examples:

```text
node-pool=payments-prod
node-pool=ml-gpu
node-pool=dev-spot
```

### 22.2 Use taints for exclusivity

Project selector ensures selected workloads go to selected nodes.

Taints ensure unrelated workloads do not land there accidentally.

Dedicated node pool pattern:

```text
Node label: node-pool=payments-prod
Node taint: dedicated=payments-prod:NoSchedule
Project selector: node-pool=payments-prod
Workload toleration: dedicated=payments-prod
```

### 22.3 Keep labels durable

Prefer MachineSet template labels over manual node-only labels for cloud or IPI-managed clusters.

### 22.4 Keep selectors minimal

Each additional key reduces scheduling flexibility.

Recommended:

```text
node-pool=payments-prod
```

Not recommended unless truly needed:

```text
node-pool=payments-prod,zone=east-a,disk=nvme,cpu=amd,owner=team-a,environment=prod
```

### 22.5 Maintain capacity headroom

A selector that matches too few nodes can create a scheduling bottleneck.

For production, ensure:

- enough matching nodes
- enough CPU/memory headroom
- multiple failure domains if HA is required
- autoscaler compatibility
- storage topology compatibility

### 22.6 Use GitOps for namespace policy

Manage namespace annotations declaratively:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments-prod
  annotations:
    openshift.io/node-selector: "node-pool=payments-prod"
```

Store it in Git with review and approval.

### 22.7 Document ownership

Document:

- who owns the node pool
- who can change labels
- which namespaces use the node pool
- whether taints are required
- expected minimum/maximum capacity
- rollback process

### 22.8 Monitor scheduling failures

Alert on pods stuck in Pending because of selector mismatch.

Useful signals:

```bash
oc get events -A | grep -i "didn't match"
oc get pods -A --field-selector=status.phase=Pending
```

Prometheus/Kube State Metrics can also expose unschedulable pod conditions.

## 23. Anti-patterns

### 23.1 Using project selectors as a security boundary by themselves

A project selector is a scheduling policy, not a complete security boundary.

Use additional controls:

- RBAC
- SCC / Pod Security Admission controls
- NetworkPolicy
- image policy
- audit logging
- taints/tolerations
- node hardening
- compliance scanning

### 23.2 Matching only one node for production

Bad:

```text
openshift.io/node-selector: "kubernetes.io/hostname=worker-1"
```

This creates a single point of failure.

Prefer selecting a node pool:

```text
node-pool=prod-apps
```

### 23.3 Labeling nodes manually without updating MachineSets

Manual labels can disappear when nodes are replaced.

Patch MachineSets or use your cluster lifecycle tooling.

### 23.4 Too many placement layers

Avoid unnecessary combinations like:

- project selector
- pod nodeSelector
- required node affinity
- hard pod anti-affinity
- topology spread `DoNotSchedule`
- restrictive PVC topology
- taints without tolerations

This can create pods that can never schedule.

### 23.5 Using cluster-wide default selector for everything

A cluster-wide default is broad and risky. Use project-level selectors for targeted placement.

### 23.6 Forgetting DaemonSet behavior

A namespace-level selector can restrict DaemonSet pods unexpectedly.

For agent namespaces, explicitly set:

```yaml
openshift.io/node-selector: ""
```

if the DaemonSet should not inherit a restrictive project selector.


```bash
oc annotate ns payments-prod \
```

## 25. Runbook: Roll Back a Bad Project Node Selector

Scenario: You added a selector and pods are stuck Pending.

### Step 1: Confirm the namespace selector

```bash
oc get ns app-prod -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
```

### Step 2: Check if matching nodes exist

```bash
oc get nodes -l '<selector-key>=<selector-value>'
```

Example:

```bash
oc get nodes -l node-pool=app-prod
```

### Step 3: Remove selector temporarily

```bash
oc annotate ns app-prod openshift.io/node-selector-
```

If the cluster-wide default selector is also problematic, set explicit empty string:

```bash
oc annotate ns app-prod openshift.io/node-selector='' --overwrite
```

### Step 4: Recreate pending pods

```bash
oc delete pod -n app-prod --field-selector=status.phase=Pending
```

For deployments:

```bash
oc rollout restart deployment -n app-prod --all
```

### Step 5: Watch recovery

```bash
oc get pods -n app-prod -w
```

### Step 6: Fix root cause

Common root causes:

- wrong selector key
- wrong selector value
- node labels missing
- labels added to MachineSet but not current nodes
- taints missing tolerations
- insufficient CPU/memory
- PVC topology conflict
- cluster autoscaler does not scale matching node group

## 27. Interview-style Deep Questions

### Q1. What problem do project-level node selectors solve?

They let cluster administrators apply namespace-level placement policy so all pods created in a project are constrained to a specific node label set without requiring every workload manifest to define its own `nodeSelector`.

### Q2. Where is the project-level node selector configured?

On the namespace annotation:

```yaml
openshift.io/node-selector: "key=value,key2=value2"
```

### Q3. Does it affect existing running pods?

No, not automatically. It affects new pod creation. Existing pods generally continue running until recreated, rescheduled, or rolled out.

### Q4. What happens if no node matches the selector?

New pods remain Pending with scheduler events similar to:

```text
node(s) didn't match Pod's node affinity/selector
```

### Q5. What happens if a pod uses a conflicting node selector?

OpenShift rejects the pod with a forbidden error because the pod selector conflicts with the project node selector.

### Q6. Which takes precedence: project selector or cluster-wide default selector?

The project-level selector takes preference. The cluster-wide default is not applied to namespaces that have their own project-level node selector.

### Q7. Can a pod add extra node selector keys?

Yes, if they do not conflict with the project selector. The result is an intersection of all required labels.

### Q8. Is project-level node selector enough for dedicated nodes?

No. It attracts project pods to matching nodes, but does not repel other pods. Use taints and tolerations for stronger exclusivity.

### Q9. What is the difference between project node selector and node affinity?

Project node selector is namespace-level and simple equality-based. Node affinity is pod-level and supports richer expressions such as `In`, `NotIn`, `Exists`, and preferred scheduling.

### Q10. Why prefer MachineSet labels over direct node labels?

MachineSet template labels are durable for newly created/replaced machines. Direct node labels can be lost when nodes are replaced.

## Final Practical Summary

For advanced OpenShift administration, remember this mental model:

```text
Project-level node selector = namespace-level hard node placement policy
```

Use it when the platform team wants to control where all workloads in a project run.

Core commands:

```bash
oc annotate ns <namespace> openshift.io/node-selector='node-pool=prod' --overwrite
oc label node <node> node-pool=prod
oc get nodes -l node-pool=prod
oc get pod <pod> -n <namespace> -o jsonpath='{.spec.nodeSelector}{"\n"}'
oc describe pod <pod> -n <namespace>
```

Production-grade design usually combines:

```text
Project selector  → require workloads to use intended node pool
Node labels       → identify node pool capability/ownership
MachineSet labels → make labels durable
Taints            → repel unrelated workloads
Tolerations       → allow approved workloads
Monitoring        → detect Pending pods quickly
GitOps            → make policy auditable and reversible
```
