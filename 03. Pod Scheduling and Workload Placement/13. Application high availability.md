# Application High Availability in Pod Scheduling and Workload Placement for Advanced OpenShift Administration

**Audience:** Advanced OpenShift administrators, SREs, platform engineers, and Linux/DevOps engineers with production experience.  
**Scope:** Application high availability from the perspective of OpenShift Container Platform pod scheduling and workload placement.  
**Assumption:** Examples use OpenShift 4.x style resources and commands. Validate exact API availability against your cluster version.

---

## 1. What Application High Availability Means in OpenShift

Application high availability, or HA, means the application continues to serve users even when one or more expected failures happen. In OpenShift, HA is not achieved by only setting `replicas: 3`. It is achieved by combining workload replicas, scheduling rules, health checks, disruption control, graceful rollouts, storage design, service routing, resource guarantees, and operational validation.

A production OpenShift application should survive these common failure events:

- A container process crashes.
- A pod is deleted or evicted.
- A worker node goes down.
- A node is drained for maintenance.
- A MachineConfigPool update reboots nodes one by one.
- A zone or rack becomes unavailable.
- A new deployment version fails readiness checks.
- A pod is scheduled on an overloaded or unsuitable node.
- A volume cannot attach in another zone.
- A route, service, or endpoint selector is misconfigured.
- A noisy-neighbor workload consumes CPU, memory, PID, or I/O capacity.

In OpenShift, application HA is implemented in layers:

| Layer | HA Responsibility |
|---|---|
| Application design | Stateless replicas, idempotency, session handling, graceful shutdown, retry logic |
| Workload controller | Keeps desired replicas running using `Deployment`, `StatefulSet`, `DaemonSet`, etc. |
| Scheduler | Places pods on eligible nodes according to labels, affinity, taints, topology, resources, and policies |
| Kubelet | Runs containers, performs probes, restarts failed containers |
| Service and route layer | Sends traffic only to ready endpoints and exposes applications internally or externally |
| Cluster operations | Node drain, updates, autoscaling, descheduling, monitoring, alerting, capacity planning |
| Storage layer | Provides persistent data availability and topology-aware volume placement |

The key mindset for a senior administrator is simple:

> HA is not a single YAML field. HA is an availability contract across failure domains.

## 2. Failure Domains: The Foundation of HA Placement

A failure domain is a boundary where a single failure can affect multiple pods at once.

Common failure domains in OpenShift include:

| Failure Domain | Example Topology Label | Impact |
|---|---|---|
| Node | `kubernetes.io/hostname` | Node crash removes all pods on that node |
| Rack | Custom label such as `topology.example.com/rack` | Rack power/network issue impacts all nodes in rack |
| Zone | `topology.kubernetes.io/zone` | Cloud availability zone or datacenter zone failure |
| Region | `topology.kubernetes.io/region` | Larger geographic outage |
| Storage domain | Storage class / storage backend topology | Volume attach or data availability issue |
| Network domain | VLAN, subnet, router, firewall path | Traffic failure or isolation issue |

For HA, replicas must be distributed across meaningful failure domains. Running three replicas on the same node is not HA. Running three replicas on three worker nodes in the same rack is better, but still weak against rack failure. Running replicas across zones is stronger, but only if networking, storage, routing, and capacity also support it.

### Practical HA Target Examples

| Application Type | Minimum Practical HA Target |
|---|---|
| Stateless web/API | 2+ replicas across different nodes; preferably 3+ across zones |
| Critical API | 3+ replicas, topology spread, PDB, HPA, strict readiness probes |
| Queue consumer | Multiple replicas across nodes; ensure idempotent processing |
| Singleton scheduler/leader app | Multiple replicas with leader election, PDB, anti-affinity |
| Stateful database | Operator-managed cluster or StatefulSet with quorum-aware placement |
| Cache | Multiple replicas, anti-affinity, client retry/reconnect logic |

## 3. HA Starts with Correct Replica Strategy

### 3.1 Stateless Applications

For stateless applications, use a `Deployment` with multiple replicas. The scheduler can then distribute those replicas according to placement rules.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-api
  namespace: prod-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-api
  template:
    metadata:
      labels:
        app: web-api
        tier: frontend
    spec:
      containers:
      - name: web-api
        image: quay.io/example/web-api:1.0
        ports:
        - containerPort: 8080
```

This gives the controller permission to run three pods, but does not guarantee good placement. Without anti-affinity or topology spread constraints, the scheduler might place more than one replica on the same node, especially in a small or constrained cluster.

### 3.2 Stateful Applications

For stateful applications, use `StatefulSet` or, preferably, a supported Operator for the product. Stateful HA is harder because storage, identity, quorum, replication, backup, and recovery matter.

A `StatefulSet` gives each replica:

- Stable network identity.
- Stable persistent volume claim.
- Ordered startup and termination behavior.
- Predictable pod names such as `db-0`, `db-1`, `db-2`.

However, `StatefulSet` does not automatically make the database highly available. The application itself must support replication or clustering.

### 3.3 Singleton Applications

A singleton pod is a single point of failure. If the application truly requires only one active instance, use one of these patterns:

- Multiple replicas with leader election.
- Active/passive application design.
- Operator-managed failover.
- External HA service dependency.

Avoid long-term production workloads with `replicas: 1` unless downtime is acceptable.

## 4. Scheduler Decision Flow for HA Workloads

When a pod is created, the OpenShift scheduler must find a node where it can run. The scheduler evaluates many constraints, including:

1. Is the node ready and schedulable?
2. Does the node have enough requested CPU, memory, ephemeral storage, and extended resources?
3. Does the pod match required node selectors and node affinity?
4. Does the pod tolerate node taints?
5. Does the pod satisfy required pod affinity or anti-affinity?
6. Does the pod satisfy topology spread constraints?
7. Does the pod fit volume topology requirements?
8. Does the pod comply with admission policies, security constraints, quotas, and limits?
9. Among eligible nodes, which one scores best?

A pod can remain `Pending` if HA rules are too strict for available cluster capacity. This is a common senior-level troubleshooting point: a perfectly written HA policy can still block scheduling if the cluster does not have enough nodes, labels, zones, storage support, or free resources.

## 5. Node Labels: The Base of Placement Control

The scheduler uses labels to understand node characteristics. Labels are key-value metadata on nodes.

Check node labels:

```bash
oc get nodes --show-labels
```

Show selected topology labels:

```bash
oc get nodes -L kubernetes.io/hostname,topology.kubernetes.io/zone,topology.kubernetes.io/region
```

Add a custom label:

```bash
oc label node worker01 node-role.kubernetes.io/app=
oc label node worker01 workload=frontend
oc label node worker02 workload=frontend
oc label node worker03 workload=frontend
```

Remove a label:

```bash
oc label node worker01 workload-
```

### Important Label Practices

Use labels that represent stable infrastructure facts:

- `workload=frontend`
- `workload=backend`
- `node-type=app`
- `topology.example.com/rack=rack-a`
- `hardware=high-memory`
- `storage=fast-ssd`

Avoid labels that change frequently or represent temporary states:

- `current-load=low`
- `maintenance=no`
- `today-special=true`

For cloud or machine API managed nodes, apply labels through `MachineSet` or machine templates when possible. If a node is replaced, labels applied only directly to the old node might not exist on the new node.

## 6. Node Selector: Simple Hard Placement

`nodeSelector` is the simplest hard placement rule. The pod schedules only on nodes with matching labels.

Example:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload: frontend
```

This is useful for dedicated worker pools, GPU nodes, storage-optimized nodes, or regional placement.

### HA Risk with Node Selectors

A node selector can reduce HA if it selects too few nodes.

Bad example:

```yaml
nodeSelector:
  kubernetes.io/hostname: worker01
```

This pins the workload to one node. If `worker01` fails, the pod cannot move elsewhere.

Better example:

```yaml
nodeSelector:
  workload: frontend
```

This allows scheduling to any node labeled for frontend workloads.

### Troubleshooting Node Selector Issues

```bash
oc describe pod <pod-name> -n <namespace>
oc get nodes --show-labels | grep workload
oc get events -n <namespace> --sort-by='.lastTimestamp'
```

Typical event:

```text
0/6 nodes are available: 6 node(s) didn't match Pod's node affinity/selector.
```

Root causes:

- Node label is missing.
- Label key or value has a typo.
- Project-level node selector conflicts with pod node selector.
- Cluster-wide default node selector limits placement.
- The selected nodes are unschedulable or tainted.

## 7. Project-Level Node Selectors

OpenShift supports project-level node selectors through a namespace annotation. This allows an administrator to force all pods in a project to run only on selected nodes.

Example:

```bash
oc annotate namespace prod-app openshift.io/node-selector='workload=frontend' --overwrite
```

Any pod created in that namespace is constrained to nodes with `workload=frontend`.

Check namespace selector:

```bash
oc get namespace prod-app -o yaml | grep -A3 openshift.io/node-selector
```

### HA Use Case

Project-level selectors are useful for multi-tenancy:

- Team A workloads run on app pool A.
- Team B workloads run on app pool B.
- Regulated workloads run on compliance nodes.
- Noisy workloads run on isolated nodes.

### HA Risk

If the selected node pool is too small, the project becomes fragile. Always size the selected pool for the expected failure domain.

For example, if `prod-app` requires three replicas and must survive one node failure, the selected node pool should have at least three healthy schedulable nodes, and preferably more.

## 8. Node Affinity: Advanced Node Selection

Node affinity is more expressive than `nodeSelector`. It supports required and preferred rules.

### 8.1 Required Node Affinity

Required node affinity is a hard rule. The pod cannot schedule unless the rule is satisfied.

Example:

```yaml
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: workload
                operator: In
                values:
                - frontend
                - api
```

This means the pod can run only on nodes where `workload` is either `frontend` or `api`.

### 8.2 Preferred Node Affinity

Preferred node affinity is a soft rule. The scheduler tries to follow it, but can place the pod elsewhere if necessary.

Example:

```yaml
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 80
            preference:
              matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                - zone-a
```

This means prefer `zone-a`, but do not block scheduling if `zone-a` is unavailable.

### 8.3 Required vs Preferred in HA Design

Use required rules only for true requirements:

- Hardware dependency.
- Compliance boundary.
- Data locality requirement.
- Licensing restriction.
- Special kernel/device requirement.

Use preferred rules for optimization:

- Prefer same region.
- Prefer low-latency zone.
- Prefer cheaper node pool.
- Prefer warm cache nodes.

Senior design rule:

> Hard constraints protect correctness. Soft constraints protect availability.

Too many hard constraints cause `Pending` pods during failures.

## 9. Pod Anti-Affinity: Avoid Co-Locating Replicas

Pod anti-affinity prevents or discourages pods from being placed together in the same topology domain.

For application HA, pod anti-affinity is commonly used to keep replicas away from each other.

### 9.1 Required Pod Anti-Affinity Across Nodes

```yaml
spec:
  template:
    metadata:
      labels:
        app: web-api
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: web-api
            topologyKey: kubernetes.io/hostname
```

This means do not schedule two `app=web-api` pods on the same node.

### 9.2 Preferred Pod Anti-Affinity Across Nodes

```yaml
spec:
  template:
    metadata:
      labels:
        app: web-api
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: web-api
              topologyKey: kubernetes.io/hostname
```

This means strongly prefer spreading replicas across different nodes, but do not block scheduling if the cluster is temporarily constrained.

### 9.3 Required Anti-Affinity Risk

Required anti-affinity can block scheduling if replicas exceed available topology domains.

Example:

- Deployment replicas: `5`
- Worker nodes matching node selector: `3`
- Required anti-affinity topology: `kubernetes.io/hostname`

Only three pods can schedule. Two pods remain `Pending`.

For critical applications, a common pattern is:

- Use topology spread constraints for even distribution.
- Use preferred anti-affinity for additional separation.
- Use required anti-affinity only when co-location is truly unacceptable.

## 10. Pod Affinity: Place Pods Near Dependencies

Pod affinity places pods close to other pods. It is less common for HA than anti-affinity, but useful for latency-sensitive workloads.

Example:

```yaml
spec:
  template:
    spec:
      affinity:
        podAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 50
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: cache
              topologyKey: topology.kubernetes.io/zone
```

This means prefer scheduling near `app=cache` pods in the same zone.

### HA Consideration

Pod affinity can accidentally concentrate dependent services in one failure domain. For example, placing API pods near cache pods is good for latency, but if both API and cache are concentrated in one zone, a zone failure can take down the complete request path.

Better design:

- Spread each tier across zones.
- Prefer API pods near cache pods inside each zone.
- Avoid all tiers being packed into one node or zone.

## 11. Topology Spread Constraints: Modern Replica Distribution

Topology spread constraints give fine-grained control over how pods are distributed across topology domains such as nodes, racks, zones, or regions.

They are one of the most important HA tools for advanced OpenShift scheduling.

### 11.1 Basic Node-Level Spread

```yaml
spec:
  template:
    metadata:
      labels:
        app: web-api
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: web-api
```

This spreads `web-api` pods evenly across nodes.

Key fields:

| Field | Meaning |
|---|---|
| `maxSkew` | Maximum allowed difference in matching pod count between topology domains |
| `topologyKey` | Node label key that defines the topology domain |
| `whenUnsatisfiable` | What to do if the constraint cannot be satisfied |
| `labelSelector` | Which pods are counted for spread calculation |

### 11.2 Zone-Level Spread

```yaml
spec:
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: payment-api
```

This aims to keep replicas balanced across zones.

### 11.3 Using Multiple Spread Constraints

For strong HA, combine zone and node spread:

```yaml
spec:
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: payment-api
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: payment-api
```

This design says:

- Zone balance is mandatory.
- Node balance is preferred but not mandatory.

This is often better than making every constraint hard. It preserves availability during partial cluster failures.

### 11.4 `DoNotSchedule` vs `ScheduleAnyway`

| Value | Behavior | HA Use |
|---|---|---|
| `DoNotSchedule` | Pod remains pending if spread cannot be satisfied | Use for strong failure-domain correctness |
| `ScheduleAnyway` | Scheduler still schedules but prefers better spread | Use when availability is more important than perfect balance |

### 11.5 Common Topology Spread Mistakes

1. **Wrong label selector**  
   The selector does not match the pod labels, so spread is not calculated as expected.

2. **Missing topology labels**  
   Some nodes do not have the `topologyKey` label.

3. **Too few domains**  
   Three replicas across one zone cannot provide zone HA.

4. **Too strict rules**  
   Multiple `DoNotSchedule` constraints can block pods.

5. **Using deployment-specific labels incorrectly**  
   If the selector includes a changing pod-template-hash, spread behavior can become rollout-specific instead of application-wide.

6. **Conflicting affinity and spread rules**  
   Node affinity says one thing, topology spread requires another.

### 11.6 Validate Spread

```bash
oc get pods -n prod-app -l app=payment-api -o wide
```

Show pod, node, and zone:

```bash
for pod in $(oc get pod -n prod-app -l app=payment-api -o name); do
  node=$(oc get $pod -n prod-app -o jsonpath='{.spec.nodeName}')
  zone=$(oc get node $node -o jsonpath='{.metadata.labels.topology\.kubernetes\.io/zone}')
  echo "$pod  node=$node  zone=$zone"
done
```

## 12. Taints and Tolerations: Protecting Node Pools

Taints are applied to nodes. Tolerations are applied to pods. A taint allows a node to repel pods that do not tolerate the taint.

### 12.1 Taint a Dedicated Node Pool

```bash
oc adm taint nodes worker-infra01 dedicated=infra:NoSchedule
oc adm taint nodes worker-infra02 dedicated=infra:NoSchedule
```

Only pods with a matching toleration can schedule there.

### 12.2 Add Toleration to a Pod Template

```yaml
spec:
  template:
    spec:
      tolerations:
      - key: dedicated
        operator: Equal
        value: infra
        effect: NoSchedule
```

### 12.3 Common Taint Effects

| Effect | Meaning |
|---|---|
| `NoSchedule` | New pods that do not tolerate the taint are not scheduled on the node |
| `PreferNoSchedule` | Scheduler tries to avoid the node but may still use it |
| `NoExecute` | New pods are blocked, and existing non-tolerating pods can be evicted |

### 12.4 HA Use Cases

- Reserve infrastructure nodes for routers, registry, monitoring, or logging.
- Keep noisy workloads away from latency-sensitive apps.
- Separate GPU workloads from standard app workloads.
- Isolate regulated workloads.
- Create emergency capacity pools.

### 12.5 Taint HA Risk

A toleration alone does not force a pod onto a tainted node. It only allows it. To dedicate workloads properly, combine:

- Node labels.
- Node affinity or selector.
- Taints.
- Tolerations.

Example dedicated app nodes:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload: critical-api
      tolerations:
      - key: dedicated
        operator: Equal
        value: critical-api
        effect: NoSchedule
```

## 13. PodDisruptionBudget: Protecting Availability During Voluntary Disruptions

A `PodDisruptionBudget` or PDB defines how many pods must remain available during voluntary disruptions such as node drain, cluster upgrades, or maintenance.

A PDB does not protect against involuntary disruptions such as sudden node power loss.

### 13.1 PDB with `minAvailable`

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-api-pdb
  namespace: prod-app
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: web-api
```

For a three-replica deployment, this allows only one healthy pod to be voluntarily evicted at a time.

### 13.2 PDB with `maxUnavailable`

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-api-pdb
  namespace: prod-app
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: web-api
```

This is often easier to reason about during maintenance.

### 13.3 PDB with Unhealthy Pod Eviction Policy

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-api-pdb
  namespace: prod-app
spec:
  minAvailable: 2
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels:
      app: web-api
```

`AlwaysAllow` helps node drains proceed when pods are already unhealthy, such as `CrashLoopBackOff` or not `Ready`.

### 13.4 PDB Design Rules

For three replicas:

```yaml
minAvailable: 2
```

For four replicas:

```yaml
maxUnavailable: 1
```

For very high replica counts:

```yaml
maxUnavailable: 10%
```

Avoid this unless you fully understand the operational impact:

```yaml
minAvailable: 100%
```

or:

```yaml
maxUnavailable: 0
```

These settings can block node drains and cluster maintenance.

### 13.5 PDB Troubleshooting

Check PDBs:

```bash
oc get pdb -A
oc describe pdb web-api-pdb -n prod-app
```

Common symptoms:

```text
Cannot evict pod as it would violate the pod's disruption budget.
```

Root causes:

- Not enough replicas.
- Pods are not Ready.
- PDB selector matches too many or too few pods.
- Rollout is in progress.
- Node drain is trying to evict too many pods at once.
- Hard anti-affinity prevents replacement pods from scheduling.

Senior troubleshooting sequence:

```bash
oc get deploy web-api -n prod-app
oc get pods -n prod-app -l app=web-api -o wide
oc get pdb web-api-pdb -n prod-app
oc describe pdb web-api-pdb -n prod-app
oc describe pod <pod-name> -n prod-app
oc get events -n prod-app --sort-by='.lastTimestamp'
```

## 14. Health Probes: Keeping Traffic Away from Bad Pods

HA depends on correct health checks. OpenShift and Kubernetes use probes to decide whether a container is ready, alive, or successfully started.

### 14.1 Readiness Probe

Readiness determines whether a pod should receive traffic through Services and Routes.

Example:

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3
```

Use readiness to check:

- Application has loaded configuration.
- Database connection is available, if required for serving.
- Cache or dependency is reachable, if failure means the pod cannot serve.
- Migration or warm-up has completed.

Avoid making readiness too strict. If every pod becomes unready because a shared dependency has a brief problem, the service can lose all endpoints.

### 14.2 Liveness Probe

Liveness determines whether the container should be restarted.

Example:

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3
```

Use liveness to detect deadlocks or unrecoverable application states.

Do not use liveness to check every downstream dependency. Restarting every pod because a database is temporarily unavailable can create a cascading outage.

### 14.3 Startup Probe

Startup probe protects slow-starting applications. Until startup succeeds, liveness and readiness behavior is controlled so the container is not killed too early.

Example:

```yaml
startupProbe:
  httpGet:
    path: /startup
    port: 8080
  periodSeconds: 10
  failureThreshold: 30
```

This gives the application up to 300 seconds to start.

### 14.4 Probe Design Matrix

| Probe | Purpose | Failure Action | HA Mistake |
|---|---|---|---|
| Readiness | Can receive traffic? | Remove endpoint from Service | Too strict; all pods removed from traffic |
| Liveness | Should container be restarted? | Restart container | Checks external dependency and causes restart storm |
| Startup | Has app finished startup? | Protect slow startup from liveness | Missing for slow Java or large apps |

## 15. Rolling Updates Without Downtime

A rolling update gradually replaces old pods with new pods. HA during rollout depends on replica count, readiness probes, `maxUnavailable`, `maxSurge`, PDBs, and cluster capacity.

### 15.1 Deployment RollingUpdate Strategy

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-api
  namespace: prod-app
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
```

This means during update:

- At most one desired pod can be unavailable.
- At most one extra pod can run above desired replicas.

### 15.2 Maximum Availability Rollout

For critical services:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

This maintains full old capacity while adding one new pod first. It requires spare cluster capacity and quota.

### 15.3 Fast Rollout with Some Availability Risk

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 25%
    maxSurge: 25%
```

This is faster but can reduce available capacity during rollout.

### 15.4 Rollout Commands

```bash
oc rollout status deploy/web-api -n prod-app
oc rollout history deploy/web-api -n prod-app
oc rollout undo deploy/web-api -n prod-app
oc rollout pause deploy/web-api -n prod-app
oc rollout resume deploy/web-api -n prod-app
```

### 15.5 Rollout Failure Example

If new pods fail readiness:

```bash
oc rollout status deploy/web-api -n prod-app
oc get pods -n prod-app -l app=web-api
oc describe pod <new-pod> -n prod-app
oc logs <new-pod> -n prod-app
```

Common causes:

- Bad image.
- Wrong environment variable.
- Secret or ConfigMap key missing.
- Readiness endpoint incorrect.
- NetworkPolicy blocks dependency.
- ServiceAccount lacks permission.
- SecurityContext/SCC issue.
- Resource limit too low.

## 16. Graceful Termination and Draining

HA is not only about starting pods. It is also about removing pods safely.

When a pod is terminated:

1. The pod receives a termination signal.
2. Readiness should fail or endpoint removal should happen.
3. The application should stop accepting new connections.
4. Existing requests should complete.
5. The container should exit before `terminationGracePeriodSeconds` expires.

Example:

```yaml
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 60
      containers:
      - name: web-api
        image: quay.io/example/web-api:1.0
        lifecycle:
          preStop:
            exec:
              command:
              - /bin/sh
              - -c
              - sleep 10
```

The `preStop` delay can help give routers and service endpoints time to stop sending new traffic. Do not use arbitrary long sleeps as a replacement for proper application shutdown logic.

### Application Code Should Handle SIGTERM

A production application should:

- Stop accepting new connections.
- Finish in-flight requests.
- Close database connections cleanly.
- Flush metrics and logs.
- Release locks.
- Exit before grace period expires.

## 17. Resource Requests, Limits, and HA

The scheduler places pods based on resource requests, not actual runtime usage. If requests are missing or wrong, HA placement becomes unreliable.

### 17.1 Example Resource Configuration

```yaml
resources:
  requests:
    cpu: 200m
    memory: 256Mi
  limits:
    cpu: 1000m
    memory: 512Mi
```

### 17.2 Why Requests Matter for HA

Requests allow the scheduler to reserve capacity. Without requests:

- Too many pods can land on the same node.
- Nodes can become overcommitted.
- Workloads can be evicted under memory pressure.
- Rolling updates can fail due to hidden capacity issues.
- HPA CPU utilization calculations may be inaccurate or unavailable.

### 17.3 QoS Classes

| QoS Class | Condition | HA Behavior |
|---|---|---|
| Guaranteed | CPU and memory request equals limit for every container | Strongest eviction protection |
| Burstable | At least one request set, but not equal to limits | Common for app workloads |
| BestEffort | No CPU/memory requests or limits | First to be evicted under pressure |

For critical applications, avoid BestEffort.

### 17.4 Capacity Check for HA

Before applying strict spread and PDBs, confirm capacity:

```bash
oc adm top nodes
oc describe node <node-name>
oc get resourcequota -n prod-app
oc get limitrange -n prod-app
```

A deployment with `maxSurge: 1` needs capacity for at least one extra pod during rollout.

## 18. Autoscaling and HA

Autoscaling improves availability under load by increasing replicas. However, autoscaling does not replace baseline HA.

### 18.1 HorizontalPodAutoscaler Example

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-api-hpa
  namespace: prod-app
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-api
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60
```

Important HA rule:

> `minReplicas` should represent minimum HA capacity, not minimum cost.

For a critical service, `minReplicas: 1` is not HA.

### 18.2 HPA Dependencies

HPA needs:

- Metrics availability.
- Correct CPU/memory requests.
- Enough cluster capacity.
- Compatible PDB and rollout settings.
- Application that can scale horizontally.

### 18.3 Cluster Autoscaler Interaction

If HPA increases desired replicas but no node has capacity, pods remain pending until the cluster autoscaler adds nodes. This takes time. For critical workloads, maintain buffer capacity or use priority classes.

## 19. Priority and Preemption

Priority classes influence scheduling during resource shortage. A high-priority pod can preempt lower-priority pods.

Example PriorityClass:

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: critical-app-priority
value: 100000
preemptionPolicy: PreemptLowerPriority
globalDefault: false
description: "Priority for critical production applications"
```

Use in workload:

```yaml
spec:
  template:
    spec:
      priorityClassName: critical-app-priority
```

### HA Caution

Priority and preemption can help critical applications recover during capacity pressure, but they can harm lower-priority services. Use them intentionally:

- Critical API gateway.
- Payment service.
- Authentication service.
- Production SLO workloads.

Do not make every application high priority. If everything is critical, nothing is critical.

## 20. Descheduler and Rebalancing

The scheduler places new pods. It does not continuously rebalance all running pods. Over time, cluster placement can become uneven because:

- Nodes are added.
- Nodes are removed.
- Labels change.
- Workloads scale up and down.
- Failures cause replacement pods to land in temporary locations.

The descheduler can evict pods based on strategies so that replacement pods are scheduled more appropriately. It should be used carefully in production because evictions interact with PDBs, application readiness, and maintenance windows.

Use cases:

- Remove duplicate pods from same node when anti-affinity is desired.
- Rebalance after adding nodes.
- Evict pods violating updated placement rules.
- Improve utilization.

Operational rule:

> The descheduler evicts; the scheduler places replacements. PDBs and readiness decide whether this is safe.

The scheduler makes pods available on nodes. Services and routes decide how traffic reaches them.

### 21.1 Service Selectors

- Pod labels.
- Service selector.

- Pod status.

```bash

```

Check route:

```bash
oc get route web-api -n prod-app
oc describe route web-api -n prod-app
```

### 21.3 HA with Routers

OpenShift ingress/router pods should also be highly available. For external application HA, ensure:

- Multiple router replicas.
- Router pods spread across nodes/zones.
- External load balancer targets multiple router nodes.
- DNS points to HA ingress endpoint.
- Route TLS certificates are valid.

Application pod HA is not enough if all external traffic depends on one router pod or one load balancer path.

### 21.4 Session Affinity and Sticky Sessions

If the application stores session state in pod memory, HA suffers. A pod restart loses user sessions. Prefer:

- External session store.
- Stateless JWT/session design.
- Distributed cache.
- Client retry logic.

Sticky sessions can hide statefulness but reduce load balancing quality and failover behavior.

## 22. NetworkPolicy and HA

NetworkPolicy can break HA if replacement pods cannot reach required dependencies.

Example issue:

- Old pod was running on allowed node or namespace.
- New replacement pod is scheduled elsewhere.
- NetworkPolicy allows old source labels but not new source labels.
- Readiness fails.
- Rollout or node drain gets stuck.

Validation commands:

```bash
oc get networkpolicy -n prod-app
oc describe networkpolicy <policy-name> -n prod-app
oc get pods -n prod-app --show-labels
oc get namespace --show-labels
```

Use debug pods carefully:

```bash
oc run net-test -n prod-app --image=registry.access.redhat.com/ubi9/ubi --command -- sleep 3600
oc rsh -n prod-app net-test
curl -v http://web-api.prod-app.svc.cluster.local
```

In minimal images, tools like `nc`, `telnet`, or `curl` may be missing. Use an image that contains the tools you need or install them if allowed.

## 23. Storage Placement and Stateful HA

Persistent storage can limit scheduling. A pod with a PVC can only run where the volume can attach or mount.

### 23.1 RWO vs RWX

| Access Mode | Meaning | HA Impact |
|---|---|---|
| `ReadWriteOnce` | Mounted read-write by one node at a time | Good for single pod or StatefulSet member; not shared across replicas |
| `ReadWriteMany` | Mounted read-write by many nodes | Useful for shared content, but application must handle concurrency |
| `ReadOnlyMany` | Mounted read-only by many nodes | Useful for static shared content |

### 23.2 RWO Rollout Risk

A `Deployment` with multiple replicas sharing one RWO PVC is usually wrong. Replicas may not start or may be forced onto one node depending on storage behavior.

Bad pattern:

```yaml
replicas: 3
volumes:
- name: data
  persistentVolumeClaim:
    claimName: app-data-rwo
```

Better patterns:

- Use `StatefulSet` with one PVC per replica.
- Use RWX storage if truly shared filesystem semantics are required.
- Externalize data to a database or object storage.
- Use an Operator for complex stateful systems.

### 23.3 Volume Binding and Zone Awareness

Some StorageClasses use delayed binding, often called `WaitForFirstConsumer`. This means the PV is chosen or provisioned after the scheduler knows where the pod will run. This helps align volume topology with pod placement.

For zone HA, ensure:

- Storage supports the target zones.
- PVCs are provisioned in appropriate zones.
- Stateful replicas are spread across zones.
- Application replication/quorum can tolerate zone failure.

### 23.4 StatefulSet HA Example Concepts

For a three-member database cluster:

- Use three replicas.
- Spread replicas across nodes/zones.
- Use one PVC per replica.
- Use a PDB that allows only one voluntary disruption.
- Use readiness checks that reflect member health.
- Ensure quorum rules tolerate one member loss.
- Test restore and failover.

## 27. Troubleshooting Pending Pods in HA Placement

A pod stuck in `Pending` is common when HA constraints are strict.

Start here:

```bash

oc get events -n <namespace> --sort-by='.lastTimestamp'
```

### 27.1 Common Scheduling Error Messages

| Error | Meaning | Fix |
|---|---|---|
| `didn't match Pod's node affinity/selector` | Node labels do not satisfy selector/affinity | Fix labels or placement rules |
| `had untolerated taint` | Pod lacks toleration | Add toleration or remove taint |
| `Insufficient cpu` | Not enough requested CPU capacity | Add nodes, reduce requests, scale down other workloads |
| `Insufficient memory` | Not enough requested memory capacity | Add nodes or adjust requests |
| `didn't match pod anti-affinity rules` | Required anti-affinity too strict | Add nodes/domains or use preferred rule |
| `node(s) didn't match pod topology spread constraints` | Spread cannot be satisfied | Add topology domains, fix labels, relax constraint |
| `volume node affinity conflict` | PV topology conflicts with node placement | Use correct StorageClass/zone or recreate PVC |
| `pod has unbound immediate PersistentVolumeClaims` | PVC not bound | Check PV/StorageClass/provisioner |

## 28. Troubleshooting Bad HA Distribution

Sometimes all pods are running, but placement is poor.

### 28.1 Detect Same-Node Concentration

```bash
oc get pods -n prod-app -l app=web-api -o wide
```

If many replicas are on the same node, check:

```bash
oc get deploy web-api -n prod-app -o yaml | grep -A80 affinity
oc get deploy web-api -n prod-app -o yaml | grep -A80 topologySpreadConstraints
```

### 28.2 Detect Same-Zone Concentration

```bash
for pod in $(oc get pod -n prod-app -l app=web-api -o name); do
  node=$(oc get $pod -n prod-app -o jsonpath='{.spec.nodeName}')
  zone=$(oc get node $node -o jsonpath='{.metadata.labels.topology\.kubernetes\.io/zone}')
  echo "$pod $node $zone"
done
```

### 28.3 Root Causes

- No topology spread constraints.
- Preferred anti-affinity ignored due to capacity constraints.
- Node labels missing or inconsistent.
- All eligible nodes are in one zone.
- Project node selector restricts workload to one pool.
- Taints block other nodes.
- PVC volume topology restricts pod movement.
- Scheduler placed pods during an outage and they were never rebalanced.

## 29. HA Design Patterns

### 29.1 Basic HA Pattern

Use for ordinary stateless apps.

- `replicas: 2` or more.
- Readiness and liveness probes.
- Preferred pod anti-affinity across hostname.
- PDB `maxUnavailable: 1`.
- Rolling update with `maxUnavailable: 1`, `maxSurge: 1`.

### 29.2 Strong Node-Level HA Pattern

Use for production APIs.

- `replicas: 3` or more.
- Topology spread across `kubernetes.io/hostname`.
- Preferred or required anti-affinity.
- PDB `minAvailable: 2`.
- Graceful termination.
- Resource requests and limits.

### 29.3 Strong Zone-Level HA Pattern

Use for critical workloads in multi-zone clusters.

- `replicas: 3` or more.
- Topology spread across `topology.kubernetes.io/zone`.
- Secondary spread across hostname.
- PDB `maxUnavailable: 1`.
- Router/ingress HA across zones.
- Storage support across zones.
- External load balancer spans zones.

### 29.4 Dedicated Node Pool Pattern

Use for critical or regulated workloads.

- Label nodes: `workload=critical`.
- Taint nodes: `dedicated=critical:NoSchedule`.
- Add workload node selector and toleration.
- Use topology spread inside the dedicated pool.
- Size the pool for N+1 capacity.

### 29.5 Stateful Quorum Pattern

Use for clustered stateful apps.

- Odd number of members, commonly 3 or 5.
- One PVC per member.
- Spread members across nodes/zones.
- PDB permits only safe voluntary disruption.
- Application-level replication and quorum.
- Tested backup and restore.
- Operator-managed failover preferred.

## 31. Real-World HA Scenarios and Recommended Designs

### Scenario 1: Three-Replica Web App on Three Workers

Goal: survive one node failure.

Recommended:

```yaml
replicas: 3
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: web
```

PDB:

```yaml
minAvailable: 2
```

Risk:

- If one node is already down, a second node drain can be blocked.
- If required spread is used and only two nodes remain, scaling above two may not schedule.

### Scenario 2: Multi-Zone Payment API

Goal: survive one zone failure as much as infrastructure allows.

Recommended:

- 6 replicas across 3 zones.
- Zone topology spread `maxSkew: 1`.
- Hostname spread `ScheduleAnyway`.
- PDB `maxUnavailable: 1` or carefully chosen percentage.
- HPA min replicas at least 6.
- Router and load balancer HA across zones.

### Scenario 3: Dedicated Nodes for Critical App

Goal: isolate critical workload from noisy workloads.

Nodes:

```bash
oc label node worker01 workload=critical
oc label node worker02 workload=critical
oc label node worker03 workload=critical
oc adm taint node worker01 dedicated=critical:NoSchedule
oc adm taint node worker02 dedicated=critical:NoSchedule
oc adm taint node worker03 dedicated=critical:NoSchedule
```

Workload:

```yaml
nodeSelector:
  workload: critical
tolerations:
- key: dedicated
  operator: Equal
  value: critical
  effect: NoSchedule
```

Risk:

- If only two critical nodes exist, three replicas cannot be strongly spread across three nodes.
- Isolation without enough capacity reduces HA.

### Scenario 4: Stateful Database with RWO Volumes

Goal: maintain database service during one member maintenance.

Recommended:

- Operator-managed database cluster.
- Three members.
- PVC per member.
- Pod anti-affinity across hostname.
- Zone spread if storage supports it.
- PDB allowing one unavailable member.
- Backup and restore tested.

Avoid:

- One Deployment with three replicas sharing one RWO PVC.
- `minAvailable: 100%` PDB.
- Hard zone spread if storage exists only in one zone.

## 33. Important Senior-Level Design Tradeoffs

### 33.1 Availability vs Placement Purity

Strict placement rules give cleaner HA distribution but can cause pods to remain pending during outages.

Example:

```yaml
whenUnsatisfiable: DoNotSchedule
```

This protects topology balance but can reduce immediate availability if domains are unavailable.

```yaml
whenUnsatisfiable: ScheduleAnyway
```

This allows recovery but may temporarily violate ideal spread.

Senior recommendation:

- Use hard rules for must-have topology requirements.
- Use soft rules where temporary imbalance is acceptable.
- Test behavior during node and zone failure.

### 33.2 PDB vs Node Maintenance

A PDB protects applications from too many voluntary evictions. But an overly strict PDB blocks maintenance.

Good:

```yaml
replicas: 3
minAvailable: 2
```

Risky:

```yaml
replicas: 3
minAvailable: 3
```

The risky setting means no pod can be voluntarily evicted while all three must remain available.

### 33.3 Readiness Strictness vs Cascading Failure

A readiness probe should answer: "Can this pod serve traffic?"

If readiness depends on every downstream service, one dependency issue can remove all application pods from service endpoints.

Better approach:

- Readiness checks local ability to serve.
- Dependency failures are handled by retries, circuit breakers, degraded responses, or partial readiness logic.
- Critical dependencies are checked carefully, but avoid making the whole fleet unready for transient dependency spikes.

### 33.4 Surge vs Quota

`maxSurge: 1` improves rollout availability but needs extra capacity and quota.

If namespace quota allows only four pods and deployment has four replicas, a rollout with surge can fail.

Check:

```bash
oc get quota -n prod-app
oc describe quota -n prod-app
```

## 34. Exam and Interview Style Points

For Advanced OpenShift Administration, explain application HA like this:

1. **Replicas provide redundancy.**  
   A single pod is not HA.

2. **Scheduling controls failure-domain distribution.**  
   Use node labels, affinity, anti-affinity, taints/tolerations, and topology spread constraints.

3. **PDB protects during voluntary disruptions.**  
   It helps during node drain and upgrades, but not sudden node failure.

4. **Readiness protects user traffic.**  
   Services and routes should send traffic only to ready pods.

5. **Rolling strategy protects during deployments.**  
   `maxUnavailable` and `maxSurge` control rollout availability.

6. **Resources protect scheduling and runtime stability.**  
   Requests are essential for scheduler decisions.

7. **Storage can break HA.**  
   RWO volumes and zone-bound PVs can limit failover.

8. **HA must be tested.**  
   Delete pods, drain nodes, test rollouts, and verify endpoints.

## 36. Common Production Mistakes

1. **Only setting replicas and calling it HA.**  
   Replicas can still land on one node without placement rules.

2. **Using hard anti-affinity with too few nodes.**  
   Pods remain pending when replicas exceed available domains.

3. **PDB selector mismatch.**  
   PDB does not protect the intended pods or protects too many pods.

4. **Readiness probe checks too much.**  
   All pods become unready during a dependency issue.

5. **Liveness probe checks external dependency.**  
   Temporary dependency outage causes mass restarts.

6. **Missing resource requests.**  
   Scheduler cannot make reliable placement decisions.

7. **RWO volume shared by multiple replicas.**  
   Multi-replica deployment fails or loses real HA.

8. **Project node selector restricts placement accidentally.**  
   Pods cannot schedule outside a small node pool.

9. **Toleration without node selector.**  
   Pod is allowed onto dedicated nodes but not forced there.

10. **Ignoring router/load balancer HA.**  
    App pods are HA, but ingress path is not.

## 38. Summary

Application high availability in OpenShift is the result of correct design across replicas, placement, disruption management, probes, traffic routing, resource guarantees, autoscaling, and operational testing.

For advanced administration, remember these core principles:

- Replicas are necessary but not sufficient.
- Spread replicas across real failure domains.
- Prefer topology spread constraints for modern HA distribution.
- Use pod anti-affinity carefully; required rules can block scheduling.
- Use taints and tolerations for isolation, not as a complete placement strategy by themselves.
- Use PDBs to protect voluntary disruptions, but avoid blocking maintenance.
- Use readiness probes to protect traffic and liveness probes to recover dead containers.
- Tune rolling updates with `maxUnavailable` and `maxSurge`.
- Set realistic resource requests.
- Validate HA by testing pod deletion, node drain, and rollout failure.

A highly available OpenShift application should answer three questions confidently:

1. Where can my pods run?
2. How many failures can I tolerate?
3. What happens during maintenance, rollout, and real failure?

If you can answer and test those three questions, you are managing application HA at a senior OpenShift administrator level.
