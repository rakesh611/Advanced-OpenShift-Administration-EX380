## 1. What “Pending Pod” Really Means

A pod in **Pending** state means Kubernetes/OpenShift has accepted the pod object, but the pod is not yet fully running. This can happen before the pod is assigned to a node, or after it is assigned but before containers are started.

From an operations perspective, **Pending** has two broad meanings:

1. **Scheduling Pending**
   - The pod has no node assigned.
   - `.spec.nodeName` is empty.
   - The scheduler cannot find a feasible node.
   - Typical reason: `FailedScheduling`.

2. **Runtime Pending**
   - The pod is already assigned to a node.
   - `.spec.nodeName` has a value.
   - Kubelet, CRI-O, storage, CNI, image pull, secret/config, or volume mount is blocking container startup.
   - Typical states: `ContainerCreating`, `ImagePullBackOff`, `ErrImagePull`, `CreateContainerConfigError`.

A 10-year-experience administrator must never treat all Pending pods the same. The first decision is always:

```bash
oc get pod <pod-name> -n <namespace> -o jsonpath='{.spec.nodeName}{"\n"}'
```

If output is empty, investigate scheduler placement.  
If output has a node name, investigate kubelet/runtime/storage/network/image configuration on that node.

## 2. Scheduling Pending vs Runtime Pending

### 2.1 Scheduling Pending

Example:

```bash
$ oc get pod -n app
NAME                     READY   STATUS    RESTARTS   AGE
api-7f9c76d8c9-vc8kg     0/1     Pending   0          4m

$ oc get pod api-7f9c76d8c9-vc8kg -n app -o jsonpath='{.spec.nodeName}{"\n"}'

```

The output is blank. The scheduler has not bound the pod to any node.

Common causes:

- Insufficient CPU or memory requests available
- Missing node labels
- Wrong `nodeSelector`
- Wrong project-level node selector
- Hard node affinity not satisfiable
- Hard pod anti-affinity not satisfiable
- Node taint not tolerated
- PVC not bound
- Storage topology mismatch
- Too many pods on node
- HostPort conflict
- Required topology spread cannot be satisfied
- Extended resource not available, such as GPU or hugepages

### 2.2 Runtime Pending

Example:

```bash
$ oc get pod web-1 -n app -o wide
NAME    READY   STATUS              NODE
web-1   0/1     ContainerCreating   worker-2

$ oc get pod web-1 -n app -o jsonpath='{.spec.nodeName}{"\n"}'
worker-2
```

The pod is scheduled. The scheduler is no longer the main problem.

Common causes:

- Image pull secret missing
- Registry authentication issue
- PVC attached but volume mount failing
- CNI plugin issue
- CRI-O issue
- Secret or ConfigMap missing
- SCC/securityContext conflict after admission
- Node disk pressure, image filesystem pressure, or runtime issue

The rest of this guide focuses mainly on **Scheduling Pending**, because it belongs directly to **Pod Scheduling and Workload Placement**.

## 3. OpenShift Scheduling Flow

OpenShift uses the Kubernetes scheduling model with OpenShift-specific configuration and integrations. At a high level:

1. User, controller, Operator, Deployment, StatefulSet, Job, CronJob, or DaemonSet creates a pod.
2. The pod is stored in the API server with no node binding.
3. The scheduler watches unscheduled pods.
4. The scheduler filters nodes that cannot run the pod.
5. The scheduler scores feasible nodes.
6. The scheduler creates a binding between pod and selected node.
7. Kubelet on that node pulls images, mounts volumes, creates sandbox, and starts containers.

### 3.1 Scheduler Filtering

Filtering removes impossible nodes.

Examples:

- Node does not match pod `nodeSelector`.
- Node does not match required node affinity.
- Node has untolerated `NoSchedule` taint.
- Node lacks requested CPU or memory.
- Node lacks required volume topology.
- Node violates required topology spread constraints.
- Node already uses requested `hostPort`.

### 3.2 Scheduler Scoring

After filtering, the scheduler scores remaining nodes.

Examples:

- Prefer nodes with available requested resources.
- Prefer nodes matching preferred affinity.
- Prefer spread across topology domains.
- Prefer image locality in some cases.

Important distinction:

- **Required rules** block scheduling.
- **Preferred rules** influence placement but normally do not cause Pending.

### 3.3 Binding

When the scheduler chooses a node, it writes a binding:

```yaml
spec:
  nodeName: worker-1.example.com
```

After this point, most failures are kubelet/runtime/storage/network related, not scheduler related.

## 4. Golden Investigation Rule

Always answer these four questions first:

1. **Is the pod assigned to a node?**
2. **What exact event explains Pending?**
3. **Which scheduling constraint filtered all nodes?**
4. **Was that constraint intentional or accidental?**

Do not immediately delete pods, scale deployments, reboot nodes, or modify taints without reading the event.

The scheduler almost always tells you the reason in pod events.

## 5. First Five Commands

Use these commands before forming a conclusion.

```bash
# 1. Identify pod status and node assignment
oc get pod <pod-name> -n <namespace> -o wide

# 2. Check whether scheduler assigned a node
oc get pod <pod-name> -n <namespace> -o jsonpath='{.spec.nodeName}{"\n"}'

# 3. Read pod events
oc describe pod <pod-name> -n <namespace>

# 4. List namespace events sorted by time
oc get events -n <namespace> --sort-by='.lastTimestamp'

# 5. Check node readiness and roles
oc get nodes
```

For a controller-created pod, also inspect the owner:

```bash
oc get pod <pod-name> -n <namespace> -o jsonpath='{.metadata.ownerReferences[*].kind}{" "}{.metadata.ownerReferences[*].name}{"\n"}'
```

Then inspect the owning Deployment, ReplicaSet, StatefulSet, Job, CronJob, or DaemonSet.

## 8. Reading `oc describe pod` Like a Senior Admin

Run:

```bash
oc describe pod <pod-name> -n <namespace>
```

Focus on these sections.

### 8.1 Node

```text
Node: <none>
```

Means scheduler has not assigned a node.

```text
Node: worker-2/10.0.0.12
```

Means scheduling succeeded. Pending is now runtime-side.

### 8.2 Status

```text
Status: Pending
```

Status alone is not enough. You must inspect events and node assignment.

### 8.3 Controlled By

```text
Controlled By: ReplicaSet/api-7f9c76d8c9
```

This tells you where to fix the spec. Do not patch the individual pod if it is controller-managed. Patch the Deployment, StatefulSet, DaemonSet, Job, or CronJob template.

### 8.4 Requests and Limits

```text
Requests:
  cpu:     500m
  memory: 1Gi
```

Scheduler uses requests to decide whether a node has enough allocatable capacity.

### 8.5 Node-Selectors

```text
Node-Selectors: disktype=ssd
```

If no node has `disktype=ssd`, the pod stays Pending.

### 8.6 Tolerations

```text
Tolerations: node.kubernetes.io/not-ready:NoExecute op=Exists for 300s
             node.kubernetes.io/unreachable:NoExecute op=Exists for 300s
```

Default tolerations do not tolerate custom taints such as:

```text
dedicated=infra:NoSchedule
```

### 8.7 Events

Events are the most important section.

Example:

```text
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  30s   default-scheduler  0/3 nodes are available: 3 Insufficient memory.
```

This is the scheduler telling you exactly why no node was feasible.

## 9. Common `FailedScheduling` Event Patterns

| Event message pattern | Meaning | Primary investigation |
|---|---|---|
| `Insufficient cpu` | Requests cannot fit on available nodes | Node allocatable vs allocated requests |
| `Insufficient memory` | Memory requests cannot fit | Node allocated resources |
| `node(s) didn't match Pod's node affinity/selector` | Hard selector/affinity mismatch | Pod `nodeSelector`, node labels, namespace selector |
| `node(s) had untolerated taint` | Node taint requires matching toleration | Node taints and pod tolerations |
| `pod has unbound immediate PersistentVolumeClaims` | PVC must bind before scheduling | PVC, PV, StorageClass, provisioner |
| `node(s) didn't match pod topology spread constraints` | Required topology spread cannot be satisfied | topology keys, labels, maxSkew, whenUnsatisfiable |
| `node(s) didn't have free ports` | HostPort conflict | `hostPort` usage on nodes |
| `Too many pods` | Node reached pod capacity | Node `pods` allocatable/maxPods |
| `Preemption is not helpful` | Even removing lower-priority pods cannot satisfy constraints | Hard constraints, storage topology, selectors, taints |
| `No preemption victims found` | Priority/preemption cannot help | PriorityClass and lower-priority pods |
| `waiting for scheduling gates` / `SchedulingGated` | Pod intentionally blocked by scheduling gates | `.spec.schedulingGates` |

## 10. Insufficient CPU / Memory

### 10.1 Symptom

```text
0/5 nodes are available: 5 Insufficient cpu.
```

or

```text
0/5 nodes are available: 2 Insufficient memory, 3 Insufficient cpu.
```

### 10.2 Important Concept

The scheduler uses **requests**, not current usage, for normal CPU and memory placement decisions.

Example:

```yaml
resources:
  requests:
    cpu: 2
    memory: 4Gi
  limits:
    cpu: 4
    memory: 8Gi
```

A node must have at least 2 CPU and 4Gi memory allocatable capacity not already requested by other scheduled pods.

### 10.3 Check Pod Requests

```bash
oc get pod <pod> -n <ns> -o jsonpath='{range .spec.containers[*]}{.name}{" requests="}{.resources.requests}{" limits="}{.resources.limits}{"\n"}{end}'
```

For init containers:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{range .spec.initContainers[*]}{.name}{" requests="}{.resources.requests}{" limits="}{.resources.limits}{"\n"}{end}'
```

Do not ignore init containers. Scheduler calculates effective pod request by considering app containers and init containers. A large init container can block scheduling even if the main container is small.

### 10.4 Check Node Allocatable and Allocated Requests

```bash
oc describe node <node-name>
```

Look for:

```text
Capacity:
  cpu:                8
  memory:             32780000Ki
Allocatable:
  cpu:                7500m
  memory:             29000000Ki
Allocated resources:
  Resource           Requests      Limits
  cpu                7100m (94%)   12000m (160%)
  memory             27000Mi (93%) 40000Mi (137%)
```

If CPU requests are already 94%, a pod requesting `1000m` might not fit even if `oc adm top node` shows low real-time CPU usage.

### 10.5 Check Current Usage Separately

```bash
oc adm top nodes
oc adm top pods -A --sort-by=cpu
oc adm top pods -A --sort-by=memory
```

Use `top` for runtime pressure and capacity planning, but use `oc describe node` allocated requests for scheduling decisions.

### 10.6 Fix Options

#### Option A: Reduce Requests

Patch Deployment:

```bash
oc set resources deployment/<deploy> -n <ns> \
  --requests=cpu=250m,memory=512Mi \
  --limits=cpu=1,memory=1Gi
```

#### Option B: Add Nodes

For MachineSet-based clusters:

```bash
oc get machinesets -n openshift-machine-api
oc scale machineset <machineset-name> -n openshift-machine-api --replicas=<count>
```

#### Option C: Move Workload to Correct Node Pool

Add or correct labels:

```bash
oc label node <node-name> workload=app
```

Patch workload selector:

```bash
oc patch deployment <deploy> -n <ns> --type='merge' -p \
'{"spec":{"template":{"spec":{"nodeSelector":{"workload":"app"}}}}}'
```

#### Option D: Review Overcommit Strategy

Requests too high can reduce schedulable density. Limits too high can create runtime contention. In production, use a workload-class policy:

- Critical services: realistic requests, controlled limits, PDB, priority class
- Batch workloads: lower priority, flexible requests
- Dev/test: overcommit allowed
- Infra/monitoring: dedicated placement and guaranteed capacity

## 11. LimitRange and Default Requests

### 11.1 Why LimitRange Matters

A pod manifest may not explicitly define requests, but a namespace `LimitRange` can inject default requests and limits.

Example:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 500m
      memory: 512Mi
    default:
      cpu: 1
      memory: 1Gi
```

A developer may think the pod has no requests, but after admission the pod requests `500m` CPU and `512Mi` memory per container.

### 11.2 Check LimitRange

```bash
oc get limitrange -n <ns>
oc describe limitrange -n <ns>
```

### 11.3 Check Actual Pod After Admission

```bash
oc get pod <pod> -n <ns> -o yaml | sed -n '/resources:/,/volumeMounts:/p'
```

or:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{range .spec.containers[*]}{.name}{" => "}{.resources}{"\n"}{end}'
```

### 11.4 Failure Pattern

```text
0/3 nodes are available: 3 Insufficient memory.
```

Root cause might not be the application YAML. It may be a default request injected by LimitRange.

### 11.5 Fix Options

- Lower namespace default requests.
- Set explicit requests on the workload.
- Increase node pool capacity.
- Split workloads across node pools.

Example:

```bash
oc set resources deployment/<deploy> -n <ns> \
  --requests=cpu=100m,memory=128Mi \
  --limits=cpu=500m,memory=512Mi
```

## 12. ResourceQuota and Namespace Capacity

### 12.1 Important Distinction

ResourceQuota usually blocks object creation at admission time. In that case, you may not see a Pending pod. Instead, the Deployment or ReplicaSet may show failure events.

Example:

```text
Error creating: pods "api-..." is forbidden: exceeded quota: compute-quota
```

### 12.2 Check Quota

```bash
oc get resourcequota -n <ns>
oc describe resourcequota -n <ns>
```

Example output:

```text
Resource              Used     Hard
requests.cpu          3900m    4
requests.memory       7Gi      8Gi
pods                  10       10
```

### 12.3 Check Controller Events

```bash
oc describe deployment <deploy> -n <ns>
oc describe replicaset <rs> -n <ns>
```

### 12.4 Common Quota Root Causes

- Pod count quota reached
- CPU request quota reached
- Memory request quota reached
- PVC count quota reached
- Storage request quota reached
- Object quota reached for services, secrets, configmaps, replicationcontrollers, or persistentvolumeclaims

### 12.5 Fix Options

- Delete unused workloads.
- Reduce requests.
- Increase quota.
- Move workloads to another namespace.
- Create separate quotas per team/environment.

Example quota patch:

```bash
oc patch resourcequota compute-quota -n <ns> --type='json' -p='[
  {"op":"replace","path":"/spec/hard/requests.cpu","value":"8"},
  {"op":"replace","path":"/spec/hard/requests.memory","value":"16Gi"}
]'
```

## 13. Node Selector Problems

### 13.1 Symptom

```text
0/4 nodes are available: 4 node(s) didn't match Pod's node affinity/selector.
```

### 13.2 Check Pod Node Selector

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.nodeSelector}{"\n"}'
```

Example:

```yaml
nodeSelector:
  workload: payments
  disk: ssd
```

### 13.3 Check Node Labels

```bash
oc get nodes --show-labels
```

More readable:

```bash
oc get nodes -L workload,disk,env,node-role.kubernetes.io/worker
```

### 13.4 Root Cause Examples

#### Typo in Label Key

Pod:

```yaml
nodeSelector:
  worload: payments
```

Node:

```yaml
workload: payments
```

The key is misspelled.

#### Wrong Label Value

Pod:

```yaml
nodeSelector:
  disk: ssd
```

Nodes:

```text
worker-1 disk=nvme
worker-2 disk=nvme
```

No matching node.

#### Label Removed During Maintenance

A node replacement or MachineSet rollout creates new nodes without custom labels. Existing pods remain running, but new pods become Pending.

### 13.5 Fix Options

Label the node:

```bash
oc label node <node-name> workload=payments disk=ssd
```

Remove incorrect selector from Deployment:

```bash
oc patch deployment <deploy> -n <ns> --type='json' -p='[
  {"op":"remove","path":"/spec/template/spec/nodeSelector"}
]'
```

Patch selector:

```bash
oc patch deployment <deploy> -n <ns> --type='merge' -p \
'{"spec":{"template":{"spec":{"nodeSelector":{"workload":"payments"}}}}}'
```

### 13.6 Production Best Practice

Do not manually label replacement nodes one by one in large clusters. Prefer:

- MachineSet labels
- MachineConfigPool role-based grouping
- GitOps-managed node labels
- Clear label taxonomy, for example:
  - `node-role.kubernetes.io/worker=`
  - `node-role.kubernetes.io/infra=`
  - `workload-tier=frontend`
  - `workload-tier=backend`
  - `storage=local-nvme`
  - `zone=az-a`

## 14. Project-Level Node Selectors

### 14.1 What It Is

OpenShift can apply a default node selector at project/namespace level. This is commonly used for workload isolation.

Example namespace annotation:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: env=prod
```

Pods in that namespace inherit or are constrained by the namespace node selector.

### 14.2 Symptom

A pod YAML has no `nodeSelector`, but scheduler reports:

```text
0/6 nodes are available: 6 node(s) didn't match Pod's node affinity/selector.
```

### 14.3 Check Namespace Annotation

```bash
oc get namespace <ns> -o yaml | grep -A3 'openshift.io/node-selector'
```

or:

```bash
oc get namespace <ns> -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
```

### 14.4 Check Cluster Default Node Selector

```bash
oc get scheduler cluster -o yaml
```

Look for:

```yaml
spec:
  defaultNodeSelector: type=user-node,region=east
```

### 14.5 Example Problem

Namespace:

```yaml
openshift.io/node-selector: env=prod
```

Pod:

```yaml
nodeSelector:
  workload=batch
```

Effective requirement:

```text
env=prod AND workload=batch
```

If no node has both labels, the pod stays Pending.

### 14.6 Fix Options

Correct node labels:

```bash
oc label node <node> env=prod workload=batch
```

Change namespace selector:

```bash
oc annotate namespace <ns> openshift.io/node-selector='env=dev' --overwrite
```

Remove namespace selector:

```bash
oc annotate namespace <ns> openshift.io/node-selector- 
```

Patch workload selector:

```bash
oc patch deployment <deploy> -n <ns> --type='merge' -p \
'{"spec":{"template":{"spec":{"nodeSelector":{"env":"prod"}}}}}'
```

### 14.7 Senior Admin Advice

Project-level selectors are powerful but dangerous. They are invisible to many application owners because they do not appear in the original Deployment YAML. Always inspect namespace annotations during Pending pod investigation.

## 15. Node Affinity Problems

### 15.1 Required vs Preferred

Node affinity has two major styles:

- `requiredDuringSchedulingIgnoredDuringExecution`
- `preferredDuringSchedulingIgnoredDuringExecution`

Required affinity must match. Preferred affinity is a soft preference.

### 15.2 Symptom

```text
0/5 nodes are available: 5 node(s) didn't match Pod's node affinity/selector.
```

### 15.3 Check Affinity

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.affinity.nodeAffinity}{"\n"}'
```

For readable output:

```bash
oc get pod <pod> -n <ns> -o yaml | sed -n '/affinity:/,/tolerations:/p'
```

### 15.4 Example Required Node Affinity

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: topology.kubernetes.io/zone
          operator: In
          values:
          - zone-a
        - key: workload
          operator: In
          values:
          - database
```

This means the node must have both:

```text
topology.kubernetes.io/zone=zone-a
workload=database
```

### 15.5 Important OR / AND Logic

Within one `nodeSelectorTerm`:

```text
matchExpressions are ANDed
```

Across multiple `nodeSelectorTerms`:

```text
terms are ORed
```

Example:

```yaml
requiredDuringSchedulingIgnoredDuringExecution:
  nodeSelectorTerms:
  - matchExpressions:
    - key: zone
      operator: In
      values: [zone-a]
    - key: disk
      operator: In
      values: [ssd]
  - matchExpressions:
    - key: zone
      operator: In
      values: [zone-b]
    - key: disk
      operator: In
      values: [nvme]
```

Effective logic:

```text
(zone=zone-a AND disk=ssd) OR (zone=zone-b AND disk=nvme)
```

### 15.6 Fix Options

- Correct node labels.
- Correct affinity keys/values.
- Change required affinity to preferred if strict placement is not necessary.
- Add more nodes in matching topology.
- Remove accidental affinity from Helm chart values or Operator CR.

Example patch to remove node affinity from Deployment:

```bash
oc patch deployment <deploy> -n <ns> --type='json' -p='[
  {"op":"remove","path":"/spec/template/spec/affinity/nodeAffinity"}
]'
```

## 16. Pod Affinity and Anti-Affinity Problems

### 16.1 What It Does

Pod affinity and anti-affinity place a pod relative to other pods.

Examples:

- Schedule frontend pods near cache pods.
- Spread replicas across nodes.
- Prevent two replicas from running on the same node.
- Keep noisy workloads away from latency-sensitive workloads.

### 16.2 Symptom

```text
0/4 nodes are available: 4 node(s) didn't match pod affinity rules.
```

or:

```text
0/4 nodes are available: 4 node(s) didn't satisfy existing pods anti-affinity rules.
```

### 16.3 Required Anti-Affinity Example

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: web
      topologyKey: kubernetes.io/hostname
```

This prevents two pods with `app=web` from running on the same node.

If you request 5 replicas but only have 3 schedulable nodes, 2 pods will remain Pending.

### 16.4 Check Pod Labels

```bash
oc get pods -n <ns> --show-labels
```

### 16.5 Check Node Topology Labels

```bash
oc get nodes -L kubernetes.io/hostname,topology.kubernetes.io/zone,topology.kubernetes.io/region
```

### 16.6 Common Root Causes

- Required anti-affinity with too few nodes
- Wrong `topologyKey`
- Missing topology labels on nodes
- Label selector too broad
- Chart uses `app=<name>` and matches unexpected pods
- Namespace selector matches more pods than intended
- Rolling update creates new pods while old pods still occupy all topology domains

### 16.7 RollingUpdate Deadlock Example

Deployment has:

```yaml
replicas: 3
strategy:
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

Pod anti-affinity requires one pod per node, and the cluster has exactly 3 nodes.

During rollout, Kubernetes tries to create one extra pod before deleting an old one. The extra pod cannot schedule because all 3 nodes already have matching pods.

Fix options:

```yaml
strategy:
  rollingUpdate:
    maxSurge: 0
    maxUnavailable: 1
```

or add one more node.

### 16.8 Senior Admin Advice

Use required pod anti-affinity only when strict HA placement is mandatory. For general spreading, prefer topology spread constraints or preferred anti-affinity to avoid unnecessary Pending pods.

## 17. Taints and Tolerations Problems

### 17.1 What Taints Do

A taint on a node repels pods unless they have a matching toleration.

Example taint:

```bash
oc adm taint nodes worker-1 dedicated=infra:NoSchedule
```

Only pods with a matching toleration can schedule there.

### 17.2 Symptom

```text
0/3 nodes are available: 3 node(s) had untolerated taint {dedicated: infra}.
```

### 17.3 Check Node Taints

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
```

Detailed:

```bash
oc describe node <node> | grep -i taints -A3
```

### 17.4 Check Pod Tolerations

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.tolerations}{"\n"}'
```

### 17.5 Taint Effects

| Effect | Meaning |
|---|---|
| `NoSchedule` | Do not schedule pods unless tolerated |
| `PreferNoSchedule` | Avoid scheduling if possible |
| `NoExecute` | Evict existing pods that do not tolerate it and block new pods |

### 17.6 Example Toleration

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: infra
  effect: NoSchedule
```

### 17.7 Exists Operator

```yaml
tolerations:
- key: dedicated
  operator: Exists
  effect: NoSchedule
```

This tolerates any value for key `dedicated` with effect `NoSchedule`.

### 17.8 Common Root Causes

- Workload intended for infra nodes lacks infra toleration
- Node was tainted during maintenance and taint not removed
- Control plane nodes are tainted and workload has no toleration
- Dedicated GPU/storage nodes are tainted but workload only has node selector
- Operator-managed workload tolerations missing from custom resource

### 17.9 Fix Options

Add toleration to Deployment:

```bash
oc patch deployment <deploy> -n <ns> --type='json' -p='[
  {
    "op":"add",
    "path":"/spec/template/spec/tolerations",
    "value":[
      {"key":"dedicated","operator":"Equal","value":"infra","effect":"NoSchedule"}
    ]
  }
]'
```

Remove taint:

```bash
oc adm taint nodes <node> dedicated=infra:NoSchedule-
```

For infra workloads, combine:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

### 17.10 Senior Admin Advice

A toleration does not force a pod onto a tainted node. It only allows it. Use node selector or affinity along with toleration when you want dedicated placement.

## 18. Topology Spread Constraint Problems

### 18.1 What It Does

Topology spread constraints control how pods are distributed across topology domains, such as:

- Hostname
- Zone
- Region
- Rack
- Custom topology labels

### 18.2 Example

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: api
```

This tells the scheduler to keep `app=api` pods evenly spread across zones. If it cannot maintain the rule, it will not schedule the pod.

### 18.3 Symptom

```text
0/6 nodes are available: 6 node(s) didn't match pod topology spread constraints.
```

### 18.4 Key Fields

| Field | Meaning |
|---|---|
| `maxSkew` | Maximum allowed imbalance between topology domains |
| `topologyKey` | Node label that defines the domain |
| `whenUnsatisfiable` | `DoNotSchedule` or `ScheduleAnyway` |
| `labelSelector` | Which pods are counted for spreading |
| `minDomains` | Minimum number of eligible domains, if used |

### 18.5 Check Constraints

```bash
oc get pod <pod> -n <ns> -o yaml | sed -n '/topologySpreadConstraints:/,/containers:/p'
```

### 18.6 Check Node Labels

```bash
oc get nodes -L topology.kubernetes.io/zone,kubernetes.io/hostname
```

### 18.7 Common Root Causes

- Nodes missing `topology.kubernetes.io/zone`
- Only one zone available but constraint expects multiple zones
- `maxSkew` too strict
- `whenUnsatisfiable: DoNotSchedule` blocks scheduling
- Label selector matches too many pods
- Namespace selector counts pods from unexpected namespaces
- Node selector narrows eligible nodes to only one topology domain

### 18.8 Fix Options

- Add missing topology labels.
- Use `ScheduleAnyway` for soft spreading.
- Increase nodes across topology domains.
- Adjust `maxSkew`.
- Correct label selector.
- Remove conflicting node selector/affinity.

Example soft spread:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: ScheduleAnyway
  labelSelector:
    matchLabels:
      app: api
```

### 18.9 Senior Admin Advice

Topology spread constraints are safer than hard pod anti-affinity for many HA use cases, but `DoNotSchedule` can still cause Pending if topology capacity is not planned.

## 19. PersistentVolumeClaim Pending Problems

### 19.1 Symptom

```text
0/4 nodes are available: pod has unbound immediate PersistentVolumeClaims.
```

or pod is Pending and PVC is Pending:

```bash
oc get pod,pvc -n <ns>
```

Example:

```text
pod/db-0          0/1   Pending
pvc/db-data-db-0        Pending
```

### 19.2 Check PVC

```bash
oc describe pvc <pvc> -n <ns>
```

Look for:

- StorageClass
- Access mode
- Requested capacity
- Events
- Provisioner errors
- Binding mode

### 19.3 Common PVC Causes

| Cause | Example |
|---|---|
| No default StorageClass | PVC does not specify `storageClassName` |
| Wrong StorageClass | `storageClassName: fast` but class does not exist |
| Provisioner down | CSI driver/operator issue |
| Static PV mismatch | PV capacity/accessMode/storageClass/selector mismatch |
| Zone mismatch | PV exists in zone-a but pod constrained to zone-b |
| Access mode mismatch | PVC asks `ReadWriteMany` but storage supports only `ReadWriteOnce` |
| VolumeMode mismatch | PVC asks Block but PV is Filesystem |
| Quota exhausted | Storage quota reached |

### 19.4 Check StorageClass

```bash
oc get storageclass
oc describe storageclass <sc-name>
```

Important fields:

```yaml
provisioner:
volumeBindingMode:
allowedTopologies:
parameters:
reclaimPolicy:
```

### 19.5 Check Static PV Matching

```bash
oc get pv
oc describe pv <pv-name>
```

A PVC matches PV based on:

- Capacity
- Access modes
- Volume mode
- StorageClass
- Selector labels
- Availability

### 19.6 Fix Examples

Create PVC with correct StorageClass:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: gp3-csi
  resources:
    requests:
      storage: 10Gi
```

Patch PVC StorageClass only if PVC is still unbound and field mutation is allowed in your scenario. In many real cases, recreate the PVC carefully after validating data safety.

## 20. Storage Topology and WaitForFirstConsumer

### 20.1 What It Is

Some StorageClasses use:

```yaml
volumeBindingMode: WaitForFirstConsumer
```

This delays volume provisioning or binding until a pod exists, because the storage system needs to know the selected node or zone before provisioning the volume.

### 20.2 Why It Can Look Confusing

You may see:

```text
PVC Pending
Pod Pending
```

This can be normal for a short time. But if it remains stuck, there may be a topology conflict.

### 20.3 Topology Deadlock Example

Pod requires zone-b:

```yaml
nodeSelector:
  topology.kubernetes.io/zone: zone-b
```

StorageClass allows only zone-a:

```yaml
allowedTopologies:
- matchLabelExpressions:
  - key: topology.kubernetes.io/zone
    values:
    - zone-a
```

No node satisfies both workload and storage requirements.

### 20.4 Investigation Commands

```bash
oc get pvc -n <ns>
oc describe pvc <pvc> -n <ns>
oc get sc <sc> -o yaml
oc get nodes -L topology.kubernetes.io/zone
oc describe pod <pod> -n <ns>
```

### 20.5 Fix Options

- Change pod node selector/affinity to match storage topology.
- Use a StorageClass available in the required zone.
- Add nodes in the storage-supported zone.
- Adjust `allowedTopologies` if appropriate.
- Recreate PVC with correct StorageClass after backup/data review.

### 20.6 Senior Admin Advice

For stateful workloads, scheduling is not just CPU/memory. Storage topology can be the hidden hard constraint.

## 21. DaemonSet Pod Pending Investigation

### 21.1 How DaemonSet Placement Differs

DaemonSets are intended to run one pod per eligible node. Examples:

- Log collectors
- Monitoring agents
- CNI components
- Storage node plugins
- Security agents

DaemonSet pods can be Pending when a node is not eligible or resources cannot fit.

### 21.2 Commands

```bash
oc get daemonset -n <ns>
oc describe daemonset <ds> -n <ns>
oc get pods -n <ns> -o wide
```

### 21.3 Check DaemonSet Template

```bash
oc get daemonset <ds> -n <ns> -o yaml | sed -n '/template:/,$p'
```

Focus on:

- Node selector
- Node affinity
- Tolerations
- Resource requests
- Host ports
- Privileged/SCC requirements
- Volumes

### 21.4 Common Causes

- DaemonSet lacks toleration for tainted nodes
- Control plane nodes are tainted
- Infra nodes have custom taints
- HostPort conflict
- CPU/memory request too high
- Node selector does not match node labels
- Operator-managed DaemonSet config is wrong

### 21.5 Fix Example

Add toleration:

```bash
oc patch daemonset <ds> -n <ns> --type='json' -p='[
  {
    "op":"add",
    "path":"/spec/template/spec/tolerations/-",
    "value":{"key":"node-role.kubernetes.io/infra","operator":"Exists","effect":"NoSchedule"}
  }
]'
```

If `tolerations` does not exist, add the list first.

## 22. Job / CronJob Pod Pending Investigation

### 22.1 Why Jobs Become Pending

Batch workloads often request too many resources or target dedicated nodes.

### 22.2 Commands

```bash
oc get job -n <ns>
oc describe job <job> -n <ns>
oc get pods -n <ns> --selector=job-name=<job>
oc describe pod <pod> -n <ns>
```

For CronJob:

```bash
oc get cronjob -n <ns>
oc describe cronjob <cronjob> -n <ns>
oc get jobs -n <ns>
```

### 22.3 Common Causes

- Job requests full node capacity
- Too many parallel completions
- Quota exceeded
- Batch namespace has strict project node selector
- Job uses PVC with RWO and previous pod still holds it
- CronJob concurrency policy creates backlog

### 22.4 Fix Options

- Reduce requests.
- Lower `parallelism`.
- Use `concurrencyPolicy: Forbid` for CronJobs that should not overlap.
- Use a batch node pool.
- Add `PriorityClass` carefully for important jobs.

Example:

```bash
oc patch job <job> -n <ns> --type='merge' -p \
'{"spec":{"parallelism":1}}'
```

For CronJob template:

```bash
oc patch cronjob <cronjob> -n <ns> --type='merge' -p \
'{"spec":{"concurrencyPolicy":"Forbid"}}'
```

Example:

  rollingUpdate:

- Temporarily reduce `maxSurge`.
- Temporarily allow more `maxUnavailable`.
- Add capacity.
- Reduce requests.
- Roll back bad placement change.

## 26. Scheduler Queue, Priority, and Preemption

### 26.1 PriorityClass

Pods can have priority:

```yaml
priorityClassName: high-priority
```

Check:

```bash
oc get priorityclass
oc describe priorityclass <class-name>
oc get pod <pod> -n <ns> -o jsonpath='{.spec.priorityClassName}{" "}{.spec.priority}{"\n"}'
```

### 26.2 What Preemption Does

If a high-priority pod cannot schedule, scheduler may evict lower-priority pods if removing them would make a node feasible.

### 26.3 Preemption Is Not Magic

Preemption cannot fix:

- Wrong node selector
- Missing node label
- Untolerated taint
- PVC topology mismatch
- HostPort conflict if same port still impossible
- Required anti-affinity impossible with node count
- Extended resource unavailable

### 26.4 Event Examples

```text
preemption: 0/4 nodes are available: 4 Preemption is not helpful for scheduling.
```

Means even evicting lower-priority pods would not satisfy the hard constraints.

```text
No preemption victims found for incoming pod
```

Means there are no suitable lower-priority pods to evict or evicting them does not help.

### 26.5 Senior Admin Advice

Use PriorityClass for truly critical workloads. Do not use priority to hide poor capacity planning. Preemption can cause service disruption.

## 29. Dedicated Node Placement

### 29.1 Common Pattern

Dedicated nodes use both:

- Label: attracts intended workloads
- Taint: repels unintended workloads

Example:

```bash
oc label node worker-5 dedicated=payments
oc adm taint node worker-5 dedicated=payments:NoSchedule
```

Workload:

```yaml
nodeSelector:
  dedicated: payments
tolerations:
- key: dedicated
  operator: Equal
  value: payments
  effect: NoSchedule
```

### 29.2 Pending Root Cause Matrix

| Node config | Pod config | Result |
|---|---|---|
| Label only | Selector matches | Schedules |
| Taint only | No toleration | Pending if only those nodes are feasible |
| Label + taint | Selector only | Pending |
| Label + taint | Toleration only | May schedule, but not guaranteed to dedicated node |
| Label + taint | Selector + toleration | Correct dedicated placement |

### 29.3 Senior Admin Advice

A dedicated node pattern is incomplete unless both sides exist:

```text
Node: label + taint
Pod: selector/affinity + toleration
```

## 33. SCC / Pod Security vs Pending

### 33.1 Important Distinction

Security Context Constraints (SCC) usually affect admission or container start, not scheduler feasibility.

If SCC denies the pod, the pod may not be created. You may see Deployment/ReplicaSet events such as:

```text
Error creating: pods "app-..." is forbidden: unable to validate against any security context constraint
```

If pod is created and assigned to a node but container cannot start, it is runtime/configuration investigation.

### 33.2 Commands

```bash
oc describe deployment <deploy> -n <ns>
oc describe rs <rs> -n <ns>
oc describe pod <pod> -n <ns>
oc get serviceaccount -n <ns>
oc adm policy who-can use scc anyuid
```

### 33.3 Fix Example

For an application service account that legitimately needs `anyuid`:

```bash
oc adm policy add-scc-to-user anyuid -z <serviceaccount> -n <namespace>
```

Then restart workload:

```bash
oc rollout restart deployment/<deploy> -n <namespace>
```

### 33.4 Senior Admin Advice

Do not misclassify SCC failures as scheduler failures. Check whether a pod exists and whether `.spec.nodeName` is empty.

## 34. Network Policy vs Pending

NetworkPolicy does not normally cause a pod to remain Pending.

NetworkPolicy can cause:

- Application timeout
- Failed database connection
- Failed readiness/liveness probe
- Service reachability issue

But it does not normally block scheduling.

Commands:

```bash
oc get networkpolicy -n <ns>
oc describe networkpolicy <policy> -n <ns>
oc get pod -n <ns> --show-labels
oc get svc,endpoints -n <ns>
```

Senior admin rule:

```text
Pending before node assignment = scheduler/placement/capacity/storage.
Connectivity after pod is running = service/network/policy/DNS/application.
```

## 35. Cluster Autoscaler and MachineAutoscaler

### 35.1 When Autoscaler Matters

In cloud or Machine API-enabled clusters, the Cluster Autoscaler can add nodes when pods are unschedulable due to capacity.

### 35.2 What Autoscaler Cannot Fix

Autoscaler may not help if Pending is caused by:

- Wrong node selector matching no MachineSet
- Untolerated taint not configured in node group template
- PVC topology mismatch
- HostPort conflict across all future nodes
- Required anti-affinity impossible by design
- Quota issue
- Unsupported instance type for requested resource

### 35.3 Commands

```bash
oc get clusterautoscaler
oc describe clusterautoscaler
oc get machineautoscaler -A
oc describe machineautoscaler <name> -n <namespace>
oc get machinesets -n openshift-machine-api
```

Check autoscaler logs:

```bash
oc logs -n openshift-machine-api deployment/cluster-autoscaler-operator
```

Actual autoscaler pod location can vary. Search:

```bash
oc get pods -A | grep -i autoscaler
```

### 35.4 Common Autoscaler Event Meaning

```text
pod didn't trigger scale-up
```

Possible interpretations:

- No autoscaled node group can satisfy constraints.
- Node group max size reached.
- Pod requests exceed instance type capacity.
- Pod has local storage restrictions.
- Pod has selectors that do not match autoscaled nodes.

### 35.5 Senior Admin Advice

When autoscaler does not scale, compare the Pending pod requirements against the labels, taints, capacity, and topology of the MachineSet that would create new nodes.

## 41. Remediation Patterns

### 41.1 Fix Resource Requests

```bash
oc set resources deployment/<deploy> -n <ns> \
  --requests=cpu=250m,memory=512Mi \
  --limits=cpu=1,memory=1Gi
```

### 41.2 Add Node Label

```bash
oc label node <node> workload=backend
```

### 41.3 Remove Node Label

```bash
oc label node <node> workload-
```

### 41.4 Add Taint

```bash
oc adm taint node <node> dedicated=backend:NoSchedule
```

### 41.5 Remove Taint

```bash
oc adm taint node <node> dedicated=backend:NoSchedule-
```

### 41.6 Add Toleration to Deployment

```bash
oc patch deployment <deploy> -n <ns> --type='json' -p='[
  {
    "op":"add",
    "path":"/spec/template/spec/tolerations",
    "value":[{"key":"dedicated","operator":"Equal","value":"backend","effect":"NoSchedule"}]
  }
]'
```

### 41.7 Add Node Selector to Deployment

```bash
oc patch deployment <deploy> -n <ns> --type='merge' -p \
'{"spec":{"template":{"spec":{"nodeSelector":{"workload":"backend"}}}}}'
```

### 41.8 Remove Node Selector From Deployment

```bash
oc patch deployment <deploy> -n <ns> --type='json' -p='[
  {"op":"remove","path":"/spec/template/spec/nodeSelector"}
]'
```

### 41.9 Scale MachineSet

```bash
oc get machinesets -n openshift-machine-api
oc scale machineset <machineset> -n openshift-machine-api --replicas=<replicas>
```

### 41.10 Cordon / Uncordon

```bash
oc adm cordon <node>
oc adm uncordon <node>
```

### 41.11 Drain Node Carefully

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
```

Use with caution. Check PDBs first:

```bash
oc get pdb -A
```

### 41.12 Roll Back Deployment

```bash
oc rollout history deployment/<deploy> -n <ns>
oc rollout undo deployment/<deploy> -n <ns>
```

## 42. Preventive Controls

### 42.1 Standardize Node Labels

Define a cluster-wide label taxonomy.

Example:

```text
workload-type=app|infra|batch|storage|gpu
environment=prod|nonprod
storage-tier=standard|fast|local
failure-domain=zone-a|zone-b|zone-c
```

### 42.2 Manage Placement Through GitOps

Avoid manual drift.

Manage these through GitOps:

- Node labels where possible
- MachineSet labels
- Namespace node selectors
- Workload node selectors
- Taints/tolerations
- PriorityClasses
- ResourceQuota
- LimitRange

### 42.3 Use Admission Policies Carefully

Project defaults and LimitRanges are good, but they can surprise teams.

Document:

- Default requests
- Default limits
- Namespace node selectors
- Quotas
- Allowed storage classes
- Dedicated node policies

### 42.4 Capacity Alerts

Monitor:

- Pending pods by namespace
- FailedScheduling events
- Node allocatable vs requested CPU/memory
- Node pod count vs maxPods
- PVC Pending count
- MachineAutoscaler max reached
- Node NotReady count
- DiskPressure/MemoryPressure/PIDPressure taints

### 42.5 Release Validation

Before production rollout, validate:

```bash
oc diff -f manifests/
oc apply --dry-run=server -f manifests/
```

Check generated Helm templates:

```bash
helm template <release> <chart> -f values.yaml > rendered.yaml
```

Search for placement changes:

```bash
grep -n "nodeSelector\|affinity\|tolerations\|topologySpreadConstraints\|resources:" rendered.yaml
```

### 42.6 Capacity Simulation Mindset

Before deploying 20 replicas with 1 CPU request each, ask:

```text
Can the selected node pool provide 20 allocatable CPUs after existing requests and system reservations?
```

Do not look only at current CPU usage. Scheduling is based on requested capacity.

## Final Senior-Level Summary

When a pod is Pending in OpenShift, do not guess. First check `.spec.nodeName`.

- If `.spec.nodeName` is empty, the scheduler has not placed the pod.
- If `.spec.nodeName` is set, the pod is already placed and the issue is runtime, volume, image, CNI, CRI-O, kubelet, or configuration.

For true scheduling Pending, the most common production causes are:

1. CPU or memory requests cannot fit.
2. Node selector or project node selector matches no node.
3. Required node affinity is too strict.
4. Required pod anti-affinity needs more nodes than available.
5. Node taints are not tolerated.
6. Topology spread constraints cannot be satisfied.
7. PVC is unbound or storage topology conflicts with pod placement.
8. Node pool reached max pod count.
9. HostPort is already allocated.
10. Priority/preemption cannot overcome hard placement constraints.

A senior OpenShift administrator solves Pending pods by reading events, identifying the exact filter that eliminated feasible nodes, and applying the smallest safe correction.
