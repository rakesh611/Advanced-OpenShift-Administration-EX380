# Dedicated Nodes in OpenShift Pod Scheduling and Workload Placement

**Audience:** Advanced OpenShift Administration / DO380-level administrators  
**Experience level:** Written for an administrator with around 10+ years of Linux, DevOps, Kubernetes, and OpenShift operations experience  
**Topic:** Dedicated nodes  
**Scope:** OpenShift Container Platform 4.x scheduling, workload placement, operational design, troubleshooting, and production patterns

---

## 1. What are dedicated nodes?

In OpenShift, **dedicated nodes** are worker nodes reserved for a specific workload category, tenant, platform component, hardware class, security zone, or operational purpose.

A dedicated node design answers questions like:

- Should production workloads run separately from development workloads?
- Should routers, registry, monitoring, logging, or storage workloads run on infra nodes?
- Should GPU workloads run only on GPU nodes?
- Should high-performance applications avoid noisy neighbors?
- Should a team or namespace be restricted to specific worker nodes?
- Should certain pods be prevented from landing on expensive or sensitive nodes?

Dedicated nodes are not a separate Kubernetes resource. They are an **administrative placement pattern** built using several scheduling controls:

- **Node labels**
- **Node selectors**
- **Node affinity**
- **Taints**
- **Tolerations**
- **Project-level node selectors**
- **MachineSets**
- **MachineConfigPools**
- **Operator-specific node placement**
- **Cluster autoscaler and machine autoscaler behavior**
- **Resource requests, limits, quotas, and priority classes**

The most important mental model is:

> **Taints repel pods. Tolerations permit pods. Node selectors or node affinity attract pods.**

A toleration alone does **not** force a pod onto a dedicated node. It only allows the pod to run there if the node has a matching taint. To make a workload actually use only dedicated nodes, combine:

1. A **taint** on the dedicated node to keep normal pods away.
2. A **toleration** on the allowed workload so it can use the node.
3. A **node selector** or **required node affinity** on the workload so it is scheduled only on that dedicated node group.

## 2. Why dedicated nodes are used in enterprise OpenShift

In small Kubernetes clusters, all workloads often share the same worker pool. In enterprise OpenShift, that model becomes risky. Dedicated nodes are used to improve:

### 2.1 Workload isolation

Dedicated nodes isolate workloads by class, team, environment, or function.

Examples:

- `prod` workloads separate from `dev`
- database workloads separate from stateless apps
- payment workloads separate from generic apps
- OpenShift infra workloads separate from user workloads
- GPU workloads separate from CPU-only workloads
- storage workloads separate from normal compute workloads

### 2.2 Performance consistency

Some workloads are sensitive to noisy neighbors.

Examples:

- JVM applications with strict latency SLOs
- Kafka brokers
- Elasticsearch / OpenSearch nodes
- PostgreSQL / MongoDB / Redis
- AI/ML workloads using GPUs
- NFV/CNF workloads using SR-IOV, huge pages, CPU pinning, or real-time kernel tuning

Dedicated nodes reduce interference from unrelated pods.

### 2.3 Licensing and subscription control

OpenShift infrastructure nodes are commonly used for routers, registry, monitoring, logging, and other cluster services. In many enterprise sizing models, infra nodes are treated differently from generic worker nodes when they are configured correctly and do not run user workloads.

The operational point is:

- Label infra nodes properly.
- Keep user workloads away using taints.
- Place only allowed infrastructure workloads there using node selectors and tolerations.

### 2.4 Security and compliance

Dedicated nodes can support stronger workload separation.

Examples:

- PCI workloads
- regulated banking workloads
- confidential workloads
- workloads requiring special node hardening
- workloads requiring dedicated runtime configuration

This is not a replacement for RBAC, SCC, SELinux, NetworkPolicy, or compliance scanning. It is an additional placement control.

### 2.5 Hardware targeting

Dedicated nodes are required when only some nodes have special capabilities.

Examples:

- GPU
- SR-IOV NIC
- FPGA
- NVMe local storage
- high-memory instances
- high-CPU instances
- huge pages
- real-time kernel
- special kernel modules or drivers

### 2.6 Operational blast-radius control

Dedicated pools make maintenance safer.

Examples:

- drain only storage nodes
- upgrade infra nodes separately through a custom MachineConfigPool
- apply kubelet tuning to performance nodes only
- scale a workload-specific MachineSet independently

## 3. Dedicated node design pattern

A production-grade dedicated node pattern usually has these layers:

```text
                ┌──────────────────────────────┐
                │ Workload / Namespace / Team   │
                └───────────────┬──────────────┘
                                │
                                │ pod spec / namespace annotations
                                │
                ┌───────────────▼──────────────┐
                │ Toleration                    │
                │ Allows pod onto tainted node  │
                └───────────────┬──────────────┘
                                │
                ┌───────────────▼──────────────┐
                │ NodeSelector / NodeAffinity   │
                │ Forces pod to target nodes    │
                └───────────────┬──────────────┘
                                │
                ┌───────────────▼──────────────┐
                │ Dedicated worker nodes        │
                │ Label + taint + capacity      │
                └──────────────────────────────┘
```

### Required components

| Component | Purpose |
|---|---|
| Node label | Identifies the node pool |
| Node taint | Prevents normal pods from landing there |
| Pod toleration | Allows selected pods to tolerate the taint |
| Node selector / required node affinity | Forces selected pods to use that node pool |
| Requests/limits | Ensures scheduler reserves proper CPU/memory |
| Project annotation | Applies placement defaults to a namespace |
| MachineSet labels/taints | Makes the design persistent for newly created nodes |
| MachineConfigPool | Applies node configuration to a custom node group |

## 4. Important scheduling rule: toleration is not attraction

This is a common mistake in real environments and exams.

Suppose a node has this taint:

```bash
oc adm taint node worker01 dedicated=payments:NoSchedule
```

And a pod has this toleration:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: payments
  effect: NoSchedule
```

This pod is **allowed** to run on `worker01`, but it is also allowed to run on any other normal worker node unless you add a selector or affinity.

To make the pod run **only** on payment nodes, add a matching label to the nodes:

```bash
oc label node worker01 dedicated=payments
```

Then add a node selector:

```yaml
nodeSelector:
  dedicated: payments
```

Final logic:

```text
Taint on node:
  "Only pods with this toleration may come here."

Toleration on pod:
  "I am allowed to run on that tainted node."

Node selector / required node affinity:
  "I must run on nodes with this label."
```

## 5. Core objects used for dedicated nodes

## 5.1 Node labels

Node labels are key-value pairs attached to nodes.

Example:

```bash
oc label node worker01 dedicated=payments
oc label node worker02 dedicated=payments
```

Verify:

```bash
oc get nodes -L dedicated
oc get nodes -l dedicated=payments
```

Example output:

```text
NAME       STATUS   ROLES    AGE   VERSION   DEDICATED
worker01   Ready    worker   20d   v1.29.x   payments
worker02   Ready    worker   20d   v1.29.x   payments
worker03   Ready    worker   20d   v1.29.x
```

Recommended label naming:

```text
dedicated=payments
workload=database
workload-tier=gold
node-role.kubernetes.io/infra=
node-role.kubernetes.io/storage=
node-role.kubernetes.io/gpu=
topology.kubernetes.io/zone=zone-a
environment=prod
team=platform
```

### Practical advice

Avoid vague labels like:

```text
type=fast
type=big
use=yes
special=true
```

Prefer clear, operationally meaningful labels:

```text
workload-type=database
performance.openshift.io/profile=low-latency
hardware.accelerator=nvidia-gpu
team=payments
environment=prod
```

## 5.2 Taints

A taint is applied to a node. It prevents pods from being scheduled onto the node unless they have a matching toleration.

Syntax:

```bash
oc adm taint nodes <node-name> <key>=<value>:<effect>
```

Example:

```bash
oc adm taint nodes worker01 dedicated=payments:NoSchedule
```

Verify:

```bash
oc describe node worker01 | grep -i taints -A3
```

Example:

```text
Taints: dedicated=payments:NoSchedule
```

### Taint effects

| Effect | Behavior |
|---|---|
| `NoSchedule` | New pods without matching toleration cannot be scheduled on the node. Existing pods remain. |
| `PreferNoSchedule` | Scheduler tries to avoid the node for pods without matching toleration, but it is not a hard rule. |
| `NoExecute` | New pods without toleration cannot schedule there, and existing pods without toleration can be evicted. |

For dedicated nodes, the most common effect is:

```text
NoSchedule
```

Use `NoExecute` carefully because it can evict existing pods.

---

## 5.3 Tolerations

A toleration is added to a pod spec. It allows the pod to tolerate a matching taint.

Example:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: payments
  effect: NoSchedule
```

With `operator: Exists`:

```yaml
tolerations:
- key: dedicated
  operator: Exists
  effect: NoSchedule
```

### Equal vs Exists

| Operator | Meaning |
|---|---|
| `Equal` | Key, value, and effect must match. |
| `Exists` | Key and effect must match. Value is not required. |

Use `Equal` when you want stricter control.

Example:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: payments
  effect: NoSchedule
```

Use `Exists` when several values under the same key should be tolerated:

```yaml
tolerations:
- key: dedicated
  operator: Exists
  effect: NoSchedule
```

### Do not overuse broad tolerations

This tolerates all taints:

```yaml
tolerations:
- operator: Exists
```

That is dangerous for normal workloads because the pod can land on nodes reserved for control plane, infra, storage, GPU, or other special purposes.

---

## 5.4 Node selectors

A node selector is a simple key-value map in the pod spec.

Example:

```yaml
nodeSelector:
  dedicated: payments
```

The pod can run only on nodes with:

```text
dedicated=payments
```

Example full pod placement section:

```yaml
spec:
  nodeSelector:
    dedicated: payments
  tolerations:
  - key: dedicated
    operator: Equal
    value: payments
    effect: NoSchedule
```

Node selectors are simple and exam-friendly. For many OpenShift admin tasks, they are enough.

---

## 5.5 Node affinity

Node affinity is more expressive than `nodeSelector`.

Use node affinity when you need:

- OR conditions
- multiple possible node groups
- preferred placement
- complex matching operators
- future-proof scheduling policy

Required node affinity example:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: dedicated
          operator: In
          values:
          - payments
```

Meaning:

```text
During scheduling, this pod must run on a node where dedicated is payments.
If labels change later while the pod is already running, Kubernetes does not evict it only because of this affinity rule.
```

Preferred node affinity example:

```yaml
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      preference:
        matchExpressions:
        - key: workload-tier
          operator: In
          values:
          - gold
```

Meaning:

```text
Try to place the pod on gold nodes, but allow scheduling elsewhere if needed.
```

For true dedicated nodes, use required affinity or nodeSelector, not only preferred affinity.

## 6. Dedicated nodes vs infra nodes vs worker nodes

## 6.1 Worker nodes

Generic worker nodes run normal application workloads.

Typical label:

```text
node-role.kubernetes.io/worker=
```

## 6.2 Infra nodes

Infra nodes are a special dedicated-node pattern for cluster infrastructure workloads.

Common workloads moved to infra nodes:

- router / ingress controller
- image registry
- monitoring stack
- logging stack
- some platform operators
- GitOps controller, depending on policy
- service mesh control plane, depending on policy

Typical label:

```text
node-role.kubernetes.io/infra=
```

Typical taint:

```text
node-role.kubernetes.io/infra=reserved:NoSchedule
```

or:

```text
node-role.kubernetes.io/infra=reserved:NoExecute
```

A common infra-node placement snippet:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: node-role.kubernetes.io/infra
  value: reserved
  effect: NoSchedule
  operator: Equal
```

### Important infra node note

In OpenShift 4, infra nodes are often created from worker MachineSets and may carry both:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

Do not casually remove the worker role label unless you understand MachineConfigPool impact. If a node is not selected by the default worker MCP or a custom MCP, it might not receive expected node configuration updates.

Recommended approach:

- Keep the worker role if required for MCP management.
- Add the infra role label.
- Add taints to prevent normal user workloads.
- Add tolerations and node selectors only to allowed infrastructure workloads.

## 6.3 Dedicated application nodes

Application-dedicated nodes are for a specific team, app, environment, or workload class.

Example:

```text
dedicated=payments
environment=prod
```

Taint:

```text
dedicated=payments:NoSchedule
```

Deployment placement:

```yaml
nodeSelector:
  dedicated: payments
tolerations:
- key: dedicated
  operator: Equal
  value: payments
  effect: NoSchedule
```

## 6.4 Dedicated storage nodes

Used for ODF, Ceph, local storage, or storage-heavy workloads.

Example labels:

```text
cluster.ocs.openshift.io/openshift-storage=
node-role.kubernetes.io/storage=
```

Example taint:

```text
node.ocs.openshift.io/storage=true:NoSchedule
```

Always validate storage operator documentation before tainting storage nodes, because platform daemonsets such as DNS, monitoring agents, CSI pods, and storage daemons might require tolerations.

## 6.5 Dedicated GPU nodes

Used for AI/ML workloads.

Example labels:

```text
hardware.accelerator=nvidia-gpu
nvidia.com/gpu.present=true
```

Example taint:

```text
nvidia.com/gpu=present:NoSchedule
```

Workload:

```yaml
nodeSelector:
  hardware.accelerator: nvidia-gpu
tolerations:
- key: nvidia.com/gpu
  operator: Equal
  value: present
  effect: NoSchedule
resources:
  limits:
    nvidia.com/gpu: 1
```

## 7. Dedicated nodes at namespace/project level

OpenShift supports project-level scheduling defaults through namespace/project annotations.

This is powerful when you want every pod in a project to use dedicated nodes without editing every Deployment.

Example project:

```yaml
apiVersion: project.openshift.io/v1
kind: Project
metadata:
  name: payments-prod
  annotations:
    openshift.io/node-selector: "dedicated=payments"
    scheduler.alpha.kubernetes.io/defaultTolerations: >-
      [{"key":"dedicated","operator":"Equal","value":"payments","effect":"NoSchedule"}]
```

Apply:

```bash
oc apply -f payments-prod-project.yaml
```

Now new workloads in `payments-prod` inherit the project placement rules.

Verify namespace annotation:

```bash
oc get namespace payments-prod -o yaml | grep -A5 annotations
```

Check created pod:

```bash
oc get pod <pod> -n payments-prod -o yaml | grep -A10 -E "nodeSelector|tolerations"
```

### Important behavior

If a pod has a node selector that conflicts with the project node selector, pod creation can fail.

Example project selector:

```text
dedicated=payments
```

Pod selector:

```yaml
nodeSelector:
  dedicated: analytics
```

Expected error:

```text
pod node label selector conflicts with its project node label selector
```

For production, project-level placement is useful because it centralizes scheduling policy at namespace level.

## 8. Cluster-wide default node selector

OpenShift can define a cluster-wide default node selector in the Scheduler object.

Example:

```bash
oc edit scheduler cluster
```

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: type=user-node,region=east
  mastersSchedulable: false
```

This makes OpenShift add default node selectors to newly created pods.

Use this carefully. A wrong cluster-wide default selector can break platform components or new workloads if matching nodes are not available.

### Project selector precedence

Project-level node selectors take precedence over cluster-wide default node selectors.

Recommended usage:

- Use cluster-wide selector only when you have a mature node classification strategy.
- Prefer project-level selectors for team/workload isolation.
- Prefer workload-level selectors for application-specific requirements.

## 9. Persistent dedicated node configuration using MachineSets

Manually labeling and tainting nodes works, but it is not always persistent across node replacement.

In cloud or Machine API environments, dedicated node settings should be added to the MachineSet template so new machines/nodes are created with the correct metadata.

Check MachineSets:

```bash
oc get machinesets -n openshift-machine-api
```

Example patch to add labels to a MachineSet template:

```bash
oc patch machineset <machineset-name> \
  -n openshift-machine-api \
  --type='merge' \
  -p '{
    "spec": {
      "template": {
        "spec": {
          "metadata": {
            "labels": {
              "dedicated": "payments"
            }
          }
        }
      }
    }
  }'
```

Example patch to add a taint to a MachineSet template:

```bash
oc patch machineset <machineset-name> \
  -n openshift-machine-api \
  --type='merge' \
  -p '{
    "spec": {
      "template": {
        "spec": {
          "taints": [
            {
              "key": "dedicated",
              "value": "payments",
              "effect": "NoSchedule"
            }
          ]
        }
      }
    }
  }'
```

### Important MachineSet behavior

Updating an existing MachineSet template does not necessarily update already-created Machines and Nodes. New Machines created from the template receive the updated settings. Existing nodes might need manual label/taint changes or MachineSet scale-down/scale-up depending on the change and operational policy.

A safe operational pattern:

```bash
# 1. Patch MachineSet template
oc patch machineset <name> -n openshift-machine-api --type=merge -p '<patch>'

# 2. Apply labels/taints manually to existing nodes if needed
oc label node <node> dedicated=payments
oc adm taint node <node> dedicated=payments:NoSchedule

# 3. Verify
oc get nodes -L dedicated
oc describe node <node> | grep -i taints -A3
```

For immutable replacement pattern:

```bash
oc scale machineset <name> -n openshift-machine-api --replicas=0
oc scale machineset <name> -n openshift-machine-api --replicas=2
```

Use this only after considering disruption, PodDisruptionBudgets, application availability, data locality, and cluster capacity.

## 10. Dedicated node implementation: complete example

## Scenario

You have an OpenShift cluster with generic workers. You want to dedicate two nodes for the `payments` application team.

Requirements:

- Only payments workloads should run on those nodes.
- Payments workloads must run only on those nodes.
- Normal workloads must not land on those nodes.
- The `payments-prod` namespace should automatically schedule pods to those nodes.

## Step 1: Identify nodes

```bash
oc get nodes
```

Example:

```text
worker01   Ready   worker
worker02   Ready   worker
worker03   Ready   worker
worker04   Ready   worker
```

Choose:

```text
worker03
worker04
```

## Step 2: Label the nodes

```bash
oc label node worker03 dedicated=payments
oc label node worker04 dedicated=payments
```

Verify:

```bash
oc get nodes -l dedicated=payments
oc get nodes -L dedicated
```

## Step 3: Taint the nodes

```bash
oc adm taint nodes worker03 dedicated=payments:NoSchedule
oc adm taint nodes worker04 dedicated=payments:NoSchedule
```

Verify:

```bash
oc describe node worker03 | grep -i taints -A3
oc describe node worker04 | grep -i taints -A3
```

Expected:

```text
Taints: dedicated=payments:NoSchedule
```

## Step 4: Create project with placement policy

```yaml
apiVersion: project.openshift.io/v1
kind: Project
metadata:
  name: payments-prod
  annotations:
    openshift.io/node-selector: "dedicated=payments"
    scheduler.alpha.kubernetes.io/defaultTolerations: >-
      [{"key":"dedicated","operator":"Equal","value":"payments","effect":"NoSchedule"}]
```

Apply:

```bash
oc apply -f payments-prod-project.yaml
```

## Step 5: Deploy test workload

```bash
oc -n payments-prod create deployment payment-api --image=registry.access.redhat.com/ubi9/httpd-24
oc -n payments-prod scale deployment payment-api --replicas=2
```

Verify pods:

```bash
oc get pods -n payments-prod -o wide
```

Expected:

```text
NAME                           READY   STATUS    NODE
payment-api-xxxxxxxxxx-aaaaa   1/1     Running   worker03
payment-api-xxxxxxxxxx-bbbbb   1/1     Running   worker04
```

## Step 6: Test that normal workloads cannot land there

Create a normal project:

```bash
oc new-project normal-apps
oc create deployment test-app --image=registry.access.redhat.com/ubi9/httpd-24 -n normal-apps
```

Verify:

```bash
oc get pods -n normal-apps -o wide
```

Expected:

```text
Normal workload should not be scheduled on worker03 or worker04 unless it has matching toleration.
```

## Step 7: Check scheduling details

```bash
oc describe pod <pod-name> -n payments-prod
```

Look for:

```text
Node-Selectors: dedicated=payments
Tolerations:    dedicated=payments:NoSchedule
Events:         Successfully assigned payments-prod/<pod> to worker03
```

## 11. Workload-level dedicated node YAML

Instead of project-level defaults, you can put placement directly in the Deployment.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payments-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      nodeSelector:
        dedicated: payments
      tolerations:
      - key: dedicated
        operator: Equal
        value: payments
        effect: NoSchedule
      containers:
      - name: payment-api
        image: registry.access.redhat.com/ubi9/httpd-24
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: 200m
            memory: 256Mi
          limits:
            cpu: 1
            memory: 512Mi
```

Apply:

```bash
oc apply -f payment-api.yaml
```

## 12. Dedicated nodes with required node affinity

For more advanced matching:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payments-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      tolerations:
      - key: dedicated
        operator: Equal
        value: payments
        effect: NoSchedule
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: dedicated
                operator: In
                values:
                - payments
              - key: environment
                operator: In
                values:
                - prod
      containers:
      - name: payment-api
        image: registry.access.redhat.com/ubi9/httpd-24
```

This requires nodes to have both:

```text
dedicated=payments
environment=prod
```

## 13. Dedicated nodes with topology spread

Dedicated nodes can still suffer from poor distribution if all replicas land on one node or one zone. Use topology spread constraints or pod anti-affinity for HA.

Example:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: payment-api
```

Full placement section:

```yaml
spec:
  nodeSelector:
    dedicated: payments
  tolerations:
  - key: dedicated
    operator: Equal
    value: payments
    effect: NoSchedule
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: payment-api
```

This tries to spread replicas across dedicated payment nodes.

## 15. Dedicated nodes and MachineConfigPools

A MachineConfigPool lets you apply node OS/kubelet configuration to a selected node group.

Use a custom MCP when dedicated nodes need different node-level configuration.

Examples:

- infra-specific files or systemd units
- performance-node kubelet settings
- custom image garbage collection settings
- reserved CPUs
- custom kubelet config
- chrony/NTP behavior
- kernel arguments
- real-time kernel
- huge pages
- CRI-O config

Example custom MCP for infra nodes:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Check MCP:

```bash
oc get mcp
oc describe mcp infra
```

### Important MCP warning

Custom MachineConfigPools inherit from worker configs only if configured properly. A node with a non-standard role label must still be managed by an MCP, otherwise node configuration updates can become inconsistent.

Before removing `worker` role labels from any node, validate MCP design carefully.

## 16. Dedicated nodes and autoscaling

When using MachineAutoscaler or ClusterAutoscaler, dedicated nodes require careful planning.

### Key considerations

- Autoscaler must know which MachineSet represents dedicated nodes.
- Workloads must have node selectors or affinity matching that MachineSet labels.
- Taints must be reflected in MachineSet templates.
- Resource requests must be accurate; autoscaler acts on schedulability and resource demand.
- Overly strict affinity can prevent scale-up if no scalable node group matches.
- A namespace-level selector can cause pods to remain pending unless matching MachineSets exist.

Example dedicated MachineSet autoscaler:

```yaml
apiVersion: autoscaling.openshift.io/v1beta1
kind: MachineAutoscaler
metadata:
  name: payments-worker-us-east-1a
  namespace: openshift-machine-api
spec:
  minReplicas: 2
  maxReplicas: 8
  scaleTargetRef:
    apiVersion: machine.openshift.io/v1beta1
    kind: MachineSet
    name: <clusterid>-payments-us-east-1a
```

For production, define at least two zones if your infrastructure supports it:

```text
payments-us-east-1a
payments-us-east-1b
payments-us-east-1c
```

Then use topology spread constraints to distribute replicas.

## 18. Dedicated nodes and DaemonSets

DaemonSets behave differently from Deployments because they try to run one pod per matching node.

Important points:

- DaemonSets can use `nodeSelector`.
- DaemonSets can use affinity.
- DaemonSets can use tolerations.
- Some OpenShift-managed DaemonSets include default tolerations for node condition taints.
- If you taint dedicated nodes, platform DaemonSets such as DNS, SDN/OVN, monitoring agents, CSI node plugins, or logging collectors may need tolerations.

Example DaemonSet targeting dedicated nodes:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: payments-agent
  namespace: payments-prod
spec:
  selector:
    matchLabels:
      app: payments-agent
  template:
    metadata:
      labels:
        app: payments-agent
    spec:
      nodeSelector:
        dedicated: payments
      tolerations:
      - key: dedicated
        operator: Equal
        value: payments
        effect: NoSchedule
      containers:
      - name: agent
        image: registry.access.redhat.com/ubi9/ubi
        command: ["sleep", "infinity"]
```

Troubleshooting DaemonSets on tainted nodes:

```bash
oc get ds -A
oc describe ds <daemonset> -n <namespace>
oc get pods -n <namespace> -o wide
oc describe pod <pod> -n <namespace>
```

## 19. Dedicated nodes and resource management

Dedicated nodes do not remove the need for proper resource management.

You still need:

- CPU requests
- memory requests
- CPU limits where appropriate
- memory limits
- LimitRanges
- ResourceQuotas
- PodDisruptionBudgets
- PriorityClasses
- HPA/VPA where applicable
- capacity planning

Example namespace ResourceQuota:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: payments-quota
  namespace: payments-prod
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    pods: "100"
```

Example LimitRange:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: payments-defaults
  namespace: payments-prod
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 200m
      memory: 256Mi
    default:
      cpu: "1"
      memory: 512Mi
```

Why this matters:

- Scheduler uses requests to decide placement.
- Autoscaler uses pending pods and requests to determine scale-up needs.
- Dedicated nodes can still be overcommitted if requests are missing.
- A pod with no request may land on a dedicated node and consume unexpected resources.

## 20. Dedicated nodes and high availability

Do not create a dedicated node group with only one node for production unless the workload is intentionally single-node.

Recommended:

```text
Minimum: 2 dedicated nodes
Better: 3 dedicated nodes across zones
Best: N+1 capacity across failure domains
```

For HA:

- Use multiple replicas.
- Use PodDisruptionBudgets.
- Use topology spread constraints.
- Spread MachineSets across zones.
- Avoid binding to a single node name.
- Avoid using `nodeName` except for debugging.
- Ensure storage supports failover if using stateful workloads.

Example PodDisruptionBudget:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-api-pdb
  namespace: payments-prod
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: payment-api
```

## 21. Scheduling flow for a pod targeting dedicated nodes

When a pod is created, the scheduler roughly evaluates:

1. Is the pod already assigned with `nodeName`?
2. Are candidate nodes Ready and schedulable?
3. Do node labels match `nodeSelector`?
4. Do node labels match required node affinity?
5. Does the pod tolerate node taints?
6. Are CPU/memory/extended resources available?
7. Do topology spread, pod affinity, anti-affinity, and volume constraints pass?
8. Are there security/admission constraints?
9. Scheduler scores remaining nodes.
10. Scheduler binds the pod to the best node.

A pod can remain Pending if any hard condition fails.

## 23.3 Pod has toleration but schedules on normal worker

Cause:

The pod tolerates the dedicated node taint but has no selector or required affinity.

Fix:

```yaml
nodeSelector:
  dedicated: payments
```

or:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: dedicated
          operator: In
          values:
          - payments
```

## 23.4 Project node selector conflicts with pod selector

Symptom:

or update the Deployment selector.

## 23.5 MachineSet labels not visible on existing nodes

Cause:

You patched the MachineSet template, but existing machines/nodes were already created.

Check MachineSet:

```bash

```

Check nodes:



## 23.6 Infra node accidentally running user workloads

Check infra nodes:

```bash
oc get nodes -L node-role.kubernetes.io/infra
```

Check pods on infra node:

```bash

```

Check taints:

```bash

```

Fix:

```bash
oc adm taint node <infra-node-name> node-role.kubernetes.io/infra=reserved:NoSchedule
```

Then evict user workloads carefully:

```bash

oc adm drain <infra-node-name> --ignore-daemonsets --delete-emptydir-data
```

Check DaemonSet:

```bash
oc describe ds <ds> -n <namespace>
```

Possible causes:

- Missing toleration for node taint
- Node selector excludes dedicated node
- Required affinity mismatch
- Host port conflict
- Resource shortage
- SCC/security issue
- Image pull issue

Fix placement:


## 23.8 Pod still running after adding NoSchedule taint

This is expected.

`NoSchedule` blocks new pods but does not evict existing pods.

If you need eviction behavior, use:

```text
NoExecute
```

But use carefully.

Alternative:

```bash
oc adm drain <node> --ignore-daemonsets
```

## 23.9 Pod evicted after NoExecute taint

Cause:

The pod did not tolerate the `NoExecute` taint, or `tolerationSeconds` expired.

Check:

```bash
oc describe pod <pod> -n <namespace>
```

Fix:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: payments
  effect: NoExecute
  tolerationSeconds: 3600
```

or no `tolerationSeconds` if it should tolerate indefinitely:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: payments
  effect: NoExecute
```

## 25. Best practices

## 25.1 Use both taint and selector

Do not rely on only tolerations.

Recommended:

```text
Node:
  label: dedicated=payments
  taint: dedicated=payments:NoSchedule

Pod:
  nodeSelector: dedicated=payments
  toleration: dedicated=payments:NoSchedule
```

## 25.2 Do not use nodeName for normal scheduling

Avoid:

```yaml
nodeName: worker03
```

This bypasses normal scheduler logic and creates fragile placement. Use labels and affinity instead.

## 25.3 Do not use one node for production dedicated pools

One dedicated node is a single point of failure.

Use at least:

```text
2 nodes for basic HA
3 nodes for zone spread and upgrade safety
```

## 25.4 Keep labels stable

Do not frequently change dedicated-node labels. Label changes can cause new pods to schedule differently and can conflict with namespace selectors.

## 25.5 Standardize naming

Example enterprise label standard:

```text
workload.openshift.io/class=payments
workload.openshift.io/tier=gold
platform.openshift.io/node-purpose=infra
hardware.openshift.io/accelerator=gpu
environment.openshift.io/name=prod
```

Example taint standard:

```text
dedicated=payments:NoSchedule
node-role.kubernetes.io/infra=reserved:NoSchedule
hardware.accelerator/gpu=true:NoSchedule
```

## 25.6 Use MachineSets for persistence

Manual labels and taints are useful for testing, but MachineSet templates are better for production node replacement.

## 25.7 Validate platform DaemonSets before tainting nodes

Before tainting infra, storage, GPU, or performance nodes, check whether cluster-critical DaemonSets require tolerations.

Check pods per node:

```bash
oc get pods -A -o wide | grep <node>
```

## 25.8 Use project-level selectors carefully

Project-level selectors are powerful but can block pods if users specify conflicting selectors.

Document namespace placement policy clearly.

## 25.9 Combine with quotas

Dedicated nodes without quotas can still be exhausted by one namespace or team.

Use:

- ResourceQuota
- LimitRange
- HPA
- alerts
- capacity dashboards

## 25.10 Monitor scheduling failures

Alert on:

- Pending pods
- FailedScheduling events
- node pressure
- MachineSet unavailable replicas
- MCP degraded
- high CPU/memory saturation
- pod disruption issues

## 29. Key interview and real-world points

### Question: What is a dedicated node?

A worker node intentionally reserved for a specific workload class, tenant, platform component, or hardware profile using labels, taints, tolerations, and selectors/affinity.

### Question: Does toleration force a pod onto a node?

No. A toleration only allows a pod to run on a tainted node. To force placement, use `nodeSelector` or required node affinity.

### Question: What keeps other workloads away from dedicated nodes?

A taint, usually with `NoSchedule`.

### Question: What pulls allowed workloads onto dedicated nodes?

A node selector or required node affinity.

### Question: What is the safest dedicated-node pattern?

```text
Label node
Taint node
Add pod toleration
Add pod nodeSelector or required affinity
Set resource requests
Verify with oc describe pod
```

### Question: Why use MachineSet labels and taints?

To ensure new replacement nodes are created with the same dedicated-node configuration.

### Question: What is the danger of changing node labels directly?

Direct node labels might be lost when nodes are replaced. Also, changes to existing MachineSet templates do not always update existing nodes.

### Question: Why can a project-level selector break pod creation?

If the pod selector conflicts with the namespace/project selector, admission can reject the pod.

### Question: Why is `NoExecute` risky?

It can evict existing pods that do not tolerate the taint.

```bash
oc describe pod <pod> -n payments-prod

# Show namespace selector
oc get ns payments-prod -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'

# Add namespace node selector
oc annotate namespace payments-prod openshift.io/node-selector='dedicated=payments' --overwrite

# Remove namespace node selector
oc annotate namespace payments-prod openshift.io/node-selector-

# Show MachineSets
oc get machinesets -n openshift-machine-api

# Show machines
oc get machines -n openshift-machine-api -o wide

# Show MachineConfigPools
oc get mcp
```

## 31. Summary

Dedicated nodes are a foundational OpenShift workload placement pattern. They are used to isolate workloads, improve performance, protect platform infrastructure, target specialized hardware, and control operational blast radius.

The core rule is:

```text
Taint = repel unwanted pods
Toleration = allow selected pods
Node selector / node affinity = attract or require selected nodes
```

For production, the best pattern is:

```text
1. Create or identify a node pool.
2. Add stable labels.
3. Add taints.
4. Add tolerations to allowed workloads.
5. Add nodeSelector or required nodeAffinity to allowed workloads.
6. Apply project-level placement if the entire namespace should be dedicated.
7. Put labels and taints in MachineSet templates for persistence.
8. Add ResourceQuota, LimitRange, PDB, monitoring, and HA spread.
9. Verify with oc get pods -o wide and oc describe pod.
10. Document and monitor the node pool.
```

A senior OpenShift administrator should not think of dedicated nodes as only a scheduling trick. They are part of a larger platform design involving tenancy, capacity, reliability, compliance, automation, and lifecycle management.
