## 1. What Are Node Labels?

A **node label** is a key-value pair attached to a Kubernetes/OpenShift `Node` object.

Example:

```yaml
metadata:
  labels:
    region: east
    workload: database
    node-role.kubernetes.io/worker: ""
```

In simple language:

> Node labels describe node characteristics so the scheduler, administrators, Operators, and workloads can identify where a pod should or should not run.

A label can describe many things:

| Label Type | Example | Meaning |
|---|---|---|
| Location | `region=delhi`, `zone=az1`, `rack=rack-22` | Physical or cloud topology |
| Hardware | `disk=ssd`, `gpu=nvidia`, `cpu=highfreq` | Hardware capability |
| Workload role | `workload=infra`, `workload=apps`, `workload=db` | Intended workload category |
| Compliance | `compliance=fips`, `pci=true` | Security/compliance grouping |
| Environment | `env=prod`, `env=dev` | Environment boundary |
| Storage role | `storage=odf`, `local-storage=true` | Storage-specific node group |
| Node role | `node-role.kubernetes.io/infra=` | OpenShift-style role marker |

Node labels are not just decoration. They become scheduling inputs when used with:

- `nodeSelector`
- `nodeAffinity`
- topology spread constraints
- project-wide node selectors
- cluster-wide default node selectors
- Operator placement rules
- taints and tolerations design
- MachineConfigPool selection
- storage and hardware placement design

## 2. Why Node Labels Matter in OpenShift

In an enterprise OpenShift cluster, all worker nodes are rarely equal. Some nodes may be dedicated for routers, registry, monitoring, logging, storage, GPU workloads, application teams, security-sensitive workloads, or heavy database workloads.

Without node labels, the scheduler mainly places pods based on available resources, constraints, taints, affinities, topology, and default scheduling policy. With node labels, you can create placement intent.

Examples:

```text
Run ingress router pods only on infra nodes.
Run database workloads only on high IOPS SSD nodes.
Run GPU workloads only on GPU nodes.
Run PCI workloads only on PCI-compliant nodes.
Run storage pods only on ODF storage nodes.
Run production workloads away from development workloads.
Spread replicas across zones using topology labels.
```

From an advanced admin perspective, node labels solve four major problems:

### 2.1 Placement Control

You can force or prefer pods to run on a selected group of nodes.

Example:

```yaml
nodeSelector:
  workload: payments
```

This tells the scheduler to place the pod only on nodes labeled:

```text
workload=payments
```

### 2.2 Hardware Awareness

Applications may require specific hardware.

Examples:

```text
disk=nvme
gpu=nvidia
cpu=amd-epyc
network=25g
```

### 2.3 Compliance and Isolation

Some workloads must run only on trusted, hardened, or audited nodes.

Examples:

```text
compliance=pci
fips=true
data-classification=restricted
```

### 2.4 Operational Separation

OpenShift cluster services should often be separated from tenant/application workloads.

Examples:

```text
node-role.kubernetes.io/infra=
workload=infra
```

Typical infra workloads:

- Ingress router
- Image registry
- Monitoring stack
- Logging stack
- GitOps/Argo CD
- RHACS Central
- Quay
- OpenShift Data Foundation components, depending on design

## 3. Node Labels vs Pod Labels vs Annotations

Many admins confuse node labels, pod labels, selectors, and annotations. They are related but not the same.

| Object | Example | Used For |
|---|---|---|
| Node label | `disk=ssd` on a node | Selecting nodes for scheduling |
| Pod label | `app=mysql` on a pod | Selecting pods for Service, NetworkPolicy, Deployment, affinity |
| Annotation | `description=...` | Non-selector metadata |
| Node selector | `nodeSelector: disk: ssd` in pod spec | Tells scheduler required node label |
| Label selector | `app=mysql` | Finds objects with matching labels |

Important rule:

> Node labels describe nodes. Pod labels describe pods. A pod's `nodeSelector` or `nodeAffinity` selects node labels.

Example:

```yaml
apiVersion: v1
kind: Node
metadata:
  name: worker01
  labels:
    disk: ssd
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mysql
  labels:
    app: mysql
spec:
  nodeSelector:
    disk: ssd
  containers:
  - name: mysql
    image: registry.redhat.io/rhel8/mysql-80
```

Here:

- `app=mysql` is a pod label.
- `disk=ssd` is a node label.
- `nodeSelector: disk: ssd` is the scheduling rule.

## 4. Node Label Syntax and Naming Rules

A label has this format:

```text
<optional-prefix>/<name>=<value>
```

Examples:

```text
disk=ssd
region=east
topology.kubernetes.io/zone=zone-a
node-role.kubernetes.io/infra=
example.com.node-restriction.kubernetes.io/pci-dss=true
```

### 4.1 Label Key Rules

A label key has two parts:

```text
[prefix/]name
```

The name part:

- is required
- must be 63 characters or less
- must start and end with an alphanumeric character
- can contain letters, numbers, hyphen `-`, underscore `_`, and dot `.`

The prefix:

- is optional
- must be a DNS subdomain if used
- must be 253 characters or less
- is separated from the name by `/`

Examples:

```text
valid: disk
valid: topology.kubernetes.io/zone
valid: example.com/workload-type
valid: node-role.kubernetes.io/infra
invalid: /disk
invalid: disk/
invalid: -disk=ssd
invalid: disk-=ssd
```

### 4.2 Label Value Rules

A label value:

- can be empty
- must be 63 characters or less
- if not empty, must start and end with an alphanumeric character
- can contain letters, numbers, hyphen `-`, underscore `_`, and dot `.`

Examples:

```text
valid: disk=ssd
valid: node-role.kubernetes.io/infra=
valid: environment=prod
valid: hardware=high-memory
invalid: environment=-prod
invalid: environment=prod-
```

### 4.3 Reserved Prefixes

Avoid creating your own labels under these reserved Kubernetes prefixes:

```text
kubernetes.io/
k8s.io/
```

These are reserved for Kubernetes core components.

For organization-owned labels, use a company or domain prefix:

```text
platform.example.com/workload=infra
corp.example.com/security-zone=pci
```

For security-sensitive node isolation, use a prefix that includes:

```text
node-restriction.kubernetes.io/
```

Example:

```text
example.com.node-restriction.kubernetes.io/pci-dss=true
```

This helps prevent kubelet self-labeling attacks when the NodeRestriction admission plugin is in use.

## 5. Common Built-in Node Labels

Kubernetes and OpenShift automatically add many labels to nodes.

Check labels:

```bash
oc get nodes --show-labels
```

Better readable output:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,LABELS:.metadata.labels
```

Common labels:

```text
kubernetes.io/hostname=<node-hostname>
kubernetes.io/os=linux
kubernetes.io/arch=amd64
topology.kubernetes.io/region=<region>
topology.kubernetes.io/zone=<zone>
node-role.kubernetes.io/worker=
node-role.kubernetes.io/master=
node-role.kubernetes.io/control-plane=
node.openshift.io/os_id=rhcos
```

Cloud environments often add provider-specific labels. For example:

```text
failure-domain.beta.kubernetes.io/zone=<old-zone-label>
topology.kubernetes.io/zone=<zone>
topology.kubernetes.io/region=<region>
node.kubernetes.io/instance-type=<instance-type>
```

Do not blindly depend on every auto-generated label across cloud providers. Some values can vary by provider, installer, platform, or cluster version.

Recommended approach:

- Use built-in topology labels for zone/region spreading.
- Use your own stable labels for business workload placement.
- Use MachineSet-level labels for durability where Machine API is available.
- Document every custom scheduling label in your platform standards.

## 6. OpenShift Node Roles and Role Labels

OpenShift displays node roles in `oc get nodes` based on labels such as:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/master=
node-role.kubernetes.io/control-plane=
node-role.kubernetes.io/infra=
```

Example:

```bash
oc get nodes
```

Output:

```text
NAME       STATUS   ROLES           AGE   VERSION
master01   Ready    control-plane   30d   v1.XX.X
worker01   Ready    worker          30d   v1.XX.X
infra01    Ready    infra,worker    20d   v1.XX.X
```

To label a worker as infra:

```bash
oc label node worker01 node-role.kubernetes.io/infra=
```

To remove worker role from an infra node, some organizations also remove the worker role label:

```bash
oc label node worker01 node-role.kubernetes.io/worker-
```

However, be careful. Removing the worker role label can affect MachineConfigPool selection, Operator assumptions, monitoring, and automation. In many OpenShift designs, infra nodes still technically remain workers but are additionally labeled as infra.

Common OpenShift pattern:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

Then place infra workloads using node selectors and taints/tolerations.

## 7. How the Scheduler Uses Node Labels

The OpenShift default scheduler performs pod placement in a multi-step process.

High-level flow:

```text
1. Watch for unscheduled pods.
2. Filter nodes that cannot run the pod.
3. Score remaining nodes.
4. Choose the best node.
5. Bind pod to selected node.
6. Kubelet on selected node starts the pod.
```

Node labels affect the filtering and scoring stages.

### 7.1 Filtering Stage

A node is removed from consideration if hard requirements are not met.

Hard requirements include:

- `nodeSelector`
- `requiredDuringSchedulingIgnoredDuringExecution` node affinity
- required pod affinity/anti-affinity
- taints without matching tolerations
- insufficient CPU/memory
- volume topology constraints
- node unschedulable state
- Pod Security / admission failures
- topology constraints with `DoNotSchedule`

Example:

```yaml
nodeSelector:
  disk: ssd
```

If a node does not have `disk=ssd`, it is filtered out.

### 7.2 Scoring Stage

After filtering, the scheduler scores candidate nodes.

Soft preferences can influence scoring:

- preferred node affinity
- topology spreading
- resource balancing policy
- scheduler profile
- image locality
- inter-pod affinity preferences

Example:

```yaml
preferredDuringSchedulingIgnoredDuringExecution:
- weight: 80
  preference:
    matchExpressions:
    - key: disk
      operator: In
      values:
      - nvme
```

This means:

> Prefer nodes with `disk=nvme`, but if none are available, still schedule elsewhere.

## 8. Node Labels with `nodeSelector`

`nodeSelector` is the simplest scheduling mechanism based on node labels.

### 8.1 Basic Example

Label a node:

```bash
oc label node worker01 disk=ssd
```

Create a pod requiring that label:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-ssd
spec:
  nodeSelector:
    disk: ssd
  containers:
  - name: nginx
    image: registry.k8s.io/nginx
```

Apply:

```bash
oc apply -f nginx-ssd.yaml
```

Verify:

```bash
oc get pod nginx-ssd -o wide
oc get node worker01 --show-labels
```

### 8.2 `nodeSelector` Logic

`nodeSelector` is equality-based and AND-based.

Example:

```yaml
nodeSelector:
  disk: ssd
  region: east
  workload: app
```

The pod can run only on nodes that have all of these labels:

```text
disk=ssd AND region=east AND workload=app
```

There is no native OR logic in `nodeSelector`.

For OR logic, use node affinity.

### 8.3 Deployment Example

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: app-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      nodeSelector:
        workload: app
        region: east
      containers:
      - name: frontend
        image: registry.k8s.io/nginx
        ports:
        - containerPort: 80
```

Verify placement:

```bash
oc get pods -n app-prod -o wide
oc get nodes -l workload=app,region=east
```

### 8.4 Important Limitation

You cannot add a `nodeSelector` directly to an already scheduled running pod. Pods are immutable for most scheduling fields after creation.

Correct approach:

- edit the controller template, such as Deployment, DeploymentConfig, StatefulSet, DaemonSet, Job, or CronJob
- let the controller recreate pods

Example:

```bash
oc patch deployment frontend -n app-prod --type='merge' -p '
{
  "spec": {
    "template": {
      "spec": {
        "nodeSelector": {
          "workload": "app"
        }
      }
    }
  }
}'
```

Then watch rollout:

```bash
oc rollout status deployment/frontend -n app-prod
oc get pods -n app-prod -o wide
```

## 9. Node Labels with Node Affinity

Node affinity is more expressive than `nodeSelector`.

It supports:

- hard rules
- soft rules
- OR logic
- operators like `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt`
- weighted preferences

### 9.1 Required Node Affinity

Required node affinity is a hard rule.

```yaml
requiredDuringSchedulingIgnoredDuringExecution
```

Meaning:

> The pod cannot be scheduled unless the rule is satisfied.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: app-prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: workload
                operator: In
                values:
                - app
              - key: region
                operator: In
                values:
                - east
      containers:
      - name: backend
        image: registry.k8s.io/nginx
```

Logic:

```text
workload in (app) AND region in (east)
```

### 9.2 OR Logic with Node Affinity

Multiple `nodeSelectorTerms` are ORed.

```yaml
requiredDuringSchedulingIgnoredDuringExecution:
  nodeSelectorTerms:
  - matchExpressions:
    - key: zone
      operator: In
      values:
      - zone-a
  - matchExpressions:
    - key: zone
      operator: In
      values:
      - zone-b
```

Logic:

```text
zone=zone-a OR zone=zone-b
```

Within one `matchExpressions` list, expressions are ANDed.

```yaml
nodeSelectorTerms:
- matchExpressions:
  - key: region
    operator: In
    values:
    - east
  - key: disk
    operator: In
    values:
    - ssd
```

Logic:

```text
region=east AND disk=ssd
```

### 9.3 Preferred Node Affinity

Preferred affinity is a soft rule.

```yaml
preferredDuringSchedulingIgnoredDuringExecution
```

Meaning:

> Try to schedule on matching nodes, but allow scheduling elsewhere if needed.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: reporting
  namespace: app-prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: reporting
  template:
    metadata:
      labels:
        app: reporting
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: kubernetes.io/os
                operator: In
                values:
                - linux
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 80
            preference:
              matchExpressions:
              - key: disk
                operator: In
                values:
                - nvme
          - weight: 20
            preference:
              matchExpressions:
              - key: zone
                operator: In
                values:
                - zone-a
      containers:
      - name: reporting
        image: registry.k8s.io/nginx
```

Meaning:

```text
Must run on linux nodes.
Prefer disk=nvme strongly.
Prefer zone=zone-a weakly.
```

### 9.4 `IgnoredDuringExecution`

This is very important.

`IgnoredDuringExecution` means:

> The scheduler checks the rule only when scheduling the pod. If node labels change later, the running pod is not automatically evicted only because the label changed.

Example:

1. Pod is scheduled on node with `disk=ssd`.
2. Admin removes `disk=ssd` from the node.
3. Existing pod usually continues running.
4. New replacement pod will not schedule there if the rule still requires `disk=ssd`.

If you need active eviction based on policy drift, you need additional mechanisms such as descheduler policies, node draining, GitOps remediation, or admission/control automation.

### 9.5 Node Affinity Operators

| Operator | Meaning | Example |
|---|---|---|
| `In` | Label value is in allowed list | `disk In [ssd,nvme]` |
| `NotIn` | Label value is not in list | `env NotIn [dev]` |
| `Exists` | Label key exists | `gpu Exists` |
| `DoesNotExist` | Label key does not exist | `maintenance DoesNotExist` |
| `Gt` | Label value greater than integer | `cpu-count Gt 16` |
| `Lt` | Label value less than integer | `latency-tier Lt 3` |

Example using `Exists`:

```yaml
matchExpressions:
- key: gpu
  operator: Exists
```

Example using `NotIn`:

```yaml
matchExpressions:
- key: environment
  operator: NotIn
  values:
  - dev
  - test
```

## 10. Cluster-wide Default Node Selectors

OpenShift supports a cluster-wide default node selector through the Scheduler configuration.

This constrains pods created in the cluster to nodes with matching labels unless project-level selector behavior takes precedence.

Check scheduler configuration:

```bash
oc get scheduler cluster -o yaml
```

Edit scheduler:

```bash
oc edit scheduler cluster
```

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: workload=app,region=east
  mastersSchedulable: false
```

Meaning:

```text
By default, schedule new pods only on nodes labeled workload=app and region=east.
```

### 10.1 When to Use Cluster-wide Default Node Selector

Use it only when you have a strong cluster-wide placement policy.

Possible use cases:

- separating application workloads from infra nodes
- ensuring tenant workloads land only on worker nodes with a specific label
- preventing accidental scheduling to special-purpose nodes

### 10.2 Risks

Cluster-wide node selectors are powerful and risky.

Potential problems:

```text
Pods remain Pending because no node matches.
Operators fail if their pods need different nodes.
Debug pods fail unexpectedly.
Install or upgrade components behave unexpectedly if selector is too restrictive.
```

Before setting it:

```bash
oc get nodes -l workload=app,region=east
oc get pods -A -o wide
```

After setting it:

```bash
oc get co
oc get pods -A --field-selector=status.phase=Pending
oc describe pod <pending-pod> -n <namespace>
```

## 11. Project-wide Node Selectors

OpenShift can apply node selectors at the namespace/project level.

This is useful when different teams or environments must use different node pools.

Example:

```bash
oc annotate namespace app-prod openshift.io/node-selector='env=prod,workload=app'
```

Check:

```bash
oc get namespace app-prod -o yaml | grep -A3 node-selector
```

Create matching node labels:

```bash
oc label node worker01 env=prod workload=app
oc label node worker02 env=prod workload=app
```

Any newly created pod in `app-prod` will be constrained by the project node selector.

### 11.1 Project Selector vs Cluster Selector

If both exist, project node selector behavior can take precedence over the cluster-wide default selector in OpenShift scheduling behavior.

Practical meaning:

- Cluster default selector defines broad default placement.
- Project selector defines namespace-specific placement.
- Pod-level selectors add more constraints.
- If constraints conflict, pods can remain Pending or be rejected.

### 11.2 Troubleshooting Project-wide Node Selector

Check namespace annotation:

```bash
oc get ns app-prod -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
```

Check pod effective selector:

```bash
oc get pod <pod> -n app-prod -o yaml | grep -A10 nodeSelector
```

Check pending reason:

```bash
oc describe pod <pod> -n app-prod
```

Common error pattern:

```text
0/6 nodes are available: node(s) didn't match Pod's node affinity/selector.
```

## 12. Node Labels with Taints and Tolerations

Node labels attract pods. Taints repel pods.

| Mechanism | Purpose | Direction |
|---|---|---|
| Node label + selector | Choose desired nodes | Attraction |
| Node affinity | Required/preferred node choice | Attraction/preference |
| Taint | Keep unwanted pods away | Repulsion |
| Toleration | Allow selected pods onto tainted node | Permission |

A common production design uses both:

```text
Label: workload=infra
Taint: workload=infra:NoSchedule
```

Then infra pods have:

```yaml
nodeSelector:
  workload: infra
tolerations:
- key: workload
  operator: Equal
  value: infra
  effect: NoSchedule
```

This ensures:

- infra pods are attracted to infra nodes
- normal app pods are repelled from infra nodes

### 12.1 Example: Dedicated Database Nodes

Label nodes:

```bash
oc label node worker-db01 workload=database disk=nvme
oc label node worker-db02 workload=database disk=nvme
```

Taint nodes:

```bash
oc adm taint nodes worker-db01 workload=database:NoSchedule
oc adm taint nodes worker-db02 workload=database:NoSchedule
```

Deployment snippet:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload: database
      tolerations:
      - key: workload
        operator: Equal
        value: database
        effect: NoSchedule
```

Without the toleration, the pod will not schedule onto tainted database nodes even if the nodeSelector matches.

## 13. Labeling Nodes: Direct Node Labeling

The simplest way to add a node label is:

```bash
oc label node <node-name> <key>=<value>
```

Example:

```bash
oc label node worker01 region=east
oc label node worker01 disk=ssd
oc label node worker01 workload=app
```

Verify:

```bash
oc get node worker01 --show-labels
oc get nodes -l region=east
oc get nodes -l disk=ssd,workload=app
```

### 13.1 Overwrite Existing Label

If the key already exists:

```bash
oc label node worker01 disk=nvme --overwrite
```

### 13.2 Remove a Label

```bash
oc label node worker01 disk-
```

### 13.3 Label Multiple Nodes

Using label selector:

```bash
oc label nodes -l node-role.kubernetes.io/worker= workload=app
```

Using explicit node names:

```bash
oc label node worker01 worker02 worker03 region=east
```

### 13.4 View Labels in a Clean Table

```bash
oc get nodes -L region,zone,workload,disk
```

Example output:

```text
NAME       STATUS   ROLES    AGE   VERSION   REGION   ZONE     WORKLOAD   DISK
worker01   Ready    worker   20d   v1.x      east     zone-a   app        ssd
worker02   Ready    worker   20d   v1.x      east     zone-b   app        ssd
worker03   Ready    worker   20d   v1.x      west     zone-c   infra      nvme
```

### 13.5 Direct Labeling Limitation

Direct node labels are quick but may not survive node replacement in Machine API-managed clusters.

If a cloud instance is replaced, autoscaled, or recreated, the new node may not have your manually added label.

For durable labels, prefer MachineSet labels where possible.

## 14. Durable Node Labels with MachineSets

In installer-provisioned OpenShift clusters using the Machine API, worker nodes are usually created by MachineSets.

If you label only the `Node`, replacement nodes may lose the label. If you configure labels in the MachineSet template, new Machines/Nodes created from that MachineSet get those labels.

Check MachineSets:

```bash
oc get machinesets -n openshift-machine-api
```

View one MachineSet:

```bash
oc get machineset <machineset-name> -n openshift-machine-api -o yaml
```

Look for provider and template sections.

Example conceptual MachineSet snippet:

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: worker-east-a
  namespace: openshift-machine-api
spec:
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-machineset: worker-east-a
    spec:
      metadata:
        labels:
          region: east
          zone: zone-a
          workload: app
```

The exact structure can vary by platform and OpenShift version, but the key idea is:

> Put node labels into the MachineSet machine template so future nodes created by that MachineSet receive the placement labels.

### 14.1 Important Operational Note

Changing an existing MachineSet does not automatically modify already-created Machines/Nodes in every case. It primarily affects new Machines created after the template change.

A safe production approach:

1. Create a new MachineSet for the desired node pool.
2. Add labels and taints to the MachineSet template.
3. Scale the new MachineSet up.
4. Verify new nodes have expected labels.
5. Drain workloads from old nodes if needed.
6. Scale down the old MachineSet.

Commands:

```bash
oc get machines -n openshift-machine-api
oc get nodes -L region,zone,workload
oc describe machineset <name> -n openshift-machine-api
```

## 15. Node Labels and MachineConfigPools

MachineConfigPools use labels to select nodes for operating system and kubelet configuration management.

This is different from pod scheduling.

A MachineConfigPool selector may match nodes using role labels such as:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

Example:

```bash
oc get mcp
```

Output:

```text
NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED
master   rendered-master-xxxx                               True      False      False
worker   rendered-worker-xxxx                               True      False      False
infra    rendered-infra-xxxx                                True      False      False
```

Example infra MCP concept:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Important distinction:

| Label Use | Example | Effect |
|---|---|---|
| Scheduling label | `workload=app` | Scheduler selects node for pods |
| Role label | `node-role.kubernetes.io/infra=` | OpenShift node role display and selection |
| MCP node selector | `node-role.kubernetes.io/infra=` | Machine Config Operator manages node config |

Be careful when adding/removing role labels because they can affect MachineConfigPool membership and trigger node configuration changes/reboots.

## 18. Real Production Design Patterns

### Pattern 1: Simple Placement with `nodeSelector`

Use when:

- one exact label match is enough
- no OR logic needed
- no preference logic needed

Example:

```yaml
nodeSelector:
  workload: app
```

Best for:

- simple team node pools
- simple environment separation
- quick lab/exam tasks

### Pattern 2: Flexible Placement with Node Affinity

Use when:

- you need OR logic
- you need soft preferences
- you need `Exists`, `NotIn`, `Gt`, `Lt`

Example:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: zone
          operator: In
          values:
          - zone-a
          - zone-b
```

Best for:

- multi-zone scheduling
- hardware class matching
- controlled fallback

### Pattern 3: Dedicated Nodes with Label + Taint

Use when:

- nodes must be reserved for special workloads
- other workloads must be blocked

Example:

```bash
oc label node worker-db01 workload=database
oc adm taint nodes worker-db01 workload=database:NoSchedule
```

Pod:

```yaml
nodeSelector:
  workload: database
tolerations:
- key: workload
  operator: Equal
  value: database
  effect: NoSchedule
```

Best for:

- database nodes
- infra nodes
- GPU nodes
- storage nodes
- regulated workload nodes

### Pattern 4: Project-level Placement

Use when:

- all pods in a project should land on a node pool
- teams should not need to define selectors in every workload

Example:

```bash
oc annotate ns team-a openshift.io/node-selector='team=a'
```

Best for:

- multi-tenant clusters
- self-service teams
- environment isolation

### Pattern 5: Cluster-wide Default Placement

Use sparingly.

Example:

```yaml
spec:
  defaultNodeSelector: workload=app
```

Best for:

- broad default placement policy
- keeping general workloads off infra/storage nodes

Risk:

- too restrictive settings can break scheduling across many namespaces

### Pattern 6: Topology-aware Labels

Use labels like:

```text
topology.kubernetes.io/region=region-a
topology.kubernetes.io/zone=zone-a
rack=rack-1
```

Best for:

- high availability
- spreading replicas
- storage failure domain awareness
- latency-sensitive design

## 19. Complete Lab: Place Workloads on Labeled Nodes

### Lab Goal

Create a project and run an application only on nodes labeled:

```text
workload=advanced
region=east
```

Then troubleshoot common placement failures.

### 19.1 Check Current Nodes

```bash
oc get nodes
oc get nodes --show-labels
```

Clean output:

```bash
oc get nodes -L workload,region,disk
```

### 19.2 Label Two Worker Nodes

Replace node names with your actual nodes.

```bash
oc label node worker01 workload=advanced region=east disk=ssd
oc label node worker02 workload=advanced region=east disk=ssd
```

Verify:

```bash
oc get nodes -l workload=advanced,region=east
oc get nodes -L workload,region,disk
```

### 19.3 Create Project

```bash
oc new-project sched-lab
```

### 19.4 Create Deployment with `nodeSelector`

```bash
cat <<'EOF_DEPLOY' | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: sched-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      nodeSelector:
        workload: advanced
        region: east
      containers:
      - name: web
        image: registry.k8s.io/nginx
        ports:
        - containerPort: 80
EOF_DEPLOY
```

### 19.5 Verify Placement

```bash
oc get pods -n sched-lab -o wide
```

Expected:

```text
Pods should run only on nodes with workload=advanced and region=east.
```

Check matching nodes:

```bash
oc get nodes -l workload=advanced,region=east
```

### 19.6 Introduce a Failure

Patch deployment to require a label that no node has:

```bash
oc patch deployment web -n sched-lab --type=merge -p '
{
  "spec": {
    "template": {
      "spec": {
        "nodeSelector": {
          "workload": "advanced",
          "region": "north"
        }
      }
    }
  }
}'
```

Check pods:

```bash
oc get pods -n sched-lab
oc describe pod <pending-pod> -n sched-lab
```

Likely event:

```text
0/3 nodes are available: node(s) didn't match Pod's node affinity/selector.
```

### 19.7 Fix the Failure

Option A: fix the pod selector:

```bash
oc patch deployment web -n sched-lab --type=merge -p '
{
  "spec": {
    "template": {
      "spec": {
        "nodeSelector": {
          "workload": "advanced",
          "region": "east"
        }
      }
    }
  }
}'
```

Option B: label a node to match:

```bash
oc label node worker03 workload=advanced region=north
```

Verify rollout:

```bash
oc rollout status deployment/web -n sched-lab
oc get pods -n sched-lab -o wide
```

### 19.8 Convert to Node Affinity

Patch deployment to use node affinity instead of simple nodeSelector.

```bash
cat <<'EOF_DEPLOY' | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-affinity
  namespace: sched-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-affinity
  template:
    metadata:
      labels:
        app: web-affinity
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: workload
                operator: In
                values:
                - advanced
              - key: region
                operator: In
                values:
                - east
                - west
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 90
            preference:
              matchExpressions:
              - key: disk
                operator: In
                values:
                - ssd
      containers:
      - name: web
        image: registry.k8s.io/nginx
EOF_DEPLOY
```

Meaning:

```text
Must run on workload=advanced and region=east or region=west.
Prefer disk=ssd.
```

Verify:

```bash
oc get pods -n sched-lab -o wide
oc describe pod <pod> -n sched-lab
```

## 20. Troubleshooting Node Label Scheduling Issues

### 20.1 Pod Pending Due to Label Mismatch

Symptoms:

```bash
oc get pods -n app-prod
```

Output:

```text
NAME        READY   STATUS    RESTARTS   AGE
backend-1   0/1     Pending   0          3m
```

Describe:

```bash
oc describe pod backend-1 -n app-prod
```

Common event:

```text
0/5 nodes are available: node(s) didn't match Pod's node affinity/selector.
```

Check pod selector:

```bash
oc get pod backend-1 -n app-prod -o yaml | grep -A20 -E 'nodeSelector|affinity'
```

Check matching nodes:

```bash
oc get nodes -l workload=backend
oc get nodes -L workload,region,zone,disk
```

Fix:

```bash
oc label node worker01 workload=backend
```

or update deployment selector.

---

### 20.2 Label Exists but Pod Still Pending

Possible causes:

1. Node has matching label but also has taint.
2. Pod lacks toleration.
3. Node lacks CPU/memory.
4. Node is cordoned.
5. Volume topology mismatch.
6. Project-wide selector conflicts.
7. Cluster-wide selector conflicts.
8. Required pod anti-affinity prevents placement.
9. Pod Security or SCC issue prevents admission/start.
10. Node is NotReady.

Commands:

```bash
oc describe pod <pod> -n <namespace>
oc describe node <node>
oc get nodes
oc get nodes -L workload,region,zone
oc get events -n <namespace> --sort-by=.lastTimestamp
```

Check taints:

```bash
oc describe node <node> | grep -i taints -A5
```

Check cordon:

```bash
oc get node <node> -o jsonpath='{.spec.unschedulable}{"\n"}'
```

Uncordon:

```bash
oc adm uncordon <node>
```

---

### 20.3 Project-wide Selector Conflict

Check namespace annotation:

```bash
oc get ns <namespace> -o yaml | grep -i node-selector -A2
```

Example conflict:

Project selector:

```text
env=prod
```

Pod selector:

```text
env=dev
```

Result:

```text
No node can satisfy both constraints.
```

Fix:

```bash
oc annotate ns <namespace> openshift.io/node-selector='env=prod' --overwrite
```

or update pod selector.

---

### 20.4 Cluster-wide Default Selector Conflict

Check scheduler:

```bash
oc get scheduler cluster -o yaml | grep -i defaultNodeSelector -A2
```

If too restrictive, edit:

```bash
oc edit scheduler cluster
```

Be careful. A cluster-wide selector affects new pod creation broadly.

### 20.5 Node Label Changed but Existing Pod Did Not Move

This is expected for `IgnoredDuringExecution` rules.

Running pods are not automatically evicted only because a node label no longer matches.

To force rescheduling:

```bash
oc delete pod <pod> -n <namespace>
```

or rollout restart:

```bash
oc rollout restart deployment/<deployment> -n <namespace>
```

For controlled production movement:

```bash
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data
oc adm uncordon <node>
```

```text
region=east vs region=East
node-role.kubernetes.io/infra vs node-role.kubernetes.io/infra=
```

Labels are case-sensitive.

```bash

```

## 21. Operational Best Practices

### 21.1 Define a Label Taxonomy

Create a standard label strategy.

Example platform standard:

```text
platform.example.com/workload=app|infra|storage|database|gpu
platform.example.com/env=dev|test|prod
platform.example.com/security-zone=standard|pci|restricted
platform.example.com/hardware=standard|highmem|gpu|nvme
platform.example.com/team=payments|erp|shared
```

Avoid random labels created by different teams without governance.

Bad:

```text
appnode=yes
application=true
apps=1
worker-type=application
workload=app
```

Good:

```text
platform.example.com/workload=app
```

### 21.2 Use Labels for Attraction, Taints for Repulsion

For dedicated nodes, never rely only on labels.

Labels alone do this:

```text
Special pods can choose special nodes.
But normal pods may still land there if unrestricted.
```

Labels + taints do this:

```text
Special pods choose special nodes.
Normal pods are blocked from special nodes.
```

### 21.3 Prefer MachineSet-level Labels for Dynamic Nodes

Manual node labels are okay for quick fixes, labs, and static/bare-metal clusters.

For cloud Machine API clusters, prefer MachineSet templates so labels survive node replacement.

### 21.4 Avoid Over-constraining Workloads

Too many hard constraints cause Pending pods.

Example risky combination:

```yaml
nodeSelector:
  workload: app
  region: east
  zone: zone-a
  disk: nvme
  compliance: pci
```

If only one node matches, HA is weak and scheduling is fragile.

Better:

- hard-require only non-negotiable labels
- use preferred affinity for nice-to-have labels
- spread replicas across topology
- ensure enough matching capacity

### 21.5 Do Not Use `nodeName` for Normal Scheduling

`nodeName` bypasses scheduler selection and binds a pod to a specific node.

Avoid this except for special debugging or system-level cases.

Bad:

```yaml
spec:
  nodeName: worker01
```

Better:

```yaml
spec:
  nodeSelector:
    workload: app
```

### 21.6 Keep Labels Stable

Do not use labels for constantly changing values.

Bad:

```text
cpu-free=high
memory-free=low
current-load=80
```

Good:

```text
hardware=highmem
disk=nvme
workload=app
```

For dynamic resource decisions, rely on scheduler resource requests, metrics, autoscaling, and descheduler policies.

### 21.7 Use Security-aware Labels for Isolation

For regulated workloads, use label keys protected from kubelet modification when possible.

Example:

```text
example.com.node-restriction.kubernetes.io/pci-dss=true
```

Then require that label in `nodeSelector` or node affinity.

### 21.8 Document Ownership

For every custom node label, document:

```text
Label key
Allowed values
Owner team
Purpose
Whether it is scheduling-critical
Whether it is applied manually, by MachineSet, GitOps, or Operator
Whether taint/toleration is paired with it
Disaster recovery/replacement behavior
```

### 21.9 Monitor Pending Pods

Use alerts for Pending pods caused by scheduling failures.

Useful checks:

```bash
oc get pods -A --field-selector=status.phase=Pending
oc get events -A --sort-by=.lastTimestamp | grep -i "didn't match"
```

Prometheus-based monitoring should alert on long-running Pending pods and insufficient capacity.

## 22. Interview and Exam-style Questions

### Q1. What is a node label?

A node label is a key-value pair on a `Node` object. It describes node attributes and can be used by `nodeSelector`, node affinity, project selectors, cluster selectors, topology spread, Operators, and automation to control workload placement.

### Q2. What is the difference between `nodeSelector` and node affinity?

`nodeSelector` is simple equality-based hard matching. Node affinity is more expressive and supports hard rules, soft preferences, operators like `In`, `NotIn`, `Exists`, `Gt`, `Lt`, weighted preferences, and OR logic through multiple node selector terms.

### Q3. If a pod is already running and the matching node label is removed, will the pod be evicted?

Normally no. Node affinity type `IgnoredDuringExecution` means label changes after scheduling do not automatically evict the running pod. New pods or replacement pods must satisfy the current labels.

### Q4. Why use taints with node labels?

Labels attract selected pods. Taints repel unapproved pods. For dedicated nodes, use both: label the node for selected workloads and taint the node so other workloads cannot land there without toleration.

### Q5. Why should MachineSet labels be preferred over manual node labels?

In Machine API-managed OpenShift clusters, nodes can be replaced or autoscaled. Manually applied node labels may disappear on replacement nodes. MachineSet template labels make labels durable for newly created nodes.

### Q6. How do you find nodes with a specific label?

```bash
oc get nodes -l workload=app
```

### Q7. How do you display selected label columns?

```bash
oc get nodes -L workload,region,zone,disk
```

### Q8. How do you remove a node label?

```bash
oc label node worker01 workload-
```

### Q9. What does this error mean?

```text
0/5 nodes are available: node(s) didn't match Pod's node affinity/selector.
```

The pod has a `nodeSelector`, node affinity rule, project selector, or cluster default selector that no available node satisfies.

### Q10. Can you add a node selector directly to an existing running pod?

No. Add it to the controller template, such as Deployment, StatefulSet, DaemonSet, DeploymentConfig, Job, or CronJob, then recreate/roll out pods.

## 24. Summary

Node labels are one of the most important building blocks for workload placement in OpenShift.

For basic placement, use:

```yaml
nodeSelector:
  workload: app
```

For advanced placement, use:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution: ...
    preferredDuringSchedulingIgnoredDuringExecution: ...
```

For dedicated nodes, combine:

```text
node label + nodeSelector/nodeAffinity + taint + toleration
```

For durable cloud node pools, apply labels through:

```text
MachineSet templates
```

For namespace-level governance, use:

```text
project-wide node selectors
```

For broad cluster-level policy, use carefully:

```text
Scheduler spec.defaultNodeSelector
```

A senior OpenShift admin should not treat labels as random metadata. In production, node labels are part of cluster architecture, workload isolation, capacity planning, compliance, HA design, and operational governance.
