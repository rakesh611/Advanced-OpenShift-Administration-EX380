# Infrastructure Nodes in OpenShift — Advanced OpenShift Administration Guide

**Topic:** Pod Scheduling and Workload Placement — Infrastructure Nodes  
**Audience:** OpenShift / Kubernetes administrator with ~10 years Linux, DevOps, and platform operations experience  
**Scope:** OpenShift Container Platform 4.x, especially IPI and UPI production clusters  
**Goal:** Understand what infrastructure nodes are, why they exist, how to create them, how to move OpenShift infrastructure workloads to them, how to protect them from user workloads, and how to troubleshoot placement issues.

---

## 1. What is an Infrastructure Node?

An **infrastructure node**, often called an **infra node**, is a node dedicated to running **cluster infrastructure workloads**, not end-user application workloads.

Typical infrastructure workloads include:

- OpenShift router / Ingress Controller pods
- OpenShift internal image registry
- Cluster monitoring components such as Prometheus, Alertmanager, Thanos Querier, Metrics Server, and related monitoring pods
- Cluster logging / observability components
- OpenShift GitOps, Pipelines, Service Mesh, ACM, ACS, Quay, and ODF components when used as cluster-supporting services

In simple words:

> Worker nodes run business applications. Infrastructure nodes run platform services that support the OpenShift cluster.

Infra nodes are not a different operating system. They are usually normal OpenShift worker nodes with special labels, optional taints, and workload placement rules.

The scheduler does **not automatically know** that only infrastructure workloads should run there. You must configure placement correctly.

---

## 2. Why Infrastructure Nodes Matter in Production

In small lab clusters, all non-control-plane workloads often run on worker nodes. In production, that becomes risky.

Infrastructure nodes are used for these reasons:

### 2.1 Isolation of Cluster Services

Cluster services such as routers, monitoring, registry, and logging are critical. If user applications consume too much CPU, memory, ephemeral storage, or network bandwidth, cluster services can become unstable.

Example:

- A user namespace deploys many memory-heavy pods.
- Worker nodes reach memory pressure.
- Router pods or monitoring pods running on the same workers become unstable.
- Routes, console access, alerting, metrics, and image pushes/pulls are affected.

Infra nodes reduce this blast radius.

### 2.2 Better Performance Predictability

Ingress traffic, metrics ingestion, log collection, and image registry operations can be noisy. Dedicated infra nodes make capacity planning easier.

For example:

- Router nodes need good network throughput.
- Monitoring nodes need memory and disk I/O.
- Logging nodes may need high ingest capacity.
- Registry nodes need stable storage and network.

### 2.3 Cleaner Maintenance Windows

When infra workloads are separated from application workloads, you can plan maintenance more cleanly:

- Drain application workers without disturbing routers or monitoring.
- Patch infra nodes separately.
- Scale infra nodes independently.
- Apply different `MachineConfig` or kubelet tuning to infra nodes through a custom MachineConfigPool.

### 2.4 Subscription / Entitlement Design

Red Hat distinguishes between compute nodes that run application workloads and infrastructure nodes that run cluster-supporting workloads. Infra nodes are generally included in the OpenShift entitlement model **only when they run supported infrastructure workloads and no end-user application workloads**.

Important practical rule:

> If an infra node runs even one end-user application pod, that node should be treated as a normal worker/compute node for subscription coverage.

## 3. Node Roles: Master, Worker, Infra

OpenShift nodes commonly have role labels such as:

```bash
node-role.kubernetes.io/master=
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
```

You can check roles with:

```bash
oc get nodes
```

Example output:

```text
NAME            STATUS   ROLES          AGE   VERSION
master-0        Ready    master         90d   v1.xx.x
master-1        Ready    master         90d   v1.xx.x
master-2        Ready    master         90d   v1.xx.x
worker-0        Ready    worker         90d   v1.xx.x
worker-1        Ready    worker         90d   v1.xx.x
infra-0         Ready    infra,worker   10d   v1.xx.x
infra-1         Ready    infra,worker   10d   v1.xx.x
infra-2         Ready    infra,worker   10d   v1.xx.x
```

Notice the common production pattern:

```text
infra,worker
```

This is normal.

OpenShift often keeps the `worker` role label on infra nodes so the Machine Config Operator can continue managing those nodes through the worker pool unless you create a custom infra MachineConfigPool.

Do **not** assume that removing the `worker` label is the best design. In many cases, you should keep `infra,worker` and use **taints and tolerations** to block normal user workloads.

## 4. The Key Scheduling Building Blocks

Infrastructure node placement uses four major concepts:

1. **Node labels**
2. **Node selectors / nodePlacement**
3. **Taints and tolerations**
4. **MachineSets / MachineConfigPools**

### 4.1 Node Label

The infra node label normally looks like this:

```bash
node-role.kubernetes.io/infra=
```

Apply it manually:

```bash
oc label node <node_name> node-role.kubernetes.io/infra=
```

Verify:

```bash
oc get nodes -L node-role.kubernetes.io/infra
```

or:

```bash
oc describe node <node_name> | grep -A5 Labels
```

### 4.2 Node Selector

A pod, deployment, operator-managed component, or operator custom resource can request infra nodes using a node selector:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

Some OpenShift operators use `nodePlacement` instead:

```yaml
nodePlacement:
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

The exact field depends on the OpenShift component.

### 4.3 Taint

A taint prevents pods from landing on a node unless they have a matching toleration.

Recommended infra taint:

```bash
oc adm taint nodes <node_name> node-role.kubernetes.io/infra=reserved:NoSchedule
```

Apply to all infra nodes:

```bash
oc adm taint nodes -l node-role.kubernetes.io/infra node-role.kubernetes.io/infra=reserved:NoSchedule
```

Verify:

```bash
oc describe node <node_name> | grep -i Taints
```

Expected:

```text
Taints: node-role.kubernetes.io/infra=reserved:NoSchedule
```

### 4.4 Toleration

A pod that is allowed to run on infra nodes must tolerate the infra taint:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  value: reserved
  effect: NoSchedule
  operator: Equal
```

A toleration does not force a pod onto the infra node. It only says, "this pod is allowed to run there." You still need a node selector or node affinity to target infra nodes.

Correct infra placement usually needs both:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: node-role.kubernetes.io/infra
  value: reserved
  effect: NoSchedule
  operator: Equal
```

### 4.5 NoSchedule vs NoExecute

Common taint effects:

| Effect | Meaning | Use Case |
|---|---|---|
| `NoSchedule` | New pods cannot be scheduled unless they tolerate the taint. Existing pods remain. | Most common for infra nodes. |
| `NoExecute` | Existing pods that do not tolerate the taint can be evicted. | Stronger isolation; use carefully. |
| `PreferNoSchedule` | Scheduler tries to avoid the node but can still schedule there. | Soft isolation only. |

For most production infra nodes, start with:

```text
node-role.kubernetes.io/infra=reserved:NoSchedule
```

Use `NoExecute` only when you understand eviction impact.

## 5. What Can Run on Infrastructure Nodes?

Infrastructure nodes should run only cluster-supporting workloads.

Common allowed examples:

| Component | Namespace / Operator Area | Notes |
|---|---|---|
| Router / HAProxy Ingress Controller | `openshift-ingress`, `openshift-ingress-operator` | Commonly moved to infra nodes. |
| Internal image registry | `openshift-image-registry` | Useful when registry traffic is heavy. |
| Monitoring stack | `openshift-monitoring` | Prometheus, Alertmanager, Thanos, metrics components. |
| Logging stack | `openshift-logging`, observability namespaces | Depends on installed logging/observability operator. |
| Quay | Quay namespaces | If used as platform registry service. |
| ODF | `openshift-storage` | Often needs separate design; not always mixed with router/monitoring. |
| ACM | `open-cluster-management` | Platform management service. |
| ACS | `stackrox` / ACS namespaces | Security platform service. |
| GitOps | `openshift-gitops` | Platform GitOps controller. |
| Pipelines | `openshift-pipelines` | Platform CI/CD service components. |
| Service Mesh control plane | Service mesh namespaces | Control plane components, not arbitrary application sidecars. |

Not allowed for infra-only entitlement:

- Business application pods
- Developer application pods
- Database workloads belonging to an application team
- Web applications belonging to an application team
- Third-party application workloads not supporting the cluster platform
- Random test/debug pods from user projects

A debug pod created by an admin may be temporary, but do not leave user or debug workloads running on infra nodes.

## 6. Infrastructure Nodes vs Dedicated Nodes

These terms are related but not identical.

| Concept | Meaning |
|---|---|
| Infrastructure node | A node intended for OpenShift cluster infrastructure workloads. |
| Dedicated node | A node reserved for a specific workload group, team, application, hardware profile, or function. |
| Worker node | A compute node that runs end-user workloads. |
| Control plane node | Runs Kubernetes/OpenShift control plane components. |

An infra node is a type of dedicated node, but not every dedicated node is an infra node.

Example dedicated node labels:

```bash
node-role.kubernetes.io/infra=
node-role.kubernetes.io/storage=
node-role.kubernetes.io/gpu=
node-role.kubernetes.io/app-a=
```

Do not label application-dedicated nodes as `infra` unless they are truly for cluster-supporting infrastructure workloads.

## 7. High-Level Design Patterns

### 7.1 Small Non-Production Cluster

```text
3 control plane nodes
2-3 worker nodes
0 infra nodes
```

Suitable for:

- Labs
- Development clusters
- Small internal testing

Not ideal for serious production.

### 7.2 Standard Production Cluster

```text
3 control plane nodes
3+ worker nodes
3 infra nodes
```

Commonly used because infra services such as routers and monitoring should remain highly available.

Spread infra nodes across failure domains:

```text
infra-0 -> zone-a
infra-1 -> zone-b
infra-2 -> zone-c
```

### 7.3 Larger Production Cluster

```text
3 control plane nodes
N worker nodes
3+ router/monitoring infra nodes
3+ storage nodes if ODF internal mode is used
optional logging nodes
optional GitOps/Pipelines/ACM/ACS infra nodes
```

For large environments, do not blindly place everything on the same infra nodes. Monitoring, logging, registry, and ingress can have very different resource profiles.

### 7.4 Bare Metal / UPI Cluster

In bare metal or UPI clusters, you might not have Machine API-based MachineSets. You can still create infra nodes by joining additional hosts as workers, labeling them as infra, and configuring taints and placement.

## 9. Creating Infra Nodes with a MachineSet

This is the preferred method for IPI/cloud clusters where Machine API is operational.

### 9.1 Get Existing MachineSets

```bash
oc get machinesets -n openshift-machine-api
```

Example:

```text
NAME                              DESIRED   CURRENT   READY   AVAILABLE
ocp4-worker-us-east-1a            2         2         2       2
ocp4-worker-us-east-1b            2         2         2       2
ocp4-worker-us-east-1c            2         2         2       2
```

### 9.2 Export a Worker MachineSet

```bash
oc get machineset <worker_machineset_name> \
  -n openshift-machine-api \
  -o yaml > infra-machineset.yaml
```

Edit the file carefully.

Remove runtime fields such as:

```yaml
status:
metadata:
  resourceVersion:
  uid:
  generation:
  creationTimestamp:
  managedFields:
```

### 9.3 Change Name and Labels

Example important fields:

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: <cluster_id>-infra-<zone>
  namespace: openshift-machine-api
  labels:
    machine.openshift.io/cluster-api-cluster: <cluster_id>
spec:
  replicas: 1
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-cluster: <cluster_id>
      machine.openshift.io/cluster-api-machineset: <cluster_id>-infra-<zone>
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-cluster: <cluster_id>
        machine.openshift.io/cluster-api-machine-role: infra
        machine.openshift.io/cluster-api-machine-type: infra
        machine.openshift.io/cluster-api-machineset: <cluster_id>-infra-<zone>
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/infra: ""
      providerSpec:
        value:
          # cloud-specific provider configuration
```

The exact providerSpec differs across AWS, Azure, GCP, vSphere, RHOSP, IBM Cloud, and other platforms.

### 9.4 Apply the MachineSet

```bash
oc apply -f infra-machineset.yaml
```

Watch machines:

```bash
watch 'oc get machines -n openshift-machine-api'
```

Watch nodes:

```bash
watch 'oc get nodes'
```

### 9.5 Scale Infra MachineSets

For one infra node per zone:

```bash
oc scale machineset <cluster_id>-infra-zone-a -n openshift-machine-api --replicas=1
oc scale machineset <cluster_id>-infra-zone-b -n openshift-machine-api --replicas=1
oc scale machineset <cluster_id>-infra-zone-c -n openshift-machine-api --replicas=1
```

Verify:

```bash
oc get nodes -l node-role.kubernetes.io/infra
```

## 11. Should You Remove the Worker Label?

Usually, **do not remove the worker label** unless you have a clear reason and you create a custom MachineConfigPool.

Why?

OpenShift Machine Config Operator manages nodes through MachineConfigPools. The default worker pool selects nodes with:

```bash
node-role.kubernetes.io/worker=
```

If you remove `worker` and leave only `infra`, the node might no longer be selected by the worker MachineConfigPool. This can affect OS configuration, kubelet configuration, updates, and MCO behavior unless you create a custom `infra` MachineConfigPool.

Recommended normal pattern:

```text
ROLES: infra,worker
Taint: node-role.kubernetes.io/infra=reserved:NoSchedule
```

This keeps the node managed while blocking user workloads.

## 12. Creating an Infra MachineConfigPool

Create a custom MachineConfigPool when infra nodes need separate host-level configuration, for example:

- Different kubelet settings
- Different container runtime settings
- Different system reserved resources
- Different kernel arguments
- Different image pull settings
- Different node tuning profile

### 12.1 MachineConfigPool Example

`infra-mcp.yaml`:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

Apply:

```bash
oc apply -f infra-mcp.yaml
```

Verify:

```bash
oc get mcp
```

Expected:

```text
NAME     UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT
master   True      False      False      3              3
worker   True      False      False      6              6
infra    True      False      False      3              3
```

### 12.2 MachineConfig for Infra Nodes

Example only:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 51-infra-example
  labels:
    machineconfiguration.openshift.io/role: infra
spec:
  config:
    ignition:
      version: 3.2.0
    storage:
      files:
      - path: /etc/example-infra-node
        mode: 0644
        contents:
          source: data:,infra-node
```

Apply:

```bash
oc apply -f 51-infra-example.yaml
```

Important:

> MachineConfig changes can reboot nodes. Plan changes carefully, especially when infra nodes run router and monitoring workloads.

## 13. Protecting Infra Nodes from User Workloads

The most important production task is this:

> Infrastructure workloads must be able to run on infra nodes, but normal user workloads must not land there.

### 13.1 Apply Taint to Infra Nodes

```bash
oc adm taint nodes -l node-role.kubernetes.io/infra node-role.kubernetes.io/infra=reserved:NoSchedule
```

### 13.2 Confirm Taint

```bash
for node in $(oc get nodes -l node-role.kubernetes.io/infra -o name); do
  echo "===== $node ====="
  oc describe "$node" | grep -i Taints
done
```

### 13.3 Test with a Normal Pod

Create a normal test pod without toleration:

```bash
oc new-project test-infra-taint
oc run test-nginx --image=registry.k8s.io/nginx --restart=Never
oc get pod -o wide
```

If normal workers are available, the pod should not land on infra nodes. If you force it with a node selector but do not add toleration, it should stay Pending.

Example forced test:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: should-not-run-on-infra
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
  containers:
  - name: nginx
    image: registry.k8s.io/nginx
```

Apply:

```bash
oc apply -f should-not-run-on-infra.yaml
oc describe pod should-not-run-on-infra
```

Expected scheduling error:

```text
node(s) had untolerated taint {node-role.kubernetes.io/infra: reserved}
```

Delete test project:

```bash
oc delete project test-infra-taint
```

## 14. Moving Router / Ingress Controller to Infra Nodes

The router is one of the most common workloads moved to infra nodes.

### 14.1 Check Current Router Placement

```bash
oc get pods -n openshift-ingress -o wide
```

Example:

```text
NAME                              READY   STATUS    NODE
router-default-xxxx               1/1     Running   worker-0
router-default-yyyy               1/1     Running   worker-1
```

### 14.2 Edit IngressController

```bash
oc edit ingresscontroller default -n openshift-ingress-operator
```

Add:

```yaml
spec:
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoSchedule
```

### 14.3 Verify Router Movement

```bash
watch 'oc get pods -n openshift-ingress -o wide'
```

Check node roles:

```bash
oc get nodes
```

Expected router pods should run on nodes with `infra,worker` role.

### 14.4 Important Router Warning

Do not scale worker MachineSets down to zero until you confirm router pods are already moved and healthy on infra nodes. If routers disappear, route access to applications and even console routes can be affected.

## 17. Moving Operator-Managed Pods to Infra Nodes

Many OpenShift components are installed through OLM. For OLM-managed operators, placement may be configured through the `Subscription` object.

### 17.1 Subscription Placement Example

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: example-operator
  namespace: example-namespace
spec:
  config:
    nodeSelector:
      node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Exists
      effect: NoSchedule
```

Patch example:

```bash
oc patch subscription <subscription_name> \
  -n <operator_namespace> \
  --type=merge \
  -p '{"spec":{"config":{"nodeSelector":{"node-role.kubernetes.io/infra":""},"tolerations":[{"key":"node-role.kubernetes.io/infra","operator":"Exists","effect":"NoSchedule"}]}}}'
```

### 17.2 Important Operator Limitation

Not every operator supports moving every operand pod to infra nodes. There are three levels to understand:

| Layer | Example | Placement Method |
|---|---|---|
| Operator pod | Controller manager installed by OLM | `Subscription.spec.config` |
| Operand pods | Pods created by the operator | Operator-specific CR fields |
| DaemonSet pods | Node-level agents | Operator CR, tolerations, or fixed operator behavior |

Always check the operator documentation before assuming the field name.

## 18. Placement for Custom Infrastructure Workloads

For your own platform services, use both node selector and toleration.

Example Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: platform-cache
  namespace: platform-services
spec:
  replicas: 2
  selector:
    matchLabels:
      app: platform-cache
  template:
    metadata:
      labels:
        app: platform-cache
    spec:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
      - key: node-role.kubernetes.io/infra
        value: reserved
        effect: NoSchedule
        operator: Equal
      containers:
      - name: cache
        image: registry.example.com/platform/cache:1.0
        resources:
          requests:
            cpu: 500m
            memory: 512Mi
          limits:
            cpu: "1"
            memory: 1Gi
```

Only do this for platform-level services, not business applications.

## 19. Project-Level Node Selectors and Infra Nodes

OpenShift supports project-level node selectors through namespace annotations.

Example:

```bash
oc annotate namespace <namespace> openshift.io/node-selector='node-role.kubernetes.io/worker='
```

This can force workloads in that namespace to worker nodes.

However, for infra node protection, **taints are stronger and safer** because they affect scheduling even if a user adds an accidental node selector to infra.

Recommended approach:

- Use infra taint to block user workloads.
- Use infra node selector + toleration for allowed platform workloads.
- Use project-level node selectors only when you need namespace-wide placement policy.

---

## 20. Global Scheduler Default Node Selector — Use Carefully

OpenShift has a cluster scheduler object:

```bash
oc get scheduler cluster -o yaml
```

It can define:

```yaml
spec:
  defaultNodeSelector: key=value
```

This is powerful and dangerous.

Do not set the global default node selector to infra in a normal production cluster because new pods without explicit placement could default to infra nodes. That defeats infra isolation.

Use global scheduler defaults only when you have a very specific cluster-wide design.

## 22. Troubleshooting Infrastructure Node Scheduling

### Problem 1: Pod is Pending with `untolerated taint`

Example event:

```text
0/6 nodes are available: 3 node(s) had untolerated taint {node-role.kubernetes.io/infra: reserved}
```

Meaning:

- Pod is trying to run on infra node.
- Infra node has taint.
- Pod does not have matching toleration.

Fix:

Add toleration:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  value: reserved
  effect: NoSchedule
  operator: Equal
```

For OLM operator pods, add it under `Subscription.spec.config` if supported.

---

### Problem 2: Pod is Pending with `didn't match node selector`

Example event:

```text
0/6 nodes are available: 6 node(s) didn't match Pod's node affinity/selector
```

Check pod selector:

```bash
oc get pod <pod> -n <namespace> -o yaml | grep -A10 nodeSelector
```

Check node labels:

```bash
oc get nodes --show-labels | grep infra
```

Fix label mismatch:

```bash
oc label node <node_name> node-role.kubernetes.io/infra=
```

or fix pod/operator placement config.

---

### Problem 3: Router Does Not Move to Infra Nodes

Check IngressController:

```bash
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
```

Check router pods:

```bash
oc get pods -n openshift-ingress -o wide
```

Check events:

```bash
oc describe pod <router_pod> -n openshift-ingress
```

Common causes:

- `nodePlacement` field is wrong.
- Toleration missing.
- Infra node label missing.
- Infra nodes are not Ready.
- Insufficient CPU/memory.
- Router replica count is higher than available infra capacity.

Fix:

- Correct `spec.nodePlacement`.
- Confirm infra taint and toleration match.
- Confirm node health.

---

### Problem 4: Registry Does Not Move

Check registry config:

```bash
oc get configs.imageregistry.operator.openshift.io/cluster -o yaml
```

Check registry operator:

```bash
oc get co image-registry
```

Check pod events:

```bash
oc describe pod <registry_pod> -n openshift-image-registry
```

Common causes:

- Wrong field name.
- Missing toleration.
- Registry storage issue.
- Operator is degraded.
- Infra node has no access to storage backend.

---

### Problem 5: Monitoring Does Not Move

Check config map:

```bash
oc get configmap cluster-monitoring-config -n openshift-monitoring -o yaml
```

Check monitoring operator logs:

```bash
oc logs deploy/cluster-monitoring-operator -n openshift-monitoring
```

Check ClusterOperator:

```bash
oc get co monitoring
oc describe co monitoring
```

Common causes:

- Invalid YAML indentation inside `config.yaml`.
- Component key name is wrong.
- Missing toleration.
- PVC or storage binding problem.
- Not enough resources on infra nodes.

---

### Problem 6: User Workloads Are Running on Infra Nodes

Find all pods on infra nodes:

```bash
for node in $(oc get nodes -l node-role.kubernetes.io/infra -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}'); do
  echo "===== $node ====="
  oc get pods -A -o wide --field-selector spec.nodeName=$node
 done
```

If user pods are found:

1. Confirm infra taint exists.
2. Check whether user pod has a broad toleration.
3. Check namespace default tolerations or custom admission policies.
4. Evict/redeploy the user workload to worker nodes.
5. Remove unnecessary tolerations from user workload specs.

Common dangerous toleration:

```yaml
tolerations:
- operator: Exists
```

This can tolerate all taints and should be avoided for normal application workloads.

---

### Problem 7: Removed Worker Label and Node Is Not Updating

Check node labels:

```bash
oc get node <node_name> --show-labels
```

Check MachineConfigPools:

```bash
oc get mcp
```

If the node is not selected by any MCP, re-add worker label or create an infra MCP.

Re-add worker label:

```bash
oc label node <node_name> node-role.kubernetes.io/worker=
```

Then verify:

```bash
oc get mcp
oc describe mcp worker
```

---

### Problem 8: Infra MachineSet Creates Machine but Node Does Not Join

Check machines:

```bash
oc get machines -n openshift-machine-api
oc describe machine <machine_name> -n openshift-machine-api
```

Check Machine API operator:

```bash
oc get co machine-api
```

Check pending CSRs:

```bash
oc get csr
```

Approve CSRs only if you understand the node identity and environment:

```bash
oc adm certificate approve <csr_name>
```

Common causes:

- Wrong providerSpec.
- Wrong subnet/security group.
- Node cannot reach API.
- DNS issue.
- Bootstrap/ignition issue.
- Cloud quota issue.
- Machine API credentials issue.

## 23. Operational Best Practices

### 23.1 Use At Least Three Infra Nodes for HA

For production, prefer at least three infra nodes across zones or racks:

```text
infra-a -> failure domain A
infra-b -> failure domain B
infra-c -> failure domain C
```

This helps keep router, registry, and monitoring services resilient.

### 23.2 Keep Infra Nodes Dedicated

Do not let application teams deploy to infra nodes.

Recommended controls:

- Infra taint
- Namespace placement policy
- RBAC guardrails
- Admission policy if needed
- Periodic audit script

### 23.3 Do Not Overload Infra Nodes

Monitoring, logging, router, and registry can each become heavy. Watch:

```bash
oc adm top nodes
oc adm top pods -A
```

Also check:

```bash
oc describe node <infra_node>
```

Look at:

- Allocated resources
- Memory pressure
- Disk pressure
- PID pressure
- Pod count
- Events

### 23.4 Separate Storage-Heavy and Network-Heavy Components When Needed

Ingress/router nodes are network-heavy. Monitoring/logging can be memory and storage-heavy. Registry can be storage and network-heavy.

In large clusters, consider separate pools:

```text
infra-router
infra-monitoring
infra-logging
storage
```

Use labels such as:

```bash
node-role.kubernetes.io/infra=
node.openshift.io/infra-role=router
node.openshift.io/infra-role=monitoring
```

Then use more specific selectors:

```yaml
nodeSelector:
  node.openshift.io/infra-role: router
```

### 23.5 Keep MachineSets Symmetric Across Zones

For cloud clusters, create one infra MachineSet per availability zone.

Bad:

```text
3 infra nodes in zone-a only
```

Better:

```text
1 infra node in zone-a
1 infra node in zone-b
1 infra node in zone-c
```

### 23.6 Watch Updates and Reboots

Infra nodes are critical. MCO updates can reboot them. Ensure enough replicas exist for router and other services before node updates.

Check update state:

```bash
oc get mcp
oc get nodes
oc get co
```

### 23.7 Be Careful with Descheduler

If descheduler is enabled, pods violating taints or placement policies may be evicted. Ensure infra workloads have correct tolerations and selectors before enabling descheduler policies.

## 24. Capacity Planning Guidance

Capacity depends on traffic, number of routes, scrape targets, log volume, image push/pull patterns, and installed operators.

General starting approach:

1. Start with 3 infra nodes for HA.
2. Place router, registry, and monitoring.
3. Observe actual usage for at least several business cycles.
4. Tune requests/limits and node sizes.
5. Split workloads into separate infra pools if needed.

Key metrics to monitor:

- CPU usage on infra nodes
- Memory usage and working set
- Network throughput
- Disk I/O and ephemeral storage
- Prometheus TSDB size and ingestion rate
- Router connection count and latency
- Registry pull/push latency
- Node pressure conditions
- Pod restarts

Useful commands:

```bash
oc adm top nodes
oc adm top pods -A | sort -k3 -h
oc describe node <infra_node>
oc get events -A --sort-by=.lastTimestamp
```

## 25. Security Considerations

Infrastructure nodes often run sensitive platform components.

Security best practices:

- Do not allow normal projects to schedule pods on infra nodes.
- Avoid broad tolerations in application workloads.
- Restrict who can edit operator placement configuration.
- Restrict who can label/taint nodes.
- Monitor for unexpected pods on infra nodes.
- Use RBAC carefully around `nodes`, `machinesets`, `scheduler`, `ingresscontrollers`, registry config, and monitoring config.
- Keep infra nodes patched through supported OpenShift mechanisms.

Check who can modify nodes:

```bash
oc adm policy who-can update nodes
oc adm policy who-can patch nodes
```

Check who can edit MachineSets:

```bash
oc adm policy who-can update machinesets.machine.openshift.io -n openshift-machine-api
```

## 26. Audit Script: Find Non-Infra Pods on Infra Nodes

This script prints pods running on infra nodes. Review namespaces manually.

```bash
#!/bin/bash
set -euo pipefail

infra_nodes=$(oc get nodes -l node-role.kubernetes.io/infra -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}')

for node in $infra_nodes; do
  echo "============================================================"
  echo "Infra node: $node"
  echo "============================================================"
  oc get pods -A -o wide --field-selector spec.nodeName=$node
  echo
done
```

To highlight likely user namespaces, you can exclude common OpenShift namespaces:

```bash
#!/bin/bash
set -euo pipefail

infra_nodes=$(oc get nodes -l node-role.kubernetes.io/infra -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}')

for node in $infra_nodes; do
  echo "===== Possible non-platform pods on $node ====="
  oc get pods -A -o wide --field-selector spec.nodeName=$node \
    | grep -v '^openshift-' \
    | grep -v '^kube-' \
    | grep -v '^NAMESPACE' || true
  echo
done
```

Do not rely only on namespace names for compliance. Some platform services may run outside `openshift-*`, and some user workloads may be placed in misleading namespaces.

## 28. Common Exam / Interview Style Questions

### Q1. Is an infra node a special node type?

No. It is normally a worker node with infra role labeling and scheduling policy. The scheduler uses labels, selectors, taints, tolerations, affinity, and operator-specific placement configuration.

### Q2. Why do infra nodes often show `infra,worker`?

Because the worker role keeps the node managed by the worker MachineConfigPool. The infra role identifies the node as infrastructure. Taints prevent user workloads from scheduling there.

### Q3. What happens if you only label a node as infra but do not taint it?

User workloads can still run there unless they are restricted by other scheduling rules. A label alone does not repel pods.

### Q4. What happens if you only taint the node but do not move infra workloads?

Infrastructure workloads without matching tolerations may not schedule there. Existing pods might stay elsewhere. To use infra nodes properly, infra workloads need selectors and tolerations.

### Q5. What is the safest combination?

Use both:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: node-role.kubernetes.io/infra
  value: reserved
  effect: NoSchedule
```

And taint infra nodes:

```bash
oc adm taint nodes -l node-role.kubernetes.io/infra node-role.kubernetes.io/infra=reserved:NoSchedule
```

### Q6. Should you remove the worker label from infra nodes?

Usually no. Keep `infra,worker` and use taints/tolerations unless you create and understand a custom infra MachineConfigPool.

### Q7. How do you verify router pods are on infra nodes?

```bash
oc get pods -n openshift-ingress -o wide
oc get node <node_name>
```

The node role should include `infra`.

### Q8. How do you find unexpected application pods on infra nodes?

```bash
for node in $(oc get nodes -l node-role.kubernetes.io/infra -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}'); do
  oc get pods -A -o wide --field-selector spec.nodeName=$node
 done
```

### Q9. Why can a pod tolerate infra taint but still not run on infra nodes?

A toleration only allows scheduling. It does not select the node. The pod also needs a node selector, node affinity, or other placement rule targeting infra nodes.

### Q10. Why is a broad `operator: Exists` toleration risky?

Because it may allow a pod to tolerate many taints, including taints intended for infra, storage, GPU, or dedicated nodes. Use specific tolerations when possible.

## 30. Real-World Design Recommendation

For a serious production OpenShift cluster, a clean baseline design is:

```text
3 control plane nodes
3 infra nodes across failure domains
3+ worker nodes for applications
optional dedicated storage/logging/router pools as scale grows
```

Use:

```bash
node-role.kubernetes.io/infra=
node-role.kubernetes.io/infra=reserved:NoSchedule
```

Place infra workloads with:

```yaml
nodeSelector or nodePlacement -> node-role.kubernetes.io/infra: ""
tolerations -> node-role.kubernetes.io/infra=reserved:NoSchedule
```

Keep infra nodes clean by auditing them regularly.

The most common production mistake is assuming that the infra label alone protects the node. It does not. A label attracts selected workloads; a taint repels unapproved workloads.
