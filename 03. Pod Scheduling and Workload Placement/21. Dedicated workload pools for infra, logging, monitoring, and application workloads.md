# Dedicated Workload Pools for Infra, Logging, Monitoring, and Application Workloads in OpenShift

**Area:** Pod Scheduling and Workload Placement  
**Audience:** Advanced OpenShift Administration / DO380-style production operations  
**Experience level:** 10+ years Linux / Kubernetes / OpenShift administration  
**Last verified:** 2026-07-03  

---

## 1. What “dedicated workload pools” means

A **dedicated workload pool** is a group of OpenShift worker nodes intentionally reserved for a workload category, such as:

- **Infrastructure workloads:** ingress/router, internal registry, platform services, sometimes core monitoring.
- **Logging workloads:** log collectors, LokiStack, log gateway, index, querier, ingester, distributor, compactor.
- **Monitoring workloads:** Prometheus, Alertmanager, Thanos Querier, metrics-server, kube-state-metrics, OpenShift state metrics.
- **Application workloads:** business applications, tenant applications, CI/CD workloads, stateful apps, batch jobs, or special app tiers.

In production, a workload pool is not just “some nodes with a label.” A mature design normally includes:

1. **MachineSet or bare-metal capacity** for that pool.
2. **Node labels** to identify the pool.
3. **Taints** to repel unrelated workloads.
4. **Tolerations** on workloads that are allowed into the pool.
5. **nodeSelector / nodeAffinity** to attract the correct workloads to the pool.
6. **MachineConfigPool** when the pool needs different kubelet, CRI-O, sysctl, kernel, or OS-level configuration.
7. **Resource requests/limits** so the scheduler can make sane placement decisions.
8. **Topology spread / anti-affinity** so the pool remains highly available across zones or racks.
9. **Operational policy** for upgrades, capacity, monitoring, and troubleshooting.

The main purpose is to keep noisy, critical, or specialized workloads from impacting each other.

## 2. Why dedicated pools matter in real clusters

OpenShift clusters often begin with generic worker nodes. That works in small labs, but it becomes risky in production.

### 2.1 Typical production problems without workload pools

| Problem | What happens |
|---|---|
| Router competes with apps | Application CPU spikes can delay ingress/router processing. |
| Prometheus competes with apps | Monitoring becomes unstable exactly when the cluster is under load. |
| Logging consumes disk/CPU | Log collectors or Loki components can cause memory, disk, and I/O pressure. |
| App teams use infra capacity | User pods land on nodes meant for platform services. |
| Upgrades affect everything together | Worker reboots, MCO changes, or kubelet changes roll through all workloads at once. |
| Wrong scheduling rules cause Pending pods | Selectors, taints, default node selectors, and affinity rules conflict. |
| Expensive nodes are wasted | GPU, high-memory, storage-heavy, or high-IO nodes are consumed by normal pods. |

### 2.2 What a good workload-pool design gives you

- **Fault isolation:** logging failure should not take down apps; app load should not starve monitoring.
- **Cost control:** infra nodes can be sized differently from application nodes.
- **Support clarity:** node purpose is visible from labels, roles, MCPs, and pod placement.
- **Security and tenancy control:** app projects can be forced onto application nodes only.
- **Upgrade control:** custom MachineConfigPools allow staged, pool-specific rollout.
- **Performance control:** monitoring and logging can get storage/CPU tuned nodes.

## 3. Scheduling mental model: label selects, taint repels, toleration permits

A senior admin must be very clear on these four concepts:

### 3.1 Node label

A label is metadata on the node:

```bash
oc label node worker-0 workload.openshift.io/pool=apps --overwrite
oc label node infra-0 node-role.kubernetes.io/infra="" workload.openshift.io/pool=infra --overwrite
```

Labels are used by `nodeSelector`, node affinity, MachineConfigPool node selection, monitoring configs, logging configs, and many Operator placement settings.

### 3.2 nodeSelector

A `nodeSelector` says: “Only schedule this pod on nodes with these labels.”

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload.openshift.io/pool: apps
```

If no node matches the selector, the pod remains `Pending`.

### 3.3 Taint

A taint says: “Do not schedule pods here unless they tolerate this taint.”

```bash
oc adm taint nodes -l workload.openshift.io/pool=infra \
  node-role.kubernetes.io/infra=reserved:NoSchedule --overwrite
```

A taint does **not** attract pods. It only repels pods that do not tolerate it.

### 3.4 Toleration

A toleration says: “This pod is allowed to run on a node with this taint.”

```yaml
spec:
  template:
    spec:
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Equal
        value: reserved
        effect: NoSchedule
```

A toleration does **not** force the pod onto that node. To reserve a pool properly, you normally use:

- **nodeSelector or nodeAffinity** to attract the pod to the correct pool.
- **taint** to repel unrelated pods.
- **toleration** to allow approved pods onto the tainted pool.

### 3.5 Required rule of thumb

```text
nodeSelector/nodeAffinity = where the pod wants to go
Taint = who is blocked from this node
Toleration = who is allowed through the block
Resource requests = whether there is enough schedulable capacity
Topology spread/anti-affinity = how replicas are distributed
```

## 4. Pool types and recommended intent

### 4.1 Control plane pool

Control plane nodes run API server, etcd, scheduler, controller manager, and control plane Operators.

Do not use control plane nodes as a general workload pool unless you are in a compact / single-node / special architecture with explicit support and sizing.

Common control plane labels and taints:

```text
node-role.kubernetes.io/master
node-role.kubernetes.io/control-plane
node-role.kubernetes.io/master:NoSchedule
```

### 4.2 Infrastructure pool

Infra nodes are for OpenShift platform infrastructure components, such as:

- default router / ingress controller
- integrated image registry
- monitoring stack components
- cluster logging / log aggregation components
- selected platform Operators or platform services

OpenShift documentation recommends preserving the dual `infra,worker` role label for infrastructure nodes and using taints/tolerations to prevent normal user workload placement. Removing the `worker` label requires a custom MachineConfigPool because the Machine Config Operator recognizes nodes through supported role labels and pools.

Example infra node identity:

```bash
oc label node infra-0 node-role.kubernetes.io/infra="" --overwrite
oc label node infra-0 node-role.kubernetes.io/worker="" --overwrite
oc label node infra-0 workload.openshift.io/pool=infra --overwrite

oc adm taint node infra-0 node-role.kubernetes.io/infra=reserved:NoSchedule --overwrite
```

Expected role output:

```bash
oc get nodes

NAME      STATUS   ROLES          AGE   VERSION
infra-0   Ready    infra,worker   10d   v1.32.x
```

### 4.3 Logging pool

A logging pool is used when logging is large enough to deserve its own failure and performance boundary.

Use it for:

- LokiStack read/write components
- high-throughput log processing
- log gateway/query components
- indexing and compaction components
- dedicated log storage nodes

Important production nuance:

- **Collectors are usually DaemonSet-style components that collect logs from nodes where they run.**
- If you restrict collectors only to logging nodes, you might collect logs only from those nodes.
- For full-cluster collection, collectors generally need to run on all eligible nodes and tolerate required taints.
- LokiStack storage/query components can be placed on dedicated logging nodes separately.

### 4.4 Monitoring pool

Monitoring can be split into:

- **Core platform monitoring:** cluster monitoring in `openshift-monitoring`.
- **User workload monitoring:** monitoring for user-defined projects in `openshift-user-workload-monitoring`.

Monitoring is CPU, memory, and storage sensitive. Prometheus TSDB can become I/O heavy. Alertmanager and Thanos Querier are less storage-heavy but still critical.

Use a dedicated monitoring pool when:

- Prometheus retention is high.
- Many ServiceMonitors/PodMonitors exist.
- The cluster has many namespaces, pods, endpoints, or alerts.
- Monitoring stability is business-critical.
- App teams create unpredictable metrics cardinality.

### 4.5 Application pool

Application pools are for normal tenant workloads.

Common patterns:

- `apps-general`: normal stateless workloads
- `apps-stateful`: databases, queues, storage-heavy apps
- `apps-batch`: CronJobs, CI runners, batch workers
- `apps-gold`: critical apps with higher CPU/memory nodes
- `apps-gpu`: GPU workloads
- `apps-edge`: low-latency or locality-sensitive apps

For most clusters, the general app pool is **not tainted**. Instead, infra/logging/monitoring pools are tainted so apps naturally land on the untainted app workers.

## 5. Reference architecture

A practical HA cluster design:

```text
Control plane pool
  master-0, master-1, master-2
  Purpose: API, etcd, scheduler, controllers

Infra pool
  infra-a, infra-b, infra-c
  Labels: node-role.kubernetes.io/infra="", workload.openshift.io/pool=infra
  Taint:  node-role.kubernetes.io/infra=reserved:NoSchedule
  Purpose: ingress, registry, selected platform services

Monitoring pool
  mon-a, mon-b, mon-c
  Labels: workload.openshift.io/pool=monitoring
  Taint:  workload.openshift.io/monitoring=reserved:NoSchedule
  Purpose: Prometheus, Alertmanager, Thanos, metrics components

Logging pool
  log-a, log-b, log-c
  Labels: workload.openshift.io/pool=logging
  Taint:  workload.openshift.io/logging=reserved:NoSchedule
  Purpose: LokiStack, log storage/query/ingest components

Application pool
  app-a, app-b, app-c, app-d, app-e, app-f
  Labels: workload.openshift.io/pool=apps
  Taint: normally none
  Purpose: application namespaces and tenant workloads
```

For multi-zone clusters, place at least one node from each critical pool in each zone:

```text
zone-a: infra-a, mon-a, log-a, app-a, app-b
zone-b: infra-b, mon-b, log-b, app-c, app-d
zone-c: infra-c, mon-c, log-c, app-e, app-f
```

Do not design a three-replica Prometheus, router, or Loki component layout if all replicas can land in one zone. Use topology spread or anti-affinity where the Operator supports it.

## 6. Naming and label strategy

Use labels that are meaningful, stable, and easy to query.

### 6.1 Recommended labels

```text
workload.openshift.io/pool=infra
workload.openshift.io/pool=logging
workload.openshift.io/pool=monitoring
workload.openshift.io/pool=apps
workload.openshift.io/tier=gold
workload.openshift.io/tier=silver
workload.openshift.io/storage=local-nvme
workload.openshift.io/network=high-throughput
```

For infra nodes, also use the standard role label:

```text
node-role.kubernetes.io/infra=""
node-role.kubernetes.io/worker=""
```

### 6.2 Recommended taints

```text
node-role.kubernetes.io/infra=reserved:NoSchedule
workload.openshift.io/logging=reserved:NoSchedule
workload.openshift.io/monitoring=reserved:NoSchedule
workload.openshift.io/gpu=reserved:NoSchedule
workload.openshift.io/stateful=reserved:NoSchedule
```

Use `NoSchedule` for reservation. Use `NoExecute` carefully because it can evict existing pods.

### 6.3 Avoid weak labels

Avoid labels like:

```text
node=infra
type=app
role=prod
```

They are too generic and can collide with application labels, user labels, or future automation.

## 7. Building pools with MachineSets

On cloud IPI clusters, create dedicated MachineSets for each pool. The exact `providerSpec` differs by platform, but the scheduling-related structure is similar.

### 7.1 Infra MachineSet skeleton

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: cluster-infra-zone-a
  namespace: openshift-machine-api
spec:
  replicas: 1
  selector:
    matchLabels:
      machine.openshift.io/cluster-api-machineset: cluster-infra-zone-a
      machine.openshift.io/cluster-api-cluster: <infra-id>
  template:
    metadata:
      labels:
        machine.openshift.io/cluster-api-machineset: cluster-infra-zone-a
        machine.openshift.io/cluster-api-cluster: <infra-id>
    spec:
      metadata:
        labels:
          node-role.kubernetes.io/worker: ""
          node-role.kubernetes.io/infra: ""
          workload.openshift.io/pool: infra
      taints:
      - key: node-role.kubernetes.io/infra
        value: reserved
        effect: NoSchedule
      providerSpec:
        value:
          # Cloud-specific providerSpec here
          # AWS, Azure, GCP, vSphere, OpenStack, etc. differ.
```

## 8. Building pools on existing nodes

If machines already exist, label and taint them directly.

### 8.1 Label nodes

```bash
# Infra
oc label node worker-0 node-role.kubernetes.io/infra="" --overwrite
oc label node worker-0 workload.openshift.io/pool=infra --overwrite

# Logging
oc label node worker-1 workload.openshift.io/pool=logging --overwrite

# Monitoring
oc label node worker-2 workload.openshift.io/pool=monitoring --overwrite

# Apps
oc label node worker-3 workload.openshift.io/pool=apps --overwrite
oc label node worker-4 workload.openshift.io/pool=apps --overwrite
```

### 8.2 Taint reserved nodes

```bash
# Reserve infra nodes
oc adm taint nodes -l workload.openshift.io/pool=infra \
  node-role.kubernetes.io/infra=reserved:NoSchedule --overwrite

# Reserve logging nodes
oc adm taint nodes -l workload.openshift.io/pool=logging \
  workload.openshift.io/logging=reserved:NoSchedule --overwrite

# Reserve monitoring nodes
oc adm taint nodes -l workload.openshift.io/pool=monitoring \
  workload.openshift.io/monitoring=reserved:NoSchedule --overwrite
```

### 8.3 Verify labels and taints

```bash
oc get nodes -L node-role.kubernetes.io/infra,workload.openshift.io/pool
oc describe node worker-0 | egrep -A8 "Labels:|Taints:"
```

### 8.4 Remove a taint if required

```bash
oc adm taint node worker-0 node-role.kubernetes.io/infra=reserved:NoSchedule-
oc adm taint node worker-1 workload.openshift.io/logging=reserved:NoSchedule-
```

## 9. MachineConfigPool design

A **MachineConfigPool (MCP)** is not the same thing as a scheduler pool.

| Concept | Purpose |
|---|---|
| Node label | Identifies node properties. |
| Taint | Reserves node by repelling pods. |
| nodeSelector / affinity | Schedules pods onto matching nodes. |
| MachineSet | Creates machines/nodes. |
| MachineConfigPool | Applies OS/kubelet/CRI-O/MCO configuration to selected nodes. |

Use a custom MCP when a pool needs different host-level configuration, for example:

- different kubelet `maxPods`
- different container log size
- custom kernel arguments
- huge pages
- tuned profiles
- special CRI-O config
- special storage or networking host configuration

### 9.1 Infra MCP example

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: infra
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - infra
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/infra: ""
```

### 9.2 Logging MCP example

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: logging
  labels:
    pools.operator.machineconfiguration.openshift.io/logging: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - logging
  nodeSelector:
    matchLabels:
      workload.openshift.io/pool: logging
```

### 9.3 Monitoring MCP example

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: monitoring
  labels:
    pools.operator.machineconfiguration.openshift.io/monitoring: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - monitoring
  nodeSelector:
    matchLabels:
      workload.openshift.io/pool: monitoring
```

### 9.4 App MCP example

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: apps
  labels:
    pools.operator.machineconfiguration.openshift.io/apps: ""
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - apps
  nodeSelector:
    matchLabels:
      workload.openshift.io/pool: apps
```

### 9.5 KubeletConfig targeted to app pool

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: apps-kubelet-config
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/apps: ""
  kubeletConfig:
    maxPods: 250
    podsPerCore: 0
    containerLogMaxSize: 50Mi
    containerLogMaxFiles: 5
```

Production warning: kubelet configs that target broad worker pools can also affect dependent custom pools. Prefer explicit MCP selectors when you want pool-specific behavior.

### 9.6 Verify MCP health

```bash
oc get mcp
oc describe mcp infra
oc describe mcp logging
oc describe mcp monitoring
oc describe mcp apps
```

Healthy state should show:

```text
UPDATED=True
UPDATING=False
DEGRADED=False
```

## 10. Moving infrastructure workloads to infra nodes

### 10.1 Move the default IngressController/router

```bash
oc edit ingresscontroller default -n openshift-ingress-operator
```

Add:

```yaml
spec:
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoSchedule
```

Verify:

```bash
oc get pods -n openshift-ingress -o wide
oc get nodes -L node-role.kubernetes.io/infra,workload.openshift.io/pool
```

Expected: `router-default-*` pods run on `infra,worker` nodes.

### 10.2 Move the integrated image registry

```bash
oc edit configs.imageregistry.operator.openshift.io/cluster
```

Add or adjust:

```yaml
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
  tolerations:
  - key: node-role.kubernetes.io/infra
    value: reserved
    effect: NoSchedule
```

Verify:

```bash
oc get pods -n openshift-image-registry -o wide
```

### 10.3 Infra workload checklist

After moving infra workloads:

```bash
oc get pods -n openshift-ingress -o wide
oc get pods -n openshift-image-registry -o wide
oc get co ingress image-registry
oc describe node <infra-node> | egrep -A8 "Allocated resources|Taints|Labels"
```

Check:

- Router replicas are spread across infra nodes.
- Registry pod can mount storage.
- Load balancer health checks still pass.
- Routes work after router movement.
- Infra nodes have spare CPU and memory.

### 11.4 Do not blindly move every monitoring component

Some components, such as `nodeExporter`, are DaemonSet-style and exist to observe nodes. If you constrain them too aggressively, you can lose visibility. Always check the current monitoring CRD/config reference for the version you operate.

### 11.5 Verify monitoring placement

```bash
watch 'oc get pods -n openshift-monitoring -o wide'
oc get pods -n openshift-monitoring -o wide | egrep 'prometheus|alertmanager|thanos|metrics|state'
oc describe pod -n openshift-monitoring <pod-name> | sed -n '/Node-Selectors/,/Events/p'
oc get events -n openshift-monitoring --sort-by=.lastTimestamp
```

If pods stay `Pending`, check:

```bash
oc describe pod -n openshift-monitoring <pod-name>
oc get nodes -L workload.openshift.io/pool,node-role.kubernetes.io/infra
oc describe node <target-node> | grep -i taints -A3
```

Common causes:

- Target nodes do not have the label.
- ConfigMap indentation is wrong under `data.config.yaml`.
- Taint exists but toleration is missing.
- Prometheus PVC is zone-bound and cannot attach to selected node.
- Requested CPU/memory is larger than available allocatable capacity.

## 12. User workload monitoring placement

User workload monitoring is configured through:

```text
Namespace: openshift-user-workload-monitoring
ConfigMap: user-workload-monitoring-config
```

Create or edit:

```bash
oc -n openshift-user-workload-monitoring get configmap user-workload-monitoring-config
oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
```

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      nodeSelector:
        workload.openshift.io/pool: monitoring
      tolerations:
      - key: workload.openshift.io/monitoring
        value: reserved
        effect: NoSchedule
    thanosRuler:
      nodeSelector:
        workload.openshift.io/pool: monitoring
      tolerations:
      - key: workload.openshift.io/monitoring
        value: reserved
        effect: NoSchedule
```

Version nuance: OpenShift monitoring documentation can differ between core platform monitoring and user workload monitoring. Always verify valid component names and placement restrictions in your installed cluster:

```bash
oc explain cm.data -n openshift-user-workload-monitoring
oc get cm user-workload-monitoring-config -n openshift-user-workload-monitoring -o yaml
oc get pods -n openshift-user-workload-monitoring -o wide
```

## 13. Moving logging workloads

OpenShift Logging has two placement categories:

1. **Collectors** configured through `ClusterLogForwarder`.
2. **LokiStack components** configured through `LokiStack.spec.template`.

### 13.1 Collector placement with ClusterLogForwarder

Example: schedule collectors on infra nodes and allow infra taints:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  collector:
    nodeSelector:
      node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Exists
      effect: NoSchedule
    - key: node-role.kubernetes.io/infra
      operator: Exists
      effect: NoExecute
```

Example: allow collectors to run on infra, monitoring, and logging tainted nodes:

```yaml
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  collector:
    tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Exists
      effect: NoSchedule
    - key: workload.openshift.io/logging
      operator: Exists
      effect: NoSchedule
    - key: workload.openshift.io/monitoring
      operator: Exists
      effect: NoSchedule
    resources:
      requests:
        cpu: 100m
        memory: 1Gi
      limits:
        memory: 2Gi
```

Production warning: Do not restrict collectors to only the logging pool unless that is intentional. A collector normally needs to run where logs are produced.

### 13.2 LokiStack placement

Example: move Loki components to logging nodes:

```yaml
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  template:
    compactor:
      nodeSelector:
        workload.openshift.io/pool: logging
      tolerations:
      - key: workload.openshift.io/logging
        value: reserved
        effect: NoSchedule
    distributor:
      nodeSelector:
        workload.openshift.io/pool: logging
      tolerations:
      - key: workload.openshift.io/logging
        value: reserved
        effect: NoSchedule
    gateway:
      nodeSelector:
        workload.openshift.io/pool: logging
      tolerations:
      - key: workload.openshift.io/logging
        value: reserved
        effect: NoSchedule
    indexGateway:
      nodeSelector:
        workload.openshift.io/pool: logging
      tolerations:
      - key: workload.openshift.io/logging
        value: reserved
        effect: NoSchedule
    ingester:
      nodeSelector:
        workload.openshift.io/pool: logging
      tolerations:
      - key: workload.openshift.io/logging
        value: reserved
        effect: NoSchedule
    querier:
      nodeSelector:
        workload.openshift.io/pool: logging
      tolerations:
      - key: workload.openshift.io/logging
        value: reserved
        effect: NoSchedule
    queryFrontend:
      nodeSelector:
        workload.openshift.io/pool: logging
      tolerations:
      - key: workload.openshift.io/logging
        value: reserved
        effect: NoSchedule
    ruler:
      nodeSelector:
        workload.openshift.io/pool: logging
      tolerations:
      - key: workload.openshift.io/logging
        value: reserved
        effect: NoSchedule
```

### 13.3 Logging HA across zones

For Loki, use the Operator-supported zone/replication/topology options for your installed version. A practical intent is:

```text
Loki ingesters: spread across zones
Loki queriers: spread across zones
Loki distributors: spread across zones
Loki gateway: spread across zones
Compactor: place carefully, usually fewer replicas
```

Use `oc explain` before editing complex CRs:

```bash
oc explain lokistack.spec.template
oc explain lokistack.spec.template.ingester
oc explain lokistack.spec.template.compactor
```

### 13.4 Verify logging placement

```bash
oc get pods -n openshift-logging -o wide
oc get pods -n openshift-logging --selector component=collector -o wide
oc get lokistack logging-loki -n openshift-logging -o yaml
oc describe pod -n openshift-logging <pod-name> | sed -n '/Node-Selectors/,/Events/p'
```

Common logging placement failures:

| Symptom | Likely cause | Fix |
|---|---|---|
| Collector Pending | Tainted node without toleration | Add matching toleration to `ClusterLogForwarder`. |
| Loki pod Pending | Node selector points to missing label | Correct node label or LokiStack selector. |
| Loki PVC Pending | StorageClass topology does not match selected node | Align storage zone, PVC, and node pool. |
| Collectors missing app logs | Collector restricted to wrong nodes | Remove restrictive nodeSelector or run collectors on app nodes. |
| High collector restart count | Insufficient memory under high log volume | Increase collector memory request/limit. |

## 14. Keeping application workloads on application nodes

### 14.1 Use project-level node selectors

For application namespaces, use the OpenShift namespace annotation:

```bash
oc adm new-project payments --node-selector="workload.openshift.io/pool=apps"
```

For an existing namespace:

```bash
oc annotate namespace payments \
  openshift.io/node-selector='workload.openshift.io/pool=apps' --overwrite
```

Verify:

```bash
oc get namespace payments -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
```

### 14.2 Deployment-level selector

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
  namespace: payments
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      nodeSelector:
        workload.openshift.io/pool: apps
      containers:
      - name: api
        image: registry.example.com/payments/api:v1
        resources:
          requests:
            cpu: 250m
            memory: 512Mi
          limits:
            cpu: "1"
            memory: 1Gi
```

### 14.3 App pool with topology spread

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
spec:
  replicas: 6
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      nodeSelector:
        workload.openshift.io/pool: apps
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: payments-api
      containers:
      - name: api
        image: registry.example.com/payments/api:v1
        resources:
          requests:
            cpu: 250m
            memory: 512Mi
```

### 14.4 Dedicated tenant app pool

For a regulated or critical tenant:

```bash
oc label node app-gold-0 workload.openshift.io/pool=apps-gold --overwrite
oc label node app-gold-1 workload.openshift.io/pool=apps-gold --overwrite

oc adm taint nodes -l workload.openshift.io/pool=apps-gold \
  workload.openshift.io/apps-gold=reserved:NoSchedule --overwrite
```

Deployment:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload.openshift.io/pool: apps-gold
      tolerations:
      - key: workload.openshift.io/apps-gold
        operator: Equal
        value: reserved
        effect: NoSchedule
```

### 14.5 Cluster-wide default node selector: use carefully

You can set a cluster-wide default node selector through the Scheduler object:

```bash
oc patch scheduler cluster --type=merge \
  -p '{"spec":{"defaultNodeSelector":"workload.openshift.io/pool=apps"}}'
```

Be careful. A cluster-wide default selector can affect pods that do not explicitly set compatible selectors. Project-level selectors are usually safer for tenant workloads.

### 14.6 DaemonSet warning

DaemonSets can behave badly with default project-wide node selectors if selectors are merged in unexpected ways. For DaemonSet-heavy namespaces, disable the namespace default selector if required:

```bash
oc patch namespace myproject -p \
  '{"metadata":{"annotations":{"openshift.io/node-selector":""}}}'
```

## 15. Capacity planning for each pool

Dedicated pools fail when they are designed only with labels and not with capacity.

### 15.1 Infra pool sizing

Consider:

- router replicas and route traffic
- TLS termination CPU
- HAProxy memory
- registry storage and pull/push rate
- router disruption during node maintenance
- cross-zone load balancer behavior

Minimum production thought process:

```text
Infra nodes: at least 3 for HA across zones/racks
Router replicas: at least 2, preferably zone-spread
Registry: storage must be accessible from selected infra nodes
CPU headroom: keep spare for route spikes
```

### 15.2 Monitoring pool sizing

Consider:

- number of pods, services, endpoints, namespaces
- scrape interval and scrape timeout
- metric cardinality
- Prometheus retention time and retention size
- remote write overhead
- Thanos query concurrency
- alert rule count

Useful checks:

```bash
oc adm top pods -n openshift-monitoring
oc adm top nodes
oc get pvc -n openshift-monitoring
oc get pods -n openshift-monitoring -o wide
```

### 15.3 Logging pool sizing

Consider:

- log volume per node
- burst rate during incidents
- application logging behavior
- collector memory
- Loki ingester memory
- object storage or local storage performance
- compaction overhead
- retention period

Useful checks:

```bash
oc adm top pods -n openshift-logging
oc get pods -n openshift-logging -o wide
oc get pvc -n openshift-logging
oc logs -n openshift-logging <collector-pod>
```

### 15.4 Application pool sizing

Consider:

- namespace quotas
- LimitRanges
- app requests/limits accuracy
- HPA behavior
- VPA recommendations if used
- PDBs during drain
- anti-affinity rules
- storage topology

Useful checks:

```bash
oc adm top nodes -l workload.openshift.io/pool=apps
oc get pods -A -o wide | grep -v openshift
oc get resourcequota -A
oc get limitrange -A
```

| Workload | Preferred pool | Selector | Toleration | Notes |
|---|---|---|---|---|
| Router / ingress | infra | `node-role.kubernetes.io/infra` | infra taint | Use IngressController `nodePlacement`. |
| Image registry | infra | `node-role.kubernetes.io/infra` | infra taint | Check storage after move. |
| Core Prometheus | monitoring or infra | pool label | pool taint | Use `cluster-monitoring-config`. |
| Alertmanager | monitoring or infra | pool label | pool taint | Spread replicas. |

## 17. Troubleshooting placement problems

### 17.1 Fast triage command set

```bash
# See node pool labels
oc get nodes -L node-role.kubernetes.io/infra,workload.openshift.io/pool,topology.kubernetes.io/zone

# See taints
for n in $(oc get nodes -o name); do
  echo "### $n"
  oc describe $n | grep -i "Taints:" -A2
Done

# See all pod placement
oc get pods -A -o wide

# Failed scheduling events
oc get events -A --field-selector reason=FailedScheduling --sort-by=.lastTimestamp

# Describe a pending pod
oc describe pod <pod-name> -n <namespace>

# Check MCP health
oc get mcp
```

Note: If your shell copy fails because of `Done`, use lowercase `done`:

```bash
for n in $(oc get nodes -o name); do
  echo "### $n"
  oc describe $n | grep -i "Taints:" -A2
done
```

### 17.2 Common scheduler errors

#### Error: node(s) didn't match Pod's node affinity/selector

Meaning:

- `nodeSelector` or required node affinity points to a label no node has.

Check:

```bash
oc describe pod <pod> -n <ns>
oc get nodes --show-labels | grep '<label-key>'
```

Fix:

```bash
oc label node <node> workload.openshift.io/pool=apps --overwrite
```

Or update the workload selector.

#### Error: node(s) had untolerated taint

Meaning:

- The pod selected the node, but the node has a taint the pod does not tolerate.

Check:

```bash
oc describe node <node> | grep -i Taints -A3
oc get pod <pod> -n <ns> -o yaml | yq '.spec.tolerations'
```

Fix:

Add a matching toleration or remove the taint if the reservation is wrong.

#### Error: Insufficient cpu / Insufficient memory

Meaning:

- Labels and taints are correct, but allocatable capacity is insufficient for the pod requests.

Check:

```bash
oc describe node <node> | sed -n '/Allocated resources/,$p'
oc adm top node
oc adm top pod -A
```

Fix:

- Add nodes to the pool.
- Reduce requests if they are inflated.
- Move workloads.
- Scale noncritical workloads down.

#### Error: volume node affinity conflict

Meaning:

- The pod selected nodes in one zone, but its PV/PVC is bound to another zone.

Check:

```bash
oc get pvc -n <ns>
oc describe pvc <pvc> -n <ns>
oc describe pv <pv>
oc get nodes -L topology.kubernetes.io/zone
```

Fix:

- Align storage class topology with selected node pool.
- Recreate PVC in correct zone if acceptable.
- Use a storage backend that supports the required topology.

## 18. Upgrade and maintenance behavior

Dedicated pools must be designed for maintenance.

### 18.1 MachineConfigPool upgrades

During MCO changes, nodes can be drained and rebooted by pool. Custom MCPs let you separate changes:

```bash
oc get mcp
oc describe mcp infra
oc describe mcp logging
oc describe mcp monitoring
oc describe mcp apps
```

Set appropriate `maxUnavailable` if supported and appropriate:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: logging
spec:
  maxUnavailable: 1
```

### 18.2 PDBs and drains

A pool with three nodes can still suffer downtime if all replicas are on one node or if PDBs block drains.

Check:

```bash
oc get pdb -A
oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --dry-run=server
```

### 18.3 Descheduler interaction

If the descheduler is enabled, pods that violate node taints or placement strategy can be evicted. This is useful but dangerous if your selectors/tolerations are inconsistent.

Before enabling aggressive descheduler profiles, verify:

```bash
oc get pods -A -o wide
oc get nodes --show-labels
oc describe node <node> | grep -i taints -A3
```

## 19. Security and governance model

### 19.1 Prevent app teams from bypassing pools

Do not give normal project users permission to edit node labels, taints, or cluster-scoped scheduler settings.

Use:

- RBAC
- project templates
- namespace node selectors
- admission policies where required
- ResourceQuota and LimitRange
- controlled Operator configuration

### 19.2 Project template idea

A project template can enforce default app placement:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  annotations:
    openshift.io/node-selector: workload.openshift.io/pool=apps
```

This helps ensure new projects do not accidentally run on infra, logging, or monitoring nodes.

### 19.3 Do not add infra tolerations to app workloads

This is a common production mistake:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
```

If app teams add this, their pods may run on infra nodes when there is pressure elsewhere. Keep infra tolerations restricted to platform-managed workloads.

## 21. Production anti-patterns

### Anti-pattern 1: Only labels, no taints

If infra nodes only have labels but no taints, normal pods can still land there if they have no restrictive selectors.

Better:

```bash
oc label node infra-0 node-role.kubernetes.io/infra="" --overwrite
oc adm taint node infra-0 node-role.kubernetes.io/infra=reserved:NoSchedule --overwrite
```

### Anti-pattern 2: Tolerations without selectors

A pod with only toleration can run anywhere, including the tainted pool. It is allowed but not directed.

Better:

```yaml
nodeSelector:
  workload.openshift.io/pool: monitoring
tolerations:
- key: workload.openshift.io/monitoring
  value: reserved
  effect: NoSchedule
```

### Anti-pattern 3: Removing `worker` label from infra nodes without MCP design

This can leave nodes unmanaged by the expected MachineConfigPool unless a correct custom MCP exists.

Better:

```text
Keep infra nodes as infra,worker.
Use taints/tolerations to reserve them.
Create custom MCP only when needed.
```

### Anti-pattern 4: One infra node

One infra node is not HA. If it drains, router or registry can be disrupted.

Better:

```text
Minimum: 2 infra nodes
Recommended production HA: 3 infra nodes across zones/racks
```

### Anti-pattern 5: Logging collectors only on logging nodes

If collectors only run on logging nodes, they might not collect application logs from app nodes.

Better:

```text
Run collectors on log-producing nodes.
Place LokiStack storage/query components on logging pool.
```

### Anti-pattern 6: Cluster-wide default node selector without testing Operators

A global default selector can break system or Operator pods that do not expect it.

Better:

```text
Use project-level selectors for application namespaces.
Use Operator-specific placement fields for platform components.
```

## 23. Interview / exam-style explanation

A good senior-level answer:

> In OpenShift, I design dedicated workload pools by combining node labels, taints, tolerations, selectors, and sometimes MachineConfigPools. Infra nodes should normally keep both `infra` and `worker` roles, with a taint such as `node-role.kubernetes.io/infra=reserved:NoSchedule`. Platform components like ingress, registry, and core monitoring are moved using their Operator-supported placement fields. Logging is split carefully: LokiStack components can run on dedicated logging nodes, but collectors usually need to run on all log-producing nodes. Monitoring can be placed through `cluster-monitoring-config`, with selectors and tolerations. Application namespaces are kept on app workers using project-level node selectors or workload selectors. I always validate with `oc get pods -A -o wide`, pod events, node labels, taints, MCP state, and resource pressure. The key is that toleration only permits scheduling; it does not attract a pod, so it must be paired with selectors or affinity.

## 26. Final senior-admin takeaways

- A dedicated pool is a scheduling and operations boundary, not only a node label.
- Keep infra nodes as `infra,worker` unless you intentionally build a custom MCP design.
- Taint reserved pools; otherwise normal pods can still land there.
- A toleration does not attract a pod; pair it with `nodeSelector` or node affinity.
- Put app namespaces on app nodes with project-level node selectors.
- Move ingress, registry, monitoring, logging through Operator-supported placement APIs, not by editing generated pods.
- Be careful with logging collectors: they must run where logs are produced.
