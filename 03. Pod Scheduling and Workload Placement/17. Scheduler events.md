# Scheduler Events in OpenShift: Advanced Pod Scheduling and Workload Placement Guide

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and Kubernetes/OpenShift support engineers with production experience.  
**Topic area:** Pod Scheduling and Workload Placement  
**Focus:** Understanding, interpreting, and troubleshooting scheduler events in OpenShift Container Platform.

---

## 1. Executive Summary

Scheduler events are one of the fastest ways to understand **why a pod is scheduled, why it remains Pending, why preemption occurred, or why the scheduler rejected every available node**. In OpenShift, these events usually appear on the pod object and are visible through `oc describe pod`, `oc get events`, the web console, and event-forwarding/observability systems.

For an experienced OpenShift administrator, scheduler events are not just messages. They are a condensed view of the scheduler decision process:

1. The pod is created and has no `spec.nodeName`.
2. The default scheduler watches the pod.
3. The scheduler filters nodes that cannot run the pod.
4. It scores feasible nodes.
5. It binds the pod to the best node.
6. It emits events such as `Scheduled`, `FailedScheduling`, or `Preempted`.

The most important scheduler event for troubleshooting is usually:

```text
Warning  FailedScheduling  default-scheduler  0/6 nodes are available: ...
```

That single line often tells you whether the issue is related to resources, taints, node selectors, affinity, topology spread, PVC binding, node readiness, unschedulable nodes, or preemption.

---

## 2. What Are Scheduler Events?

A Kubernetes/OpenShift event is a short-lived API object that reports something meaningful about a cluster object. Scheduler events are events reported by the scheduler component, commonly `default-scheduler`, about pod placement decisions.

In OpenShift, scheduler events commonly answer questions such as:

- Was the pod assigned to a node?
- Which node was selected?
- Why did scheduling fail?
- Did preemption happen?
- Would preemption help?
- Is the pod blocked by taints, labels, resource pressure, affinity, topology spread, or storage constraints?

Scheduler events are especially important when a pod is stuck in:

```text
STATUS: Pending
```

A pod can be Pending for two broad reasons:

1. **The pod has not been scheduled to a node yet.**  
   This is where scheduler events are most useful.

2. **The pod has been scheduled, but containers are not yet running.**  
   This usually moves troubleshooting toward image pull, kubelet, CNI, CSI, SCC, runtime, or container startup events.

The first check is therefore:

```bash
oc get pod <pod-name> -n <namespace> -o wide
```

If `NODE` is empty, the pod is not scheduled yet.

If `NODE` has a value, scheduling is already complete and you should continue with kubelet, image, volume, or runtime troubleshooting.

## 3. How the OpenShift Scheduler Works Internally

OpenShift uses Kubernetes scheduling concepts and provides cluster-level configuration through OpenShift APIs and Operators. The default scheduler is responsible for placing new pods onto nodes. It watches for pods without a node assignment and creates a binding between the pod and a selected node.

At a high level, the scheduler follows this model:

```text
Pod created
   |
   v
Scheduler sees unscheduled pod
   |
   v
Filter phase: remove nodes that cannot run the pod
   |
   v
Score phase: rank feasible nodes
   |
   v
Reserve / assume / volume checks
   |
   v
Bind pod to selected node
   |
   v
Emit Scheduled event
```

If no node passes the filtering phase, the scheduler emits `FailedScheduling`.

If a higher-priority pod cannot fit and lower-priority pods might be removed to make space, preemption logic may run. Depending on the outcome, you might see messages such as:

```text
preemption: 0/5 nodes are available: 5 Preemption is not helpful for scheduling.
```

or events on victim pods showing they were preempted.

## 4. Important Scheduler Event Types

OpenShift documentation commonly identifies these scheduler event reasons:

| Event Reason | Type | Meaning | Typical Location |
|---|---:|---|---|
| `Scheduled` | Normal | The scheduler successfully assigned the pod to a node. | Pod events |
| `FailedScheduling` | Warning | The scheduler could not find a suitable node or failed during binding/volume assumptions. | Pod events |
| `Preempted` | Normal or Warning depending on context | A pod was preempted by a higher-priority pod. | Usually victim pod events |

### 4.1 `Scheduled`

Example:

```text
Normal  Scheduled  default-scheduler  Successfully assigned prod/api-78d9f7d9b7-kx8q2 to worker-2.example.com
```

Meaning:

- The scheduler found at least one feasible node.
- It selected a node after scoring.
- It created a binding for the pod.
- The pod now has `spec.nodeName` set.

Check:

```bash
oc get pod api-78d9f7d9b7-kx8q2 -n prod -o jsonpath='{.spec.nodeName}{"\n"}'
```

After this point, if the pod is still not Running, the scheduler has already done its job. Continue with:

```bash
oc describe pod <pod> -n <namespace>
oc logs <pod> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

### 4.2 `FailedScheduling`

Example:

```text
Warning  FailedScheduling  default-scheduler  0/4 nodes are available: 2 Insufficient cpu, 1 node(s) had untolerated taint {dedicated: infra}, 1 node(s) didn't match Pod's node affinity/selector. preemption: 0/4 nodes are available: 2 No preemption victims found for incoming pod, 2 Preemption is not helpful for scheduling.
```

Meaning:

- The scheduler evaluated available nodes.
- No node satisfied all hard requirements.
- The pod remains unscheduled.
- The event message lists why nodes were rejected.

This event is often repeated. Kubernetes may compact repeated events into a series with a count.

Check count and last occurrence:

```bash
oc get events -n <namespace> --field-selector reason=FailedScheduling --sort-by=.lastTimestamp
```

### 4.3 `Preempted`

Preemption happens when a high-priority pod cannot be scheduled and the scheduler tries to make room by evicting lower-priority pods.

Example:

```text
Normal  Preempted  default-scheduler  By prod/critical-api-5c949bdbd8-qzw6s on node worker-3.example.com
```

Important notes:

- Preemption is based on **PriorityClass**, not QoS alone.
- Preemption is not guaranteed to solve scheduling.
- PodDisruptionBudget is considered best-effort during scheduler preemption.
- Preempted pods receive their graceful termination period.
- A preemptor can have `status.nominatedNodeName` before it is actually bound.

Check priority:

```bash
oc get pod <pod> -n <namespace> -o jsonpath='{.spec.priorityClassName}{"\n"}{.spec.priority}{"\n"}'
```

Check nominated node:

```bash
oc get pod <pending-pod> -n <namespace> -o jsonpath='{.status.nominatedNodeName}{"\n"}'
```

## 5. Anatomy of a Scheduler Event

A scheduler event contains fields that matter during troubleshooting.

Example YAML:

```bash
oc get event -n prod <event-name> -o yaml
```

Representative structure:

```yaml
apiVersion: v1
kind: Event
metadata:
  name: api-78d9f7d9b7-kx8q2.187abcd12345
  namespace: prod
type: Warning
reason: FailedScheduling
message: >-
  0/5 nodes are available: 3 Insufficient memory,
  2 node(s) had untolerated taint {dedicated: infra}.
source:
  component: default-scheduler
involvedObject:
  kind: Pod
  namespace: prod
  name: api-78d9f7d9b7-kx8q2
firstTimestamp: "2026-07-03T06:20:10Z"
lastTimestamp: "2026-07-03T06:24:10Z"
count: 8
```

Key fields:

| Field | Meaning |
|---|---|
| `type` | `Normal` or `Warning`. Scheduling failures are usually `Warning`. |
| `reason` | Short reason such as `Scheduled`, `FailedScheduling`, `Preempted`. |
| `message` | Human-readable scheduling result. This is the most useful field. |
| `source.component` or `reportingComponent` | Usually `default-scheduler`. |
| `involvedObject` | The object the event refers to, usually a Pod. |
| `count` | Number of times this event was repeated. |
| `firstTimestamp` / `lastTimestamp` | When the event was first and last observed. |

Events are useful but should be treated as **short-lived diagnostic data**, not as a permanent audit log.

## 6. How to View Scheduler Events in OpenShift

### 6.1 Describe the pod

This is the first command for a Pending pod:

```bash
oc describe pod <pod-name> -n <namespace>
```

At the bottom, check the `Events` section:

```text
Events:
  Type     Reason            Age                 From               Message
  ----     ------            ----                ----               -------
  Warning  FailedScheduling  2m (x7 over 8m)     default-scheduler  0/3 nodes are available: 3 Insufficient cpu.
```

### 6.2 List events in a namespace

```bash
oc get events -n <namespace> --sort-by=.lastTimestamp
```

### 6.3 List only scheduling failures

```bash
oc get events -n <namespace> \
  --field-selector reason=FailedScheduling \
  --sort-by=.lastTimestamp
```

### 6.4 List scheduling events across all namespaces

```bash
oc get events -A \
  --field-selector reason=FailedScheduling \
  --sort-by=.lastTimestamp
```

### 6.5 Watch events live

```bash
oc get events -n <namespace> --watch
```

For active incidents, use one terminal for pods and one terminal for events:

```bash
watch -n2 'oc get pods -n prod -o wide'
```

```bash
oc get events -n prod --watch
```

### 6.6 Filter events for one pod

```bash
oc get events -n <namespace> \
  --field-selector involvedObject.kind=Pod,involvedObject.name=<pod-name> \
  --sort-by=.lastTimestamp
```

### 6.7 Show raw event details

```bash
oc get events -n <namespace> -o yaml
```

or:

```bash
oc get events -n <namespace> -o json | jq '.items[] | select(.reason=="FailedScheduling") | {lastTimestamp, reason, message, involvedObject}'
```

## 7. Scheduler Events vs Other Pod Events

Not all pod events are scheduler events.

| Event Source | Example Reason | Area |
|---|---|---|
| `default-scheduler` | `Scheduled`, `FailedScheduling`, `Preempted` | Node placement |
| `kubelet` | `Pulled`, `Started`, `FailedMount`, `BackOff` | Node-level pod/container lifecycle |
| `attachdetach-controller` | `FailedAttachVolume` | Volume attach/detach |
| `deployment-controller` | `ScalingReplicaSet` | Workload controller |
| `job-controller` | `SuccessfulCreate` | Job/CronJob controller |
| `cluster-autoscaler` | `NotTriggerScaleUp` | Autoscaler decision |

A practical rule:

- If `From` is `default-scheduler`, you are diagnosing **placement**.
- If `From` is `kubelet`, you are diagnosing **node execution** after placement.
- If the pod already has a node, scheduler events are usually no longer the main issue.

## 8. Reading a `FailedScheduling` Message Like a Senior Admin

A `FailedScheduling` message usually follows this pattern:

```text
0/<total-nodes> nodes are available: <count> <reason>, <count> <reason>. preemption: <details>.
```

Example:

```text
0/7 nodes are available: 2 Insufficient cpu, 2 node(s) had untolerated taint {node-role.kubernetes.io/infra: }, 2 node(s) didn't match Pod's node affinity/selector, 1 node(s) were unschedulable. preemption: 0/7 nodes are available: 2 No preemption victims found for incoming pod, 5 Preemption is not helpful for scheduling.
```

Interpretation:

| Fragment | Meaning |
|---|---|
| `0/7 nodes are available` | Scheduler evaluated 7 nodes; none passed all hard filters. |
| `2 Insufficient cpu` | Two nodes do not have enough unallocated requested CPU. |
| `untolerated taint` | Pod lacks a matching toleration for tainted nodes. |
| `didn't match Pod's node affinity/selector` | Pod has hard node placement rules that exclude nodes. |
| `were unschedulable` | Nodes are cordoned or otherwise marked unschedulable. |
| `preemption is not helpful` | Removing lower-priority pods would not make enough nodes feasible. |

Important: node rejection counts can overlap conceptually in your investigation, but the scheduler message groups reasons based on plugin/filter outcomes. Do not assume a single root cause just because one reason appears first.

## 9. Common Scheduler Event Messages and Fixes

### 9.1 `Insufficient cpu`

Example:

```text
0/4 nodes are available: 4 Insufficient cpu.
```

Meaning:

The pod's CPU **requests** cannot fit on any node based on allocatable CPU minus already requested CPU.

Check pod requests:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{range .spec.containers[*]}{.name}{" cpu="}{.resources.requests.cpu}{" memory="}{.resources.requests.memory}{"\n"}{end}'
```

Check node allocatable:

```bash
oc describe node <node> | egrep -A8 'Allocatable|Allocated resources'
```

Check all pods on a node:

```bash
oc adm top node
oc adm top pod -A --containers
```

Remember:

- Scheduling uses **requests**, not current usage.
- `oc adm top` shows usage, not requested reservation.
- A node can look idle but still reject pods because requested CPU is already reserved.

Fix options:

1. Lower unrealistic CPU requests.
2. Add more worker capacity.
3. Move workloads to appropriate node pools.
4. Use ResourceQuota and LimitRange to control request defaults.
5. Check namespace defaults that might inject high requests.
6. Review HPA/VPA behavior if present.

Example patch:

```bash
oc set resources deployment/api -n prod \
  --requests=cpu=250m,memory=512Mi \
  --limits=cpu=1,memory=1Gi
```

### 9.2 `Insufficient memory`

Example:

```text
0/5 nodes are available: 5 Insufficient memory.
```

Meaning:

No node has enough allocatable memory remaining for the pod's requested memory.

Check:

```bash
oc describe pod <pod> -n <ns> | sed -n '/Requests:/,/Limits:/p'
oc describe node <node> | egrep -A12 'Allocatable|Allocated resources'
```

Fix options:

- Correct excessive memory requests.
- Add nodes with more memory.
- Use workload isolation for memory-heavy workloads.
- Ensure LimitRange is not injecting unsuitable defaults.

### 9.3 `Too many pods`

Example:

```text
0/3 nodes are available: 3 Too many pods.
```

Meaning:

The nodes reached their maximum pod density. This can happen even when CPU/memory look available.

Check pod density:

```bash
oc get pods -A -o wide | awk '{print $8}' | sort | uniq -c | sort -nr
```

Check node pod CIDR and kubelet max pods configuration depending on cluster design.

Fix options:

- Add worker nodes.
- Reduce daemonset overhead.
- Review small sidecar-heavy deployments.
- Review MachineConfig/KubeletConfig if you intentionally manage max pods.

### 9.4 `node(s) had untolerated taint`

Example:

```text
0/6 nodes are available: 3 node(s) had untolerated taint {dedicated: infra}, 3 node(s) had untolerated taint {node-role.kubernetes.io/master: }.
```

Meaning:

The node has a taint and the pod does not have a matching toleration.

Check node taints:

```bash
oc describe node <node> | grep -i Taints -A3
```

or:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
```

Example taint:

```bash
oc adm taint nodes worker-1 dedicated=infra:NoSchedule
```

Matching toleration:

```yaml
tolerations:
- key: "dedicated"
  operator: "Equal"
  value: "infra"
  effect: "NoSchedule"
```

Fix options:

1. Add the correct toleration to workloads that are allowed on that node group.
2. Remove accidental taints.
3. Do not blindly tolerate infra/master/control-plane taints unless workload placement policy allows it.
4. Use taints plus labels together for dedicated nodes.

Remove taint:

```bash
oc adm taint nodes worker-1 dedicated=infra:NoSchedule-
```

### 9.5 `node(s) didn't match Pod's node affinity/selector`

Example:

```text
0/4 nodes are available: 4 node(s) didn't match Pod's node affinity/selector.
```

Meaning:

The pod has a hard node constraint that no node satisfies.

Sources of this constraint may include:

- `spec.nodeSelector`
- `requiredDuringSchedulingIgnoredDuringExecution` node affinity
- OpenShift project-level node selector
- OpenShift cluster default node selector
- Operator-managed placement configuration
- Helm chart values
- Deployment/Kustomize overlays

Check pod node selector:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.nodeSelector}{"\n"}'
```

Check affinity:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.affinity}{"\n"}' | jq
```

Check node labels:

```bash
oc get nodes --show-labels
```

Check project-level selector:

```bash
oc get namespace <ns> -o yaml | grep -i node-selector -A2
```

Common OpenShift annotation:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: env=prod
```

Check cluster scheduler default selector:

```bash
oc get scheduler cluster -o yaml
```

Look for:

```yaml
spec:
  defaultNodeSelector: env=prod
```

Fix options:

- Label nodes correctly:

```bash
oc label node worker-1 env=prod
```

- Correct the pod/deployment `nodeSelector`.
- Correct namespace annotation.
- Correct `Scheduler` cluster configuration.
- Avoid conflicting selectors such as project selector `env=prod` and pod selector `disk=nvme` when no node has both labels.

### 9.6 `node(s) didn't match Pod topology spread constraints`

Example:

```text
0/6 nodes are available: 6 node(s) didn't match pod topology spread constraints.
```

Meaning:

The pod has hard topology spread rules and scheduling it would violate the allowed skew across topology domains.

Check:

```bash
oc get pod <pod> -n <ns> -o jsonpath='{.spec.topologySpreadConstraints}{"\n"}' | jq
```

Common hard constraint:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: api
```

Root causes:

- Missing zone labels on nodes.
- Only one zone available but constraint expects multiple zones.
- Existing pods are unevenly distributed.
- `maxSkew` too strict.
- Label selector matches more pods than expected.
- Node selector restricts the pod to a subset of zones.

Fix options:

- Ensure nodes have correct topology labels.
- Use `ScheduleAnyway` if spread is preferred, not mandatory.
- Adjust `maxSkew`.
- Fix the label selector.
- Ensure enough eligible nodes exist in every topology domain.

### 9.7 `node(s) didn't satisfy existing pods anti-affinity rules`

Example:

```text
0/3 nodes are available: 3 node(s) didn't satisfy existing pods anti-affinity rules.
```

Meaning:

A pod anti-affinity rule blocks placement because matching pods already exist in the required topology domain.

Example hard anti-affinity:

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: api
      topologyKey: kubernetes.io/hostname
```

This says: do not place two `app=api` pods on the same hostname.

Root causes:

- Replicas exceed eligible node count.
- Topology key missing from nodes.
- Label selector too broad.
- Required anti-affinity used where preferred anti-affinity would be safer.

Fix options:

- Add eligible nodes.
- Change hard anti-affinity to preferred anti-affinity if strict separation is not required.
- Fix labels/selectors.
- Use topology spread constraints for more flexible HA placement.

### 9.8 `pod has unbound immediate PersistentVolumeClaims`

Example:

```text
0/4 nodes are available: pod has unbound immediate PersistentVolumeClaims.
```

Meaning:

The pod references a PVC that is not bound, and the storage binding mode requires the PVC to be bound before scheduling can finish.

Check PVC:

```bash
oc get pvc -n <ns>
oc describe pvc <pvc> -n <ns>
```

Check storage class:

```bash
oc get sc
oc describe sc <storageclass>
```

Important binding modes:

| Binding Mode | Scheduling Behavior |
|---|---|
| `Immediate` | PVC is bound before pod scheduling. If no PV/provisioning is available, pod remains Pending. |
| `WaitForFirstConsumer` | PVC binding waits until scheduler chooses a node, useful for topology-aware storage. |

Root causes:

- StorageClass missing.
- Dynamic provisioner not working.
- PVC requests too much storage.
- Access mode unsupported.
- No matching PV exists.
- CSI driver not healthy.
- Volume topology conflicts.

Fix options:

```bash
oc get pods -n openshift-cluster-csi-drivers
oc get co storage
oc describe pvc <pvc> -n <ns>
oc describe pv <pv>
```

Then fix the storage class, PV, access mode, capacity, or CSI driver.

### 9.9 `volume node affinity conflict`

Example:

```text
0/5 nodes are available: 5 node(s) had volume node affinity conflict.
```

Meaning:

The pod uses a PV that can only be attached or used from certain nodes/zones, but the pod's other scheduling requirements point elsewhere.

Common cases:

- Local PV bound to one node.
- Cloud disk bound to one zone.
- Pod node affinity selects nodes in another zone.
- StatefulSet pod is recreated with a PVC tied to a different topology.

Check PV node affinity:

```bash
oc get pv <pv-name> -o yaml | yq '.spec.nodeAffinity'
```

Check pod scheduling rules:

```bash
oc get pod <pod> -n <ns> -o yaml | yq '.spec.nodeSelector, .spec.affinity'
```

Fix options:

- Align pod node affinity with PV topology.
- Use the correct StorageClass binding mode.
- Recreate PVC if data can be discarded.
- Restore data to storage in the correct topology.
- For StatefulSets, understand that each replica has identity and PVC binding.

### 9.10 `node(s) were unschedulable`

Example:

```text
0/3 nodes are available: 3 node(s) were unschedulable.
```

Meaning:

Nodes are cordoned or marked unschedulable.

Check:

```bash
oc get nodes
oc describe node <node> | grep -i Unschedulable
```

Fix:

```bash
oc adm uncordon <node>
```

Use this only after confirming the node is healthy and intended to receive workloads.

### 9.11 `node(s) had condition: [DiskPressure|MemoryPressure|PIDPressure]`

Example:

```text
0/5 nodes are available: 2 node(s) had condition: DiskPressure, 3 Insufficient memory.
```

Meaning:

Node conditions make nodes unsuitable or risky for scheduling.

Check:

```bash
oc get nodes
oc describe node <node> | sed -n '/Conditions:/,/Addresses:/p'
```

Fix options:

- Free disk space.
- Investigate image garbage collection.
- Check `/var/lib/kubelet`, CRI-O storage, container logs.
- Resolve node memory pressure.
- Add capacity.
- Drain and remediate unhealthy nodes.

### 9.12 `preemption: No preemption victims found`

Example:

```text
preemption: 0/4 nodes are available: 4 No preemption victims found for incoming pod.
```

Meaning:

The scheduler could not find lower-priority pods whose removal would make the pending pod fit.

Reasons:

- Existing pods have equal or higher priority.
- Hard constraints still fail after removing lower-priority pods.
- Node selector or taints exclude nodes regardless of free resources.
- Volume topology blocks placement.
- Anti-affinity/topology rules still cannot be satisfied.

Fix options:

- Do not assume adding PriorityClass solves all Pending pods.
- Fix hard placement constraints first.
- Add capacity if resource pressure is real.
- Review PDB and priority design.

### 9.13 `preemption: Preemption is not helpful for scheduling`

Example:

```text
preemption: 0/6 nodes are available: 6 Preemption is not helpful for scheduling.
```

Meaning:

Even if lower-priority pods were removed, the pending pod still would not fit. This usually points to non-resource hard constraints.

Most likely causes:

- Taints not tolerated.
- Node selector/affinity mismatch.
- Required pod anti-affinity impossible.
- Topology spread too strict.
- Volume node affinity conflict.
- Node is unschedulable.
- Pod requests exceed every node's allocatable capacity.

## 10. OpenShift-Specific Scheduling Controls That Affect Events

### 10.1 Cluster `Scheduler` object

OpenShift manages cluster scheduler configuration through:

```bash
oc get scheduler cluster -o yaml
```

Important fields include:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  mastersSchedulable: false
  profile: LowNodeUtilization
  defaultNodeSelector: env=prod
```

Possible impacts:

| Field | Impact |
|---|---|
| `mastersSchedulable` | Controls whether control-plane nodes can receive regular workloads. |
| `profile` | Controls scheduler scoring behavior such as spreading or packing. |
| `defaultNodeSelector` | Adds default node placement constraints to pods. |

If a default node selector is configured incorrectly, pods can show:

```text
node(s) didn't match Pod's node affinity/selector
```

Check:

```bash
oc get scheduler cluster -o jsonpath='{.spec.defaultNodeSelector}{"\n"}'
```

### 10.2 Scheduler profiles

OpenShift scheduler profiles can influence where pods land after feasible nodes are identified.

Common profiles:

| Profile | Behavior |
|---|---|
| `LowNodeUtilization` | Spreads pods more evenly; default behavior. |
| `HighNodeUtilization` | Packs pods onto fewer nodes; can reduce node count but increases blast radius. |
| `NoScoring` | Optimizes for low-latency scheduling by disabling score plugins; can reduce placement quality. |

Important distinction:

- Profiles mainly affect **scoring** after nodes are feasible.
- `FailedScheduling` usually means the pod failed **filtering**, not scoring.

So changing scheduler profile is usually not the first fix for Pending pods.

### 10.3 Project-level node selectors

OpenShift namespaces can have node selectors through annotations such as:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: env=prod
```

Check:

```bash
oc get namespace <namespace> -o yaml | grep -i 'openshift.io/node-selector' -A2
```

If the project selector conflicts with the pod's own selector or node labels, you may see:

```text
node(s) didn't match Pod's node affinity/selector
```

### 10.4 Dedicated nodes

A common OpenShift production pattern is dedicated node groups:

- Infra nodes
- Logging nodes
- Monitoring nodes
- Router nodes
- Storage nodes
- GPU nodes
- Application-specific nodes

Correct design usually combines:

1. Node labels to attract allowed workloads.
2. Node taints to repel unauthorized workloads.
3. Pod node selectors/affinity to target the node group.
4. Pod tolerations to allow scheduling onto tainted nodes.

Example node:

```bash
oc label node worker-infra-1 node-role.kubernetes.io/infra=
oc adm taint node worker-infra-1 node-role.kubernetes.io/infra=:NoSchedule
```

Example workload placement:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: "node-role.kubernetes.io/infra"
  operator: "Exists"
  effect: "NoSchedule"
```

If you use only labels without taints, regular workloads might still land there.  
If you use only taints without matching tolerations, intended workloads might remain Pending.

## 11. Full Troubleshooting Workflow for Scheduler Events

Use this workflow during production incidents.

### Step 1: Identify the pending pod

```bash
oc get pods -A | grep Pending
```

or for one namespace:

```bash
oc get pods -n <namespace> -o wide
```

### Step 2: Check whether the pod has a node

```bash
oc get pod <pod> -n <ns> -o wide
```

If `NODE` is empty, continue with scheduler troubleshooting.

If `NODE` is set, move to kubelet/container/volume troubleshooting.

### Step 3: Read scheduler events

```bash
oc describe pod <pod> -n <ns>
```

## 13. Scheduler Events in Real-World Scenarios

### Scenario 1: New deployment stuck Pending because of project node selector

Symptoms:

```bash
oc get pods -n app1
```

```text
NAME                     READY   STATUS    RESTARTS   AGE
api-7f88bc9c87-mx2cq     0/1     Pending   0          8m
```

Event:

```text
0/5 nodes are available: 5 node(s) didn't match Pod's node affinity/selector.
```

Investigation:

```bash
oc get pod api-7f88bc9c87-mx2cq -n app1 -o yaml | yq '.spec.nodeSelector'
oc get namespace app1 -o yaml | grep -i node-selector -A2
oc get nodes --show-labels | grep env=dev
```

Finding:

```yaml
openshift.io/node-selector: env=prod
```

But no node has `env=prod`.

Fix:

```bash
oc label node worker-1 env=prod
```

or correct the namespace annotation:

```bash
oc annotate namespace app1 openshift.io/node-selector='env=dev' --overwrite
```

Then recreate the pod if necessary:

```bash
oc delete pod api-7f88bc9c87-mx2cq -n app1
```

### Scenario 2: Infra workload blocked by taint

Event:

```text
0/3 nodes are available: 3 node(s) had untolerated taint {node-role.kubernetes.io/infra: }.
```

Investigation:

```bash
oc describe node worker-infra-1 | grep -i Taints -A2
oc get deploy router -n openshift-ingress -o yaml | yq '.spec.template.spec.tolerations'
```

Finding:

The workload selects infra nodes but does not tolerate the infra taint.

Fix pattern:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
tolerations:
- key: "node-role.kubernetes.io/infra"
  operator: "Exists"
  effect: "NoSchedule"
```

### Scenario 3: StatefulSet blocked by zone-bound PV

Event:

```text
0/6 nodes are available: 3 node(s) had volume node affinity conflict, 3 node(s) didn't match Pod's node affinity/selector.
```

Investigation:

```bash
oc get pod db-0 -n prod -o yaml | yq '.spec.nodeSelector, .spec.affinity'
oc get pvc data-db-0 -n prod -o yaml | yq '.spec.volumeName'
oc get pv <pv-name> -o yaml | yq '.spec.nodeAffinity'
oc get nodes -L topology.kubernetes.io/zone,disk
```

Finding:

- PVC is bound to a PV in `zone-a`.
- Pod requires `topology.kubernetes.io/zone=zone-b`.

Fix options:

- Change pod affinity to allow `zone-a`.
- Restore/migrate data to storage in `zone-b`.
- Recreate PVC if data is disposable.
- Review StorageClass `volumeBindingMode`.

### Scenario 4: Strict anti-affinity with too many replicas

Event:

```text
0/3 nodes are available: 3 node(s) didn't satisfy existing pods anti-affinity rules.
```

Workload:

```yaml
replicas: 4
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: api
      topologyKey: kubernetes.io/hostname
```

Problem:

There are only three eligible nodes, but four replicas require four different hosts.

Fix options:

- Add one more eligible worker.
- Reduce replicas to 3.
- Change hard anti-affinity to preferred.
- Use topology spread with appropriate `maxSkew`.

### Scenario 5: Requests larger than any node

Event:

```text
0/5 nodes are available: 5 Insufficient memory. preemption: 0/5 nodes are available: 5 No preemption victims found for incoming pod.
```

Pod request:

```yaml
resources:
  requests:
    memory: 128Gi
```

Node allocatable:

```text
worker nodes: 64Gi each
```

Preemption cannot help because even an empty node cannot fit the pod.

Fix options:

- Correct the request.
- Use larger nodes.
- Split workload.
- Move to a dedicated high-memory node pool.

## 15. Scheduler Events and Resource Requests

A common mistake is comparing scheduler failures with live usage.

Example:

```text
FailedScheduling: 0/3 nodes are available: 3 Insufficient cpu.
```

Admin checks:

```bash
oc adm top nodes
```

and sees nodes only 30% used.

Why still Pending?

Because scheduler uses **requested resources**, not current usage, for bin-packing decisions.

Example node:

```text
Allocatable CPU: 8 cores
Already requested CPU: 7.8 cores
Current actual usage: 2.4 cores
New pod request: 500m
```

The scheduler rejects the node because:

```text
7.8 cores requested + 0.5 core requested > 8 cores allocatable
```

Even though actual CPU usage is low.

Best-practice actions:

- Set realistic requests.
- Avoid default LimitRange values that are too high.
- Use namespace ResourceQuota to prevent overcommit abuse.
- Review workloads with no requests or excessive requests.
- Use metrics over time to right-size workloads.

## 16. Scheduler Events and Taints/Tolerations

Taints repel pods. Tolerations allow pods to tolerate taints, but they do not force scheduling.

Example node taint:

```bash
oc adm taint node worker-gpu-1 accelerator=nvidia:NoSchedule
```

Pod toleration:

```yaml
tolerations:
- key: accelerator
  operator: Equal
  value: nvidia
  effect: NoSchedule
```

Important effects:

| Effect | Behavior |
|---|---|
| `NoSchedule` | New pods without toleration are not scheduled. |
| `PreferNoSchedule` | Scheduler tries to avoid the node but may still schedule there. |
| `NoExecute` | Existing pods without toleration can be evicted; new pods also need toleration. |

Common production mistakes:

1. Taint added to a node pool but workloads were not updated with tolerations.
2. Toleration exists but node selector points to another node group.
3. Toleration key/value/effect mismatch.
4. Using `Exists` too broadly, allowing workloads onto nodes they should not use.
5. Tolerating control-plane taints for normal applications.

Debug checklist:

```bash
oc get pod <pod> -n <ns> -o yaml | yq '.spec.tolerations'
oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
oc describe node <node> | grep -i Taints -A5
```

## 17. Scheduler Events and Node Selectors/Affinity

Node selectors and required node affinity are hard filters.

### Node selector

```yaml
nodeSelector:
  workload: payment
```

Node must have:

```bash
oc label node worker-1 workload=payment
```

### Required node affinity

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: workload
          operator: In
          values:
          - payment
          - settlement
```

If no node matches, expect:

```text
node(s) didn't match Pod's node affinity/selector
```

### Preferred node affinity

```yaml
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 80
      preference:
        matchExpressions:
        - key: disk
          operator: In
          values:
          - ssd
```

Preferred affinity affects scoring, not feasibility. If preferred rules cannot be satisfied, the pod can still schedule elsewhere.

Senior admin guidance:

- Use hard node affinity only for true requirements.
- Use preferred affinity for optimization.
- Combine labels and taints for dedicated nodes.
- Avoid environment-specific hardcoding in Helm charts unless intentional.
- Always check namespace and cluster default selectors in OpenShift.

## 18. Scheduler Events and Pod Affinity / Anti-affinity

Pod affinity places pods near other pods. Pod anti-affinity keeps pods away from other pods.

### Pod affinity example

```yaml
affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: cache
      topologyKey: kubernetes.io/hostname
```

Meaning:

The pod must run on a node where a pod with `app=cache` already exists.

### Pod anti-affinity example

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: api
      topologyKey: kubernetes.io/hostname
```

Meaning:

Do not place this pod on a node where another `app=api` pod already exists.

Common event:

```text
node(s) didn't satisfy existing pods anti-affinity rules
```

Troubleshooting:

```bash
oc get pod <pod> -n <ns> -o yaml | yq '.spec.affinity'
oc get pods -n <ns> -l app=api -o wide
oc get nodes -L kubernetes.io/hostname,topology.kubernetes.io/zone
```

Senior guidance:

- Hard anti-affinity can block scale-out if replicas exceed topology domains.
- Topology keys must exist on eligible nodes.
- Label selectors must be precise.
- Required anti-affinity is useful for strict HA but dangerous for large deployments if node count changes.

## 19. Scheduler Events and Topology Spread Constraints

Topology spread constraints are used to distribute pods across topology domains such as hostname, zone, or rack.

Example:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: api
```

Important fields:

| Field | Meaning |
|---|---|
| `maxSkew` | Maximum allowed difference in matching pod count between topology domains. |
| `topologyKey` | Node label that defines the domain. |
| `whenUnsatisfiable` | `DoNotSchedule` makes it hard; `ScheduleAnyway` makes it preferred. |
| `labelSelector` | Which pods are counted for spread. |

Common event:

```text
node(s) didn't match pod topology spread constraints
```

Check:

```bash
oc get nodes -L topology.kubernetes.io/zone,kubernetes.io/hostname
oc get pods -n <ns> -l app=api -o wide
oc get pod <pod> -n <ns> -o yaml | yq '.spec.topologySpreadConstraints'
```

Fix options:

- Add nodes in missing topology domains.
- Correct topology labels.
- Change `DoNotSchedule` to `ScheduleAnyway` if strict enforcement is not required.
- Increase `maxSkew`.
- Fix label selector.

## 20. Scheduler Events and Storage

Scheduling and storage are tightly connected, especially with topology-aware CSI drivers.

### Immediate binding storage

If PVC binding mode is `Immediate`, PVC binding happens before pod scheduling.

Problem event:

```text
pod has unbound immediate PersistentVolumeClaims
```

Check:

```bash
oc get pvc -n <ns>
oc describe pvc <pvc> -n <ns>
oc get sc <storageclass> -o yaml
```

### WaitForFirstConsumer

If binding mode is `WaitForFirstConsumer`, the scheduler helps choose a node before the PV is provisioned/bound. This prevents a volume from being created in the wrong zone.

Check:

```bash
oc get sc -o custom-columns=NAME:.metadata.name,BINDING:.volumeBindingMode,PROVISIONER:.provisioner
```

### Local PVs

Local PVs often include node affinity. If a pod has conflicting node affinity, scheduling fails.

Check:

```bash
oc get pv <pv> -o yaml | yq '.spec.nodeAffinity'
```

### CSI driver health

```bash
oc get co storage
oc get pods -n openshift-cluster-csi-drivers
oc get pods -A | grep -i csi
```

Senior guidance:

- Do not troubleshoot all Pending pods as CPU/memory issues.
- Always check PVC status for StatefulSets.
- For zone-aware storage, verify node zone labels and StorageClass binding mode.
- For local PVs, pod placement must match PV node affinity.

## 21. Scheduler Events and Priority / Preemption

PriorityClass influences scheduling queue order and preemption.

Example PriorityClass:

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: platform-critical
value: 1000000
globalDefault: false
description: "Critical platform workloads"
```

Pod usage:

```yaml
spec:
  priorityClassName: platform-critical
```

Check:

```bash
oc get priorityclass
oc get pod <pod> -n <ns> -o jsonpath='{.spec.priorityClassName}{" "}{.spec.priority}{"\n"}'
```

Preemption workflow:

1. High-priority pod is pending.
2. No feasible node is found.
3. Scheduler checks whether removing lower-priority pods can make a node feasible.
4. If yes, it nominates a node and evicts victims.
5. Victims terminate according to grace period.
6. Preemptor is eventually scheduled if no higher-priority pod takes the space first.

Common messages:

```text
No preemption victims found for incoming pod
Preemption is not helpful for scheduling
```

Senior guidance:

- Priority is not a replacement for capacity planning.
- Preemption does not fix bad node selectors, missing tolerations, or impossible storage topology.
- Use ResourceQuota to control who can use high PriorityClasses.
- Use `preemptionPolicy: Never` when queue priority is desired without evicting other workloads.

## 22. Scheduler Events and Cluster Autoscaler

In clusters with Machine API and Cluster Autoscaler, scheduling failures can interact with autoscaling decisions.

You might see events such as:

```text
NotTriggerScaleUp
```

This is usually from cluster autoscaler, not from the scheduler.

Important distinction:

- Scheduler says: "I cannot place this pod on current nodes."
- Cluster autoscaler says: "Can adding nodes solve this?"

Scale-up might not happen if:

- Pod has node selector that no MachineSet can satisfy.
- Pod needs a taint/toleration combination not represented by autoscaled nodes.
- Pod requests exceed max node size.
- Cluster has reached max nodes.
- Storage topology prevents placement.
- Pod has local constraints that autoscaler cannot satisfy.

Check:

```bash
oc get machinesets -n openshift-machine-api
oc get machineautoscalers -A
oc get clusterautoscaler -A
oc logs -n openshift-machine-api deploy/cluster-autoscaler
```

## 23. Scheduler Events Retention and Observability

Events are short-lived. They are stored through the Kubernetes API and expire based on event TTL configuration. In modern OpenShift, event TTL can be managed through the `KubeAPIServer` custom resource using `eventTTLMinutes`.

Check configured API server event TTL:

```bash
oc get cm config -n openshift-kube-apiserver -o jsonpath='{.data.config\.yaml}' \
| jq -r '.apiServerArguments["event-ttl"][0]'
```

Example patch:

```bash
oc patch kubeapiserver/cluster \
  -p='{"spec": {"eventTTLMinutes": 60 }}' \
  --type=merge
```

Then wait for stability:

```bash
oc adm wait-for-stable-cluster
```

Production guidance:

- Events are excellent for immediate troubleshooting.
- Events are not a replacement for audit logs or monitoring.
- Forward events to Loki, Elasticsearch, OpenTelemetry, or another observability backend if you need historical analysis.
- Do not set excessively long event TTL without understanding etcd impact.

## 24. Difference Between Events, Logs, Metrics, and Conditions

| Data Source | Best For | Limitation |
|---|---|---|
| Events | Recent object lifecycle and scheduling reasons | Short retention; best-effort; messages can change |
| Scheduler logs | Deep scheduler internals and plugin-level behavior | Requires access to control-plane/scheduler logs |
| Metrics | Trends, saturation, scheduling latency, pending pod counts | Needs Prometheus/monitoring queries |
| Pod conditions | Current state summary | Less detailed than events |
| Audit logs | API actions and user/system requests | Does not explain scheduler algorithm decisions directly |

Useful pod condition check:

```bash
oc get pod <pod> -n <ns> -o yaml | yq '.status.conditions'
```

Pending pod condition may include:

```yaml
- type: PodScheduled
  status: "False"
  reason: Unschedulable
  message: '0/3 nodes are available: 3 Insufficient cpu.'
```

## 28. Best Practices for Avoiding Bad Scheduler Events

### 28.1 Use labels consistently

Create a label strategy:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
topology.kubernetes.io/zone=zone-a
workload=payments
hardware=gpu
storage=local-nvme
env=prod
```

Avoid random labels with inconsistent names:

```text
prod=yes
production=true
env=prd
environment=prod
```

### 28.2 Use hard constraints only when required

Use required rules for:

- GPU workloads needing GPU nodes
- Local PV workloads tied to nodes
- Compliance isolation
- Dedicated hardware
- Zone-specific workloads with hard requirements

Use preferred rules for:

- Better distribution
- Cost optimization
- Cache locality
- Soft HA preference

### 28.3 Pair taints with labels

For dedicated nodes:

```bash
oc label node worker-payment-1 workload=payment
oc adm taint node worker-payment-1 workload=payment:NoSchedule
```

Workload:

```yaml
nodeSelector:
  workload: payment
tolerations:
- key: workload
  operator: Equal
  value: payment
  effect: NoSchedule
```

### 28.4 Right-size resource requests

Bad request design causes unnecessary Pending pods.

Use:

```bash
oc adm top pods -A --containers
```

and historical metrics to adjust requests.

### 28.5 Design topology rules with capacity in mind

Before applying hard anti-affinity or topology spread, verify:

```bash
oc get nodes -L topology.kubernetes.io/zone,kubernetes.io/hostname
```

Ensure enough eligible topology domains exist for desired replicas.

### 28.6 Monitor Pending pods and FailedScheduling events

Recommended alerts:

- Pending pods for more than N minutes.
- Increasing `FailedScheduling` events.
- `kube-scheduler` degraded.
- Unschedulable nodes count.
- Nodes under pressure.
- PVCs Pending for too long.

## 29. Exam and Interview-Oriented Notes

For Advanced OpenShift Administration, remember these practical points:

1. `oc describe pod` is the fastest way to find scheduler events.
2. `FailedScheduling` means the pod has not been placed on a node.
3. If the pod already has `NODE`, do not keep troubleshooting the scheduler.
4. `Insufficient cpu/memory` refers to requests, not actual live usage.
5. Untolerated taint means add a matching toleration or remove/fix the taint.
6. Node selector/affinity mismatch can come from pod, namespace, or cluster scheduler defaults.
7. PVC issues can block scheduling.
8. Topology spread and anti-affinity can block pods even when resources are free.
9. Preemption cannot solve hard policy conflicts.
10. Events are short-lived and should be exported for long-term observability.

```bash
oc get pvc -n <ns>

# Storage classes
oc get sc
```

## 31. Quick Reference: Message-to-Action Mapping

| Event Message Contains | Primary Area | First Checks | Typical Fix |
|---|---|---|---|
| `Insufficient cpu` | Resource requests | Pod requests, node allocated resources | Right-size requests or add CPU capacity |
| `Insufficient memory` | Resource requests | Pod requests, node allocated resources | Right-size requests or add memory capacity |
| `Too many pods` | Node pod density | Pod count per node, kubelet max pods | Add nodes or reduce pod density |
| `untolerated taint` | Taints/tolerations | Node taints, pod tolerations | Add correct toleration or remove accidental taint |
| `node affinity/selector` | Labels/selectors | Pod selector, affinity, namespace selector, node labels | Fix labels or selectors |
| `pod topology spread constraints` | HA/topology | Topology labels, spread rules, replica placement | Fix labels/rules or add domains |
| `anti-affinity rules` | Pod placement relation | Existing pods, anti-affinity, topology key | Add nodes or loosen hard anti-affinity |
| `unbound immediate PersistentVolumeClaims` | Storage | PVC, PV, StorageClass, CSI | Fix PVC/provisioning/storage class |
| `volume node affinity conflict` | Storage topology | PV node affinity, pod node affinity, zones | Align pod placement with PV topology |
| `were unschedulable` | Node state | `oc get nodes`, cordon state | Uncordon after validation |
| `Preemption is not helpful` | Hard constraints/capacity | All placement constraints | Fix hard constraints or add suitable capacity |

## 32. Senior-Level Troubleshooting Mindset

When troubleshooting scheduler events, avoid these common mistakes:

### Mistake 1: Looking only at CPU/memory usage

Scheduler uses requests and hard constraints. Always check:

```bash
oc describe node <node>
```

### Mistake 2: Adding broad tolerations without policy review

This can accidentally place workloads on infra, storage, or control-plane nodes.

### Mistake 3: Ignoring namespace node selectors

OpenShift project-level node selectors are easy to forget and can silently constrain workloads.

### Mistake 4: Assuming preemption will fix everything

Preemption cannot fix missing tolerations, impossible selectors, or volume topology conflicts.

### Mistake 5: Troubleshooting scheduler after the pod already has a node

If `NODE` is set, move to kubelet/image/volume/network/runtime events.

### Mistake 6: Treating events as permanent history

Events expire. Export them if you need historical incident timelines.

```bash

```

Create a pod targeting that node label but without toleration.

```bash
oc label node <worker-node> labnode=reserved
oc new-project taint-lab
```

```yaml
cat <<'EOF' | oc apply -f -
apiVersion: v1

  name: taint-test

  - name: sleep
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "3600"]
```

Check:


```text
untolerated taint {lab: reserved}
```

```bash
oc patch pod taint-test -n taint-lab --type='json' -p='[
  {"op":"add","path":"/spec/tolerations","value":[{"key":"lab","operator":"Equal","value":"reserved","effect":"NoSchedule"}]}
```


```yaml
apiVersion: v1
kind: Pod
metadata:
  name: taint-test
  namespace: taint-lab
spec:
  nodeSelector:
    labnode: reserved
  tolerations:
  - key: lab
    operator: Equal
    value: reserved
    effect: NoSchedule

  - name: sleep
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "3600"]
EOF
```

```bash
oc adm taint node <worker-node> lab=reserved:NoSchedule-
oc label node <worker-node> labnode-
oc delete project taint-lab
```

## 34. Production Runbook: Pending Pod Due to Scheduler Failure

Use this as an incident runbook.

### Input

Application team reports:

```text
Pods are stuck in Pending.
```

### Runbook

```bash
NS=<namespace>
POD=<pod-name>
```

1. Confirm pod status:

```bash
oc get pod "$POD" -n "$NS" -o wide
```

2. Check events:

```bash
oc describe pod "$POD" -n "$NS"
```

3. Extract pod scheduling policy:

```bash
oc get pod "$POD" -n "$NS" -o yaml > /tmp/${NS}-${POD}.yaml
```

Review:

```bash
yq '.spec.nodeSelector, .spec.affinity, .spec.tolerations, .spec.topologySpreadConstraints, .spec.priorityClassName, .spec.volumes' /tmp/${NS}-${POD}.yaml
```

4. Check namespace selector:

```bash
oc get namespace "$NS" -o yaml | grep -i node-selector -A2
```

5. Check scheduler config:

```bash
oc get scheduler cluster -o yaml
```

6. Check nodes:

```bash
oc get nodes -o wide
oc get nodes --show-labels
oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
```

7. Check resource fit:

```bash
for n in $(oc get nodes -o name | cut -d/ -f2); do
  echo "===== $n ====="
  oc describe node "$n" | egrep -A12 'Allocatable|Allocated resources'
done
```

8. Check PVC if present:

```bash
oc get pvc -n "$NS"
```

9. Classify root cause:

```text
[ ] Resource fit
[ ] Taint/toleration
[ ] Node selector/affinity
[ ] Project selector
[ ] Cluster default selector
[ ] Anti-affinity/topology spread
[ ] PVC/storage topology
[ ] Node unschedulable/NotReady
[ ] Priority/preemption
```

10. Apply minimal safe fix and verify:

```bash
oc get pod "$POD" -n "$NS" -o wide
oc get events -n "$NS" --sort-by=.lastTimestamp | tail -20
```

### Incident closure notes

Record:

- Exact `FailedScheduling` message.
- Root cause.
- Change applied.
- Whether pod was recreated.
- Preventive action.

## 35. Final Key Takeaways

Scheduler events are your first diagnostic signal for OpenShift pod placement problems. A senior administrator should be able to read a `FailedScheduling` event and immediately map it to the correct subsystem:

- `Insufficient cpu/memory` -> resource requests and node allocatable capacity
- `untolerated taint` -> taints and tolerations
- `node affinity/selector` -> pod, namespace, or cluster placement policy
- `topology spread` / `anti-affinity` -> HA placement rules
- `unbound PVC` / `volume node affinity` -> storage and topology
- `unschedulable` -> cordoned or unavailable nodes
- `preemption not helpful` -> hard constraints or impossible fit

The best troubleshooting sequence is:

```text
oc get pod -o wide
    -> oc describe pod
        -> read FailedScheduling message
            -> inspect pod scheduling spec
                -> inspect namespace and scheduler defaults
                    -> inspect node labels/taints/capacity/storage
                        -> apply minimal safe fix
```

Mastering scheduler events gives you a major advantage in OpenShift administration because most workload placement issues become clear before you even need deep component logs.
