# Node Pressure Conditions in OpenShift: Advanced Pod Scheduling and Workload Placement Guide

**Audience:** Advanced OpenShift administrators, platform engineers, SREs, and Kubernetes/OpenShift operators with production experience.  
**Level:** Senior / 10-year experience depth.  
**Scope:** OpenShift Container Platform 4.x, Kubernetes scheduling, kubelet eviction, node conditions, taints, tolerations, troubleshooting, prevention, and operational runbooks.

---

## 1. Executive summary

Node pressure conditions are kubelet-reported node health signals that tell the OpenShift control plane that a node is running short of a critical local resource. The most important pressure conditions are:

- `MemoryPressure`
- `DiskPressure`
- `PIDPressure`

These conditions directly affect workload placement. When a node reports pressure, Kubernetes/OpenShift can automatically apply node-condition taints such as:

- `node.kubernetes.io/memory-pressure`
- `node.kubernetes.io/disk-pressure`
- `node.kubernetes.io/pid-pressure`

For scheduling, the important behavior is:

1. The kubelet detects local resource pressure.
2. The node status changes, for example `DiskPressure=True`.
3. The control plane maps the condition to a taint.
4. The scheduler avoids placing new pods on that node unless the pod has a matching toleration.
5. If pressure continues, the kubelet can evict pods to protect node stability.

A senior OpenShift administrator must understand this clearly:

> Node pressure is not only a node health issue. It is also a scheduling, eviction, capacity, reliability, and application design issue.

---

## 2. Where node pressure fits in workload placement

OpenShift scheduling normally works like this:

1. A pod is created.
2. The default scheduler filters nodes.
3. It removes nodes that do not satisfy hard requirements:
   - node selectors
   - required node affinity
   - pod affinity / anti-affinity
   - resource availability
   - taints without tolerations
   - volume topology constraints
   - node readiness
4. It scores remaining nodes.
5. It binds the pod to the best node.

Node pressure affects step 3. A pressure taint makes the node unsuitable for most new pods.

Example scheduling failure:

```text
0/5 nodes are available: 1 node(s) had untolerated taint {node.kubernetes.io/disk-pressure: },
2 Insufficient memory, 2 node(s) didn't match Pod's node affinity/selector.
```

In this example, do not immediately add tolerations. First ask:

- Why is the node under pressure?
- Is this a real capacity issue?
- Is one workload consuming too much local resource?
- Are requests and limits missing?
- Is the node filesystem full?
- Is log or image garbage collection failing?
- Is the workload safe to run on a pressured node?

For normal application pods, tolerating pressure taints is usually the wrong fix. It bypasses a safety signal. Use tolerations for platform-level DaemonSets only when you understand the risk.

## 3. Important node conditions

OpenShift node status contains conditions. You can view them with:

```bash
oc describe node <node-name>
```

Typical output section:

```text
Conditions:
  Type             Status  Reason                       Message
  ----             ------  ------                       -------
  MemoryPressure   False   KubeletHasSufficientMemory   kubelet has sufficient memory available
  DiskPressure     False   KubeletHasNoDiskPressure     kubelet has no disk pressure
  PIDPressure      False   KubeletHasSufficientPID      kubelet has sufficient PID available
  Ready            True    KubeletReady                 kubelet is posting ready status
```

### 3.1 Node pressure condition table

| Condition | Meaning | Main resource signal | Scheduling impact | Operational risk |
|---|---|---|---|---|
| `MemoryPressure=True` | Node available memory crossed an eviction threshold | `memory.available` | Node can receive `node.kubernetes.io/memory-pressure:NoSchedule`; new BestEffort pods are commonly blocked | Workload eviction, kernel OOM, degraded kubelet/CRI-O stability |
| `DiskPressure=True` | Node filesystem, image filesystem, container filesystem, or inode availability crossed threshold | `nodefs.available`, `nodefs.inodesFree`, `imagefs.available`, `imagefs.inodesFree`, `containerfs.available`, `containerfs.inodesFree` | Node can receive `node.kubernetes.io/disk-pressure:NoSchedule`; new pods are blocked unless tolerated | Evicted pods, failed image pulls, lost container logs, kubelet instability |
| `PIDPressure=True` | Available process IDs are too low | `pid.available` | Node can receive `node.kubernetes.io/pid-pressure:NoSchedule` | Processes cannot fork, node can become unstable, workloads may fail strangely |
| `Ready=False` | Kubelet reports node unhealthy | kubelet/node health | Node normally becomes unsuitable for scheduling | Existing pods might be evicted depending on taints and tolerations |
| `Ready=Unknown` | Node controller has not heard from the node | missed node heartbeats | Node may receive `node.kubernetes.io/unreachable` | Network partition, node crash, control-plane reachability issue |
| `NetworkUnavailable=True` | Node network is not correctly configured | CNI/network setup | Scheduling impact depends on taints and component behavior | Pod networking can fail |

## 4. Node pressure is detected by the kubelet, not by the scheduler

A common misunderstanding is that the scheduler directly calculates disk pressure or memory pressure. It does not.

The scheduler mainly consumes node objects, taints, capacity, allocatable resources, pod requests, affinity, and topology information. The kubelet runs on every node and monitors local resource signals.

The kubelet is responsible for:

- monitoring node memory
- monitoring root filesystem space and inodes
- monitoring image/container storage
- monitoring process ID availability
- comparing signals against eviction thresholds
- reporting node conditions
- attempting node-level cleanup
- evicting pods if necessary

The scheduler is responsible for:

- seeing taints and resource availability
- excluding pressured nodes from new scheduling decisions unless the pod tolerates the taint

This separation matters during troubleshooting:

- If a pod is **Pending**, inspect scheduler events and node taints.
- If a pod is **Evicted**, inspect kubelet events, node conditions, and eviction messages.
- If a node is **NotReady** or oscillating, inspect kubelet, CRI-O, disk, memory, PIDs, and node lifecycle events.

## 5. Node pressure and automatic taints

OpenShift uses the Kubernetes “Taint Nodes by Condition” behavior. When specific node conditions are present, the control plane adds corresponding taints.

Examples:

```bash
oc get nodes -o custom-columns=NAME:.metadata.name,STATUS:.status.conditions[-1].type,TAINTS:.spec.taints
```

Better command:

```bash
oc get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{.spec.taints}{"\n\n"}{end}'
```

Common pressure taints:

| Node condition | Taint key | Typical effect |
|---|---|---|
| `MemoryPressure=True` | `node.kubernetes.io/memory-pressure` | `NoSchedule` |
| `DiskPressure=True` | `node.kubernetes.io/disk-pressure` | `NoSchedule` |
| `PIDPressure=True` | `node.kubernetes.io/pid-pressure` | `NoSchedule` |
| `Ready=False` | `node.kubernetes.io/not-ready` | `NoExecute` / `NoSchedule` depending on situation |
| `Ready=Unknown` | `node.kubernetes.io/unreachable` | `NoExecute` / `NoSchedule` depending on situation |
| `NetworkUnavailable=True` | `node.kubernetes.io/network-unavailable` | usually relevant to networking components |

### Important scheduling point

The scheduler checks taints, not the raw condition itself.

That means this logic is true:

```text
Node has DiskPressure=True
        ↓
Control plane adds node.kubernetes.io/disk-pressure taint
        ↓
Scheduler sees taint
        ↓
Pod without toleration is not scheduled there
```

### Do not blindly tolerate pressure taints

This is dangerous for normal workloads:

```yaml
 tolerations:
 - key: node.kubernetes.io/disk-pressure
   operator: Exists
   effect: NoSchedule
```

Use this only for carefully designed platform DaemonSets or node repair agents, not for general applications.

Why?

Because scheduling into a pressured node can make the pressure worse. A pod that tolerates `DiskPressure` might pull a large image, write logs, create `emptyDir` data, and trigger more evictions.

## 6. Node pressure versus pod eviction

Node pressure and eviction are related but not identical.

### 6.1 Node pressure condition

A condition is a status signal:

```text
DiskPressure=True
MemoryPressure=True
PIDPressure=True
```

It tells the cluster: “This node is short of a local resource.”

### 6.2 Node-pressure eviction

Node-pressure eviction is an action performed by the kubelet. The kubelet can terminate pods to reclaim resources and preserve node stability.

During node-pressure eviction:

- selected pods move to `Failed` phase
- the pod reason can show `Evicted`
- replacement pods might be created by Deployments, ReplicaSets, StatefulSets, DaemonSets, or other controllers
- PodDisruptionBudgets are not treated the same as voluntary API-initiated evictions
- hard eviction thresholds can cause immediate termination

Example evicted pod:

```bash
oc get pods -A | grep Evicted
```

Example pod description:

```bash
oc describe pod <pod-name> -n <namespace>
```

Possible event/message:

```text
Status:         Failed
Reason:         Evicted
Message:        The node was low on resource: ephemeral-storage.
```

## 7. Eviction signals and thresholds

The kubelet compares eviction signals to eviction thresholds.

### 7.1 Eviction signal table

| Signal | What it represents | Common pressure condition |
|---|---|---|
| `memory.available` | Available memory from kubelet/cgroup accounting | `MemoryPressure` |
| `nodefs.available` | Free bytes on the node filesystem | `DiskPressure` |
| `nodefs.inodesFree` | Free inodes on the node filesystem | `DiskPressure` |
| `imagefs.available` | Free bytes on the image filesystem | `DiskPressure` |
| `imagefs.inodesFree` | Free inodes on the image filesystem | `DiskPressure` |
| `containerfs.available` | Free bytes on a separate container writable-layer filesystem, where used | `DiskPressure` |
| `containerfs.inodesFree` | Free inodes on a separate container filesystem, where used | `DiskPressure` |
| `pid.available` | Available process IDs | `PIDPressure` |

### 7.2 Filesystem terminology

OpenShift nodes using RHCOS and CRI-O commonly have important data under:

```text
/var/lib/kubelet
/var/lib/containers
/var/log
```

Kubernetes uses logical filesystem identifiers:

| Identifier | Meaning |
|---|---|
| `nodefs` | Main node filesystem; includes kubelet data, local volumes, non-memory `emptyDir`, logs, and other node-local storage |
| `imagefs` | Optional filesystem used by the container runtime for images |
| `containerfs` | Optional separate filesystem for writable container layers |

In many clusters, `/var/lib/kubelet` and `/var/lib/containers` are on the same filesystem. In that case, one physical disk pressure problem can show up through multiple logical signals.

## 8. Soft eviction and hard eviction

### 8.1 Soft eviction threshold

A soft threshold has a grace period.

Example concept:

```text
memory.available < 500Mi for 1m30s
```

Meaning:

- If available memory dips below 500 MiB briefly, kubelet waits.
- If it stays below the threshold longer than the grace period, eviction can start.

Soft thresholds help avoid unnecessary evictions caused by short spikes.

### 8.2 Hard eviction threshold

A hard threshold has no grace period.

Example concept:

```text
memory.available < 200Mi
```

Meaning:

- The node is in immediate danger.
- The kubelet acts quickly.
- Pod termination might be abrupt.

### 8.3 Default hard threshold examples

Common upstream kubelet default hard eviction thresholds include:

```text
memory.available < 100Mi
nodefs.available < 10%
imagefs.available < 15%
nodefs.inodesFree < 5%
imagefs.inodesFree < 5%
```

In OpenShift, review your effective kubelet configuration because cluster version, MachineConfig, KubeletConfig, and vendor defaults can matter.

## 9. Eviction order: which pods are killed first?

When the kubelet cannot reclaim node-level resources, it chooses pods for eviction.

The eviction decision considers:

1. Whether pod usage exceeds requests
2. Pod priority
3. Usage relative to requests

Typical memory-pressure risk order:

| Pod class / behavior | Eviction risk |
|---|---|
| BestEffort pods with no requests/limits | Highest |
| Burstable pods exceeding requests | High |
| Burstable pods close to requests | Medium |
| Guaranteed pods | Lowest |
| Critical system pods with high priority | Very low, but not magically immune to all failures |

Important detail:

- QoS class is useful for estimating memory eviction risk.
- Kubelet eviction is not simply “BestEffort first always.”
- Priority and usage above requests matter.
- For PID and inode pressure, there are no normal pod resource requests for those resources, so priority becomes very important.
- For disk pressure, pod local storage usage matters heavily.

## 10. MemoryPressure deep dive

`MemoryPressure=True` means kubelet believes available node memory crossed an eviction threshold.

### 10.1 Common causes

| Cause | Explanation |
|---|---|
| Missing memory requests | Scheduler overpacks pods because it only sees low/no requested memory |
| Memory limits too high or absent | A container can consume more memory than expected |
| Memory leak | Long-running service gradually consumes node memory |
| JVM heap misconfiguration | Java process sees large node/container memory and allocates aggressively |
| Too many BestEffort pods | No requests, no limits, high eviction risk |
| DaemonSet growth | Logging, monitoring, CNI, storage, or security agents consume more than reserved |
| Page cache pressure | Heavy local disk I/O can affect memory accounting |
| Host daemons consuming memory | CRI-O, kubelet, journald, or third-party agents exceed expected usage |

### 10.2 Symptoms

```bash
oc get nodes
oc describe node <node-name>
oc adm top nodes
oc adm top pods -A --sort-by=memory
oc get events -A --sort-by=.lastTimestamp | grep -Ei 'memory|evict|pressure|oom'
```

Pod-level symptoms:

```bash
oc describe pod <pod> -n <namespace>
oc get pod <pod> -n <namespace> -o yaml | grep -A5 -i state
```

Possible reasons:

```text
OOMKilled
Evicted
The node was low on resource: memory
```

### 10.3 MemoryPressure troubleshooting flow

#### Step 1: Confirm condition and timing

```bash
NODE=<node-name>

oc describe node $NODE | sed -n '/Conditions:/,/Addresses:/p'
oc get events --field-selector involvedObject.kind=Node,involvedObject.name=$NODE -A --sort-by=.lastTimestamp
```

Check:

- `MemoryPressure=True` or historical transitions
- `LastTransitionTime`
- kubelet reason and message
- whether `Ready` also changed

#### Step 2: Identify top memory pods

```bash
oc adm top pods -A --sort-by=memory
oc get pods -A -o wide --field-selector spec.nodeName=$NODE
```

Then inspect suspicious pods:

```bash
oc describe pod <pod> -n <namespace>
oc get pod <pod> -n <namespace> -o jsonpath='{.spec.containers[*].resources}'
```

Look for:

- missing `resources.requests.memory`
- missing `resources.limits.memory`
- memory request much lower than real usage
- BestEffort QoS
- recent rollout increasing memory usage

#### Step 3: Check node memory from host view

```bash
oc debug node/$NODE
chroot /host
free -h
vmstat 1 5
ps aux --sort=-%mem | head -30
journalctl -u kubelet --since "2 hours ago" | grep -Ei 'memory|evict|pressure|oom'
journalctl -k --since "2 hours ago" | grep -Ei 'oom|killed process|memory'
```

Exit after inspection:

```bash
exit
exit
```

#### Step 4: Decide the correct fix

| Finding | Fix |
|---|---|
| One app is leaking memory | Restart only as emergency; fix app; set correct requests/limits |
| Many pods have no requests | Apply LimitRange defaults and enforce requests |
| Node is legitimately undersized | Add workers, resize machines, or reduce density |
| System daemons consume memory | Review `systemReserved`, agent configuration, and platform add-ons |
| Workload burst is expected | Increase requests, use HPA/VPA process, spread pods, add capacity |

### 10.4 Good memory resource pattern

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: app-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: api
        image: registry.example.com/app/api:1.0
        resources:
          requests:
            cpu: 250m
            memory: 512Mi
          limits:
            cpu: "1"
            memory: 1Gi
```

Senior guidance:

- Requests are for scheduling and eviction protection.
- Limits are for containment.
- Do not set tiny requests just to fit more pods.
- Do not run production workloads as BestEffort.

## 11. DiskPressure deep dive

`DiskPressure=True` means kubelet sees low disk space or low inode availability on one of the node-local filesystems.

Disk pressure is very common in OpenShift production clusters because many things write to node-local storage:

- container images
- writable container layers
- pod logs
- terminated container metadata
- `emptyDir` volumes
- CSI/node plugin temporary data
- build workloads
- registry/cache activity
- debug sessions
- node logs/journals

### 11.1 DiskPressure is not only “disk full”

A node can have DiskPressure because:

- bytes are low
- inodes are low
- image filesystem is full
- root filesystem is full
- container writable layer filesystem is full

Example:

```bash
df -h
df -hi
```

You might see:

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda4       120G   70G   50G  59% /
```

But:

```text
Filesystem      Inodes  IUsed IFree IUse% Mounted on
/dev/sda4          10M   9.8M  200K   99% /
```

This is inode pressure, not byte pressure.

### 11.2 Symptoms

```bash
oc get nodes
oc describe node <node-name>
oc get events -A --sort-by=.lastTimestamp | grep -Ei 'disk|ephemeral|evict|pressure|image|inode'
oc get pods -A | grep Evicted
```

Pod messages might say:

```text
The node was low on resource: ephemeral-storage.
Container <name> was using 4Gi, which exceeds its request of 0.
```

or:

```text
The node had condition: [DiskPressure].
```

### 11.3 DiskPressure troubleshooting flow

#### Step 1: Confirm node condition and taints

```bash
NODE=<node-name>

oc describe node $NODE | sed -n '/Taints:/,/Unschedulable:/p'
oc describe node $NODE | sed -n '/Conditions:/,/Addresses:/p'
```

Check for:

```text
Taints: node.kubernetes.io/disk-pressure:NoSchedule
DiskPressure True
```

#### Step 2: Check pods on that node

```bash
oc get pods -A -o wide --field-selector spec.nodeName=$NODE
oc adm top pods -A --containers
```

Note: `oc adm top` might not show full ephemeral-storage detail depending on metrics availability and configuration.

#### Step 3: Inspect node filesystems

```bash
oc debug node/$NODE
chroot /host

df -h
df -hi
mount | grep -E '/var|kubelet|containers|overlay'
```

Important locations:

```bash
du -xhd1 /var | sort -h
du -xhd1 /var/lib | sort -h
du -xhd1 /var/lib/kubelet | sort -h
du -xhd1 /var/lib/containers | sort -h
du -xhd1 /var/log | sort -h
```

CRI-O and kubelet logs:

```bash
journalctl -u kubelet --since "2 hours ago" | grep -Ei 'disk|image|evict|pressure|garbage|inode'
journalctl -u crio --since "2 hours ago" | grep -Ei 'disk|image|storage|overlay|no space|inode'
```

#### Step 4: Check images and containers carefully

From the node debug chroot:

```bash
crictl images
crictl ps -a
```

Be careful with manual deletion. Prefer kubelet/CRI-O supported cleanup and workload correction. Do not randomly delete files under `/var/lib/kubelet` or `/var/lib/containers` in production unless you fully understand the consequence or are following vendor support guidance.

#### Step 5: Find workloads using local ephemeral storage

Look for pods with:

- large logs
- `emptyDir`
- build caches
- temporary exports
- application file uploads written to container filesystem
- missing ephemeral-storage requests/limits

```bash
oc get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"/"}{.metadata.name}{" node="}{.spec.nodeName}{"\n"}{range .spec.volumes[*]}{.name}{" emptyDir="}{.emptyDir}{"\n"}{end}{"\n"}{end}' | less
```

### 11.4 Corrective actions for DiskPressure

| Cause | Corrective action |
|---|---|
| Old evicted pods visible in API | Delete evicted pod objects after recording evidence |
| Huge container logs | Fix app logging, reduce verbosity, externalize logs, review log rotation |
| Large `emptyDir` | Set `emptyDir.sizeLimit`, use PVC for persistent data, set ephemeral-storage limits |
| Too many unused images | Tune image garbage collection; reduce image churn |
| Build pods filling local disk | Move build cache to PVC or dedicated nodes; limit ephemeral storage |
| Inode exhaustion | Identify small-file explosion; fix app; clean safely |
| Node filesystem too small | Resize node disk or add worker nodes |
| Same node repeatedly pressured | Investigate workload placement, affinity, topology spread, and noisy neighbors |

### 11.5 Clean up evicted pods safely

Evicted pod objects do not consume major node disk by themselves, but they clutter the API and confuse operations.

List:

```bash
oc get pods -A | awk '$4 == "Evicted" {print $1, $2, $4}'
```

Delete after review:

```bash
oc get pods -A | awk '$4 == "Evicted" {print "oc delete pod "$2" -n "$1}'
```

Then run the printed commands manually after checking.

For a direct command:

```bash
oc get pods -A | awk '$4 == "Evicted" {print $1, $2}' | while read ns pod; do
  oc delete pod "$pod" -n "$ns"
done
```

Use the direct version carefully in production.

### 11.6 Add ephemeral-storage requests and limits

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: worker
  namespace: app-prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: worker
  template:
    metadata:
      labels:
        app: worker
    spec:
      containers:
      - name: worker
        image: registry.example.com/app/worker:1.0
        resources:
          requests:
            cpu: 250m
            memory: 512Mi
            ephemeral-storage: 1Gi
          limits:
            cpu: "1"
            memory: 1Gi
            ephemeral-storage: 4Gi
        volumeMounts:
        - name: tmp
          mountPath: /tmp
      volumes:
      - name: tmp
        emptyDir:
          sizeLimit: 2Gi
```

Senior guidance:

- If an app writes temporary files, define ephemeral-storage requests and limits.
- If data must survive restart, use PVC, not container writable layer or `emptyDir`.
- If logs are huge, fix logging behavior; do not only increase disk.

## 12. PIDPressure deep dive

`PIDPressure=True` means available process identifiers are too low.

This is less common than memory or disk pressure but can be severe. When a node runs out of PIDs, new processes cannot start. This can break kubelet, CRI-O, shell sessions, monitoring agents, and application containers.

### 12.1 Common causes

| Cause | Explanation |
|---|---|
| Fork bomb | Application or script rapidly creates processes |
| Thread explosion | Java, Go, Python, or application server creates excessive threads |
| Bad worker pool config | Too many processes per pod |
| Too many pods per node | Aggregate process count becomes high |
| High `podPidsLimit` combined with dense scheduling | Node-level PID capacity can be exhausted |
| Zombie process accumulation | Parent process fails to reap children |

### 12.2 OpenShift PID controls

OpenShift has a pod-level PID limit controlled by kubelet configuration. Modern OpenShift 4.x defaults commonly use a `podPidsLimit` such as `4096`, but always verify the effective config in your cluster.

Check from node debug:

```bash
oc debug node/<node-name>
chroot /host
cat /etc/kubernetes/kubelet.conf | grep -i pids
```

### 12.3 Symptoms

```bash
oc describe node <node-name> | grep -A10 PIDPressure
oc get events -A --sort-by=.lastTimestamp | grep -Ei 'pid|process|fork|pressure|evict'
```

On the node:

```bash
oc debug node/<node-name>
chroot /host
ps -eLf | wc -l
cat /proc/sys/kernel/pid_max
ps -eLf | awk '{print $2}' | sort | uniq -c | sort -nr | head
ps -eo pid,ppid,user,stat,comm,args --sort=ppid | head -100
```

### 12.4 PIDPressure troubleshooting flow

1. Confirm `PIDPressure=True`.
2. Identify process-heavy pods on the node.
3. Map host processes back to containers where needed.
4. Inspect application thread/process behavior.
5. Reduce pod density or fix the offending app.
6. Review `podPidsLimit` only after root cause is understood.

### 12.5 Do not solve PIDPressure only by increasing limits

Increasing `podPidsLimit` can make a bad workload consume more node-level PIDs. It might delay symptoms while increasing blast radius.

Better fixes:

- fix fork/thread leak
- set application worker limits
- reduce replicas per node
- use pod anti-affinity or topology spread
- tune requests so the scheduler does not overpack
- isolate process-heavy workloads to dedicated nodes

## 13. Node-pressure eviction and PodDisruptionBudget

A PodDisruptionBudget protects against voluntary disruptions such as administrator-initiated evictions and some controlled operations. Node-pressure eviction is different.

When kubelet must protect the node from resource starvation, it can terminate pods even if that violates your desired availability plan.

Senior takeaway:

> PDBs are not a substitute for proper resource requests, limits, capacity planning, and node health monitoring.

For high availability, combine:

- multiple replicas
- topology spread constraints
- pod anti-affinity
- correct requests and limits
- PDBs
- sufficient node capacity
- alerting before pressure thresholds are crossed

## 14. Scheduling behavior during node pressure

### 14.1 Pending pod example

A pod might remain Pending with events like:

```bash
oc describe pod <pod> -n <namespace>
```

Example event:

```text
Warning  FailedScheduling  default-scheduler  0/4 nodes are available:
1 node(s) had untolerated taint {node.kubernetes.io/memory-pressure: },
1 node(s) had untolerated taint {node.kubernetes.io/disk-pressure: },
2 Insufficient memory.
```

This means the scheduler could not find a suitable node.

### 14.2 What not to do

Do not immediately patch the pod like this:

```yaml
 tolerations:
 - key: node.kubernetes.io/memory-pressure
   operator: Exists
   effect: NoSchedule
```

That might make the pod schedule, but it can worsen the node condition.

### 14.3 Correct response

1. Check if only one node has pressure or many nodes.
2. Check cluster capacity.
3. Check workload requests.
4. Check whether pressure is real or stale.
5. Fix the pressure source.
6. Add capacity if needed.
7. Retry scheduling.

## 15. DaemonSets and pressure tolerations

DaemonSets are special. Node-level agents often need to run even when the node is under partial pressure:

- CNI agents
- log collectors
- monitoring agents
- node exporters
- storage node plugins
- security agents

The DaemonSet controller automatically adds some tolerations to DaemonSet pods for backward compatibility and node operation reasons.

Example custom DaemonSet toleration:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-helper
  namespace: platform-tools
spec:
  selector:
    matchLabels:
      app: node-helper
  template:
    metadata:
      labels:
        app: node-helper
    spec:
      tolerations:
      - key: node.kubernetes.io/disk-pressure
        operator: Exists
        effect: NoSchedule
      - key: node.kubernetes.io/memory-pressure
        operator: Exists
        effect: NoSchedule
      containers:
      - name: helper
        image: registry.example.com/platform/node-helper:1.0
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 200m
            memory: 256Mi
```

Guidance:

- Keep DaemonSet resource usage small and predictable.
- Give critical DaemonSets appropriate priority.
- Avoid allowing noisy DaemonSets to worsen pressure.
- Do not copy DaemonSet tolerations into normal app Deployments.

## 16. OpenShift-specific management: KubeletConfig and MachineConfigPool

In OpenShift, do not SSH to nodes and permanently edit kubelet config by hand. OpenShift manages node configuration through the Machine Config Operator and `KubeletConfig` custom resources.

### 16.1 View MachineConfigPools

```bash
oc get machineconfigpool
oc get mcp --show-labels
```

### 16.2 Check existing KubeletConfig objects

```bash
oc get kubeletconfig
oc describe kubeletconfig <name>
```

Important:

- OpenShift supports only one `KubeletConfig` object per MachineConfigPool.
- Creating or changing `KubeletConfig` can roll/reboot nodes in the selected pool.
- Bad kubelet config can make nodes unusable.
- Always test on a small/custom pool before applying broadly.

### 16.3 Example KubeletConfig for eviction and image GC

> Validate values against your OpenShift version, workload pattern, and Red Hat guidance before applying.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-eviction-policy
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
  kubeletConfig:
    evictionSoft:
      "memory.available": "500Mi"
      "nodefs.available": "10%"
      "nodefs.inodesFree": "5%"
      "imagefs.available": "15%"
      "imagefs.inodesFree": "10%"
    evictionSoftGracePeriod:
      "memory.available": "1m30s"
      "nodefs.available": "1m30s"
      "nodefs.inodesFree": "1m30s"
      "imagefs.available": "1m30s"
      "imagefs.inodesFree": "1m30s"
    evictionHard:
      "memory.available": "200Mi"
      "nodefs.available": "5%"
      "nodefs.inodesFree": "4%"
      "imagefs.available": "10%"
      "imagefs.inodesFree": "5%"
    evictionPressureTransitionPeriod: "3m"
    imageMinimumGCAge: "5m"
    imageGCHighThresholdPercent: 80
    imageGCLowThresholdPercent: 75
```

Apply:

```bash
oc apply -f worker-eviction-policy.yaml
oc get mcp worker -w
```

### 16.4 Critical warning about `evictionHard`

When configuring `evictionHard`, specify all relevant thresholds. If you configure only one value and omit the others, you can accidentally remove useful defaults or cause garbage collection/eviction behavior to work incorrectly.

Bad example:

```yaml
kubeletConfig:
  evictionHard:
    "memory.available": "500Mi"
```

Better example:

```yaml
kubeletConfig:
  evictionHard:
    "memory.available": "500Mi"
    "nodefs.available": "10%"
    "nodefs.inodesFree": "5%"
    "imagefs.available": "15%"
    "imagefs.inodesFree": "5%"
```

## 17. Node allocatable, reservations, and pressure

Node capacity is not the same as allocatable capacity.

```bash
oc describe node <node-name> | sed -n '/Capacity:/,/System Info:/p'
```

You will see:

```text
Capacity:
  cpu:     8
  memory: 32768000Ki
  pods:   250
Allocatable:
  cpu:     7500m
  memory: 30000000Ki
  pods:   250
```

The scheduler uses `Allocatable` to decide if a node can fit a pod. Allocatable accounts for reservations and eviction buffers.

### 17.1 Why this matters

If you do not reserve enough for system daemons, pods can consume too much and leave kubelet, CRI-O, journald, SDN/OVN, monitoring agents, or storage daemons starved.

If you reserve too much, cluster utilization drops.

A senior platform engineer balances:

- workload density
- reliability
- eviction thresholds
- `systemReserved`
- infrastructure daemon overhead
- node size
- upgrade behavior
- autoscaling behavior

### 17.2 Example resource reservation

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: worker-reserved-resources
spec:
  machineConfigPoolSelector:
    matchLabels:
      pools.operator.machineconfiguration.openshift.io/worker: ""
  kubeletConfig:
    systemReserved:
      cpu: "1000m"
      memory: "1Gi"
```

Do not copy these values blindly. Size them based on node capacity, installed platform components, monitoring agents, storage plugins, and real historical usage.

## 18. Application design to avoid node pressure

### 18.1 Avoid BestEffort production pods

A BestEffort pod has no CPU or memory requests/limits.

Check QoS:

```bash
oc get pod <pod> -n <namespace> -o jsonpath='{.status.qosClass}{"\n"}'
```

Production workloads should normally be `Burstable` or `Guaranteed`, depending on the use case.

### 18.2 Use LimitRange for defaults

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-compute-limits
  namespace: app-prod
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 256Mi
      ephemeral-storage: 512Mi
    default:
      cpu: 500m
      memory: 512Mi
      ephemeral-storage: 2Gi
```

Apply:

```bash
oc apply -f limitrange.yaml
```

### 18.3 Use ResourceQuota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: app-prod-quota
  namespace: app-prod
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    requests.ephemeral-storage: 50Gi
    limits.ephemeral-storage: 100Gi
    pods: "100"
```

Apply:

```bash
oc apply -f quota.yaml
```

### 18.4 Use topology spread constraints

Pressure often appears when too many replicas or noisy pods concentrate on the same node.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: app-prod
spec:
  replicas: 6
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: web
      containers:
      - name: web
        image: registry.example.com/app/web:1.0
        resources:
          requests:
            cpu: 250m
            memory: 512Mi
          limits:
            cpu: "1"
            memory: 1Gi
```

### 18.5 Use anti-affinity for noisy workloads

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: batch-worker
  namespace: app-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: batch-worker
  template:
    metadata:
      labels:
        app: batch-worker
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: batch-worker
              topologyKey: kubernetes.io/hostname
      containers:
      - name: batch-worker
        image: registry.example.com/app/batch-worker:1.0
```

### 19.3 Alerting strategy

Alert before kubelet declares pressure:

| Risk | Warning threshold idea | Critical threshold idea |
|---|---|---|
| Root filesystem available | `< 20%` | `< 12%` |
| Root filesystem inode free | `< 20%` | `< 10%` |
| Node memory available | `< 15%` | `< 8%` |
| PID usage | `> 70%` | `> 85%` |
| Evicted pods | any unexpected increase | repeated or widespread evictions |

Tune thresholds to your environment. Do not blindly use generic numbers for all clusters.

## 20. Operational runbooks

## 20.1 Runbook: Node has `DiskPressure=True`

### Goal

Restore node disk/inode health and prevent new pod evictions.

### Commands

```bash
NODE=<node-name>

oc describe node $NODE | sed -n '/Taints:/,/Conditions:/p'
oc describe node $NODE | sed -n '/Conditions:/,/Addresses:/p'
oc get pods -A -o wide --field-selector spec.nodeName=$NODE
oc get events -A --sort-by=.lastTimestamp | grep -Ei "$NODE|disk|evict|pressure|ephemeral|inode"
```

Debug node:

```bash
oc debug node/$NODE
chroot /host

df -h
df -hi
du -xhd1 /var | sort -h
du -xhd1 /var/lib | sort -h
du -xhd1 /var/lib/kubelet | sort -h
du -xhd1 /var/lib/containers | sort -h
du -xhd1 /var/log | sort -h
journalctl -u kubelet --since "2 hours ago" | grep -Ei 'disk|evict|pressure|image|inode|garbage'
```

### Decision tree

```text
DiskPressure=True
│
├── df -h shows low bytes?
│   ├── /var/lib/containers large → image/writable layer/log issue
│   ├── /var/lib/kubelet large → emptyDir/local volume/pod data issue
│   └── /var/log large → logging/journald issue
│
├── df -hi shows low inodes?
│   └── find small-file explosion and fix app/cache behavior
│
├── one namespace responsible?
│   └── enforce quota, limits, app fix, temporary scale down if needed
│
└── recurring on same nodes?
    └── spread workload, add storage/capacity, tune image GC, review node sizing
```

### Emergency actions

Choose the least risky action:

1. Stop or scale down the offending workload.
2. Delete unnecessary failed/evicted pod objects.
3. Allow kubelet/CRI-O garbage collection to recover space.
4. If safe, cordon the node:

```bash
oc adm cordon $NODE
```

5. Drain only if needed and safe:

```bash
oc adm drain $NODE --ignore-daemonsets --delete-emptydir-data
```

Be careful: `--delete-emptydir-data` deletes pod local ephemeral data.

6. Add/resize worker capacity if pressure is cluster-wide.

### Permanent fixes

- Set ephemeral-storage requests and limits.
- Add `emptyDir.sizeLimit`.
- Fix excessive logging.
- Tune image garbage collection.
- Separate high-churn build/cache workloads.
- Add capacity.
- Improve topology spread.

## 21. Cordon, drain, and pressure conditions

### 21.1 Cordon

Cordon prevents new pods from scheduling to a node.

```bash
oc adm cordon <node-name>
```

This is useful when:

- a node repeatedly hits pressure
- you need to investigate without more workload landing there
- you plan to drain/reboot/replace the node

### 21.2 Drain

Drain evicts pods from the node.

```bash
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data
```

Use with care:

- It can delete `emptyDir` data.
- It can disrupt applications without enough replicas.
- It can be blocked by PDBs.
- It can worsen cluster pressure if other nodes lack capacity.

### 21.3 Uncordon

After fixing:

```bash
oc adm uncordon <node-name>
```

Before uncordoning, verify:

```bash
oc describe node <node-name> | sed -n '/Conditions:/,/Addresses:/p'
oc get node <node-name> -o jsonpath='{.spec.taints}{"\n"}'
oc adm top node <node-name>
```

## 22. How to interpret common event messages

| Message | Meaning | Action |
|---|---|---|
| `The node had condition: [DiskPressure]` | Pod could not remain safely on node due to disk pressure | Inspect node filesystem and pod local storage |
| `The node was low on resource: memory` | Memory eviction happened | Check pod requests, limits, top memory usage, OOM events |
| `The node was low on resource: ephemeral-storage` | Local disk usage triggered eviction | Add ephemeral requests/limits; inspect logs, `emptyDir`, writable layers |
| `had untolerated taint {node.kubernetes.io/disk-pressure: }` | Scheduler avoided a pressured node | Fix node pressure; do not blindly add toleration |
| `Preemption is not helpful for scheduling` | Even evicting lower-priority pods would not make a suitable node | Check constraints, taints, node selectors, resource shortage |
| `pod didn't tolerate node.kubernetes.io/memory-pressure` | Pod lacks toleration for pressure taint | Usually correct behavior for application pods |
| `OOMKilled` | Container exceeded memory or kernel killed it | Review container memory limit, app memory behavior, node pressure |

## 24. Real-world troubleshooting scenarios

## Scenario 1: New pods are Pending after one worker hits DiskPressure

### Symptoms

```text
FailedScheduling: node(s) had untolerated taint {node.kubernetes.io/disk-pressure: }
```

### Senior analysis

The scheduler is working correctly. It is protecting the cluster from placing more workload on a bad node.

### Fix sequence

1. Check the pressured node:

```bash
oc describe node <node>
```

2. Inspect disk and inode usage:

```bash
oc debug node/<node>
chroot /host
df -h
df -hi
du -xhd1 /var/lib/containers /var/lib/kubelet /var/log | sort -h
```

3. Identify workload source.
4. Fix logs/emptyDir/images.
5. Wait for pressure taint to clear.
6. If needed, cordon/drain and repair.
7. Do not solve by adding disk-pressure toleration to application pods.

---

## Scenario 2: Deployment replicas keep getting Evicted due to ephemeral storage

### Symptoms

```text
The node was low on resource: ephemeral-storage.
```

### Root cause pattern

The application writes large temporary files to `/tmp`, logs to container filesystem, or uses `emptyDir` without size limits.

### Fix

Use ephemeral-storage requests/limits and `emptyDir.sizeLimit`:

```yaml
resources:
  requests:
    ephemeral-storage: 1Gi
  limits:
    ephemeral-storage: 4Gi
volumes:
- name: tmp
  emptyDir:
    sizeLimit: 2Gi
```

Move persistent or large temporary data to PVC where appropriate.

---

## Scenario 3: MemoryPressure occurs after a new release

### Symptoms

- New version deployed.
- Memory usage grows.
- Node reports `MemoryPressure=True`.
- Some pods are `OOMKilled` or `Evicted`.

### Senior analysis

This might be:

- app memory leak
- increased cache size
- changed JVM heap behavior
- low memory request
- HPA scaling too many replicas onto same node

### Fix

1. Roll back if production impact is high.
2. Compare old and new memory profiles.
3. Correct app memory configuration.
4. Adjust requests/limits.
5. Spread replicas.
6. Add capacity if the new version legitimately needs more memory.

---

## Scenario 4: PIDPressure caused by one Java service

### Symptoms

```text
PIDPressure=True
```

Node debug:

```bash
ps -eLf | awk '{print $2}' | sort | uniq -c | sort -nr | head
```

One process has thousands of threads.

### Fix

- Set application thread pool limits.
- Tune JVM/container thread behavior.
- Add liveness/readiness protection if service stops responding.
- Keep `podPidsLimit` reasonable.
- Use anti-affinity to avoid multiple process-heavy pods on one node.

## 25. Production prevention checklist

### 25.1 Workload resource hygiene

- [ ] Every production container has CPU and memory requests.
- [ ] Every production container has memory limits unless intentionally omitted for a documented reason.
- [ ] Temporary-file-heavy apps have ephemeral-storage requests/limits.
- [ ] `emptyDir` volumes have `sizeLimit` where possible.
- [ ] No critical production workload runs as BestEffort.
- [ ] JVM and application memory settings are container-aware.

### 25.2 Scheduling and placement hygiene

- [ ] Use topology spread for replicated apps.
- [ ] Use anti-affinity for noisy workloads.
- [ ] Avoid concentrating CI/build/cache/log-heavy workloads on general workers.
- [ ] Use dedicated nodes for special workload classes when needed.
- [ ] Do not add pressure tolerations to ordinary workloads.

### 25.3 Node capacity hygiene

- [ ] Worker disk size matches image churn, logs, and ephemeral usage.
- [ ] Inode availability is monitored.
- [ ] Memory headroom is monitored.
- [ ] PID usage is monitored.
- [ ] `systemReserved` is reviewed for platform daemon footprint.
- [ ] KubeletConfig changes are tested on limited pools first.

### 25.4 Operational hygiene

- [ ] Alerts fire before pressure conditions appear.
- [ ] Evicted pods are reviewed and cleaned up.
- [ ] Repeated pressure on same node triggers root-cause review.
- [ ] Runbooks are documented.
- [ ] Cluster autoscaling or manual capacity process is defined.
- [ ] Upgrade/reboot/drain processes account for reduced capacity.

## 26. Senior-level interview/exam explanation

Use this explanation when asked in an interview or advanced admin discussion:

> Node pressure conditions are kubelet-reported node status conditions that indicate resource starvation on a node, mainly memory, disk/inodes, or process IDs. In OpenShift, when conditions such as `MemoryPressure`, `DiskPressure`, or `PIDPressure` become true, the control plane can map those conditions to taints like `node.kubernetes.io/disk-pressure:NoSchedule`. The scheduler then avoids placing new pods on the affected node unless the pod has a matching toleration. If the pressure continues, the kubelet first tries node-level reclamation, such as image or container garbage collection for disk pressure. If that is not enough, it performs node-pressure eviction and terminates selected pods based on usage above requests, priority, and relative usage. For production, the fix is not to blindly add tolerations. The correct approach is to identify the resource causing pressure, fix workload requests/limits, ephemeral storage, logging, image garbage collection, PID usage, or node capacity, and then allow the node condition and taint to clear.

| Ignoring ephemeral-storage | DiskPressure repeats | Set requests/limits and `emptyDir.sizeLimit` |
| Running BestEffort production pods | High eviction risk | Use realistic requests/limits |
| Only checking `df -h` | Misses inode exhaustion | Check `df -hi` too |
| Deleting random files under kubelet directories | Can corrupt running pods/node state | Use supported cleanup and fix root cause |
| Increasing `podPidsLimit` without investigation | Increases blast radius | Fix process/thread leak first |
| Treating PDB as eviction protection for node pressure | Kubelet pressure eviction is node-protection behavior | Use HA plus resource hygiene |
| Sizing nodes only by CPU | Memory, disk, inodes, and PIDs also matter | Capacity-plan all local resources |
| Forgetting system daemons | Kubelet/CRI-O/CNI/storage need reserved resources | Review `systemReserved` and add headroom |

---

## 29. Final mental model

Think of node pressure as a three-layer control loop:

```text
Layer 1: Detection
  kubelet watches memory, disk, inodes, and PIDs

Layer 2: Scheduling protection
  condition becomes taint; scheduler avoids the node

Layer 3: Node survival
  kubelet reclaims resources; if needed, evicts pods
```

A junior admin sees `DiskPressure=True` and tries to clear the event.  
A senior admin asks:

- What changed?
- Which workload consumed the resource?
- Why did scheduling allow this density?
- Are requests/limits wrong?
- Is node allocatable/reservation wrong?
- Did monitoring warn early enough?
- Is this isolated or systemic?
- Should workload placement change?
- Should node size or pool design change?

That is the correct production mindset for Advanced OpenShift Administration.
