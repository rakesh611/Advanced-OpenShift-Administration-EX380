## 1. What is a node selector?

A **node selector** is a hard scheduling constraint used to tell the Kubernetes/OpenShift scheduler that a pod is eligible to run only on nodes with matching labels.

At pod level, it is defined under:

```yaml
spec:
  nodeSelector:
    key1: value1
    key2: value2
```

A pod using this selector can run only on a node that has **all** of the specified label key/value pairs.

Example:

```yaml
spec:
  nodeSelector:
    workload: database
    zone: dc1
```

The scheduler will consider only nodes with both labels:

```text
workload=database
zone=dc1
```

If no node matches, the pod stays in `Pending` state.

### Simple explanation

Think of node selectors as a gate:

```text
Pod requirement: workload=database
Node A labels:   workload=database     -> allowed
Node B labels:   workload=frontend     -> rejected
Node C labels:   no workload label     -> rejected
```

### Important characteristics

| Feature | Behavior |
|---|---|
| Type | Hard constraint |
| Matching | Exact key/value match |
| Logic between keys | AND |
| Logic between values | No native OR support |
| Runtime enforcement | Scheduling-time only |
| If labels change after pod is running | Existing pod normally continues running |
| Best for | Simple, deterministic placement |
| Not best for | Complex placement rules, preferences, weighted logic |

## 2. Why node selectors matter in OpenShift

In a small test cluster, letting the scheduler place pods anywhere is often acceptable. In enterprise OpenShift, workload placement becomes a major operational topic because clusters commonly host workloads with different performance, compliance, availability, storage, and ownership requirements.

Node selectors help you answer questions like:

- Which nodes should run router, registry, monitoring, logging, or GitOps components?
- Which nodes should run user applications?
- Which nodes are dedicated to PCI, banking, government, or restricted workloads?
- Which nodes have GPUs or high memory?
- Which nodes are close to a storage backend?
- Which nodes belong to a particular availability zone or datacenter?
- Which workloads should not run on infra or control-plane nodes?
- Which projects should be restricted to specific worker pools?

In OpenShift, node selectors exist at multiple levels:

1. **Pod-level node selectors** using `spec.nodeSelector`.
2. **Controller-level node selectors** in Deployment, DeploymentConfig, StatefulSet, DaemonSet, Job, CronJob, etc.
3. **Project-level node selectors** using the namespace annotation `openshift.io/node-selector`.
4. **Cluster-wide default node selector** using the `Scheduler` custom resource.
5. **Operator-specific node placement** using fields such as `nodePlacement`, `nodeSelector`, affinity, and tolerations depending on the Operator/component.

This is why advanced administrators must understand not only Kubernetes `nodeSelector`, but also the OpenShift admission and operator behavior around it.

## 3. How OpenShift schedules a pod

At a high level, scheduling works like this:

```text
Pod created
   |
   v
Admission plugins apply defaults, policies, project selector rules, SCC-related checks, etc.
   |
   v
Scheduler receives unscheduled pod
   |
   v
Filter phase: remove nodes that cannot run the pod
   |
   v
Score phase: rank eligible nodes
   |
   v
Bind phase: assign pod to selected node
   |
   v
Kubelet starts containers on that node
```

Node selectors participate in the **filter phase**. A node that does not match the selector is not a candidate.

The scheduler also evaluates many other constraints:

- node readiness
- taints and tolerations
- CPU and memory requests
- volume topology
- pod/node affinity
- pod anti-affinity
- topology spread constraints
- resource pressure
- node unschedulable status
- security and admission controls
- scheduler profile and scoring configuration

A node selector alone does not guarantee the pod will run. It only narrows the set of eligible nodes.

Example:

```text
Cluster has 10 worker nodes.
Pod has nodeSelector: workload=database.
Only 3 nodes have workload=database.
Scheduler now considers only those 3 nodes.
If all 3 lack CPU, have taints not tolerated, or cannot mount the volume, pod stays Pending.
```

## 4. Node labels: the foundation of node selectors

Node selectors depend on node labels. Without correct labels, selectors do nothing useful.

### View node labels

```bash
oc get nodes --show-labels
```

More readable:

```bash
oc get nodes -L kubernetes.io/hostname,node-role.kubernetes.io/worker,topology.kubernetes.io/zone
```

Show selected labels:

```bash
oc get nodes -L workload,region,zone,type
```

Describe one node:

```bash
oc describe node <node-name>
```

Query nodes by label:

```bash
oc get nodes -l workload=database
oc get nodes -l region=east,type=user-node
```

### Add a label directly to a node

```bash
oc label node <node-name> workload=database
```

Example:

```bash
oc label node worker-1.example.com workload=database region=east
```

Overwrite an existing label:

```bash
oc label node worker-1.example.com workload=database --overwrite
```

Remove a label:

```bash
oc label node worker-1.example.com workload-
oc label node worker-1.example.com region-
```

### Recommended label naming

Use clear, stable, purpose-based labels.

Good labels:

```text
workload=apps
workload=infra
workload=database
region=delhi
zone=dc1
nodepool=gold
hardware=gpu
storage=odf
compliance=pci
team=payments
```

Avoid labels that are too temporary or ambiguous:

```text
fast=true
new=true
special=true
rakesh=true
prod=yes
```

### Kubernetes reserved labels

OpenShift and Kubernetes already place many labels on nodes, such as:

```text
kubernetes.io/hostname
kubernetes.io/os
kubernetes.io/arch
node-role.kubernetes.io/worker
node-role.kubernetes.io/master
node-role.kubernetes.io/control-plane
topology.kubernetes.io/region
topology.kubernetes.io/zone
```

Use built-in labels carefully. Do not modify system-owned labels unless you understand the impact.

### Direct node labels vs MachineSet labels

Direct node labels are quick and useful for troubleshooting, labs, and static clusters. However, in Machine API managed clusters, a replaced node might not keep manually applied node labels.

For production worker pools managed by MachineSets, prefer adding labels to the MachineSet template so new Machines/Nodes are created with the correct labels.

## 5. Pod-level nodeSelector

A direct pod example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-db-node
  namespace: demo
spec:
  nodeSelector:
    workload: database
  containers:
  - name: nginx
    image: registry.access.redhat.com/ubi9/nginx-120
    ports:
    - containerPort: 8080
```

Create it:

```bash
oc apply -f pod.yaml
```

Verify where it landed:

```bash
oc get pod nginx-db-node -n demo -o wide
```

Check the selector on the pod:

```bash
oc get pod nginx-db-node -n demo -o jsonpath='{.spec.nodeSelector}{"\n"}'
```

### Multiple selectors

```yaml
spec:
  nodeSelector:
    workload: database
    region: east
    storage: fast
```

This means:

```text
workload=database AND region=east AND storage=fast
```

All three must match on the same node.

### What happens when no node matches?

The pod remains `Pending`.

```bash
oc get pods -n demo
oc describe pod nginx-db-node -n demo
```

Typical event:

```text
Warning  FailedScheduling  default-scheduler  0/5 nodes are available:
5 node(s) didn't match Pod's node affinity/selector.
```

Note: Kubernetes often reports node selector failures under a combined message containing `node affinity/selector` because node selectors and node affinity are both node-filtering mechanisms.

## 6. Node selectors on controllers

In production, you normally do not create standalone pods. You create controllers such as Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, and Operators.

For controllers, the node selector belongs inside the **pod template**:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload: app
```

### Deployment example

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      nodeSelector:
        workload: app
        region: east
      containers:
      - name: web
        image: registry.access.redhat.com/ubi9/nginx-120
        ports:
        - containerPort: 8080
```

Apply:

```bash
oc apply -f deployment.yaml
```

Verify:

```bash
oc get pods -n demo -o wide
oc get nodes -l workload=app,region=east
```

### Patch an existing Deployment

```bash
oc patch deployment web -n demo --type='merge' -p \
'{"spec":{"template":{"spec":{"nodeSelector":{"workload":"app","region":"east"}}}}}'
```

Watch rollout:

```bash
oc rollout status deployment/web -n demo
oc get pods -n demo -o wide
```

### Remove nodeSelector from a Deployment

```bash
oc patch deployment web -n demo --type='json' -p \
'[{"op":"remove","path":"/spec/template/spec/nodeSelector"}]'
```

### Why not patch the existing pod?

You cannot directly add or change `nodeSelector` on a running scheduled pod. For managed workloads, update the controller pod template. The controller recreates pods with the new scheduling rule.

## 7. Project-level node selectors

OpenShift adds an important enterprise feature: **project-level node selectors**.

A project is backed by a Kubernetes namespace. OpenShift can add a node selector to all pods created in a project using this namespace annotation:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: "region=east,type=user-node"
```

This restricts all workloads in the project to matching nodes unless the pod adds only compatible additional selectors.

### Example namespace

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: east-apps
  annotations:
    openshift.io/node-selector: "region=east,type=user-node"
```

Create:

```bash
oc apply -f namespace.yaml
```

Or edit an existing namespace:

```bash
oc edit namespace east-apps
```

Or patch:

```bash
oc patch namespace east-apps --type=merge -p \
'{"metadata":{"annotations":{"openshift.io/node-selector":"region=east,type=user-node"}}}'
```

Verify:

```bash
oc get namespace east-apps -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
```

### Create a project with an empty selector

For some workloads, especially DaemonSets or cluster tools, you might need to disable project node selector behavior:

```bash
oc adm new-project myproject --node-selector=""
```

For an existing namespace:

```bash
oc patch namespace myproject -p \
'{"metadata":{"annotations":{"openshift.io/node-selector":""}}}'
```

### Important behavior

If a namespace has:

```yaml
openshift.io/node-selector: "region=east"
```

And a pod specifies:

```yaml
nodeSelector:
  region: west
```

OpenShift rejects or prevents scheduling because the pod selector conflicts with the project selector.

Typical error:

```text
pods "pod-4" is forbidden: pod node label selector conflicts with its project node label selector
```

A pod may add additional keys, but it cannot use a different value for a key enforced by the project selector.

Valid:

```yaml
Project selector: region=east
Pod selector:     region=east,workload=api
```

Invalid:

```yaml
Project selector: region=east
Pod selector:     region=west
```

## 8. Cluster-wide default node selector

OpenShift also supports a **cluster-wide default node selector** using the Scheduler custom resource:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: type=user-node,region=east
```

Edit it:

```bash
oc edit scheduler cluster
```

Or patch it:

```bash
oc patch scheduler cluster --type=merge -p \
'{"spec":{"defaultNodeSelector":"type=user-node,region=east"}}'
```

Verify:

```bash
oc get scheduler cluster -o jsonpath='{.spec.defaultNodeSelector}{"\n"}'
```

### Effect

The cluster-wide default selector is applied to pods created in namespaces that do not have a project-wide selector.

Example:

```text
Cluster default: type=user-node,region=east
Pod selector:    workload=api
Final effective: type=user-node AND region=east AND workload=api
```

### Very important caution

Do not set a default selector that blocks cluster components or user workloads unexpectedly.

Bad example:

```yaml
spec:
  defaultNodeSelector: node-role.kubernetes.io/infra=
```

If workloads also require a different role or if not all required namespaces/components are exempted, pods can become unschedulable.

A safer pattern is:

```yaml
spec:
  defaultNodeSelector: node-role.kubernetes.io/worker=
```

But even this should be tested carefully because some OpenShift-managed namespaces and add-on Operators have their own placement needs.

### Wait for effect

After changing the Scheduler `defaultNodeSelector`, OpenShift documentation notes that related API server components may redeploy before the default takes effect. Do not assume the change is instant for every new pod.

## 9. Precedence and merge behavior

Understanding merge behavior is critical for troubleshooting.

### Pod-level only

```text
Pod selector: workload=api
Effective selector: workload=api
```

### Cluster-wide default + pod selector

```text
Cluster default: type=user-node,region=east
Pod selector:    workload=api
Effective:       type=user-node AND region=east AND workload=api
```

The pod must match both.

### Project selector + pod selector

```text
Project selector: region=east
Pod selector:     workload=api
Effective:        region=east AND workload=api
```

Valid if there is no conflict.

### Project selector overrides cluster-wide default

```text
Cluster default: type=user-node,region=east
Project selector: region=west
Effective:        region=west
```

OpenShift treats the project selector as preferred over the cluster-wide default for that namespace.

### Conflict example

```text
Project selector: region=east
Pod selector:     region=west
Result:           forbidden or unschedulable due to conflict
```

### nodeSelector + nodeAffinity

If a pod has both:

```yaml
nodeSelector:
  workload: database

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: region
          operator: In
          values:
          - east
```

Effective requirement:

```text
workload=database AND region in (east)
```

Both must pass.

## 10. Node selector vs node affinity

Node selector is simple. Node affinity is more expressive.

### nodeSelector example

```yaml
spec:
  nodeSelector:
    workload: database
    region: east
```

This supports exact key/value AND matching only.

### Required node affinity example

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: region
            operator: In
            values:
            - east
            - west
          - key: workload
            operator: In
            values:
            - database
```

This supports operators such as:

```text
In
NotIn
Exists
DoesNotExist
Gt
Lt
```

### Preferred node affinity example

```yaml
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: storage
            operator: In
            values:
            - fast
      - weight: 20
        preference:
          matchExpressions:
          - key: region
            operator: In
            values:
            - east
```

This says:

```text
Prefer storage=fast strongly.
Prefer region=east weakly.
But if not possible, still schedule elsewhere if all hard requirements pass.
```

### Comparison

| Requirement | Use nodeSelector | Use nodeAffinity |
|---|---:|---:|
| Exact label match | Yes | Yes |
| Multiple labels with AND | Yes | Yes |
| OR between values | No | Yes |
| Soft preference | No | Yes |
| NotIn / Exists / DoesNotExist | No | Yes |
| Weighted placement | No | Yes |
| Simple admin policy | Yes | Sometimes |
| Complex placement | No | Yes |

### Rule of thumb

Use `nodeSelector` for simple hard placement:

```text
Run this workload only on nodes labeled workload=infra.
```

Use `nodeAffinity` for advanced logic:

```text
Run this workload in east or west, prefer fast storage, avoid GPU nodes, and support weighted preference.
```

## 11. Node selector vs taints and tolerations

Node selectors and taints/tolerations solve different problems.

### Node selector attracts pods to matching nodes

```text
Pod says: I want nodes with workload=infra.
```

### Taint repels pods from nodes unless tolerated

```text
Node says: Do not schedule normal pods here unless they tolerate this taint.
```

Example taint infra nodes:

```bash
oc adm taint nodes <node-name> node-role.kubernetes.io/infra=reserved:NoSchedule
```

Pod toleration:

```yaml
spec:
  tolerations:
  - key: node-role.kubernetes.io/infra
    operator: Equal
    value: reserved
    effect: NoSchedule
```

Node selector:

```yaml
spec:
  nodeSelector:
    node-role.kubernetes.io/infra: ""
```

### Why both are often used together

For dedicated infra nodes:

1. Label nodes as infra.
2. Add a taint to repel normal workloads.
3. Configure infra components with node selector and toleration.

This gives two-way control:

```text
nodeSelector: workload chooses infra nodes
Taint: infra nodes reject non-infra workloads
```

Without taint, other pods may still land on infra nodes if they have no conflicting selector.

Without nodeSelector, a pod with only toleration may run on infra nodes but is not forced to run there.

## 12. Node selector with DaemonSets

A DaemonSet creates one pod per eligible node. Node selectors determine which nodes are eligible.

Example:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
  namespace: agents
spec:
  selector:
    matchLabels:
      app: node-agent
  template:
    metadata:
      labels:
        app: node-agent
    spec:
      nodeSelector:
        workload: app
      containers:
      - name: agent
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["/bin/sh", "-c", "while true; do date; sleep 30; done"]
```

This runs one pod on every node labeled:

```text
workload=app
```

### OpenShift project selector warning for DaemonSets

OpenShift documentation warns that DaemonSet scheduling can be affected by a project's default node selector. If a namespace has a project selector, the DaemonSet pod selector may merge with it, limiting or disturbing placement.

For DaemonSet namespaces, disable the project selector if required:

```bash
oc patch namespace agents -p \
'{"metadata":{"annotations":{"openshift.io/node-selector":""}}}'
```

Or create the namespace/project with an empty selector:

```bash
oc adm new-project agents --node-selector=""
```

### Verify DaemonSet placement

```bash
oc get daemonset node-agent -n agents
oc get pods -n agents -o wide
oc get nodes -l workload=app
```

Number of DaemonSet pods should match the number of eligible nodes, minus nodes that are unschedulable or blocked by taints/resources/security rules.

## 13. Node selectors for infrastructure workloads

OpenShift clusters often use dedicated infrastructure nodes for platform services such as:

- Ingress router
- Image registry
- Monitoring stack
- Logging stack
- GitOps controllers
- Service Mesh control plane
- Cluster observability components
- Some operators and platform agents

### Typical infra labels

```bash
oc label node <node-name> node-role.kubernetes.io/infra=""
oc label node <node-name> workload=infra
```

### Optional infra taint

```bash
oc adm taint nodes <node-name> node-role.kubernetes.io/infra=reserved:NoSchedule
oc adm taint nodes <node-name> node-role.kubernetes.io/infra=reserved:NoExecute
```

### Example node placement pattern

Many OpenShift components use `nodePlacement` rather than raw pod `nodeSelector`.

Example pattern:

```yaml
spec:
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoSchedule
    - key: node-role.kubernetes.io/infra
      value: reserved
      effect: NoExecute
```

Exact fields differ by Operator. Always check the CRD or official docs for the component you are moving.

### Router example pattern

IngressController resources support node placement controls. A typical pattern is:

```yaml
apiVersion: operator.openshift.io/v1
kind: IngressController
metadata:
  name: default
  namespace: openshift-ingress-operator
spec:
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Equal
      value: reserved
      effect: NoSchedule
```

Verify router pods:

```bash
oc get pods -n openshift-ingress -o wide
oc get ingresscontroller default -n openshift-ingress-operator -o yaml
```

### Image registry example pattern

```yaml
apiVersion: imageregistry.operator.openshift.io/v1
kind: Config
metadata:
  name: cluster
spec:
  nodePlacement:
    nodeSelector:
      matchLabels:
        node-role.kubernetes.io/infra: ""
    tolerations:
    - key: node-role.kubernetes.io/infra
      operator: Equal
      value: reserved
      effect: NoSchedule
```

Verify:

```bash
oc get pods -n openshift-image-registry -o wide
oc get configs.imageregistry.operator.openshift.io cluster -o yaml
```

## 14. Node selectors for application workload isolation

A common enterprise use case is isolating application groups.

Example node pools:

```text
workload=frontend
workload=backend
workload=database
workload=batch
workload=infra
```

### Frontend Deployment

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload: frontend
```

### Backend Deployment

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload: backend
```

### Database StatefulSet

```yaml
spec:
  template:
    spec:
      nodeSelector:
        workload: database
```

### Batch CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-report
  namespace: reports
spec:
  schedule: "0 1 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          nodeSelector:
            workload: batch
          containers:
          - name: report
            image: registry.access.redhat.com/ubi9/ubi-minimal

```

### Why this helps

- Prevents noisy batch jobs from affecting latency-sensitive apps.
- Keeps database workloads on tuned nodes.
- Simplifies capacity planning.
- Supports team or environment isolation.
- Makes troubleshooting easier because workload-to-node mapping is predictable.

## 15. Node selectors for storage-heavy workloads

Storage-aware scheduling is important when workloads depend on local disks, fast network storage, ODF/Ceph nodes, or topology-bound persistent volumes.

Example labels:

```text
storage=fast
storage=odf
storage=local-nvme
storage-zone=zone-a
```

StatefulSet example:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
  namespace: database
spec:
  serviceName: db
  replicas: 3
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      nodeSelector:
        storage: fast
      containers:
      - name: db
        image: registry.access.redhat.com/ubi9/ubi
        command: ["/bin/sh", "-c", "sleep infinity"]
        volumeMounts:
        - name: data
          mountPath: /data
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi
```

### Important storage interaction

A pod can be blocked even when node selector matches if the PV has topology restrictions or the volume cannot attach to that node.

Troubleshoot with:

```bash
oc describe pod <pod> -n <ns>
oc describe pvc <pvc> -n <ns>
oc get pv -o wide
oc describe pv <pv-name>
oc get storageclass
```

Look for events like:

```text
pod has unbound immediate PersistentVolumeClaims
volume node affinity conflict
node(s) had volume node affinity conflict
```

In storage-heavy placement, coordinate:

- node labels
- StorageClass topology
- PV node affinity
- access mode
- zone labels
- replica count
- anti-affinity or topology spread constraints

## 16. Node selectors for GPU, high-memory, and special hardware nodes

Special hardware nodes should be explicitly labeled.

Examples:

```bash
oc label node worker-gpu-1 hardware=gpu accelerator=nvidia
oc label node worker-mem-1 hardware=highmem memory-tier=large
oc label node worker-nvme-1 disk=nvme storage=local-fast
```

GPU workload example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: inference
  namespace: ai
spec:
  replicas: 2
  selector:
    matchLabels:
      app: inference
  template:
    metadata:
      labels:
        app: inference
    spec:
      nodeSelector:
        hardware: gpu
      containers:
      - name: inference
        image: example.com/ai/inference:latest
        resources:
          limits:
            nvidia.com/gpu: 1
```

### Important

Node selector only selects the node pool. It does not allocate GPUs by itself. You still need the correct device plugin/operator and resource requests/limits such as:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

For high-memory nodes:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        memory-tier: large
      containers:
      - name: analytics
        resources:
          requests:
            memory: 64Gi
            cpu: "8"
          limits:
            memory: 96Gi
            cpu: "16"
```

The scheduler must satisfy both:

```text
node label match AND enough allocatable resources
```

## 17. Node selectors and autoscaling

When using MachineAutoscaler or Cluster Autoscaler, node selectors become part of capacity design.

Example:

```text
Deployment requires nodeSelector: workload=batch
But no existing node has workload=batch.
```

If an autoscaled MachineSet template has label `workload=batch`, the autoscaler may scale that MachineSet when pending pods require that label.

If no MachineSet can create nodes with the required labels, the pod remains pending forever.

### Production checklist

For every selector used by application teams, confirm:

```bash
oc get nodes -l <key>=<value>
oc get machinesets -n openshift-machine-api -o yaml | grep -A5 -B5 '<key>'
oc get machineautoscaler -n openshift-machine-api
oc get clusterautoscaler
```

### Common autoscaling issue

A pod says:

```yaml
nodeSelector:
  workload: gpu
```

But the MachineSet template says:

```yaml
labels:
  hardware: gpu
```

The autoscaler cannot satisfy `workload=gpu` because the new nodes would be labeled `hardware=gpu`. Standardize labels.

## 18. Node selectors and MachineSets

For Machine API managed clusters, adding labels to the MachineSet template is the production-friendly way to ensure replacement nodes have the correct labels.

### List MachineSets

```bash
oc get machinesets -n openshift-machine-api
```

### Patch MachineSet labels for new nodes

Example:

```bash
oc patch MachineSet <machineset-name> -n openshift-machine-api --type='json' -p='[
  {
    "op":"add",
    "path":"/spec/template/spec/metadata/labels",
    "value":{
      "workload":"database",
      "region":"east"
    }
  }
]'
```

If labels already exist and you need to add only one label, a safer patch might target the specific path:

```bash
oc patch machineset <machineset-name> -n openshift-machine-api --type='merge' -p \
'{"spec":{"template":{"spec":{"metadata":{"labels":{"workload":"database","region":"east"}}}}}}'
```

### Verify MachineSet template

```bash
oc get machineset <machineset-name> -n openshift-machine-api -o yaml | less
```

Look for:

```yaml
spec:
  template:
    spec:
      metadata:
        labels:
          workload: database
          region: east
```

### Important: existing nodes

Changing the MachineSet template affects newly created Machines/Nodes. Existing nodes may not immediately receive the new labels. You can:

1. Label existing nodes directly for immediate effect.
2. Roll or replace Machines in a controlled maintenance window.
3. Scale MachineSet down/up if appropriate and safe.
4. Use MachineConfig/automation/GitOps where applicable for your platform design.

Never blindly scale worker MachineSets down in production without checking workload disruption, PodDisruptionBudgets, storage, and capacity.

## 19. Node selectors and upgrades

Node selectors influence cluster upgrades indirectly because they affect where workloads run and whether workloads can be drained, rescheduled, or restarted.

### Upgrade risk examples

1. A workload is restricted to only one node:

```yaml
nodeSelector:
  kubernetes.io/hostname: worker-1.example.com
```

During node drain, the pod cannot move elsewhere.

2. A project selector points to labels that exist on only one node.

```yaml
openshift.io/node-selector: "team=payments"
```

If only one node has `team=payments`, the namespace has no real HA.

3. A DaemonSet namespace has a restrictive project selector and does not deploy to all intended nodes.

4. Infra components are moved to infra nodes, but there are too few infra nodes for HA.

### Pre-upgrade checks

```bash
oc get pods -A --field-selector=status.phase=Pending
oc adm top nodes
oc get nodes --show-labels
oc get pdb -A
oc get machineconfigpool
oc get co
```

Check workloads with selectors:

```bash
oc get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"/"}{.metadata.name}{" => "}{.spec.nodeSelector}{"\n"}{end}' | grep -v '=> map\[\]'
```

Check namespace selectors:

```bash
oc get ns -o jsonpath='{range .items[*]}{.metadata.name}{" => "}{.metadata.annotations.openshift\.io/node-selector}{"\n"}{end}'
```

## 20. Security and multi-tenancy considerations

Node selectors are not a complete security boundary by themselves, but they are useful in a defense-in-depth platform design.

### What node selectors can do

- Restrict namespaces to specific node pools.
- Keep sensitive workloads away from general workloads.
- Place regulated workloads on compliant nodes.
- Separate noisy workloads from production workloads.
- Enforce default project placement.

### What node selectors cannot do alone

- Prevent privileged pods from accessing host resources.
- Enforce network isolation.
- Replace SCCs/Pod Security Admission.
- Replace RBAC.
- Replace NetworkPolicy.
- Guarantee data encryption or compliance.
- Prevent a cluster-admin from changing placement.

### Recommended multi-tenancy stack

Use node selectors together with:

- RBAC
- SCC / Pod Security Admission
- NetworkPolicy
- ResourceQuota
- LimitRange
- namespace/project lifecycle control
- taints and tolerations
- dedicated node pools
- admission policies
- GitOps-controlled manifests
- monitoring and alerting

### Example: restricted project to PCI nodes

Namespace:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: pci-payments
  annotations:
    openshift.io/node-selector: "compliance=pci"
```

Nodes:

```bash
oc label node worker-pci-1 compliance=pci workload=payments
oc label node worker-pci-2 compliance=pci workload=payments
oc label node worker-pci-3 compliance=pci workload=payments
```

Optional taint:

```bash
oc adm taint nodes worker-pci-1 compliance=pci:NoSchedule
oc adm taint nodes worker-pci-2 compliance=pci:NoSchedule
oc adm taint nodes worker-pci-3 compliance=pci:NoSchedule
```

Workload toleration:

```yaml
spec:
  tolerations:
  - key: compliance
    operator: Equal
    value: pci
    effect: NoSchedule
```

## 22. Common production mistakes

### Mistake 1: Label exists on node, but selector has typo

Node:

```text
workload=database
```

Pod:

```yaml
nodeSelector:
  workload: databse
```

Result: Pending.

### Mistake 2: Using hostname selector for high availability

```yaml
nodeSelector:
  kubernetes.io/hostname: worker-1.example.com
```

This pins the pod to one node. During maintenance or failure, it cannot move.

Use a pool label instead:

```yaml
nodeSelector:
  workload: database
```

### Mistake 3: Project selector conflicts with pod selector

Namespace:

```text
region=east
```

Pod:

```text
region=west
```

Result: forbidden or unschedulable.

### Mistake 4: Setting an aggressive cluster default selector

```yaml
defaultNodeSelector: node-role.kubernetes.io/infra=
```

This can accidentally push normal workloads or platform components into the wrong node pool or make them unschedulable.

### Mistake 5: Labeling only existing nodes, not MachineSet template

Replacement nodes come up without labels, causing future scheduling failures.

### Mistake 6: Using node selector instead of taints

A node selector controls pods that request nodes. It does not repel other pods from those nodes. Use taints for dedicated nodes.

### Mistake 7: Forgetting tolerations on tainted nodes

Pod has:

```yaml
nodeSelector:
  workload: infra
```

Node has:

```text
workload=infra
Taint: workload=infra:NoSchedule
```

If pod has no toleration, it remains Pending.

### Mistake 8: Assuming node selector balances pods

Node selectors restrict nodes. They do not spread pods. Use pod anti-affinity or topology spread constraints for spreading.

### Mistake 9: Applying nodeSelector under wrong YAML path

Wrong:

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  nodeSelector:
    workload: app
```

Correct:

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      nodeSelector:
        workload: app
```

### Mistake 10: Applying selector directly to an existing pod

Scheduled pod placement fields are effectively immutable. Update the controller and recreate pods.

## 23. Best practices

### 1. Design labels before using selectors

Create a label taxonomy:

```text
workload=infra|app|database|batch|gpu
region=north|south|east|west
zone=dc1|dc2|dc3
env=prod|nonprod
compliance=pci|standard
storage=fast|standard|odf
nodepool=gold|silver|bronze
```

### 2. Use pool labels, not individual node labels

Prefer:

```yaml
nodeSelector:
  nodepool: database
```

Avoid:

```yaml
nodeSelector:
  kubernetes.io/hostname: worker-1.example.com
```

### 3. Use MachineSet labels for persistent placement

Patch MachineSet templates for managed worker pools.

### 4. Use project selectors for tenant-level policy

Restrict an entire project:

```yaml
openshift.io/node-selector: "team=payments"
```

### 5. Use taints for dedicated node pools

For truly dedicated pools, use:

- label
- taint
- toleration
- selector

### 6. Use node affinity for complex logic

Use node affinity when you need:

- OR logic
- preferred placement
- Exists/DoesNotExist
- NotIn
- weighted preference

### 7. Keep selectors small and meaningful

Too many labels make scheduling fragile.

Good:

```yaml
nodeSelector:
  workload: database
```

Risky:

```yaml
nodeSelector:
  workload: database
  region: east
  zone: dc1
  hardware: highmem
  storage: fast
  team: payments
  rack: r42
```

The more constraints you add, the fewer eligible nodes remain.

### 8. Monitor pending pods

Create alerts for:

```text
Pod Pending > 5 minutes
FailedScheduling events
DaemonSet desired != current
MachineSet unavailable replicas
Cluster Autoscaler unable to scale
```

### 9. Document ownership

Every custom node label should have an owner and purpose.

Example label registry:

| Label | Owner | Purpose | Allowed values |
|---|---|---|---|
| workload | Platform | Workload pool | infra, app, database, batch |
| compliance | Security | Compliance placement | pci, standard |
| storage | Storage | Storage topology | odf, fast, standard |
| hardware | Platform | Special hardware | gpu, highmem, standard |

### 10. Test failure scenarios

Before production rollout, test:

- node drain
- node replacement
- MachineSet scale out
- zone failure
- selector conflict
- taint/toleration mismatch
- upgrade drain
- workload rollout

## 25. Real-world design scenarios

### Scenario 1: Dedicated infra nodes

Goal:

```text
Run router, registry, monitoring, and logging on infra nodes only.
Normal apps should not run on infra nodes.
```

Design:

```text
Label: node-role.kubernetes.io/infra=""
Taint: node-role.kubernetes.io/infra=reserved:NoSchedule
Infra components: nodeSelector + toleration
Normal namespaces: no toleration
```

Validation:

```bash
oc get pods -n openshift-ingress -o wide
oc get pods -n openshift-image-registry -o wide
oc get pods -n openshift-monitoring -o wide
oc describe node <infra-node> | grep -i taints -A2
```

### Scenario 2: Payments namespace restricted to PCI nodes

Goal:

```text
All payments workloads must run on PCI-certified nodes.
```

Design:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: "compliance=pci"
```

Optional taint:

```bash
oc adm taint nodes -l compliance=pci compliance=pci:NoSchedule
```

Workload toleration:

```yaml
spec:
  tolerations:
  - key: compliance
    value: pci
    effect: NoSchedule
```

### Scenario 3: High-memory analytics

Goal:

```text
Analytics workloads require high-memory nodes but can run in any zone.
```

Use nodeSelector:

```yaml
nodeSelector:
  memory-tier: large
```

Use anti-affinity/topology spread if you need HA across zones.

### Scenario 4: Prefer zone east, but allow west

Do not use nodeSelector because it cannot express preference. Use node affinity:

```yaml
nodeAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    preference:
      matchExpressions:
      - key: topology.kubernetes.io/zone
        operator: In
        values:
        - east
```

### Scenario 5: Batch workloads should not disturb APIs

Design:

```text
API nodes:   workload=api
Batch nodes: workload=batch
```

Batch namespace:

```yaml
openshift.io/node-selector: "workload=batch"
```

API namespace:

```yaml
openshift.io/node-selector: "workload=api"
```

Add quotas and limits to both projects.

## 27. Interview and exam-style questions

### Q1. What is the difference between nodeSelector and node affinity?

`nodeSelector` is a simple hard constraint using exact key/value label matching. Node affinity is more expressive and supports operators like `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt`, as well as required and preferred scheduling rules.

### Q2. If a pod has both nodeSelector and required node affinity, which one wins?

Neither wins. Both must be satisfied. The pod can be scheduled only on nodes matching the node selector and the required node affinity rules.

### Q3. Can you add a nodeSelector directly to an already running pod?

No. Update the controller pod template, such as Deployment, StatefulSet, DaemonSet, DeploymentConfig, Job, or CronJob, and let the workload recreate pods.

### Q4. What happens if a project selector conflicts with a pod selector?

OpenShift rejects pod creation or prevents scheduling because pod node label selector conflicts with the project node label selector.

### Q5. Which is safer for production: labeling a node directly or labeling the MachineSet template?

For Machine API managed worker pools, label the MachineSet template so replacement nodes receive the labels. Direct node labels are useful for quick operations but can be lost when nodes are replaced.

### Q6. Does nodeSelector prevent other pods from running on a node?

No. Node selector only tells a pod where it may run. To repel other pods from a node, use taints and tolerations.

### Q7. Why might a pod remain Pending even though a matching node label exists?

Possible reasons:

- node has taint not tolerated by pod
- insufficient CPU/memory
- node is NotReady or unschedulable
- volume topology conflict
- project selector conflict
- cluster default selector conflict
- affinity/anti-affinity conflict
- max pods reached
- SCC/admission issue

### Q8. How do you restrict all pods in a namespace to specific nodes?

Set the namespace annotation:

```yaml
openshift.io/node-selector: "key=value"
```

Example:

```bash
oc patch namespace payments --type=merge -p \
'{"metadata":{"annotations":{"openshift.io/node-selector":"compliance=pci"}}}'
```

### Q9. How do you configure a cluster-wide default node selector?

Edit or patch the Scheduler CR:

```bash
oc patch scheduler cluster --type=merge -p \
'{"spec":{"defaultNodeSelector":"type=user-node,region=east"}}'
```

### Q10. Why should you be careful with defaultNodeSelector?

Because it applies broadly to pods in namespaces without a project selector. A wrong default can make many workloads unschedulable or force workloads onto inappropriate nodes.

## Final takeaway

For an advanced OpenShift administrator, node selectors are not just a YAML field. They are part of a complete workload placement strategy.

Use them to create predictable placement, but combine them correctly with:

- node label governance
- MachineSet templates
- project selectors
- cluster defaults
- node affinity
- taints and tolerations
- quotas and limits
- topology spread
- storage topology
- monitoring and troubleshooting

A good production design is not simply:

```text
Put nodeSelector in pod YAML.
```

A good production design is:

```text
Define node pools clearly.
Label them persistently.
Protect dedicated nodes with taints.
Apply namespace-level policy where needed.
Use node affinity for complex logic.
Continuously monitor pending pods and scheduling failures.
```
