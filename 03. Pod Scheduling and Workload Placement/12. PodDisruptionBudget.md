# PodDisruptionBudget in OpenShift — Advanced Administration Deep Dive

**Topic area:** Pod Scheduling and Workload Placement  
**Audience:** Advanced OpenShift Administrator / Kubernetes Platform Engineer with ~10 years experience  
**Focus:** OpenShift 4.x / Kubernetes `policy/v1` `PodDisruptionBudget`  
**File purpose:** Study notes, production design guide, troubleshooting runbook, and exam/interview reference.

---

## 1. Executive Summary

A **PodDisruptionBudget**, usually called a **PDB**, is a Kubernetes/OpenShift policy object that limits how many matching application pods may be voluntarily disrupted at the same time.

A PDB does **not** decide where pods are scheduled. It does **not** spread pods across nodes. It does **not** repair an unhealthy app. Its job is narrower and very important:

> During planned disruption, such as node drain, machine replacement, cluster upgrade, node maintenance, or some autoscaler actions, a PDB tells the platform: “Do not evict too many of these pods at once.”

For a senior OpenShift administrator, the key point is this:

> **Scheduling controls placement; PDB controls safe eviction.**

You normally combine PDBs with:

- replica count
- readiness probes
- anti-affinity
- topology spread constraints
- resource requests
- rollout strategy
- HPA minimum replicas
- zone-aware node design
- controlled node maintenance process

Without a PDB, `oc adm drain` or automated node maintenance can evict multiple replicas of the same app at the same time. With a good PDB, OpenShift can continue cluster operations while preserving application availability.

---

## 2. Where PDB Fits in Pod Scheduling and Workload Placement

PDB is often discussed with scheduling, but it is technically part of **policy and eviction control**, not initial placement.

| Feature | Primary job | When it acts |
|---|---|---|
| `nodeSelector` | Places pods on matching nodes | Scheduling time |
| Node affinity | Places pods based on node labels | Scheduling time |
| Pod affinity / anti-affinity | Places pods near or away from other pods | Scheduling time |
| Taints and tolerations | Allows or prevents scheduling onto tainted nodes | Scheduling time and some eviction cases |
| Topology spread constraints | Spreads pods across topology domains | Scheduling time |
| Priority and preemption | Makes room for higher priority pods | Scheduling / preemption |
| **PodDisruptionBudget** | Limits voluntary pod evictions | Eviction / drain / maintenance time |

A PDB is a **safety contract** between the application owner and cluster administrator:

- Application owner defines how much temporary disruption the application can tolerate.
- Cluster administrator performs node maintenance, upgrade, scaling, and drain operations without guessing application availability requirements.

Example:

```text
Deployment: web
Replicas: 5
PDB: maxUnavailable: 1
Meaning: during voluntary eviction, OpenShift should evict only one healthy web pod at a time.
```

## 3. Official API Identity

Modern OpenShift 4.x uses the Kubernetes `policy/v1` API for PDBs.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
  namespace: production
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: web
```

Common short names:

```bash
oc get pdb
oc get poddisruptionbudget
oc get poddisruptionbudgets.policy
```

Important API fields:

| Field | Meaning |
|---|---|
| `spec.selector` | Selects pods protected by the PDB. |
| `spec.minAvailable` | Minimum number or percentage of selected pods that must remain available after eviction. |
| `spec.maxUnavailable` | Maximum number or percentage of selected pods that may be unavailable after eviction. |
| `spec.unhealthyPodEvictionPolicy` | Defines whether unhealthy running pods may be evicted when the budget is already disrupted. |
| `status.currentHealthy` | Current number of selected pods that are Ready. |
| `status.desiredHealthy` | Minimum number of healthy pods required by the PDB. |
| `status.expectedPods` | Total selected pods counted by the budget. |
| `status.disruptionsAllowed` | Number of pod disruptions currently allowed. |

## 4. What Is a Disruption?

A disruption is any event that causes a pod to stop serving, disappear, restart, or become unavailable.

Kubernetes documentation separates disruptions into two categories.

### 4.1 Involuntary disruptions

These are unplanned or unavoidable events.

Examples:

- node hardware failure
- VM crash
- hypervisor issue
- kernel panic
- network partition
- node becomes unreachable
- pod evicted due to node resource pressure
- disk pressure
- memory pressure
- node power failure

A PDB **cannot prevent** involuntary disruptions.

However, involuntary disruptions **do count against the budget**.

Example:

```text
Deployment replicas: 3
PDB: minAvailable: 2
Current state: 1 pod already NotReady due to node failure
Result: disruptionsAllowed becomes 0
Node drain will be blocked until availability recovers.
```

### 4.2 Voluntary disruptions

These are intentional or controlled actions.

Examples:

- `oc adm drain <node>`
- planned node reboot
- worker node maintenance
- cluster upgrade that drains nodes
- MachineConfig update that drains nodes
- cluster autoscaler scale-down
- administrator-initiated eviction
- some descheduler or rebalancing actions if they use the Eviction API

PDBs protect mainly against **voluntary evictions that use the Kubernetes Eviction API**.

Important warning:

> PDBs do not block every possible voluntary disruption. Directly deleting a pod, deleting a deployment, or changing a deployment rollout strategy can bypass or act outside PDB enforcement.

## 5. PDB and the Eviction API

The key mechanism behind PDB is the **Eviction API**.

When a node is drained properly, the tool does not simply delete every pod. It sends eviction requests. The API server checks PDBs before accepting those evictions.

Typical OpenShift node maintenance flow:

```bash
oc adm cordon worker-1
oc adm drain worker-1 --ignore-daemonsets --delete-emptydir-data --timeout=30m
# perform maintenance
oc adm uncordon worker-1
```

During `oc adm drain`:

1. Node is marked unschedulable.
2. Drain identifies evictable pods.
3. For each pod, OpenShift/Kubernetes checks whether eviction is allowed.
4. If the pod is protected by a PDB and `disruptionsAllowed` is `0`, the eviction request is rejected temporarily.
5. Drain retries until the pod can be evicted or the drain times out.

This is why a drain can appear “stuck” even when the cluster is healthy. It may be correctly respecting a PDB.

## 6. PDB Mental Model

Think of PDB as an availability budget.

```text
Available pods now - Minimum healthy pods required = Disruptions currently allowed
```

Example:

```text
Deployment replicas: 5
Healthy pods: 5
PDB: minAvailable: 4
Disruptions allowed: 1
```

After one pod is evicted:

```text
Healthy pods: 4
Minimum required: 4
Disruptions allowed: 0
```

Only after the replacement pod becomes Ready again:

```text
Healthy pods: 5
Minimum required: 4
Disruptions allowed: 1
```

This is why readiness probes matter. A pod is counted as healthy for PDB purposes only when it is Ready.

## 7. `minAvailable` vs `maxUnavailable`

A PDB can use **either** `minAvailable` **or** `maxUnavailable`, not both.

### 7.1 `minAvailable`

`minAvailable` defines how many selected pods must remain available.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: web
```

Meaning:

```text
At least 3 matching pods must remain Ready after a voluntary eviction.
```

Good for:

- quorum-based systems
- fixed minimum service capacity
- explicit availability requirement
- custom controllers where Kubernetes cannot infer desired replicas for `maxUnavailable`

Example:

```text
StatefulSet replicas: 5
Quorum required: 3
PDB: minAvailable: 3
```

### 7.2 `maxUnavailable`

`maxUnavailable` defines how many selected pods may be unavailable.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: web
```

Meaning:

```text
At most 1 matching pod may be unavailable after a voluntary eviction.
```

Good for:

- Deployments
- ReplicaSets
- StatefulSets
- workloads where replica count changes over time
- HPA-managed applications

For most replicated stateless applications, `maxUnavailable: 1` is a good starting point.

### 7.3 Practical comparison

Assume a deployment has 5 replicas.

| PDB | Meaning | Disruptions allowed when all 5 are Ready |
|---|---|---|
| `minAvailable: 4` | Keep at least 4 Ready | 1 |
| `maxUnavailable: 1` | Allow at most 1 unavailable | 1 |
| `minAvailable: 80%` | Keep 80% Ready | 1 |
| `maxUnavailable: 20%` | Allow 20% unavailable | 1 |

For 5 replicas, these may behave similarly. For changing replica counts, `maxUnavailable` is often easier to manage because it scales naturally with desired replicas.

## 8. Percentage Rounding Rules

`minAvailable` and `maxUnavailable` can be integers or percentages.

Examples:

```yaml
minAvailable: 80%
```

```yaml
maxUnavailable: 25%
```

Be careful with rounding.

### 8.1 `minAvailable` percentage

Kubernetes rounds up.

Example:

```text
Replicas: 7
minAvailable: 50%
50% of 7 = 3.5
Rounded up = 4
At least 4 pods must remain Ready.
```

### 8.2 `maxUnavailable` percentage

Kubernetes also rounds up the number of pods that may be disrupted.

Example:

```text
Replicas: 7
maxUnavailable: 30%
30% of 7 = 2.1
Rounded up = 3
Up to 3 pods may be unavailable.
```

This can surprise administrators because the real disruption can be slightly higher than the plain percentage suggests.

### 8.3 Dangerous single-replica percentage case

```yaml
maxUnavailable: 30%
```

For one replica:

```text
30% of 1 = 0.3
Rounded up = 1
The only pod may be evicted.
```

So for single-replica workloads, do not assume a percentage PDB protects availability.

## 9. Selector Design: The Most Common PDB Mistake

A PDB protects pods selected by `spec.selector`.

Example deployment selector:

```yaml
spec:
  selector:
    matchLabels:
      app: web
      tier: frontend
```

Matching PDB selector:

```yaml
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: web
      tier: frontend
```

Best practice:

> The PDB selector should normally match the workload controller selector exactly.

### 9.1 Selector mismatch symptoms

If the PDB selector does not match pods:

```bash
oc get pdb
```

You may see:

```text
NAME      MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web-pdb   N/A             1                 0                     2m
```

Then inspect YAML:

```bash
oc get pdb web-pdb -o yaml
```

Look for:

```yaml
status:
  expectedPods: 0
```

If `expectedPods` is `0`, your selector likely matches no pods.

Check pod labels:

```bash
oc get pods --show-labels
oc get deploy web -o jsonpath='{.spec.selector.matchLabels}'
```

### 9.2 Empty selector danger in `policy/v1`

In `policy/v1`, an empty selector `{}` selects **all pods in the namespace**.

Dangerous example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: accidental-namespace-pdb
spec:
  minAvailable: 1
  selector: {}
```

This can unexpectedly protect many unrelated pods and block node drains.

Do not use an empty selector unless you intentionally want namespace-wide selection.

### 9.3 Null selector vs empty selector

Conceptually:

| Selector form | Meaning in `policy/v1` |
|---|---|
| `selector: null` or omitted | Matches no pods / invalid for intended use depending on validation and context |
| `selector: {}` | Matches all pods in the namespace |
| `selector.matchLabels` | Matches pods with those labels |
| `selector.matchExpressions` | Advanced label selection |

Use explicit labels.

## 10. How PDB Status Is Calculated

A PDB controller continuously updates PDB status.

Example:

```bash
oc get pdb web-pdb -o yaml
```

Output:

```yaml
status:
  currentHealthy: 3
  desiredHealthy: 2
  disruptionsAllowed: 1
  expectedPods: 3
  observedGeneration: 1
```

Meaning:

| Status field | Interpretation |
|---|---|
| `currentHealthy: 3` | Three matching pods are currently Ready. |
| `desiredHealthy: 2` | Two healthy pods are required by the PDB. |
| `disruptionsAllowed: 1` | One pod may currently be voluntarily evicted. |
| `expectedPods: 3` | Three pods are counted under this PDB. |
| `observedGeneration: 1` | Status is calculated for the latest observed PDB generation. |

Fast check:

```bash
oc get pdb -A
```

Detailed check:

```bash
oc describe pdb web-pdb -n production
```

Useful JSONPath:

```bash
oc get pdb web-pdb -n production \
  -o jsonpath='currentHealthy={.status.currentHealthy}{"\n"}desiredHealthy={.status.desiredHealthy}{"\n"}disruptionsAllowed={.status.disruptionsAllowed}{"\n"}expectedPods={.status.expectedPods}{"\n"}'
```

## 11. Healthiness and Readiness

For PDB calculation, a pod is healthy when it has a Ready condition with status `True`.

This means:

- Running but not Ready does not count as healthy.
- CrashLoopBackOff does not count as healthy.
- A pod with failing readiness probe does not count as healthy.
- A pod stuck pulling an image does not count as healthy.
- A pod terminating may reduce availability.

Example issue:

```text
Deployment replicas: 3
PDB: minAvailable: 2
Pods:
- web-1 Ready
- web-2 Ready
- web-3 Running but NotReady

currentHealthy = 2
desiredHealthy = 2
disruptionsAllowed = 0
```

Node drain is blocked because the application is already at minimum availability.

## 12. `unhealthyPodEvictionPolicy`

Modern Kubernetes includes `spec.unhealthyPodEvictionPolicy` for PDBs.

Valid values:

- `IfHealthyBudget`
- `AlwaysAllow`

### 12.1 Default: `IfHealthyBudget`

If not specified, the default behavior corresponds to `IfHealthyBudget`.

With this policy, running but unhealthy pods can be evicted only if the application is not already disrupted.

This gives unhealthy pods a chance to become Ready, but it can also block node drains when misbehaving pods are stuck in states such as:

- `CrashLoopBackOff`
- readiness probe failure
- application starts but never becomes Ready
- bad configuration
- broken dependency

### 12.2 `AlwaysAllow`

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels:
      app: web
```

With `AlwaysAllow`, running but unhealthy pods may be evicted regardless of whether the PDB budget is currently satisfied.

Operational value:

```text
Misbehaving application pods do not block node drain forever.
```

Recommended production approach:

- Use `AlwaysAllow` for workloads where an unhealthy pod should not hold a node hostage.
- Keep `IfHealthyBudget` where preserving recovery chance is more important than drain progress.
- Make this an application/platform standard and document it.

## 13. PDB with Deployments

A common stateless web deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: production
spec:
  replicas: 4
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: registry.access.redhat.com/ubi9/httpd-24
        ports:
        - containerPort: 8080
        readinessProbe:
          httpGet:
            path: /
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
```

PDB:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
  namespace: production
spec:
  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels:
      app: web
```

Meaning:

```text
During voluntary eviction, keep at least 3 of 4 pods available.
```

This works well with node maintenance because one pod can be evicted, a replacement can become Ready, and then the next pod can be evicted.

### Important: Deployment rolling updates are not governed by PDB

PDB status may count pods unavailable during a rollout, but Deployments do not use PDB as the primary control for rolling updates. Deployment rollout availability is controlled by:

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
```

Production guidance:

- Align Deployment `maxUnavailable` with PDB design.
- Avoid rollout strategy and PDB fighting each other during upgrades.
- Use readiness probes to avoid routing traffic to unready pods.
- Avoid `maxUnavailable` values that reduce capacity below SLO.

## 14. PDB with StatefulSets

Stateful workloads need more careful budgeting because replacement can be slower due to:

- ordered termination
- ordered startup
- persistent volume detach/attach
- leader election
- quorum
- replication lag
- storage backend recovery

Example StatefulSet PDB for a 3-replica quorum service:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: zk-pdb
  namespace: data
spec:
  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels:
      app: zookeeper
```

For a 5-replica quorum service:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: quorum-db-pdb
  namespace: data
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: quorum-db
```

Rule of thumb:

```text
For quorum systems, never allow voluntary eviction to drop below quorum.
```

Better design:

- 3 replicas across 3 nodes/zones: `maxUnavailable: 1`
- 5 replicas across 3 zones: `minAvailable: 3` or `maxUnavailable: 1`
- use topology spread or anti-affinity to prevent replicas landing on the same failure domain

PDB alone does not create high availability if all replicas are on the same node.

## 15. PDB with Single-Replica Applications

Single-replica application:

```text
replicas: 1
```

Possible PDB:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: single-app-pdb
spec:
  maxUnavailable: 0
  selector:
    matchLabels:
      app: single-app
```

Meaning:

```text
Do not voluntarily evict the only pod.
```

This can be useful for stateful legacy applications, but it has operational cost:

- node drain can block forever
- cluster upgrade can stall
- worker replacement can be delayed
- MachineConfig rollout can be blocked
- autoscaler cannot remove the node

Production guidance:

- Prefer making the application highly available instead of blocking all disruption.
- Use `maxUnavailable: 0` only where downtime must be manually coordinated.
- Document an emergency runbook to temporarily remove or relax the PDB.
- Do not blindly add strict PDBs to every single-replica workload.

Emergency relaxation example:

```bash
oc patch pdb single-app-pdb -n legacy --type=merge -p '{"spec":{"maxUnavailable":1}}'
```

Or temporarily delete and recreate later:

```bash
oc get pdb single-app-pdb -n legacy -o yaml > single-app-pdb.backup.yaml
oc delete pdb single-app-pdb -n legacy
# perform controlled maintenance
oc apply -f single-app-pdb.backup.yaml
```

## 16. PDB with HPA

Horizontal Pod Autoscaler changes replica count dynamically.

Example:

```text
HPA minReplicas: 2
HPA maxReplicas: 10
PDB: maxUnavailable: 1
```

This is usually safe because at least one voluntary disruption is possible when two pods are healthy.

Dangerous example:

```text
HPA minReplicas: 1
PDB: minAvailable: 1
```

When HPA scales to one replica:

```text
currentHealthy = 1
desiredHealthy = 1
disruptionsAllowed = 0
```

Drain is blocked.

Production guidance:

```text
HPA minReplicas should usually be >= desiredHealthy + allowed disruption.
```

For high availability:

```text
HPA minReplicas: 3
PDB: maxUnavailable: 1
Topology spread: across nodes/zones
```

---

## 17. PDB with Cluster Autoscaler

Cluster autoscaler scale-down may need to evict pods from a node. If workloads on that node are protected by PDBs with no allowed disruptions, scale-down can be skipped or delayed.

Common symptoms:

- nodes remain underutilized
- autoscaler says node cannot be removed
- events mention pods cannot be evicted
- PDB `ALLOWED DISRUPTIONS` is `0`

Platform guidance:

- Do not set every workload to `minAvailable: 100%`.
- Keep application replica counts aligned with PDBs.
- Spread replicas so one node does not hold multiple replicas of the same app.
- Use realistic budgets so autoscaler and maintenance can function.

---

## 18. PDB with OpenShift Cluster Upgrades and MachineConfig

OpenShift upgrades and MachineConfig changes often involve draining and rebooting worker nodes. PDBs can slow or block these operations if application availability rules do not allow eviction.

Examples of maintenance events that may interact with PDBs:

- OpenShift cluster version upgrade
- RHCOS update
- kubelet configuration change
- MachineConfigPool rollout
- worker node reboot
- manual `oc adm drain`
- machine replacement

When an update appears stuck, check:

```bash
oc get mcp
oc describe mcp worker
oc get nodes
oc get pdb -A
```

Look for PDBs with:

```text
ALLOWED DISRUPTIONS = 0
```

Then inspect related pods:

```bash
oc get pods -n <namespace> -o wide
oc describe pdb <pdb-name> -n <namespace>
oc describe pod <pod-name> -n <namespace>
```

Do not immediately delete PDBs in production. First determine whether the application is genuinely below its availability requirement.

## 19. PDB and Priority / Preemption

PDB can be considered during preemption, but it is not an absolute guarantee.

If the scheduler needs to preempt lower-priority pods to schedule a higher-priority pod, it tries to choose victims in a way that does not violate PDBs. If there is no suitable alternative, lower-priority pods may still be preempted even if their PDB would be violated.

Operational meaning:

- PDB is strong for Eviction API based voluntary disruptions.
- PDB is not a hard security or priority boundary.
- Do not use PDB as a replacement for PriorityClass design.

## 20. PDB with Operators and Custom Resources

Many OpenShift workloads are managed by Operators. The visible resource may be a custom resource, while pods are created by Deployments, StatefulSets, ReplicaSets, or custom controllers.

Examples:

- databases managed by an Operator
- Kafka clusters
- monitoring components
- logging components
- storage operators
- GitOps controllers

Before creating your own PDB, check whether the Operator already manages one:

```bash
oc get pdb -n <namespace>
oc get all -n <namespace>
oc get deploy,sts,rs,pods -n <namespace> --show-labels
```

Risks of manually creating PDBs around Operator-managed pods:

- overlapping PDB selectors
- operator reconciliation overwrites changes
- unsupported configuration
- node drain blocked unexpectedly
- PDB protects wrong pods because labels change across upgrades

Best practice:

- Use the Operator-supported configuration field if available.
- Avoid overlapping PDBs.
- Match selectors carefully.
- Read the Operator documentation before adding custom PDBs.

## 21. Overlapping PDBs

A pod should normally be selected by only one PDB.

Bad example:

```text
PDB 1 selector: app=web
PDB 2 selector: tier=frontend
Pod labels: app=web,tier=frontend
```

The pod matches both PDBs.

This can cause eviction to be rejected because Kubernetes cannot safely determine one clear budget for that pod.

Troubleshooting:

```bash
oc get pdb -n production -o yaml
oc get pod <pod-name> -n production --show-labels
```

Check all PDB selectors in the namespace and identify overlaps.

Best practice:

```text
One workload controller selector = one PDB selector.
```

## 22. PDB and DaemonSets

DaemonSet pods run one per selected node. During node drain, DaemonSet pods are normally ignored by drain when using:

```bash
oc adm drain <node> --ignore-daemonsets
```

PDBs are usually not useful for DaemonSet pods in the same way they are useful for Deployments or StatefulSets.

For DaemonSets, availability is typically controlled by:

```yaml
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 10%
```

Use PDB primarily for replicated application workloads, not as the main availability mechanism for DaemonSets.

---

## 23. PDB and Jobs / CronJobs

PDBs are usually not required for restartable Jobs because the Job controller can create replacement pods.

For batch workloads, think differently:

- Can the job restart safely?
- Is the job idempotent?
- Does it checkpoint progress?
- Is completion time more important than node maintenance speed?

For most restartable batch workloads:

```text
Do not create a strict PDB.
```

For critical long-running batch jobs, consider:

- workload-specific retry design
- checkpointing
- `podFailurePolicy`
- priority class
- maintenance windows

## 24. PDB and Topology Spread / Anti-Affinity

PDB cannot protect availability if replicas are poorly placed.

Bad placement:

```text
3 replicas of app=web all run on worker-1
PDB: minAvailable: 2
Drain worker-1 requires evicting all 3 pods
Only one may be evicted at first
Drain blocks until replacements become Ready elsewhere
```

Better placement:

```text
web-1 on worker-1
web-2 on worker-2
web-3 on worker-3
PDB: maxUnavailable: 1
```

Use topology spread:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: web
      containers:
      - name: web
        image: registry.access.redhat.com/ubi9/httpd-24
```

Or pod anti-affinity:

```yaml
spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: web
          topologyKey: kubernetes.io/hostname
```

Best production combination:

```text
replicas >= 3
+ PDB maxUnavailable: 1
+ topology spread across nodes or zones
+ readiness probe
+ resource requests
```

## 25. PDB Design Patterns

### 25.1 Stateless frontend

Requirement:

```text
Keep most serving capacity available during maintenance.
```

Recommended:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: frontend-pdb
spec:
  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels:
      app: frontend
```

Replica guidance:

```text
Minimum replicas: 3
Better replicas: 4+
```

### 25.2 API service with SLO

Requirement:

```text
Maintain at least 80% capacity.
```

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  minAvailable: 80%
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels:
      app: api
```

Be careful with percentage rounding and low replica counts.

### 25.3 Quorum database

Requirement:

```text
Never voluntarily drop below quorum.
```

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: db-pdb
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: db
```

For five replicas, quorum is usually three. Confirm the application’s real quorum behavior before setting this.

### 25.4 Single-replica legacy workload

Requirement:

```text
No voluntary interruption unless manually approved.
```

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: legacy-pdb
spec:
  maxUnavailable: 0
  selector:
    matchLabels:
      app: legacy
```

Document the operational trade-off clearly.

### 25.5 HPA-managed service

Requirement:

```text
Allow one pod disruption while scaling from 3 to 20 replicas.
```

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: hpa-api-pdb
spec:
  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels:
      app: hpa-api
```

```yaml

maxReplicas: 20
```

## 27. Troubleshooting Runbook

### Problem 1: `oc adm drain` is stuck

Symptom:

```text
Cannot evict pod as it would violate the pod's disruption budget.
```

Check:

```bash
oc get pdb -A
oc describe pdb <pdb-name> -n <namespace>
oc get pods -n <namespace> -o wide
```

Likely causes:

- PDB is too strict.
- Application has too few replicas.
- Some pods are NotReady.
- Replacement pods cannot schedule.
- HPA scaled workload too low.
- Topology constraints prevent replacement scheduling.
- PVC attach/detach is slow.
- Selector accidentally covers more pods than intended.

Fix options:

1. Restore app health.
2. Scale replicas up temporarily.
3. Fix readiness probe or dependency.
4. Add capacity to cluster.
5. Relax PDB after approval.
6. Reschedule workload using topology and resource changes.
7. Delete or patch PDB only with application owner approval.

Useful commands:

```bash
oc scale deploy <name> -n <namespace> --replicas=3
oc patch pdb <pdb-name> -n <namespace> --type=merge -p '{"spec":{"maxUnavailable":1}}'
oc describe pod <pod-name> -n <namespace>
oc get events -n <namespace> --sort-by=.lastTimestamp
```

### Problem 2: `ALLOWED DISRUPTIONS` is `0`

Check PDB status:

```bash
oc get pdb <pdb-name> -n <namespace> -o yaml
```

Interpret:

```yaml
status:
  currentHealthy: 2
  desiredHealthy: 2
  disruptionsAllowed: 0
  expectedPods: 3
```

Meaning:

```text
The application is already at the minimum allowed healthy count.
```

Fix:

- Wait for unavailable pod to become Ready.
- Check readiness probe.
- Check image pull, crash loops, PVC, resource pressure.
- Scale up if application supports it.

### Problem 3: PDB created but protects no pods

Check:

```bash
oc get pdb <pdb-name> -n <namespace> -o yaml
```

If:

```yaml
status:
  expectedPods: 0
```

Then selector likely matches no pods.

Fix:

```bash
oc get pods -n <namespace> --show-labels
oc get deploy <deploy-name> -n <namespace> -o jsonpath='{.spec.selector.matchLabels}'
```

Patch selector only by recreating PDB if needed. Some selector changes may be restricted or risky.

### Problem 4: PDB blocks OpenShift upgrade

Check cluster operators and MCP:

```bash
oc get clusterversion
oc get co
oc get mcp
oc describe mcp worker
oc get pdb -A
```

Find strict PDBs:

```bash
oc get pdb -A | awk '$5==0 {print}'
```

Then inspect affected workloads:

```bash
oc describe pdb <pdb> -n <namespace>
oc get pods -n <namespace> -o wide
```

Do not remove PDB blindly. Determine whether application can tolerate disruption.

### Problem 5: Replacement pod cannot schedule

Symptoms:

```text
0/5 nodes are available
node(s) had untolerated taint
node(s) didn't match node selector
insufficient cpu
insufficient memory
pod topology spread constraints not satisfied
```

Check:

```bash
oc describe pod <pending-pod> -n <namespace>
oc get nodes --show-labels
oc adm top nodes
oc get events -n <namespace> --sort-by=.lastTimestamp
```

PDB may not be the root cause. The real issue may be scheduling constraints.

## 29. Operational Decision Matrix

| Workload type | Replica count | Recommended PDB | Notes |
|---|---:|---|---|
| Stateless web/API | 3+ | `maxUnavailable: 1` | Best default for HA apps. |
| Stateless web/API | 10+ | `maxUnavailable: 10%` or `1` | Percentage may be okay, but understand rounding. |
| Critical API | 4+ | `minAvailable: 75%` or `maxUnavailable: 1` | Match SLO and capacity model. |
| Quorum DB | 3 | `maxUnavailable: 1` | Also spread across nodes/zones. |
| Quorum DB | 5 | `minAvailable: 3` | Protect quorum. |
| Single replica legacy | 1 | Usually no PDB or `maxUnavailable: 0` with manual process | Strict PDB blocks drain. |
| Batch Job | variable | Usually no PDB | Prefer retries/checkpointing. |
| DaemonSet | per-node | Usually no PDB | Use DaemonSet update strategy. |
| Operator-managed app | varies | Use Operator-supported config | Avoid manual overlapping PDBs. |

## 30. PDB Best Practices for Production OpenShift

1. **Use PDBs for HA workloads.**  
   Any important replicated service should declare disruption tolerance.

2. **Do not use PDB as a substitute for replicas.**  
   A single pod with a strict PDB is still a single point of failure.

3. **Prefer `maxUnavailable: 1` for many replicated workloads.**  
   It is simple and scales better than hardcoded `minAvailable` when replicas change.

4. **Use `minAvailable` for quorum systems.**  
   Define the real minimum healthy count required for safe operation.

5. **Always check selectors.**  
   Selector mistakes are one of the most common causes of broken or useless PDBs.

6. **Avoid empty selectors.**  
   In `policy/v1`, an empty selector selects all pods in the namespace.

7. **Avoid overlapping PDBs.**  
   One pod should normally be protected by one PDB.

8. **Use readiness probes.**  
   PDB availability depends on Ready pods.

9. **Align HPA minimum replicas with PDB.**  
   Do not let HPA scale below the level required for maintenance.

10. **Combine with topology spread or anti-affinity.**  
    PDB is less effective if all replicas run on the same node.

11. **Be careful with percentages.**  
    Rounding can allow more disruption than expected, especially with small replica counts.

12. **Plan for OpenShift upgrades.**  
    Strict PDBs can slow or block worker node updates.

13. **Document emergency override.**  
    Platform teams need a controlled process to relax a PDB during urgent maintenance.

14. **Use GitOps.**  
    Manage PDBs in Git with the workload manifests.

15. **Monitor PDB status.**  
    Alert on important PDBs stuck with `disruptionsAllowed=0` for long periods.

## 31. Common Bad Practices

### Bad practice: PDB for every workload without thinking

```text
Every namespace gets minAvailable: 100%
```

Result:

- node drains fail
- cluster upgrades stall
- autoscaler cannot scale down
- platform team must manually override many PDBs

### Bad practice: strict PDB with HPA minReplicas 1

```text
HPA minReplicas: 1
PDB minAvailable: 1
```

Result:

- no voluntary disruption allowed when scaled down
- drain blocked

### Bad practice: selector too broad

```yaml
selector:
  matchLabels:
    app: backend
```

But multiple different backend workloads use `app=backend`.

Result:

- one PDB protects unrelated pods
- budget calculation is misleading
- drain behavior is unpredictable

### Bad practice: no topology spread

```text
replicas: 3
all pods on same node
PDB: maxUnavailable: 1
```

Result:

- PDB helps, but drain may be slow
- node failure takes down all replicas anyway

## 32. Monitoring and Alerting Ideas

PDB health can be observed through Kubernetes state metrics if your OpenShift monitoring stack exposes them.

Important signals:

- desired healthy pods
- current healthy pods
- disruptions allowed
- expected pods
- workload replica count
- pod readiness
- node drain duration
- MachineConfigPool update duration

Example operational alert logic:

```text
Critical workload PDB has disruptionsAllowed=0 for more than 15 minutes
AND currentHealthy < expectedPods
```

This indicates the app is already degraded and cannot tolerate maintenance.

Another useful alert:

```text
PDB expectedPods=0 for more than 10 minutes
```

This may indicate a selector mismatch or deleted workload.

## 35. Exam and Interview Notes

### 35.1 One-line definition

```text
A PodDisruptionBudget limits how many matching pods can be voluntarily evicted at the same time, helping maintain application availability during operations such as node drain and cluster maintenance.
```

### 35.2 What PDB protects

Protects against:

- Eviction API based voluntary disruption
- `oc adm drain`
- node maintenance using eviction
- some cluster upgrade and machine replacement flows
- autoscaler scale-down if eviction is used

Does not fully protect against:

- node crash
- direct `oc delete pod`
- deleting the Deployment/StatefulSet
- application rollout strategy
- hardware failure
- resource pressure already happening
- best-effort preemption cases

### 35.3 Fast command set

```bash
oc get pdb -A
oc describe pdb <name> -n <namespace>
oc get pdb <name> -n <namespace> -o yaml
oc get pods -n <namespace> --show-labels

oc adm drain <node> --ignore-daemonsets --delete-emptydir-data --timeout=30m
```

### 35.4 Create PDB quickly

```bash
cat <<'YAML' | oc apply -f -

kind: PodDisruptionBudget
metadata:
  name: web-pdb
  namespace: app1
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: web
YAML
```

### 35.5 Verify allowed disruptions


Expected:

```text
web-pdb   N/A             1                 1                     30s
```

### 35.6 Explain why drain fails

```text
Drain fails because the Eviction API checks the PodDisruptionBudget. If evicting a pod would reduce the number of Ready pods below desiredHealthy, the API rejects the eviction and drain retries.
```

## 36. Real Production Scenario

### Scenario

You manage an OpenShift cluster with three worker nodes. A production API has three replicas and a PDB:

```yaml
maxUnavailable: 1
```

Current placement:

```text
worker-1: api-1
worker-2: api-2
worker-3: api-3
```

All pods are Ready.

PDB status:

```text
currentHealthy: 3
desiredHealthy: 2
disruptionsAllowed: 1
```

You drain `worker-1`.

### Expected behavior

`api-1` can be evicted because after eviction two pods remain Ready.

Then:

- Deployment creates replacement pod.
- Replacement schedules to another available node.
- Replacement becomes Ready.
- PDB returns to `disruptionsAllowed: 1`.

Now another node can be drained.

### Bad version of the same scenario

Placement:

```text
worker-1: api-1, api-2, api-3
worker-2: empty
worker-3: empty
```

Drain `worker-1`:

- first eviction allowed
- second eviction blocked until replacement becomes Ready
- if replacement cannot schedule due constraints, drain stalls

Lesson:

```text
PDB must be combined with good placement strategy.
```

## 38. Senior Admin Checklist When Designing PDBs

Ask these questions:

1. How many replicas does the app normally run?
2. What is the minimum safe number of Ready replicas?
3. Does the app use quorum?
4. Is the app stateless or stateful?
5. How long does a replacement pod take to become Ready?
6. Are replicas spread across nodes and zones?
7. Does HPA ever scale replicas below the safe number?
8. Are readiness probes accurate?
9. Does the workload use local storage or PVCs?
10. Can OpenShift upgrades drain nodes with this budget?
11. Who can approve relaxing the PDB?
12. Is this workload managed by an Operator?

## 39. Important Edge Cases

### 39.1 PDB with `maxUnavailable: 0`

This prevents voluntary eviction.

Good for:

- explicit manual downtime approval
- temporary freeze during critical business period

Bad for:

- routine cluster maintenance
- autoscaling
- automated upgrades

### 39.2 PDB with `minAvailable: 100%`

Equivalent operational effect: no voluntary disruption if all replicas are required.

This can block drains.

### 39.3 PDB with unavailable pods

If pods are already NotReady, PDB budget is consumed.

### 39.4 PDB with slow readiness

Drain speed depends on replacement pods becoming Ready. If startup takes 10 minutes, draining each protected pod may take 10 minutes or more.

### 39.5 PDB with local storage

Drain may require `--delete-emptydir-data` for pods using `emptyDir`. Stateful apps with local persistent storage may have additional constraints.

### 39.6 PDB with strict topology spread

A replacement pod may not schedule if topology spread constraints cannot be satisfied. PDB may then block further evictions.

### 39.7 PDB with taints and dedicated nodes

If replacement pods do not tolerate available nodes, they remain Pending. PDB remains at zero allowed disruptions.

### 39.8 PDB with resource shortage

If no node has enough CPU/memory, replacement pods cannot become Ready. PDB blocks further drain.

## 42. Final Senior-Level Takeaways

- PDB is an eviction safety policy, not a scheduler placement policy.
- It protects mainly against Eviction API based voluntary disruptions.
- It cannot prevent node failure or direct object deletion.
- A useful PDB requires healthy replicas, accurate readiness probes, and enough cluster capacity.
- `minAvailable` is best when you know the required minimum healthy count.
- `maxUnavailable` is often best for replicated controllers and HPA-managed workloads.
- Avoid strict budgets on single-replica workloads unless downtime must be manually coordinated.
- Empty selectors in `policy/v1` can accidentally select all pods in a namespace.
- PDBs can block OpenShift upgrades and node drains when apps are unhealthy or budgets are unrealistic.
- Combine PDB with topology spread constraints, anti-affinity, replicas, and HPA minimums for real high availability.
