## 1. What Workload Isolation Means

**Workload isolation** means ensuring that workloads run only where they are allowed to run, only with the permissions they require, only with the network access they need, and only with the resources they are entitled to consume.

In OpenShift, workload isolation is not one single feature. It is a **layered platform design** built from multiple controls:

- **Scheduling isolation**: place pods on specific node groups.
- **Node isolation**: dedicate nodes for teams, environments, hardware, compliance, or performance.
- **Namespace isolation**: separate tenants, projects, teams, and application boundaries.
- **RBAC isolation**: restrict who can create, update, delete, and administer resources.
- **Resource isolation**: prevent one workload from consuming all CPU, memory, storage, objects, or pods.
- **Security isolation**: prevent privileged container behavior, host access, UID misuse, and unsafe capabilities.
- **Network isolation**: control pod-to-pod, namespace-to-namespace, ingress, and egress communication.
- **Storage isolation**: restrict access to persistent volumes, storage classes, credentials, and snapshots.
- **Operational isolation**: separate system, infra, tenant, CI/CD, GPU, database, and regulated workloads.

A senior administrator should think of isolation as a **bulkhead design**. If one tenant, app, or node class fails or misbehaves, it should not damage the rest of the cluster.

## 2. Why Workload Isolation Matters in Enterprise OpenShift

In small labs, all workloads often run on the same worker nodes. In production, this is risky.

Workload isolation is required for:

### 2.1 Security

You may need to separate:

- Payment workloads from general business workloads.
- Production workloads from development workloads.
- Privileged platform components from tenant workloads.
- High-trust namespaces from low-trust namespaces.
- External-facing apps from internal-only apps.

### 2.2 Compliance

Regulated environments may require separation for:

- PCI-DSS workloads.
- Government workloads.
- Healthcare workloads.
- Financial data workloads.
- Audit-sensitive workloads.

### 2.3 Reliability

Isolation prevents noisy-neighbor problems:

- CPU starvation.
- Memory pressure.
- Disk I/O contention.
- Network saturation.
- Excessive pod churn.
- Eviction storms.

### 2.4 Performance

Some workloads need dedicated hardware or topology:

- GPU workloads.
- High-memory databases.
- Low-latency trading or telecom workloads.
- Storage-heavy services.
- NUMA-sensitive workloads.
- AI/ML workloads.

### 2.5 Operational Control

Platform teams often isolate:

- Router/Ingress pods.
- Registry pods.
- Monitoring stack.
- Logging stack.
- GitOps controllers.
- Operators.
- CI/CD runners.
- Build workloads.

## 3. OpenShift Scheduling Flow: Where Isolation Decisions Happen

When a pod is created, the scheduler evaluates possible nodes and chooses one suitable node.

High-level scheduling process:

```text
Pod created
   |
   v
Admission plugins mutate/validate pod
   |
   v
Scheduler watches unscheduled pod
   |
   v
Filter phase: remove nodes that do not satisfy hard rules
   |
   v
Score phase: rank remaining nodes
   |
   v
Bind phase: bind pod to selected node
   |
   v
Kubelet starts pod on that node
```

Isolation controls participate at different stages:

| Control | Stage | Hard or Soft | Purpose |
|---|---:|---:|---|
| Namespace/project policy | Admission | Hard | Enforce project defaults and allowed behavior |
| Node selector | Scheduling filter | Hard | Pod can run only on matching nodes |
| Required node affinity | Scheduling filter | Hard | Advanced node selection logic |
| Preferred node affinity | Scheduling score | Soft | Prefer matching nodes |
| Taints and tolerations | Scheduling filter / eviction | Hard or soft depending effect | Repel pods from nodes |
| Pod anti-affinity | Filter or score | Hard or soft | Separate pods from other pods |
| Topology spread constraints | Filter or score | Hard or soft | Spread pods across domains |
| Resource requests | Filter | Hard | Node must have allocatable resources |
| Priority/preemption | Scheduling | Hard operational behavior | Higher-priority pods may displace lower-priority pods |
| NetworkPolicy | Runtime traffic | Hard network rule | Control pod communication |
| SCC / Pod security | Admission/runtime | Hard | Restrict Linux/container privileges |

A key principle: **scheduling isolation alone is not security isolation**. Node placement controls decide where pods run; they do not automatically prevent network access, RBAC misuse, unsafe SCC grants, or shared storage mistakes.

## 4. Isolation Models

### 4.1 Soft Isolation

Soft isolation expresses preference, not a strict requirement.

Examples:

- Preferred node affinity.
- Preferred pod anti-affinity.
- `PreferNoSchedule` taint.
- Topology spread with `ScheduleAnyway`.

Use soft isolation when:

- Availability is more important than strict placement.
- You want the scheduler to try best effort placement.
- You do not want workloads to remain Pending if the preferred nodes are full.

### 4.2 Hard Isolation

Hard isolation rejects nodes that do not satisfy the rule.

Examples:

- `nodeSelector`.
- `requiredDuringSchedulingIgnoredDuringExecution` node affinity.
- `NoSchedule` taint without matching toleration.
- Project node selector.
- Topology spread with `DoNotSchedule`.

Use hard isolation when:

- Compliance requires strict placement.
- A workload requires special hardware.
- A workload must never run on general nodes.
- Nodes are dedicated to a tenant or environment.

### 4.3 Physical Isolation

Physical isolation separates workloads onto separate nodes, racks, zones, or clusters.

Examples:

- Dedicated worker nodes for a tenant.
- Infra nodes for routers, monitoring, registry, logging.
- GPU nodes for AI/ML workloads.
- Separate clusters for production and development.

### 4.4 Logical Isolation

Logical isolation separates workloads using policies on shared infrastructure.

Examples:

- Namespaces/projects.
- RBAC.
- ResourceQuota.
- LimitRange.
- NetworkPolicy.
- SCC.
- ServiceAccounts.

Production environments normally use both physical and logical isolation.

## 5. Node Labeling Strategy

Node labels are the foundation for placement. Poor labels create poor scheduling design.

### 5.1 Label Naming Principles

Use labels that describe **platform intent**, not temporary implementation details.

Good examples:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
workload.openshift.io/class=general
workload.openshift.io/class=pci
workload.openshift.io/class=ci
workload.openshift.io/class=gpu
workload.openshift.io/class=database
env=prod
tenant=finance
zone=zone-a
hardware=gpu
storage=fast-ssd
```

Bad examples:

```text
new-node=true
special=yes
rakesh-test=ok
use-this-node=true
node1only=yes
```

Avoid labels tied to one incident or one short-term project.

### 5.2 Recommended Label Dimensions

| Dimension | Example | Use Case |
|---|---|---|
| Workload class | `workload.openshift.io/class=infra` | Infra vs app vs CI |
| Environment | `env=prod` | Prod/dev/stage placement |
| Tenant | `tenant=finance` | Business unit isolation |
| Compliance | `compliance=pci` | Regulated workloads |
| Hardware | `hardware=gpu` | GPU or special devices |
| Storage | `storage=fast-ssd` | Storage-intensive workloads |
| Network zone | `network-zone=dmz` | External-facing workloads |
| Failure domain | `topology.kubernetes.io/zone=zone-a` | HA spreading |

### 5.3 Apply Labels

```bash
oc label node worker-0 workload.openshift.io/class=pci
oc label node worker-1 workload.openshift.io/class=pci
oc label node worker-2 workload.openshift.io/class=general
```

Verify:

```bash
oc get nodes --show-labels
oc get nodes -l workload.openshift.io/class=pci
```

Remove label:

```bash
oc label node worker-0 workload.openshift.io/class-
```

### 5.4 Do Not Manually Label Autoscaled Nodes Only

If nodes are managed by MachineSets or MachinePools, labels added directly to a node can disappear when nodes are replaced.

For persistent labels:

- Add labels to the **MachineSet** template.
- Add labels through supported cloud/machine pool configuration.
- Use MachineConfig/MachineConfigPool only when appropriate for node OS/kubelet configuration.

## 6. Node Selectors

A `nodeSelector` is the simplest hard placement rule.

The pod can schedule only on nodes with matching labels.

### 6.1 Example

Label nodes:

```bash
oc label node worker-0 workload.openshift.io/class=payments
oc label node worker-1 workload.openshift.io/class=payments
```

Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payments
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      nodeSelector:
        workload.openshift.io/class: payments
      containers:
      - name: payment-api
        image: registry.example.com/apps/payment-api:v1
        resources:
          requests:
            cpu: 250m
            memory: 512Mi
          limits:
            cpu: "1"
            memory: 1Gi
```

### 6.2 Characteristics

| Feature | Behavior |
|---|---|
| Type | Hard requirement |
| Logic | Exact key/value match |
| Expressiveness | Basic only |
| Good for | Simple node groups |
| Weakness | No `In`, `NotIn`, `Exists`, preference, weighted rules |

### 6.3 When to Use Node Selectors

Use node selectors for:

- Simple workload class placement.
- Exam/lab tasks.
- Simple production patterns.
- Project-wide placement enforcement.

Use node affinity instead when:

- You need multiple acceptable values.
- You need `In`, `NotIn`, `Exists`, `DoesNotExist`.
- You need soft preference.
- You need complex node selection logic.

## 7. Project-Level Node Selectors

OpenShift supports project-level node selectors using the namespace annotation:

```text
openshift.io/node-selector
```

This is very useful for tenant or environment isolation.

### 7.1 Example: Force All Pods in a Project to PCI Nodes

```bash
oc new-project pci-apps
oc annotate namespace pci-apps openshift.io/node-selector='workload.openshift.io/class=pci'
```

Verify:

```bash
oc get namespace pci-apps -o yaml | grep -A3 annotations
```

Now, pods created in this namespace are constrained to nodes matching:

```text
workload.openshift.io/class=pci
```

### 7.2 Why Project-Level Selectors Are Powerful

They allow platform administrators to enforce placement without relying on every developer to set `nodeSelector` correctly.

This is important because developers may forget placement rules in:

- Deployment YAML.
- Helm values.
- Kustomize overlays.
- Operators.
- CI/CD generated manifests.

### 7.3 Example Namespace YAML

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: finance-prod
  annotations:
    openshift.io/node-selector: "tenant=finance,env=prod"
```

### 7.4 Operational Warning

If a pod has a conflicting node selector, it will not schedule or may be rejected depending on admission behavior.

Example conflict:

Namespace selector:

```text
tenant=finance
```

Pod selector:

```yaml
nodeSelector:
  tenant: hr
```

Result: pod cannot be placed because no node can satisfy both tenant labels at the same time.

## 8. Cluster-Wide Default Node Selectors

A cluster-wide default node selector applies default placement for pods that do not have a more specific project selector.

Edit scheduler configuration:

```bash
oc edit scheduler cluster
```

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: workload.openshift.io/class=general
  mastersSchedulable: false
```

### 8.1 Use Cases

Use cluster-wide selectors to:

- Keep normal tenant pods off infra nodes.
- Keep normal pods on general worker nodes.
- Prevent accidental scheduling to special hardware nodes.

### 8.2 Be Careful

A cluster-wide default node selector can break workloads if:

- Operators need to run on specific nodes.
- DaemonSets expect to run on all workers.
- Nodes do not have the required label.
- Existing automation creates pods without correct overrides.

### 8.3 Project Selector Precedence

In OpenShift, a project node selector takes preference over the cluster-wide default node selector.

This allows a general cluster default such as:

```text
workload.openshift.io/class=general
```

while allowing a namespace such as `pci-apps` to use:

```text
workload.openshift.io/class=pci
```

## 9. Node Affinity

Node affinity is a more expressive scheduling mechanism than node selectors.

It supports:

- Hard rules.
- Soft preferences.
- Multiple acceptable values.
- Operators such as `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt`.

### 9.1 Required Node Affinity

Required node affinity is a hard rule.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: report-engine
  namespace: analytics
spec:
  replicas: 2
  selector:
    matchLabels:
      app: report-engine
  template:
    metadata:
      labels:
        app: report-engine
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: workload.openshift.io/class
                operator: In
                values:
                - analytics
                - high-memory
      containers:
      - name: report-engine
        image: registry.example.com/apps/report-engine:v1
```

This pod can schedule only on nodes where:

```text
workload.openshift.io/class=analytics
```

or

```text
workload.openshift.io/class=high-memory
```

### 9.2 Preferred Node Affinity

Preferred node affinity is a soft rule.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-cache
  namespace: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-cache
  template:
    metadata:
      labels:
        app: web-cache
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 80
            preference:
              matchExpressions:
              - key: storage
                operator: In
                values:
                - fast-ssd
      containers:
      - name: web-cache
        image: registry.example.com/apps/web-cache:v1
```

The scheduler prefers `storage=fast-ssd` nodes, but may use other nodes if needed.

### 9.3 Required vs Preferred

| Type | Hard/Soft | Result if no matching node |
|---|---|---|
| `requiredDuringSchedulingIgnoredDuringExecution` | Hard | Pod stays Pending |
| `preferredDuringSchedulingIgnoredDuringExecution` | Soft | Pod can schedule elsewhere |

### 9.4 Meaning of `IgnoredDuringExecution`

If a pod is already running and node labels change later, the pod is not automatically evicted just because its affinity rule is no longer satisfied.

This matters in operations:

- Label changes do not automatically rebalance old pods.
- You may need rollout restart or descheduler behavior.
- Always validate placement after label changes.

## 10. Taints and Tolerations

Taints are applied to nodes. Tolerations are applied to pods.

Taints repel pods unless those pods tolerate the taint.

### 10.1 Basic Example

Taint a node:

```bash
oc adm taint node worker-pci-0 dedicated=pci:NoSchedule
```

Pod toleration:

```yaml
spec:
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "pci"
    effect: "NoSchedule"
```

Now the pod is allowed to schedule on tainted PCI nodes.

### 10.2 Taint Effects

| Effect | Meaning |
|---|---|
| `NoSchedule` | New pods without toleration cannot schedule on the node |
| `PreferNoSchedule` | Scheduler tries to avoid placing pods without toleration, but not guaranteed |
| `NoExecute` | Existing pods without toleration can be evicted; new pods without toleration cannot schedule |

### 10.3 Remove Taint

```bash
oc adm taint node worker-pci-0 dedicated=pci:NoSchedule-
```

Or remove by key:

```bash
oc adm taint node worker-pci-0 dedicated-
```

### 10.4 Toleration with Exists

```yaml
spec:
  tolerations:
  - key: "dedicated"
    operator: "Exists"
    effect: "NoSchedule"
```

This tolerates any value for key `dedicated`.

Use `Exists` carefully. It can be too broad.

### 10.5 `NoExecute` with `tolerationSeconds`

```yaml
spec:
  tolerations:
  - key: "node.kubernetes.io/not-ready"
    operator: "Exists"
    effect: "NoExecute"
    tolerationSeconds: 300
```

This means the pod tolerates the taint for 300 seconds before eviction.

## 11. Combining Taints, Tolerations, and Affinity for Real Isolation

This is one of the most important senior-level points.

### 11.1 Toleration Alone Is Not Enough

A toleration allows a pod to run on a tainted node. It does **not** force the pod to run there.

Example:

```yaml
spec:
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "pci"
    effect: "NoSchedule"
```

This pod can run on PCI nodes, but it may also run on general nodes unless it also has node selector or node affinity.

### 11.2 Node Affinity Alone Is Not Enough

Node affinity attracts selected workloads to matching nodes. It does **not** stop other pods from landing on those nodes.

Example:

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: workload.openshift.io/class
            operator: In
            values:
            - pci
```

This requires the pod to run on PCI nodes, but normal pods may still run on PCI nodes unless those nodes are tainted.

### 11.3 Real Dedicated Isolation Pattern

For real workload isolation:

1. **Label dedicated nodes**.
2. **Taint dedicated nodes**.
3. **Add required node affinity or nodeSelector to target workloads**.
4. **Add matching toleration to target workloads**.
5. **Optionally set project-level node selector**.
6. **Add ResourceQuota, LimitRange, NetworkPolicy, and SCC controls**.

Example node setup:

```bash
oc label node worker-pci-0 workload.openshift.io/class=pci
oc label node worker-pci-1 workload.openshift.io/class=pci

oc adm taint node worker-pci-0 dedicated=pci:NoSchedule
oc adm taint node worker-pci-1 dedicated=pci:NoSchedule
```

Workload spec:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pci-api
  namespace: pci-prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: pci-api
  template:
    metadata:
      labels:
        app: pci-api
        workload: pci
    spec:
      tolerations:
      - key: "dedicated"
        operator: "Equal"
        value: "pci"
        effect: "NoSchedule"
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: workload.openshift.io/class
                operator: In
                values:
                - pci
      containers:
      - name: pci-api
        image: registry.example.com/apps/pci-api:v1
        resources:
          requests:
            cpu: 500m
            memory: 512Mi
          limits:
            cpu: "1"
            memory: 1Gi
```

This gives two-way control:

- Taint keeps general pods away from PCI nodes.
- Affinity forces PCI pods onto PCI nodes.
- Toleration grants PCI pods permission to use PCI nodes.

## 12. Pod Anti-Affinity and Topology Spread Constraints

Node isolation decides which node pool can host a workload. Pod anti-affinity and topology spread decide how replicas are distributed within that pool.

### 12.1 Pod Anti-Affinity

Pod anti-affinity prevents or discourages pods from being colocated with matching pods.

Example: avoid putting two replicas of the same app on the same node.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api
  namespace: orders
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-api
  template:
    metadata:
      labels:
        app: order-api
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - order-api
            topologyKey: kubernetes.io/hostname
      containers:
      - name: order-api
        image: registry.example.com/apps/order-api:v1
```

### 12.2 Problem with Hard Anti-Affinity

If you have 3 replicas but only 2 eligible nodes, one pod remains Pending.

Hard anti-affinity is good for strict HA, but can reduce availability during node failure or maintenance.

### 12.3 Preferred Anti-Affinity

```yaml
spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: order-api
          topologyKey: kubernetes.io/hostname
```

This spreads when possible but does not block scheduling.

### 12.4 Topology Spread Constraints

Topology spread constraints give more balanced control than basic anti-affinity.

Example: spread replicas across nodes.

```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: order-api
```

Example: spread replicas across zones.

```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app: order-api
```

### 12.5 `DoNotSchedule` vs `ScheduleAnyway`

| Value | Behavior |
|---|---|
| `DoNotSchedule` | Hard enforcement; pod remains Pending if spread cannot be satisfied |
| `ScheduleAnyway` | Soft enforcement; scheduler still tries to reduce skew |

### 12.6 Best Practice

For production:

- Use node affinity to select the right node pool.
- Use topology spread to spread replicas across hostname and zone.
- Avoid too many hard rules unless you have enough capacity.

Example combined:

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: workload.openshift.io/class
            operator: In
            values:
            - pci
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: pci-api
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app: pci-api
```

## 13. Dedicated Nodes

Dedicated nodes are worker nodes reserved for a workload class, team, tenant, or environment.

### 13.1 Common Dedicated Node Types

| Dedicated Node Type | Example Use |
|---|---|
| Tenant dedicated | Finance, HR, banking app |
| Environment dedicated | Production only |
| Compliance dedicated | PCI, government, audit workloads |
| Hardware dedicated | GPU, FPGA, high-memory |
| Performance dedicated | Low-latency or database workloads |
| CI/CD dedicated | Build workloads and runners |
| Edge/DMZ dedicated | External-facing workloads |

### 13.2 Dedicated Node Implementation

```bash
# Label nodes
oc label node worker-fin-0 tenant=finance env=prod workload.openshift.io/class=tenant-dedicated
oc label node worker-fin-1 tenant=finance env=prod workload.openshift.io/class=tenant-dedicated

# Taint nodes
oc adm taint node worker-fin-0 dedicated=finance:NoSchedule
oc adm taint node worker-fin-1 dedicated=finance:NoSchedule

# Namespace selector
oc annotate namespace finance-prod openshift.io/node-selector='tenant=finance,env=prod'
```

Deployment toleration:

```yaml
spec:
  tolerations:
  - key: dedicated
    operator: Equal
    value: finance
    effect: NoSchedule
```

### 13.3 Dedicated Does Not Mean Secure by Default

Dedicated nodes do not automatically isolate:

- Network traffic.
- RBAC permissions.
- Secrets access.
- SCC privileges.
- Image pull credentials.
- Storage access.

Dedicated node isolation must be combined with namespace, RBAC, security, network, and storage controls.

## 14. Infrastructure Nodes

Infrastructure nodes are usually used to run OpenShift platform infrastructure workloads separately from application workloads.

Typical infrastructure workloads include:

- Ingress/router pods.
- Image registry.
- Monitoring components.
- Logging components.
- Cluster observability components.
- GitOps/platform controllers where required.

### 14.1 Why Isolate Infrastructure Workloads?

Reasons:

- Prevent tenant apps from competing with routers or monitoring.
- Improve platform stability.
- Keep system components on predictable nodes.
- Simplify capacity planning.
- Separate infra subscription/accounting considerations where applicable.

### 14.2 Label Infra Nodes

```bash
oc label node worker-infra-0 node-role.kubernetes.io/infra=
oc label node worker-infra-1 node-role.kubernetes.io/infra=
oc label node worker-infra-2 node-role.kubernetes.io/infra=
```

Optional workload label:

```bash
oc label node worker-infra-0 workload.openshift.io/class=infra
oc label node worker-infra-1 workload.openshift.io/class=infra
oc label node worker-infra-2 workload.openshift.io/class=infra
```

### 14.3 Taint Infra Nodes

```bash
oc adm taint node worker-infra-0 node-role.kubernetes.io/infra=:NoSchedule
oc adm taint node worker-infra-1 node-role.kubernetes.io/infra=:NoSchedule
oc adm taint node worker-infra-2 node-role.kubernetes.io/infra=:NoSchedule
```

Then platform workloads that should run there need suitable placement and tolerations.

### 14.4 Important Warning

Do not taint infra nodes until required platform components have tolerations and placement rules. Otherwise, routers, registry, monitoring, or other platform pods may become Pending.

## 15. MachineSets, MachineConfigPools, and Persistent Node Isolation

### 15.1 Why MachineSet-Level Labels Matter

If you label a node manually and that node is deleted/replaced, the new node might not have the label. This breaks workload placement.

For cloud IPI clusters, apply labels and taints in the MachineSet template.

Example conceptual MachineSet snippet:

```yaml
apiVersion: machine.openshift.io/v1beta1
kind: MachineSet
metadata:
  name: cluster-worker-pci-us-east-1a
  namespace: openshift-machine-api
spec:
  template:
    spec:
      metadata:
        labels:
          workload.openshift.io/class: pci
          compliance: pci
      taints:
      - key: dedicated
        value: pci
        effect: NoSchedule
```

The exact MachineSet provider section differs by platform: AWS, vSphere, Azure, GCP, bare metal, OpenStack, etc.

### 15.2 MachineConfigPool for Node Configuration Isolation

Use a MachineConfigPool when a node class needs different operating system or kubelet-level configuration.

Examples:

- Infra nodes with different kubelet config.
- Worker-rt nodes for real-time tuning.
- Nodes with special kernel arguments.
- Nodes with custom systemd units.

Example MCP:

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: pci
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - pci
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/pci: ""
```

Then label nodes:

```bash
oc label node worker-pci-0 node-role.kubernetes.io/pci=
oc label node worker-pci-1 node-role.kubernetes.io/pci=
```

### 15.3 Senior-Level Rule

Use these layers correctly:

| Layer | Use For |
|---|---|
| Node label | Scheduling identity |
| Taint | Repelling unauthorized workloads |
| Namespace selector | Project-wide scheduling enforcement |
| MachineSet label/taint | Persistent node lifecycle configuration |
| MachineConfigPool | OS/kubelet configuration grouping |
| NetworkPolicy | Runtime traffic boundary |
| SCC/RBAC | Security and permission boundary |

## 16. Namespace, RBAC, Quota, and LimitRange Isolation

Scheduling isolation decides where workloads run. Namespace policy controls what tenants can do.

### 16.1 Namespace as Isolation Boundary

In OpenShift, projects are Kubernetes namespaces with additional OpenShift behavior.

Use one namespace per:

- Application environment.
- Team.
- Tenant.
- Security zone.
- Lifecycle stage.

Example:

```text
finance-dev
finance-test
finance-prod
hr-prod
platform-monitoring
build-runners
pci-prod
```

### 16.2 RBAC Isolation

Give users only required permissions.

Examples:

```bash
# Developer can edit objects in one namespace
oc adm policy add-role-to-user edit alice -n finance-dev

# Auditor can view objects
oc adm policy add-role-to-user view auditor -n finance-prod

# Team lead can administer namespace resources
oc adm policy add-role-to-user admin lead1 -n finance-prod
```

Avoid unnecessary `cluster-admin`.

### 16.3 ResourceQuota

ResourceQuota prevents one namespace from consuming the cluster.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: finance-prod-quota
  namespace: finance-prod
spec:
  hard:
    pods: "50"
    requests.cpu: "20"
    requests.memory: 80Gi
    limits.cpu: "40"
    limits.memory: 160Gi
    services: "20"
    secrets: "50"
    configmaps: "50"
    persistentvolumeclaims: "20"
```

### 16.4 LimitRange

LimitRange sets defaults and bounds for pods/containers.

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: finance-prod-limits
  namespace: finance-prod
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 256Mi
    default:
      cpu: 500m
      memory: 512Mi
    min:
      cpu: 10m
      memory: 64Mi
    max:
      cpu: "2"
      memory: 4Gi
```

### 16.5 Why Quota and LimitRange Matter for Workload Isolation

Without requests and limits:

- Scheduler cannot accurately place pods.
- HPA may not behave correctly for CPU-based scaling.
- Noisy workloads can overconsume resources.
- Node pressure and evictions become more likely.
- Tenant fairness is weak.

## 17. Security Isolation with SCC, Pod Security, SELinux, and ServiceAccounts

OpenShift security isolation is stronger than vanilla Kubernetes defaults because of Security Context Constraints, SELinux integration, and default restricted behavior.

### 17.1 Security Context Constraints

SCCs define what security features a pod can use.

They control things such as:

- Running privileged containers.
- Running as root or fixed UID.
- Host networking.
- Host PID/IPC.
- HostPath volume usage.
- Linux capabilities.
- SELinux context.
- FSGroup and supplemental groups.
- Privilege escalation.

### 17.2 Default Approach

Use the default restricted behavior wherever possible.

Avoid granting:

```text
privileged
anyuid
hostnetwork
hostaccess
```

unless the workload truly needs it.

### 17.3 Grant SCC to a ServiceAccount, Not a User

Preferred:

```bash
oc create sa app-sa -n finance-prod
oc adm policy add-scc-to-user anyuid -z app-sa -n finance-prod
```

Deployment:

```yaml
spec:
  serviceAccountName: app-sa
```

Avoid broad SCC grants to all users or large groups.

### 17.4 Validate SCC Used by Pod

```bash
oc describe pod <pod-name> -n <namespace> | grep openshift.io/scc
```

### 17.5 Security Isolation Best Practices

- Use separate ServiceAccounts per app.
- Do not run all apps under `default` ServiceAccount.
- Avoid `anyuid` unless needed.
- Avoid `privileged` except trusted node agents.
- Drop Linux capabilities.
- Set `allowPrivilegeEscalation: false`.
- Use `seccompProfile: RuntimeDefault`.
- Avoid `hostNetwork`, `hostPID`, `hostIPC`.
- Avoid `hostPath` unless required and tightly controlled.
- Use read-only root filesystem if the app supports it.

Example secure container context:

```yaml
securityContext:
  allowPrivilegeEscalation: false
  capabilities:
    drop:
    - ALL
  runAsNonRoot: true
  seccompProfile:
    type: RuntimeDefault
```

## 18. Network Isolation with NetworkPolicy

Scheduling isolation does not block traffic. A pod on a dedicated node can still talk to other pods unless network policy prevents it.

### 18.1 Default Deny Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: pci-prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
```

### 18.2 Default Deny Egress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: pci-prod
spec:
  podSelector: {}
  policyTypes:
  - Egress
```

Warning: default deny egress can block DNS, image registry access, database access, APIs, and external endpoints unless explicitly allowed.

### 18.3 Allow Same Namespace Traffic

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-namespace
  namespace: pci-prod
spec:
  podSelector: {}
  ingress:
  - from:
    - podSelector: {}
  policyTypes:
  - Ingress
```

### 18.4 Allow Ingress from OpenShift Router Namespace

In many clusters, router pods run in `openshift-ingress`. You may allow ingress traffic from router pods to app pods.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-openshift-ingress
  namespace: pci-prod
spec:
  podSelector:
    matchLabels:
      app: pci-api
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-ingress
  policyTypes:
  - Ingress
```

### 18.5 Allow Application to Database

Database namespace label:

```bash
oc label namespace pci-db zone=pci-db
```

Application namespace label:

```bash
oc label namespace pci-prod zone=pci-app
```

NetworkPolicy in database namespace:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-pci-api-to-db
  namespace: pci-db
spec:
  podSelector:
    matchLabels:
      app: mysql
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          zone: pci-app
      podSelector:
        matchLabels:
          app: pci-api
    ports:
    - protocol: TCP
      port: 3306
  policyTypes:
  - Ingress
```

### 18.6 Network Isolation Checklist

- Start with default deny for sensitive namespaces.
- Allow only required ingress.
- Allow only required egress.
- Allow DNS explicitly if using egress deny.
- Allow router traffic if route exposure is required.
- Allow monitoring scraping only from monitoring namespace if needed.
- Avoid broad namespace selectors such as `{}` unless intentional.

## 19. Storage Isolation

Storage is often overlooked in workload isolation.

### 19.1 Risks

- One namespace mounts another namespace's data accidentally.
- Reused static PV exposes old data.
- Wrong reclaim policy deletes or retains sensitive data unexpectedly.
- Broad storage class access allows tenants to create expensive volumes.
- Backups and snapshots expose data across tenants.

### 19.2 Storage Isolation Controls

Use:

- Separate PVCs per namespace/app.
- Separate StorageClasses for performance/compliance classes.
- ResourceQuota for PVC count and storage requests.
- Encryption at rest where required.
- Correct reclaim policy.
- RBAC restrictions on PV and StorageClass administration.
- Backup policy separation.

### 19.3 Example Storage Quota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: storage-quota
  namespace: pci-prod
spec:
  hard:
    persistentvolumeclaims: "10"
    requests.storage: 500Gi
```

### 19.4 StorageClass Selection

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pci-db-data
  namespace: pci-db
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: encrypted-fast
  resources:
    requests:
      storage: 100Gi
```

## 20. Performance and Noisy Neighbor Isolation

Workload isolation is not only about security. It is also about predictable performance.

### 20.1 Resource Requests

Requests affect scheduling.

```yaml
resources:
  requests:
    cpu: "1"
    memory: 2Gi
  limits:
    cpu: "2"
    memory: 4Gi
```

Without requests, the scheduler cannot properly account for workload demand.

### 20.2 QoS Classes

Kubernetes assigns QoS classes:

| QoS Class | Condition | Eviction Preference |
|---|---|---|
| Guaranteed | Requests equal limits for CPU and memory on all containers | Least likely to be evicted |
| Burstable | At least one request set, but not Guaranteed | Medium |
| BestEffort | No requests/limits | Most likely to be evicted |

For critical workloads, use appropriate requests and limits.

### 20.3 Dedicated Performance Nodes

For heavy workloads:

- Label nodes by performance class.
- Taint nodes to repel normal workloads.
- Use required node affinity.
- Use Guaranteed QoS where appropriate.
- Avoid mixing bursty CI builds with databases.

Example:

```bash
oc label node worker-db-0 workload.openshift.io/class=database storage=fast-ssd
oc adm taint node worker-db-0 dedicated=database:NoSchedule
```

### 20.4 Build Workload Isolation

Builds can be noisy:

- High CPU.
- High network pull/push.
- Heavy disk I/O.
- Many short-lived pods.

Recommended:

- Dedicated CI/build nodes.
- Build namespace quotas.
- Taints for build nodes.
- LimitRange defaults.
- Separate image registry capacity planning.

## 21. Workload Isolation Design Patterns

### 21.1 General Shared Worker Pool

Use for low-risk, normal apps.

```text
Label: workload.openshift.io/class=general
Taint: none or general policy
Namespace: normal project
Policy: quota + limitrange + baseline network policy
```

### 21.2 Dedicated Tenant Pool

Use for business unit or customer isolation.

```text
Labels: tenant=finance, env=prod
Taint: dedicated=finance:NoSchedule
Namespace selector: tenant=finance,env=prod
Workload toleration: dedicated=finance
NetworkPolicy: default deny + required allow rules
Quota: tenant-specific
```

### 21.3 Compliance Pool

Use for regulated data.

```text
Labels: compliance=pci, workload.openshift.io/class=pci
Taint: dedicated=pci:NoSchedule
Namespace selector: compliance=pci
NetworkPolicy: default deny ingress and egress
SCC: restricted by default; exceptions by ServiceAccount only
StorageClass: encrypted-fast
Audit: strict
```

### 21.4 Infra Pool

Use for OpenShift platform workloads.

```text
Labels: node-role.kubernetes.io/infra=, workload.openshift.io/class=infra
Taint: node-role.kubernetes.io/infra=:NoSchedule
Workloads: router, registry, monitoring, logging
```

### 21.5 GPU Pool

```text
Labels: hardware=gpu, accelerator=nvidia
Taint: nvidia.com/gpu=true:NoSchedule
Workloads: AI/ML, inference, training
Resource: nvidia.com/gpu request/limit
```

Example pod snippet:

```yaml
spec:
  tolerations:
  - key: nvidia.com/gpu
    operator: Equal
    value: "true"
    effect: NoSchedule
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: hardware
            operator: In
            values:
            - gpu
  containers:
  - name: trainer
    image: registry.example.com/ml/trainer:v1
    resources:
      limits:
        nvidia.com/gpu: "1"
```

### 21.6 Database Pool

```text
Labels: workload.openshift.io/class=database, storage=fast-ssd
Taint: dedicated=database:NoSchedule
Policy: strict resource requests, careful anti-affinity, storage quotas
```

## 22. End-to-End Example: Isolating a PCI Workload

This example combines node, namespace, RBAC, quota, security, and network isolation.

### 22.1 Goal

Run `pci-api` only on PCI nodes, prevent normal workloads from using those nodes, restrict namespace resources, and deny network traffic by default.

### 22.2 Label and Taint Nodes

```bash
oc label node worker-pci-0 workload.openshift.io/class=pci compliance=pci
oc label node worker-pci-1 workload.openshift.io/class=pci compliance=pci

oc adm taint node worker-pci-0 dedicated=pci:NoSchedule
oc adm taint node worker-pci-1 dedicated=pci:NoSchedule
```

### 22.3 Create Namespace with Project Node Selector

```bash
oc new-project pci-prod
oc annotate namespace pci-prod openshift.io/node-selector='workload.openshift.io/class=pci,compliance=pci'
```

### 22.4 Create Quota

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: pci-prod-quota
  namespace: pci-prod
spec:
  hard:
    pods: "20"
    requests.cpu: "10"
    requests.memory: 40Gi
    limits.cpu: "20"
    limits.memory: 80Gi
    persistentvolumeclaims: "10"
    requests.storage: 500Gi
```

Apply:

```bash
oc apply -f pci-prod-quota.yaml
```

### 22.5 Create LimitRange

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: pci-prod-limits
  namespace: pci-prod
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 256Mi
    default:
      cpu: 500m
      memory: 512Mi
    min:
      cpu: 10m
      memory: 64Mi
    max:
      cpu: "2"
      memory: 4Gi
```

Apply:

```bash
oc apply -f pci-prod-limits.yaml
```

### 22.6 ServiceAccount

```bash
oc create sa pci-api-sa -n pci-prod
```

No special SCC is granted unless required.

### 22.7 Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pci-api
  namespace: pci-prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: pci-api
  template:
    metadata:
      labels:
        app: pci-api
        compliance: pci
    spec:
      serviceAccountName: pci-api-sa
      tolerations:
      - key: dedicated
        operator: Equal
        value: pci
        effect: NoSchedule
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: workload.openshift.io/class
                operator: In
                values:
                - pci
              - key: compliance
                operator: In
                values:
                - pci
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: pci-api
      containers:
      - name: pci-api
        image: registry.example.com/apps/pci-api:v1
        ports:
        - containerPort: 8443
        resources:
          requests:
            cpu: 500m
            memory: 512Mi
          limits:
            cpu: "1"
            memory: 1Gi
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop:
            - ALL
          runAsNonRoot: true
          seccompProfile:
            type: RuntimeDefault
```

### 22.8 NetworkPolicy Default Deny

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: pci-prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
```

### 22.9 Allow Router to App

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-router-to-pci-api
  namespace: pci-prod
spec:
  podSelector:
    matchLabels:
      app: pci-api
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-ingress
    ports:
    - protocol: TCP
      port: 8443
  policyTypes:
  - Ingress
```

### 22.10 Allow DNS Egress

The namespace needs DNS if egress is denied.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: pci-prod
spec:
  podSelector: {}
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
  policyTypes:
  - Egress
```

### 22.11 Validate Placement

```bash
oc get pods -n pci-prod -o wide
oc get nodes -l workload.openshift.io/class=pci
oc describe pod -n pci-prod -l app=pci-api | egrep -i 'node:|tolerations|affinity|scc|events'
```

- Pods run only on PCI nodes.
- General pods cannot run on PCI nodes without toleration.

## 24. Troubleshooting Pending Pods and Wrong Placement

### 24.1 Pod Pending Due to Node Selector

Symptom:

```text
0/5 nodes are available: node(s) didn't match Pod's node affinity/selector
```

Check:

```bash
oc get pod <pod> -n <ns> -o yaml | grep -A10 nodeSelector
oc get nodes --show-labels | grep <label>
oc get namespace <ns> -o yaml | grep openshift.io/node-selector
```

Fix:

- Add correct label to nodes.
- Correct pod nodeSelector.
- Correct namespace node selector.
- Remove conflicting selector.

### 24.2 Pod Pending Due to Untolerated Taint

Symptom:

```text
0/3 nodes are available: node(s) had untolerated taint {dedicated: pci}
```

Check:

```bash
oc describe node <node> | grep -i taints
oc get pod <pod> -n <ns> -o yaml | grep -A20 tolerations
```

Fix:

- Add matching toleration to workload.
- Remove taint if node should not be dedicated.
- Ensure toleration key/value/effect match exactly.

### 24.3 Pod Has Toleration But Runs on General Node

Cause:

A toleration permits use of a tainted node but does not force placement there.

Fix:

Add node affinity or nodeSelector.

### 24.4 General Pods Running on Dedicated Nodes

Cause:

Dedicated nodes are labeled but not tainted.

Fix:

Add a taint to dedicated nodes.

```bash
oc adm taint node worker-dedicated-0 dedicated=team-a:NoSchedule
```

### 24.5 Pods Not Spreading Across Nodes

Check:

```bash
oc get pods -n <ns> -o wide
oc get pod <pod> -n <ns> -o yaml | grep -A20 topologySpreadConstraints
```

Common causes:

- Label selector does not match pod labels.
- Not enough eligible nodes.
- Topology labels missing on nodes.
- Hard constraints too strict.
- Other affinity rules reduce eligible nodes.

### 24.6 Namespace Selector Conflicts with Pod Selector

Namespace:

```text
openshift.io/node-selector=env=prod
```

Pod:

```yaml
nodeSelector:
  env: dev
```

Fix:

- Align pod selector with namespace selector.
- Move workload to correct namespace.
- Change namespace policy if design is wrong.

### 24.7 Node Label Changed But Existing Pods Still Running

Reason:

`IgnoredDuringExecution` means scheduling rules are checked during scheduling, not continuously enforced after scheduling.

Fix:

- Rollout restart workloads.
- Evict/recreate pods carefully.
- Consider descheduler where appropriate.

```bash
oc rollout restart deployment/<name> -n <namespace>
```

## 25. Common Mistakes

### Mistake 1: Only Using Tolerations

Toleration does not force pod placement.

Correct pattern:

```text
Taint + toleration + node affinity/nodeSelector
```

### Mistake 2: Only Using Node Affinity

Affinity does not repel other pods.

Correct pattern:

```text
Label + required affinity + taint
```

### Mistake 3: Labeling Nodes Manually in Autoscaled Clusters

Manual labels can disappear when nodes are replaced.

Correct pattern:

```text
Configure labels/taints in MachineSet or supported machine pool template
```

### Mistake 4: Forgetting Namespace-Level Policy

Developers may omit placement from manifests.

Correct pattern:

```text
Use project-level node selector for tenant/environment isolation
```

### Mistake 5: Assuming Node Isolation Means Network Isolation

Dedicated nodes do not block traffic.

Correct pattern:

```text
Use NetworkPolicy default deny plus explicit allow rules
```

### Mistake 6: Overusing Hard Anti-Affinity

Hard anti-affinity can leave pods Pending during capacity shortage.

Correct pattern:

```text
Use topology spread or preferred anti-affinity where availability matters
```

### Mistake 7: Broad SCC Grants

Granting `anyuid` or `privileged` broadly weakens isolation.

Correct pattern:

```text
Grant SCC to specific ServiceAccount only
```

### Mistake 8: No Resource Requests

Without requests, scheduling and isolation become inaccurate.

Correct pattern:

```text
Set requests/limits and enforce defaults with LimitRange
```

### Mistake 9: Missing DNS Egress Allow Rule

Default deny egress blocks DNS.

Correct pattern:

```text
Add explicit DNS egress policy
```

### Mistake 10: Too Many Conflicting Rules

A workload with nodeSelector, node affinity, taints, anti-affinity, spread constraints, resource requests, and quota can easily become unschedulable.

Correct pattern:

```text
Design rules deliberately and validate with events
```

## 27. Interview and Real-World Scenario Questions

### Q1. Why is toleration alone not enough for dedicated nodes?

Because toleration only allows a pod to run on a tainted node. It does not require the pod to run there. The pod may still schedule on untainted general nodes unless nodeSelector or node affinity also targets the dedicated nodes.

### Q2. Why is node affinity alone not enough for dedicated nodes?

Node affinity can attract selected pods to dedicated nodes, but it does not prevent other pods from scheduling there. Taints are needed to repel unauthorized pods.

### Q3. How do you isolate PCI workloads?

Use a layered model:

- Dedicated PCI nodes.
- PCI labels on nodes.
- `dedicated=pci:NoSchedule` taint.
- Project node selector for PCI namespaces.
- Required node affinity and toleration in PCI workloads.
- ResourceQuota and LimitRange.
- Restricted SCC by default.
- NetworkPolicy default deny.
- Encrypted storage class and storage quota.
- Audit and monitoring.

### Q4. A pod is Pending with `untolerated taint`. What do you check?

Check node taints and pod tolerations:

```bash
oc describe node <node> | grep -i taints
oc get pod <pod> -n <ns> -o yaml | grep -A20 tolerations
oc describe pod <pod> -n <ns>
```

Then add a matching toleration or change the placement design.

### Q5. A pod has a toleration for PCI nodes but is running on a general node. Why?

Because toleration is permission, not a placement requirement. Add required node affinity or nodeSelector.

### Q6. How do you enforce all pods in a project to run on selected nodes?

Use the namespace annotation:

```bash
oc annotate namespace <namespace> openshift.io/node-selector='key=value'
```

### Q7. What happens if namespace node selector conflicts with pod nodeSelector?

The pod cannot be created or scheduled successfully because the effective selector cannot be satisfied.

### Q8. How do you stop general workloads from running on infra nodes?

Taint infra nodes and ensure only infra workloads have matching tolerations and placement rules.

### Q9. How do you verify actual workload isolation?

Use:

```bash
oc get pods -A -o wide
oc get nodes --show-labels
oc describe node <node>
oc describe pod <pod> -n <namespace>
oc get networkpolicy -n <namespace>
oc describe quota -n <namespace>
```

### Q10. Why should labels and taints be added to MachineSets?

Because directly modified nodes can be replaced. MachineSet-level labels and taints persist across machine replacement in supported IPI/cloud environments.
