## 1. What Affinity Means in OpenShift

In OpenShift, **affinity** is a pod scheduling feature that tells the scheduler where a pod **should** or **must** run.

Affinity is not a runtime feature. It is a **scheduling decision feature**. It works before a pod is bound to a node.

In simple terms:

```text
Affinity = attract workload to selected nodes or near selected pods
Anti-affinity = repel workload from selected pods or topology domains
```

OpenShift uses the Kubernetes scheduler underneath. The scheduler evaluates the pod specification, cluster state, node labels, pod labels, taints, tolerations, resource requests, topology rules, and other constraints before assigning a pod to a node.

Affinity is defined under:

```yaml
spec:
  affinity:
```

The main affinity types are:

```yaml
spec:
  affinity:
    nodeAffinity: {}
    podAffinity: {}
    podAntiAffinity: {}
```

Affinity is commonly used for:

- Running workloads on specific hardware nodes.
- Placing latency-sensitive services close to each other.
- Spreading replicas across nodes, zones, racks, or failure domains.
- Keeping noisy workloads away from critical workloads.
- Separating application tiers.
- Dedicating infrastructure nodes, storage nodes, GPU nodes, edge nodes, or compliance nodes.
- Improving high availability and fault tolerance.

## 2. Why Affinity Matters in Real Production Clusters

In a small lab cluster, pods can run anywhere. In a real enterprise OpenShift cluster, that is rarely acceptable.

A senior OpenShift administrator must think about:

```text
Availability
Performance
Security
Compliance
Cost
Hardware specialization
Storage locality
Failure domains
Operational blast radius
Upgrade behavior
Application dependency placement
```

### Example production problems solved by affinity

#### Problem 1: Critical app replicas landing on the same worker

A payment application has three replicas. Without placement rules, the scheduler may place two or more replicas on the same node depending on current resource scoring.

If that node fails, multiple replicas disappear together.

Solution:

```text
Use pod anti-affinity or topology spread constraints to avoid co-locating same app replicas.
```

#### Problem 2: GPU workload scheduled on non-GPU nodes

A machine-learning workload requires GPU nodes.

Solution:

```text
Label GPU nodes and use required node affinity.
```

#### Problem 3: Logging or monitoring workload should run on infra nodes

OpenShift monitoring, logging, ingress, registry, or GitOps workloads may be moved to infrastructure nodes.

Solution:

```text
Use node labels, node affinity, node selectors, and tolerations if infra nodes are tainted.
```

#### Problem 4: Database and web pods need low-latency placement

An application tier performs better when backend pods run in the same zone as frontend pods.

Solution:

```text
Use pod affinity with topologyKey topology.kubernetes.io/zone.
```

#### Problem 5: Two noisy apps interfere with each other

A CPU-heavy reporting workload affects a latency-sensitive API workload.

Solution:

```text
Use pod anti-affinity to keep the workloads apart.
```

## 3. Scheduling Flow: Where Affinity Fits

When a pod is created, it normally starts in `Pending` state. The scheduler then tries to find a suitable node.

A simplified scheduling flow:

```text
1. Pod is created
2. Scheduler watches unscheduled pod
3. Scheduler filters nodes
4. Scheduler scores remaining nodes
5. Highest scoring node is selected
6. Pod is bound to selected node
7. Kubelet on that node starts containers
```

Affinity can participate in both filtering and scoring.

### Required rules

Required affinity rules are hard constraints.

```text
If node does not match -> node is filtered out
```

### Preferred rules

Preferred affinity rules are soft constraints.

```text
If node matches -> node receives scheduling score boost
If no node matches -> pod can still be scheduled elsewhere
```

### Important scheduler principle

The scheduler does not only evaluate affinity. A node must satisfy all relevant scheduling requirements, such as:

- Node readiness.
- Unschedulable flag.
- Resource availability.
- Pod resource requests.
- Node selectors.
- Node affinity.
- Pod affinity.
- Pod anti-affinity.
- Taints and tolerations.
- Volume binding requirements.
- Topology spread constraints.
- Pod security and admission outcomes.

Affinity alone cannot force a pod onto a node that fails other scheduler filters.

## 4. Types of Affinity

OpenShift supports three major affinity categories.

| Affinity Type | Based On | Purpose |
|---|---|---|
| `nodeAffinity` | Node labels | Place pod on specific groups of nodes |
| `podAffinity` | Existing pod labels | Place pod close to other matching pods |
| `podAntiAffinity` | Existing pod labels | Keep pod away from other matching pods |

### 4.1 Node affinity

Node affinity says:

```text
Schedule this pod on nodes that match these node labels.
```

Example:

```text
Run this workload only on nodes labeled disktype=ssd.
```

### 4.2 Pod affinity

Pod affinity says:

```text
Schedule this pod near pods that match these pod labels.
```

Example:

```text
Run cache pods in the same zone as frontend pods.
```

### 4.3 Pod anti-affinity

Pod anti-affinity says:

```text
Do not schedule this pod near pods that match these pod labels.
```

Example:

```text
Do not run two replicas of the same application on the same node.
```

## 5. Node Affinity

Node affinity controls scheduling by matching **labels on nodes**.

It is similar to `nodeSelector`, but much more expressive.

### 5.1 Basic node affinity structure

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: node-role.example.com/workload
            operator: In
            values:
            - app
```

### 5.2 Required node affinity

Required node affinity is a hard rule.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-on-ssd
  namespace: affinity-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: app-on-ssd
  template:
    metadata:
      labels:
        app: app-on-ssd
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: storage-tier
                operator: In
                values:
                - ssd
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

This pod can run only on nodes with:

```text
storage-tier=ssd
```

If no matching node exists, the pod remains `Pending`.

### 5.3 Preferred node affinity

Preferred node affinity is a soft rule.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-prefers-ssd
  namespace: affinity-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: app-prefers-ssd
  template:
    metadata:
      labels:
        app: app-prefers-ssd
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 80
            preference:
              matchExpressions:
              - key: storage-tier
                operator: In
                values:
                - ssd
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

This pod prefers `storage-tier=ssd`, but can run elsewhere if needed.

### 5.4 Required and preferred together

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-required-zone-preferred-ssd
  namespace: affinity-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: app-required-zone-preferred-ssd
  template:
    metadata:
      labels:
        app: app-required-zone-preferred-ssd
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                - zone-a
                - zone-b
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 90
            preference:
              matchExpressions:
              - key: storage-tier
                operator: In
                values:
                - ssd
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

Meaning:

```text
Must run in zone-a or zone-b.
Prefer nodes with storage-tier=ssd.
```

### 5.5 How nodeSelectorTerms work

This is critical for exams and troubleshooting.

```yaml
nodeSelectorTerms:
- matchExpressions:
  - key: env
    operator: In
    values: ["prod"]
  - key: disk
    operator: In
    values: ["ssd"]
- matchExpressions:
  - key: gpu
    operator: Exists
```

Logic:

```text
Terms are ORed.
Expressions inside one term are ANDed.
```

So the above means:

```text
(env=prod AND disk=ssd) OR (gpu label exists)
```

### 5.6 Labeling nodes for node affinity

Check nodes:

```bash
oc get nodes
```

Show labels:

```bash
oc get nodes --show-labels
```

Add a label:

```bash
oc label node worker01.example.com storage-tier=ssd
```

Overwrite an existing label:

```bash
oc label node worker01.example.com storage-tier=ssd --overwrite
```

Remove a label:

```bash
oc label node worker01.example.com storage-tier-
```

Verify:

```bash
oc get nodes -l storage-tier=ssd
```

### 5.7 Recommended node label categories

Use stable, meaningful labels:

```text
node-role.kubernetes.io/worker=
node-role.kubernetes.io/infra=
node-role.kubernetes.io/storage=
node-role.kubernetes.io/gpu=
topology.kubernetes.io/zone=zone-a
topology.kubernetes.io/region=region-1
kubernetes.io/hostname=worker01.example.com
node.openshift.io/os_id=rhcos
workload-type=frontend
workload-type=backend
hardware-type=gpu
storage-tier=ssd
compliance-zone=pci
```

Avoid labels that change frequently.

## 6. Pod Affinity

Pod affinity places a pod relative to **other existing pods**.

It uses pod labels and a topology domain.

### 6.1 Pod affinity concept

Pod affinity answers:

```text
Where are pods matching this label already running?
Schedule my new pod in the same topology domain.
```

Topology domain can be:

```text
Same node
Same zone
Same region
Same rack
Any custom topology label
```

Common topology keys:

```text
kubernetes.io/hostname
topology.kubernetes.io/zone
topology.kubernetes.io/region
```

### 6.2 Pod affinity structure

```yaml
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values:
            - backend
        topologyKey: kubernetes.io/hostname
```

Meaning:

```text
Schedule this pod onto a node where a pod labeled app=backend already exists.
```

Because `topologyKey` is `kubernetes.io/hostname`, the topology domain is the node.

### 6.3 Required pod affinity example

Suppose you want a sidecar helper workload to run on the same node as backend pods.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: helper-near-backend
  namespace: affinity-demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: helper
  template:
    metadata:
      labels:
        app: helper
    spec:
      affinity:
        podAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - backend
            topologyKey: kubernetes.io/hostname
      containers:
      - name: helper
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

If no `app=backend` pod exists, this pod can remain `Pending`.

### 6.4 Preferred pod affinity example

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cache-prefers-frontend-zone
  namespace: affinity-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: cache
  template:
    metadata:
      labels:
        app: cache
    spec:
      affinity:
        podAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 70
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: frontend
              topologyKey: topology.kubernetes.io/zone
      containers:
      - name: cache
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

Meaning:

```text
Prefer to schedule cache pods in the same zone as frontend pods.
```

### 6.5 namespaceSelector and namespaces

By default, pod affinity commonly evaluates pods in the same namespace unless namespaces are specified depending on API field usage.

You can scope pod affinity to specific namespaces:

```yaml
namespaces:
- production
- shared-services
```

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-near-shared-cache
  namespace: production
spec:
  replicas: 1
  selector:
    matchLabels:
      app: app-near-shared-cache
  template:
    metadata:
      labels:
        app: app-near-shared-cache
    spec:
      affinity:
        podAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: redis-cache
            namespaces:
            - shared-services
            topologyKey: topology.kubernetes.io/zone
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

Meaning:

```text
Run this pod in the same zone as redis-cache pods in namespace shared-services.
```

### 6.6 When to use pod affinity

Use pod affinity when workloads benefit from locality.

Good cases:

```text
Frontend close to cache
API close to database proxy
Application close to node-local sidecar service
Batch worker close to data-preparation pod
Logging helper close to source workload
Zone-local traffic optimization
```

Bad cases:

```text
Using hard pod affinity for services that may scale independently
Using hostname-level required affinity without enough capacity
Using affinity when service discovery is enough
Using affinity to solve network policy issues
```

## 7. Pod Anti-Affinity

Pod anti-affinity prevents pods from being scheduled in the same topology domain as matching pods.

It is one of the most common HA placement techniques.

### 7.1 Pod anti-affinity concept

Pod anti-affinity answers:

```text
Where are pods matching this label already running?
Avoid scheduling my new pod in that same topology domain.
```

### 7.2 Same-node anti-affinity

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-ha
  namespace: affinity-demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-ha
  template:
    metadata:
      labels:
        app: web-ha
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - web-ha
            topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

Meaning:

```text
Do not place two app=web-ha pods on the same node.
```

If the cluster has fewer schedulable nodes than replicas, some pods remain `Pending`.

### 7.3 Zone-level anti-affinity

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: critical-zone-ha
  namespace: affinity-demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: critical-zone-ha
  template:
    metadata:
      labels:
        app: critical-zone-ha
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: critical-zone-ha
            topologyKey: topology.kubernetes.io/zone
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

Meaning:

```text
Do not place two app=critical-zone-ha pods in the same zone.
```

This requires at least as many zones as replicas. Otherwise, pods can stay `Pending`.

### 7.4 Preferred anti-affinity

In many production environments, preferred anti-affinity is safer.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-soft-ha
  namespace: affinity-demo
spec:
  replicas: 5
  selector:
    matchLabels:
      app: web-soft-ha
  template:
    metadata:
      labels:
        app: web-soft-ha
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: web-soft-ha
              topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

Meaning:

```text
Strongly prefer spreading pods across nodes, but do not block scheduling if capacity is limited.
```

### 7.5 Anti-affinity for noisy-neighbor isolation

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: low-latency-api
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: low-latency-api
  template:
    metadata:
      labels:
        app: low-latency-api
        tier: critical
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchExpressions:
                - key: workload-profile
                  operator: In
                  values:
                  - cpu-heavy
              topologyKey: kubernetes.io/hostname
      containers:
      - name: api
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

Meaning:

```text
Prefer not to run low-latency API pods on the same node as CPU-heavy workloads.
```

## 8. Required vs Preferred Affinity

Affinity rules usually come in two scheduling strengths.

| Rule Type | Meaning | Scheduler Behavior | Risk |
|---|---|---|---|
| `requiredDuringSchedulingIgnoredDuringExecution` | Hard rule | Pod schedules only if rule matches | Pending pods if too strict |
| `preferredDuringSchedulingIgnoredDuringExecution` | Soft rule | Scheduler tries to honor rule | May not get desired placement |

### 8.1 Required rule

Use required rules for non-negotiable requirements.

Examples:

```text
GPU workload must run on GPU node
PCI workload must run on PCI node
ARM image must run on ARM node
Storage workload must run on storage node
App must avoid incompatible hardware
```

### 8.2 Preferred rule

Use preferred rules for optimization.

Examples:

```text
Prefer SSD nodes
Prefer same zone for latency
Prefer spreading replicas
Prefer low-cost node pool
Prefer non-busy node type
```

### 8.3 Senior admin rule

```text
Use required affinity only when running elsewhere is incorrect.
Use preferred affinity when running elsewhere is merely less ideal.
```

This distinction prevents avoidable outages caused by unschedulable pods.

## 9. IgnoredDuringExecution Explained

Most affinity fields include:

```text
IgnoredDuringExecution
```

Example:

```yaml
requiredDuringSchedulingIgnoredDuringExecution
```

This means:

```text
The rule is checked during scheduling.
After the pod is running, if labels change, the pod is not automatically evicted only because the affinity rule is no longer satisfied.
```

### Example

1. Node has label:

```text
storage-tier=ssd
```

2. Pod with required node affinity is scheduled to that node.
3. Admin removes node label:

```bash
oc label node worker01 storage-tier-
```

4. The existing pod continues running.
5. New pods requiring that label cannot schedule to that node.

### Operational implication

Affinity is not a continuous enforcement engine.

If you change labels, existing pods may need rollout or eviction:

```bash
oc rollout restart deployment/app -n production
```

or:

```bash
oc delete pod <pod-name> -n production
```

The replacement pod will be rescheduled according to current rules.

## 10. Affinity Operators

Affinity uses label selector operators.

| Operator | Meaning | Example |
|---|---|---|
| `In` | Label value must be in list | `disk In [ssd,nvme]` |
| `NotIn` | Label value must not be in list | `env NotIn [dev]` |
| `Exists` | Label key must exist | `gpu Exists` |
| `DoesNotExist` | Label key must not exist | `dedicated DoesNotExist` |
| `Gt` | Label value must be greater than integer | `cpu-count Gt 16` |
| `Lt` | Label value must be less than integer | `latency-tier Lt 5` |

### 10.1 In

```yaml
- key: storage-tier
  operator: In
  values:
  - ssd
  - nvme
```

Meaning:

```text
storage-tier must be either ssd or nvme.
```

### 10.2 NotIn

```yaml
- key: environment
  operator: NotIn
  values:
  - dev
  - test
```

Meaning:

```text
environment must not be dev or test.
```

If the key does not exist, `NotIn` usually evaluates as true.

### 10.3 Exists

```yaml
- key: hardware-type
  operator: Exists
```

Meaning:

```text
Node must have label key hardware-type, regardless of value.
```

### 10.4 DoesNotExist

```yaml
- key: node-role.kubernetes.io/infra
  operator: DoesNotExist
```

Meaning:

```text
Avoid nodes with infra role label.
```

### 10.5 Gt and Lt

```yaml
- key: cpu-count
  operator: Gt
  values:
  - "16"
```

Meaning:

```text
Node label cpu-count must be greater than 16.
```

Important:

```text
The label value must be parseable as an integer.
```

## 11. Node Selector vs Node Affinity

### 11.1 nodeSelector

`nodeSelector` is the simplest node placement method.

```yaml
spec:
  nodeSelector:
    storage-tier: ssd
```

It means:

```text
Schedule only on nodes with storage-tier=ssd.
```

### 11.2 nodeAffinity

Node affinity supports more expressive logic.

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: storage-tier
            operator: In
            values:
            - ssd
            - nvme
```

### 11.3 Comparison

| Feature | nodeSelector | nodeAffinity |
|---|---:|---:|
| Simple key-value match | Yes | Yes |
| Multiple values for same key | No | Yes |
| Soft preference | No | Yes |
| OR logic | No | Yes |
| Operators like Exists, NotIn, Gt, Lt | No | Yes |
| Pod-to-pod relationship | No | No, use podAffinity |

### 11.4 Important interaction

If both `nodeSelector` and `nodeAffinity` are configured:

```text
Both must be satisfied.
```

Example:

```yaml
spec:
  nodeSelector:
    environment: prod
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: storage-tier
            operator: In
            values:
            - ssd
```

Meaning:

```text
Node must have environment=prod AND storage-tier=ssd.
```

This is a common reason for `Pending` pods.

## 12. Affinity vs Taints and Tolerations

Affinity and taints solve different scheduling problems.

| Feature | Controls | Direction |
|---|---|---|
| Node affinity | Pod chooses node | Pod attracts itself to nodes |
| Pod affinity | Pod chooses location near pods | Pod attracts itself to pods/topology |
| Pod anti-affinity | Pod avoids pods/topology | Pod repels itself from pods/topology |
| Taints | Node rejects pods | Node repels pods |
| Tolerations | Pod can tolerate tainted nodes | Pod is allowed onto tainted node |

### 12.1 Key principle

```text
Affinity does not override taints.
```

If a node is tainted, the pod also needs a matching toleration.

### 12.2 Example: dedicated GPU node

Label node:

```bash
oc label node worker-gpu01 hardware=gpu
```

Taint node:

```bash
oc adm taint node worker-gpu01 dedicated=gpu:NoSchedule
```

Pod needs both:

```yaml
spec:
  tolerations:
  - key: dedicated
    operator: Equal
    value: gpu
    effect: NoSchedule
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: hardware
            operator: In
            values:
            - gpu
```

Meaning:

```text
Affinity selects GPU node.
Toleration allows pod onto tainted GPU node.
```

Without toleration, pod remains `Pending` even if node affinity matches.

### 12.3 Senior design pattern

For dedicated nodes, use both:

```text
Label + node affinity/nodeSelector = attraction
Taint + toleration = isolation
```

## 13. Affinity vs Topology Spread Constraints

Pod anti-affinity was traditionally used to spread pods across nodes or zones.

Modern Kubernetes and OpenShift clusters often use **topology spread constraints** for controlled spreading.

### 13.1 Pod anti-affinity spreading

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app: web
      topologyKey: kubernetes.io/hostname
```

This says:

```text
Prefer not to place web pods together on the same node.
```

### 13.2 Topology spread constraint

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: web
```

This says:

```text
Keep app=web pods evenly spread across nodes with max skew 1.
```

### 13.3 Comparison

| Requirement | Better Choice |
|---|---|
| Avoid two same pods on same node | Pod anti-affinity or topology spread |
| Even distribution across zones | Topology spread constraints |
| Strong co-location with another app | Pod affinity |
| Avoid noisy neighbor app | Pod anti-affinity |
| Basic hardware selection | Node affinity |

### 13.4 Interaction with node affinity

If a pod has node affinity, topology spread calculations only consider nodes that match the incoming pod's node affinity and node selector. This matters when you combine zone spreading with node pools.

Example:

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: nodepool
            operator: In
            values:
            - app
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: web
```

The scheduler spreads only across nodes in `nodepool=app`, not across every node in the cluster.

## 14. Label Strategy for Affinity

Affinity is only as good as your labels.

Poor labels create fragile scheduling.

### 14.1 Good label design

Use labels that represent stable scheduling intent:

```text
nodepool=app
nodepool=infra
nodepool=storage
nodepool=gpu
workload-zone=trusted
storage-tier=ssd
compliance=pci
hardware=gpu
failure-domain=rack-01
```

### 14.2 Use standard topology labels

Preferred:

```text
topology.kubernetes.io/region
topology.kubernetes.io/zone
kubernetes.io/hostname
```

Avoid older beta labels in new designs:

```text
failure-domain.beta.kubernetes.io/zone
failure-domain.beta.kubernetes.io/region
```

### 14.3 Avoid unstable labels

Avoid labels based on:

```text
Current load
Temporary maintenance state
Human names
Ticket numbers
Short-lived projects
Application versions
```

### 14.4 Protect important labels

In large clusters, node labels may be managed by:

```text
MachineSets
MachineConfigPools
Infrastructure-as-code
Cluster autoscaler groups
Cloud provider metadata
GitOps
```

Do not manually label nodes if automation will overwrite labels.

### 14.5 Label naming recommendations

Use simple internal platform labels:

```text
platform.example.com/nodepool=app
platform.example.com/hardware=gpu
platform.example.com/compliance=pci
platform.example.com/storage=fast
```

Example:

```bash
oc label node worker01 platform.example.com/nodepool=app
oc label node worker02 platform.example.com/storage=fast
```

## 16. Advanced Production Patterns

### 16.1 Dedicated application nodes

Goal:

```text
Only selected workloads should run on app-dedicated nodes.
```

Node configuration:

```bash
oc label node worker-app01 dedicated=app
oc adm taint node worker-app01 dedicated=app:NoSchedule
```

Pod configuration:

```yaml
spec:
  tolerations:
  - key: dedicated
    operator: Equal
    value: app
    effect: NoSchedule
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: dedicated
            operator: In
            values:
            - app
```

This ensures:

```text
Only pods with matching toleration can run there.
The intended pod actively selects those nodes.
```

### 16.2 Infrastructure node placement

OpenShift infrastructure workloads may include:

```text
Ingress router
Image registry
Monitoring
Logging
GitOps
Service mesh control plane
```

Typical pattern:

```text
Label infra nodes.
Optionally taint infra nodes.
Configure workload nodeSelector/affinity and tolerations.
```

Example node label:

```bash
oc label node worker-infra01 node-role.kubernetes.io/infra=
```

Example node affinity:

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: node-role.kubernetes.io/infra
            operator: Exists
```

### 16.3 PCI or compliance workload placement

Node label:

```bash
oc label node worker-pci01 compliance-zone=pci
```

Deployment:

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: compliance-zone
            operator: In
            values:
            - pci
```

Add taint for stronger isolation:

```bash
oc adm taint node worker-pci01 compliance=pci:NoSchedule
```

Pod toleration:

```yaml
spec:
  tolerations:
  - key: compliance
    operator: Equal
    value: pci
    effect: NoSchedule
```

### 16.4 GPU workload placement

Node label:

```bash
oc label node worker-gpu01 accelerator=nvidia-gpu
```

Deployment fragment:

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: accelerator
            operator: In
            values:
            - nvidia-gpu
```

For real GPU workloads, also configure resource requests such as:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

Affinity selects node class; GPU resource request reserves device capacity.

### 16.5 Zone-aware high availability

For cloud or multi-zone clusters:

```yaml
spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: checkout
          topologyKey: topology.kubernetes.io/zone
```

This prefers spreading replicas across zones.

For strict zone distribution, topology spread constraints may be better.

### 16.6 Storage-aware placement

Some workloads perform better when scheduled near storage-capable nodes.

```bash
oc label node worker-storage01 storage-node=true
```

```yaml
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: storage-node
            operator: In
            values:
            - "true"
```

Be careful with dynamic storage classes. Volume binding can also influence scheduling, especially with `WaitForFirstConsumer` storage classes.

### 16.7 Blue/green node pool migration

You can migrate workloads from old nodes to new nodes gradually.

Old nodes:

```text
nodepool=blue
```

New nodes:

```text
nodepool=green
```

Stage 1: prefer green

```yaml
preferredDuringSchedulingIgnoredDuringExecution:
- weight: 100
  preference:
    matchExpressions:
    - key: nodepool
      operator: In
      values:
      - green
```

Stage 2: require green

```yaml
requiredDuringSchedulingIgnoredDuringExecution:
  nodeSelectorTerms:
  - matchExpressions:
    - key: nodepool
      operator: In
      values:
      - green
```

Stage 3: drain old nodes

```bash
oc adm drain worker-blue01 --ignore-daemonsets --delete-emptydir-data
```

### 16.8 Avoiding co-location of active and standby replicas

For stateful or HA applications:

```yaml
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: postgres
        topologyKey: kubernetes.io/hostname
```

This prevents primary and standby pods from landing on the same node, assuming they share labels.

## 17. Affinity with Deployments, StatefulSets, DaemonSets, Operators

### 17.1 Deployment

In a Deployment, affinity goes under pod template:

```yaml
spec:
  template:
    spec:
      affinity:
```

Not directly under Deployment `spec` root.

Correct:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo
spec:
  template:
    spec:
      affinity:
        nodeAffinity: {}
```

Wrong:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo
spec:
  affinity: {}
```

### 17.2 StatefulSet

StatefulSet uses the same pod template structure:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  template:
    spec:
      affinity:
        podAntiAffinity: {}
```

Common use:

```text
Avoid placing multiple database replicas on same node.
```

### 17.3 DaemonSet

DaemonSet creates one pod per matching node. Affinity can still restrict eligible nodes.

Example:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
  namespace: affinity-demo
spec:
  selector:
    matchLabels:
      app: node-agent
  template:
    metadata:
      labels:
        app: node-agent
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: nodepool
                operator: In
                values:
                - app
      containers:
      - name: agent
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

Meaning:

```text
Run daemon pods only on nodes labeled nodepool=app.
```

### 17.4 Operators

Many OpenShift Operators expose scheduling configuration in their custom resources.

Examples may include fields like:

```yaml
nodeSelector:
tolerations:
affinity:
```

You should not always edit operator-managed Deployments directly. The Operator may revert changes.

Senior admin approach:

```text
1. Check the Operator CRD or documentation.
2. Configure affinity in the supported custom resource field.
3. Verify generated pods.
4. Avoid manual edits to managed deployments unless documented.
```

Commands:

```bash
oc get csv -A | grep -i <operator>
oc get crd | grep -i <operator>
oc explain <resource>.spec
```

## 19. Troubleshooting Affinity Issues

Affinity troubleshooting is mostly about proving why the scheduler cannot find a valid node.

### 19.1 Start with pod status

```bash
oc get pods -n <namespace> -o wide
```

If pod is pending:

```bash
oc describe pod <pod-name> -n <namespace>
```

Check `Events`.

### 19.2 Common event: node affinity mismatch

Example:

```text
0/5 nodes are available: 5 node(s) didn't match Pod's node affinity/selector.
```

Check pod affinity:

```bash
oc get pod <pod-name> -n <namespace> -o yaml | grep -A50 affinity:
```

Check nodes with labels:

```bash
oc get nodes --show-labels
```

Check specific label:

```bash
oc get nodes -L nodepool,storage-tier,topology.kubernetes.io/zone
```

### 19.3 Common event: anti-affinity too strict

Example:

```text
0/3 nodes are available: 3 node(s) didn't match pod anti-affinity rules.
```

Check:

```bash
oc get pods -n <namespace> -o wide --show-labels
```

Confirm:

```text
How many replicas?
How many eligible nodes?
What topologyKey is used?
Are labels matching too broadly?
```

If you require one replica per node but have 5 replicas and 3 nodes, 2 pods stay pending.

### 19.4 Common event: missing topology label

If using:

```yaml
topologyKey: topology.kubernetes.io/zone
```

All candidate nodes should have that label.

Check:

```bash
oc get nodes -L topology.kubernetes.io/zone
```

If a node lacks the topology label, scheduling behavior may not match your expectation.

### 19.5 Common issue: pod labels do not match selector

Pod anti-affinity depends on matching labels.

Deployment selector:

```yaml
selector:
  matchLabels:
    app: web
```

Pod template labels:

```yaml
template:
  metadata:
    labels:
      app: web
```

Anti-affinity selector:

```yaml
labelSelector:
  matchLabels:
    app: web
```

If one of these is different, anti-affinity may not work.

### 19.6 Common issue: nodeSelector and nodeAffinity conflict

Example:

```yaml
nodeSelector:
  nodepool: infra

nodeAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    nodeSelectorTerms:
    - matchExpressions:
      - key: nodepool
        operator: In
        values:
        - app
```

This means:

```text
nodepool must be infra AND app
```

No node can satisfy both if label has one value.

### 19.7 Common issue: taint blocks node despite matching affinity

Check node taints:

```bash
oc describe node <node-name> | grep -i taints -A3
```

If node has:

```text
dedicated=app:NoSchedule
```

Pod needs:

```yaml
tolerations:
- key: dedicated
  operator: Equal
  value: app
  effect: NoSchedule
```

### 19.8 Common issue: hard rule used where soft rule was intended

Required anti-affinity can block rollouts.

Example:

```text
Deployment has replicas=10.
Only 5 nodes match node affinity.
Required podAntiAffinity uses hostname.
Only 5 pods can run.
```

Fix options:

```text
Use preferred anti-affinity.
Add more eligible nodes.
Reduce replicas.
Change topologyKey.
Use topology spread with ScheduleAnyway.
```

### 19.9 Common issue: namespace mismatch in pod affinity

If target pod is in another namespace, specify `namespaces` or `namespaceSelector`.

Check pod namespaces:

```bash
oc get pods -A -l app=redis-cache -o wide
```

### 19.10 Common issue: rollout stuck

Check rollout:

```bash
oc rollout status deployment/<name> -n <namespace>
```

Check replica sets:

```bash
oc get rs -n <namespace>
```

Check pending new pods:

```bash
oc describe pod <new-pod> -n <namespace>
```

Affinity problems commonly show up during rollout because new pods must satisfy new rules before old pods are fully replaced.

## 20. Common Mistakes

### Mistake 1: Putting affinity in the wrong YAML level

Wrong:

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  affinity: {}
```

Correct:

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      affinity: {}
```

### Mistake 2: Using required anti-affinity with too many replicas

```text
3 nodes + 5 replicas + required hostname anti-affinity = 2 Pending pods
```

### Mistake 3: Expecting affinity to evict running pods after label change

Affinity with `IgnoredDuringExecution` does not automatically evict running pods when labels change.

### Mistake 4: Forgetting taints

Affinity attracts. Taints repel.

A pod matching node affinity still cannot run on a tainted node without toleration.

### Mistake 5: Using hostname hard affinity for apps that need elasticity

Hostname-level hard affinity can make workloads fragile.

Prefer soft rules unless strict placement is required.

### Mistake 6: Matching the wrong labels

Pod affinity uses pod labels, not service labels.

Node affinity uses node labels, not pod labels.

### Mistake 7: Forgetting that expressions are ANDed inside one term

```yaml
matchExpressions:
- key: env
  operator: In
  values: ["prod"]
- key: disk
  operator: In
  values: ["ssd"]
```

Means:

```text
env=prod AND disk=ssd
```

### Mistake 8: Forgetting that nodeSelectorTerms are ORed

```yaml
nodeSelectorTerms:
- matchExpressions: ...
- matchExpressions: ...
```

Means:

```text
term1 OR term2
```

### Mistake 9: Using untrusted or manually inconsistent labels

If node labels are inconsistent, scheduling is inconsistent.

### Mistake 10: Operator-managed resources edited directly

Operators may revert manual Deployment changes.

Use supported CR fields.

## 21. Best Practices

### 21.1 Prefer soft rules for availability

Use preferred anti-affinity for general HA spreading:

```yaml
preferredDuringSchedulingIgnoredDuringExecution:
- weight: 100
```

Use required rules only for real hard requirements.

### 21.2 Combine affinity with resource requests

Affinity decides where pods can go. Resource requests decide whether the node has enough capacity.

Always set requests for production workloads:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 256Mi
  limits:
    memory: 512Mi
```

### 21.3 Use topology spread for even distribution

For modern HA spreading, prefer topology spread constraints when you need balanced distribution.

### 21.4 Use standard topology labels

Use:

```text
topology.kubernetes.io/zone
topology.kubernetes.io/region
kubernetes.io/hostname
```

### 21.5 Use labels that reflect platform intent

Good:

```text
nodepool=app
nodepool=infra
storage-tier=ssd
compliance-zone=pci
```

Bad:

```text
use-this-node=yes
temp=true
rakesh-test=1
```

### 21.6 Do not over-constrain

Every hard constraint reduces the scheduler's options.

Example over-constrained pod:

```text
nodeSelector requires nodepool=app
nodeAffinity requires zone=zone-a
podAntiAffinity requires no matching pod on hostname
PVC requires zone-b volume
taint requires toleration missing
```

Such pods often remain pending.

### 21.7 Test scheduling after label changes

Before changing many workloads, test with a simple pod:

```bash
oc run test-affinity --image=registry.access.redhat.com/ubi9/ubi-minimal \
  -n affinity-demo --command -- sleep 3600
```

Then edit/patch affinity and observe placement.

### 21.8 Keep placement rules version-controlled

Use GitOps for:

```text
Node labels
MachineSet labels
Deployment affinity
Operator CR scheduling fields
Taints and tolerations
```

### 21.9 Monitor Pending pods

Pending pods are often the first signal of bad affinity design.

Use:

```bash
oc get pods -A --field-selector=status.phase=Pending
```

### 22.2 Interview answer: What is affinity?

Good answer:

```text
Affinity is a scheduling feature used to influence or enforce where pods run. Node affinity selects nodes based on node labels. Pod affinity places pods near other pods based on pod labels and topology domains. Pod anti-affinity keeps pods away from matching pods, commonly for high availability. Required affinity is a hard scheduling constraint, while preferred affinity is a soft preference. In OpenShift, it is configured under the pod template spec and evaluated by the scheduler during pod placement.
```

### 22.3 Interview answer: nodeSelector vs nodeAffinity

Good answer:

```text
nodeSelector is a simple hard key-value match. nodeAffinity is more expressive because it supports operators such as In, NotIn, Exists, DoesNotExist, Gt, and Lt, supports multiple values, OR logic through nodeSelectorTerms, and soft preferences through preferredDuringSchedulingIgnoredDuringExecution.
```

### 22.4 Interview answer: affinity vs taints

Good answer:

```text
Affinity is pod-driven attraction or avoidance. Taints are node-driven repulsion. A pod can select a tainted node with affinity, but it still needs a matching toleration to be scheduled there.
```

## 23. Hands-On Lab

### Objective

Configure node affinity and pod anti-affinity in OpenShift.

### Lab topology

Assume three worker nodes:

```text
worker01
worker02
worker03
```

### Step 1: Create namespace

```bash
oc new-project affinity-lab
```

### Step 2: Label nodes

```bash
oc label node worker01 nodepool=app topology.kubernetes.io/zone=zone-a --overwrite
oc label node worker02 nodepool=app topology.kubernetes.io/zone=zone-b --overwrite
oc label node worker03 nodepool=infra topology.kubernetes.io/zone=zone-a --overwrite
```

Verify:

```bash
oc get nodes -L nodepool,topology.kubernetes.io/zone
```

### Step 3: Create deployment with node affinity

Create `app-node-affinity.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-node-affinity
  namespace: affinity-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: app-node-affinity
  template:
    metadata:
      labels:
        app: app-node-affinity
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: nodepool
                operator: In
                values:
                - app
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

Apply:

```bash
oc apply -f app-node-affinity.yaml
```

Verify:

```bash
oc get pods -n affinity-lab -o wide
```

Expected:

```text
Pods should run only on worker01 and worker02, not worker03.
```

### Step 4: Add pod anti-affinity

Create `app-anti-affinity.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-anti-affinity
  namespace: affinity-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: app-anti-affinity
  template:
    metadata:
      labels:
        app: app-anti-affinity
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: nodepool
                operator: In
                values:
                - app
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: app-anti-affinity
            topologyKey: kubernetes.io/hostname
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/ubi-minimal
        command: ["sleep", "3600"]
```

Apply:

```bash
oc apply -f app-anti-affinity.yaml
```

Verify:

```bash
oc get pods -n affinity-lab -o wide
```

Expected:

```text
One pod should run on worker01 and one on worker02.
```

### Step 5: Scale beyond eligible nodes

```bash
oc scale deployment app-anti-affinity -n affinity-lab --replicas=3
```

Check:

```bash
oc get pods -n affinity-lab -o wide
oc describe pod <pending-pod> -n affinity-lab
```

Expected:

```text
Third pod may remain Pending because required anti-affinity allows only one matching pod per eligible node, and only two app nodes exist.
```

### Step 6: Convert required anti-affinity to preferred

Edit:

```bash
oc edit deployment app-anti-affinity -n affinity-lab
```

Change from:

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
```

to:

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app: app-anti-affinity
      topologyKey: kubernetes.io/hostname
```

Verify rollout:

```bash
oc rollout status deployment/app-anti-affinity -n affinity-lab
oc get pods -n affinity-lab -o wide
```

Expected:

```text
All pods should be able to run, but scheduler will still prefer spreading them.
```

## 26. Summary

Affinity is one of the most important workload placement tools in OpenShift.

Remember these points:

```text
Node affinity selects nodes based on node labels.
Pod affinity places pods near matching pods.
Pod anti-affinity keeps pods away from matching pods.
Required rules are hard constraints.
Preferred rules are soft preferences.
IgnoredDuringExecution means existing pods are not automatically evicted if labels change.
nodeSelector and nodeAffinity both must match if both are configured.
Affinity does not bypass taints; tolerations are still required.
Hard anti-affinity can cause Pending pods if replicas exceed eligible topology domains.
Topology spread constraints are often better for even distribution.
Good label strategy is the foundation of good scheduling design.
```

For a 10+ year OpenShift administrator, affinity should not be treated as a YAML feature only. It is a platform design tool used for high availability, performance isolation, compliance, infrastructure workload placement, node pool strategy, and operational resilience.
