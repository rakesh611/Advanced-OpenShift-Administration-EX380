# Scheduling Troubleshooting in OpenShift

**Area:** Pod Scheduling and Workload Placement  
**Level:** Advanced OpenShift Administration / 10+ years experience  
**Target platform:** Red Hat OpenShift Container Platform 4.x, with examples aligned to current 4.20 behavior  
**Primary goal:** Diagnose why a workload did not land on the expected node, why a pod is stuck in `Pending`, why a pod was rejected after scheduling, or why cluster placement policy is producing unhealthy workload distribution.

---

## 1. What “Scheduling Troubleshooting” Means

In OpenShift, scheduling troubleshooting is the process of identifying why the control plane cannot place a pod on a suitable node, or why the placement result is different from the intended design.

A pod can fail before, during, or after scheduling:

| Stage | Typical symptom | Main component involved | Example |
|---|---|---|---|
| API admission | Pod is rejected immediately | API server admission, quota, SCC, namespace node selector | `Forbidden`, quota exceeded, project node selector conflict |
| Scheduler filtering | Pod remains `Pending` | `default-scheduler` | `0/6 nodes are available: Insufficient memory` |
| Scheduler scoring/binding | Pod gets assigned to a node | Scheduler | Pod has `.spec.nodeName` set |
| Kubelet admission | Pod assigned but cannot start | Kubelet, CRI-O, Topology Manager, device plugin, CSI | `UnexpectedAdmissionError`, `Topology Affinity Error` |
| Runtime/startup | Pod scheduled but containers fail | Kubelet, image registry, app process | `ImagePullBackOff`, `CrashLoopBackOff` |

A senior OpenShift administrator must not treat every non-running pod as a scheduler problem. A pod stuck in `Pending` with `FailedScheduling` is usually a scheduling issue. A pod in `ImagePullBackOff`, `CrashLoopBackOff`, or `CreateContainerConfigError` is usually already scheduled, so the investigation must shift to image, secret, config, SCC, storage mount, or application startup.

## 2. OpenShift Scheduler Mental Model

When a new pod is created, the OpenShift/Kubernetes scheduler evaluates whether the pod can run on any node. The simplified flow is:

```text
Pod created
  ↓
API admission checks
  ↓
Scheduler queue
  ↓
Filter phase: remove nodes that cannot run the pod
  ↓
Score phase: rank feasible nodes
  ↓
Optional preemption evaluation
  ↓
Bind pod to selected node
  ↓
Kubelet on that node admits and starts the pod
```

The scheduler does **not** look at actual live CPU/memory usage first. It schedules mainly from declared **resource requests** and node **allocatable** capacity. This is why a node may show low real CPU usage in Prometheus, but a new pod still fails with `Insufficient cpu`: the node’s requested CPU is already committed.

Key scheduling inputs:

- Pod resource requests: `resources.requests.cpu`, `resources.requests.memory`, `ephemeral-storage`
- Node capacity and allocatable resources
- Existing pod requests already assigned to each node
- Node readiness and schedulability
- Taints and pod tolerations
- `nodeSelector`
- Required and preferred node affinity
- Required and preferred pod affinity / anti-affinity
- Topology spread constraints
- PVC binding and storage topology
- Pod priority and preemption
- Project/namespace node selector in OpenShift
- Cluster-wide default node selector in OpenShift
- Workload-specific operators that inject scheduling rules
- Kubelet admission constraints such as device availability, CPU Manager, Topology Manager, and NUMA alignment

## 3. First 5-Minute Triage Method

Use this sequence before changing YAML. It prevents random fixes.

### 3.1 Identify the affected pod and controller

```bash
NS=<namespace>
POD=<pod-name>

oc get pod -n $NS $POD -o wide
oc describe pod -n $NS $POD
oc get pod -n $NS $POD -o yaml
```

Check:

- `STATUS`
- `NODE`
- `Events`
- `.spec.nodeName`
- `.spec.schedulerName`
- `.spec.nodeSelector`
- `.spec.affinity`
- `.spec.tolerations`
- `.spec.topologySpreadConstraints`
- `.spec.containers[].resources.requests`
- PVCs used by the pod

Find the controller:

```bash
oc get pod -n $NS $POD -o jsonpath='{.metadata.ownerReferences}' | jq
```

Or:

```bash
oc describe pod -n $NS $POD | sed -n '/Controlled By:/p'
```

If the pod belongs to a `Deployment`, `StatefulSet`, `DaemonSet`, `Job`, or Operator-managed CR, fix the pod template or custom resource, not the temporary pod object.

### 3.2 Look at scheduler events

```bash
oc get events -n $NS --sort-by=.lastTimestamp | tail -40
oc describe pod -n $NS $POD | sed -n '/Events:/,$p'
```

Common event reasons:

```text
FailedScheduling
NotTriggerScaleUp
FailedMount
FailedAttachVolume
UnexpectedAdmissionError
TopologyAffinityError
```

The most important line is usually like:

```text
0/6 nodes are available: 2 Insufficient memory, 2 node(s) had untolerated taint, 2 node(s) didn't match Pod's node affinity/selector.
```

Read this as a count of rejection reasons. Every node failed at least one scheduler filter.

### 3.3 Check node inventory

```bash
oc get nodes -o wide
oc get nodes --show-labels
oc describe nodes
```

Useful compact views:

```bash
oc get nodes -o custom-columns='NAME:.metadata.name,STATUS:.status.conditions[-1].type,ROLES:.metadata.labels.node-role\.kubernetes\.io/worker,UNSCHED:.spec.unschedulable,TAINTS:.spec.taints'

oc get node -L topology.kubernetes.io/zone,topology.kubernetes.io/region,kubernetes.io/hostname,node-role.kubernetes.io/worker,node-role.kubernetes.io/infra
```

### 3.4 Check namespace-level OpenShift selectors and quotas

```bash
oc get namespace $NS -o yaml | egrep -A5 'annotations:|openshift.io/node-selector'
oc describe quota -n $NS
oc describe limitrange -n $NS
oc get appliedclusterresourcequota -n $NS
```

### 3.5 Check scheduler health

```bash
oc get co kube-scheduler
oc get pods -n openshift-kube-scheduler -o wide
oc logs -n openshift-kube-scheduler -l app=openshift-kube-scheduler -c kube-scheduler --tail=100
```

Only suspect the scheduler component itself after confirming many unrelated pods are not being scheduled and events are absent or stale.

## 4. Decision Tree for Pod Pending

```text
Pod Pending?
  |
  +-- Is there a FailedScheduling event?
  |      |
  |      +-- Yes → Decode event message
  |      |       |
  |      |       +-- Insufficient cpu/memory/ephemeral-storage/pods → Resource/capacity issue
  |      |       +-- untolerated taint → Taint/toleration issue
  |      |       +-- node affinity/selector mismatch → Label/selector/affinity issue
  |      |       +-- pod affinity/anti-affinity mismatch → Inter-pod placement rule issue
  |      |       +-- topology spread mismatch → Zone/hostname spread issue
  |      |       +-- unbound PVC / volume node affinity conflict → Storage scheduling issue
  |      |       +-- preemption not helpful → Priority/capacity/design issue
  |      |
  |      +-- No → Check events, scheduler health, admission rejection, controller status
  |
  +-- Does pod already have NODE assigned?
         |
         +-- No → Scheduler has not bound it
         +-- Yes → It is post-scheduling; check kubelet, volume, image, SCC, runtime
```

## 5. Troubleshooting Pattern: `Insufficient cpu` or `Insufficient memory`

### Symptom

```text
Warning  FailedScheduling  default-scheduler  0/5 nodes are available: 5 Insufficient memory.
```

or:

```text
0/4 nodes are available: 4 Insufficient cpu.
```

### What it means

The scheduler could not find a node where:

```text
node allocatable - sum(existing pod requests) >= new pod requests
```

It does not mean the node is currently using all CPU or memory. It means the requested/committed capacity does not fit.

### Commands

```bash
# Pod requests
oc get pod -n $NS $POD -o jsonpath='{range .spec.containers[*]}{.name}{" cpu="}{.resources.requests.cpu}{" mem="}{.resources.requests.memory}{"\n"}{end}'

# Node allocatable and requested resources
oc describe node <node-name> | sed -n '/Allocatable:/,/System Info:/p'
oc describe node <node-name> | sed -n '/Allocated resources:/,/Events:/p'

# Metrics, if metrics are available
oc adm top nodes
oc adm top pods -A --sort-by=memory
oc adm top pods -A --sort-by=cpu
```

### Senior admin checks

1. Did the pod request too much CPU/memory?
2. Did a `LimitRange` inject default requests unexpectedly?
3. Did many small pods fragment resources across nodes?
4. Is the workload pinned to too few nodes by selector/affinity?
5. Is cluster autoscaler expected to add nodes but not doing so?
6. Are infra/control-plane nodes tainted and therefore unavailable?
7. Is the node allocatable lower than capacity due to system/kube reservations?

### Fix options

#### Option A: Right-size the request

```bash
oc set resources deployment/<deploy> -n $NS \
  --requests=cpu=100m,memory=256Mi \
  --limits=cpu=500m,memory=512Mi
```

#### Option B: Add capacity

Scale worker machines or add nodes through your platform method. On IPI/cloud clusters, inspect compute machine sets:

```bash
oc get machinesets -n openshift-machine-api
oc scale machineset/<machineset-name> -n openshift-machine-api --replicas=<count>
```

#### Option C: Relax placement rules

If the pod has both high resource requests and strict node affinity, capacity may exist in the cluster but not in the allowed node pool.

```bash
oc get deploy <deploy> -n $NS -o yaml | yq '.spec.template.spec.nodeSelector'
oc get deploy <deploy> -n $NS -o yaml | yq '.spec.template.spec.affinity'
```

## 6. Troubleshooting Pattern: Node Is Cordoned or Unschedulable

### Symptom

```text
0/3 nodes are available: 1 node(s) were unschedulable.
```

or node status:

```text
Ready,SchedulingDisabled
```

### Commands

```bash
oc get nodes
oc describe node <node-name> | egrep -i 'Unschedulable|Taints|Conditions'
```

### Fix

If maintenance is finished:

```bash
oc adm uncordon <node-name>
```

To cordon safely before maintenance:

```bash
oc adm cordon <node-name>
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data
```

### Important distinction

`cordon` stops **new** pods from being scheduled to the node. It does not evict existing pods. `drain` evicts eligible pods so they can be recreated elsewhere.

## 7. Troubleshooting Pattern: Untolerated Taints

### Symptom

```text
0/6 nodes are available: 3 node(s) had untolerated taint {node-role.kubernetes.io/infra: }, 3 node(s) had untolerated taint {dedicated: app1}.
```

or:

```text
node(s) had taint {node.kubernetes.io/not-ready: }, that the pod didn't tolerate
```

### Concepts

Taints are applied to nodes. Tolerations are applied to pods. A node with a `NoSchedule` taint rejects pods that do not tolerate that taint.

Effects:

| Effect | Meaning |
|---|---|
| `NoSchedule` | Do not schedule new pods unless tolerated |
| `PreferNoSchedule` | Try not to schedule unless tolerated, but not strict |
| `NoExecute` | Evict existing pods unless tolerated; also prevents scheduling |

### Commands

```bash
oc describe node <node-name> | grep -i Taints -A3
oc get node <node-name> -o jsonpath='{.spec.taints}' | jq
oc get pod -n $NS $POD -o yaml | yq '.spec.tolerations'
```

### Fix option A: Add toleration to workload

Example for a dedicated node pool:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app1
spec:
  template:
    spec:
      tolerations:
      - key: dedicated
        operator: Equal
        value: app1
        effect: NoSchedule
```

Patch example:

```bash
oc patch deployment app1 -n $NS --type='json' -p='[
  {"op":"add","path":"/spec/template/spec/tolerations","value":[
    {"key":"dedicated","operator":"Equal","value":"app1","effect":"NoSchedule"}
  ]}
]'
```

### Fix option B: Remove wrong taint from node

```bash
oc adm taint node <node-name> dedicated=app1:NoSchedule-
```

### Senior admin warning

Do not blindly add tolerations for control-plane, infra, storage, or GPU nodes. A toleration only allows scheduling; it does not force the pod to the correct node. For dedicated placement, combine toleration with `nodeSelector` or node affinity.

## 8. Troubleshooting Pattern: Node Selector Mismatch

### Symptom

```text
0/4 nodes are available: 4 node(s) didn't match Pod's node affinity/selector.
```

### Commands

```bash
oc get pod -n $NS $POD -o yaml | yq '.spec.nodeSelector'
oc get nodes --show-labels
oc get nodes -l '<key>=<value>'
```

Example:

```bash
oc get nodes -l disktype=ssd
```

If no nodes are returned, the selector is impossible.

### Fix options

#### Fix the pod template selector

```bash
oc patch deployment <deploy> -n $NS --type='merge' -p '{
  "spec": {
    "template": {
      "spec": {
        "nodeSelector": {
          "workload": "app"
        }
      }
    }
  }
}'
```

#### Add the required label to appropriate nodes

```bash
oc label node <node-name> workload=app
```

For Machine API managed clusters, prefer labeling the compute machine set template so replacement nodes receive the label:

```bash
oc patch machineset <machineset-name> -n openshift-machine-api --type='merge' -p '{
  "spec": {
    "template": {
      "spec": {
        "metadata": {
          "labels": {
            "workload": "app"
          }
        }
      }
    }
  }
}'
```

### Senior admin warning

Labels applied directly to nodes can disappear when nodes are replaced. For long-term node pools, apply labels at the machine set or provisioning layer when possible.

## 9. OpenShift-Specific Issue: Project-Level Node Selector Conflict

OpenShift can enforce node selectors at namespace/project level using the namespace annotation:

```yaml
metadata:
  annotations:
    openshift.io/node-selector: "type=user-node,region=east"
```

A project node selector can silently affect every pod in that namespace because OpenShift adds the selector to pods created in the project.

### Symptom 1: Pod rejected at creation

```text
Error from server (Forbidden): pods "pod-4" is forbidden: pod node label selector conflicts with its project node label selector
```

### Symptom 2: Pod Pending because no nodes match combined selectors

```text
0/5 nodes are available: 5 node(s) didn't match Pod's node affinity/selector.
```

### Commands

```bash
oc get namespace $NS -o jsonpath='{.metadata.annotations.openshift\.io/node-selector}{"\n"}'
oc get scheduler cluster -o yaml | yq '.spec.defaultNodeSelector'
oc get pod -n $NS $POD -o yaml | yq '.spec.nodeSelector'
oc get nodes --show-labels
```

### Fix options

#### Update namespace selector

```bash
oc annotate namespace $NS openshift.io/node-selector='workload=app' --overwrite
```

#### Clear namespace selector for special namespaces

```bash
oc annotate namespace $NS openshift.io/node-selector='' --overwrite
```

#### Update cluster default node selector

```bash
oc edit scheduler cluster
```

Example:

```yaml
apiVersion: config.openshift.io/v1
kind: Scheduler
metadata:
  name: cluster
spec:
  defaultNodeSelector: type=user-node,region=east
  mastersSchedulable: false
```

### Senior admin warning

Changing the cluster-wide default node selector is a platform-level decision. It can affect workloads in many namespaces and may require API server rollout before it fully takes effect.

## 10. Troubleshooting Pattern: Required Node Affinity Mismatch

### Symptom

```text
0/6 nodes are available: 6 node(s) didn't match Pod's node affinity/selector.
```

### Important structure

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: workload
          operator: In
          values:
          - app
```

`requiredDuringSchedulingIgnoredDuringExecution` is a hard rule. If no node satisfies it, the pod stays Pending.

### Commands

```bash
oc get pod -n $NS $POD -o yaml | yq '.spec.affinity.nodeAffinity'
oc get nodes -L workload,region,zone,disktype
```

Test a selector manually:

```bash
oc get nodes -l workload=app
oc get nodes -l 'region in (east,west)'
```

### Fix options

- Correct the node labels.
- Correct the affinity key/value.
- Use `preferredDuringSchedulingIgnoredDuringExecution` for soft placement.
- Remove conflicting `nodeSelector` if affinity already controls placement.

Preferred example:

```yaml
nodeAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 80
    preference:
      matchExpressions:
      - key: workload
        operator: In
        values:
        - app
```

## 11. Troubleshooting Pattern: Pod Affinity or Anti-Affinity Blocks Scheduling

### Symptom

```text
0/3 nodes are available: 3 node(s) didn't match pod affinity rules.
```

or:

```text
0/3 nodes are available: 3 node(s) didn't satisfy existing pods anti-affinity rules.
```

### Concept

Pod affinity/anti-affinity uses labels on **other pods**, not labels on nodes only. It also uses a topology key such as:

```text
kubernetes.io/hostname
topology.kubernetes.io/zone
topology.kubernetes.io/region
```

Required pod anti-affinity is common for high availability, but it can block scheduling if there are not enough nodes or zones.

### Commands

```bash
oc get pod -n $NS $POD -o yaml | yq '.spec.affinity.podAffinity'
oc get pod -n $NS $POD -o yaml | yq '.spec.affinity.podAntiAffinity'
oc get pods -n $NS --show-labels -o wide
oc get nodes -L kubernetes.io/hostname,topology.kubernetes.io/zone
```

### Example failure

A deployment has 3 replicas and required anti-affinity by hostname, but the namespace has only 2 eligible worker nodes.

```yaml
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchLabels:
        app: payments
    topologyKey: kubernetes.io/hostname
```

The third pod will remain Pending.

### Fix options

- Add eligible nodes.
- Relax required anti-affinity to preferred anti-affinity.
- Reduce replicas.
- Use zone-level spreading if hostname-level spreading is too strict.
- Confirm pod labels actually match the selector.

Preferred anti-affinity example:

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app: payments
      topologyKey: kubernetes.io/hostname
```

## 12. Troubleshooting Pattern: Topology Spread Constraint Failure

### Symptom

```text
0/6 nodes are available: 6 node(s) didn't match pod topology spread constraints.
```

### Concept

Topology spread constraints distribute matching pods across topology domains such as zones or hostnames.

Example:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: frontend
```

If `whenUnsatisfiable: DoNotSchedule`, the rule is hard. If the scheduler cannot keep skew within `maxSkew`, the pod remains Pending.

### Commands

```bash
oc get pod -n $NS $POD -o yaml | yq '.spec.topologySpreadConstraints'
oc get nodes -L topology.kubernetes.io/zone,kubernetes.io/hostname
oc get pods -n $NS -l app=frontend -o wide
```

Count existing pods by zone:

```bash
for n in $(oc get nodes -o name | cut -d/ -f2); do
  zone=$(oc get node $n -o jsonpath='{.metadata.labels.topology\.kubernetes\.io/zone}')
  echo "$n $zone"
done
```

### Common root causes

1. Nodes do not have consistent topology labels.
2. Some zones have no eligible nodes after taints/selectors/affinity are applied.
3. `maxSkew` is too strict for the number of replicas and zones.
4. Multiple topology spread constraints conflict with each other.
5. Selector matches pods unexpectedly because labels are too broad.
6. Mixed deployments in the same namespace use different spread rules for the same app.

### Fix options

- Ensure all nodes in the intended topology domain have consistent labels.
- Use well-known labels like `topology.kubernetes.io/zone` and `kubernetes.io/hostname` where available.
- Change `whenUnsatisfiable` from `DoNotSchedule` to `ScheduleAnyway` if strict spreading is not required.
- Increase eligible node count per topology domain.
- Tune `maxSkew`.
- Make the `labelSelector` precise.

Soft spread example:

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: ScheduleAnyway
  labelSelector:
    matchLabels:
      app: frontend
```

## 13. Troubleshooting Pattern: PVC or Storage Binding Blocks Scheduling

### Symptoms

```text
pod has unbound immediate PersistentVolumeClaims
```

```text
0/3 nodes are available: 3 node(s) had volume node affinity conflict.
```

```text
running PreBind plugin "VolumeBinding": binding volumes: timed out waiting for the condition
```

### Why storage affects scheduling

A pod that uses a PVC might be restricted to nodes that can access the selected volume. With local PVs, zonal disks, topology-aware CSI drivers, or `WaitForFirstConsumer` storage classes, the scheduler and storage binding logic interact.

### Commands

```bash
oc get pvc -n $NS
oc describe pvc -n $NS <pvc-name>
oc get pv
oc describe pv <pv-name>
oc get storageclass
oc describe storageclass <storageclass-name>
oc get pod -n $NS $POD -o yaml | yq '.spec.volumes'
```

Check volume binding mode:

```bash
oc get storageclass <sc-name> -o jsonpath='{.volumeBindingMode}{"\n"}'
```

### Root causes

| Event | Meaning | Typical fix |
|---|---|---|
| `unbound immediate PersistentVolumeClaims` | PVC is not bound and storage class expects immediate binding | Fix StorageClass/provisioner/PV/PVC size/access mode |
| `volume node affinity conflict` | PV is bound to a topology that does not match eligible nodes | Align pod placement with PV topology or recreate storage correctly |
| PVC `Pending` | No matching PV or dynamic provisioner issue | Check storage class, provisioner, quota, access mode |
| Pod stuck after node assignment with mount error | Scheduling succeeded; mount failed | Check CSI driver, node plugin, volume attachment, permissions |

### Storage-specific checks

```bash
# CSI pods/operators
oc get pods -n openshift-cluster-csi-drivers
oc get co | grep -i storage

# VolumeAttachment objects
oc get volumeattachment

# Events around PVC
oc get events -n $NS --sort-by=.lastTimestamp | egrep -i 'pvc|volume|attach|mount|provision'
```

### Senior admin warning

Do not solve a storage topology problem by randomly removing node affinity or tolerations. A database pod may schedule on a node that cannot access its volume, causing a worse outage.

## 14. Troubleshooting Pattern: ResourceQuota or LimitRange Causes Scheduling-Like Failure

### Symptom: Pod rejected before scheduling

```text
Error from server (Forbidden): pods "app" is forbidden: exceeded quota
```

or:

```text
minimum memory usage per Container is 5Mi, but request is 1Mi
```

### Symptom: Pod created with unexpected requests

A `LimitRange` may inject default CPU/memory requests into containers. This can make the pod larger than expected from a scheduling perspective.

### Commands

```bash
oc describe quota -n $NS
oc describe limitrange -n $NS
oc get resourcequota -n $NS -o yaml
oc get limitrange -n $NS -o yaml
oc get pod -n $NS $POD -o yaml | yq '.spec.containers[].resources'
```

### Root causes

- Namespace quota is exhausted.
- LimitRange default request makes each pod consume more scheduled capacity than expected.
- LimitRange min/max rejects the pod.
- ClusterResourceQuota applies across multiple namespaces.
- Object quota blocks additional pods, secrets, PVCs, services, or config maps.

### Fix options

#### Adjust workload requests

```bash
oc set resources deployment/<deploy> -n $NS --requests=cpu=50m,memory=128Mi
```

#### Adjust quota if policy allows

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: app-quota
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    pods: "20"
```

#### Adjust LimitRange defaults carefully

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
spec:
  limits:
  - type: Container
    defaultRequest:
      cpu: 100m
      memory: 128Mi
    default:
      cpu: 500m
      memory: 512Mi
```

## 15. Troubleshooting Pattern: Too Many Pods on Node

### Symptom

```text
0/3 nodes are available: 3 Too many pods.
```

### Meaning

Each node has a maximum number of pods it can run. Even if CPU/memory are available, the scheduler will not place more pods on a node after the pod count limit is reached.

### Commands

```bash
oc describe node <node-name> | egrep -i 'pods:|Non-terminated Pods'
oc get pods -A --field-selector spec.nodeName=<node-name> --no-headers | wc -l
```

### Fix options

- Add nodes.
- Reduce small-pod fragmentation.
- Consolidate sidecars or daemonsets where appropriate.
- Review node sizing and supported maximums before tuning node-level pod limits.

## 16. Troubleshooting Pattern: Preemption Is Not Helping

### Symptom

```text
preemption: 0/5 nodes are available: 5 No preemption victims found for incoming pod
```

or:

```text
preemption: 0/5 nodes are available: 5 Preemption is not helpful for scheduling
```

### Meaning

The scheduler considered evicting lower-priority pods but still could not make the incoming pod fit, or no suitable lower-priority victims existed.

### Commands

```bash
oc get pod -n $NS $POD -o jsonpath='{.spec.priorityClassName}{" priority="}{.spec.priority}{"\n"}'
oc get priorityclass
oc get pods -A -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,PRIORITY:.spec.priority,PC:.spec.priorityClassName,NODE:.spec.nodeName' | sort -k3 -n
```

### Root causes

- All pods have equal or higher priority.
- Node selector/affinity/taints still prevent placement after possible preemption.
- PVC topology or topology spread still prevents placement.
- Pod request is larger than any node’s allocatable capacity.
- Preemption would violate PodDisruptionBudgets.

### Fix options

- Right-size the pod.
- Add appropriate node capacity.
- Review priority class design.
- Remove impossible placement constraints.
- Do not use priority as a substitute for capacity planning.

## 17. Troubleshooting Pattern: DaemonSet Pod Not Scheduled on Some Nodes

### Symptom

A DaemonSet is expected to run on every worker node, but some nodes do not have a pod.

### Commands

```bash
oc get daemonset -n $NS <ds-name> -o wide
oc describe daemonset -n $NS <ds-name>
oc get pods -n $NS -o wide -l <daemonset-label>
oc get nodes --show-labels
oc describe node <node-name> | grep -i Taints -A3
```

### Root causes

- DaemonSet has `nodeSelector` or affinity that excludes nodes.
- Nodes have taints not tolerated by the DaemonSet.
- Node is cordoned or NotReady.
- The DaemonSet update strategy is blocked.
- Security/admission failure prevents pod creation.
- Cluster-wide or namespace node selector excludes nodes.

### Fix options

- Add required tolerations.
- Fix DaemonSet node selector.
- Label intended nodes.
- Check operator-managed DaemonSet configuration instead of editing generated YAML directly.

## 18. Troubleshooting Pattern: Operator Workload Scheduling Problems

Many OpenShift components and Operators manage their own deployments. Examples include monitoring, logging, ingress, image registry, storage operators, and third-party Operators.

### Symptoms

- Operator pod Pending.
- Operand pod Pending.
- ClusterOperator degraded because a deployment is unavailable.
- Manual edits are reverted.

### Commands

```bash
oc get co
oc describe co <cluster-operator-name>
oc get pods -n <operator-namespace> -o wide
oc describe pod -n <operator-namespace> <pod>
oc get events -n <operator-namespace> --sort-by=.lastTimestamp | tail -50
```

### Senior admin method

1. Identify whether the pod is managed by Deployment, DaemonSet, StatefulSet, or Operator CR.
2. Inspect the operator CR for placement configuration.
3. Avoid editing generated deployments unless Red Hat documentation says it is supported.
4. Confirm namespace node selector does not block operator pods.
5. Confirm infra-node taints are tolerated if moving platform components to infra nodes.

Example namespaces to check:

```bash
openshift-ingress
openshift-monitoring
openshift-image-registry
openshift-logging
openshift-storage
openshift-cluster-csi-drivers
```

## 19. Troubleshooting Pattern: Pod Has `nodeName` Manually Set

### Symptom

Pod bypasses scheduler behavior or appears on a node even though selectors/taints do not match.

### Command

```bash
oc get pod -n $NS $POD -o jsonpath='{.spec.nodeName}{"\n"}'
```

### Meaning

If `.spec.nodeName` is set directly, the scheduler is bypassed. The kubelet may still reject or evict the pod depending on `NoExecute` taints or local admission checks.

### Fix

Remove manual `nodeName` and use proper placement controls:

- `nodeSelector`
- node affinity
- taints and tolerations
- topology spread constraints

For controllers, edit the pod template, not the generated pod.

## 20. Troubleshooting Pattern: Pod Scheduled but Kubelet Rejects It

### Symptom

Pod has a node assigned but does not start. Events may show:

```text
UnexpectedAdmissionError
Topology Affinity Error
failed to allocate device
```

### Meaning

The scheduler selected a node, but kubelet admission failed. This often happens with specialized resources:

- HugePages
- GPUs or device plugins
- SR-IOV
- CPU Manager static policy
- Topology Manager single-NUMA-node policy
- NUMA-sensitive workloads
- Local device availability

### Commands

```bash
oc get pod -n $NS $POD -o wide
oc describe pod -n $NS $POD
oc describe node <assigned-node>
oc debug node/<assigned-node>
```

Check node logs through supported methods, for example:

```bash
oc adm node-logs <node-name> -u kubelet --tail=200
oc adm node-logs <node-name> -u crio --tail=200
```

### Fix options

- Ensure extended resources are advertised on the node.
- Ensure requests equal limits for Guaranteed workloads when required.
- Align pod CPU/device requests with NUMA topology.
- Use NUMA-aware scheduling for latency-sensitive workloads where applicable.
- Check device plugin/operator health.

## 21. Troubleshooting Pattern: Node NotReady or Pressure Conditions

### Symptoms

```text
node(s) had condition {Ready:False}
node(s) had taint {node.kubernetes.io/memory-pressure: }
node(s) had taint {node.kubernetes.io/disk-pressure: }
node(s) had taint {node.kubernetes.io/not-ready: }
```

### Commands

```bash
oc get nodes
oc describe node <node-name> | sed -n '/Conditions:/,/Addresses:/p'
oc describe node <node-name> | sed -n '/Taints:/,/Unschedulable:/p'
oc adm top node <node-name>
oc adm node-logs <node-name> -u kubelet --tail=200
```

### Common pressure taints

| Taint | Typical cause |
|---|---|
| `node.kubernetes.io/memory-pressure` | Node memory pressure; kubelet eviction thresholds |
| `node.kubernetes.io/disk-pressure` | Root disk/image filesystem pressure |
| `node.kubernetes.io/pid-pressure` | Too many processes |
| `node.kubernetes.io/not-ready` | Node unhealthy |
| `node.kubernetes.io/unreachable` | Control plane cannot reach node |

### Fix options

- Resolve node health issue, not just pod YAML.
- Free disk space or expand disk.
- Fix kubelet/CRI-O/network issue.
- Drain and reboot if needed.
- Investigate MachineConfigPool state.
- Replace bad node if cloud/IPI managed.

## 22. Troubleshooting Remote Worker / Edge Node Scheduling

Remote or edge worker nodes can become unreachable because of latency or network partitions. OpenShift marks node readiness as `Unknown` or `False` and applies taints such as:

```text
node.kubernetes.io/unreachable:NoExecute
node.kubernetes.io/not-ready:NoExecute
```

Default pod tolerations usually allow pods to remain bound for approximately 300 seconds for these taints. DaemonSet pods commonly tolerate these taints indefinitely.

### Commands

```bash
oc get nodes
oc describe node <remote-node>
oc get pods -A --field-selector spec.nodeName=<remote-node>
```

### Design fixes

- Use DaemonSets for node-local services that should survive disconnection.
- Use appropriate `NoExecute` tolerations for edge workloads.
- Avoid stateful workloads that cannot safely move between storage zones.
- Use topology labels and anti-affinity to avoid concentrating replicas in one site.
- Consider worker latency profiles for high-latency environments.

## 23. Troubleshooting Scheduling for Infra Nodes

OpenShift clusters often use dedicated infrastructure nodes for routers, registry, monitoring, logging, or storage components.

Typical infra node setup:

```bash
oc label node <node> node-role.kubernetes.io/infra=""
oc adm taint node <node> node-role.kubernetes.io/infra=:NoSchedule
```

### Common mistake

Adding only a toleration:

```yaml
tolerations:
- key: node-role.kubernetes.io/infra
  operator: Exists
  effect: NoSchedule
```

This allows the pod to run on infra nodes but does not require it. Add node selector/affinity too:

```yaml
nodeSelector:
  node-role.kubernetes.io/infra: ""
```

### Troubleshooting commands

```bash
oc get nodes -l node-role.kubernetes.io/infra=
oc describe node <infra-node> | grep -i Taints -A3
oc get pod -n <ns> <pod> -o yaml | yq '.spec.nodeSelector,.spec.tolerations,.spec.affinity'
```

## 24. Troubleshooting Dedicated Node Pools

Dedicated nodes are commonly used for workloads such as databases, PCI workloads, GPU workloads, security-sensitive apps, or noisy workloads.

A robust dedicated pool usually uses both taints and labels:

```bash
oc label node <node> dedicated=payments
oc adm taint node <node> dedicated=payments:NoSchedule
```

Workload template:

```yaml
spec:
  template:
    spec:
      nodeSelector:
        dedicated: payments
      tolerations:
      - key: dedicated
        operator: Equal
        value: payments
        effect: NoSchedule
```

### Common failures

| Failure | Cause |
|---|---|
| Pod Pending due to taint | Toleration missing |
| Pod runs outside dedicated pool | Toleration exists but selector missing |
| Pod Pending due to selector | Node label missing or typo |
| Some replicas Pending | Dedicated pool has insufficient capacity |
| New replacement node not used | Label was added only to old node, not MachineSet |

## 26. Event Message Decoder

| Event text | Likely root cause | First command |
|---|---|---|
| `Insufficient cpu` | CPU requests do not fit eligible nodes | `oc describe node` |
| `Insufficient memory` | Memory requests do not fit eligible nodes | `oc describe node` |
| `Insufficient ephemeral-storage` | Ephemeral storage requests do not fit | `oc describe node` |
| `Too many pods` | Node pod capacity reached | `oc describe node` |
| `node(s) were unschedulable` | Node cordoned | `oc get nodes` |
| `had untolerated taint` | Missing toleration | `oc describe node` |
| `didn't match Pod's node affinity/selector` | Bad nodeSelector/affinity/project selector | `oc get nodes --show-labels` |
| `didn't match pod affinity rules` | Required pod affinity impossible | `oc get pods --show-labels -o wide` |
| `didn't satisfy existing pods anti-affinity rules` | Required anti-affinity too strict | `oc get pods -o wide` |
| `didn't match pod topology spread constraints` | Spread rule impossible | `oc get nodes -L topology.kubernetes.io/zone` |
| `pod has unbound immediate PersistentVolumeClaims` | PVC not bound | `oc describe pvc` |
| `volume node affinity conflict` | PV topology conflicts with eligible nodes | `oc describe pv` |
| `No preemption victims found` | Priority cannot solve placement | `oc get priorityclass` |
| `Preemption is not helpful` | Non-resource constraint or pod too large | Decode all filters |
| `UnexpectedAdmissionError` | Kubelet admission after scheduling | `oc adm node-logs <node> -u kubelet` |

## 27. Practical Lab: Diagnose a Pending Pod

### Broken workload

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: payments
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment-api
  template:
    metadata:
      labels:
        app: payment-api
    spec:
      nodeSelector:
        dedicated: payments
      containers:
      - name: app
        image: registry.access.redhat.com/ubi9/httpd-24
        resources:
          requests:
            cpu: "2"
            memory: 4Gi
```

### Event

```text
0/6 nodes are available: 2 Insufficient memory, 2 node(s) had untolerated taint {dedicated: payments}, 2 node(s) didn't match Pod's node affinity/selector.
```

### Investigation

```bash
oc get nodes -l dedicated=payments
oc describe node <payments-node> | grep -i Taints -A3
oc describe node <payments-node> | sed -n '/Allocated resources:/,/Events:/p'
oc get deploy payment-api -n payments -o yaml | yq '.spec.template.spec'
```

### Diagnosis

The workload is restricted to `dedicated=payments` nodes, but:

1. Some nodes do not have the label.
2. Payments nodes have `dedicated=payments:NoSchedule` taint.
3. The pod has no toleration.
4. The resource request might be too large for remaining memory.

### Corrected workload fragment

```yaml
spec:
  template:
    spec:
      nodeSelector:
        dedicated: payments
      tolerations:
      - key: dedicated
        operator: Equal
        value: payments
        effect: NoSchedule
      containers:
      - name: app
        resources:
          requests:
            cpu: 500m
            memory: 512Mi
          limits:
            cpu: "1"
            memory: 1Gi
```

## 28. Advanced Production Runbook

Use this when troubleshooting a real incident.

### Step 1: Capture current state

```bash
mkdir -p /tmp/scheduling-debug
oc get pod -n $NS $POD -o yaml > /tmp/scheduling-debug/pod.yaml
oc describe pod -n $NS $POD > /tmp/scheduling-debug/pod-describe.txt
oc get events -n $NS --sort-by=.lastTimestamp > /tmp/scheduling-debug/events.txt
oc get nodes -o wide > /tmp/scheduling-debug/nodes.txt
oc get nodes --show-labels > /tmp/scheduling-debug/node-labels.txt
oc describe nodes > /tmp/scheduling-debug/nodes-describe.txt
oc describe quota -n $NS > /tmp/scheduling-debug/quota.txt
oc describe limitrange -n $NS > /tmp/scheduling-debug/limitrange.txt
```

### Step 2: Decode constraints

```bash
yq '.spec.nodeSelector' /tmp/scheduling-debug/pod.yaml
yq '.spec.affinity' /tmp/scheduling-debug/pod.yaml
yq '.spec.tolerations' /tmp/scheduling-debug/pod.yaml
yq '.spec.topologySpreadConstraints' /tmp/scheduling-debug/pod.yaml
yq '.spec.containers[].resources' /tmp/scheduling-debug/pod.yaml
```

### Step 3: Build eligible node set manually

Start with all Ready and schedulable nodes:

```bash
oc get nodes --no-headers | awk '$2 ~ /Ready/ && $2 !~ /SchedulingDisabled/ {print $1}'
```

Then remove nodes that fail:

1. Node selector
2. Required node affinity
3. Untolerated taints
4. Resource fit
5. PVC topology
6. Pod affinity/anti-affinity
7. Topology spread constraints

### Step 4: Apply the least risky fix

Preferred order:

1. Fix obvious label typo.
2. Add missing toleration only for intended dedicated nodes.
3. Right-size unrealistic requests.
4. Add capacity.
5. Relax hard affinity/spread rule if business allows.
6. Change namespace/cluster default selector only after impact analysis.

### Step 5: Validate rollout

```bash
oc rollout status deployment/<deploy> -n $NS
oc get pods -n $NS -o wide
oc describe pod -n $NS <new-pod> | sed -n '/Events:/,$p'
```

## 30. Best Practices to Prevent Scheduling Incidents

1. **Use labels consistently.** Standardize labels such as `workload`, `environment`, `topology.kubernetes.io/zone`, and `node-role.kubernetes.io/infra`.
2. **Do not use node names for long-term placement.** Use labels and affinity instead.
3. **Combine taints with selectors for dedicated nodes.** Toleration alone only permits scheduling.
4. **Prefer soft rules unless hard isolation is required.** Use `preferredDuringSchedulingIgnoredDuringExecution` for preferences.
5. **Right-size requests.** Bad requests cause both failed scheduling and poor capacity planning.
6. **Use namespace quotas and LimitRanges carefully.** Defaults can unexpectedly increase scheduled footprint.
7. **Use anti-affinity and topology spread for HA.** But ensure enough nodes/zones exist.
8. **Label machine set templates, not only nodes.** Replacement nodes must inherit placement labels.
9. **Keep infra and app workloads separate intentionally.** Do not let application workloads drift into infra nodes accidentally.
10. **Monitor Pending pods and FailedScheduling events.** Alert before users report outage.
11. **Review storage topology before moving stateful workloads.** PV accessibility is part of scheduling design.
12. **Document node pool purpose.** Every taint/label should have an owner and reason.

## 32. Common Mistakes by Administrators

### Mistake 1: Looking only at `oc adm top nodes`

Real-time usage does not equal schedulable capacity. Scheduling uses requests and allocatable.

### Mistake 2: Adding tolerations without selectors

This allows a workload onto a tainted node pool but does not force it there.

### Mistake 3: Editing generated pods

Pods from Deployments, StatefulSets, DaemonSets, Jobs, or Operators will be recreated. Fix the owner/template.

### Mistake 4: Ignoring namespace node selectors

OpenShift namespace annotations can alter pod placement even when the deployment YAML looks correct.

### Mistake 5: Using required anti-affinity with insufficient nodes

Required anti-affinity by hostname needs at least as many eligible nodes as replicas.

### Mistake 6: Treating PVC Pending as only a storage issue

PVC binding can be directly tied to scheduling because of storage topology.

### Mistake 7: Labeling only current nodes

Replacement nodes may not inherit manually added node labels.

### Mistake 8: Overusing hard topology spread

`DoNotSchedule` with strict `maxSkew` can block rollouts during zone/node failure.

## 33. Final Troubleshooting Checklist

Before declaring a scheduling issue solved, verify:

- [ ] Pod has no new `FailedScheduling` events.
- [ ] Pod is assigned to the intended node pool.
- [ ] Placement does not violate isolation policy.
- [ ] Requests fit the node pool with headroom.
- [ ] Replicas are spread as intended.
- [ ] PVCs are bound and mounted.
- [ ] Namespace and cluster node selectors are understood.
- [ ] Taints and tolerations are intentional.
- [ ] Labels are applied at MachineSet/provisioning layer if nodes are replaceable.
- [ ] Operator-managed changes are made through supported CRs.
- [ ] Runbook notes are updated for the team.
